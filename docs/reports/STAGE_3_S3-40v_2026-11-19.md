# S3-40v. Прогретый вызов checked-memory с точным ключом кеша

`MemoryPairCache::run` переиспользует ранее проверенный ключ при точном
совпадении профиля, поколения контекста, диапазона и байтов кода, RIP входа
и упорядоченного списка зависимостей. При другом порядке зависимостей,
смене ключа или некорректном входе запрос проходит прежнюю нормализацию
и проверку. Для точного попадания больше не нужны сортировка и
временные коллекции. Кеш сохраняет ёмкость в одну запись.

## Методика

Две подписанные ARM64 Release-сборки на `f108140` отличаются изменением
кеша. Хост Apple M3 Max (Mac15,11) использует macOS 26.7.1 (25G241) и
rustc 1.99.0. Обе сборки используют Hardened Runtime и `allow-jit`.
Каждый процесс до запуска таймеров подтвердил обычный эффективный UID,
`nice -5` и QoS `USER_INTERACTIVE`.

Первая серия была прервана при падении простоя хоста до 18,7–28,9%.
В зачётной серии 12 предварительных проб дали 65,3–89,4% простоя.
Во время замеров 42 пробы дали 38,9–91,1%, с медианой 84,65%.
Порядок отдельных процессов менялся в шести парных раундах.
Весь зачётный ряд сохранён. Разброс нагрузки учитывается при
интерпретации сравнений отдельных процессов.

Драйвер S3-40u повторяет 1 200 входов на поток для двух профилей S3-34a.
Два пилота дали общие числа проходов 251 и 227. В каждом процессе
шесть троек на поток чередуют порядок cold, warm и interpreter.
Cold начинает вызов с пустым кешем, warm использует заранее
опубликованную запись. Для всех 432 зачётных интервалов минимум
составил 55,672 мс при пороге 35 мс. Измерено 123 897 600 вызовов.
Драйвер проверяет CPU, RAM и ожидаемые счётчики кеша. Логический
размер удерживаемой записи составил 4 782 байта в обеих сборках.

## Результат

В таблице приведены медианы отношений candidate/baseline по шести
раундам с минимумом и максимумом. Для нормализации по интерпретатору
отношение соответствующего пути делится на отношение интерпретатора
в том же раунде.

| Поток | Warm | Warm с нормализацией | Cold | Cold с нормализацией | Interpreter |
| --- | ---: | ---: | ---: | ---: | ---: |
| Store → load | 0.714 [0.576, 0.743] | 0.704 [0.674, 0.725] | 1.035 [0.807, 1.079] | 1.018 [0.942, 1.052] | 1.015 [0.855, 1.027] |
| Load → store | 0.713 [0.570, 0.746] | 0.711 [0.691, 0.724] | 0.993 [0.763, 1.074] | 0.997 [0.926, 1.043] | 1.004 [0.824, 1.031] |

На обоих потоках прогретый кандидат быстрее базовой сборки во всех
шести раундах. Нормализованные холодные диапазоны пересекают единицу
на обоих потоках. Устойчивого изменения времени холодного пути
по этим замерам не обнаружено.

Следующая таблица использует парные отношения внутри одного процесса.
Для каждого потока и сборки проверено 36 троек.

| Поток | Baseline warm/interpreter | Candidate warm/interpreter | Candidate cold/interpreter | Warm быстрее интерпретатора у кандидата |
| --- | ---: | ---: | ---: | ---: |
| Store → load | 1.130 [1.049, 1.194] | 0.799 [0.767, 1.136] | 27.283 [25.041, 30.084] | 35/36 |
| Load → store | 1.127 [1.079, 1.192] | 0.802 [0.756, 0.908] | 27.031 [25.358, 29.946] | 36/36 |

Для одной компиляции с последующими прогретыми вызовами модель
`cold + (N - 1) * warm <= N * interpreter` даёт медианы 132 и 134
суммарных вызовов по тройкам с конечным порогом. Диапазоны 107–145
и 104–276. У одной store→load тройки порога по этой модели нет.
Длинная последовательность с таким числом повторов отдельно не измерялась.

Измеренный путь принят. Тесты публичного `run` подтверждают повторное
использование записи при обратном порядке зависимостей, отказ при
несогласованных версиях, замену при согласованной смене версии и
приоритет STOP, бюджета и события перед переполнением счётчика
попаданий. `cargo test --offline --locked -p od-jit --lib memory_cache::tests::`
прошёл 14/14. Полный набор `od-jit --lib` дал 504 passed и 2 ignored.
Проверка всех целей workspace в offline-режиме завершилась успешно.
Результат замера относится к двум проверенным профилям, одному
удерживаемому ключу и данному ARM64-хосту. Физические проверки и общая
приёмка этапа остаются открытыми. Остаточный рост времени интерпретатора
относительно исторической сборки остаётся в ISSUE-521.

## Воспроизведение

[Архив замеров и инструментов](data/stage3/s3-40v-20261119/checked-memory-exact-key.json.gz)
имеет SHA-256 `f88218d6cfa5915a345f381adb9f0270784ac6d7b9bf938b9869a904bbd2edd2`.
В нём 59 файлов, включая CSV, журналы UID/nice/QoS, нагрузку,
зафиксированный при сборке патч, отпечатки бинарников и манифесты сборок.
Для офлайн-аудита извлеките соседние `offline_audit.py` и `audit.py`
из поля `files`, сверив `file_sha256`, и запустите
`python3 offline_audit.py checked-memory-exact-key.json.gz`.
Результат совпадает с `run/audit.json` из архива.

Для нового прогона разложите исходники драйвера, скрипты и патч по
указаниям в сохранённом `README.md`. Базовая сборка успела завершиться
и подписать бинарник до ошибки в конце первоначальной оболочки сборки.
Перед измерением подпись, архитектура, entitlements и хеш этого
бинарника перепроверены. Повторная компиляция для восстановления
метаданных не потребовалась.
