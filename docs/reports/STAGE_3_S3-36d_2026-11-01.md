# S3-36d — resident warm direct-entry checked-memory comparison

**Status:** three release scored runs and the calibration-only pilot completed
on the committed implementation. Source, per-run evidence, and the cross-run
manifest passed independent review. This is partial evidence for one bounded
warm direct-entry checked-memory profile; it does not establish general memory
performance or close the full S3-36 matrix.

## Scope and correctness

The opt-in `od-bench two-site-memory-warm` profile uses only the two original
S3-34a sequences: `store_then_load` and `load_then_store`. Each sequence has
three fixed seeds and 400 inputs per seed (1,200 per sequence, 2,400 unique
inputs total). `load_then_load`, added later to the broader testkit corpus, is
excluded. The shared input digest is
`b09478b556aa91234d8c453f20e70f637222c5de2d7369d305ffe7c78caae540`.

Before timing, every input ran twice on each backend. The preflight compared
complete CPU state, RAM, exit, retirement, budget, and callback events in
memory for each trial, including ordered callback details. The archived
preflight report records counts and fingerprints rather than per-trial state or
trace dumps. Preflight produced 4,800 interpreter and 4,800 native executions
with 4,800 parity trials. Each scored sequence then had one validated
interpreter and one native warmup sweep.

For each sequence, the profile compiled and published one native block, kept
that same `PublishedCode` resident through the sequence's preflight, warmup,
calibration, and samples, then explicitly dropped it before compiling the next
sequence. The report records one compile, publish, IR drop, and published-code
drop per sequence, with resident mapping high-water one. Timed native calls use
the direct typed entry; the interpreter calls `od_isa::execute::run`. State,
RAM, and callback reset and result validation are outside the timers. There is
no dispatcher lookup or cache activity in this profile, so it reports no cache
hit/miss counters.

The separate calibration-only process met the 200 ms floor for both backends
and both sequences at 2,048 repetitions per side. It retained 12 durable
calibration attempts per sequence, reported
`calibration_only_unscored`, and contained no scored pairs. The three scored
processes used 2,048 repetitions per side and retained all 20 alternating
pairs per sequence. Every measured side exceeded 200 ms; no pair was trimmed.

## Host, load, and limits

The scored runs used an Apple M3 Max, aarch64, macOS 26.7.1, and rustc 1.99.0.
The build source tree was clean. Runtime `working_tree_dirty` is `null` because
the two-second Git status probe timed out.

Monitoring envelopes contain point-in-time CPU, load, Stage 2, and Graphify
snapshots. Stage 2 test processes were sampled idle at 0% CPU with no `rustc`
visible in the scored-run snapshots; this is not continuous process accounting.
The calibration-only envelope records a Stage 2 `od_testkit` compiler at
21.4% CPU in a snapshot after or near that short run. Graphify was not visible
in the scored-run snapshots. Reports have no per-pair wall-clock timestamps,
so overlap during unobserved intervals and its effect on individual pairs are
unknown. Processes were not stopped and all retained pairs remain included.
The UTC monitoring bounds cover the outer `cargo`/benchmark process interval,
including cargo startup and pre-profile work; they are not the report's
`total_elapsed_ns` measurement duration. The early run 1/run 2 snapshots with an
empty journal establish only that the benchmark process was present. They do
not identify a measured phase such as preflight or warmup; monitoring phase
labels are observational, not internal phase markers.

This is one bounded checked-memory slice. It does not cover the third sequence,
other memory forms, cache hits/misses, dispatcher or lookup overhead, VMHost,
owner/MMU integration, SMC, other workloads, broad ISA behavior, physical x86
equivalence, or whole-system performance. Full S3-36 dispatcher/lookup and
workload coverage remains open. Mac mini checks were not run and remain
deferred to the end of Stage 3.

## Reproduction and evidence

The preflight and calibration-only invocations were:

```sh
cargo run --release -p od-bench --offline -- two-site-memory-warm \
  --preflight-only --process-run 1 \
  --output work/tmp/stage3/s3-36d/preflight.json
cargo run --release -p od-bench --offline -- two-site-memory-warm \
  --calibration-only --process-run 1 \
  --output work/tmp/stage3/s3-36d/calibration.json
```

The scored commands used process runs 1, 2, and 3 with distinct `run1.json`,
`run2.json`, and `run3.json` output paths:

```sh
for run in 1 2 3; do
  cargo run --release -p od-bench --offline -- two-site-memory-warm \
    --process-run "$run" \
    --output "work/tmp/stage3/s3-36d/run$run.json"
done
```

Their immutable reports, journals,
monitoring envelopes, preflight, calibration, and suite manifest are archived
under [data/stage3/s3-36d/](data/stage3/s3-36d/). The
[suite manifest](data/stage3/s3-36d/suite-manifest.json), SHA-256
`ae855641e2643d7888558ffddf8ef29eb40021605e47ed8d27e8021058c5be19`, binds
all 14 report, journal, and monitoring artifacts. All 15 archived files were
checked byte-identical to their source evidence and all bound hashes matched.
