# S3-20l — RIP-relative MOV through shared IR and bounded dispatch

## Scope

This slice extends only the checked singleton `48 8B /r disp32` and
`48 89 /r disp32` forms with ModRM `mod=00,r/m=101`, qword data registers
RAX..RBX, and exact seven-byte source. It does not extend pair shapes, add
prefixes/SIB, or introduce multi-instruction compilation. Direct V2 support
already existed; this change carries the decoded operand through shared IR,
validates the seven-byte typed host artifact, and lets `memory_dispatch` compile
the same bounded singleton.

The decoder's `MemoryOperand` remains the only effective-address description.
Its `NextRip` base and signed disp32 are used at the instruction's own
`next_rip`; no host-side address reconstruction was introduced. Existing
private synchronous ordinary data RAM and non-aliasing unsafe preconditions
remain in force. This does not integrate an `od-machine` owner or production
MMU.

## Evidence

- `od-jit` compiler coverage checks negative, zero, and positive/extreme disp32
  for IR load and store, entry at an offset inside CodeView, operand base,
  decoded displacement, `next_rip`, source bytes, and one-instruction PC map.
- The native host RIP-relative test compares direct V2, shared IR, and the
  interpreter for load/store at negative, zero, and positive displacement and
  at an entry inside CodeView. It checks complete CPU state, RAM, store count,
  and the seven-byte RIP advance. Shared-IR load and store are also tested with
  exact architectural-fault payloads and backend errors: faults retain the
  full CPU/RAM snapshot, destination, RIP, and budget with zero retirement;
  backend errors remain host errors. A successful shared-IR store that raises
  STOP in its callback retains the write, returns at next RIP, and retires once.
- The bounded dispatch composition test runs RIP-relative singleton → exact
  bare NOP interpreter step → existing two-site pair. Budgets 0..4 match full
  interpreter state and RAM, and the complete path accounts three native
  retirements and one interpreter retirement. Continuation from the actual RIP
  after the first singleton completes without repeating its read.
- The same dispatch test checks every source-window length 1..6. Each returns
  fixture `BoundaryReached` at the entry with zero retirements, blocks, data
  callbacks, or CPU/RAM changes.
- A complementary composition starts with the interpreter-only NOP, then
  executes RIP-relative load and the existing pair. Distinct adjacent data
  sentinels verify the load uses the RIP-relative instruction's `next_rip`
  after the interpreter step, rather than the prior RIP or source base.

## Review follow-up evidence

The host RIP-relative case now injects architectural faults independently on
shared-IR load and store and verifies exact #PF payload, full unchanged CPU/RAM,
unchanged load destination/RIP, remaining budget 1, and zero retirement. Backend
read/write failures return typed host `MemoryError` with the expected address
and zero length; neither is reclassified as a guest fault. A successful shared-
IR RIP-relative store whose callback raises STOP commits bytes, advances RIP by
seven, reports one retirement and zero remaining budget.

The dispatcher has a second composition order, bare NOP → RIP-relative load →
existing pair. Adjacent data sentinels distinguish the correct address derived
from the RIP-relative instruction's `next_rip` after NOP from one derived from
its entry RIP. It reaches the expected pair result and callback counts.

Follow-up full checks passed: `cargo test -p od-host --offline` (64 unit, 12
integration; two environment-driven cases ignored), `cargo test -p od-jit
--offline` (133 tests), workspace all-target check, and Linux x86_64 od-host /
od-jit check. `cargo fmt --all -- --check` and `git diff --check` passed;
Graphify was refreshed and queried. Linux continues to report the existing
platform-specific dead-code warnings in host mapping/arena paths.

Independent review signed off with no open findings after verifying the
