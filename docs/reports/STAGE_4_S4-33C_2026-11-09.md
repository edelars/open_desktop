# Stage 4 S4-33c — права: запись в supervisor RO при CPL0 и WP=1, и #PF repair/retry на собственном ядре

Статус: ограниченный системный кейс реализован; независимое ревью проведено, срез принят.
Кейс не закрывает родителя S4-33 и Stage 4.

## Что сделано

`Stage4PfRepairProbeV1` — строгий raw-image профиль собственного ядра поверх
принятых примитивов S4-19b/c/d/e1/e2 (семантика не менялась). Fixture
`tests/fixtures/guest/stage4/pf_repair/` (`entry.S`, `layout.ld`) собирается
`tools/build/build_stage4_pf_repair_probe.py` в образ 0xd000 байт (GPA
`0x1000..0xe000`, 128 KiB RAM, без устройств).

- Код: main GVA `0x401000` — `48 89 0B` (`MOV [RBX],RCX`), `48 8B 03`
  (`MOV RAX,[RBX]`); handler GVA `0x402000` — `MOV [RDI],RSI`, `INVLPG [RBX]`,
  `LEA RSP,[RSP+8]`, `IRETQ` (13 байт). IDT (GVA `0x600000`, шлюз 14 -> handler,
  CS 0x08, IST 0) и GDT (GVA `0x601000`) лежат в образе.
- Страницы: data GPA `0xd000` на GVA `0x800000` — supervisor RO (PTE `0xd001`,
  A=0); страница таблицы data (GPA `0x6000`) отображена RW на GVA `0x403000`
  (alias для repair); стек `0x701000/0x702000` (GPA `0xb000/0xc000`).
- Handoff задаёт loader (гостевых LIDT/LGDT нет): CR0 `0x80010033` (WP=1), CR3
  `0x1000`, CR4 `0x20`, EFER `0xd00`, GDTR/IDTR, RBX `0x800000`, RCX = store
  qword, RDI `0x403000`, RSI `0xd023`, RSP `0x702027`.
- Sequencer (8 шагов), состояние после шага (RIP / RSP / RF / PTE):
  fault (`0x401000`/`0x702027`/0/`0xd021`, #PF код 3, CR2 `0x800000`, A на PD и PTE);
  delivery (`0x402000`/`0x701ff0`/0/`0xd021`, код 3 на стеке, 8 committed writes);
  repair (`+3`/`0xd023`, D на alias PTE); INVLPG (`+6`); discard (`+11`, RSP+8);
  IRETQ (`0x401000`/`0x702027`/RF=1, RIP из кадра = fault RIP); retry
  (`0x401003`, RF=0, PTE `0xd063`, data = store); load (`0x401006`, RAX = store).
  Всего 14 committed writes, 6 retired инструкций, бюджет считается в шагах.
- Runner: `od-runner --stage4-pf-repair-probe IMAGE [--budget N]
  [--inject-pte-readonly | --inject-skip-lea | --inject-pte-writable]`; JSON:
  `guest_state`, `event_trace` по шагам (RIP/RSP/RFLAGS/RF/CR2/PTE/data/canary,
  #PF, A/D, committed writes), `committed_write_trace`, `budget`, `stop_reason`,
  `checks`, `failed_checks`. Коды: 0 принято, 7 завершено без принятия, 5
  остановка до конца, 3/4 ошибки аргументов/образа.

## Инъекции

| Инъекция | Результат |
| --- | --- |
| `--inject-pte-readonly` (handler пишет `0xd021`) | `stop_reason=second_page_fault` на retry (код 3, CR2 `0x800000`), steps 7, retired 4, PTE `0xd021`, data = initial; провалены `pte_repaired_to_rw`, `no_second_fault`, `retry_store_committed`, `pte_accessed_dirty` и др.; код 5 |
| `--inject-skip-lea` (в handler перезаписаны байты LEA, шаг Discard убран из плана) | IRETQ стоит на `0x402006` и читает кадр, сдвинутый на один слот; вершина стека (`iretq_frame_rip`=3) - код ошибки, который IRETQ трактует как RIP; примитив возвращает `Unsupported`: `unsupported`, steps 5, retired 2, RIP `0x402006`; архитектурный #GP(0x1000) (в слоте CS `0x401000`) не моделируется; провалены `error_code_discarded_before_iretq`, `iretq_returned_to_fault_rip`; код 5 |
| `--inject-pte-writable` (PTE `0xd003` от loader) | `stop_reason=no_page_fault`, steps 1, store выполнен без delivery, стек не тронут; провален `fault_raised_on_readonly_store`; код 5 |

Мутационная проверка (machine-тесты): loader по умолчанию отдаёт handler RO-значение
(RSI `0xd021`) — падают 3 теста из 7 (handoff, успех, budget); loader по умолчанию
ставит PTE RW — падают 5 из 7.

## Открыто

- Только uncached tracked walker: TLB-on не проверяется; необходимость INVLPG не
  заявляется (его пропуск в этом профиле ничего не ломает и не проверялся).
- LIDT/LGDT гость не исполняет: GDTR/IDTR — часть handoff loader (хотя
  `step_paged_lidt/lgdt` существуют); перевод на гостевые инструкции — отдельный шаг.
- Все три инъекции дают код 5; путь кода 7 (sequencer завершён, oracle не принят)
  в этом кейсе не достигается ни одной инъекцией и покрыт только логикой runner.
- Инъекция `skip_lea` меняет байты handler (LEA затирается) и план sequencer
  (шаг Discard убирается); `pte_stays_readonly` и `pte_writable_at_load` меняют RSI/PTE loader.
- Нет контрольного прогона с CR0.WP=0. Что #PF вызван именно из-за WP,
  подтверждают только тесты примитивов (`paged_probe_quantum.rs` `cr0_wp_clear_*`,
  `page_walk.rs` около строки 455). Покрыто: запись в supervisor RO при CPL0 и
  WP=1 даёт #PF(P|W). Не покрыто в этом кейсе: контраст с WP=0, U/S, SMEP/SMAP,
  NX, CPL3.
- Четвёртая инъекция для кода выхода 7 (loader кладёт в RCX не store-qword,
  например canary) не сделана; проверки после успешного sequencer
  (`retry_store_committed`, `load_observed_stored_value`, `canary_intact`,
  `pte_accessed_dirty`, `final_rip`, `rsp_preserved`) в текущих прогонах не падают.
  Это не блокер.
- Вопрос A-бита на PTE при отказе по правам унаследован от S4-19b; SDM это
  допускает, но поведение не единственно возможное (для S4-34 помнить).
- Не входят: cross-page доступ к данным кейса, IST/TSS, другие пары исключений,
  JIT, IRQ/timer. Кадр доставки исключения `0x701ff0..0x702020` пересекает две
  страницы стека (D ставится на обоих PTE стека, `0x5810` и `0x5808`) - это
  входит в кейс и зафиксировано. Родитель S4-33 открыт.
- `python3 tools/check_layout.py` сообщает «Unmapped root directory: .claude» —
  замечание не связано с этим срезом.

## Ревью

Независимое ревью Opus (high, read-only): архитектурные значения
PTE/кадра/RFLAGS/RSP подтверждены; замечания 1–5 учтены; код выхода 7 допустим
для закрытия, четвёртая инъекция — открытый пункт.
