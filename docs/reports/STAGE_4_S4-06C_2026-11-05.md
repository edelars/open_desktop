# Stage 4 S4-06c: CPU-connected paged MOV to MMIO

## Результат

Принят bounded срез на baseline `833ea99`. Две точные формы из S4-06b
(`48 8B 03`, `48 89 0B`) теперь могут обращаться к qword MMIO после
существующих Long64 four-level 4 KiB translation и permission checks. RAM
по-прежнему использует единственный `PhysicalMemory`; физический MMIO operand
направляется в уже настроенный `MachineBus` binding. Fetch из MMIO и split
access не поддерживаются.

MMIO write выполняет leaf D update вместе с committed-write callback до
единственного вызова устройства. MMIO read передаёт CPU destination только
после успешного чтения. Translation/permission fault не обращается к устройству.
Device failure возвращается как backend error, MOV не retire-ится и CPU state
не коммитится; уже совершённые A/D writes и callbacks сохраняются. По контракту
`BusDevice` ошибка должна быть возвращена до guest-visible device side effect.
Автоматического retry нет.


Integration target: **11 tests passed**. Они покрывают полный `DeviceAccess`,
точный qword payload, ненулевой read result, один dispatch, порядок A/D callbacks
до MMIO, отсутствие вызова при permission fault и полный event journal для
backend write error: шесть A updates, D update и ровно один device write. При
device error проверены неизменность CPU state и нулевой retirement.

## Границы

Срез не подтверждает cross-page MMIO, другие operand widths, instruction fetch
из устройства, device read failure semantics beyond backend typing, retry,
exception delivery/CR2 commit, TLB/invalidation, JIT, interrupts, SMP или Linux.
Родительский S4-06 и этап 4 остаются открытыми.
