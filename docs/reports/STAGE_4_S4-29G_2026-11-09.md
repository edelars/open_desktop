## Подтверждено по исходникам и config

### 1. io_delay: по умолчанию 0xED, а не 0x80 (расхождение с планом)

- В config `CONFIG_IO_DELAY_0XED=y` (строка 13256), `0X80`, `UDELAY`, `NONE` не заданы (13255, 13257, 13258). Значит `DEFAULT_IO_DELAY_TYPE = IO_DELAY_TYPE_0XED` (`arch/x86/kernel/io_delay.c:21-29`), а `native_io_delay()` делает `outb %al,$0xed` (`io_delay.c:38-61`). Дефолт Kconfig (`arch/x86/Kconfig.debug:123-137`) — 0x80, но Ubuntu его переопределяет.
- `outb_p/inb_p` вызывают `slow_down_io()` (`arch/x86/include/asm/io.h:261-273`); при `CONFIG_PARAVIRT=y` (строка 415) это `pv_ops.cpu.io_delay` (`asm/paravirt.h:23-29`), равный `native_io_delay` (`arch/x86/kernel/paravirt.c:104`); подмена есть только у Xen (`arch/x86/xen/enlighten_pv.c:1394`).
- Следствие: PIT clockevent (`drivers/clocksource/i8253.c:130-134, 149, 159-161, 175-176`) пишет задержку в порт 0xED, который в модели — явное устройство (S4-29b: чтение `0xFF`, запись игнорируется). Порт 0x80 при выбранном config в основном пути не используется. Блокер S4-38 по 0x80 из S4-29b/плана для этого config не возникает, пока параметр `io_delay=` не задан.
- Порт 0x80 достижим только из real-mode кода `arch/x86/boot` (`arch/x86/boot/boot.h:39-42`, `a20.c`, `pm.c`) или при `io_delay=0x80`. Если загрузчик S4-37 пройдёт через setup-код bzImage, sink 0x80 нужен; для прямого 64-битного входа — нет. Sink остаётся страховкой и ничему не мешает.
- Решение: `io_delay` в cmdline не задаём (подтверждено, обоснование уточнено: дефолт 0xED, не 0x80).

### 2. check_timer и no_timer_check: путь через IOAPIC pin 2 (ISO 0→2), `no_timer_check` не задаём

- `check_timer()` выходит сразу, если `global_clock_event == NULL` (`arch/x86/kernel/apic/io_apic.c:2060-2061`). Вызывается из `setup_IO_APIC()` при `nr_legacy_irqs()` (`io_apic.c:2294`).
- `global_clock_event` ставит только `pit_timer_init()` (`arch/x86/kernel/i8253.c:41-54`) или HPET (`arch/x86/kernel/hpet.c:467`). HPET нет: в прошивке нет таблицы HPET: в `firmware/uefi/src/acpi/` нет модуля `hpet`, а список модулей-таблиц — `rsdp`, `fadt`, `madt`, `mcfg`, `dsdt` (`firmware/uefi/src/acpi/mod.rs:7-16`); комментарий `dsdt.rs:5` («RTC, HPET ... belong to S7-14/S7-22») подтверждает только, что HPET не описан в DSDT, `hpet_address == 0`, `is_hpet_capable()` ложно (`hpet.c:129-132, 998-999`; `acpi/boot.c:897-906, 1666`), поэтому `hpet_time_init` идёт в PIT (`arch/x86/kernel/time.c:57-64`).
- PIT пропускается, только если `apic_needs_pit()` ложно (`i8253.c:32-39`, `arch/x86/kernel/apic/apic.c:753-791`). Это требует одновременно: известные `tsc_khz` и `cpu_khz`, ARAT в CPUID и (TSC-deadline либо уже известный `lapic_timer_period`, например из CPUID 0x15, `tsc.c:740`). TSC-deadline у нас не объявляется (решение п. 11). Если CPUID объявит ARAT и 0x15, PIT и `check_timer` не запустятся и путь PIT→INTIN2 не будет проверен. Содержимое CPUID в этом аудите не проверялось (см. «не подтверждено»).
- Без `no_timer_check` `timer_irq_works()` реально ждёт тиков (`io_apic.c:1519-1544`): включает прерывания, ждёт по TSC до `40000000000/HZ` циклов или `jiffies+4` (`io_apic.c:1475-1492`), успех при `jiffies > t1+4`, то есть нужно минимум 5 тиков (при `HZ=1000`, config 544 — около 5 мс). С `no_timer_check` (`io_apic.c:1466-1473, 1523-1524`) функция всегда возвращает 1 и не проверяет ничего. Параметр не задаём: он скрыл бы ошибку маршрута PIT→INTIN2.
- Порядок в `check_timer`: `legacy_pic->mask(0)`, LVT0 masked ExtINT (`io_apic.c:2068-2079`), `legacy_pic->init(1)` (2080), `pin1 = find_isa_irq_pin(0, mp_INT)` из ISO (2082, `io_apic.c:635-646`; override IRQ0→GSI 2 даёт `firmware/uefi/src/acpi/madt.rs:23`, обработка `acpi/boot.c:373-435, 527-563`). ExtINT при ACPI нет, поэтому `pin2 = -1` (`io_apic.c:1270, 2084-2085`), печатается `..TIMER: vector=0x.. apic1=0 pin1=2 apic2=-1 pin2=-1` (2087-2088), затем `pin2 = pin1` (2102-2105). Успех — `goto out` на 2124-2128. Ветки отказа (сообщения «MP-BIOS bug», «trying to set up timer», `panic("IO-APIC + timer doesn't work!...")`) — `io_apic.c:2129-2189`. Последняя ветка зовёт `unlock_ExtINT_logic()` (2176), которая читает CMOS (`io_apic.c:1980-1989`), — только на пути отказа.
- Путь реализован в модели в S4-29f (PIT ch0 → INTIN2, `docs/reports/STAGE_4_S4-29F_2026-11-09.md`, проверено только на flat-пробе с вектором 0x60). Подключения к плате и paged-пути (S4-37a) нет.

### 3. AEOI: check_timer пишет ICW4=0x03 на мастер; модель сейчас это ОТВЕРГАЕТ

- `check_timer` вызывает `legacy_pic->init(1)` (`io_apic.c:2080`), то есть `init_8259A(1)`: мастер получает `MASTER_ICW4_DEFAULT | PIC_ICW4_AEOI = 0x01 | 0x02 = 0x03` (`arch/x86/kernel/i8259.c:370-371`; `arch/x86/include/asm/i8259.h:27, 29`), слейв всегда `SLAVE_ICW4_DEFAULT = 0x01` (`i8259.c:381-382`; `i8259.h:28`). Поэтому отказ AEOI на слейве (решение п. 9) Linux не затрагивает.
- До этого `init_ISA_irqs()` делает `legacy_pic->init(0)` (ICW4=0x01, `arch/x86/kernel/irqinit.c:67`, из `init_IRQ`, `init/main.c:1069`). Запись команд PIC — `outb_pic` = `outb` + `udelay(2)`, не `io_delay` (`i8259.h:47-55`); `udelay(100)` внутри `init_8259A` — `i8259.c:393`.
- При `global_clock_event != NULL` AEOI ничему не мешает: LVT0 замаскирован (`io_apic.c:2079`), у пары нет INTR, при AEOI `irq_mask_ack` просто маскирует (`i8259.c:384-391`). Если путь через IOAPIC успешен, PIC остаётся в AEOI.
- Зондирование PIC пропускается: MADT несёт `PCAT_COMPAT` (`madt.rs:41`), Linux тогда не читает IMR обратно (`i8259.c:306-328`; `acpi/boot.c:149-150`). Зондирование (`probe_8259A`, 337-345) вызывается из `early_irq_init` (`kernel/irq/irqdesc.c:558`, `arch/x86/kernel/apic/vector.c:741`).
- РАСХОЖДЕНИЕ с планом (блокер S4-38): по состоянию HEAD `cc70151` (закоммиченный код) ICW4 с битом AEOI отвергается (`crates/od-machine/src/pic_8259.rs:278-282`, `PIC_ICW4_ACCEPTED = 0x01` на строке 50). Утверждение относится только к HEAD `cc70151`; незакоммиченная правка S4-29a2 в рабочем дереве (её ведёт координатор) источником этого аудита не является и здесь не оценивалась. Решение п. 9 («AEOI на мастере принимается») ссылается на «правку S4-29a2», но на HEAD `cc70151` такого блока в `STAGE_4.md` нет и в закоммиченном коде правки нет. Без неё `check_timer` остановит машину на записи ICW4=0x03 в 0x21 (`UnsupportedConfiguration`). Нужен срез «S4-29a2»: принять ICW4=0x03 на мастере (флаг хранится), слейв AEOI отвергать, тест.

### 4. CMOS/RTC: что читает Linux и что обязательно для S4-38

- Единственное обязательное чтение CMOS на пути загрузки — `timekeeping_init()` (`init/main.c:1076`): `read_persistent_wall_and_boot_offset` → `read_persistent_clock64` (`kernel/time/timekeeping.c:1745-1770, 1810`; `arch/x86/kernel/rtc.c:108-111`) → `x86_platform.get_wallclock = mach_get_cmos_time` (`arch/x86/kernel/x86_init.c:149`; подмена на заглушку есть только для DT и особых платформ: `x86_init.c:51-58`, `hyperv/hv_vtl.c:81`, `kvmclock.c:326`). `FADT NO_CMOS_RTC=1` его не отключает: флаг гасит только платформенное устройство (`acpi/boot.c:988-991`, `rtc.c:149-150`).
- `mach_get_cmos_time` вызывает `mc146818_get_time(&tm, 1000)` (`rtc.c:69`): цикл `mc146818_avoid_UIP` читает `RTC_SECONDS` и `RTC_FREQ_SELECT` (reg A) и при бите UIP (0x80) делает `udelay(100)` (`drivers/rtc/rtc-mc146818-lib.c:29-47`). Таймаут 1000 мс = 10000 итераций (`UIP_RECHECK_LOOPS_MS`, `rtc-mc146818-lib.c:11-13`). Чтение `0xFF` даёт UIP=1 каждый раз, итог: около 20000 пар `outb(0x70)/inb(0x71)`, около 1 с виртуального времени в `udelay`, затем `-ETIMEDOUT` и `pr_err("Unable to read current time from RTC")` (`rtc.c:69-73`; `rtc-mc146818-lib.c:160-163`), время 1970. Цикл ограничен, паники нет.
- Этот цикл идёт до `console_init` (`init/main.c:1101`) и до калибровки задержек. `udelay` здесь работает по TSC (`tsc_early_init` → `use_tsc_delay`, `tsc.c:1511`; `init/main.c:1130` — `calibrate_delay` позже), если ранняя калибровка TSC удалась; иначе по `loops_per_jiffy` по умолчанию. Если RDTSC в модели не будет продвигаться пропорционально выполненным инструкциям, 10000 `udelay(100)` не закончатся — это зависание, ограниченное только бюджетом S4-38 (см. «не подтверждено»).
- Драйвер `rtc_cmos` (`CONFIG_RTC_DRV_CMOS=y`, строка 9821) загрузке не нужен и не активируется: при `legacy.rtc = 0` `add_rtc_cmos` возвращает `-ENODEV` (`rtc.c:134-150`), PNP-устройств `PNP0B00..02` в DSDT нет (`dsdt.rs:4-12`: PCI0, ECAM, COM1), `cmos_init` ничего не находит (`rtc-cmos.c:1547-1562`). `mc146818_does_rtc_work()` (`rtc-cmos.c:1038`) не вызывается. ACPI-обработчик CMOS-региона ставится только на устройства `PNP0B00..02` (`drivers/acpi/x86/cmos_rtc.c:20-23, 67-68`) — не применимо. `CONFIG_RTC_HCTOSYS=y` (9722) при отсутствии `rtc0` — мягкий отказ (не проверялся).
- Остальные читатели CMOS не на пути загрузки: `io_apic.c:1980-1989` (только ветка отказа check_timer), `arch/x86/kernel/hpet.c` (нет HPET), `arch/x86/kernel/bootflag.c:50` (`sbf_port` ставится из ACPI-таблицы BOOT, её в прошивке нет; `bootflag.c:22, 46, 70`), `drivers/char/nvram.c` (модуль, `CONFIG_NVRAM=m`, строка 5018), `mach_set_cmos_time` (`rtc.c:35-54`) — только при NTP-синхронизации (`CONFIG_GENERIC_CMOS_UPDATE=y`, строка 103). `CONFIG_PM_TRACE_RTC=y` (649) CMOS не трогает (`include/linux/pm-trace.h:12-15`).
- Для S4-38 обязательно: порты 0x70/0x71 принимают байтовые `outb`/`inb` с чтением `0xFF` (S4-29b), цикл UIP завершается, момент и длительность наблюдаемы. Опция «сделать reg A = 0x00, чтобы не терять 1 с» противоречит решению S4-29b и в этом срезе не принимается.

### 5. Калибровка TSC: путь, который выбирает config

- Ранняя (до PIT clockevent и до `console_init`): `tsc_early_init()` из `setup_arch` (`arch/x86/kernel/setup.c:1017`) → `determine_cpu_tsc_frequencies(true)` (`tsc.c:1456-1498`): `cpu_khz = native_calibrate_cpu_early` (`tsc.c:919-931`) и `tsc_khz = native_calibrate_tsc` (`tsc.c:672-744`; `x86_init.c:147-148`).
- Порядок источников: CPUID 0x16 (`cpu_khz_from_cpuid`, `tsc.c:746-761`, только Intel) → `cpu_khz_from_msr` (`tsc_msr.c:166-175`, только списка моделей) → `quick_pit_calibrate()` (`tsc.c:577-666`). `native_calibrate_tsc` берёт CPUID 0x15 (только Intel, `tsc.c:677-743`) и при успехе сам задаёт `lapic_timer_period` (`tsc.c:740`). Что отдаст CPUID модели, не проверялось.
- `quick_pit_calibrate` требует `has_legacy_pic()` (`tsc.c:583`; на этот момент верно: `probe_8259A` ещё не вызывался, и из-за PCAT_COMPAT он не запустится), работает с PIT ch2: RMW порта 0x61 (`tsc.c:587`), `0xB0` в 0x43, счёт `0xFFFF` в 0x42 (598-602), затем только чтения 0x42 (по два на проход: `pit_verify_msb`, `tsc.c:540-545`) с RDTSC между ними (`pit_expect_msb`, `tsc.c:547-566`); успех при погрешности менее 500 ppm (`tsc.c:623-642`), сообщение `Fast TSC calibration using PIT` (664), иначе `Fast TSC calibration failed` (645).
- Запасной путь, если ранняя калибровка вернула 0: `tsc_init()` (`tsc.c:1548-1556`) → `pit_hpet_ptimer_calibrate_cpu` (`tsc.c:767-914`): PIT ch2 10 мс, `latch=11931`, `loopmin=1000` (423-425), опрос бита 5 порта 0x61 (476-485), до 3 попыток, при двух неудачах PIT окно 50 мс (860-864). Опорный счётчик: HPET, если включён, иначе PM-таймер (`tsc_read_refs`, `tsc.c:367-384`, чтение `acpi_pm_read_early`, `include/linux/acpi_pmtmr.h`; порт из FADT, `acpi/boot.c:998-1019`). Условия выбора: PIT и опора в пределах 10% — берётся опора (`tsc.c:838-852`); PIT не дал значения — берётся опора, а если и её нет, то `return 0` («No reference (HPET/PMTIMER) available», `tsc.c:870-884`) и TSC помечается нестабильным (`tsc.c:1550-1553`); опоры нет — PIT (`tsc.c:893-897`); расхождение — PIT (`tsc.c:905-913`).
- HPET как запасной путь недоступен (нет таблицы HPET, см. п. 2), `CONFIG_HPET_TIMER=y` (459) значения не имеет. PM-таймер как запасной путь доступен, если FADT даёт `PM_TMR_BLK` (S4-31e, не перепроверялось).
- Для S4-38 обязательно из PIT: ch2 в режиме 0 с gate=1 (0x61 bit0), счёт 0xFFFF/11931, чтение 0x42 LSB+MSB, бит 5 порта 0x61 (OUT2), «порт-тик» на чтениях 0x42 и 0x61 (решение п. 5; на 0x42 пока не реализован, S4-37a), TSC, согласованный с этим тиком. Из PM-таймера: монотонное 24-битное чтение (см. п. 6).

### 6. LAPIC timer, PM-таймер и clocksource

- `calibrate_APIC_clock()` (`apic.c:793-964`): CPUID TSC-deadline нет → `lapic_timer_period` обычно 0 (если не пришёл из CPUID 0x15) → калибровка 100 тиков (`LAPIC_CAL_LOOPS = HZ/10`, `apic.c:646`), конец тика определяется по TSC при известном `tsc_khz` (`apic.c:843-872`), на каждом шаге читаются TMCCT, RDTSC и PM-таймер (`lapic_cal_handler`, `apic.c:657-683`). Результат корректируется по PM-таймеру (допуск 1%, `calibrate_by_pmtimer`, `apic.c:685-733`; `CONFIG_X86_PM_TIMER=y`, строка 735). Если `deltapm = 0` (PM-таймера нет), `pm_referenced = 0` и включается проверка по тикам PIT через `global_clock_event` (`apic.c:926-955`). Отказы: «APIC frequency too slow, disabling apic timer» (`apic.c:913-917`), «APIC timer disabled due to verification failure» (958-961). Сообщения самой калибровки (`calibration result` и др.) печатаются через `apic_pr_verbose` только при `apic=verbose` (`apic.c:2642-2644`, `asm/apic.h:44`).
- Роль PM-таймера в S4-38 обязательна: калибровка LAPIC (`apic.c:661`), `acpi_pm` clocksource (`drivers/clocksource/acpi_pm.c:208-249`: 10 проверок монотонности, до 10000 чтений каждая, `rating = 200`, строка 98), watchdog и refine TSC (`tsc.c:1323-1375`).
- Какие часы будут тиком: PIT-clockevent регистрируется без `.rating` (то есть 0; `drivers/clocksource/i8253.c:186-192`), LAPIC имеет `rating = 100` (`apic.c:509`), поэтому LAPIC заменяет PIT как tick device (`kernel/time/tick-common.c:289-307, 326-352`), PIT гасится (`kernel/time/clockevents.c:100-108, 592-609`; `drivers/clocksource/i8253.c:104-134`: `0x30` в 0x43, два нулевых байта в 0x40 и снова `0x30`, все через `outb_p`). PIT затем ставится broadcast-устройством (`tick-common.c:361`, `tick-broadcast.c:88-100, 166-195`), но не взводится, пока CPU не уходит в C3STOP-состояние (`tick-broadcast.c:1105-1126`); `CONFIG_CPU_IDLE=y` (780), но `_CST` в DSDT нет — простой это HLT.
- Модель PIT принимает только режимы 0 и 2 (`crates/od-machine/src/pit_8254.rs:25-28, 364-367`), остальные управляющие слова — `UnsupportedConfiguration`. Linux в oneshot PIT пишет `0x38` (режим 4, `drivers/clocksource/i8253.c:146-152`; регистрация oneshot — `drivers/clocksource/i8253.c:198-203`, `pit_timer_init` передаёт `true`, `arch/x86/kernel/i8253.c:53`). На обычном пути UP PIT в oneshot не доходит (его гасит LAPIC и не взводит broadcast), но он достижим, если LAPIC-таймер откажет (см. отказы выше): тогда PIT остаётся tick device и после переключения на hrtimer запишет `0x38`.
- Clocksource: `tsc-early` rating 299 (`tsc.c:1175-1177`, регистрация `tsc.c:1575`), `acpi_pm` rating 200, финальный `tsc` rating 300 после refine (`tsc.c:1199`, `device_initcall(init_tsc_clocksource)`, 1454), `jiffies` запасной. HPET нет. Сообщение выбора — `Switched to clocksource <имя>` (`kernel/time/clocksource.c:1070`).

### 7. Другие legacy-порты, которых Linux не должен коснуться

- i8042 (`CONFIG_SERIO_I8042=y`, строка 4877): FADT rev 6 без флага 8042 → `x86_platform.legacy.i8042 = FIRMWARE_ABSENT` (`acpi/boot.c:981-986`), PNP-устройств нет → `i8042_pnp_init` возвращает `-ENODEV` без обращений к 0x60/0x64 (`drivers/input/serio/i8042-acpipnpio.h:1628-1641`). Подтверждает, что ловушка `UnmappedPort` на 0x60/0x64 (решение п. 7) безопасна. FADT-флаги — S4-29b/S4-31e.
- ELCR 0x4D0/0x4D1: пишутся только в режиме без IOAPIC (`drivers/acpi/bus.c:1394-1401`, `acpi/boot.c:604-640`, `675-686`, `acpi_pic_sci_set_trigger`). С MADT IOAPIC не используются.
- Остальные UART: `CONFIG_SERIAL_8250_RUNTIME_UARTS=32` (4926), а `old_serial_port` регистрирует ttyS0..3 на 0x3F8, 0x2F8, 0x3E8, 0x2E8 (`arch/x86/include/asm/serial.h:23-28`; `8250_platform.c:48-91, 303-330`; `8250_core.c:368-386`), и `autoconfig` читает их регистры (`8250_port.c:3114-3120`). В модели привязан только COM1 (`dsdt.rs:4`), то есть обращения к 0x2F8/0x3E8/0x2E8 дали бы `UnmappedPort`. Параметр `8250.nr_uarts=1` (`8250_platform.c:35, 63-64, 78, 383-384`; `drivers/tty/serial/8250/Makefile:7-8`: объект называется `8250`) оставляет только ttyS0.
- Остальное на пути загрузки (PCI conf1 0xCF8..0xCFF, ECAM, PM-блок, GPE/SMI_CMD из FADT) — зона S4-30/S4-31, здесь не перепроверялось.

### 8. Выбранная cmdline

```
console=ttyS0,115200 earlycon=uart8250,io,0x3f8 8250.nr_uarts=1 od.nonce=<nonce>
```

- `console=ttyS0,115200`: нужна, чтобы `/init` (S4-36) выводил `OD_NONCE=...` в fd 1. Без `console=` консоль — tty0 (`CONFIG_VT_CONSOLE=y`, 4902; `VGA_CONSOLE=y`, 7842; VGA на плате нет), а boot-консоль earlycon снимается при регистрации любой реальной консоли и в `printk_late_init` (снятие при регистрации консоли — `register_console`, `kernel/printk/printk.c:4209-4216`; `printk_late_init` — `printk.c:4427`, там снимаются только boot-консоли из init-секции). Драйвер: `CONFIG_SERIAL_8250_CONSOLE=y` (4918). Уровень логов по умолчанию 7 (`CONFIG_CONSOLE_LOGLEVEL_DEFAULT=7`, 12863), `quiet` не задан, поэтому `pr_info` видны.
- `earlycon=uart8250,io,0x3f8` (без скорости): сообщения до `console_init` (`init/main.c:1101`) иначе не выводятся, а именно там расположены новые риски (`tsc_early_init` в `setup_arch`, `timekeeping_init` на `init/main.c:1076` с циклом UIP). Без earlycon зависание до `console_init` было бы видно только по бюджету. Без скорости `early_serial8250_setup` не программирует делитель и не трогает LCR, а лишь читает/пишет IER (`drivers/tty/serial/8250/8250_early.c:155-167`); передача — запись THR и опрос LSR (`8250_early.c:85-95`). `CONFIG_SERIAL_EARLYCON=y` (4913). Дублирования нет: boot-консоль снимается при регистрации `ttyS0` (`register_console`, `printk.c:4209-4216`; строка 3986 относится к `get_init_console_seq` и снятия не делает).
- `8250.nr_uarts=1`: см. п. 7. Без него запуск остановится на `UnmappedPort` при пробе ttyS1..3.
- `od.nonce=<nonce>`: параметр с точкой в имени классифицируется как параметр модуля и молча игнорируется ядром (`init/main.c:524-530`), в окружение и argv `init` не попадает (это и нужно: `/init` читает его из `/proc/cmdline` сам, S4-36). Полная строка сохраняется (`COMMAND_LINE_SIZE = 2048`, `arch/x86/include/asm/setup.h:7`), nonce 16..128 символов помещается. Токен не должен стоять после `--`. Остальные параметры S4-29g `od.nonce` не затрагивают (разделение пробелом, парсер `/init` ищет токен в начале строки или после пробела, S4-36).
- Не добавляется: `io_delay=` (п. 1), `no_timer_check` (п. 2), `apic=verbose` (при нём `print_ICs` на `late_initcall` читает все регистры LAPIC/IOAPIC и PIC, `arch/x86/kernel/apic/vector.c:1370-1387`, — неаудированная поверхность; включать отдельным прогоном после аудита регистров), `earlyprintk=` (дублирует earlycon; `early_printk.c:406` программирует делитель), `nosmp`/`maxcpus` (в MADT один LAPIC), `acpi=`/`noapic`/`nolapic` (ломают проверяемый путь), `notsc`/`clocksource=` (скрывают калибровку), `panic=` (reboot через неподдерживаемые порты), `nokaslr` (необязателен, см. открытые вопросы).

GSI 0-23` (`io_apic.c:2759`), `APIC: Switch to symmetric I/O mode setup` (`apic.c:1375`), `ECAM ... for domain 0000` (`arch/x86/pci/mmconfig-shared.c:113`), строка `..TIMER: ... apic1=0 pin1=2` (`io_apic.c:2087`); значения диапазона шин и вектора берутся из прогона.

## Не подтверждено (нужен запуск S4-38 или срез реализации)

- Содержимое CPUID модели (ARAT, лист 0x15/0x16, бит hypervisor): определяет, пропустит ли Linux PIT и `check_timer`, и источник калибровки. Требуется сверка CPUID с этим аудитом перед S4-38.
- Частота TSC относительно часов платы: `delay_with_tsc` в `timer_irq_works` обрывается на 40 млн тактов (`io_apic.c:1484-1491`), а 5 тиков PIT при `HZ=1000` занимают ~5 мс, поэтому при TSC выше ~8 ГГц относительно часов платы проверка `check_timer` по этому пути не пройдёт (ветка отказа). Допустимая частота модельного TSC и её согласование с часами платы не проверены.
- Что RDTSC (и `udelay`) продвигаются пропорционально времени платы: без этого зависнут цикл UIP (10000 `udelay(100)`), `delay_with_tsc` в `timer_irq_works`, `quick_pit_calibrate`. Порт-тик на 0x42 и PM_TMR — S4-37a (S4-29d сделал только 0x61).
- ICW4=0x03 на мастере: по состоянию HEAD `cc70151` модель его отвергает; срез «S4-29a2» на HEAD отсутствует в плане и в закоммиченном коде (блокер S4-38, см. п. 3; рабочее дерево с правкой S4-29a2 аудитом не рассматривалось).
- Режим PIT 4 (`0x38`) и однобайтный/другие режимы: модель отвергает; достижимо только при отказе LAPIC timer (п. 6).
- Тип UART, поведение `autoconfig` ttyS0 на модели без FIFO/loopback, `hctosys` без `rtc0`, `perf`-NMI watchdog (`CONFIG_HARDLOCKUP_DETECTOR_PERF=y`, строка 13023: при отсутствии PMU должен тихо отключиться; не проверялось).
- PM-блок и FADT `PM_TMR_BLK` (S4-31e) и PM-таймер на общих часах (S4-37a): реальное поведение чтений PM_TMR в Linux-профиле.
- Связь source/config с бинарями `vmlinuz` (S4-35: hash only).

## Открытые вопросы для оркестратора

1. Срез S4-29a2 (ICW4=0x03 на мастере) нужен до S4-37a/S4-38: на HEAD `cc70151` без него `check_timer` останавливает машину (правка координатора в рабочем дереве аудитом не оценивалась).
2. Принять ли около 1 с виртуального времени на цикл UIP в `timekeeping_init` (бюджет S4-38) или менять решение S4-29b (reg A без UIP)? Параметра cmdline, который отключает чтение, нет.
3. Нужен ли `nokaslr`: в распаковщике `choose_random_location` (`arch/x86/boot/compressed/misc.c:490`, `kaslr.c:861-870`) использует RDRAND или RDTSC, i8254 только без TSC (`arch/x86/lib/kaslr.c:57-85`). Решается при выборе способа входа в S4-37 (bzImage или vmlinux).
4. Править ли формулировку п. 7 решений Opus и блок S4-29b («io_delay по умолчанию 0x80 / блокер 0x80»): по config дефолт 0xED, sink 0x80 не обязателен для выбранной cmdline. Отчёт S4-29b и план в этом срезе не менялись.
