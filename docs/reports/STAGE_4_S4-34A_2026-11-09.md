# Stage 4 S4-34a — метод: реальное CPL0 исполнение через KVM на Mac mini

Статус: метод реализован и выполнен на реальном железе; ревью Opus приняло метод
с замечаниями, замечания закрыты этим перепрогоном. В evidence JSON верхний
статус разделён: `method_status: "accepted"` (метод работает) и
`s4_34: "not_accepted"` (S4-34 не принят). Срез не закрывает S4-34 и Stage 4,
физическая приёмка S4-34 не заявляется. В плане `[x]` не ставился.

## Что сделано

- `tools/kvm-runner/kvm_runner.c` (+ `Makefile`): хост-раннер на C11, один файл.
  `/dev/kvm`, `KVM_GET_API_VERSION` (требует 12), `KVM_CREATE_VM`, 2 MiB
  анонимной RAM в GPA 0, образ по GPA `0x1000`, собственные page tables гостя
  (PML4 `0x2000`, PDPT `0x3000`, PD `0x4000`, 2 MiB identity-лист), GDT по
  `0x5000` (null, code64 `0x08`, data `0x10`), `KVM_SET_CPUID2` из
  `KVM_GET_SUPPORTED_CPUID`, sregs/regs, цикл `KVM_RUN`. Выводит одну JSON-строку.
- Гостевой образ `tests/fixtures/guest/stage4/kvm_method/` (`entry.S`,
  `layout.ld`): `mov $0x3f8,%dx; out 'O','K','\n'; hlt`, 16 байт, линковка на
  `0x1000`, entry `0x1000`. Сборка на Mac: `clang --target=x86_64-unknown-none-elf`,
  `ld.lld` и `objcopy` из Rust sysroot (в PATH нет отдельных lld/objcopy).
  Фактические инструменты (поле `tools` в JSON): `clang` `/usr/bin/clang`
  (Apple clang 21.0.0, clang-2100.3.34.2); линкер `~/.rustup/toolchains/stable-aarch64-apple-darwin/lib/rustlib/aarch64-apple-darwin/bin/gcc-ld/ld.lld`
  (это обёртка gcc-ld над `rust-lld`, `--version` печатает `LLD 23.1.1`);
  `rust-objcopy` из того же sysroot (`llvm-objcopy`, совместим с GNU objcopy).
- `tools/build/build_stage4_kvm_method.py` + `test_build_stage4_kvm_method.py`
  (25 тестов без железа). Оркестратор: сборка, SHA-256, scp, `gcc` на mini,
  запуск, проверка, evidence.
- Evidence: `docs/reports/data/stage4/s4-34a-kvm-method.json`.

## Основной прогон (accepted)

- exit `hlt`, `stop_reason` `guest_hlt`, `run_count` 4, `intr_count` 0.
- Последовательность exit'ов (строго, иначе отвержение): три `io` (OUT `0x3f8`, size 1,
  данные `0x4f`, `0x4b`, `0x0a`), затем `hlt`; любой другой порт, размер, направление,
  данные или лишний/недостающий exit и `exits_dropped != 0` отвергаются.
  Раннер печатает данные как `%llx` (`0xa`), поэтому сравнение нормализует hex в числа.
- UART: hex `4f4b0a`, text `OK\n`.
- Entry state (прочитан обратно из KVM перед первым запуском): RIP `0x1000`,
  RSP `0x8000`, RFLAGS `0x2`, CR0 `0x80000033`, CR3 `0x2000`, CR4 `0x20`,
  EFER `0x500`, CS selector `0x8` (L=1, D=0, DPL=0), SS selector `0x10`.
- Все проверки (exit, uart, rip, rsp, cr0 `0x80000033`, cr3, cr4, efer, cs selector, CS.L=1, CS.D=0, CS.DPL=0, SS `0x10`, последовательность exit'ов, API 12, sha) пройдены.

## Наблюдения

- Без `KVM_SET_CPUID2` `KVM_SET_SREGS` с `EFER.LME` возвращает `EINVAL`
  (KVM проверяет EFER по guest CPUID); раннер передаёт CPUID, поддерживаемый хостом.
- `HLT` доходит до userspace, потому что irqchip не создаётся.
- Зависший гость прерывается периодическим `SIGALRM` (10 мс, без `SA_RESTART`)
  через `EINTR`; такие возвраты считаются отдельно в `intr_count`, а `run_count` — число
  возвратов `KVM_RUN` с настоящим exit. Лимит 1000 применяется к `run_count + intr_count`,
  wall-дедлайн 2000 мс не менялся.
- `KVM_GET_SUPPORTED_CPUID` вызывается с 128 записями и при `E2BIG` растёт до 256.

## Что не проверено и граница

- Один образ, без прерываний и irqchip; нет page-walk/rights/A-D/CR2, CR-переходов,
  дескрипторов и доставки (это S4-34b и далее).
- Нет Linux, reboot, изменения загрузки; S4-34 не принят.
- CPUID гостя равен supported-набору хоста; независимость от нашего oracle для
  будущих кейсов определяется их собственными ожиданиями, здесь она не оценивалась.
- Hardware identity и вывод раннера получены по ssh и не имеют отдельной
  подписи; доверие к хосту принимается по хэшам артефактов и повторяемости.
- Повторяемость прогона между перезапусками хоста не измерялась (один запуск каждого случая).

## Методика для S4-34b

Тот же канал: образ собирается на Mac (clang/lld/objcopy), раннер принимает raw-образ
и пишет JSON (UART, exits, entry state). Для кейсов S4-34b потребуются: больший
guest RAM/layout (сейчас образ ограничен `0x1000..0x1FFF`), чтение
регистров/памяти после `HLT` как evidence, обработка исключений гостя собственной
IDT (в S4-34a IDT нет, #PF/#GP привели бы к triple fault и `shutdown`).
