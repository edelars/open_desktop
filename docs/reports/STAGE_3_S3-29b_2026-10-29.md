# S3-29b: uncached demand-flags multi-block NOP dispatch

## Result

Added `dispatch::run_with_nop_fallback_demand_flags_candidate` as an explicit
opt-in entry point. It selects the existing demand-flags candidate compiler on
each reached native block and shares the eager NOP-fallback loop for admission,
dispatch control, counters, bare-NOP interpreter fallback, event ordering,
terminal exits and errors. The eager `run_with_nop_fallback` remains the
reference/default. The candidate is not connected to the shared translation
cache. `PublishedBlockExecutor` continues to drop the executable mapping before
the loop performs the next compilation or interpreter step.

The native test exercises three ADD/JNZ iterations (two taken back-edges and a
non-taken branch), bare NOP, CMP/JZ with both outcomes, and MOV after the
non-taken JZ. A block-executor witness requires an actual
`InadmissiblePendingFlags` PC-map range. Candidate state and accounting are
compared with eager dispatch and independent `od_isa::execute::step` execution.
The test covers budgets 0 through full completion, every reachable instruction
stop-RIP boundary, and resume from each boundary without replay. It injects
events after a loop block and immediately before the NOP, verifies canonical
pending-event state, then clears and resumes. STOP-RIP, STOP and exhausted
budget retain priority over an event.

No ISA, memory profile, ABI, owner, Stage 2 or `od-machine` changes were made.
The eager default and cache compilation identity are unchanged. This remains a
bounded correctness candidate; no performance conclusion or policy choice is
made.
