**Date:** 2026-11-08  
**Scope:** documentation inventory for a single Ubuntu Generic amd64
`7.0.0-38.38` candidate, using the existing contracts and evidence. The
[versioned manifest v0.1](data/stage4/s4-00c-machine-candidate-v0.1.json)

It is not a new normative board specification. Component contracts remain in

[VIRTUAL_BOARD](../specs/VIRTUAL_BOARD.md) and

running timer), so every item was re-derived from the slices that exist here.

## Evidence and entry

The selected image is `vmlinuz-7.0.0-38-generic`; its recorded SHA-256 is
`9f55ef7253055a9cf68f8a04323c93dead2fca617386d842fbde9ca7b178b27e`.
In this slice the SHA-256 of the image, `.deb`, `vmlinux`, debug `vmlinux`, source package, source
archive and extracted config were recomputed from the local ignored artifacts under
`work/vms/s2-00-ubuntu-26.04.1/` and match the values in [S4-00a](STAGE_4_S4-00A_2026-11-05.md)
and the manifest. The recovered `head_64.S`, `pgtable_64.c` and `kernel/head_64.S` hashes also match S4-00a; the two
further source files read in this slice are recorded here: `arch/x86/boot/compressed/ident_map_64.c`
`015bb473b34b6469e015c6cbff94d532ec883aca45a013334d7d98b1037ae733` and
`arch/x86/boot/compressed/misc.c` `4a13a95905df1c07accb53a313b78963e4f9ef36735523a8a635da84ab9fbf4f`. The
source claims used in the direct64 table (`configure_5level_paging` call, the LA57 request
condition and trampoline, `PMD_SIZE`/`_PAGE_PSE` identity maps with `write_cr3`, decompression in
`misc.c`, and the `MSR_GS_BASE`/`lgdt`/`verify_cpu`/`%cr3` sequence in `kernel/head_64.S`) were
re-read in the extracted source archive. This is local-byte evidence, not current authenticated
source/config-to-binary correspondence: Stage 2 recorded an earlier authenticated mapping and this
capture did not reproduce its signed chain (ISSUE-036). The source path analysis is conditional and
no runtime branch selection has been established.

The bzImage header records protocol 2.15 and `XLF_KERNEL_64` ([S4-00b](STAGE_4_S4-00B_2026-11-06.md)).
The candidate entry is `+0x200` from the loaded protected-mode image. The loader must establish
Long64 paging, identity mappings for `init_size`, zero page and command line, flat boot
GDT/segments, disabled interrupts, and RSI pointing to `boot_params`. The manifest distinguishes
these requirements and the selected four-level `CR4.LA57=0` policy from the unknown observed
snapshot. Exact RAM placement, reservations, initial tables and other control values remain open. A
4 GiB Windows-oriented board target does not establish the Linux RAM map.

## CPU, MMU and device prerequisite matrix

Navigation summary; per-item evidence, ownership and next checks are in the manifest. `known`
means a documented fact, not runtime readiness; `selected-but-unverified` is a candidate, a
requirement or a bounded local slice pending integrated Linux validation; `required-unimplemented`
means missing or unaccepted integration; `unknown` records an unresolved value, proof or
requirement.

| Item | Status | Current boundary / next decision |

The recovered source's LA57 branch and 2 MiB identity maps are conditional source evidence under
the proposed CPUID and initial CR4, not proof of binary execution. The need for 2 MiB MMIO for this
Linux target has not been established. Neither a complete MSR allowlist nor a full Linux device
profile is implied by the local slices. No Linux image, initramfs, runtime trace or source archive
is added to Git.

## Review

Independent review (Claude Opus, effort medium) re-derived each of the 22 items against the slices
in `main`, recomputed the local artifact hashes and re-read the cited Linux source. No P0–P1 findings;
statuses match `main` and nothing is overstated. P2 fixed: the review section was empty, and the
direct64 table understated the compressed `startup_64` prerequisites (null-selector loads including
SS, `lgdt` + `lretq`, `load_stage1_idt`, `sev_enable` CPUID probing, the CR4 read-modify-write; the
`lgdt`, second GS-base write and EFER accesses belong to `common_startup_64`). P3 fixed: S4-28a3 is
noted as awaiting review, the matrix gained an entry-protocol row, the hashes of `ident_map_64.c` and
`misc.c` are recorded, the lists of paging/descriptor/target slices were completed, and ISSUE-036 is
described as the FPU-origin tracker of the same provenance gap. Not carried over from `stage4`: its
`KNOWN_ISSUES.md` edits (ISSUE-027/036 rewording) — those issues keep their existing text, which cites
the earlier Stage 2 mapping.

Checks: manifest JSON parses (22 unique ids); `tools/check_layout.py` reports only the missing
ignored `work/` links of the isolated worktree; `git diff --check` is clean. No Rust code or runtime
behavior changed.
