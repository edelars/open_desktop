# S3-39 — bounded ARM64 smoke on M1 Pro

**Status:** The requested bounded smoke passed on a MacBook Pro with Apple M1
Pro, using artifacts built from the S3-39 baseline revision. This records one
host configuration and these cases only; it does not claim broad Apple Silicon
support or replace physical x86 validation.

## Source and artifact

The dedicated worktree was pinned to clean commit
`00bf9476f107eb7343026b81899e3ec8111543f1` (`docs: refresh stage 3 evidence
summary`), before the in-progress S3-40d changes in the other worktree. The
release `od-host` static library was cross-built on the local M3 Max host with
Rust/Cargo 1.99.0, target `aarch64-apple-darwin`,
`MACOSX_DEPLOYMENT_TARGET=14.0`, and `RUSTFLAGS='-C target-cpu=generic'`.
`otool -l` reported `minos 14.0` for the archive's object members. No
M1-specific Rust installation was needed: neither `rustc` nor `cargo` was in
PATH or `~/.cargo/bin` on the M1.

The archive, ABI header, VMHost Swift sources, launcher source, and VMHost
entitlements were copied to a unique directory under `/tmp` on the M1. Xcode
15.4 / Swift 5.10 / Apple clang 15.0 and SDK 14.5 compiled all three ARM64
executables with `-target arm64-apple-macosx14.0`. Both VMHost and launcher
were signed ad-hoc with Hardened Runtime and passed
`codesign --verify --strict`. VMHost has
`com.apple.security.cs.allow-jit=true`; the launcher has no JIT entitlement.
The small C ABI lifecycle probe was also signed with Hardened Runtime and the
same JIT entitlement and passed strict verification.

## M1 Pro execution

The target machine was MacBookPro18,3 / Apple M1 Pro, arm64, macOS 14.6.1
(23G93), 16 GiB RAM, and 16,384-byte host pages. A Python 3.12.5 driver
launched the signed programs directly, outside a debugger, with a 15-second
per-process timeout. Each case captured argv, stdout, stderr, exit status, and
monotonic elapsed duration. All elapsed times are smoke-process observations,
not performance measurements.

| Case | Bounded result | Process duration |
|---|---|---:|
| Arithmetic: `48 2b c1 75 fb`, RAX=3, RCX=1, budget 32 | RAX=0, RIP=5, reason 0, 6 instructions | 693.6 ms |
| Taken multi-block path: `48 3b c1 74 03 48 03 c3 48 03 c2`, RAX=5, RCX=5, RDX=2 | RAX=7, RIP=11, reason 0, 3 instructions | 8.6 ms |
| Accepted `s3_14_live_through_helpers` fixture | RAX=1, RCX=0, RDX=0, RBX=1, RIP=17, reason 0, 6 instructions | 17.7 ms |
| Cooperative STOP: `75 fe`, STOP after 25 ms | reason 2, RIP=0, 27,772 instructions | 39.2 ms |
| Repeated VMHost publication/execute invocation | Same arithmetic result in a fresh VMHost process | 9.0 ms |
| Same-process C ABI lifecycle | One handle: create, execute twice, destroy; both runs returned RAX=0, RIP=5, reason 0, 6 instructions; all ABI statuses 0 | 503.5 ms |

The same-process probe exercises the public `od_fragment_create`,
`od_fragment_execute`, and `od_fragment_destroy` functions. A second execution
on the same handle completed after the first call returned, which checks that
sequential per-call publication can run again without a stale/busy handle
state. It does not measure memory release, stress repeated allocation, or
establish persistent cache reuse.

An earlier constructed multi-block input used `ADD RAX,imm8`, outside the
accepted S0-09 register-only admission, and VMHost returned
`OD_STATUS_INVALID_CODE` (status 2). That rejected input and its empty stdout,
status, and stderr are retained in the raw run record, but are excluded from
the passing cases. The accepted replacement uses only admitted register to
register arithmetic and a valid taken JZ into a separate block.

## Evidence and limits

[Accepted case summary](data/stage3/s3-39-m1pro/accepted-summary.json) records
all six passing cases and the excluded probe. Per-case stdout, stderr, status,
and duration files, the C lifecycle source, runner scripts, machine facts, and
artifact metadata are in
[`docs/reports/data/stage3/s3-39-m1pro/`](data/stage3/s3-39-m1pro/). Their
SHA-256 values are listed in
[raw-evidence-sha256.txt](data/stage3/s3-39-m1pro/raw-evidence-sha256.txt).

The run checks a narrow portable build and execution path on one M1 Pro. It
does not run the broad VMHost process suite, physical x86 oracle, Mini, GUI or
VM lifecycle, owner/MMU or SMC integration, Developer ID signing, notarization,
or performance tests. It does not exhaustively disassemble the binaries; the
Rust build used `target-cpu=generic` and the exercised paths ran successfully
on M1 Pro. The M1 result is not a full CPU or host support claim.
