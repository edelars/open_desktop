# S3-30a — bounded allocator cost diagnostic

**Status:** the bounded comparison completed and passed independent evidence review. It does not complete S3-30 allocator selection or make a production policy choice.

## Scope

The opt-in `od-bench allocator-cost` command compared the existing `register_homes` configuration at budget 4 (production baseline) and budget 0 (spill-only diagnostic). No allocation algorithm, runtime compiler behavior, or production default changed.

The fixture is one frozen six-instruction register-only multi-helper block (`frozen_code_sha256` `4fe980f463d01c3fc413943b73860314d9c780c638acdc9bf50072290c89f778`). Two initial states produce ZF=1 and ZF=0. The final `JZ +0` has convergent taken and fall-through targets at `code_end`, so these states do not exercise distinct branch routing. The evidence covers this helper transport and allocator profile only; it does not cover maximum register pressure, pending flags, memory workloads, or a broader program corpus.

## Method and correctness gates

The release runner rebuilt and validated each variant separately, keeping at most one published mapping alive. Compile batches contain 32,768 calls and include build/decode, lowering, allocation, ARM64 emission, finalization, and destruction of each unpublished `CompiledBlock`. Publication and `PublishedCode` destruction are recorded separately. Execution repeats the full interpreter and directly calls `PublishedCode::execute_block` for native block entry over preinitialized states; cache lookup and dispatcher work are excluded. Setup, reset, and full-state validation occur outside timed intervals.

Each process records 20 alternating-order paired compile samples comparing the two budgets, and 20 interpreter/native execution pairs for each of the two cases and each budget. Calibration selected 8,388,608 common calls per side; the minimum retained sample floor is 200 ms. All three reports contain 20 compile pairs and 80 execution pairs, and every retained side passed the floor. Across the suite that is 60 compile pairs, 240 execution pairs, and 192 calibration attempts. Preflight and each process compare complete CPU state, exit, retired count, and remaining budget, allowing only the documented `BlockComplete`/`InstructionBudgetExhausted` exit normalization when full state matches, six instructions retire, budget is zero, and RIP equals `code_end`.

## Results

The table gives medians and full observed ranges over 60 retained samples per case/budget. Nanoseconds per call are recomputed from raw total nanoseconds divided by 8,388,608 calls; the report's integer-truncated per-call fields are not used. The ratio is raw native total divided by interpreter total.

| ZF=1 | 4 | 43.5195 (41.9681–44.9925) | 277.7745 (266.1791–284.4849) | 0.15652 (0.15152–0.16159) |
| ZF=1 | 0 | 44.3761 (42.5741–46.0665) | 279.0467 (266.2824–284.5165) | 0.15939 (0.15518–0.16340) |
| ZF=0 | 4 | 43.2271 (41.3485–47.8473) | 280.0786 (267.1955–289.5835) | 0.15416 (0.14990–0.17864) |
| ZF=0 | 0 | 45.2711 (43.4873–46.5666) | 281.2374 (272.7260–285.5179) | 0.16101 (0.15685–0.16384) |

Across the 60 paired compile samples, the budget0/budget4 compile-time ratio median was 0.99284 (range 0.95969–1.03218). The block used 3,052 emitted bytes at budget4 and 3,040 at budget0; both used a 288-byte frame. Budget4 assigned four register-home values and spilled ten temporaries, with three helper saves, three reloads, and three capture slots. Budget0 assigned no homes and spilled fourteen temporaries, with no helper saves/reloads or capture slots. Both variants crossed five helper boundaries.

The medians and ranges overlap. These measurements are descriptive for this one block and do not establish an allocator winner or justify a production change. Compilation, publication, destruction, and repeated execution are separate measurements and must not be summed into a synthetic cold-runtime value.

## Load and evidence limits

The benchmark ran on Apple M3 Max, macOS 26.7.1, aarch64, with `rustc 1.99.0 (b940084d7 2026-09-28)`, release profile. Source revision was `fa0c1329a432885432bb8ada3e45c50edc69b830`, source SHA-256 `049fdd15756203bfbb791f8ccb5462bbfaafe4c89fd0d30dc4839bd30ecd7aa9`; frozen code SHA-256 is listed above. Runtime `working_tree_dirty` is unknown (`null`): host metadata collection hit its two-second git-status timeout. Run1's executor exit code was not recoverable after its session expired; its report completed without a failure field and all sample floors passed. Run2 and run3 returned exit 0, with the same metadata timeout.

Point-in-time monitoring observed Stage2 cargo/rustc activity during portions of each process. Monitoring is reconstructed and not continuous; reports do not contain per-pair wall-clock timestamps, so load cannot be attributed to specific pairs. All samples are retained without trimming or retry. The Mac mini check is deferred until the end of Stage 3. This result does not cover that host, physical x86 comparison, memory workloads, or full Stage 3 performance acceptance.
