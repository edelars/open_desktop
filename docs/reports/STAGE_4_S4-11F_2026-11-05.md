# S4-11f — CPU-connected cross-page word MOV instruction fetch

## Scope

Architecture-approved. Implementation and focused verification are complete; independent `gpt-6.1-sol/high` review approved with no remaining P0—P3 findings. Add a separate opt-in
`PagedMovCrossPageWordFetchLong64V1` profile for exact `66 8B 03`
(`MOV AX,[RBX]`) at CPL0, `RFLAGS.AC=0`, and NXE=1. It uses one vCPU,
Long64, canonical48/physical36, four-level 4 KiB uncached paging. Instruction
starts at offsets `0xffe` or `0xfff` and crosses into a non-contiguous RAM code
page. The operand is wholly within a separate RAM page. The S4-11e profile
continues to reject cross-page instruction fetch. Code, operand and page-table
mappings have no aliases in this fixture.

## Acceptance contract

- Same-page instruction at `0xffd` succeeds even when the next code page is
  absent; crossing starts `0xffe` and `0xfff` succeed across RAM pages.
- Success updates AX, preserves RAX[63:16], other registers, flags and
  definedness, advances RIP by 3 and retires once.
- Second-page non-present/NX fetch faults report PFEC `0x10`/`0x11`, exact
  fault-byte linear address, original RIP and Fetch/Long64/Explicit context;
  CPU state and retirement are unchanged, completed A updates persist, D is
  clear, and the operand page is not walked.
- Hole/MMIO code-page outcomes do not call devices. A fetch fault takes
  precedence over an inaccessible operand. Negative encodings and profile
  boundaries are tested. A decoded word operand at data offset `0xfff` is
  rejected before a data walk. CR0-only `run` and `step` APIs reject the
  profile before fetch because matching CR4 is required.
- Cross-page operands, stores, exception delivery/CR2/retry, restart, JIT/TLB,
  IRQ and Linux remain excluded.
