# S4-14e: CR0.WP invalidation in the mutable diagnostic session

**Date:** 2026-11-06  
**Scope:** a MOV-only CPU transition profile and feature-gated machine handoff
for CR0.WP changes in `MutableTranslationProbeSession`. Parent S4-14 and Stage
4 remain open.

## Behavior

`step_mov_cr0_wp` admits only exact bare `MOV CR0,RAX`. It shares the already
accepted S4-12d CR0 commit logic but excludes that broader profile's store
allowlist, so the session's fetch-only memory adapter cannot misclassify a
store as a backend failure.

The mutable session admits CR0=`0x80010033` (WP=1) and `0x80000033` (WP=0),
with CR3/CR4/EFER unchanged. `execute_mov_cr0_wp` verifies CPU state against
the session before fetch, fetches through the pure walker without using the
resident cache, validates the retired `Cr0Write`, installs a replacement
snapshot and clears the one-entry cache before returning. This diagnostic
policy also clears on same-value CR0 writes. A direct `write_pte` does not
invalidate; a matching probe can still hit the prior entry until the retired
effect is consumed.

After WP=0, the existing INVLPG and MOV CR3 entries retain their S4-14d
admission requirement for WP=1 and reject before fetch. They are available
again after the session returns to WP=1. Post-retirement reconciliation errors
clear stale state and poison the session, matching S4-14d's explicit failure
contract.

## Limits

This is still a one-entry diagnostic translation session, not a production
TLB or tracked A/D path. Existing INVLPG and MOV CR3 profiles do not run while
WP=0. Reset, EFER transitions, generations, huge pages, PCID/global semantics,
JIT invalidation, DMA and SMP remain outside this slice; full S4-14 remains
open.
