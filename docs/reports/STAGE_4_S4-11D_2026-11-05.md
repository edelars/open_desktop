# S4-11d — CPU-connected cross-page instruction fetch

## Scope

This slice permits the exact bare `8B 03` (`MOV EAX,[RBX]`) form in the
existing `PagedMovCrossPageDwordReadLong64V1` profile to fetch its opcode and
ModRM across one 4 KiB boundary. The opcode is at linear RIP offset `0xfff`;
the next byte is on a non-contiguous RAM page, and the dword operand is on a
separate RAM page. The one-byte HLT boundary case is tested only at decoder
level and does not expand the CPU-connected allowlist.

The synthetic profile uses one vCPU, Long64, canonical48/physical36,
four-level 4 KiB uncached translation, CPL0 and NXE=1. It does not claim
general cross-page fetch, exception delivery/CR2/retry, cross-page stores,
JIT/TLB behavior, aliases or Linux support.

## Results

- Success across non-contiguous code pages completes the dword read, zero-
  extends EAX, advances RIP by 2 and retires once while preserving unrelated
  CPU state.
- Second-byte non-present and NX faults report PFEC `0x10`/`0x11`, the second
  byte's linear address, original RIP and Fetch/Long64/Explicit context. CPU
  state and retirement are unchanged; committed A effects persist, D stays
  clear, and the operand page is not walked.
- A hole and MMIO second code page retain their backend classifications and do
  not dispatch a device.
- Decoder-only one-byte HLT at page offset `0xfff` succeeds without fetching
  from the unmapped next page.
