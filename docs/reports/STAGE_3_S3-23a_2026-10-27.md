# S3-23a — bounded fixture cache invalidation between dispatch calls

**Date:** 2026-10-27. **Status:** bounded fixture slice implemented locally; independent review pending. This does not complete S3-23. No physical Mac mini testing was run.

## Scope and contract

Added `CodeInvalidation` notifications for committed backing-content version changes, mapping replacement/removal, and execute-permission changes. Both single-entry and bounded multi-entry caches remove affected inactive entries from lookup; multi-entry accounting is decremented and the published handle is dropped immediately. Backing invalidation follows backing identity across mapping aliases. Mapping notifications use address-space plus mapping identity.

The test fixture owner validates write range and nonwrapping version increment before mutation. On successful write it updates code bytes, advances backing version, and invalidates cache before making a later snapshot available. Injected failure leaves bytes, version, resident entry, and published handle unchanged. Safe borrowing limits notification calls to between completed synchronous dispatch invocations.

## Behavioral tests

- Changed code bytes invalidate/drop the old entry; next dispatch compiles an artifact with different emitted code and executes the new published ID.
- A backing-content notification invalidates entries through two mapping aliases sharing one backing ID.
- Failed write preserves code bytes, version, and cached hit.
- Mapping replacement at the same guest address drops the old entry and publishes the replacement.
- Execute-permission revocation drops the entry and the next dispatch fails on non-executable dependency before backend execution.
- An unrelated backing notification preserves the resident entry and next dispatch hits it.
- Mapping removal drops the published handle and returns resident code/metadata accounting to zero.

## Limits and checks

This is fixture-only invalidation after dispatch returns. It does not wire interpreter, V2 memory store, control-plane writers, production MMU, DMA, or devices. It does not serialize owner mutation that races compilation/publication after snapshot capture and does not retire active/self-modifying code; these remain S3-23/24/25 work. The V2 unsafe store API was not used for code writes. Stage 2 files were not changed, and Mini checks remain deferred.
