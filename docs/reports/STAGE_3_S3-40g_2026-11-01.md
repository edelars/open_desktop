# S3-40g — aliased ADD allocator diagnostic ledger addendum

**Date:** 2026-11-01  
**Status:** bounded measurement-ledger update; no speedup/default conclusion. The S3-32a diagnostic is complete; the broader S3-32 gate, S3-40, and S3-41 remain open.

This addendum records the completed S3-32a diagnostic for the frozen 27-byte
distinct-JZ fixture with aliased `ADD RAX,RAX` W64. It adds no measurement run
or new raw data. The exact protocol, fixture, timer boundaries, per-run records,
profile counts, and artifact bindings remain in the
[S3-32a source report](STAGE_3_S3-32a_2026-11-01.md) and its
[suite manifest](data/stage3/s3-32a/suite-manifest.json).

Three sequential release processes yielded 60 pooled paired samples per set;
all 360 timed sides met the 200 ms floor. Candidate/baseline ratios from
pooled pair totals had medians 0.9832762133712801 for compile,
0.9878736671103938 for JZ taken, and 0.9975100869584979 for JZ fallthrough.
All three ranges cross 1. These lower pooled medians are observations on one
fixture and support no speedup, allocator-winner, or default claim.

`958be7edf97dd0e421454630285dc4d6e711b2a7`, source SHA-256
`97d0130cb448f4834840fcbbeadb449067c6b05a0d664c4d99d03e7f1a4898c3`; its
SHA-256 is
`98e7fafa0a548e4eb56d77639949527be0b6c8b0b2fb076feb8e96d7b6165a65`.
The host was Apple M3 Max / macOS 26.7.1 / aarch64 / rustc 1.99.0. The release
build source tree was clean. Runtime `working_tree_dirty` is `null` because Git
status timed out, so the runtime tree is not asserted clean.

The candidate profile used 3,032 code bytes, a 272 B frame, 9 `ReadGpr`
operations, 13 temporary definitions, and 9 spills, versus 3,052 bytes,
288 B, 10, 14, and 10 for baseline. Helper capture/save/reload counts were
3/3/3 for both. This is a bounded allocator diagnostic, not general workload
evidence. The broader S3-32 gate remains open; Stage 2 activity is not a blocker,
and Mini checks remain deferred until the end of Stage 3.
