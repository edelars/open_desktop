# S4-35: staging зафиксированного Linux artifact

**Дата:** 2026-11-09
**Статус:** `staged (content hash verified; provenance not authenticated)`.
Подлинность (provenance) не подтверждена; подтверждён только content hash.

## Что сделано

- `tools/build/stage_linux_artifact.py` читает manifest S4-00a
  ([JSON](data/stage4/s4-00a-source-audit-2026-11-05.json)), для каждого из 10 файлов
  (4 бинарных артефакта, source `.deb`, source `tar.bz2`, три выбранных source-файла, config)
  проверяет наличие, размер и SHA-256 во входном каталоге
  (`work/vms/s2-00-ubuntu-26.04.1`). Только если проверены все файлы, они кладутся
  hardlink-ом (при ошибке - копией) в игнорируемый `work/stage4/linux-7.0.0-38.38/` с тем же
  относительным расположением, плюс маркер `STAGED.json`.
- Evidence: [s4-35-linux-artifact.json](data/stage4/s4-35-linux-artifact.json) (около 7 КБ):
  версия, для каждого файла путь, размер, sha256, verdict, способ staging; раздел
  `provenance`; ссылки на source/config evidence S4-00a; ограничения. Без временных меток,
  поэтому повторный запуск даёт побайтово тот же JSON и тот же набор файлов.
- `tools/build/test_stage_linux_artifact.py`: 14 тестов на временных каталогах с мелкими
  фиктивными файлами и собственной копией manifest; реальные файлы ядра тесты не трогают.
- В `docs/PROJECT_LAYOUT.md` в строку про `work/` добавлен `work/stage4/`.

## Что НЕ подтверждено (provenance)

`provenance.authenticated` всегда `false`. Открытые пункты (из `status` manifest S4-00a):
подписанный `.dsc`, `orig.tar.gz`, `diff.gz`, `Sources.xz`, `InRelease`,
`apt-provenance.json`, authenticated source-to-binary mapping, `full_source_provenance_passed`.
Source `.deb` скачан с зеркала Huawei без восстановленной подписанной цепочки.
Бинарные пакеты: archive.ubuntu.com, S2 profile
([STAGE_2_LINUX_PROFILE.md](STAGE_2_LINUX_PROFILE.md): URL `linux-signed/linux-image-…deb`,
историческая цепочка APT с InRelease fingerprint F6EC…C93C и `Packages.xz`, у которых
совпадали хеши `.deb`); цепочка APT однажды проверялась, но `InRelease`, `Packages.xz` и
`apt-provenance.json` сейчас отсутствуют, S4-35 её не перепроверял; PE/Authenticode не
проверен; `authenticated=false`. Совпадение
Build ID и 38 общих секций ELF (S4-00a) не доказывает, что эти source/config собрали
выбранные бинарники. Если рядом окажутся `.dsc`/`InRelease`, инструмент перечислит их как
`signed_chain_files_found_unverified`, но подписи не проверяет и `authenticated` не меняет.
Пункты не переносятся в «подтверждено». S4-00/S4-01 остаются открытыми.

## Отказы

Код возврата 1, сообщение с причиной в stderr, в staging ничего не пишется, evidence
не перезаписывается, ранее созданный `STAGED.json` удаляется:

- `sha256_mismatch` - содержимое не совпало с manifest;
- `truncated` - размер меньше pinned (если manifest его задаёт) либо после несовпадения
  hash структурная диагностика нашла усечение (обрыв ar-члена `.deb`, короткий `vmlinuz` по
  boot header, таблица секций ELF за концом файла, оборванный bz2-поток);
- `missing` - нет файла, включая source/config evidence (`tar.bz2`, `source/extracted/`);
- код 2 - ошибка manifest/аргументов.

Все сценарии покрыты тестами; сухой прогон с пустым `--input-dir` отвергает все 10 файлов.

## Как воспроизвести

```sh

```

## Ограничения

- Manifest S4-00a не содержит размеров файлов: размеры измеряются и записываются в evidence;
  критерий отказа - sha256 (и размер там, где он pinned); структурная диагностика
  вызывается только после несовпадения hash и лишь уточняет вердикт `truncated`. Тесты проверяют ветку pinned size
  (`size_bytes` в manifest), реальный manifest её пока не использует.
- Hardlink не замораживает файл: staged-файлы имеют тот же inode, что и `work/vms`
  (link count 2); если входной файл изменить на месте, staged-копия изменится вместе с ним.
  Потребитель (S4-37 и далее) обязан перехешировать файлы по `STAGED.json` перед
  использованием.
- Проверка zstd не выполняется (только stdlib): `data.tar.zst` внутри `.deb` не
  распаковывается; проверяются размер и sha256.
- `linux-buildinfo-*.deb`, `kernel-payload.zst`, `buildinfo-data.tar` в manifest S4-00a не
  закреплены, поэтому не стейджатся (config берётся из уже захешированного
  `source/extracted/config`).
- Staging не доказывает загрузку Linux, runtime-поведение или физический CPU.
- Большие файлы остаются только в `work/` (`/work/**` в `.gitignore`); в Git идут код и
  маленький JSON.
