# S3-40h — cached register recurrence performance ledger addendum

## Acceptance

Add the completed S3-36f full cached-dispatch versus interpreter measurement to
the provisional S3-40 ledger. Preserve its synthetic workload and full-call
timer boundaries, and record whether it supports a performance or policy
conclusion.

## Result

S3-36f measured two fixed helper-free `NativeRegisterV1` recurrences at 1, 64,
and 4,096 iterations. Three release processes retained 60 pairs per stratum;
all 720 timed sides passed the 200 ms floor. The median and full range of
paired native/interpreter ratios were:

| Stratum | Median | Full range |
|---|---:|---:|
| `a_1` | 4.7661 | 4.4800–5.1930 |
| `a_64` | 4.8890 | 4.4135–5.1931 |
| `a_4096` | 4.8938 | 4.6885–5.2546 |
| `b_1` | 3.7205 | 3.5583–3.9703 |
| `b_64` | 3.8092 | 3.2670–4.0133 |
| `b_4096` | 3.7805 | 3.4622–4.0340 |

Every observed ratio exceeded 1, so the interpreter was faster on all six
synthetic strata. The data support no useful native target scenario, cache
policy change, or runtime default change. First-dispatch durations include the
first compile, publication, and full execution; they are not compile-only
measurements and are not combined with warm-call results to infer break-even.
The workload does not represent a real guest application and does not close
S3-36, S3-40, or S3-41. Mini checks remain deferred to the end of Stage 3.

The evidence is tied to Apple M3 Max / aarch64 / macOS 26.7.1 / rustc 1.99.0,
profile commit `a5b368eab1d1cdfa3e47a28d0d7c1263b12978c7`. Build source tree
cleanliness is recorded as true; runtime Git status is unknown because its
two-second probe timed out. See the [S3-36f source report](STAGE_3_S3-36f_2026-11-01.md)
and [suite manifest](data/stage3/s3-36f-20261101/suite-manifest.json).
