# S3-25b — capacity-two V3/cache lifetime partial

## Scope

This slice exercises one V3 active-code artifact and one cached code block in a
two-slot `PublishedArenaBackend`. It adds no production lifecycle mechanism.
The existing slot handles and synchronous safe points provide the lifetime
boundary.

## Evidence

The fixture publishes active V3 artifact A and caches prefix A. A third V3
publication returns `CapacityFull` while both residents remain present and the
cached prefix still hits. Clearing the cache while V3 remains live releases
only the cached slot. After republishing the prefix, the V3 self-write commits
two instructions and returns `CodeInvalidated`; invalidation drops the cached
prefix while the V3 handle retains its slot. The released slot then holds a
fresh tail block, which executes the sentinel once without replaying the store.

Calling the original V3 handle after the source changed rejects before CPU,
RAM, or write-count effects. Dropping that handle releases its slot, allowing a
new artifact compiled from the updated source to publish and execute. The
fixture also requests STOP during this new artifact's successful store and
checks that the store commits while the tail stays unexecuted. Existing
`active_code_v3_guards_faults_aliases_and_committed_stop_are_precise` coverage
checks a store fault after the register prefix. Existing arena lease coverage
checks that backend drop does not release the mapping before the last handle
and that the mapping can reopen afterward.

## Limits

This is a synchronous single-vCPU capacity fixture. It does not add reentrant
or concurrent eviction, active retirement beyond the bounded V3 artifact,
SMP reclamation, a deferred deletion queue, or the complete S3-25 lifecycle.
Stage 2 files are untouched. Physical Mac Mini checks and long benchmarks
remain deferred to the final S3-21 gate.
