# S4-00b: Ubuntu kernel entry and paging-transition evidence

**Date:** 2026-11-06  
**Scope:** bounded boot-path evidence for the selected Ubuntu 26.04
`linux-image-7.0.0-38-generic` artifact. This does not accept parent S4-00 or
S4-01 and does not implement a loader.

## Selected binary and boot header

The exact `.deb` and `vmlinuz` are the artifacts recorded in the
[S4-00a source audit](STAGE_4_S4-00A_2026-11-05.md). The official Ubuntu
[Resolute package page](https://packages.ubuntu.com/resolute/amd64/linux-image-7.0.0-38-generic/download)
publishes the same SHA-256 as the local binary package. This checksum match
does not authenticate the locally recovered source package or establish a
source-to-binary mapping.

The local `vmlinuz-7.0.0-38-generic` header was parsed at the Linux x86 boot
protocol offsets. It has `HdrS`, protocol version 2.15, `relocatable_kernel=1`,
2 MiB kernel alignment, `init_size=0x044c1000`, `handover_offset=0x01072530`,
`loadflags=0x01` and `xloadflags=0x007f`. Its SHA-256 is
`9f55ef7253055a9cf68f8a04323c93dead2fca617386d842fbde9ca7b178b27e` and its
length is 17,320,328 bytes. The field values and offsets are included in the
[machine-readable manifest](data/stage4/s4-00b-kernel-entry-2026-11-06.json).

The [Linux x86 boot protocol §1.14](https://docs.kernel.org/arch/x86/boot.html#id14)
defines the 64-bit entry at the loaded protected-mode kernel address plus
`0x200`. In this `vmlinuz`, `setup_sects=39`, so the protected-mode payload
starts at file offset `0x5000` and the corresponding entry bytes are at file
offset `0x5200`; runtime entry is based on the payload's loaded address, not
that file offset. The loader loads the compressed kernel payload; kernel
startup decompresses it after entry. Entry state requires 64-bit mode with
paging enabled; identity maps covering the loaded kernel's `init_size` range,
zero page and command-line buffer; a GDT with 4 GiB flat `__BOOT_CS` selector
`0x10` (execute/read) and `__BOOT_DS` selector `0x18` (read/write);
`CS=__BOOT_CS` and `DS=ES=SS=__BOOT_DS`; interrupts disabled; and the
boot-parameter pointer in RSI. This is a viable direct-entry candidate; it
does not mean the existing project probe handoff satisfies the Linux boot
protocol.

## Reachable transitions in the recovered source snapshot

The version-matched source archive recovered from a Huawei Ubuntu mirror in
S4-00a contains these paths (its signed repository provenance remains
unavailable):

- `arch/x86/boot/compressed/head_64.S` has a 32-bit `startup_32` entry as well
  as the compressed-kernel `startup_64` entry at the protocol's `+0x200`
  location. The latter can be entered directly by a 64-bit bootloader with
  the required identity map and boot parameters. The former transitions to
  long mode and imposes its own low-memory boot-data requirements.
- `configure_5level_paging()` in `arch/x86/boot/compressed/pgtable_64.c`
  selects five-level paging when `no5lvl` is absent and CPUID leaf 7 ECX bit 16
  (LA57) is present. If the current CR4.LA57 state differs from the selected
  mode, the code uses a 32-bit-addressable trampoline to toggle paging levels.
- `arch/x86/kernel/head_64.S::startup_64` is the later decompressed-kernel
  entry. It expects the CPU already in Long64 with suitable identity-mapped
  tables; it is not the bootloader entry point.

For a first implementation restricted to four-level paging, the loader/CPU
profile must consistently prevent selection of LA57 (for example, omit LA57
from guest CPUID and enter with CR4.LA57 clear), or implement the required
transition/trampoline behavior. Passing `no5lvl` alone can still require the
trampoline if the initial CR4.LA57 state is set. A 32-bit boot entry is a
separate path and may be excluded only by making the supported direct 64-bit
entry explicit. These are constraints for the S4-00 machine contract and
S4-01 support mapping, not proof that the project currently implements them.

The header's `xloadflags=0x007f` includes the protocol's 5-level capability
bits. The recovered config has `CONFIG_X86_64=y`, `CONFIG_RELOCATABLE=y` and
`CONFIG_RANDOMIZE_BASE=y`; these facts do not by themselves prove an
authenticated source/config-to-binary relationship. Full provenance remains
open as recorded in S4-00a.

## Result and remaining work

This slice documents an exact binary header and the direct Long64 and
conditional paging-transition paths visible in the recovered version-matched
source snapshot. It rules out treating “64-bit entry” as sufficient evidence
that no 32-bit or LA57 transition exists. It does not select the final loader
contract, verify actual guest boot, provide initramfs/boot parameters, or close
source provenance. S4-00 and S4-01 remain open.
