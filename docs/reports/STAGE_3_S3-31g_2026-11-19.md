# S3-31g. Reusing resident entries across S0-09 RIP transitions

The S0-09 dispatcher already reuses a just-executed entry when a block
returns to its own RIP. The evaluated change also retains one verified
entry inside the current dispatch invocation. When the next RIP matches
that entry, the dispatcher uses its index and records a normal cache hit.
An LRU touch adjusts the saved index if another entry moves. Installing a
block discards the saved index before any eviction can shift it. Every
native entry still validates the code and dependency snapshot and checks
STOP, events and remaining budget. A RIP absent from the remembered
entries uses ordinary block construction and key lookup.

Two versions were measured against the same baseline `ac3395d`. One
updated the saved entry after every continued block. The other updated it
only when execution changes RIP, leaving the existing same-RIP
continuation without a memo update. The baseline and both candidates were
compiled in isolated trees with release settings and signed with the same
local Hardened Runtime and JIT entitlement.

The experiment uses the six countdown inputs from S3-35f/S3-36h and a
three-RIP control. The control bytes are `48 2B C1 74 04 75 00 75 F7`.
For 64 iterations it retires 254 instructions in 190 native blocks and
uses three resident entries. The retained-session driver checks full
CPU state, exit, budget, retirement, native block count and hit-only
cache activity. In the cold driver, a new `Session` starts with empty
accounting on every measured call and publishes one block per visited
entry. Code and logical metadata footprints match across builds.

The warm timer covers a full retained `Session::run` after initial
publication. The cold timer includes session construction, its two
empty-cache probes and the first RUN. Both compare against the same
interpreter work. State reset, result verification, teardown and process
launch occur outside the timed intervals.


## Matched release results

Each comparison has four rounds per timing mode. The baseline and
candidate run sequentially in each round, with reversed order in
rounds two and four. Each process scores eight JIT/interpreter pairs per
profile with alternating call order. Pilot calibration fixes one call
count per profile for both builds in that mode. The warm floor is 30 ms
and the cold floor is 16 ms.

Each comparison retained 896 warm sides and 896 cold sides. The shortest
warm/cold intervals were 57.317/21.452 ms for the version that updates
after every continued block and 56.447/25.889 ms for the version that
updates on RIP changes.

## Dispatcher decision

Keep the first version, which remembers the immediately preceding
executed entry. Both versions improve the two-RIP profiles. The first
has lower normalized warm medians for the 64-iteration one-RIP control
and the three-RIP control, and a narrower range on the long one-RIP
control. Moving the memo update to RIP changes still leaves a slowdown
on the long warm one-RIP inputs.

With the selected version, the warm JIT time for two RIPs is 9.05% and
7.36% of the previous dispatcher after normalization. The cold figures
are 20.36% and 7.52%. The JIT beats the interpreter in all 32 pairs of
each two-RIP profile in both modes. Warm JIT medians are 6.512 µs and
345.237 µs. Cold JIT medians are 17.334 µs and 346.575 µs. The raw
candidate/baseline JIT ratio also stays below 1 in all four rounds
for each of these comparisons.

The selected version's warm one-RIP medians increase by 2.30% and 4.16%
at 64 and 4,096 iterations after normalization. The raw warm ratios
also exceed 1 in all four rounds for both profiles. The long cold
one-RIP median increases by 1.31% after normalization and its raw
range crosses parity. The warm three-RIP range crosses parity
relative to the old dispatcher, and the interpreter remains faster on
that profile. The decision applies to the measured register-only
dispatch workloads. Wider shapes and direct linking remain open.

## Verification

The committed dispatcher matches the measured patch outside the test
module. The regression exercises A, A, B, A, B, B, A with FIFO and LRU
at capacities one and two. It checks exact handle sequences, hit,
publication and eviction counts, retirement and remaining budget.
`cargo test --offline -p od-jit -p od-host --lib` passed 501 JIT and 488
host tests, with two and one ignored respectively. Both archives passed
file-hash verification and reproduced the saved audits and runtime
patches on the baseline.

## Reproduction and evidence

The host used Apple M3 Max with 14 cores, 36 GB RAM, macOS 26.7.1
(25G241), and rustc 1.99.0. Each archive contains the exact measured
runtime diff, driver sources, binary identities, schedule, raw rows
and its offline audit.

Extract each archive's `files` into a separate scratch directory and
run `audit.py` there with Python. For a fresh measurement, copy the
Rust drivers and scripts to an empty scratch directory. Invoke that
directory's `build.sh` with `zsh`, `ac3395d`, and `baseline` or
`candidate` from the repository root. Build both variants, then run
`run.py` and `audit.py` with Python.
