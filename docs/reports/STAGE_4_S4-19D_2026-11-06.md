# Этап 4 — S4-19d: гостевой ремонт PTE и INVLPG

## Результат

В ограниченном сценарии гостевой обработчик после настоящего #PF при CR0.WP
исправляет leaf PTE через writable alias отдельной точной инструкцией
`MOV [RDI],RSI`, затем исполняет `INVLPG [RBX]` для исходного faulting GVA.
После этого срез останавливается до guest IRETQ и повтора исходной записи.

Тест подтверждает порядок tracked операций: начальный PTE `0xe001` получает
Accessed (`0xe021`) при page walk; гостевая запись устанавливает только RW,
сохраняя supervisor-only U/S=0 и Accessed (`0xe023`), с tracked Dirty для
writable alias; INVLPG ретируется
ровно один раз для исходного GVA. Данные по faulting адресу остаются прежними,
CR2 и RBX/RCX сохраняют исходные значения. После старта faulting сценария
хост не исправляет PTE.

ISA selector ограничен exact encoding `48 89 37`, Long64, CPL0 и профилем
пейджинга с WP. Он проверяет canonicality каждого fetch адреса до обращения к
памяти и отклоняет пересекающий страницу qword до operand access. Fixture
задаёт RDI alias и RSI значение PTE; сам selector не проверяет семантику PTE.

Tracked execution path не кеширует translations. Сценарий доказывает выполнение
гостевого INVLPG и ремонт PTE, но не необходимость invalidation для видимости
записи и не eviction stale TLB. Guest discard кода ошибки, IRETQ, retry и
успешный commit faulting data остаются в S4-19e; родительский S4-19 открыт.
