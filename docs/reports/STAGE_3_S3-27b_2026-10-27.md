# S3-27b — faulting next fetch after a committed two-site pair

**Date:** 2026-10-27. **Status:** bounded native fixture verification complete;
independent review pending. This is not a production MMU/dispatcher result.

## Scenario and evidence

The ARM64-only `od-host` fixture executes each exact two-site artifact once:
store→load and load→store. It begins with a six-byte compiler `CodeView`, while
the fixture `GuestMemory` independently maps byte `0x90` at `A+6`. The fixture
then injects an architectural fault from `GuestMemory::fetch` at that valid
address. The native-returned CPU/RAM is used directly for the interpreter step.

For each pair sequence, `od_isa::execute::run` on an independent initial copy
runs the two successful instructions and the same third-step fault. It reports
the exact fault and `instructions_executed == 2`. `execute::run` on the native
entry's returned state/RAM reports the same fault with zero continuation
instructions. Complete CPU state (including flags and RIP), RAM and exact
vector/error-code/linear-address payload match; retries do not repeat the pair
data callbacks. Unmapped and backend fetch errors are checked after both pair
sequences and remain host errors with zero continuation instructions.

Real interpreter `RunConfig` calls at `A+6` verify a zero budget returns
`InstructionBudgetExhausted` without fetching, and a set STOP closure returns
`StopRequested` without fetching. Replenishing budget or clearing STOP then
returns the architectural fetch fault with zero continuation instructions.

## Boundaries

This proves only the fixture boundary between a generated pair entry and a
subsequent interpreter fetch. It does not implement a production dispatcher,
owner-backed MMU, code-page mapping/invalidation, or cross-block fault delivery.
The compiler's six-byte buffer ending at `A+6` remains separate from the valid
guest fetch mapping and injected fetch result. No `od-isa` or Stage 2 files,
benchmark, or physical x86/Mac mini run were involved.
