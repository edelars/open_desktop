# S3-20ai — RSP data with an RBP-base direct displacement

## Scope and implementation

Admitted exact singleton forms `48 8B/89 65 ib` (disp8, length 4) and
`48 8B/89 A5 id` (disp32, length 7). ModRM is `mod=01/10, reg=4, rm=5`;
address is qword RBP plus the signed displacement and data is qword RSP.
Address calculation remains owned by the decoded `MemoryOperand`. Generic
GPR validation, SIB forms, pair/V3 profiles, frame layout and host ABI are
unchanged. Existing RBP-data `mod=10/rm=5` and RIP-relative `mod=00/rm=5`
remain distinct.

## Evidence

- Descriptor tests cover both operations, both lengths, disp8 -128/-1/0/127,
  disp32 MIN/-1/0/MAX/128, exact source bytes and decoded metadata. Partial
  windows, indexed SIB, forbidden prefixes and malformed ModRM/data fields
  reject. The direct V2 and shared IR site descriptors must agree.
- Host direct V2/shared IR/interpreter parity compares full CPU/RAM state,
  callbacks and retirement for both operations. Tests independently compute
  `target = entry_rbp.wrapping_add_signed(displacement)`; entry RSP and RBP
  differ. Loads commit RSP after success; stores preserve all bits of a
  noncanonical old RSP payload.
- For disp32, changing only source byte 6 from 1 to 2 with fixed RBP=0 yields
  exact callbacks at `0x01000000` and `0x02000000`. A separate `mod=00/rm=5`
  control verifies RIP-relative addressing from NextRip.
- Noncanonical RBP causes exact #SS before a callback for load/store, with
  CPU/accounting unchanged. Store callback STOP keeps the committed write.
  Address/permission/backend behavior continues to use the shared decoded
  helper semantics.
- Dispatcher tests verify entry STOP and budget zero make no publication or
  callback, and both budget and STOP split at the actual next RIP. The next
  `[RSP]` access uses the loaded canonical RSP without repeating the first
  effect. A noncanonical loaded RSP commits, then `[RSP]` faults #SS at its own
  RIP without a second callback. Invalid encodings and partial windows stop
  with no effects.
- On macOS/ARM64, the x19 canary covers successful execution of both lengths.
