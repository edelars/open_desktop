# S3-40aa RUN with and without fetch and decode on M1 Pro

The experiment compared historical `d24865d` and current `5275d67` at
budget 2 over the same 2,400 frozen S3-34a inputs as S3-40z. Each build
ran the original public RUN and two diagnostic variants. Both variants
follow the same RUN and STEP code through an erased callback at the
existing decode boundary. The pass-through variant calls the original
decoder from that callback. The other variant returns instructions
decoded before timing at the two expected RIPs.
[Earlier RUN budget measurements](STAGE_3_S3-40z_2026-11-19.md)

The source of public RUN stays byte-identical to each pinned Git
revision. The extra functions can affect the linked binary layout. A
separate untimed run checked complete CPU state, RAM, ordered data
accesses, two retirements, budget exit and defined flags for every input
on all three variants. It also checked the identical six ordered FETCH
callbacks and access contexts in public RUN and pass-through. The
predecoded variant made zero FETCH callbacks. The timed variants use
the same fixture memory without fetch instrumentation.

Pilots set 864,000 calls per interval for `store_then_load` and 853,200
for `load_then_store`. Six paired process rounds alternated build and
sequence order and covered all six variant permutations per process.
The run retained 432 intervals and 370,915,200 calls. The shortest timed
interval was 78.270 ms, above the 45 ms floor.

The pooled current-minus-historical gap was 162.2 and 163.0 ns with
public RUN, 157.6 and 157.6 ns with pass-through, and 176.8 and 176.5 ns
with predecoded instructions. The gap persists through the diagnostic
path that bypasses fetch and decode. Both callback variants include
the costs of the indirect call, and the predecoded path includes the
instruction lookup. These are whole-call comparisons for the two
sequences. Attribution among RUN control, STEP entry guards and
instruction execution remains open.

## Environment and reproduction

MacBookPro18,3, Apple M1 Pro, eight logical CPUs, macOS 14.6.1 (23G93),
Xcode 15.4 (15F31d), Rust and Cargo 1.99.0. The two release binaries
target macOS 14.0 with the standard `aarch64-apple-darwin` CPU settings
and passed strict signature verification with Hardened Runtime and
`allow-jit`. The M1 Pro was on AC power. All 14 pilot and scored
processes confirmed UID 501, nice −5 and QoS `0x21`. During 24 preflight
probes, CPU idle ranged from 86.4% to 99.6%. During scoring, ten probes
ranged from 67.5% to 86.9%, with a median of 86.2%.

Extract the archived `files` and place the harness scripts under
`work/tmp/s3-40-decode-boundary/` in a repository with both pinned Git
revisions and the S3-40m and S3-40w input archives. Use an isolated Cargo
home with the lockfile dependencies. Build in the harness directory with
the following settings.

```sh
export MACOSX_DEPLOYMENT_TARGET=14.0
unset RUSTFLAGS CARGO_ENCODED_RUSTFLAGS CARGO_BUILD_RUSTFLAGS
unset CARGO_TARGET_AARCH64_APPLE_DARWIN_RUSTFLAGS
zsh build.sh historical
zsh build.sh current
zsh check.sh
```

Follow the archived `README.md` to monitor a fresh `python3 run.py run-NAME`
and package its results. `python3 offline_audit.py /path/to/evidence.json.gz`
reproduced the saved audit. The archive retains 79 files including all
timings, original and compiled source bindings, exact hook generator,
untimed check receipts, and load logs.
