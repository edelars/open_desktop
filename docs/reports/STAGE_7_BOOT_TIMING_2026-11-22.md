# Замер времени загрузки Linux до /init (EFI, 1 vCPU, собственная прошивка)

Дата: 2026-11-22. Стенд: Mac (Apple Silicon, 14 ядер, 36 ГиБ), runner — release-сборка из 29c1c07.

## Что замерено и как

- Маршрут: собственная UEFI-прошивка (ROM 4 МиБ, `build_firmware.py`), ESP с BOOTX64.EFI (ядро Ubuntu 7.0.0-38 как есть) и INITRD.IMG, режим `--cpu-loop unified`, одна CPU (cpu_count = 1 в handoff; это ограничение текущего кода, см. ниже).
- Входы (SHA-256): ядро `9f55ef7253055a9cf68f8a04323c93dead2fca617386d842fbde9ca7b178b27e` (совпадает с приёмкой S7-31); initramfs `b88cd99616611124e4616aea4274d49b4bb48bf421ae798215390e251a499ac9` (собран `build_s7_31n_initramfs.py`).
- Маркер «до /init»: строка `Run /init as init process` в COM1. Бюджет задаётся в инструкциях (`--budget`), по нему runner останавливает гостя.
- Диагностика выключена. Проверено по коду и по JSON короткого прогона (2 млн инструкций): `unified.call_trace = null`, `journal = null`, `framebuffer = null`, `unified.checkpoints = []`. Трассировка включается только флагами `--trace-call`/`--trace-system-table`, дамп кадров — `--framebuffer-out`/`--framebuffer-dir`, чекпоинты — `--mark-rip`; ни один из них в замерах не задан.

## Результаты

Шесть прогонов запущены параллельно (одновременно 6 процессов на 14 ядрах). Все завершились по бюджету (`exit = budget_exhausted`), кроме прогона на 5 млрд, который остановлен вручную на 3485 с (после маркера, без результата).

Вывод по замеру:
- Маркер `Run /init as init process` достигнут между 2,4 и 3,2 млрд инструкций. Точный момент внутри интервала не измерен: отдельного прогона до маркера на одном процессе не сделано.
- Прогон на 3,2 млрд: 2474 с wall при параллельной нагрузке. Средняя скорость ≈ 1,29 млн инстр./с.
- Одиночный прогон (100 млн инструкций, без параллельной нагрузки): 49,9 с ≈ 2,0 млн инстр./с. Значит параллельные прогоны замедляли друг друга примерно на треть.
- Оценка времени до /init на одном процессе: 2,4…3,2 млрд инструкций при ≈2,0 млн инстр./с ≈ 1200…1600 с (≈20…27 мин). Это оценка по скорости одиночного прогона, а не измерение.
- В COM1 между 3,2 и 4,0 млрд байт не прибавилось: гость после /init ждёт (efivars, без дальнейшего вывода), конец сценария не достигнут.

## Ограничения и что не сделано

- **2 vCPU через EFI не запускаются.** Маршрут собственной прошивки передаёт в handoff `cpu_count = 1`, опции числа vCPU в runner нет (S6-18b открыт). Замер с 2 vCPU требует реализации S6-18b; без неё такой прогон невозможен.
- Точное время до /init (в секундах) требует одного прогона без параллельной нагрузки с бюджетом, ограниченным концом интервала (2,4…3,2 млрд). Это ≈20–30 мин на одном процессе; выполнить по команде.
- Вывод COM1 содержит самотесты прошивки (`OD-FW S7-05 …`) и вывод ядра. Это поведение прошивки, а не диагностика runner.
- Не проверялось, сколько из времени занимают самотесты прошивки: отдельного маркера для них нет.

## Воспроизведение

Скрипты в scratchpad сессии: `boot_timing.py` (сборка), `boot_run.py` (один прогон), `parallel_runs.py` (параллельные бюджеты). Артефакты прогонов: `par-<бюджет>m/com1.bin`, `par_results.json`.
