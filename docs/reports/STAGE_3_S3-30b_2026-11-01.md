# S3-30b — distinct-branch allocator-configuration evidence

**Date:** 2026-11-01  
**Status:** three bounded release runs completed; S3-30 remains open.

## Scope and fixture

The opt-in `allocator-cost-branch-routing` diagnostic compared `register_homes=4` with diagnostic budget `0` on the frozen `distinct-jz-fallthrough` register-only multi-helper fixture. The 27-byte input has SHA-256 `72210fb82b0ffa9f88f10f63697a1051347d07587e3569028947119726fac8c7`. Its first five instructions preserve the S3-30a prefix, followed by `JZ +10` and an admitted `MOV RBX,imm64` suffix. With base RIP `0x1000`, ZF=1 exits the emitted block at `0x101b`; ZF=0 exits at the fallthrough RIP `0x1011`.

These are one-block Jcc exits. The fallthrough MOV and any following dispatcher/downstream execution are outside the measured native call. The results describe the cost of these two allocator configurations on this fixture; they do not isolate marginal spill cost, evaluate an allocator algorithm, identify a winner, or select a production default.

Each scored binary was built from source revision `35da9aaf4234b4673b53605a0e8cb853ad9960dc`, source SHA-256 `23ec849569f653f87d630f3488c849836ecff18c0e7db465c3b5a83bf071b824`, with build source tree reported clean. Executable SHA-256 was `2fd3c82678708b87348ec9bab26379d81e9e86e4034c62c256f9400a6b165b81`.

The runtime capture revisions differ across runs (`305dd65fdbbc8a51543577dee363c03c2a8053c5`, `09232bc1de9f6d24d4e0da84b6ed9af15bee494b`, and `de3b4f333ebd1a4f4e93806fcd94a6aa28f03472`) as documentation/evidence commits advanced. Runtime `working_tree_dirty` is `null`, not a clean-tree assertion. The run logs record that runtime Git status collection timed out after two seconds. This does not alter the common build-source fingerprint or permit attributing any timing variation to the runtime revision.

## Protocol and timer boundaries

Three sequential process reports each retained 20 compile pairs and 20 budget4/budget0 native pairs for each of the two branch inputs. Pair order alternated: each 60-sample set contains 30 budget0-then-budget4 pairs and 30 budget4-then-budget0 pairs. Every native side executed 8,388,608 calls; this is 503,316,480 calls per budget and branch stratum across 60 sides. Each compile side performed 32,768 calls, or 1,966,080 calls per budget across 60 sides. Warmup was 64 calls per publication, excluded from the execution timer.

All 360 measured compile and execution sides passed the 200 ms floor. The minimum compile side was 289,931,459 ns; the minimum native execution side was 345,072,526 ns. No samples were trimmed. The per-run reports record the complete raw paired totals and their order.

Compile timing includes block build/decode, lowering, allocation, ARM64 emission/finalization, and destruction of each unpublished `CompiledBlock`. Publication and published-mapping drop are timed and reported separately. The repeated direct `PublishedCode::execute_block` timer includes the safe host wrapper/context setup, generated entry, and result copy/decode; state creation and full-state/exit validation are outside. A single `MAP_JIT` mapping is live at a time. The timed block stops at Jcc; there is no cache lookup, dispatcher traversal, or timing of the fallthrough suffix. This is not pure guest-instruction time.

## Limits and next gate

This evidence is a bounded ARM64 release measurement of a single emitted block and two allocator configurations. It does not cover dispatcher or cache behavior, execution beyond the Jcc exits, broader live-value/pressure combinations, a general allocator comparison, physical x86 equivalence, or production policy. S3-30 remains open for broader workload correctness and cost evidence; the production allocator and default are not selected by this report. Mac mini checks remain deferred to the end of Stage 3.
