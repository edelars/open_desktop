# S4-27e — ordinary APIC quantum and pending IRQ during handler

## Result

Added `DiagnosticVcpuSession::run_apic_quantum` with its own
`DiagnosticApicQuantumResult`. At a caller-certified completed boundary it
checks STOP first, then selects one APIC-eligible vector when IF is set. A
successful entry acknowledges the exact vector and attempts one ordinary
handler instruction with the session's normal interpreter configuration. If
IF is clear or no vector is eligible, it attempts one ordinary instruction.
The existing `rflags_defined` and optional caller-configured TSC source remain
in use.

The end-to-end scenario delivers IRQ A, posts IRQ B as a self-IPI while A's
handler is active, and confirms B remains pending while IF is clear. The handler
performs guest EOI and IRETQ; the next APIC quantum delivers B before fetching
the interrupted instruction. A second EOI/IRETQ then resumes the original
stream. Successful entry remains committed if handler execution faults,
returns unsupported or stops. Delivery abort is terminal, may preserve a frame
write prefix, leaves the vector pending and blocks retry.

STOP before APIC selection marks the session Stopped and preserves the
request. Partial REP work invalidates the tracked instruction boundary until
ordinary execution retires the instruction. This operation requires explicit
Clear STI shadow; broader STI/MOV SS/NMI arbitration remains outside this slice.

## Boundaries

This is explicit one-budget interpreter polling. It does not provide automatic
arbitration inside longer runs or JIT blocks, event-queue dispatch, MOV-SS/NMI
handling, HLT integration, automatic EOI/IRET, board registration or Linux
acceptance. Parent S4-27 and Stage 4 remain open.
