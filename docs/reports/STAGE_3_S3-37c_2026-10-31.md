# S3-37c — deterministic FIFO16 invalidation and runtime lifecycle

**Status:** three sequential native Apple Silicon release runs completed in a
confirmed quiet window; their JSON records passed lifecycle assertions.
Independent source and evidence reviews were clean. This is bounded
between-call cache lifecycle evidence; S3-37 remains partial.

## Scope and schedule

`od-bench cache-lifecycle` uses the production FIFO16 cache and its existing
published arena. Each run prepares the frozen S3-17 corpus, then executes the
same 27-step schedule:

1. Dispatch 16 distinct admitted one-entry cases to fill FIFO16.
2. Issue controlled stop-RIP at the target's current RIP. Require
   `Runtime(StopAddress)`, zero blocks and retirement, unchanged full guest
   state/budget, and unchanged lookup counters, current resident values, and
   allocator slots. This does not exercise asynchronous `StopRequested`.
3. Repeat the newest target and require a real hit.
4. Dispatch a seventeenth key and require exactly one FIFO eviction.
5. Between synchronous calls, invalidate the target backing at version 2.
   Dispatch different admitted bytes under that version and require a miss,
   compile, publication, and interpreter-distinct result; repeat and require a
   hit.
6. Advance execution-context generation from 1 to 2 and require automatic
   cache flush followed by recompile.
7. Explicitly clear, check current entries/code/metadata are zero and all 16
   allocator slots are available, drop the runtime, construct a fresh runtime,
   then execute the target with context generation 3 and require a fresh miss.

Every guest dispatch checks complete CPU state (with the admitted fixture's
undefined-RFLAGS mask), dispatch exit, native block count, retirement, and
remaining budget against its interpreter oracle. The controlled stop-RIP step
instead checks the no-execution state and accounting contract described above.
The exact 27-step schedule, code hashes, dependency identities/versions,
context IDs, before/after counters, full recorded CPU states, and raw elapsed
values are in each JSON record.

Backing invalidation is the existing cache API called between dispatch calls.
This does not demonstrate production owner notification, guest-write SMC,
active-code invalidation, guest faults, simultaneous arenas/SMP, or leak-free
behavior. STOP itself does not clear the cache; explicit clear and runtime drop
are separate operations. Per-action times below are diagnostic observations for
this schedule and support no performance claim. Total run time includes corpus
preparation and is not a lifecycle timing.

Two earlier three-run batches were excluded: the first because Stage 2 tests
appeared between process snapshots and possible overlap could not be ruled out;
the second because a later rustfmt-only change altered the build source hash.
Their raw files and notes remain under ignored `work/tmp/stage3/` directories.

## Results

All three runs passed their internal assertions and the saved JSON checks:
27 steps, correct stop-RIP/`StopAddress` with no cache change, one invalidated
target, changed interpreter-visible result, full clear with 16 available slots,
and successful fresh-runtime execution. The original target retires 3 guest
instructions and ends with `RIP=25`, `RBX=11157442094209678835`; changed code
retires 2 and ends with `RIP=13`, `RBX=12206589113854719474`. The changed-code
repeat and context-generation recompilation match that changed result.

| Lifecycle state | Current entries | Current code bytes | Current logical metadata bytes | Actual free slots | Relevant counter result |
|---|---:|---:|---:|---:|---|
| FIFO filled | 16 | 20,244 | 48,468 | 0 | 16 misses/compiles/publications |
| After controlled stop-RIP and repeated target | 16 | 20,244 | 48,468 | 0 | STOP adds no lookup; repeat adds one hit |
| After overflow replacement | 16 | 20,624 | 49,056 | 0 | one new compile/publication and one eviction |
| After target backing invalidation | 15 | 19,140 | 45,671 | 1 | exactly one entry removed |
| After changed code compile and hit | 16 | 20,244 | 48,468 | 0 | one miss/compile/publication, then one hit |
| After context generation 2 | 1 | 1,104 | 2,797 | 15 | flush then one miss/compile/publication |
| After explicit clear | 0 | 0 | 0 | 16 | high-water remains 16 / 20,624 B / 49,056 B |
| Fresh runtime after execution | 1 | 1,484 | 3,385 | 15 | fresh counters: one miss/compile/publication |

Current values above were read from current cache counters and
`backend.available_slots()`. High-water values are separately retained by the
cache and were not used to derive current residency. The original runtime's
high-water remained 16 entries, 20,624 code bytes, and 49,056 logical metadata
bytes in each run.

Per-action elapsed nanoseconds (runs 1 / 2 / 3) were:

| Action | Raw samples (ns) |
|---|---|
| Backing invalidation | 542 / 416 / 459 |
| Changed-code dispatch after invalidation | 5,667 / 6,125 / 5,667 |
| Explicit cache clear | 583 / 250 / 500 |
| Runtime/arena drop | 10,625 / 5,667 / 6,292 |
| Fresh runtime construction | 3,625 / 3,709 / 3,583 |

These are single observations within one bounded schedule per process, not
paired performance measurements. Total runner durations, including corpus
preparation, were 14.922 s, 15.499 s, and 15.398 s.
