### S10-02. Контракт дисплейного устройства

- Статус: ревью пройдено (два прохода; blocker и major нет). Кода нет. Открытые блокеры для S10-08 — dword MMIO (§13.1).
- Ревью 1 (архитектурное):
  - **major:** §7.2/§7.4 описывали код `feat/s9-stage`, который отстаёт от `main` на 20 коммитов (merge-base `336083a`). Условия безопасности «без callback» теперь сверены с `main`: page generations только для `Ram`; `write_bytes` проверяет и повышает поколения до копирования; `code_page_generation` и `tracked_code_snapshot` требуют `Ram`; JIT-путь `f300ef8`. Записано, что S10-03 сверяет эти условия с собственной базой, а правка «Committed writes» в `MACHINE_CONTRACT.md` делается по тексту `main`.
  - **minor, исправлены:**
    - A/D-эффекты walk при `DeviceError` (§9.2);
    - `COUNTER_EXHAUSTED` как шаг 5 в `MODE_COMMIT` (§5);
    - класс доступа «RO + doorbell» (§4);
    - `ACTIVE` в предикате «кадр есть» (§6, §10.1);
    - согласование `FB_BASE`/`FB_SIZE` с картой при сборке шины и типизированный handle (§7.3);
    - имя `BusAccessError::UnmappedPhysical`;
    - ширины 36/64 (§2.1);
    - блокер S10-08 (§13.1).
- Файлы: [DISPLAY_DEVICE.md](../specs/DISPLAY_DEVICE.md) (новый); строка «Экран» в [VIRTUAL_BOARD.md](../specs/VIRTUAL_BOARD.md) — ссылка на контракт и фиксированные адреса.
- Конфигурация v1: один экран, `BGRX8888` (байты B,G,R,X; LE), stride = width × 4, до 4096×2304, `FB_SIZE` = 37 748 736 байт (36 MiB). Лимиты проверяются до умножения: после проверки произведение < 2^26; без проверки переполняется даже `u64`.
- Адреса без PCI: framebuffer `0xF800_0000` + 36 MiB, регистры MMIO `0xFC00_0000` + 4 KiB; диапазон `0xF800_0000–0xFC00_0FFF` зарезервирован под дисплей. Существующие карты `od-machine` его не пересекают; общей карты платы ещё нет — открытый вопрос.
- Регистры: 32 бита, LE, только dword-доступ. `WIDTH`/`HEIGHT`/`FORMAT` — запрос; `MODE_COMMIT` применяет режим атомарно или пишет код в `STATUS.COMMIT_ERROR`; `FRAME_GENERATION` — doorbell «кадр готов»; host не сканирует по таймеру. Внутренний `frame_mode_epoch` не даёт показать старую память в новом режиме.
- Backing: выбран вариант (б) — новый `MemoryRegionKind::Framebuffer`. Backing в `PhysicalMemory`, вне `RamLimits`, без committed-write callback. Fetch и page-table структуры в регионе запрещены (backend-ошибка), поэтому кеши кода и трансляций от его байтов не зависят. Вариант (а) отвергнут: callback на каждый пиксель, учёт в `RamLimits`, риск показать регион ОС как RAM. Места кода для S10-03 перечислены в §7.4 контракта.
- Ошибки: исправимые гостем (коды в `STATUS`, RO/резерв игнорируются) и backend (`DeviceError::UnsupportedWidth`/`Misaligned`/`UnsupportedSpace`, выход за окно — ошибка шины). Сверено с разделами «Синхронная MMIO/PIO bus» и «Committed writes» `MACHINE_CONTRACT.md` и с `enum DeviceError` в `bus.rs`.
- Источник формата: UEFI 2.11, GOP `PixelBlueGreenRedReserved8BitPerColor`. Страница uefi.org вернула 403, номер подраздела не перепроверен.
- **Блокер для S10-08** (не закрыт): tracked paged-путь CPU делает в MMIO только qword-записи, а контракт требует dword. Без dword MMIO-профиля probe не написать.
- Открытые вопросы (§13 контракта): подтвердить адреса после карты S4-00/S4-30; reset не сбрасывает `generation`; состав snapshot.

### S10-05. Транспорт кадров VMHost → UI — ревью пройдено (2 прохода)

- Файлы: [protocols/control/FRAME_TRANSPORT_V1.md](../../protocols/control/FRAME_TRANSPORT_V1.md) (новый, нормативный); обзорная ссылка в [docs/specs/CONTROL_PROTOCOL_V1.md](../specs/CONTROL_PROTOCOL_V1.md). Control v0/v1 не изменены. Кода нет.
- Решения:
  - Память создаёт VMHost: `shm_open` со случайным именем, сразу `shm_unlink`, один `ftruncate`. Дескриптор передаётся один раз сообщением `ANNOUNCE` с `SCM_RIGHTS`; путь и имя не передаются.
  - Слотов 2…4, рекомендация 3 — гипотеза до S10-10. Слот кратен 16 KiB, наибольший — 36 MiB. Максимум памяти — 151 011 328 байт, меньше 2^28.
  - Seqlock на `generation` описателя (`0` — слот недействителен). Writer: relaxed-запись `0`, `fence(release)`, пиксели и поля, release-запись `N`. Reader: acquire-чтение, затем каждое поле описателя ровно один раз relaxed-чтением в локальную копию. Проверки и копирование идут только по копиям, без гонки и TOCTOU. Затем копия пикселей, `fence(acquire)`, relaxed-перечитывание. `reader_claim` — подсказка, корректность от неё не зависит. Swift выполняет атомарные операции через C-shim со встроенными функциями clang `__atomic_*`.
  - Уведомления идут отдельным протоколом `ODFT` v1 (`VERSION`, `HELLO`, `ANNOUNCE`, `MODE`, `FRAME`) по тому же унаследованному `socketpair`, fd 3, в дисплейном режиме VMHost. Control v1 не расширялся: его текст запрещает неизвестные виды и профили без смены версии. На `HELLO` с чужой версией VMHost отвечает 16-байтным заголовком `VERSION` со своей версией и закрывает соединение. UI переходит в `INCOMPATIBLE` и показывает версию; закрытие без заголовка — `DISCONNECTED`.

  - **Переполнение:** отказ новому (`QueueFull` host-у), старые не сбрасываются. Семантику «важно последнее» даёт объединение по типу: не больше одного `MODE_REQUEST` на экран.
  - **Запрос смены разрешения** — событие `MODE_REQUEST`. Ответ: `RESPONSE_SEQ_LO/HI` + `REQUEST_RESPONSE` (`ACCEPT` или `REJECT` с причиной). `ACCEPT` принимается, только если активный режим уже равен запрошенному. Режим меняет только `MODE_COMMIT`.
  - **Включение событий:** `DRIVER_PROTOCOL` ← 1 (новый класс «RW с проверкой»). До этого механизм инертен, host получает `NoDriver`.
  - **Опрос:** прерываний нет. Каждый шаг читает `DRIVER_PROTOCOL` (если `0`, значит был reset, и драйвер повторяет инициализацию), затем `EVENT_PENDING`. Период 100 мс номинально, не больше 200 мс; выборка до опустошения; не чаще 10 мс. Период — гипотеза до замеров S10-21/S10-22.
  - **`CAPS`** = `0x3`:
    - бит 0 `MODE_LIST`, бит 1 `EVENTS`;
    - бит 2 `CURSOR` (S10-14) и бит 3 `SECOND_SCREEN` (S10-15) зарезервированы, равны `0`;
    - смещения `0x200–0x2FC` и `0x300–0x3FC` предварительно отведены этим блокам без регистров.
  - **`VERSION` = 2. Совместимость:** строгое надмножество версии 1. Новые регистры только в бывшем резерве, остальное без изменений. Гость проверяет `VERSION ≥ N` и игнорирует неизвестные биты `CAPS`. Probe S10-08 по плану `VERSION` не сравнивает, поэтому работает без изменений.

### S10-14. Курсор — спецификация, ревью пройдено, код не начат

- Статус: спецификация написана 2026-11-06, **ожидает ревью**. Код не начат: в `od-machine`, display host ABI, VMHost и `apps/macos` курсора нет. Чекбокс плана не отмечен.
- Файлы:
  - [docs/specs/DISPLAY_DEVICE.md](../specs/DISPLAY_DEVICE.md) — новый раздел 15 «Курсор (S10-14)»; строка статуса в заголовке, строка бита 2 в таблице 14.3, ссылка в разделе 12;
  - [protocols/control/FRAME_TRANSPORT_V1.md](../../protocols/control/FRAME_TRANSPORT_V1.md) — новый раздел 10 «Версия 2: курсор»; абзац о версии 2 в начале, пометка в разделе 9.
- Решения:
  - **Устройство.** Блок `0x200–0x2FC` при `CAPS` бит 2, `VERSION` остаётся `2`, `CAPS = 0x7`. 13 регистров: пределы, форматы, `CURSOR_STATUS`, staged-форма (`WIDTH`/`HEIGHT`/`FORMAT`/`HOTSPOT`), загрузка образа (`IMAGE_INDEX` с автоинкрементом, `IMAGE_DATA`, `IMAGE_COMMIT`), `CURSOR_POSITION` (упакованная пара X/Y hotspot, проверка по активному кадру), `CURSOR_ENABLE`. Новые коды `0x0C–0x0F`, все ошибки исправимы гостем.
  - **Размер и формат образа:** до 64 × 64 (по умолчанию в Linux DRM; 16 384 байт — одна гранула транспорта), `BGRA8888_PREMUL` (код 2, предумноженная альфа, как у плоскости курсора DRM; одно смешивание Metal, точное при `A ∈ {0, 255}`). Монохромные и XOR-курсоры не поддержаны.
  - **Память образа:** только регистровое окно. Буферы `staging` и `active` по 16 KiB внутри устройства, не в карте гостя и не в Framebuffer, без committed-write callback. Commit атомарно копирует `staging → active`. Отвергнуты отдельный RAM-подобный регион (`VERSION = 3`, новый вид региона, разрыв формы), место за кадром в Framebuffer (нет места при 4096 × 2304) и DMA из RAM. Цена — `W × H` MMIO-записей на смену формы, перемещение — одна запись.
  - **Счётчики:** `cursor_seq` и `shape_seq` только для host, независимы от `generation` и `mode_change_count`. Курсор не меняет поколение кадра и не публикует кадр.
  - **Передача на host:** frame transport **v2**. Отдельная область курсора в разделяемой памяти: 3 описателя в странице заголовка, 3 слота образа по 16 KiB, свой seqlock со словом публикации `cursor_seq`. Сообщение `CURSOR` (`kind = 5`, 16 байт payload, без пикселей). Поле в описателе кадра отвергнуто: курсор потребовал бы нового `generation` или переписи под тем же `generation`, которую seqlock не замечает. Образ в сокете отвергнут: принцип «пиксели не по сокету» и рост границы очереди. Слоты кадров начинаются с `65536`.
  - **Наложение:** второй draw в том же render pass. Прямоугольник `pos − hot` обрезается по кадру и переводится в пиксели drawable той же функцией, что кадр (`ViewportLayout`). Scissor = видимый viewport. Смешивание `one`/`oneMinusSourceAlpha` без записи alpha (байт X кадра не меняется). Ошибка не больше одного гостевого пикселя; в 1:1 наложение точное.
  - **Совместимость:** драйверы без курсора бит 2 игнорируют, probe S10-08 не затронут. UI и VMHost разных версий транспорта получают `INCOMPATIBLE`.
- Проверки спецификации (2026-11-06): `python3 -c` подтвердил, что 13 регистров курсора попарно различны, кратны 4, лежат в `0x200–0x2FC` и не совпадают с 23 смещениями версии 1 и 273 смещениями версии 2. Ни одно смещение версий 1 и 2 не лежит в блоке, `0x300–0x3FC` не тронут. Раскладка транспорта v2: описатели курсора кончаются на 640, слоты образа на `0x4000/0x8000/0xC000`, `total_size` для 2–4 слотов, `MIN_TOTAL = 98 304`, `MAX_TOTAL = 151 060 480`, все кратны 16384, граница очереди 168 байт.
- Проверки для реализации записаны в DISPLAY_DEVICE.md §15.13 и FRAME_TRANSPORT_V1.md §10.9. Среди них оба критерия плана: offscreen дамп с курсором в известной позиции против эталона скрипта (генератор — отдельный шаг в `tools/build/`, допуск 0 при `A ∈ {0, 255}`) и тест «перемещение курсора не меняет поколение кадра» на уровнях устройства и транспорта.

  - **сообщения** (заголовок 16 байт, фиксированные длины): `VERSION` 16, `HELLO` 16, `ACCEPT` 24, `FOCUS` 24, `USAGE` 24, `MOTION` 64, `STATUS` 48 байт. Неизвестный `kind` — ошибка протокола;
  - **клавиатура и кнопки** — USB HID usage (страницы `0x07` и `0x09`) по HID Usage Tables 1.7 (USB-IF, 26.01.2026; на usb.org/hid это текущая редакция), не PS/2. Таблица `kVK_*` → usage — код S10-16; примеры сверены с `Events.h` SDK 27.0 и PDF HUT 1.7;
  - **мышь** — относительные `dx`/`dy`, колесо и `AC Pan` в 1/120 щелчка, плюс абсолютный пиксель гостя с `mode_change_count` и размером кадра. Абсолютная часть служит тестом границы и заделом; absolute pointer device не делается;
  - **координаты** — `ViewportLayout` S10-11 без копии формул: точка AppKit → физический пиксель по `Dw/Bw` с переворотом Y → центр пикселя → `guestPixel`. Ошибка относительно нарисованного текселя ≤ 1 гостевого пикселя. Устаревшая после смены режима позиция сбрасывается VMHost, это не ошибка;
  - **фокус** — `FOCUS LOST` отпускает все клавиши и кнопки на обеих сторонах;
  - **очереди** — UI и VMHost по 256 записей × 64 байта = 16 384 байт (всего 16 496 байт у UI, 16 544 у VMHost). Перемещения объединяются с хвостом и не теряются. Нажатие получает отказ и счётчик (`STATUS.rejected_downs`), если не остаётся запаса `2h + 5`. Отпускание и перемещение в фокусе отказа не получают по инварианту `free ≥ 2h + m + 1`. Без потребителя память не растёт.
