# S4-27b — guest EOI, same-CPL IRETQ and resume

## Result

The S4-27a handler now performs a real guest Dword store of zero to Local APIC
EOI at `0xFEE000B0` through the existing `IdentityMemoryAdapter → MachineBus`
MMIO route. The caller explicitly invokes
`DiagnosticVcpuSession::run_same_cpl0_iretq`, which uses the existing
`SameCpl0ValidFrameV1` ISA profile with a one-instruction budget. A successful
return restores the same-CPL five-qword frame and the next ordinary
`session.run(1)` executes the interrupted instruction.

The end-to-end fixture tests every low-nibble alignment of the original RSP.
It validates restored RIP/RSP/CS/SS/RFLAGS and a resumed RAM sentinel load. With
the line deasserted, one guest EOI clears Remote IRR. With the line held, the
EOI accepts one new level request into IRR; its CPU delivery waits until the
caller's next explicit boundary.

An IRETQ fetch/frame/CS/SS read abort does not commit the candidate CPU, does
not undo the already committed guest EOI, and makes the session terminal so
the same EOI/IRETQ sequence cannot be retried automatically.

## Boundaries

This is a caller-driven same-CPL0 diagnostic path over flat identity RAM. It
does not add automatic interrupt polling, paged IRETQ, privilege transitions,
HLT wakeup, general IF/STI/MOV SS/NMI scheduling, JIT integration, board
registration or Linux acceptance. Parent S4-27 and Stage 4 remain open.

The frame and flag behavior use the existing
[CPU same-CPL IRETQ contract](../specs/CPU_CONTRACT.md#s2-27k--exact-long64-same-cpl0-iretq).
