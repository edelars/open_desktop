# ADR-0006: оболочка настольного приложения — сборка, песочница, модель и размещение CLI

- **Дата:** 6 ноября 2026 года.
- **Статус:** **предложен, ждёт архитектурного ревью** (S11-00). Решение (б) дополнительно ждёт подтверждения владельца: **подтверждение владельца: ожидается (да/нет/дата)**.
- **Связанные документы:** [план этапа 11](../plans/STAGE_11.md), [отчёт этапа 11](../reports/STAGE_11_REPORT.md), [архитектура](../ARCHITECTURE.md) (разделы 3, 4, 6, 7, 9), [карта проекта](../PROJECT_LAYOUT.md), [apps/AGENTS.md](../../apps/AGENTS.md), [состояние VM](../specs/VM_STATE.md), [протокол control v1](../../protocols/control/CONTROL_PROTOCOL_V1.md), [ADR-0001](ADR-0001-dependencies-and-boundaries.md), [политика зависимостей](../policies/DEPENDENCIES.md).

## Вопрос

Как собирать `OpenDesktop.app` вместе с VMHost, как приложению и VMHost получать доступ к файлам, которые выбрал пользователь, как устроен CLI управления машинами и где он лежит в репозитории — так, чтобы приложение оставалось тонкой оболочкой ([ARCHITECTURE §3](../ARCHITECTURE.md)), а `libod_host.a` линковался только в VMHost.

## Контекст

На 2026-11-06 (коммит плана `5e9e4e9`) в `apps/` нет ни Xcode project, ни `Package.swift`. Всё собирается прямыми вызовами `xcrun swiftc` из [apps/macos/README.md](../../apps/macos/README.md) и [apps/vmhost/README.md](../../apps/vmhost/README.md). Тесты `apps/macos/Tests/*.swift` и `apps/vmhost/Tests/*.swift` — исполняемые файлы с `@main`, не XCTest. Исходник VMHost называется `main.swift` и содержит `@main`. Общие файлы (`ControlFrame.swift`, `InputProtocol.swift`, `VMHostLaunch.swift`, `FrameReader.swift`, …) лежат в `apps/macos/Sources/` и `apps/vmhost/Sources/` и подключаются к разным бинарникам явными путями. Локальная сборка `.app` для smoke — [vmhost_app_bundle_smoke.sh](../../tests/system/vmhost_app_bundle_smoke.sh); VMHost подписывается с `com.apple.security.cs.allow-jit` ([vmhost-smoke.entitlements](../../apps/vmhost/Configuration/vmhost-smoke.entitlements)).

Control v1 — унаследованный `socketpair`, без listener и без дескрипторов в сообщениях. Control v2 (S11-03) добавит единственное сообщение `ATTACH_RESOURCE` с одним дескриптором `SCM_RIGHTS`. [ARCHITECTURE §3](../ARCHITECTURE.md): постоянный daemon не нужен; CLI на диаграмме идёт к приложению тем же контрактом управления; фоновая жизнь машин после выхода приложения — отдельное осознанное решение.

## Решение

### (а) Сборка

**Swift Package `apps/Package.swift` плюс скрипт `tools/build/build_app_bundle.py`, собирающий `.app`.** Пакет — один корневой, без внешних зависимостей. Цели:

| Цель | Тип | Содержимое и правило |
|---|---|---|
| `ODShared` | библиотека Swift | Общий код приложения и CLI. Состав — по списку задачи S11-05a (он источник для этой цели): `ControlFrame`, `InputProtocol`, `InputQueue`, `VMHostLaunch`, `FrameReader`, `HIDUsage`, `InputTranslation`, `Viewport`; позже `ControlV2` и каталог ошибок. **Не** содержит `FrameTransport` и **не** линкует `libod_host.a`. Путь исходников — **`apps/macos/Sources/Shared/`** (создан в S11-05a). Публичный API помечен `public`, потому что цель — отдельный модуль; UI-конец `InputChannel` остаётся в цели viewer, а не в `ODShared`. Зависимость: `ODAtomics` (`FrameReader` использует атомики из `FrameTransportAtomics.h`) |
| `ODAtomics` | C-цель | Путь `apps/macos/Sources/ODAtomics/`: `FrameTransportAtomics.h` (в `include/`) и `ODAtomics.c` (`_Static_assert` на lock-free 32- и 64-битные атомики); нужна Swift-целям, которые читают/пишут кадры атомарно. Объявления C ABI движка (`host_abi.h`, `session_abi_v1.h`, `display_abi_v1.h`, `VMHostABI.h`) в неё **не** входят: иначе приложение и CLI получили бы их транзитивно через `ODAtomics` |
| `ODHostConstants` | C-цель | Путь `apps/macos/Sources/ODHostConstants/`: `ODHostConstants.h` (в `include/`, только `include/open_desktop/host_abi.h`: `OD_HOST_ABI_VERSION_V0`, `OD_FRAGMENT_MAX_LENGTH_V0`) и `ODHostConstants.c` (компилирует заголовок как C). Зависимостей нет. Нужна `open-desktop-launcher-smoke`, чтобы тот не получал транзитивно `session_abi_v1.h`, `display_abi_v1.h` и помощников VMHost (`vmhost_shm_create_excl`); добавлена в S11-05a по замечанию ревью. `libod_host.a` не линкует |
| `ODHostABI` | C-цель | Путь `apps/vmhost/Sources/ODHostABI/`: `VMHostABI.h` (в `include/`, объявления C ABI движка для VMHost) и `ODHostABI.c` (компилирует заголовок как C). Зависит от `ODAtomics`. Используют `od-vmhost` и его тесты (`OpenDesktopVMHostTests`); `libod_host.a` не линкует (её линкует только `od-vmhost`; тестовый бандл линкует её транзитивно, потому что зависит от `od-vmhost`) |
| `od-vmhost` | исполняемая | Зависимости: `ODShared` (`ControlFrame`, `InputProtocol` нужны VMHost), `ODAtomics`, `ODHostABI`. Единственная цель, линкующая `target/<profile>/libod_host.a` (linker settings). Исходники: `InputChannel`, `FrameTransport`, `VMHostMain`. `VMHostABI.h` подключается через C-цель `ODHostABI`, а не через `ODAtomics`. Исходный `main.swift` переименован в `VMHostMain.swift` (в цели не может быть `main.swift` вместе с `@main`) |
| `OpenDesktop` | исполняемая | Приложение (SwiftUI/AppKit), зависит от `ODShared`; движок не линкует. Путь `apps/macos/Sources/App/`; VMHost внутри bundle по пути `Contents/Helpers/od-vmhost` (источник по структуре bundle не найден, выбор по соглашению); `platforms: .v14` — решение владельца |
| `odctl` | исполняемая | CLI (решения в, г), зависит от `ODShared`; движок не линкует |
| тестовые цели | test | Перевод существующих исполняемых `@main`-тестов; выбор XCTest или Swift Testing — в S11-05a по доступной toolchain |
| `open-desktop-display-viewer`, `open-desktop-launcher-smoke` | исполняемые | Сохраняются на время перехода для существующих smoke |

`.app` собирает `tools/build/build_app_bundle.py`: раскладывает бинарники из `swift build -c release`, пишет `Info.plist`, подписывает ad-hoc `codesign --options runtime`, VMHost — с `allow-jit`, приложение и CLI — без. Все пути — аргументами.

**Не принятые альтернативы.**

1. *Xcode project (`.xcodeproj`).* Даёт готовые подпись, entitlements, ресурсы и XCUITest. Отвергнут для этапа 11 как выбор по умолчанию: `project.pbxproj` плохо читается в построчном diff при ревью (суждение, замеров нет); текущая сборка уже идёт через CLI toolchain (`xcrun swiftc`), и пакет — её прямое продолжение с графом целей; пустой проект запрещён ([apps/AGENTS.md](../../apps/AGENTS.md)). Цена отказа: нет XCUITest и нет автоматической подписи Developer ID (этап 12). Пересмотр — на этапе 12 или при необходимости UI-автоматизации; общие цели тогда подключаются к Xcode как пакет, переносить код не придётся.
2. *Оставить прямые вызовы `swiftc`.* Нет графа зависимостей, общий код подключается копированием путей, тесты не запускаются одной командой. Не выдерживает рост числа бинарников (приложение, VMHost, CLI, viewer).
3. *Общий код копировать в каждую цель.* Нарушает DRY ([AGENTS.md](../../AGENTS.md)) и принцип «один исходник».

### (б) App Sandbox и доступ к файлам

**Рекомендация для этапа 11 (требует подтверждения владельца): приложение и VMHost без App Sandbox; пути пользователя (ISO, диски вне bundle, общие папки) приложение получает только через `NSOpenPanel` (для CLI без UI вопрос открыт — см. (в)), хранит как bookmark и передаёт VMHost открытыми дескрипторами через `SCM_RIGHTS` (`ATTACH_RESOURCE`, S11-03); VMHost подписывается с `com.apple.security.cs.allow-jit`.**

Обоснование:

- VMHost исполняет JIT и, как встроенный инструмент, был бы обязан наследовать песочницу приложения (источник выше). Совмещение песочницы с JIT и с передачей доступа дочернему процессу не проверено ничем в репозитории.
- Единственный канал доступа к пользовательским файлам — открытый дескриптор. **Гипотеза (не проверена; проверяется в S11-04, smoke):** открытый дескриптор не зависит от того, как система (TCC, песочница) приписывает доступ процессу, поэтому VMHost, получив его, может работать с файлом независимо от собственных прав. Если гипотеза верна, VMHost работает только с тем, что приложение явно ему передало. Пути пользователя через control не идут ([план, §4.2](../plans/STAGE_11.md)).
- Приложение закрывает доступ (`stopAccessing…`), как только дескриптор передан и продублирован в VMHost (при условии, что `SCM_RIGHTS` работает как предполагается — тоже гипотеза S11-04).

**Соотношение с правилом [ARCHITECTURE §4](../ARCHITECTURE.md)** («Парсер не должен принимать неограниченные длины, дескрипторы или пути»). Правило запрещает неограниченный приём. Передача дескриптора в `ATTACH_RESOURCE` ограничена: она допустима только в одном типе сообщения; число дескрипторов в сообщении — ровно один; роль ресурса (ISO, диск, общая папка) — значение закрытого перечисления, которое проверяет получатель; размеры и число подключённых ресурсов должен ограничить контракт S11-03 (он ещё не написан, ограничения станут нормативными только там). Это ограниченная передача, а не «неограниченный дескриптор». Пути же через control не принимаются вообще, поэтому в альтернативе 2 нарушается правило именно по путям. Формулировка §4 не различает «неограниченный» и «ограниченный, но допустимый» дескриптор — см. открытый вопрос 2.

Оговорки, которые рецензенту и владельцу нужно видеть прямо:

1. **Расхождение с формулировкой плана.** Документация описывает security-scoped bookmark как средство App Sandbox. **Гипотеза (не проверена):** без песочницы `withSecurityScope` не нужен, хватает обычного bookmark (устойчивого к перемещению файла). Доступ к файлу после перезапуска приложения при этом зависит от TCC — это не исследовано, особенно для каталога по умолчанию `~/Documents/Open Desktop/`. Формат хранения в `config.plist` (S11-02) от выбора не меняется: это `Data` bookmark; различается лишь опция при создании и разрешении. Проверка — S11-04 и S11-06 (smoke перезапуска); до неё формулировки плана про bookmark (S11-02, S11-04, S11-06) остаются непроверенными.
2. Источник для «доступ по bookmark привязан к процессу приложения» в строгой форме не найден: документация говорит о других sandboxed приложениях. Решение не опирается на это утверждение: оно опирается на гипотезу, что дескриптор — единственное, что VMHost получает, и что его достаточно для работы с файлом.
3. `SCM_RIGHTS` на macOS и поведение TCC для дочернего процесса — не проверены (таблица выше). До smoke S11-04 решение считается гипотезой.
4. Mac App Store требует App Sandbox. Дистрибуция через Mac App Store в этапе 11 не планируется; решение пересматривается при её появлении.

**Альтернативы.**

1. *Полная песочница для приложения, VMHost наследует песочницу (embedded tool).* Безопаснее по умолчанию и совместимо с Mac App Store, но: JIT в наследуемой песочнице и права на `MAP_JIT` не проверены; пользовательские каталоги потребуют `files.user-selected.*` и security-scoped bookmark для каждого ресурса, и всё равно дескрипторы нужны; CLI вне `.app` лишается доступа. Откладывается; пересмотр — вместе с решением о дистрибуции (этап 12).
2. *Без песочницы, пути передаются строкой, VMHost открывает файлы сам.* Проще, но зависит от того, как TCC и права процесса приписываются дочернему VMHost (не исследовано), расширяет доверенную поверхность VMHost путями из control и нарушает правило [ARCHITECTURE §4](../ARCHITECTURE.md) в части «неограниченные … пути» (парсер control не должен принимать пути; ограниченный дескриптор в `ATTACH_RESOURCE` этому правилу не противоречит — см. выше).
3. *Отдельный XPC-сервис для файлового доступа.* Добавляет транспорт и именованные endpoints, которых нет ([ARCHITECTURE §4](../ARCHITECTURE.md)); не нужен, пока `socketpair` с дескрипторами достаточен.

Статус решения (б): **рекомендация; подтверждение владельца: ожидается (да/нет/дата).** Пока подтверждения нет, задачи, зависящие от (б) (S11-03 `ATTACH_RESOURCE`, S11-05b entitlements), не должны считать его принятым.

### (в) Модель CLI

CLI `odctl` — не демон и не слушает endpoint. Команда **`odctl run <bundle> --script FILE`** сама запускает VMHost (унаследованный `socketpair`, как приложение), ведёт его по control v2 до конца сценария и завершает. `list`, `create`, `delete`, `inspect` работают с bundle напрямую, без VMHost; исключение — `create --disk`: она запускает VMHost для `PREPARE_DISK` и завершает его. Это не нарушает «один VMHost на машину» по проекту: lock задуман как `flock` на `<bundle>/lock`, который держит VMHost; второй VMHost на тот же bundle получает `busy`, а lock снимается ядром при смерти процесса. Файл `<bundle>/lock` ещё не существует — он **появится в S11-02/S11-04**; S9-04 закрыт частично (advisory lock), поэтому это проектное утверждение, а не описание реализованного ([план §4.1](../plans/STAGE_11.md)). Если приложение уже держит машину, `odctl run` получает `busy` и сообщает об этом; он не подключается к работающему VMHost приложения.

**Вне этапа:** связь CLI ↔ приложение (пунктир на диаграмме [ARCHITECTURE §3](../ARCHITECTURE.md)), фоновая жизнь машин после выхода CLI/приложения, центральный supervisor.

**Альтернативы.**

1. *CLI как клиент приложения (по диаграмме).* Требует listener/endpoint, идентификации клиента и протокола «CLI ↔ приложение», которых нет; CLI не работал бы без запущенного приложения. Откладывается до отдельного решения о supervisor.
2. *Постоянный daemon/supervisor.* [ARCHITECTURE §3](../ARCHITECTURE.md): «не требуется для первого продукта»; меняет жизненный цикл (восстановление соединений, фоновая работа).
3. *Свой протокол CLI.* Противоречит правилу «тот же контракт управления» (gate G3). CLI обязан использовать `ODShared`/control v2.

Остаётся открытым для S11-13/`CLI.md`:

- как `odctl` находит бинарник `od-vmhost` (рядом с собой в `.app`, аргументом или переменной окружения) и как он подписан для запуска VMHost;
- **как `odctl run` без UI получает ISO и диски вне bundle.** Правило (б) «пути пользователя приложение получает только через `NSOpenPanel`» к CLI неприменимо: пути приходят из аргументов или сценария. Не решено, кто открывает файл (сам `odctl` по пути из аргумента/сценария — тогда это явное исключение из правила (б), расширяющее его до «путь из доверенного аргумента командной строки пользователя»), как путь превращается в дескриптор для `ATTACH_RESOURCE` и должен ли сценарий (`--script`) вообще содержать пути или только ссылки на ресурсы, уже подключённые аргументами. Это открытый вопрос; до решения (б) сформулировано только для приложения.

### (г) Размещение CLI

**`apps/cli/Sources/`** (цель `odctl`; каталог создаёт S11-13, а в машиночитаемый перечень каталогов [PROJECT_LAYOUT.md](../PROJECT_LAYOUT.md) его добавляет та же задача). CLI — часть оболочки macOS-продукта (управление машинами пользователя тем же контрактом), а не инструмент разработчика.

**Альтернативы.**

1. *`tools/` (например `tools/runner/src/`).* По [PROJECT_LAYOUT.md](../PROJECT_LAYOUT.md) `tools/` — исполняемые инструменты разработчика; `tools/runner` — headless-запуск CPU-фрагментов, а не управление VM по control v2. Смешение размыло бы границу «продукт ↔ инструмент».
2. *Внутри `apps/macos/Sources/`.* Смешивает UI-код и неинтерактивный процесс; `odctl` не должен тянуть AppKit/SwiftUI. Общая часть уже вынесена в `ODShared`.
3. *Rust-бинарник в `crates/`.* Нарушает «`crates/` — только библиотеки», дублирует клиент control v2 на втором языке (два независимых набора кода одного контракта, [apps/AGENTS.md](../../apps/AGENTS.md)).

## Последствия

- `Package.swift` создан в S11-05a (реализовано в рабочем дереве, ревью пройдено; см. отчёт). Команды `xcrun swiftc` из README остаются для сборок без пакета, кроме тестов: они стали XCTest-случаями и запускаются через `swift test --filter` (отступление от плана S11-05a, отмечено в README). Отступлений от решения (а) по зависимостям нет: `open-desktop-launcher-smoke` зависит от `ODShared` и `ODHostConstants`, а не от `ODHostABI`; `libod_host.a` линкует только `od-vmhost` (тестовый бандл `OpenDesktopVMHostTests` получает её транзитивно через `od-vmhost`). Наличие этого ADR, каталога `apps/cli/` или пакета не закрывает ни одну задачу сверх S11-05a.
- `libod_host.a` линкуется только в `od-vmhost`; приложение и CLI зависят от `ODShared` и не знают про движок.
- Все утверждения про macOS API в этом ADR привязаны к таблице источников; пункты со статусом «источник не найден» — гипотезы до проверки smoke на реальном macOS (S11-04).
- Дистрибуция, Developer ID, нотарификация и обновления остаются этапом 12; Mac App Store ADR не рассматривает.

## Открытые вопросы

Ждут решения архитектурного ревью, владельца или указанной задачи. Нормативные документы в рамках S11-00 не менялись.

1. **Расхождение с ARCHITECTURE §2 и §9 по Xcode.** Решение (а) отказывается от Xcode project как способа сборки, а [ARCHITECTURE §2](../ARCHITECTURE.md) (таблица стека, «Cargo workspace + Xcode») и §9 («Xcode — за app/helper, entitlements, подпись и notarization») закрепляют Xcode. Кто и когда обновит §2/§9 — не определено; предложение: после принятия ADR архитектурным ревью, отдельной правкой архитектуры.
2. **Уточнение ARCHITECTURE §4.** Правило «Парсер не должен принимать неограниченные длины, дескрипторы или пути» не различает неограниченный приём и ограниченную передачу одного дескриптора с ролью в типе сообщения (см. решение б). Предложение архитектурному ревью: уточнить §4 (например, «дескриптор допускается только в перечисленных типах сообщений, в ограниченном числе и с проверяемой ролью»).
3. **План S11-05a и `VMHostABI.h`.** **Решён в S11-05a (реализация ждёт принятия).** Строка S11-05a в [плане этапа 11](../plans/STAGE_11.md) помещала `VMHostABI.h` в `ODAtomics`, что противоречило решению ADR (заголовок относится к `od-vmhost`). Теперь `VMHostABI.h` лежит в C-цели `ODHostABI`, а `ODAtomics` содержит только `FrameTransportAtomics.h`; строка плана приведена в соответствие.
4. **Источник доступа CLI к пользовательским файлам** — см. решение (в), S11-13.
5. **Гипотезы S11-04:** поведение `SCM_RIGHTS` для файла и каталога на macOS; независимость доступа по дескриптору от TCC/песочницы; поведение обычного bookmark без песочницы после перезапуска, в том числе для `~/Documents/Open Desktop/`.

## Условие пересмотра

- Владелец отклоняет рекомендацию (б) или выбирает песочницу.
- S11-04 показывает, что `SCM_RIGHTS` с дескриптором файла/каталога на macOS не работает так, как предполагает S11-03; либо выясняется, что доступ дочернего VMHost зависит от TCC иначе, чем предполагалось.
- Появляется требование UI-автоматизации (XCUITest) или подписи Developer ID, которые SwiftPM плюс скрипт не покрывают, — тогда пересмотреть выбор между Xcode project и пакетом (этап 12).
- Принято решение о фоновых машинах или центральном supervisor — пересмотреть (в).
