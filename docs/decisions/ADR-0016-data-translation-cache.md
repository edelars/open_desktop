## Вопрос

Каждое чтение и каждая запись данных в цикле набора CPL0 делают полный четырёхуровневый обход таблиц (`PagedMovMemoryAdapter::access_with`, [paged_memory_adapter.rs](../../crates/od-machine/src/paged_memory_adapter.rs):5165 → `access_long64_2m_with_mmio` → `access_long64_4k_internal_windowed`, [page_walk.rs](../../crates/od-machine/src/page_walk.rs):1887 → `walk_long64_4k_with_writer`, page_walk.rs:1015). Можно ли запоминать результат обхода данных так же точно, как `FetchTranslationCache` (S4-13) запоминает обход выборки, и где этот кеш должен жить?

## Факты

1. **Доля в профиле** (PERF-02, текущий HEAD с кешем декодирования PERF-10; `work/cpu-core-perf/*-base-profile.json`). Окно ядра (15 108 отсчётов): `access_with` включая — 1682 (11,1 %), `walk_long64_4k_with_writer` включая — 1194 (7,9 %), своё — 515 (3,4 %); `PagedMovMemoryAdapter::read` включая — 963 (6,4 %), `write` — 752 (5,0 %); `PhysicalMemory::load_u64` своё — 679 (4,5 %, сюда входят и чтения записей таблиц). Окно прошивки (15 121): `access_with` — 2119 (14,0 %), обход — 1344 (8,9 %). Верхняя граница выигрыша кеша (обход исчезает целиком при 100 % попаданий) — порядка 8–9 % времени; для прототипа «только чтение» — заметно меньше. Это гипотеза, а не выигрыш: засчитывается только K4.
2. **Обход сам ставит accessed** на каждом уровне до проверки прав (page_walk.rs:1159–1210, compare-and-replace S6-25) и не ставит dirty. Dirty листа ставит только запись после проверки региона: `commit_leaf_dirty` (page_walk.rs:929, вызов page_walk.rs:2020). Ошибочный обход возвращает ошибку и ничего не кеширует.
3. **Все зафиксированные записи RAM цикла** — запись гостя, коммиты A/D обходчика, кадры исключений — идут через замыкание `watch` (paged_memory_adapter.rs:2764), которое уже сообщает их `FetchTranslationCache::note_write`. Регион `Framebuffer` пишет без уведомления ([physical_memory.rs](../../crates/od-machine/src/physical_memory.rs):114–117), поэтому таблицы в нём недопустимы для кеша.
4. **Снимок прав** — `Long64ProbeConfig` (page_walk.rs:69–170): полные CR0, CR3, CR4, EFER, сравнение по равенству (`derive(Eq)`). Цикл пересобирает его при каждом `TranslationContextChange` (CR3, NXE в EFER: `handle_set_exit`, paged_memory_adapter.rs:4290) и тут же сбрасывает кеш выборки (paged_memory_adapter.rs:3474–3480).
5. **Время жизни кеша выборки в этом пути** — один вызов цикла (один квант): `run_cpl0_set_paged_2m_ram_observed_with_sweep` создаёт новый кеш на каждый вызов (paged_memory_adapter.rs:2434). Поэтому DMA устройств между квантами (`nvme.service` и др., [firmware_board.rs](../../crates/od-machine/src/firmware_board.rs):4076–4085) не может оставить устаревшую запись. PERF-07 постоянный кеш выборки не вводит.
6. **Диагностика.** Счётчики обходов `WalkCounter` ([fetch_cache_report.rs](../../crates/od-machine/src/fetch_cache_report.rs):111) создаются на каждый вызов всегда (paged_memory_adapter.rs:2799) и считают обходы в `access_with` (paged_memory_adapter.rs:5191–5206), `access_vector` и `read_integer_for_write`; плата суммирует их только при `fetch_cache_report_enabled` (firmware_board.rs:3810–3812, 4086–4094). Наружу их выводит только команда `linux` runner: `DiagnosticEnv` ([tools/runner/src/linux_direct.rs](../../tools/runner/src/linux_direct.rs):319–337), переменная `OD_FETCH_CACHE_STATS=<путь>` (linux_direct.rs:2405, 2457), файл-спутник (`fetch_cache_stats_json`, linux_direct.rs:2511; запись — 2638) и ключ `fetch_cache_stats_sidecar` в отчёте (linux_direct.rs:958). В `boot-firmware` ([tools/runner/src/firmware_boot.rs](../../tools/runner/src/firmware_boot.rs)) переменная не читается, плата не просит отчёт, JSON unified-прогона (firmware_boot.rs:1417–1636) счётчиков не содержит. При включённом отчёте плата выключает кеш декодирования (firmware_board.rs:4024–4029), поэтому диагностический прогон медленнее, но счётчики обходов данных от кеша декодирования не зависят.

## 1. Диагностика (пункт 1 PERF-11) — задание исполнителю

Цель — три числа на бюджетах 300 млн и 3,2 млрд инструкций, до любого кода кеша: обходов данных на инструкцию (чтение, запись), доля повторных обращений к той же странице, записи в кадры таблиц на миллион инструкций.

**1а. Вывод в `boot-firmware`.**
- Та же переменная `OD_FETCH_CACHE_STATS` с тем же смыслом, что у `linux`: непустое значение — путь файла-спутника. Без неё runner не вызывает `enable_fetch_cache_report`, и stdout, `--out`, COM1 и NVRAM побайтно прежние (проверка K3 G100 без переменной; G3200 — при приёмке).
- `firmware_boot.rs`: прочитать переменную (переиспользовать `DiagnosticEnv::from_process` и `fetch_cache_stats_path` из `tools/runner/src/linux_direct.rs`, сделав их `pub(crate)`; новой функции разбора не писать). Перед `run_firmware_unified_traced` (firmware_boot.rs:1417) — `board.enable_fetch_cache_report()` (firmware_board.rs:2781); после — `board.take_fetch_cache_report()` (firmware_board.rs:2787).
- В JSON unified-прогона добавить `unified.fetch_cache_stats` — тот же объект, что даёт `fetch_cache_stats_json` (одна функция на обе команды), и записать его же в файл по пути переменной (резервирование `create_new` как у `linux`, linux_direct.rs:719–779). Ошибка записи — поле `write_error` рядом, прогон не проваливается. `OD_FETCH_CACHE_SWEEP` и `OD_FETCH_CACHE_TAG` в `boot-firmware` не поддерживать (они не нужны PERF-11).
- Конфликт с PERF-20: он сейчас меняет те же места `firmware_boot.rs` (`run_firmware_unified_profiled`, `--op-histogram-out`) и `paged_memory_adapter.rs`. По правилу 3.4 плана шаг 1 начинать после коммита PERF-20 и вызывать уже ту функцию входа, которую оставит PERF-20.

**1б. Новые счётчики (только измерение).** Тип `DataWalkShadow` в `fetch_cache_report.rs`; адаптер получает `Option<&DataWalkShadow>` рядом с `walks`; `Some` — только когда плата включила отчёт, иначе `None` и одна проверка ветки. Тень ничего не обслуживает и не меняет ни одного пути.
- В `access_with` после успешного отчёта обхода (`report.outcome` — `Ok`) для операций `Read` и `Write` с происхождением `Explicit` до нормализации: ключ `(address >> 12, paging, нормализованный context, класс Read/Write)`; кадры таблиц и адреса записей пути берутся из `report.trace` (`WalkEntry::entry_address`), страница обходчика не меняется.
- Счётчики: `same_page_as_previous` (тот же ключ, что у предыдущего обхода данных; класс Write покрывает Read), попадания в LRU на 4 и на 8 записей без сбросов (верхняя граница) и в те же LRU с точным сбросом по кадру таблицы и по 8-байтовой записи таблицы (две оценки политики раздела 2), `ad_commits` (`report.ad_update_count` обходов данных).
- В `watch` (paged_memory_adapter.rs:2764): `table_frame_writes` — зафиксированные записи, задевшие кадр таблицы живой записи тени; `table_entry_writes` — задевшие сам 8-байтовый адрес записи пути.
- В JSON — в объект фазы (`fetch_cache_phase_json`, linux_direct.rs:2476) ключ `data_shadow` с абсолютными числами и долями на инструкцию / на миллион инструкций; `schema_version` файла поднять до 2.
- Записать в отчёт линии: обходов чтения и записи на инструкцию, `same_page_as_previous` (доля), попадания LRU-4/LRU-8 без сброса и со сбросом по кадру / по записи, `table_frame_writes` и `table_entry_writes` на миллион инструкций — для обоих бюджетов и для фаз до и после C5, если они есть.

**Что из этих чисел решается:** размер (4 или 8 записей) и гранулярность сброса (раздел 2, п. 6). Решения «делать/не делать» эти числа не дают — только K4 прототипа (правило «не оценивать выигрыш без замера»).

## 2. Политика (по образцу S4-13 `WriteWatch`)

1. **Создание записи — только после успешного полного обхода** тем же `access_with`. Неудача любого вида (`#PF` любой причины, неканонический адрес, `CrossesPage`, `UnsupportedPageSize`, ошибка региона, отказ MMIO) записи не создаёт; следующий такой же доступ снова обходит таблицы и даёт ту же ошибку с тем же кодом и CR2.
2. **Чтение:** запись создаёт только успешный доступ `Read`; к этому моменту обход уже установил accessed всех уровней пути (п. 2 «Фактов»). Попадание чтения не пишет ничего — ровно как повторный обход без кеша, который нашёл бы все A установленными.
3. **Запись:** запись класса Write создаёт только успешный доступ `Write` после `commit_leaf_dirty`, то есть когда dirty листа установлен (им самим или раньше). Попадание записи пишет только байты операнда через `PhysicalMemory::store_bytes(physical, …, committed_write)` — ту же функцию, что и путь с обходом (page_walk.rs:2060): поколение страницы растёт, `watch` уведомляется, кеш декодирования и кеш выборки видят запись (самомодифицирующийся код). Запись класса Write обслуживает и чтение (права записи включают права чтения; A уже стоят). Запись класса Read запись не обслуживает никогда (не проверены R/W и WP, может не стоять D): промах, полный обход `Write`, затем запись класса Write заменяет запись класса Read того же ключа.
4. **Что кешируется — только plain RAM.** Кадр операнда — `MemoryRegionKind::Ram` с подложкой (`PhysicalMemory::ram_frame`, physical_memory.rs:1062); каждый кадр таблиц пути — тоже `Ram` (как `is_ram` в `remember_fetch_translation`, paged_memory_adapter.rs:5358–5376). **MMIO, ROM, Reserved и Framebuffer не кешируются никогда** — ни как кадр операнда, ни как кадр таблицы. Поэтому попадание никогда не обращается к устройству, не меняет `mmio_written`/`port_accessed`/`stop_after_mmio` и счётчик доступов к устройствам PERF-05.
5. **Слежение за таблицами.** Запись хранит кадры таблиц своего пути (3 для листа 2 МиБ, 4 для 4 КиБ) и адреса 8-байтовых записей пути. Любая зафиксированная запись, дошедшая до `watch`, проверяется: задела кадр таблицы записи → запись сбрасывается. Сбрасываются только записи, следящие за этим кадром (не весь кеш, как в `FetchTranslationCache`: это по-прежнему точно — трансляция записи зависит только от её пути).
6. **Гранулярность сброса** (выбор по числам п. 1б; оба варианта точные): (а) по кадру таблицы — базовый вариант, буквально как в плане; (б) по 8-байтовой записи пути — разрешённое уточнение: перевод и права зависят только от значений этих записей и снимка регистров, а коммиты A/D соседних записей того же кадра (частые в ядре) запись не сбрасывают. Вариант (б) берётся, только если `table_frame_writes` заметно больше `table_entry_writes`; иначе (а).
7. **Контекст.** Ключ содержит весь снимок `Long64ProbeConfig` адаптера (то, что читает обходчик, а не `state`) и нормализованный `AccessContext`; при каждом `TranslationContextChange` кеш сбрасывается в той же точке, что и кеш выборки (paged_memory_adapter.rs:3474–3480). Политики «как TLB» (`GuestOnly`: `INVLPG`, `#PF` как события сброса, устаревшие трансляции до сброса гостем) нет и не вводится: при точном слежении `INVLPG` ничего менять не должен — эталон не имеет TLB.
8. **Время жизни — один вызов цикла (квант)**, как у кеша выборки в этом пути (п. 5 «Фактов»): кеш создаётся рядом с ним (paged_memory_adapter.rs:2434) и умирает с вызовом. Печать и проверка поколений S4-14i (`seal`/`revalidate`) не нужны и не делаются. Постоянный кеш данных — отдельное решение, не этого ADR.
9. **Ширина и граница страницы.** Обслуживается только доступ, не пересекающий 4 КиБ: `(address & 0xfff) + width <= 4096` — то же условие, что `CrossesPage` обходчика (page_walk.rs:1911). Ключ — 4 КиБ-страница; лист 2 МиБ даёт запись на одну 4 КиБ-страницу внутри листа (`ram_frame` кадра операнда). Тег 2 МиБ (как S4-13d) — возможное расширение PERF-12 по числам, не прототип.
10. **Отказ по умолчанию.** Кеш получает только цикл платы `run_linux_boot_cpl0_set` (firmware_board.rs), то есть `boot-firmware --cpu-loop unified` и команда `linux`, которые идут через неё, и только в обычном прогоне. Остальные вызывающие `run_cpl0_set_loop_impl` (`parallel_run.rs`, `host_parallel.rs`, `firmware_board/vcpu_quantum.rs`, `linux_direct/interleaved.rs`, `paged_host_loop.rs`, probe) передают `None`. Режим нескольких vCPU (строгие поколения S6-34) кеш данных не получает.

## 4. Размещение и обход режимов (пункт 4 PERF-11)

**Решение: отдельная структура `DataTranslationCache`** в новом модуле `crates/od-machine/src/data_translation_cache.rs`, не новый вид доступа в `FetchTranslationCache`.

Почему не расширять `FetchTranslationCache`:
- Общие 4 слота: записи данных вытесняли бы записи выборки, а на попаданиях кеша выборки держится кеш декодирования PERF-10 (`decoded_cache_lookup`, paged_memory_adapter.rs:5401: условие (а) — запись выборки для RIP). Риск регрессии принятого +25 %.
- Сброс «всего кеша» при записи в любой отслеживаемый кадр (fetch_translation_cache.rs:500–503) годится для 4 кодовых страниц, но для данных означает, что каждый коммит A/D соседней записи таблицы сбрасывает и кодовые трансляции.
- `FetchTranslationCache` несёт механизмы, которые данным не нужны и которые пришлось бы протаскивать через новый вид доступа: `GuestOnly` (S4-14h), теневые кеши `FetchCacheSweep` и `LookupKind` (S4-13c), печать поколений (S4-14i), строгий режим (S6-34), схему файла-спутника. Каждый тест S4-13…S6-34 пришлось бы перепроверить.
- Ключ и условия другие: класс Read/Write, условие dirty, гранулярность сброса, больше слотов.

Что переиспользуется (без общего «фреймворка», правило 3.6): `Long64ProbeConfig`, `AccessContext`, `RamFrame` и `ram_frame`, `GuestPhysicalRange`, константа `NO_TABLE`. Чтение байтов по `RamFrame` — новая функция `PhysicalMemory::read_ram_frame` рядом с `read_ram_frame_u8` (physical_memory.rs:1099) с тем же `by_mode!`; запись — только `store_bytes` по физическому адресу.

Проводка:
- Плата решает, включать ли кеш, тем же условием, что кеш декодирования (firmware_board.rs:4024–4029): `fetch_cache && fetch_sweep.is_none() && !fetch_cache_report_enabled && execution_observations.is_none()`; новый параметр `run_cpl0_set_paged_2m_ram_observed_with_sweep` (`data_cache: bool`), кеш создаётся на вызов (рядом с paged_memory_adapter.rs:2434).
- В `run_cpl0_set_loop_impl` — тот же фильтр, что для кеша декодирования (paged_memory_adapter.rs:2749–2757: `!TRACE_ENABLED && !ELF_COPY_ENABLED && execution_observations.is_none()` и кеш выборки `WriteWatch` без теней); `watch` (paged_memory_adapter.rs:2764) вызывает и `data_cache.note_write`; сброс при `TranslationContextChange` — рядом с paged_memory_adapter.rs:3479.
- Адаптер: новое поле `data_cache: Option<&'a DataTranslationCache>` в `set_loop_adapter` (paged_memory_adapter.rs:3580; у всех остальных конструкторов `None`). Поиск — только в ветке обычного доступа `read` (paged_memory_adapter.rs:5994) и `write` (paged_memory_adapter.rs:6064), не в `access_with`.

Как кеш обходит режимы:
- **`capture_effects`** — кеш не используется вовсе (условие в ветке, как у выборки paged_memory_adapter.rs:5824): в этом режиме записи уходят в сборщик, а не в `committed_write`, и кеш не узнал бы о записи в таблицы. У адаптера цикла флаг всегда `false` (paged_memory_adapter.rs:3604); условие — защита, а не путь.
- **`capture_page_fault_trace`** — кеш не используется (`memory.capture_page_fault_trace = execution_observations.is_some()`, paged_memory_adapter.rs:3086; плата при наблюдениях кеш и так не создаёт). Иначе попадание должно было бы повторить сброс `page_fault_trace = None` из начала `access_with` (paged_memory_adapter.rs:5172–5174) — второе место той же семантики.
- **Счётчик `walks`** — попадание его не трогает (обхода нет). Счётчики видны только при `fetch_cache_report_enabled`, а тогда кеш данных выключен платой, поэтому `walk_counts` любого диагностического прогона побайтно прежние (правило 4.2). Собственные счётчики кеша (`hits`, `misses`, `inserts`, `flushes` по причинам) живут в `DataTranslationCache::stats` и наружу в обычном прогоне не выходят; для замера прототипа их можно временно печатать в stderr вне основной ветки.
- **Расщеплённые доступы через границу страницы** не обслуживаются и не создают записей: `access_split_byte` (paged_memory_adapter.rs:5156; слово на 0xfff, dword/qword через границу), `write_crossing_page` (5501), `access_cross_page_read` (5453) остаются на обходе. Проверка пересечения стоит до поиска (раздел 2, п. 9).
- **Не обслуживаются (первая версия PERF-12 и прототип):** исходное происхождение `DescriptorTable` (у него своя область `begin_descriptor_scope`/`check_descriptor_write`, paged_memory_adapter.rs:3845, 3935, и запись дескрипторов) и `ImplicitStack` (кадры исключений); `access_vector` (5112), `read_integer_for_write` (5834), блокированные операции (`locked_target`, 5619; `AtomicTarget`), `ReadForWrite`, `ReadPseudoDescriptor`. Расширение на них — только отдельным решением с тестами.
- **Получение физического адреса при промахе.** Прототип: как S4-13 — второй обход только для чтения `translate_long64_2m_ram_read_only_with_tables` (page_walk.rs:1346) после успешного доступа; `page_walk.rs` не меняется. PERF-12: выходной параметр у `access_long64_4k_internal_windowed` (физический адрес операнда, кадры таблиц, адреса записей пути) — один обход на промах, формулы адреса остаются в обходчике (правило 4.5). Добавлять поле в `TrackedAccessReport` не надо: это 37 мест построения.

## 5. Прототип и критерий приёмки

**Прототип пункта 5 PERF-11** (вне `main`): только чтение qword (`MOV r64, m64` и любые формы набора, читающие 8 байт через ветку paged_memory_adapter.rs:5994), исходное происхождение `Explicit`, без пересечения страницы, 4 или 8 слотов по п. 1б, гранулярность по п. 1б, политика раздела 2 целиком (кроме класса Write).

**Приёмка прототипа (решение «делать»):**
- K3: `GOLDEN: MATCH` на G100 в ходе работы и на G3200 перед K4.
- K4 только по K3200 (`--budget 3200000000 --runs 3`, приоритет −5): интервалы [min, max] «до» и «после» не пересекаются **и** медиана лучше не меньше чем на 2 %. База собрана с теми же параметрами сборки и на том же коммите (если PERF-03 позже изменит параметры — замер повторить). F100 записывается, решения не принимает.
- Исход: выигрыш подтверждён → «делать PERF-12»; подтверждён только с оговорками (например, выигрыш есть, но запись не окупается по числам п. 1б) → «делать урезанно: только чтение»; не подтверждён → «не делаем», с записанным замером (задача считается принятой по правилу раздела 6 плана).

**Тесты политики (обязательны для PERF-12; для прототипа — те, что касаются чтения):**
1. Попадание требует той же страницы, того же снимка (по отдельности меняются CR0.WP, CR3, CR4, EFER.NXE) и того же нормализованного контекста (CPL0/CPL3); `DescriptorTable` при CPL3 не попадает в запись CPL3.
2. После ошибочного обхода (не присутствует, зарезервированный бит, включая NX при NXE = 0, U/S, WP, неканонический адрес) записи нет; повтор даёт ту же ошибку с тем же кодом и CR2.
3. Попадание чтения не делает ни одной зафиксированной записи; последовательность `committed_write`, биты A/D и RAM совпадают с прогоном без кеша.
4. Запись класса Read не обслуживает запись; запись после чтения ставит D ровно один раз и создаёт запись класса Write; запись класса Write обслуживает чтение.
5. Запись гостя в каждый из кадров таблиц пути (и коммит A/D другого обхода в этот кадр) сбрасывает записи, следящие за ним; для варианта (б) — запись в соседнюю 8-байтовую запись того же кадра запись не сбрасывает, в собственную — сбрасывает, в том числе однобайтовая.
6. Операнд в MMIO, ROM, Reserved, Framebuffer — записи нет, устройство вызывается при каждом доступе; таблица в не-`Ram` — записи нет.
7. Доступ через границу страницы не обслуживается; байты расщеплённого доступа идут обходом.
8. При `capture_effects`, `capture_page_fault_trace`, отчёте кеша (`walk_counts` равны прогону без кеша), тенях и наблюдениях кеш не создаётся или не используется.
9. `MOV CR3` и смена NXE сбрасывают кеш; новый вызов цикла начинается с пустого кеша.
10. Запись через попадание в кодовую страницу делает промах кеша декодирования (поколение страницы выросло) — самомодифицирующийся код виден.
11. Лист 2 МиБ: запись 4 КиБ внутри листа, три отслеживаемых кадра.
12. Расширенный K2 (`od-testkit`, `od-host`, `od-jit`), включая `cpl0_set_differential`, — как для задач, меняющих адаптер памяти.

**Отступления реализованного прототипа** (рабочее дерево поверх HEAD `2c5b80e`: `data_translation_cache.rs` (файл удалён), `read_qword_through_data_cache` в [paged_memory_adapter.rs](../../crates/od-machine/src/paged_memory_adapter.rs), [page_walk.rs](../../crates/od-machine/src/page_walk.rs)) от разделов 2, 4 и 5. Политика раздела 2 (запись только после успешного обхода, только plain RAM, сброс по кадру таблицы — вариант (а) п. 6, ключ на полном `Long64ProbeConfig` и нормализованной привилегии, сброс при `TranslationContextChange`, время жизни — один вызов цикла) соблюдена; отличается следующее.

1. **Размер и устройство.** Вместо LRU на 4 или 8 записей (п. 1б, раздел 5) — 64 набора прямого отображения по младшим битам номера линейной страницы (тег: база страницы, привилегия, бит занятости; один снимок `Long64ProbeConfig` на все живые записи, запись под другим снимком сначала сбрасывает всё) и таблица до 16 различных отслеживаемых кадров таблиц с маской наборов на кадр и границами `[lo, hi]`, чтобы `note_write` для записи вне кадров таблиц выходил после двух сравнений. Нет места для нового кадра — сбрасывается всё (16 слотов вмещают 4 кадра одного пути). Выбор сделан по устройству попадания (одно сравнение тега и одно — снимка), а не по числам п. 1б; если эти числа будут сняты, размер пересмотреть по ним.
2. **Физический адрес и кадры таблиц при промахе** берутся из трассы того же успешного обхода (`TrackedAccessReport::trace`, через `access_with_observed`), а не вторым обходом только для чтения `translate_long64_2m_ram_read_only_with_tables`: трасса успешного обхода кончается листом (PDE для 2 МиБ, PTE для 4 КиБ), поэтому второго обхода нет.
3. **`page_walk.rs` изменён** (вопреки разделу 4 и «Последствиям»: «не меняется в прототипе»): формула физического адреса листа вынесена в `leaf_physical` — одна на обходчик и на новую `data_translation_of_walk_trace` (правило 4.5: формула адреса остаётся в обходчике); поведение обходчика не меняется.
4. **Происхождение доступа.** Обслуживаются `Explicit` и `ImplicitStack` (вопреки разделу 4: «не обслуживаются … `ImplicitStack`», и разделу 5: «исходное происхождение `Explicit`»); не обслуживается только `DescriptorTable`. Это точно: `page_privilege()` у `ImplicitStack` та же, что у `Explicit` (привилегия контекста), обход и права те же, а записи кадров исключений идут записью (кеш их не обслуживает) и проходят через `watch`. Поэтому qword-чтения стека (`POP`, `RET`) тоже идут через кеш.

Тесты прототипа: `crates/od-machine/src/paged_memory_adapter/data_cache_tests.rs` (в том числе PTE с XD при NXE = 1 и NXE = 0 с точными счётчиками и запись через «прогретое» отображение таблицы) и тесты платы `the_unified_run_with_the_data_cache_prototype_equals_the_run_without_it`, `the_data_cache_prototype_sees_a_guest_pte_store_and_a_cr3_switch_in_the_unified_run` (запись PTE гостем и `MOV CR3` в unified-цикле; без `note_write` в `watch` цикла тест падает).

## Последствия

- `FetchTranslationCache`, его тесты и схема файла-спутника выборки не меняются; добавляется только ключ `data_shadow` в схеме версии 2.
- `page_walk.rs` не меняется в прототипе; в PERF-12 — один выходной параметр внутреннего обходчика.
- Новые входы прав (SMEP, SMAP, PKE, проверка выравнивания с RFLAGS.AC) при появлении в модели обязаны войти в ключ; ключ на полном `Long64ProbeConfig` даёт это для CR4 автоматически, а для RFLAGS.AC — нет (это не часть снимка): при моделировании SMAP добавить AC в ключ или выключать кеш при CR4.SMAP = 1.

## Открытые вопросы

1. **DMA внутри кванта.** Точность опирается на то, что любая запись RAM внутри вызова цикла проходит через `watch`. Устройства обслуживаются между квантами (firmware_board.rs:4076–4085), но не проверено, что ни один обработчик MMIO не пишет RAM синхронно в `dispatch` другим путём. Тот же допуск уже несёт кеш выборки (fetch_translation_cache.rs:15–20). Проверить в PERF-12 чтением обработчиков MMIO платы (NVMe, xHCI, NIC, framebuffer) и тестом.
2. **Гранулярность сброса** (кадр или запись таблицы) и размер (4 или 8) — по числам п. 1б.
3. **Схема JSON `boot-firmware`:** `unified.fetch_cache_stats` в stdout плюс файл по пути переменной — предложено; если владелец хочет только файл, как у `linux`, в stdout остаётся лишь `unified.fetch_cache_stats_sidecar` (`path`, `write_error`).
4. **Порядок с PERF-20:** шаг 1 меняет `paged_memory_adapter.rs` и `firmware_boot.rs`, которые сейчас меняет PERF-20; начинать после его коммита.

### Д1. Диагностика пункта 1 (отступление от раздела 1)

**Отступление (решение Opus).** Механизм раздела 1 (`OD_FETCH_CACHE_STATS` в `boot-firmware`, тень `DataWalkShadow` с LRU-4/LRU-8) не построен. Вместо него — временная сборка (не коммитится, патч `work/cpu-core-perf/e8diag-temp.patch` вне git; раздел 4 допускает временный вывод счётчиков в stderr): счётчики на входе `PagedMovMemoryAdapter::read`/`write`, `read_integer_for_write`, `access_vector`, `locked_target` адаптера цикла и счётчики `DataTranslationCache` (попадания, промахи, сбросы; в этой сборке они считают и в release) в **режиме по умолчанию с блоками** (`--fast-path --data-cache-prototype`), а не в режиме `OD_FETCH_CACHE_STATS`, где плата выключает кеш декодирования, кеш данных, пакеты и блоки. Почему: (1) части (а) и (б) пункта 1 снимаются одним прогоном на одном и том же режиме; (2) гостевые обращения к данным — свойство гостевой программы, а не пути исполнения, поэтому их число и вид на входе адаптера равны числу обходов данных без кеша (один обход на обращение внутри страницы; расщеплённое обращение — несколько обходов, их доля дана отдельно); (3) тень LRU оценивала бы политику, которая не реализована: реализованное устройство (64 набора прямого отображения, отступление 1 прототипа) измерено прямо. Отсюда два ограничения: доля повторных обращений к той же странице считается по последовательности обращений адаптера цикла (обращения адаптеров доставки IRQ не видны: у них нет кеша), а «записи в кадры таблиц» — только по кадрам, за которыми следил кеш прототипа (записи класса Read qword).

### Д2. Происхождение `ImplicitStack` для записи класса Write (шаг 2 (а))

**Решение: не обслуживать.** Запись класса Write обслуживает и создаёт только доступ `Write` с исходным происхождением `Explicit`. Факт по коду: `PUSH`, `CALL`, `POP`, `RET` и `IRETQ` набора идут с контекстом цикла (`push_stack_value` → `write_integer(address, context, …)` в `crates/od-isa/src/execute.rs`; происхождение `Explicit`), а `ImplicitStack` ставят только записи кадров исключений и прерываний в `crates/od-isa/src/interrupt.rs` (`deliver_page_fault_cpl0_set`, `deliver_general_protection_cpl0_set`, `deliver_external_interrupt_cpl0_set`, `deliver_nmi_cpl0_set` через `commit_cpl0_gate`; вне цикла — `deliver_exception` и `deliver_interrupt` адаптера `paged_exception_delivery.rs`); чтений с этим происхождением нет ни у одного пути (`IRETQ` читает кадр с контекстом цикла). Их 113 на 3,2 млрд инструкций (Д1): выигрыша нет, а запрет снимает вопрос о точности кеша внутри доставки (кадр пишется при сменённой привилегии стека, `IST`, отказ посередине кадра). Для чтения правило прототипа не меняется (отступление 4: `ImplicitStack` допускается), но читателей с этим происхождением нет.

### Д3. Адаптеры доставки исключений и IRQ (шаг 2 (б))

Проверено по коду, **утверждение шага 2 (б) верно только для IRQ и NMI**:
- доставка внешнего прерывания и NMI (`deliver_pending_irq`, `deliver_polled_irq`, `deliver_nmi_at_boundary`) строит свой адаптер в `with_cpl0_gate_memory` через `set_loop_adapter`, у которого `data_cache = None`; кеш данных она не получает;
- доставка `#PF` и `#GP` в цикле (`with_gated_cpl0_delivery(&mut memory, …)`) идёт **адаптером цикла**, у которого кеш данных есть. Её обращения: чтение шлюза IDT, дескриптора целевого CS в GDT и RSP0/IST из TSS и запись бита Accessed дескриптора целевого CS (`commit_cpl0_gate`) — `DescriptorTable` (не обслуживаются никогда), запись кадра — `ImplicitStack` (не обслуживается по Д2); обращений `Explicit` и чтений `ImplicitStack` в ней нет. Значит, ни одно обращение доставки `#PF`/`#GP` кеш данных не использует; это закреплено тестом (запись `ImplicitStack` и запись `DescriptorTable` идут обходом и не создают записи класса Write). Доставка вне цикла (`deliver_host_native_fault_gated`) строит свой адаптер без кеша.

### Д4. Место кеша, класс Write и узкие чтения (шаги 4–7)

1. **Правило места.** Кеш обслуживает доступ, только если без кеша он был бы ровно `self.access(address, context, Read { width })` или `self.access(address, context, Write { width, value })`: проверка стоит после всех отказов ширины и профиля и требует `large_ram_profile`, ширину, разрешённую профилем (`read`: байт — `cpl0_set_byte_read`, слово — `word_read_profile || cpl0_set_word_read`, dword — `dword_read_profile || cpl0_set_dword_read`, qword — `!dword_read_profile && !word_read_profile`; `write`: ширина и длина, которые `write` принял), доступ внутри 4 КиБ, происхождение не `DescriptorTable` (у записи — только `Explicit`, Д2), нет `capture_effects` и `capture_page_fault_trace`; у `write` ещё нет `read_only_qword`. Ветка qword-чтения переводится под это правило: `debug_assert!` профиля заменяется проверкой.
2. **Класс в теге.** Бит класса Write в теге набора. Чтение попадает в запись любого класса; запись — только в запись класса Write. Промах записи — полный `access` `Write`; после успеха запись класса Write заменяет запись того же набора (в том числе запись класса Read того же ключа). Ширина в ключ не входит: права и перевод от ширины не зависят, а условие «внутри страницы» проверено до поиска.
3. **Дополнительное условие вставки (строже ADR):** запись класса Write не создаётся, если 4 КиБ кадр операнда — один из кадров таблиц её пути: байты операнда записаны после обхода и могли изменить запись пути, а `note_write` этой записи пришёл до вставки. Для чтения это условие не нужно (чтение ничего не пишет).
4. **Попадание записи** пишет только байты операнда через `PhysicalMemory::store_bytes(physical, …, committed_write)` — ту же функцию и тот же `committed_write` (`watch` цикла), что путь с обходом; поколение страницы растёт, кеш выборки, кеш данных, кеш декодирования и блоки видят запись. Ошибка `store_bytes` (не ожидается для кадра `Ram`) ничего не меняет (S6-30b) и уводит доступ на обход.
5. **Чтение-изменение-запись быстрого пути** (`fast_alu_into_memory`: `read_integer`, затем `write_integer`) идёт через `read` и `write` без изменений порядка: на странице с записью класса Read запись промахивается, обход ставит D, как без кеша. `read_integer_for_write`, `ReadForWrite`, блокированные операции (`locked_target` → `AtomicTarget`), `access_vector`, `ReadPseudoDescriptor` не обслуживаются. Исключение, которое не меняет точности: невыровненная блокированная операция режима чередования (`LockedTarget::Serial`, `locked_serial`) — это пара `read_integer`/`write_integer` по умолчанию трейта, то есть обычные `read` и `write` адаптера, и кеш обслуживает их по правилу места (так было и у qword-чтения прототипа); шина цикла с кешем — исключительная, один vCPU.
6. **Счётчики** `DataCacheCounters` (только отладочная сборка): прежние `hits`/`misses`/`inserts` — чтения, новые `write_hits`/`write_misses`/`write_inserts` — записи. Счётчик обходов `walks` попадание не трогает (раздел 4, «Счётчик `walks`»: при отчёте кеша выборки кеш данных выключен).
7. **Запись хранит** физическую базу 4 КиБ кадра (для `store_bytes` попадания записи и для сверки) и номера кадров таблиц своего пути (для сверки) рядом с `RamFrame`.

### Д5. Сверочный режим `--data-cache-verify` (шаг 8)

- Флаг runner `boot-firmware --data-cache-verify` (только с `--data-cache-prototype` и `--cpu-loop unified`; с `--fast-path-verify` и `--block-cache-verify` — ошибка разбора аргументов). Блоки, пакеты и быстрый путь остаются как в обычном прогоне: проверяется кеш данных режима по умолчанию. Плата: `enable_data_cache_verify` (включает и кеш данных); кеш вызова создаётся со сверкой.
- На **каждом попадании** (чтение и запись), до использования записи: чистая трансляция `translate_long64_2m_ram_read_only_with_trace` (no-op writer: без A/D, без `watch`, без изменения любого кеша; сверка не зовёт `lookup`, `insert`, `note_write` и не трогает `walks`, `access_error`, `page_fault_trace`) с нормализованным контекстом и видом доступа (`Read`/`Write`) и сравнение с записью: исход `Ok`; физический 4 КиБ кадр; кадры таблиц пути (хранятся в записи по уровням и сравниваются по уровням); бит A во всех записях трассы; для записи класса Write — бит D листа (последней записи трассы); попадание записи — только в запись класса Write; `ram_frame` кадра равен хранимому (и для чтения, и для записи).
- Расхождение: первое записывается в счётчики потока и останавливает прогон — доступ возвращает `MemoryError::Backend` с текстом расхождения (линейный адрес, вид, причина, оба значения) до любого эффекта, как `--block-cache-verify` (E5 первой части); runner считает прогон проваленным и при `divergences > 0`, даже если ошибку кто-то поглотил. Счётчики потока (`verified_reads`, `verified_writes`, `divergences`) и первое расхождение — как у сверки блоков (сброс в `run_firmware_unified_with_fast_path`, чтение после прогона); в JSON — `data_cache_check`; расхождение — ошибка прогона `run_error`/`data_cache_check` с кодом выхода 5 и счётчиками.
- Мутации под `#[cfg(test)]` (по образцу E5): «запись класса Read обслуживает запись» (выключенная проверка D) и «`note_write` не сбрасывает записи класса Write» (выключенное слежение за кадрами таблиц для класса Write); на каждую — тест «мутация видна» (сверка находит расхождение, а прогон без сверки расходится с прогоном без кеша).

### Д6. Запись RAM внутри вызова цикла мимо `watch` (открытый вопрос 1 — закрыт)

Чтением кода установлено: **ни один путь не пишет гостевую RAM внутри вызова цикла мимо `watch`** в unified-прогоне платы прошивки.
- Устройства не имеют доступа к RAM: `BusDevice::write(&mut self, DeviceAccess, u64)` (`crates/od-machine/src/bus.rs`) без параметра памяти; MMIO-диспетчер цикла (`MachineBusSetStepIo::dispatch`) и порты (`SetStepPortIo`) только вызывают устройства и ставят `mmio_written`. Дверные звонки NVMe (`write_doorbell`), xHCI (`write_doorbell`) и NIC e1000 (`write_register`) только ставят флаги; MSI-X идёт в LAPIC, не в RAM.
- DMA есть только в `NvmeHandle::service_ram`, `XhciHandle::service`, `NicHandle::service`, которые берут `&mut MachineBus` и вызываются платой между квантами (`run_linux_boot_cpl0_set`); во время вызова цикл держит `LoopBus::Exclusive(&mut board.bus)`, кеш данных отфильтрован ровно на этот случай, `PhysicalMemory` принадлежит `MachineBus` по значению и не разделяется с другими потоками; runner не запускает потоков, пишущих RAM.
- Внутри цикла все записи RAM (адаптер шага, `access_vector`, `write_crossing_page`, `read_integer_for_write`, блокированные операции через `locked_finish`, доставка `#PF`/`#GP` адаптером цикла, доставка IRQ адаптером `with_cpl0_gate_memory` с тем же `watch`) идут с `committed_write` = `watch`; журнал области дескрипторов уведомляет `watch` при закрытии области и есть только с `split_gate`, которого в unified-прогоне нет. Запись в `Framebuffer` идёт без уведомления, но такие кадры не бывают ни кадром операнда, ни кадром таблицы записи кеша.
- Между вызовами, без `watch`, пишут RAM: DMA `service` (плюс `NvmeHandle::try_service_one_pending_ram` — только параллельный режим, `vcpu_quantum.rs`) и доставка NMI платой (`deliver_nmi_at_boundary` с `committed_write = |_| {}`, вызывается из `deliver_pending_nmi_of` между вызовами). Ни то, ни другое не может оставить устаревшую запись: кеш создаётся на вызов. Тест: запись PTE «мимо watch» (как DMA, `store_bytes(…, |_| {})`) между двумя вызовами цикла — второй вызов видит новый перевод.
- Инвариант ломается, если: устройство получит доступ к памяти в `write`; DMA станет синхронным в обработчике звонка; цикл будет идти по `LoopBus::Shared` с кешем данных; кеш станет постоянным между вызовами. Каждое из этих изменений обязано пересмотреть этот пункт.

## Дополнение E12 (2026-11-25): хранилище кеша на прогон платы — не принято
