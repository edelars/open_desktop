# ADR-0011. Ключи и политика Secure Boot

- **Дата решений владельца** 2026-11-07 (D3–D7). Источники данных закреплены 2026-11-19.
- **Статус** Реализация S7-24 в работе. [Решения D3–D7 и условия приёмки](../plans/STAGE_7.md#s7-24-реализовать-secure-boot).

Новая VM загружается в UserMode с `SecureBoot=1`. `db` включает Microsoft Windows Production PCA 2011, Windows UEFI CA 2023, Microsoft Corporation UEFI CA 2011 и Microsoft UEFI CA 2023. Это поддерживает Windows Boot Manager и загрузчики сторонних ОС с подписями обоих поколений. Вариант только с Windows UEFI CA 2023 сузил бы набор загрузчиков. Microsoft Option ROM UEFI CA 2023 исключён, поскольку плата не исполняет option ROM. В `KEK` входят Microsoft Corporation KEK CA 2011 и Microsoft Corporation KEK 2K CA 2023 для подписанных обновлений `db`/`dbx`. [Ключи и рекомендации Microsoft](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/windows-secure-boot-key-creation-and-management-guidance?view=windows-11), [происхождение и хеши](../../tests/fixtures/firmware/certs/README.md).

Начальный `dbx` — официальный x64 firmware payload Microsoft Secure Boot Objects v1.7.2. Вариант с пустым `dbx` оставил бы известные отозванные образы допустимыми. Дальнейшие обновления приходят от гостя и проходят проверку подписи и авторизации. При загрузке образа совпадение с `dbx` имеет приоритет перед `db`. [UEFI 2.11, §32](https://uefi.org/specs/UEFI/2.11/32_Secure_Boot_and_Driver_Signing.html), [исходный выпуск](https://github.com/microsoft/secureboot_objects/releases/tag/v1.7.2).

Host при создании VM генерирует свой RSA-2048 `PK` и самоподписанный сертификат, уничтожает закрытый ключ после подписания и передаёт в построитель NVRAM только публичный сертификат. Сервис host формирует начальные `PK`, `KEK`, `db` и `dbx` как первоначальный enroll в SetupMode. Действие host «сбросить ключи Secure Boot» возвращает SetupMode или строит новый набор умолчаний с новым PK. Сохранение закрытого PK ради будущего подписанного обновления потребовало бы отдельной защиты секрета и политики восстановления. На этапе 7 инициализацию использует runner, интеграция с созданием VM и bundle относится к S9-26. [План S7-24](../plans/STAGE_7.md#s7-24-реализовать-secure-boot).

`notBefore` и `notAfter` не ограничивают валидацию X.509 для образов и authenticated variables. У прошивки нет доверенного времени, а проверка этих полей исключила бы выбранные сертификаты 2011 года после их истечения. Отзыв производится через `dbx`. Время в `EFI_VARIABLE_AUTHENTICATION_2` используется для монотонности обновлений. SHA-1 для подписи образов и authenticated variables исключён из проверяемого профиля S7-24. Объявленный профиль подписи — RSA PKCS#1 v1.5 и SHA-256. SetupMode и отключение Secure Boot доступны для диагностики по правилам плана. [UEFI 2.11, §8.2.6](https://uefi.org/specs/UEFI/2.11/08_Services_Runtime_Services.html#using-the-efi-variable-authentication-2-descriptor), [сроки сертификатов Microsoft](https://support.microsoft.com/en-us/servicing/os/secure-boot/2025/06/windows-secure-boot-certificate-expiration-and-ca-updates), [границы UEFI профиля](../plans/STAGE_7.md#43-переменные-tpm-secure-boot).

Для `PK` и `KEK` обновление авторизует текущий `PK`. Для `db`, `dbx` и `dbt` авторизацией служит текущий `PK` или цепочка от подписанта к сертификату в `KEK`. В SetupMode действуют проверки формата Auth2 и времени. При `APPEND_WRITE` отметка времени сохраняет максимальное значение, а дубликаты знакомых `EFI_SIGNATURE_DATA` пропускаются. Для `EFI_CERT_X509_SHA256_GUID` сравнивается SHA-256 DER-структуры `tbsCertificate`; профиль без RFC 3161 отвергает совпадение независимо от `TimeOfRevocation`. [UEFI 2.11, §§8.2.6](https://uefi.org/specs/UEFI/2.11/08_Services_Runtime_Services.html#using-the-efi-variable-authentication-2-descriptor) и [32.5](https://uefi.org/specs/UEFI/2.11/32_Secure_Boot_and_Driver_Signing.html#uefi-image-validation).

У общего верификатора для PKCS7 Verify Protocol разрешение после отзыва с датой опирается на X.509 из переданного вызывающей стороной `TimeStampDb`. Допустимый токен RFC 3161 подписан RSA-2048/SHA-256, содержит SHA-256 исходного значения подписи и связывает фактический сертификат TSA через ESSCertID или ESSCertIDv2. Сертификаты TSA проверяются на момент `genTime`. Принимается только токен, чья верхняя граница времени по `accuracy` строго меньше всех подходящих дат отзыва. При отсутствии поля сравнивается подписанное `genTime`. Внешние параметры точности политики TSA не загружаются. Безусловный отзыв, совпадение хеша сообщения и отзыв TSA запрещают проверку. Для записей с неопределённой зоной или флагами daylight исключение не применяется. SHA-1 используется только для отпечатка сертификата ESSCertID. Политика загрузчика PE и Auth2 остаётся определена их правилами выше. [UEFI 2.11 §37.4](https://uefi.org/specs/UEFI/2.11/37_Secure_Technologies.html#pkcs7-verify-protocol), [RFC 3161](https://www.rfc-editor.org/rfc/rfc3161.html), [RFC 5816](https://www.rfc-editor.org/rfc/rfc5816.html).

В PCR7 первоначальная конфигурация измеряется до запуска внешнего кода, а запись `EV_EFI_VARIABLE_AUTHORITY` создаётся при первом использовании конкретной `EFI_SIGNATURE_DATA`. После изменения конфигурации до EBS применяется повторное измерение или перезапуск. [TCG PC Client Platform Firmware Profile 1.06, §3.3.4.8](https://medias.cdn.trustedcomputinggroup.org/production/TCG_PC_Client_Platform_Firmware_Profile_Version_1_06_Revision_52_pub_3_1184065dfc.pdf).

Форматы и верификатор Secure Boot вынесены в `od-uefi-security`. Это чистый слой без доступа к шине и состоянию VM. `Guid` и имя переменной имеют общее представление. Firmware заимствует Auth2 и ESL без `alloc`, а feature `verify` подключает X.509 и RSA для проверки подписи и цепочки. Правила создания переменных, timestamp и успешный commit принадлежат владельцу persistent state. [Карта проекта](../PROJECT_LAYOUT.md), [зависимости](../policies/DEPENDENCIES.md#криптографические-библиотеки-vtpm-и-прошивки-s7-20).

Для защищённого профиля `NvramDevice` владеет политикой, отметками времени и режимом инициализации. Для обычного MMIO `WRITE`/`FLUSH` устройство сверяет защищённые записи и метаданные с активным банком. Отдельный путь authenticated update принимает поля исходного `SetVariable` и полный Auth2. Устройство проверяет подпись и время относительно текущей политики и атомарно применяет обновление. Это позволяет штатные обновления после EBS, сохраняя проверку при прямом доступе гостя к MMIO. Повреждённый защищённый снимок отклоняется. Перевод legacy-снимка на защищённый режим и сброс ключей выполняет доверенный host API. `ODVARSTR` v1 остаётся форматом legacy-профиля. Защита от подмены файла снимка host-стороной остаётся в S9-26 по D1. [ISSUE-600](../KNOWN_ISSUES.md#issue-600), [формат NVRAM](../specs/NVRAM_DEVICE.md).
