# ADR-0008 — Сетевой backend: размещение, собственный стек и контракт NAT

**Дата:** 2026-11-22

**Задача:** [S11-30](../plans/STAGE_11.md#s11-30-adr-0008-и-контракт-сети)

**Статус:** принят архитектурным ревью (Opus high); подтверждение владельца по стеку — ожидается.

**Связанные документы:** [контракт сети](../specs/NETWORK.md), [план этапа 11](../plans/STAGE_11.md), [виртуальная плата](../specs/VIRTUAL_BOARD.md), [политика зависимостей](../policies/DEPENDENCIES.md), [ADR-0001](ADR-0001-dependencies-and-boundaries.md), [ADR-0002](ADR-0002-general-purpose-libraries.md), [apps/AGENTS.md](../../apps/AGENTS.md), [карта проекта](../PROJECT_LAYOUT.md).

## Вопрос

Где размещается backend сети (режим NAT для гостя с NIC, совместимой с Intel 82540EM) и чем реализуются трансляция и TCP/IP в пользовательском пространстве: собственным кодом или библиотекой общего назначения. Решение нужно до начала S11-31a…e: без него неизвестно, что писать в 31b–d.

## Контекст

- Плата выбрала NIC, совместимую с 82540EM (`8086:100E`): у Windows есть inbox-драйвер, [VIRTUAL_BOARD.md](../specs/VIRTUAL_BOARD.md) оставляет «host NAT/backend» в host-компоненте. Устройства, backend и PCI (S4-30) в коде нет.
- [AGENTS.md](../../AGENTS.md) разрешает библиотеки общего назначения, в том числе сетевую инфраструктуру ([ROADMAP](../ROADMAP.md): «общая сетевая инфраструктура допустима по политике зависимостей»), и запрещает готовые реализации ключевых компонентов (модели устройств, firmware и т. д.). Модель NIC и семантика устройства остаются собственными при любом выборе.
- Пакеты гостя — недоверенный ввод ([план этапа 11, §3, п. 8](../plans/STAGE_11.md)): разбор в Rust, без паники на мусоре.
- В workspace нет сетевых зависимостей. [od-host](../../crates/od-host/Cargo.toml) использует только `libc` (macOS aarch64) и собственные crate; проверка сборки идёт с `--offline` ([политика зависимостей](../policies/DEPENDENCIES.md): отсутствие пакета в локальном кеше не запрет, но каждый новый пакет — отдельный шаг получения).
- Цель версии 1 — гость выходит в интернет и локальную сеть (DHCP, DNS, HTTP(S), обновления пакетов), входящих соединений нет. Пропускная способность не обещается ([AGENTS.md](../../AGENTS.md), решения по скорости — по замерам).

## Решение 1. Размещение backend

Backend NAT находится в `od-host` (Rust), в каталоге `crates/od-host/src/nat/`. Граница с моделью NIC — Rust trait в `od-machine` (`crates/od-machine/src/net_backend.rs`, S11-31a) с ограниченными очередями кадров; trait не содержит сокетов, файловых дескрипторов и типов host ([NETWORK.md, раздел 4](../specs/NETWORK.md)). Сетевой ввод-вывод выполняется в собственных потоках backend; вызовы `transmit`/`poll_receive` не блокируются.

Альтернативы:

| Вариант | Результат | Причина |
|---|---|---|
| `vmnet.framework` | отклонён для версии 1 | API требует entitlement `com.apple.vm.networking`; Apple указывает, что он «ограничен разработчиками программного обеспечения виртуализации», и предлагает обращаться к контактному лицу Apple. Источник: [Apple Developer Documentation, com.apple.vm.networking](https://developer.apple.com/de/documentation/bundleresources/entitlements/com.apple.vm.networking) (через Context7, 2026-11-22; немецкая версия страницы). Получение entitlement от нас не зависит и в плане этапа 11 не предполагается ([план, §3, п. 7](../plans/STAGE_11.md)). Если entitlement будет получен, vmnet может стать вторым backend за тем же trait (кадры внутрь и наружу); этот вывод — гипотеза, не проверена. |
| Backend в VMHost на Swift | отклонён | вызов Swift на каждый пакет против [apps/AGENTS.md](../../apps/AGENTS.md) («Не вызывать Swift/UI/IPC на каждой гостевой инструкции…» и «модель устройства … размещать в соответствующем Rust-компоненте»); горячий путь пакетов принадлежит Rust. |
| Backend в приложении (UI-процесс) | отклонён | приложение не владеет ресурсами VM ([ARCHITECTURE §3](../ARCHITECTURE.md)); пакеты не идут через control-протокол ([план, §3, п. 9](../plans/STAGE_11.md)). |

## Решение 2. Реализация трансляции и TCP/IP

**Принят вариант (А): собственный стек в усечённом профиле** — Ethernet, ARP, IPv4, DHCP-сервер (один lease), DNS-пересылка через системный резолвер, UDP, ICMP echo, TCP. Профиль и числа — [NETWORK.md](../specs/NETWORK.md). Решение принято архитектурным анализом (Opus high, 2026-11-22), подтверждение владельца ожидается.

**Запасной вариант (Б)** — библиотека общего назначения **только для TCP**, если сработают критерии ниже. Сейчас **ничего не добавляется** в `Cargo.toml` и `Cargo.lock`: пакет, версия, лицензия, features и транзитивные зависимости фиксируются по [политике зависимостей](../policies/DEPENDENCIES.md) в момент срабатывания критериев, а не заранее. Кандидат (`smoltcp`) назван как направление исследования; его применимость к проксированию соединений гостя (завершение TCP гостя на стороне backend) **в этой задаче не исследовалась**, лицензия и версия не проверялись. Dev-оракул (сравнение своего TCP с другой реализацией на одном трафике) — позже, при доступе к сети, и сам по себе не добавляет runtime-зависимость.

**Отклонён: `libslirp`** (готовая C-библиотека пользовательской сети из окружения QEMU; сведения общие, источник в этой задаче не исследован). Причины, не требующие проверки версии: (1) C-код на недоверенном вводе гостя против правила «разбор — в Rust»: граница FFI на каждом пакете и вся поверхность атаки — не наша; (2) готовая реализация целой сетевой модели чужого эмулятора — спорная граница [политики](../policies/DEPENDENCIES.md) о ключевых компонентах; (3) C-сборка и её зависимости усложняют воспроизводимую сборку с `--offline`; (4) тот же объём «склейки» с сокетами host всё равно пришлось бы писать. Лицензия и транзитивные зависимости не оценивались и не будут, пока вариант не пересмотрен.

### Почему (А) сейчас

1. **Объём известен и мал.** Профиль версии 1 — IPv4 без фрагментов и опций, один гость, один lease, DNS только A/AAAA, TCP без масштабирования окна, SACK и временных меток. Это не общий IP-стек.
2. **Склейка наша при любом выборе.** Таблица flow, сопоставление соединений гостя с сокетами host, DHCP, DNS через `getaddrinfo`, политика адресов, лимиты, счётчики и отказы — код проекта и при варианте (Б). Библиотека заменила бы только конечный автомат TCP (часть S11-31d). Риск варианта (А) сосредоточен в одном модуле.
3. **Ни одного нового пакета.** Нет вопросов о лицензии, транзитивных зависимостях и `--offline`-кеше, пока они не нужны.
4. **Разбор недоверенного ввода под контролем.** Полный набор проверок длин и контрольных сумм — до обращения к сокетам ([NETWORK.md, раздел 5](../specs/NETWORK.md)); тесты S11-31a это проверяют.
5. **Критерии (Б) — измеримые**, значит, решение обратимо без потери задач 31a–c.

### Критерии перехода на вариант (Б) — только для TCP

Решение пересматривается при срабатывании **любого** критерия; проверяются на S11-31d и S11-33.

| № | Критерий | Порог (гипотеза до накопления данных) |
|---|---|---|
| К1 | Объём | Нетестовый код `nat/tcp.rs` превышает 1 500 строк. |
| К2 | Корректность на синтетическом трафике | Передача 64 MiB в каждую сторону через генератор кадров с потерей, дублированием и перестановкой по 1 % (не менее 20 seed): хотя бы один seed даёт расхождение байтов, зависание более 30 с без прогресса или паническое завершение, не исправленное за два раунда ревью. |
| К3 | Ревью | После второго раунда исправлений независимое ревью (Opus high) подтверждает дефект конечного автомата TCP (воспроизведён тестом). |
| К4 | Реальный гость | При S11-33 (Linux, `curl` или менеджер пакетов, передачи ≥ 100 MiB) зависания или обрывы объясняются нашим TCP, а не NIC/хостом. Для Windows критерий не применим: сетевого сценария нет. |
| К5 | Скорость | Применяется только если к S11-31e есть прототип (Б) на том же генераторе (dev-оракул): сравнение по правилам [AGENTS.md](../../AGENTS.md) (≥ 5 повторов, одинаковые условия). Без прототипа критерий не используется и производительность не обещается. |

Если (Б) выбран: S11-31a остаётся, S11-31b, c, d становятся интеграцией библиотеки с теми же тестами ([план S11-30, п. 2](../plans/STAGE_11.md)); контракт [NETWORK.md](../specs/NETWORK.md) (адреса, лимиты, таблица «что видит гость») не меняется — меняется только внутренность TCP. Перед добавлением обязательна запись по [политике зависимостей](../policies/DEPENDENCIES.md): назначение, источник, версия, лицензия (permissive; copyleft — только с согласия владельца), features, транзитивные зависимости, подтверждение, что пакет не заменяет ключевую технологию, и способ проверки.

## Решение 3. Контракт сети

Нормативный текст — [NETWORK.md](../specs/NETWORK.md). Сводка:

- **Режимы:** `none` (устройства нет) и `nat` (NIC + backend). Других нет.
- **Адресация:** подсеть `10.0.2.0/24`, гость `10.0.2.15`, шлюз `10.0.2.2`, DNS `10.0.2.3`, MTU 1500. Причина и недостаток записаны в NETWORK.md, раздел 3.
- **DHCP:** один lease, без состояния. **DNS:** A через системный резолвер, AAAA — пустой ответ, остальное NOTIMP. **UDP:** сокет на flow, бездействие 120 с. **ICMP echo:** шлюз и DNS — синтетически; внешние — непривилегированный сокет ICMP (источник — исходник `ping` Apple, не проверено в VMHost), иначе без ответа. **TCP:** проксирование соединения, усечённый профиль, лимиты и таймеры в NETWORK.md.
- **Лимиты (все — числа, гипотезы до S11-31e):** очереди 256/256, TCP 128 flow, UDP 64, ICMP 8, буфер TCP 64 KiB на направление, MSS 1460, таймауты 30 с / 120 с / 7 440 с.
- **Безопасность:** петля host недоступна гостю; слушающих сокетов нет; IPv6, port forwarding, фрагменты, multicast — вне версии 1.
- **Ошибки backend** — потеря пакета, RST или ICMP unreachable по таблице, **не panic**.

## Последствия

- S11-31a…e пишутся независимо от модели NIC (S11-32): граница — trait и NETWORK.md, раздел 4; обязанности NIC (offload до `transmit`, `Dropped` как успешная отправка, буфер 1514 байт) записаны там же.
- S11-31d — самая рискованная задача: критерии К1–К4 проверяются в ней.
- Пока нет S11-32 и S4-30, backend проверяется только синтетическими кадрами; в продуктовом профиле режим `nat` отвечает `unsupported`.
- Тесты с сервером на `127.0.0.1` требуют тестового режима политики адресов: гость в продукте не видит петлю host.
- ICMP echo наружу и DNS через `getaddrinfo` зависят от поведения macOS, которое не проверено в этой задаче; сужение (синтетический echo только для шлюза, расширение типов DNS) не нарушает контракт.
- Гость может обращаться к локальной сети и к не-loopback адресам самого host; ограничение по умолчанию — вопрос владельцу.

## Вопросы владельцу

1. **Стек.** Подтверждаете ли вариант (А) — собственный TCP/IP-профиль в `od-host` с запасным вариантом (Б) только для TCP по критериям К1–К5? Ответ владельца: **ожидается** (дата не получена). Задача S11-31a (trait, очереди, разбор кадров) от ответа не зависит; S11-31b–d до ответа не начинать ([план: «не начинать 31b–d без решения 2»](../plans/STAGE_11.md)).
2. **Политика назначения.** Разрешён ли гостю доступ к локальной сети и к не-loopback адресам самого host без межсетевого экрана (так записано в NETWORK.md, раздел 5, п. 6)? Альтернативы: запретить частные диапазоны host, ограничить портами. Ответа нет; значение по умолчанию — «разрешено».

## Не проверено в этой задаче

- Ни одна строка кода и ни одна зависимость не добавлены; backend, trait и тесты не существуют.
- Применимость кандидата (Б) и его лицензия; сведения о `libslirp`.
- Поведение `getaddrinfo` и непривилегированного ICMP в процессе VMHost; число доступных дескрипторов.
- Работа Windows- и Linux-гостей с профилем (S11-33 — для Linux; Windows-сценария нет).
- Все числовые лимиты — гипотезы до замеров S11-31e.
