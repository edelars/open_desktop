# ADR-0013 — Профиль CPU для Linux через собственную UEFI

**Дата:** 2026-11-20

**Задача:** [S7-31](../plans/STAGE_7.md#s7-31-загрузить-linux-через-собственную-uefi), срез S7-31a (диагностика)

**Статус:** Предложено. Решение за Opus high; до него допуски CPU, `firmware_board.rs` и загрузчик образов не меняются.

## Контекст

Ядро Ubuntu 7.0.0-38 и initramfs Stage 4 доходят до `/init` на `linux-direct` без UEFI. Прошивка исполняет свой код только профилем `PagedCpl0FirmwareBootV1` (`run_paged_firmware_probe`: точные кодировки инструкций собственного ROM, добавлявшиеся по одной в срезах ISSUE-385, 386, 594, 595 и далее). Linux идёт другим путём — `run_linux_boot_cpl0_set` с `Cpl0ProfileSet`. Срез S7-31a запустил EFI stub ядра через существующий путь `od-runner boot-firmware` ([отчёт](../reports/STAGE_7_REPORT.md#s7-31a--диагностика-пути-linux-через-собственную-uefi-2026-11-20), [запись остановки](../reports/data/stage7/s7-31a-linux-uefi-stop-record.json), [инвентарь](../reports/data/stage7/s7-31a-efi-stub-isa-inventory.json)). Установлено:

1. Неизменённый `vmlinuz` не загружается: образ с ImageBase 0 без `.reloc` отвергает LoadImage ([ISSUE-620](../KNOWN_ISSUES.md#issue-620)). Менеджер загрузки печатает «no bootable option».
2. Диагностическая копия с ImageBase 0x1000000 останавливается в коде самой прошивки на форме `and qword ptr [rsp+8], -2` ([ISSUE-621](../KNOWN_ISSUES.md#issue-621)).
3. Если обойти и это (SizeOfHeaders 0x400), машина останавливается на первой инструкции stub, `endbr64` ([ISSUE-622](../KNOWN_ISSUES.md#issue-622)). До ExitBootServices прогон не дошёл; поведение stub после первой инструкции не наблюдалось.
4. Статическая оценка: из 7 474 инструкций, достижимых от `efi_pe_entry` и не достижимых от `.Lrelocated` (код stub), профиль прошивки не допускает 252 (3,4 %, 119 различных кодировок из 3 485). Вне CPU_CONTRACT (CPL0-набор) остаются 14 форм, 67 экземпляров (0,9 %), главным образом `endbr64` (43). Это оценка: косвенные переходы не прослежены, невзятые ветки учтены; число реальных остановок она не даёт.
5. В `FirmwareBoardConfig` уже есть опции `linux_profile` (PIT, 8259, поглотители портов), `nvme_pci` (NVMe как PCI-функция 00:04.0, handoff v1.3), `pci_ecam`, `acpi_pm` и `acpi_tables`. Они задумывались для прямой загрузки Linux на той же плате, но запускает их другой цикл исполнения.

## Варианты

### (a) Расширить профиль прошивки до того, что исполняет stub и ядро

Профиль `PagedCpl0FirmwareBootV1` получает недостающие кодировки (`endbr64`, формы `rol`, `mov`, `imul` и остальные из инвентаря, затем всё, что понадобится ядру после ExitBootServices).

- Плюсы: плата и цикл прошивки остаются как есть; каждый шаг маленький и проверяется тестом на соседей кодировки.
- Минусы: допуск по точным кодировкам не масштабируется на чужой код: по оценке 119 различных кодировок только в stub, и неизвестно, сколько из них исполнится; каждая остановка — отдельный срез с ISSUE и ревью. Ядро после ExitBootServices всё равно требует набор CPL0 и состояния Linux-платы, то есть вторую копию семантики (нарушение DRY): профиль прошивки ограничен ровно тем, что нужно ROM, и менять его смысл на «что угодно ядру» значит заменить его CPL0-набором под другим именем.
- Не снимает ISSUE-620 (политика LoadImage) и ISSUE-621 (форма в коде ROM — снимет, как отдельная кодировка).

### (b) Единая плата «UEFI + Linux»: прошивка, `linux_profile` и `nvme_pci` в одном цикле

Прошивка и гость исполняются через `Cpl0ProfileSet` (им выполнены прогоны Linux-direct, S4/S5), а устройства платы прошивки (TPM CRB, NVRAM, порт вывода, NVMe) подключаются к тому же шине, что и Linux-устройства.

- Плюсы: одна семантика CPU для обоих этапов; чужой EFI-код и ядро исполняются одним набором; опции платы уже существуют. Снимает ISSUE-621 для кода ROM, если набор допускает форму (это надо проверить).
- Минусы и непроверенное: (1) не измерено, входит ли весь код ROM в CPL0-набор (то же статическое сравнение для ELF прошивки не строилось; плюс неизвестно, как набор обслуживает MMIO устройств прошивки); (2) прошивка работает с NVMe через handoff-устройство 8, а `nvme_pci` даёт Linux PCI-функцию и handoff v1.3: совместимость двух описаний одного контроллера в одном запуске не доказана; (3) не проверено, умеет ли цикл `run_linux_boot_cpl0_set` то, что цикл прошивки: TPM, NVRAM, остановку по Reset/Shutdown; (4) ISSUE-620 остаётся. Ожидаемая цена выше, чем у (a), на первом срезе, и ниже на стадии ядра.

### (c) Другой путь

- (c1) Собственный загрузчик Linux внутри прошивки (приложение FV читает ядро с ESP по протоколу загрузки x86 и передаёт управление минуя EFI stub, с `boot_params` и информацией о карте памяти и таблицах). Чужой EFI-код не исполняется; дальше работает CPL0-набор. Но это не «стандартный загрузчик дистрибутива»: S7-31 требует, чтобы ОС загружал штатный загрузчик (shim/GRUB/EFI stub), поэтому такой путь дал бы лишь частичное подтверждение (efivarfs и таблицы), а критерий готовности S7-31 не закрывается. Требует отдельного решения владельца о границе требования.
- (c2) Штатные shim/GRUB вместо EFI stub: исполняют больше чужого кода до ядра, чем stub (не измерено), и упираются в тот же барьер профиля. Не рассматривается как путь к решению.
- (c3) Менять устройство образа Debian d-i: сырой ISO прошивка не видит (защитная MBR отсутствует, GPT в LBA 0, тип разделов Basic Data); это вопрос S7-35-образной конвертации, а не профиля CPU.

## Предложение

Не решение; рекомендация для Opus high. Вариант (b) как целевой, потому что после ExitBootServices ядро в любом случае исполняется CPL0-набором, и (a) дублировал бы его. Перед выбором выполнить две дешёвые проверки: (1) инвентарь формы кода ROM против CPL0-набора (скрипт `tools/build/s7_31a_efi_stub_isa_inventory.py` принимает образ PE; для ROM нужна ELF-версия входа); (2) прогон прошивки под `Cpl0ProfileSet` до сообщения «no bootable option» и сравнение вывода COM1 с эталоном. ISSUE-620 нужно закрывать при любом варианте и сначала: без него stub не стартует. Если проверка (1) покажет, что в наборе CPL0 нет форм ROM, остаётся (a) для кода ROM и (b) для гостя, с явным переключением исполнителя в момент `StartImage` чужого образа — решение того же ADR.

## Что нужно для S7-31 целиком

1. Политика LoadImage для образа без перемещений и с ImageBase 0 (ISSUE-620), тесты на реальные заголовки ядра.
2. Решение по этому ADR и реализация выбранного варианта (S7-31b), включая форму в `load_into` (ISSUE-621) и `endbr64` с остальными формами stub (ISSUE-622).
3. Прогон EFI stub до ExitBootServices: перечень запрошенных протоколов (трассировка прошивки), нужные stub сервисы (LoadedImage, SimpleFileSystem и разбор `initrd=` или LoadFile2, GetMemoryMap, AllocatePages, GetVariable для `Boot####`, при желании RNG и TCG2, таблицы ACPI и SMBIOS), результат ExitBootServices.
4. Достаточный объём RAM (плата прошивки даёт 128 МиБ; для ядра с распаковкой это не проверялось).
5. После ExitBootServices: Runtime Services (`SetVirtualAddressMap`, `GetVariable`/`SetVariable`) для `efivarfs`, GOP для `efifb`/`simpledrm` и дамп framebuffer (S10).
6. Принятое Linux guest evidence этапа 5, S4-39 (userspace), S4-30 (PCI-привязка NVMe), S4-31 (ACPI), принятый S7-16 — предпосылки из плана этапа 7.
7. Параметры загрузки, доставляемые OptionalData записи `Boot####` (проверено S7-31a: прошивка передаёт её как LoadOptions); initrd по пути ESP (генератор ESP получил `--boot-file`).
8. Критерии S7-31: строка `init` на COM1, `cat /sys/firmware/efi/efivars/...`, `dmesg | grep -i acpi` без `error`, скриншот framebuffer.

## Последствия принятия

Решение определит, где живёт семантика CPU для чужого EFI-кода, и тем самым границу между S7-31b и S5/S6. Документы `UEFI_PROFILE.md` и `FIRMWARE_BOOT.md` обновляются после принятия, а не в этом срезе.
