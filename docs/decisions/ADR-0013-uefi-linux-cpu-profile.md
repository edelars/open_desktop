# ADR-0013 — Профиль CPU для Linux через собственную UEFI

**Дата:** 2026-11-20

**Задача:** [S7-31](../plans/STAGE_7.md#s7-31-загрузить-linux-через-собственную-uefi), срез S7-31a (диагностика)

**Статус:** Принято (вариант (b)), 2026-11-21. Решение владельца проекта (2026-11-21), по рекомендации Opus high: единая плата «UEFI + Linux», один цикл исполнения `Cpl0ProfileSet` для ROM и гостя. Реализация — срез S7-31c ([отчёт](../reports/STAGE_7_REPORT.md#s7-31c--единая-плата-uefi--linux-rom-и-гость-в-одном-цикле-cpl0-2026-11-21)); до его слияния допуски CPU и `firmware_board.rs` менялись только им.

## Контекст

Ядро Ubuntu 7.0.0-38 и initramfs Stage 4 доходят до `/init` на `linux-direct` без UEFI. Прошивка исполняет свой код только профилем `PagedCpl0FirmwareBootV1` (`run_paged_firmware_probe`: точные кодировки инструкций собственного ROM, добавлявшиеся по одной в срезах ISSUE-385, 386, 594, 595 и далее). Linux идёт другим путём — `run_linux_boot_cpl0_set` с `Cpl0ProfileSet`. Срез S7-31a запустил EFI stub ядра через существующий путь `od-runner boot-firmware` ([отчёт](../reports/STAGE_7_REPORT.md#s7-31a--диагностика-пути-linux-через-собственную-uefi-2026-11-20), [запись остановки](../reports/data/stage7/s7-31a-linux-uefi-stop-record.json), [инвентарь](../reports/data/stage7/s7-31a-efi-stub-isa-inventory.json)). Установлено:

1. Неизменённый `vmlinuz` не загружается: образ с ImageBase 0 без `.reloc` отвергает LoadImage ([ISSUE-620](../KNOWN_ISSUES.md#issue-620)). Менеджер загрузки печатает «no bootable option».
2. Диагностическая копия с ImageBase 0x1000000 останавливается в коде самой прошивки на форме `and qword ptr [rsp+8], -2` ([ISSUE-621](../KNOWN_ISSUES.md#issue-621)).
3. Если обойти и это (SizeOfHeaders 0x400), машина останавливается на первой инструкции stub, `endbr64` ([ISSUE-622](../KNOWN_ISSUES.md#issue-622)). До ExitBootServices прогон не дошёл; поведение stub после первой инструкции не наблюдалось.
4. Статическая оценка: из 7 474 инструкций, достижимых от `efi_pe_entry` и не достижимых от `.Lrelocated` (код stub), профиль прошивки не допускает 252 (3,4 %, 119 различных кодировок из 3 485). Вне CPU_CONTRACT (CPL0-набор) остаются 14 форм, 67 экземпляров (0,9 %), главным образом `endbr64` (43). Это оценка: косвенные переходы не прослежены, невзятые ветки учтены; число реальных остановок она не даёт.
5. В `FirmwareBoardConfig` уже есть опции `linux_profile` (PIT, 8259, поглотители портов), `nvme_pci` (NVMe как PCI-функция 00:04.0, handoff v1.3), `pci_ecam`, `acpi_pm` и `acpi_tables`. Они задумывались для прямой загрузки Linux на той же плате, но запускает их другой цикл исполнения.

## Варианты

### (a) Расширить профиль прошивки до того, что исполняет stub и ядро

Профиль `PagedCpl0FirmwareBootV1` получает недостающие кодировки (`endbr64`, формы `rol`, `mov`, `imul` и остальные из инвентаря, затем всё, что понадобится ядру после ExitBootServices).

- Плюсы: плата и цикл прошивки остаются как есть; каждый шаг маленький и проверяется тестом на соседей кодировки.
- Минусы: допуск по точным кодировкам не масштабируется на чужой код: по оценке 119 различных кодировок только в stub, и неизвестно, сколько из них исполнится; каждая остановка — отдельный срез с ISSUE и ревью. `PagedCpl0FirmwareBootV1` — не вторая копия семантики CPU, а фильтр допуска поверх той же семантики `od-isa` ([CPU_CONTRACT.md](../specs/CPU_CONTRACT.md)), поэтому довод о дублировании здесь не применим. Реальная цена (a) другая: (1) процесс допуска не ограничен по объёму, потому что список разрешённых кодировок растёт по одной остановке; (2) профиль привязан к выводу компилятора: форма из ISSUE-621 появилась из кода ROM только на ветке, которую прежние образы не проходили, и тот же риск возвращается при каждой пересборке ROM или смене версии компилятора.
- Не снимает ISSUE-620 (политика LoadImage) и ISSUE-621 (форма в коде ROM — снимет, как отдельная кодировка).

### (b) Единая плата «UEFI + Linux»: прошивка, `linux_profile` и `nvme_pci` в одном цикле

Прошивка и гость исполняются через `Cpl0ProfileSet` (им выполнены прогоны Linux-direct, S4/S5), а устройства платы прошивки (TPM CRB, NVRAM, дисплей, NVMe) подключаются к той же шине, что и Linux-устройства.

- Плюсы: одна семантика CPU для обоих этапов; чужой EFI-код и ядро исполняются одним набором; опции платы уже существуют. Снимает ISSUE-621 для кода ROM, если набор допускает форму (это надо проверить).
- **Главная работа по (b).** Сочетание «ROM + `linux_profile`» сегодня неработоспособно. `FirmwareMmio` (NVRAM, дисплей, NVMe, TPM) передаётся только в `run_paged_firmware_probe` ([firmware_board.rs](../../crates/od-machine/src/firmware_board.rs), около строк 2798–2806). При `linux_profile` `run_boot_with` выключает профиль прошивки (`firmware_boot_profile = !large_ram && !has_linux_profile()`, около строки 3796), и ROM идёт через `run_paged_probe_with_rdtsc` без этих MMIO: прошивка не доберётся ни до NVRAM, ни до NVMe, ни до TPM. Работа по (b) — подключить `FirmwareMmio` в цикл `Cpl0ProfileSet` (`run_linux_boot_cpl0_set`, около строки 3048, он уже принадлежит той же плате) так, чтобы один цикл исполнения обслуживал и ROM, и гостя.
- Минусы и непроверенное: (1) не измерено, входит ли весь код ROM в CPL0-набор (то же статическое сравнение для ELF прошивки не строилось); (2) прошивка работает с NVMe через handoff-устройство 8, а `nvme_pci` даёт Linux PCI-функцию и handoff v1.3: совместимость двух описаний одного контроллера в одном запуске не доказана; (3) цикл `run_linux_boot_cpl0_set` должен получить то, что цикл прошивки уже делает (MMIO устройств, остановка по Reset/Shutdown, `FirmwareMmio` выше); (4) ISSUE-620 остаётся. Ожидаемая цена выше, чем у (a), на первом срезе, и ниже на стадии ядра.

### (c) Другой путь

- (c1) Собственный загрузчик Linux внутри прошивки (приложение FV читает ядро с ESP по протоколу загрузки x86 и передаёт управление минуя EFI stub, с `boot_params` и информацией о карте памяти и таблицах). Чужой EFI-код не исполняется; дальше работает CPL0-набор. Но это не «стандартный загрузчик дистрибутива»: S7-31 требует, чтобы ОС загружал штатный загрузчик (shim/GRUB/EFI stub), поэтому такой путь дал бы лишь частичное подтверждение (efivarfs и таблицы), а критерий готовности S7-31 не закрывается. Требует отдельного решения владельца о границе требования.
- (c2) Штатные shim/GRUB вместо EFI stub: исполняют больше чужого кода до ядра, чем stub (не измерено), и упираются в тот же барьер профиля. Не рассматривается как путь к решению.
- (c3) Менять устройство образа Debian d-i: сырой ISO прошивка не видит (защитная MBR отсутствует, GPT в LBA 0, тип разделов Basic Data); это вопрос S7-35-образной конвертации, а не профиля CPU.

## Предложение

Не решение; рекомендация для Opus high. Вариант (b) в уточнённой формулировке: один цикл исполнения `Cpl0ProfileSet` с `FirmwareMmio` для ROM и гостя. Основание: код Boot Services (ROM) исполняется до ExitBootServices, код Runtime Services (тоже ROM) после, на том же CPL0, поэтому исполнитель нельзя выбирать по событию, он должен быть один. Перед выбором выполнить две дешёвые проверки: (1) инвентарь форм кода ROM против CPL0-набора (скрипт `tools/build/s7_31a_efi_stub_isa_inventory.py` принимает образ PE; для ROM нужна ELF-версия входа); (2) прогон одного и того же ROM под двумя исполнителями (профиль прошивки и `Cpl0ProfileSet` с `FirmwareMmio`) до сообщения «no bootable option» и сравнение их выводов COM1 между собой. Эталон COM1 `boot_core` для этого сравнения не используется: после слияния S7-23 он изменился (ISSUE-611 закрыт). ISSUE-620 нужно закрывать при любом варианте и сначала: без него stub не стартует. Если проверка (1) покажет, что в наборе CPL0 нет части форм ROM, эти формы добавляются в набор CPL0 или ROM пересобирается без них; переключать исполнителя по событию (например, в момент `StartImage` чужого образа) нельзя: stub вызывает Boot Services, а ядро после ExitBootServices вызывает Runtime Services, и то и другое — код ROM на CPL0. Переключение возможно только по области кода, и это отдельное решение. Статус ADR остаётся «Предложено» до выполнения P0 (две проверки выше и политика LoadImage ISSUE-620).

## Решение (2026-11-21)

Принят вариант (b). Цикл профиля прошивки (`PagedCpl0FirmwareBootV1`, `run_boot`) не удалён: он остаётся путём прежних системных проверок. Для Linux через собственную UEFI используется отдельный путь: `run_firmware_unified` (`crates/od-machine/src/linux_direct.rs`), `boot-firmware --cpu-loop unified`. Что установлено в S7-31c (подробности и таблица — в отчёте):

- Формы ISSUE-621 и ISSUE-622 (`and qword [mem], imm8`, `endbr64`) набор CPL0 исполнял и до решения; дефектом была узость профиля прошивки. Ответ на «входит ли код ROM в набор CPL0»: не весь; на пути до stub потребовалась модель входного состояния (GDTR и сегментные кэши) и две формы набора (`NOTRACK JMP r64` на CPL0, `REPE CMPSB` из любого состояния флагов).
- Устройства платы прошивки (NVRAM, дисплей, NVMe, TPM) — устройства шины; цикл набора обслуживает их через привязки шины после разрешения окон. Отдельный `FirmwareMmio` в цикле набора не потребовался.
- Единый цикл снимает остановки ISSUE-621 и ISSUE-622 (`Unsupported 131`, `Unsupported 30`). В S7-31d после общих форм `FNSTSW/FNSTCW m16` stub доходит до входа в `exit_boot_services` (ISSUE-622 закрыт), а следующая остановка — `#PF` по адресу `0x59253e0` после входа, `HLT` прошивки (ISSUE-632); S7-31e измерил причину: нарушение NX при выборке из страницы RAM, отображённой прошивкой как `PRESENT | WRITABLE | NO_EXECUTE`; S7-31f исправил её (страницы `AllocatePages` типов Code исполняемы), ISSUE-632 закрыт, следующая остановка — `MOV SS, EAX` в коде ядра (ISSUE-633).
- Открыто: совместимость описаний NVMe (handoff-устройство прошивки и PCI-функция `nvme_pci`; загрузчик ROM по-прежнему отвергает `nvme_pci`); Runtime Services после ExitBootServices; ISSUE-620 закрыт в S7-31b.

## Что нужно для S7-31 целиком

1. Политика LoadImage для образа без перемещений и с ImageBase 0 (ISSUE-620), тесты на реальные заголовки ядра.
2. Решение по этому ADR и реализация выбранного варианта (S7-31b), включая форму в `load_into` (ISSUE-621) и `endbr64` с остальными формами stub (ISSUE-622).
3. Прогон EFI stub до ExitBootServices: перечень запрошенных протоколов (трассировка прошивки), нужные stub сервисы (LoadedImage, SimpleFileSystem и разбор `initrd=` или LoadFile2, GetMemoryMap, AllocatePages, GetVariable для `Boot####`, при желании RNG и TCG2, таблицы ACPI и SMBIOS), результат ExitBootServices.
4. Достаточный объём RAM (плата прошивки даёт 128 МиБ; для ядра с распаковкой это не проверялось).
5. После ExitBootServices: Runtime Services (`SetVirtualAddressMap`, `GetVariable`/`SetVariable`) для `efivarfs`, GOP для `efifb`/`simpledrm` и дамп framebuffer (S10).
6. Принятое Linux guest evidence этапа 5, S4-39 (userspace), S4-30 (PCI-привязка NVMe), S4-31 (ACPI), принятый S7-16 — предпосылки из плана этапа 7.
7. Параметры загрузки, доставляемые OptionalData записи `Boot####` (проверено S7-31a: прошивка передаёт её как LoadOptions); initrd по пути ESP (генератор ESP получил `--boot-file`).
8. Критерии S7-31: строка `init` на COM1, `cat /sys/firmware/efi/efivars/...`, `dmesg | grep -i acpi` без `error`, скриншот framebuffer.

## Последствия принятия

Решение определит, где живёт семантика CPU для чужого EFI-кода, и тем самым границу между S7-31b и S5/S6. Документы `UEFI_PROFILE.md` и `FIRMWARE_BOOT.md` обновляются после принятия, а не в этом срезе.
