# ADR-0018 — Стратегия блочного исполнения (PERF-31)

**Дата:** 2026-11-24

**Задача:** [PERF-31](../plans/CPU_CORE_PERF.md#perf-31-решение-о-стратегии-блочного-исполнения) линии [CPU_CORE_PERF](../plans/CPU_CORE_PERF.md); вход — [PERF-32](../plans/CPU_CORE_PERF.md#perf-32-какую-долю-загрузки-покрывает-существующий-jit) (отчёт линии, раздел 7.22); следующая задача — PERF-33 (план ступени E).

**Статус:** принято (вариант а). Блоки включены по умолчанию при --fast-path (E1, отчёт 7.30); флаг --block-cache-prototype удалён, --no-block-cache выключает. Замеры: K3200 +88,7 % локально, +81,6 % на M1.

**Замена:** Заменено [ADR-0022](ADR-0022-turbo-jit.md) (2026-11-25): код удалён из unified-цикла (кеш предекодированных блоков, кеш декодированных инструкций, флаги `--no-block-cache`, `--block-stats`, `--block-cache-verify`). Исходники — в коммите `ca2fc78` (последний, где они есть); ссылки на удалённые файлы ниже даны как текст. Текст решения не переписывался: это история.

**Код, на который ссылается документ:** HEAD `2e2d68f`. «PMA» — [paged_memory_adapter.rs](../../crates/od-machine/src/paged_memory_adapter.rs); «DIC» — `decoded_instruction_cache.rs` (файл удалён); «JC» — [JIT_CONTRACT.md](../specs/JIT_CONTRACT.md).

## Вопрос

После ступени D (кеш декодирования PERF-10, быстрый путь Г1–Г5 PERF-23/24/25, несколько инструкций за вызов PERF-25, прототип кеша трансляции данных PERF-11) цикл платы исполняет 6,52 млн инстр./с (K3200 с `--fast-path --data-cache-prototype`, раздел 7.21). Каждая инструкция по-прежнему проходит поиск в кеше декодирования, проверку шлюза кеша выборки, допуск быстрого пути и диспетчеризацию по варианту `Operation`. Какой механизм блочного исполнения выбрать следующим: кеш заранее декодированных блоков без генерации кода, подключение `od-jit` к циклу платы или оба яруса?

## Факты

1. **Покрытие существующего JIT** (PERF-32, раздел 7.22). Фактически 0 %: цикл платы (`tools/runner/src/firmware_boot.rs`, unified) od-jit не вызывает. Верхняя граница по классам гистограммы: все пути — 57,27 % (300 млн) / 43,36 % (3,2 млрд), путь со страничной памятью и исключениями (`paged_host_loop`: формы S4-15 и атомарный V4) — 19,75 % / 14,95 %. Допущенные формы точные: регистры RAX..RBX, REX `48`, JZ/JNZ rel8, шесть форм MOV с памятью, одна инструкция на блок на страничной памяти, только 4 КиБ страницы кода.
2. **Покрытие быстрого пути интерпретатора** (ADR-0017, раздел 1; раздел 7.21): Г1–Г5 — 97,87 % / 93,24 % по гистограмме; в сверке сравнено 293,6 млн из 300 млн и 2,98 млрд из 3,2 млрд.
3. **Последний профиль K6** — HEAD `0cfe874` (раздел 7.19), до PERF-25 и PERF-11, «своё» ядро / прошивка: `step_configured_with_profile_mode` 44,55 / 40,32 %; `run_cpl0_set_loop_impl` 13,46 / 12,85 %; обход таблиц (`walk_long64_4k_with_writer` + `load_u64` + `access_long64_4k_internal_windowed`) ≈ 12,5 / 12 %; `run_configured_with_profile_mode` 4,65 / 4,30 %; `_platform_memmove` 4,34 / 4,28 %; `DecodedInstructionCache::lookup` 0,96 / 3,58 % (в разделе 7.12 на `331df9d` — 3,67 % в окне ядра). **Профиля на `2e2d68f` нет**: после PERF-25 и PERF-11 скорость выросла с 4,07 до 6,52 млн инстр./с, доли сместились, и оценки ниже по старому профилю — только порядок величины.
4. **Кеш декодирования** (DIC 1–27): ключ — линейный RIP, физическое место первого байта (регион, смещение), поколение 4 КиБ страницы кода (читается до байтов), `AccessContext`; попадание дополнительно требует, чтобы кеш выборки держал трансляцию страницы RIP для текущего снимка (права выборки, U/S, SMEP, биты A — как у побайтной выборки). Каждая зафиксированная запись RAM повышает поколение своей страницы, поэтому самомодифицирующийся код, запись устройства и DMA дают только промах. Запись делается только для инструкции, все байты которой лежат на странице RIP. Таблица direct-mapped, 2^16 записей, живёт между квантами.
5. **Границы вызова набора** (PERF-25, раздел 7.20): пакетный вызов возвращается ровно после инструкции с событием — смена CR0/CR3/CR4, CPL, IF/RF/TF/IOPL/AC/NT/VM, `sti_shadow`, `activity`; MOV CR3/EFER, вход в CPL3, HLT, исключение, `PortIo`, `Unsupported`, частичный REP; обращение к порту или MMIO; RIP — кандидат трассы; `stop()`; вектор IRQ к доставке; конец бюджета. Исключение внутри вызова учитывает отретайренные до него инструкции (исправленный блокер `Run(Fault)` с `instructions_executed > 0`).
6. **Эквивалентность** (план, раздел 4.1): JSON runner (`retired`, `quanta`, `virtual_ns`, `rip`, итоговое состояние, прерывания, счётчики), COM1 и NVRAM побайтно равны прежним. Доставка IRQ и конец кванта должны приходиться на ту же границу инструкции, что у интерпретатора.
7. **Механизмы JIT, которые уже есть** (JC): ключ `TranslationKey` (flavor, снимок контекста, entry RIP, байты, зависимости, диапазоны выборки); `MultiEntryBlockCache` (FIFO/LRU) на fixture-пути; production-кеш на одну запись (S6-42d); повторный допуск по RIP, физической странице, поколению и байтам (S4-15, S4-16); выход `CodeInvalidated` при записи в страницу активного блока (S4-16i, S6-41d); сторожа бюджета и STOP-байта перед каждой инструкцией (S3-28c); PC-map и точный fault по инструкции только у атомарного V4; ARM64-энкодер собственный, LLVM запрещён (AGENTS.md).
8. **Записанная скорость JIT** (STAGE_3_CORE.md, раздел 2): прогретый FIFO 3,736–3,959 мкс против интерпретатора 0,726–0,751 мкс на корпусе fixture (интерпретатор быстрее ≈ 5,3 раза, S3-36b); холодный 6,64–6,69 мс против 0,164–0,166 мс (S3-35a). Для путей на страничной памяти скорость не измерялась.
9. **Границы крейтов** (ARCHITECTURE.md, раздел 5): цикл платы — `od-machine`; публикация исполняемой памяти — `od-host`; `od-machine` не переносит политику исполняемой памяти. `od-machine` зависит от `od-jit`, но не от `od-host`.

## 1. Варианты

- **(а) Кеш блоков без генерации кода.** Блок — последовательность заранее декодированных инструкций с одного входного RIP до первого перехода, конца 4 КиБ страницы, инструкции вне быстрого пути или предела длины. У каждой инструкции хранится указатель на обработчик быстрого пути (те же функции, что у общего пути: `exec_arithmetic`, `transfer`, `exec_call` и др.) и подготовленные операнды. Исполнитель блока работает внутри пакетного вызова PERF-25: после каждой инструкции — тот же учёт и та же проверка границы. Инструкция вне быстрого пути заканчивает блок и идёт общим шагом. Живёт в `od-machine` рядом с кешем декодирования и в `od-isa` (обработчики).
- **(б) od-jit для горячих блоков.** Счётчик входов блока; горячий блок компилируется собственным lowering в ARM64, публикуется через `od-host` и исполняется из цикла платы. Всё, что блок не допускает, а также холодный код — интерпретатор (текущий путь ступени D).
- **(в) Два яруса.** (а) — нижний ярус для всего кода; блоки (а) с большим счётчиком и допустимым составом компилируются по (б). Ключ, инвалидация и границы — общие.

Связывание: в блоке хранится индекс или указатель на следующий блок для прямого перехода и fallthrough с повторной проверкой поколения при входе. **E11 (2026-11-25), строка «Ленивые флаги», (а):** статический пропуск и ленивое состояние в проходе прототипированы и **не приняты** отсевом F100 (оба дороже базы вне разброса) — [ADR-0020](ADR-0020-lazy-flags.md); обработчики по-прежнему вычисляют флаги как общий путь.

**E13 (2026-11-25), строка «Поиск и связывание», (а):** ссылка с прямого выхода блока (Jcc, JMP rel, CALL rel) на блок той же 4 КиБ страницы с проверкой поколения, кеша выборки, эпохи, контекста и серийного номера записи прототипирована и **не принята**: отсев F100 −3,4 % инструкций, но K3200 −1,19 % вне разброса (запись таблицы 64 → 128 байт удорожила полный поиск) — [ADR-0021](ADR-0021-block-links.md); после каждого блока — полный поиск.

**E9 (2026-11-25), строка «Доставка IRQ и конец кванта», (а):** полная граница — после каждой инструкции, кроме короткой внутри прохода одного блока (счётчик обращений к устройствам и атомарные флаги `stop`, только при «тихом» IRQ) по [ADR-0019](ADR-0019-block-run-boundary.md) (принят 2026-11-25; приёмка по скорости — пара K3200 E9); место и порядок наблюдаемых границ не меняются.

**Оценка выигрыша (гипотеза, не замер).**

- (а) убирает на каждой инструкции, кроме первой в блоке: поиск в кеше декодирования (0,96–3,58 % «своего»), проверку шлюза кеша выборки, допуск быстрого пути и `match` по варианту `Operation` (заменяется вызовом по указателю), часть накладных расходов вызова набора. Доля этих расходов после PERF-25 неизвестна (факт 3); по старому профилю — единицы процентов, но при 6,52 млн инстр./с относительная доля постоянных расходов выше. Средняя длина блока неизвестна.
- (б) дополнительно убирает тело обработчика регистровых инструкций (АЛУ, переходы, MOV reg). На fixture-корпусе текущий JIT в 5,3 раза медленнее интерпретатора (переход Rust↔native и helper флагов на каждый блок короткий). Выигрыш на плате возможен только при длинных горячих блоках, связывании и ленивых флагах; до замера неизвестен даже знак.
- (в) = выигрыш (а) на всём коде плюс выигрыш (б) на доле инструкций в горячих полностью допустимых блоках; эта доля измеряется прототипом (а).

## 3. Предварительный выбор

**Предварительно: (в) как направление, реализация по ярусам — сначала только (а); (б) — после измерения (а) и только для горячих блоков, если прототип (б) покажет выигрыш над (а).** Вариант (б) без нижнего яруса предварительно отвергнут.

Основания (по чтению, без замеров):

1. (а) переиспользует уже проверенные механизмы ступени D: обработчики Г1–Г5 (одна семантика), учёт исключений и список событий PERF-25 (точные границы IRQ и кванта по построению), ключ и инвалидацию кеша декодирования, кеш трансляции данных PERF-11, сверочный режим PERF-22. Новых доказательств требует только сам исполнитель блока и его кеш.
2. (б) сегодня не имеет ни покрытия (0 % фактически, ≤ 19,75 / 14,95 % на страничной памяти по классам), ни модели состояния, ни многоинструкционных блоков с памятью и точным fault, ни выходов на событиях платы (PERF-32, пункты 1–10). Подключение — новая работа по всем строкам таблицы раздела 2, а записанная скорость JIT на fixture хуже интерпретатора.
3. (в) не закрывает (б): блоки (а) — естественная единица компиляции, их ключ, инвалидация и счётчики входов нужны (б) в любом случае.

Это решение **не окончательное**: AGENTS.md запрещает выбирать вариант на критичном участке без замера прототипов, а PERF-31 шаг 3 не выполнен.

## 4. Сверка с ARCHITECTURE.md, раздел 5

Архитектура предполагает конвейер JIT (IR, lowering, карты состояния, кеш блоков, инвалидация, безопасное освобождение) и интерпретатор как обязательный режим диагностики. Вариант (а) — оптимизация интерпретатора, архитектуре не противоречит, но ярус предекодированных блоков в разделе 5 не описан: при принятии его надо добавить туда (PERF-41). Вариант (б) и верхний ярус (в) совпадают с описанным JIT runtime, но требуют внедрения исполнителя блоков в цикл `od-machine` без переноса политики исполняемой памяти в `od-machine` (граница крейтов, факт 9).

## 5. План измерения (PERF-31 шаг 3 — не выполнен)

## 6. Условия пересмотра

1. M0 покажет, что поиск, шлюз, допуск и диспетчеризация вместе дают меньше 2 % — выигрыш (а) не дотягивает до порога K4; (а) снимается, рассматривается (б) или другие задачи (обход таблиц, PERF-12).
2. M1 покажет среднюю динамическую длину блока меньше 3 инструкций — (а) почти не экономит на поиске; пересмотреть правило границы блока (например, через безусловные переходы и CALL) или отказаться от (а).
3. P-b не быстрее P-a на регистровом блоке в 2 раза (вход/выход, флаги) — верхний ярус (б) снимается.
4. M0 покажет, что основное время — тела обработчиков (вычисление флагов, адресация), а не диспетчеризация — (б) идёт раньше, (а) становится только инфраструктурой ключа и инвалидации.
5. Изменится нагрузка: значимая доля CPL3 (пользовательский режим), SMP или 2 МиБ страницы кода — пересмотреть правила (а) (CPL3 по одной инструкции, SMP-инвалидация) и допуск (б).
6. Обязательный пересмотр — после замеров раздела 5: этот ADR дополняется разделом «Итог» с числами и переводится в «принято» или «отклонено».

## Последствия

- PERF-33 (план ступени E) не начинается до «Итога».
- Если (а) будет принят: новый кеш в `od-machine` по образцу кеша декодирования (тот же ключ и правило поколения), исполнитель внутри пакетного вызова PERF-25, включение за флагом и только в unified-цикле платы (план 4.4), обязательный сверочный режим и тест записи в страницу активного блока; описание яруса в ARCHITECTURE.md (PERF-41).
- Если будет принят верхний ярус (б): отдельный контракт исполнителя native-блоков для цикла `od-machine` (внедрение из `od-host`), модель состояния с `rflags_defined`, многоинструкционные блоки с памятью и точным fault, выходы на событиях платы; каждая форма — отдельный допуск по JIT_CONTRACT.

## Открытые вопросы

1. Средняя динамическая длина блока и доля горячих регистровых блоков (M1).
2. Доля постоянных расходов на инструкцию после PERF-25 и PERF-11 (M0).

### Дополнение E10 (2026-11-25): обработчики, выбранные при построении блока — решение Opus (high) до кода

Задача [E10](../plans/CPU_CORE_PERF_BLOCKS_PART2.md#e10-обработчики-выбранные-при-построении-блока) плана части 2 ступени E. Меняет контракт 1 раздела 4 [первой части](../plans/CPU_CORE_PERF_BLOCKS.md) («каждая инструкция блока исполняется `try_fast_step` с сохранённым декодом»). Код на момент решения — HEAD `1500400` (E9 — `26a3e1a`). Ревью решения (Opus high, только чтение, 2026-11-25): блокеров нет, «принять с правками»; правки M1–M5 внесены ниже (M5 — сжатие `FlagEffects` в `u16` снято: эффекты хранятся как есть, размер держит запрет `Operand` в вариантах). «EX» — `crates/od-isa/src/execute.rs`, «PB» — `crates/od-isa/src/predecoded_block.rs`.

**Факты.** (1) `try_fast_step` (EX, `#[inline(never)]`) на каждую инструкцию блока делает: динамический допуск (CPL0, TF = RF = 0, тень `Clear`) и статический (group1, FS/GS), `match` по `Operation`, внутри ветки — разбор форм `Operand` (регистр/память/непосредственное), для переходов — допуск формы `executable` (карта, байт, префиксы по умолчанию), для АЛУ — хвост `instruction.flag_effects()` (большой `match` по `Operation`) и `apply`. (2) Статическое правило записано дважды: `fast_block_role` (PB) и `try_fast_step`; переходы с префиксами DS/CS/66/67 фильтр допускает, а быстрый путь отклоняет (отчёт 7.28; тест `fast_step_static_filter_tests`, категория `role_only`). (3) KC `e8` (отчёт 7.33): строка (г) «исполнение в блоке» — 27,96 % / 4,87 % (прошивка / ядро), флаги — 4,30 % / 1,35 %; строка (в) «граница + проход блока» (в ней встроенный `block_step`) — 40,83 % / 24,74 % до E9. (4) Тип памяти платы — `PagedMovMemoryAdapter<'a>` (время жизни вызова), блоки живут в кеше платы (`DecodedBlockCache`, `od-machine`) дольше вызова. (5) `size_of::<Instruction>()` = 72; граница памяти таблицы блоков — тест `the_memory_of_the_table_is_bounded` (38 404 096 байт при 2^13 слотах и блоках до 64 инструкций; предел 64 МиБ).

**Решение 1 — представление обработчика.** Обработчик — значение `FastHandler` (`Copy`, `Eq`): вариант перечисления `FastOp` = (операция, форма операндов) с готовыми операндами — `RegisterView`, `MemoryOperand`, непосредственное значение, вид операции (`ArithmeticKind`/`LogicKind`/`ShiftKind`/`ConditionCode`), размер операнда, ширина стека, смещение перехода, и (для АЛУ и IMUL) `Instruction::flag_effects()`, посчитанное при выборе (`FlagEffects` как есть, без сжатия). Варианты хранят только `RegisterView` (3 байта), `MemoryOperand` (16), `u64` и мелкие поля — **`Operand` (24 байта) внутри вариантов запрещён** (размер, решение 5). Длина инструкции берётся из `Instruction` рядом (поле `length`). Выбор — `fast_handler(&Instruction) -> Option<FastHandler>` (EX), **единственное место статического правила**: префиксы group1, сегмент FS/GS, классы операций, формы операндов, форма `executable` переходов (карта, байт, префиксы по умолчанию). Исполнение — одна функция `run_fast_handler` (EX): `match` по варианту, каждая ветка — свой экземпляр для известной формы операндов, который вызывает общие функции общего пути (`exec_shift`, `exec_imul`, `fast_alu_into_memory`/`fast_alu_from_memory` с `arithmetic_result`/`logic_result`, для регистровых АЛУ — см. «Отступление 1», `read_memory_operand`, `write_memory_operand`, `extended_source`, `exec_lea`, `exec_stack_register`, `exec_call`, `exec_return`, `relative_target`, `ConditionCode::evaluate`). Формулы флагов и адресации не копируются.
- Блок (`DecodedBlock`) хранит пары (`FastHandler`, `Instruction`) в одном `Arc<[…]>`: `Instruction` нужен сверке, диагностике `--block-stats` (`block_run_cut`) и `exec_shift` (размер и `flag_effects_for_count`). Построение блока (`DecodedBlock::from`) выбирает обработчик каждой инструкции; инструкция без обработчика в блок не попадает по построению (`predecode_block` берёт только инструкции с `fast_block_role`), а прямое построение из такой инструкции — ошибка программы (паника).
- `fast_block_role(i)` = `fast_handler(i).map(роль варианта)`: `Terminator` у Jcc/JMP/CALL/RET, иначе `Straight` (одно правило, без двойного вычисления на горячем пути: в блоке правило считается один раз при построении, вне блока — один раз в `try_fast_step`; это закрывает GE2 первой части без причины отката E3).
- `try_fast_step` вне блоков = динамический допуск `fast_admitted` + `fast_handler` + `run_fast_handler` (тот же исполнитель с той же структурой операндов; различается только место, где лежит результат `fast_handler`), поэтому `--fast-path-verify` проверяет исполнитель блока.
- Отказ после выбора обработчика — только динамический допуск (CPL0, TF/RF, тень) и `NopModrm` без политики управляющих регистров (параметр вызова, как сейчас); оба — до любого эффекта.

**Отклонённые представления.** (б) Указатель на функцию, мономорфизированную по типу памяти: экземпляр для `PagedMovMemoryAdapter<'a>` нельзя хранить в кеше, живущем дольше `'a`, без стирания типа; `fn(&mut dyn GuestMemory, …)` делает каждое обращение к памяти виртуальным вызовом. `match` по перечислению компилируется в одну таблицу переходов — тот же один косвенный переход, без вызова и без стирания. (в) Хранить только `Instruction` и номер обработчика: операнды снова разбираются из `Operation` на каждой инструкции — шаг 3 плана не выполнен. (г) Специализация по размеру операнда (шаг 6 плана) в этом шаге **не делается**: `arithmetic_result`/`logic_result` принимают размер аргументом и не встроены; экземпляры с константным размером потребовали бы встроить общую функцию флагов в каждый (×4 кода ветки) ради строки «флаги» (г) KC `e8` (≈ 46 / 14 инструкций хоста на гостевую на всё, а не на разницу); флаги — предмет E11 (ленивые флаги). Специализация по (операция, форма) — вариантами `FastOp`. Отступление от шага 6 записано здесь.

**Решение 2 — изменение состава блоков (шаг 2 плана, разрешённое).** Jcc/JMP/CALL/RET вне формы `executable` (префиксы DS/CS/66/67/REX и т. п.) больше не входят в блок: блок кончается перед ними (`BlockEnd::OutsideFastPath`, причина `branch_prefix_filtered`), причина `branch_prefix_refused` становится нулевой. Изменение `block_stats` на 300 млн записывается в отчёт.

**Решение 3 — динамический допуск в проходе (шаг 5 плана), два варианта для отсева F100** (константа времени компиляции; Д2 — только в режимах короткой границы E9, см. «Диагностические режимы»): **Д1** — на каждой инструкции, как сейчас; **Д2** — один раз в начале прохода (при выборе блока курсором), на следующих инструкциях того же прохода — только `debug_assert!`. Доказательство Д2: вход допуска — `context.privilege` (константа вызова цикла), биты TF и RF `state.rflags` и `state.sti_shadow`. Между двумя соседними инструкциями прохода исполняется только предыдущая инструкция блока и хвост цикла: инструкция блока не пишет TF/RF и тень (ADR-0019, раздел 1, строки 5 и 8: в блоке нет POPF, IRET, STI, MOV SS/POP SS; АЛУ, сдвиги и IMUL пишут только флаги арифметики), хвост пишет тень только при `old_shadow == Blocking` (невозможно: допуск требовал `Clear`), а проверка пакета (`BatchBoundary::check`) получает состояние только для чтения; проход кончается (курсор сбрасывается) на любом отказе, ошибке, переходе и отказе удержания. Это близко к отклонённому PERF-06 (+1,43 %): выигрыш — гипотеза. Выбор: Д2, если цена инструкции F100 у Д2 ниже, чем у Д1, вне разброса (интервалы [min, max] `host_instr_per_guest` не пересекаются); иначе Д1 (проще).

**Решение 4 — сверка (шаг 4 плана).** `--block-cache-verify` кроме декода сравнивает сохранённый в блоке обработчик с `fast_handler` свежего декода; расхождение обработчика — то же расхождение сверки (`BlockCheckDivergence` получает оба обработчика). Исход исполнителя сверяет `--fast-path-verify` (тот же исполнитель вне блоков).

**Решение 5 — память.** Граница таблицы блоков пересчитывается в `the_memory_of_the_table_is_bounded` по `size_of` элемента (обработчик, `Instruction`); предел 64 МиБ сохраняется: 2^13 × 64 + 2^13 × (16 + 64 × E) ≤ 64 МиБ даёт E ≤ 126, при выравнивании 8 — E ≤ 120, то есть обработчик ≤ 48 байт. Тест закрепляет константами `size_of::<FastHandler>()` и размер элемента (по образцу `INSTRUCTION_BYTES`).


**Отступление 1 (от списка функций шага 1 плана).** Регистровые формы АЛУ (`Arithmetic`/`Logic` с регистром-приёмником и регистром или непосредственным источником) исполняются не вызовом `exec_arithmetic`/`exec_logic`, а их составом при CPL0: `state.read` приёмника (`read_rmw_destination` при CPL0 — это `read_operand` → `state.read`; ветка CPL3 недостижима при допуске CPL0), `state.read` источника или непосредственное, `arithmetic_result`/`logic_result` с размером `instruction.operand_size` (не `RegisterView::size()`), `state.write` результата, кроме CMP/TEST, затем `state.rflags`. Формула флагов — та же общая функция; прецедент — `fast_alu_from_memory` (G5). Inc/Dec/Neg/Not декодируются с непосредственным источником (`Immediate(1)`/`Immediate(0)`), который общие функции не читают. Эквивалентность сторожат тесты G2 (`every_g2_register_form_equals_the_general_path`: все виды и размеры, AH–BH без REX и SPL–DIL с REX, INC/DEC/NOT/NEG, TEST, 10 состояний флагов — против общего шага).

**Неизменность допущенного множества (ревью решения, M2).** Шаг 2 разрешает только одно изменение состава: префиксные переходы. Поэтому множество кодировок, которые обрабатывает `try_fast_step`, не меняется. Снято на HEAD `1500400` тем же генератором `fast_step_static_filter_tests` (временная печать, не коммитится): декодов 126 403, обработано 33 009 (`Straight` 32 128, `Terminator` 881), `role_only` 11 273, FNV-1a-64 отсортированного множества обработанных кодировок `0xed771809cfcbdeab`. После E10 тест требует: обработано ровно 33 009 с тем же хешем, `role_only = 0` (фильтр блока = быстрый путь), `Straight`/`Terminator` — 32 128 / 881.

**Диагностические режимы (часть 2, раздел 4 п. 4; ревью решения, M1).** Обработчики — не отключаемая оптимизация, а единственный исполнитель быстрого пути: старого исполнителя после E10 нет, и вне блоков (`try_fast_step`, в том числе в `--fast-path-verify` и его повторе) работает тот же код; в диагностических режимах, где быстрый путь или блоки выключены (план линии, 4.2), они выключены и сейчас. **Д2** (если его выберет отсев) — оптимизация и включается только там, где включена короткая граница E9 (ADR-0019, 2.4): блоки без `--block-cache-verify`, без трассы вызовов (`call_trace`) и без `--block-boundary-verify`. Цикл спрашивает об этом память один раз на вызов (новый метод `GuestMemory` с умолчанием `false`; адаптер отвечает «поле `decoded.pass` есть и не в режиме сверки»). В остальных случаях с блоками действует Д1.

**Мелкое (ревью решения).** `DecodedBlock` — новый тип (обёртка над `Arc<[BlockInstruction]>` с `Deref` на срез и построением `From<Vec<Instruction>>`/`FromIterator<Instruction>`), а не псевдоним. Сравнение обработчиков в `--block-cache-verify` при равных инструкциях почти тавтология: оно сторожит расхождение места построения (обработчик блока выбран не тем правилом или не из той инструкции). Причина `refused` в `--block-stats` после E10 значит только динамический отказ (а при Д2 — только на первой инструкции прохода); `branch_prefix_refused` остаётся в формате JSON и равна нулю. Путь вне блоков (`try_fast_step`) — два `match` (выбор и исполнение) вместо одного с хвостом `flag_effects`; `fast_handler` в нём встроен; отдельный замер пути без блоков в E10 не делается (решение — K3200 в режиме с блоками), это оговорка отчёта.
