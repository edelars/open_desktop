# Политика зависимостей и происхождения

**Статус:** действует; уточнена по согласованию с пользователем. **Дата:** 22 октября 2026 года.

Политика задаёт границу между разрешённой инфраструктурой и собственными ключевыми компонентами Open Desktop. Начальный стек описан в [ADR-0001](../decisions/ADR-0001-dependencies-and-boundaries.md), разрешение библиотек общего назначения — в [ADR-0002](../decisions/ADR-0002-general-purpose-libraries.md). Общего запрета сторонних runtime-пакетов больше нет.

## Начальный стек

- Приложение macOS и его UI пишутся на Swift с системными SwiftUI/AppKit API.
- CPU, JIT, модели машины и прочее host-ядро пишутся на Rust.
- Для межъязычной границы применяется небольшой собственный C ABI; формат ABI описывается отдельно до его реализации.

Это начальные решения, а не утверждение, что перечисленные компоненты уже реализованы.

## Разрешённые инструменты и системные компоненты

Допустимы стандартные библиотеки языков, штатные компиляторы и линкеры, SDK, системные framework и API macOS, Metal, системная криптография, файловые и сетевые API. Системный компилятор Rust может использовать LLVM как backend при сборке. Это не разрешает подключать LLVM к приложению как библиотеку runtime-JIT или транслятора.

Допустимы штатные компоненты поддерживаемой гостевой ОС, включая её загрузчик и драйверы. Они используются как часть гостевой ОС и не копируются в проект как реализация Open Desktop.

## Разрешённые библиотеки общего назначения

Допустимы сторонние библиотеки в runtime, dev- и build-зависимостях, если они предоставляют общую инфраструктуру и не заменяют собственную ключевую технологию:

- логирование, диагностика, CLI и конфигурация;
- сериализация и разбор общих форматов данных;
- коллекции, очереди, синхронизация и асинхронная инфраструктура;
- bindings системных API, файловые и сетевые вспомогательные средства;
- криптографические примитивы без готовой реализации TPM/firmware;
- инструменты тестирования, генерации входов, fuzzing и измерений.

Это категории разрешённых зависимостей, а не поручение заранее добавить пакеты каждой категории. Список не является жёстким whitelist имён. Решение принимается по фактической ответственности пакета, включённым features и транзитивным зависимостям. Правила действуют и для Rust, и для других языков проекта с учётом ограничений target/runtime.

Например, общий сериализатор может кодировать сообщения, но wire format, проверка ограничений, версионирование и поведение нашего протокола остаются проектными. Общая очередь не реализует модель памяти x86; системный binding не становится готовым JIT runtime. Криптографические примитивы не требуется писать самостоятельно.

## Самостоятельная реализация

В runtime продукта используются только собственные реализации следующих компонентов:

- семантика и декодер x86, интерпретатор, промежуточное представление, ARM64 emitter и JIT runtime;
- гостевая MMU/TLB, архитектурная модель памяти и модели виртуальной платы/устройств;
- firmware/UEFI, логика TPM-протокола и его состояния;
- собственные гостевые драйверы и графическая трансляция гостевых API;
- собственные форматы дисков/снимков и их семантика, с возможностью применять общие средства кодирования данных.

Готовые сторонние реализации этих компонентов запрещены как прямые и транзитивные зависимости, а также как перенесённые исходники/таблицы. LLVM не используется как runtime-движок. Общая библиотека не может служить обёрткой, скрывающей подключение готового эмулятора, decoder, assembler/emitter, JIT, firmware, TPM или графического транслятора.

## Учёт и проверка зависимостей

Перед добавлением внешней зависимости фиксировать в описании соответствующего компонента или решении:

1. Назначение и причину, почему стандартной библиотеки/уже имеющихся средств недостаточно.
2. Категорию: toolchain, системный API, общая runtime/dev/build-библиотека либо запрещённый ключевой компонент.
3. Источник, версию, лицензию и необходимые features. Проект распространяется под `AGPL-3.0-only` и по коммерческим лицензиям владельца, поэтому лицензия зависимости должна допускать оба варианта: MIT, Apache-2.0, BSD-2/3-Clause, ISC, Zlib, Unlicense, Unicode-3.0 или эквивалентная пермиссивная. Copyleft-лицензии (GPL, LGPL, AGPL, MPL, EUPL и подобные) требуют предварительного согласования с владельцем.
4. Существенные транзитивные зависимости и подтверждение, что они не включают запрещённый компонент.
5. Применимый target, ограничения runtime и способ проверки. Для критичного по скорости применения — ссылку на воспроизводимые замеры.

Разрешённые зависимости добавляются в рамках текущей задачи без отдельного подтверждения пользователя. Неясную категорию сначала исследовать. Пакет не добавляется, пока его соответствие политике не установлено. Исключение для запрещённого ключевого компонента требует явного изменения требования и архитектурного решения; прототип или test-only использование не являются способом обойти границу самостоятельной реализации.

- Rust: `Cargo.lock` хранится в Git. Изменения `Cargo.toml` и `Cargo.lock` проверяются вместе; новые пакеты должны иметь явное обоснование, происхождение и проверку соответствия этой политике. Получение/обновление заявленных пакетов выполняется отдельным шагом; после подготовки кеша проверка сборки выполняется с `--locked --offline`. Отсутствие пакета в локальном кеше не означает запрет этой зависимости. Сам по себе `--offline` не доказывает отсутствие сторонних пакетов или сетевых обращений build scripts.
- Swift: если будет добавлен Swift Package Manager, декларации зависимостей и разрешённые версии проверяются вместе; `Package.resolved` хранится в Git для приложения. Системные framework фиксируются как системные зависимости, а не как внешние пакеты. `apps/Package.swift` создан в S11-05a; внешних зависимостей нет, `Package.resolved` не возникает. `unsafeFlags` в манифесте нужны только для линковки `target/<profile>/libod_host.a` в `od-vmhost`; для корневого пакета это допустимо, как зависимость пакет не подключается.
- Firmware и гостевые компоненты собираются отдельно от host runtime; их зависимости проверяются по тем же правилам самостоятельной реализации.

На момент S0-01 workspace содержал шесть собственных crate без объявленных внешних зависимостей; Swift Package-манифесты отсутствовали. Это исходное состояние, а не запрет будущих разрешённых пакетов. Текущее уточнение политики само по себе не добавляет зависимостей и не означает готовность CPU-прототипа.

Новые транзитивные: `crypto-bigint 0.7.10` (MSRV 1.87; initial slice lock, updated to 0.7.11 by 2026-11-18 stable migration), `crypto-primes 0.7.2`, `elliptic-curve 0.14.3` (MSRV 1.87), `ecdsa 0.17.0`, `primefield 0.14.0`, `primeorder 0.14.0`, `sec1 0.8.1`, `rfc6979 0.6.0`, `signature 3.0.0`, `der 0.8.3`, `base16ct 1.0.0`, `ff 0.14.0`, `group 0.14.0`, `wnaf 0.14.1`, `cpubits 0.1.1`, `num-traits 0.2.19`; `rand_core 0.10.1`, `const-oid 0.10.2`, `subtle 2.6.1` (BSD-3-Clause) и остальные уже были транзитивными. Proc-macro и `serde` в дерево не входят. Ни один пакет не является реализацией TPM, UEFI или эмулятора (примитивы, большие числа, кодирование, константное время).
- **Подключено в S7-23 после ревью среза B (шифрование `outPrivate`):** `aes =0.9.4` (`default-features = false`, без `hazmat`; MIT OR Apache-2.0; MSRV 1.89 — наибольший в дереве `od-tpm`; используется `Aes128`) и `cfb-mode =0.9.1` (`default-features = false`, `features = ["zeroize"]`; MIT OR Apache-2.0; MSRV 1.85) — AES-128 в режиме CFB с полноблочной обратной связью, `crates/od-tpm/src/object.rs`. Транзитивно новых пакета два: `cipher 0.5.2` (MIT OR Apache-2.0; MSRV 1.85) и `inout 0.2.6` (MIT OR Apache-2.0; MSRV 1.85); `crypto-common 0.2.2`, `hybrid-array`, `cpubits 0.1.1`, `cpufeatures 0.3.1`, `zeroize 1.9.1` уже были в дереве. Всего срез B добавил 22 пакета (18 записаны в предыдущем пункте, 4 — здесь). Источник — crates.io, контрольные суммы в `Cargo.lock`; пакеты получены `cargo fetch` (сеть доступна), дальше `cargo build/test --offline` проходят. Backend AES на host-target выбирается самим крейтом (`cpufeatures`); для `x86_64-unknown-none` решение остаётся за прошивкой (ADR-0009, «Последствия»).
- **Подключено в S7-23, срез C1 (`TPM2_RSA_Encrypt/Decrypt`, `TPM2_ECDH_ZGen`):** новых пакетов нет, `Cargo.lock` не изменился. `rsa =0.10.0-rc.22`: к `pkcs1v15` добавлен feature `hazmat` (`default-features = false` сохранён; feature не тянет зависимостей) — только ради «сырого» RSA (схема NULL: `rsa::hazmat::rsa_encrypt`/`rsa_decrypt_and_check`, blinding от DRBG); RSAES-PKCS1-v1_5 (`Pkcs1v15Encrypt`, feature `pkcs1v15`) и RSAES-OAEP (`Oaep<Sha256>`, без feature) доступны уже без него. RSAES-расшифровка в этой версии `rsa` использует implicit rejection (отклонение от Part 3, 14.3.1 записано в `VTPM.md`). `p256 =0.14.0`: feature **`ecdh` не включён** — ADR-0009 и таблица выше его перечисляют, но `p256::ecdh::diffie_hellman` отдаёт только координату `x`, а `TPM2_ECDH_ZGen` возвращает точку `(x, y)`; она считается умножением точки `p256` под feature `arithmetic` (входит в `ecdsa`), и feature `ecdh` тянул бы `hkdf` без пользы. `ecdh` вернётся, если срезу C2 понадобится KDFe/`diffie_hellman`; решение ADR-0009 о семействе и версиях не меняется.
- **S7-23, срез C2 (policy-сессии, `ContextSave/Load`, `TPM2_HMAC`, `Quote`, `Certify`):** новых пакетов и изменений features нет, `Cargo.toml` и `Cargo.lock` не менялись. Контексты используют `aes`/`cfb-mode` (AES-128-CFB), `hmac`/`sha2` (HMAC-SHA-256, KDFa) срезов A–B; `Quote`/`Certify` — `rsa`/`p256` среза B; `TPM2_HMAC` — `hmac`.
- **S7-23, срез C3 (NV counter/bits/extend, `TPM2_GetTime`, NULL `signHandle`, шифрование параметров, snapshot v3):** новых пакетов и изменений features нет, `Cargo.toml` и `Cargo.lock` не менялись. Шифрование параметров использует уже подключённые `aes` и `cfb-mode` (AES-128-CFB, общая функция с `outPrivate`) и `hmac`/`sha2` (KDFa для XOR и CFB); `TPM2_NV_Extend` — `sha2`. XOR-обфускация, KDFa, формат snapshot — собственные.
- **Фактически подключено в firmware S7-06:** `sha2 =0.11.1` из crates.io для Authenticode SHA-256 с `default-features = false`. Locked-дерево на `x86_64-unknown-none` включает `cfg-if 1.0.5`, `cpufeatures 0.3.1`, `digest 0.11.3`, `block-buffer 0.12.1`, `crypto-common 0.2.2`, `hybrid-array 0.4.15` и `typenum 1.20.1`. `libc 0.2.190` в lockfile относится к другим целям и отсутствует в дереве firmware. SHA-2 собирается c `sha2_backend="soft"`, `alloc` не включён. [Проверка](../reports/STAGE_7_REPORT.md#s7-06--дайджест-authenticode).
- **S7-22:** `od-machine` связывает собственный `od-tpm` с MMIO и напрямую использует уже зафиксированный `zeroize =1.9.1` из crates.io (Apache-2.0 OR MIT, `default-features = false`, feature `alloc`) для очистки host-конфигурации, буфера CRB и временного ответа TPM. Новых пакетов в lockfile нет. Прошивка использует существующий программный SHA-256 из S7-06 для measured boot.
- Для `firmware/uefi/` в следующих задачах предусмотрены `sha1` для S7-22 и `rsa`, `der`, `x509-cert`, `spki` для S7-24 при необходимости по плану.

Собственными остаются протокол TPM, KDFa/KDFe, HMAC-DRBG, логика PKCS#7/Authenticode и политика цепочки сертификатов. Добавление crate'а сверх этого перечня, смена версии или features требует правки ADR-0009.

## Происхождение собственных данных

Собственные таблицы, генераторы и тестовые fixtures должны сопровождаться указанием исходного публичного стандарта или спецификации, её редакции и правил преобразования в проектный формат. Нельзя переносить сторонние исходники, таблицы или тестовые данные без зафиксированного разрешённого происхождения. Для каждого результата теста сохраняется способ его воспроизведения.

## Архитектура и производительность

Границы CPU, UI и процессов определяются ответственностью компонентов, изоляцией сбоев и явными интерфейсами. Любое решение, влияющее на критичный по производительности участок, принимается по повторяемым замерам целевого сценария с проверкой корректности; теоретическая сложность служит гипотезой, а не результатом.

Если применимая лицензия, происхождение или категория зависимости неясны, пакет не добавляется до прояснения вопроса и фиксации решения.
