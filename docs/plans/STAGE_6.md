# Этап 6. Несколько CPU и модель памяти x86 — пошаговый план реализации

Статус: **этап в работе**. S6-00…S6-16 (включая S6-12c) и S6-26 приняты после независимого ревью (состояние по gates — в разделе 8, «Фактическое состояние»; на 2026-11-17). Исходное состояние плана проверено 2026-11-13 на `main`, коммит `8625699`. Наличие каталога, пустого модуля или успешной сборки само по себе не закрывает задачу.

Нормативный объём — [этап 6 дорожной карты](../ROADMAP.md#этап-6-несколько-cpu-и-модель-памяти-x86). Обязательные границы задают [архитектура](../ARCHITECTURE.md) (раздел 5: «JIT runtime», «Память и MMU», «Планирование и устройства»; раздел о снимках), [карта проекта](../PROJECT_LAYOUT.md), [контракт CPU](../specs/CPU_CONTRACT.md), [контракт машины](../specs/MACHINE_CONTRACT.md), [контракт JIT](../specs/JIT_CONTRACT.md), [виртуальная плата](../specs/VIRTUAL_BOARD.md) и [политика зависимостей](../policies/DEPENDENCIES.md). Это план выполнения, а не вторая архитектура и не спецификация: спецификации создаются отдельными задачами ниже.

Главное уточнение области, без которого этап легко сделать неправильно: **несколько vCPU — это не «запустить два потока»**. Сегодня вся машина однопроцессорная по конструкции, а атомарность `LOCK`-инструкций держится только на том, что vCPU один (это прямо написано в комментариях кода). Поэтому этап идёт ступенями: сначала несколько vCPU исполняются **по очереди в одном host-потоке** (корректность доказуема без гонок), и только потом — параллельными потоками с настоящими атомарными операциями и барьерами.

Документ написан так, чтобы исполнитель с ограниченным контекстом мог взять **одну** задачу, выполнить её по шагам и честно отчитаться. Если какой-то шаг непонятен, остановиться и записать вопрос в отчёт, а не угадывать.

## 0. Как читать этот план

1. Выполнять ровно одну задачу `S6-NN` за один заход. Не начинать следующую, пока текущая не прошла ревью или не записан точный blocker.
2. У каждой задачи есть поля: **Где** (какие файлы трогать), **Сделать** (пронумерованные шаги), **Проверить** (конкретные команды и наблюдения), **Готово** (критерий приёмки), **Не делать** (частые ошибки). Делать только то, что перечислено.
3. Чекбокс `- [ ]` ставится в `- [x]` только после ревью по правилам [AGENTS.md](../../AGENTS.md). Исполнитель сам чекбокс не отмечает; он добавляет строку **Текущий статус (дата):** с фактами и ссылками на коммит и отчёт.
4. Слово «реализовано» означает: код есть, тесты проходят, ревью пройдено, отчёт записан. «Выполнено исполнителем, ожидает ревью» — это **не** «реализовано»; на такой результат нельзя опираться как на принятый. Слово «подготовлено» означает: есть документ или каркас без доказанного поведения.
5. **Блокировки наследуются по зависимостям.** Если задача зависит от задачи с пометкой `blocked до X`, она тоже заблокирована до X, даже если в её заголовке это не повторено. Подменять отсутствующий результат заглушкой запрещено. Будущую функциональность в `KNOWN_ISSUES.md` не писать: туда идут только найденные дефекты.
6. Все пути ниже даны от корня репозитория. Команды выполнять из корня репозитория. Большие образы (ядро, rootfs) в Git не попадают: они живут в игнорируемом `work/`. У каждого рецепта `tools/build/build_*.py` должен быть парный `test_build_*.py`.
7. Если тест модели памяти один раз показал запрещённый исход, а при повторе «прошёл» — это **дефект**, а не шум. Записать seed или условия, сохранить вывод и остановиться.

### Словарь

| Термин | Значение в этом плане |
|---|---|
| vCPU | Один виртуальный процессор гостя: собственные регистры, MSR, Local APIC и очередь событий. |
| BSP | Bootstrap processor: vCPU с индексом 0, который исполняется сразу после включения машины. |
| AP | Application processor: любой vCPU, кроме BSP. После включения не исполняет код, пока BSP его не запустит. |
| Local APIC (LAPIC) | Контроллер прерываний одного процессора. У каждого vCPU свой. |
| APIC ID | Номер процессора, которым адресуют прерывания. В этом плане APIC ID равен индексу vCPU. |
| IPI | Межпроцессорное прерывание: один vCPU посылает его другому записью в регистр ICR своего LAPIC. |
| ICR | Interrupt Command Register LAPIC (смещения `0x300` и `0x310`): куда, какое прерывание и в каком режиме послать. |
| INIT, SIPI | Два специальных IPI. INIT сбрасывает процессор-адресат. SIPI (Startup IPI) сообщает ему адрес, с которого начать исполнение. |
| Wait-for-SIPI | Состояние AP после включения или INIT: процессор не исполняет код и ждёт SIPI. |
| Trampoline | Маленький кусок гостевого кода, с которого стартует AP. Начинается в real mode и сам переводит процессор в long mode. |
| TLB shootdown | Действие гостевой ОС: изменив таблицы страниц, она посылает IPI остальным процессорам, чтобы те выбросили устаревшие переводы адресов. |
| `LOCK`-операция | Инструкция с префиксом `LOCK` (или `XCHG` с памятью): чтение, изменение и запись памяти, которые остальные процессоры видят как одно неделимое действие. |
| x86-TSO | Модель памяти x86 (Total Store Order). Существует **единый для всех процессоров порядок всех записей**: два процессора не могут увидеть две чужие записи в разном порядке. Записи одного процессора входят в этот порядок в той последовательности, в какой сделаны. Процессор видит собственную запись сразу (читает её из своего буфера записей), ещё до того, как её увидели остальные. Единственное наблюдаемое переупорядочивание — более поздняя загрузка выполняется раньше, чем более ранняя запись этого же процессора в **другую** ячейку стала видна остальным. |
| Litmus-тест | Маленькая программа из 2–4 потоков по несколько инструкций, у которой заранее известно, какие конечные значения возможны по модели памяти, а какие запрещены. |
| Допустимый / запрещённый исход | Конечные значения регистров и памяти litmus-теста, которые модель x86-TSO разрешает / запрещает. Множества берутся из источника, а не из нашей реализации. |
| SC | Sequential consistency: поведение, как будто все **доступы к памяти** всех процессоров выполнились по одному в каком-то общем порядке. Неделимая единица — доступ: `INC [x]` без `LOCK` — это два доступа, между которыми может вклиниться другой процессор. Любой SC-исход разрешён x86-TSO. |
| SC при неделимости инструкции | То же, но неделима целая инструкция. Это подмножество SC и эталон режима чередования. |
| Режим чередования | Все vCPU исполняются одним host-потоком по очереди; переключение — только на границе переключения (см. ниже). Любое исполнение в нём — SC, причём **каждая инструкция целиком неделима**. Это сильнее настоящего x86: там `INC [m]` без `LOCK` неделимой не является, а в режиме чередования — является. |
| Граница переключения | Граница гостевой инструкции либо граница частичного прогресса `REP`-инструкции (интерпретатор прерывает длинный `REP` с RIP на самой инструкции — так же, как настоящий процессор принимает прерывание между итерациями). Точное определение записывает `SMP_CONTRACT.md`. |
| Параллельный режим | У каждого активного vCPU свой host-поток; гостевая память общая. |
| Квант | Число шагов цикла исполнения (каждый шаг заканчивается на границе переключения), которое vCPU делает в режиме чередования до переключения на следующий. |
| Seed | Число, из которого детерминированно получаются длины квантов. Один seed — одно и то же исполнение. |
| Safe point | Граница переключения, на которой всё состояние vCPU лежит в его структуре, а не в регистрах host. |
| Остановка всех vCPU | Операция, после которой каждый vCPU стоит на safe point и не исполнит ни одной гостевой инструкции до возобновления. |
| Kick | Сигнал vCPU-потоку «проверь события сейчас»: атомарный флаг плюс пробуждение, если поток спит в `HLT`. |
| Host-барьер | Инструкция ARM64, ограничивающая переупорядочивание обращений к памяти (семейство `DMB`), либо load/store с acquire/release. |
| LSE, LL/SC | Два способа атомарной операции на ARM64: одна инструкция (`CAS`, `SWP`, `LDADD`) или пара «эксклюзивное чтение — условная запись» (`LDXR`/`STXR`). |
| Split lock | `LOCK`-операция, операнд которой пересекает границу строки кеша или страницы. |
| SMC | Self-modifying code: гость изменяет уже исполнявшийся код. Cross-modifying — когда код меняет другой процессор. |

## 1. Результат этапа и первый срез

В конце этапа гость видит 2–4 процессора, сам запускает дополнительные процессоры штатным способом, обменивается между ними прерываниями, согласованно меняет адресные пространства; `LOCK`-операции атомарны, а порядок наблюдения памяти никогда не выходит за пределы x86-TSO; переведённый код корректно инвалидируется и освобождается при нескольких vCPU; все vCPU можно остановить для снимка и восстановить их очереди событий; обычный доступ к памяти не берёт глобальную блокировку. Корректность не зависит от недокументированного режима TSO процессоров Apple.

Ступени этапа, в порядке выполнения:

1. **Контракты и методика** (S6-00…S6-09): что именно гарантируем, из каких источников, чем проверяем. Без кода машины.
2. **Режим чередования** (S6-10…S6-24): несколько vCPU в одном host-потоке. Старт AP, IPI, shootdown, Linux с двумя процессорами, снятие и восстановление состояния. Корректность модели памяти здесь следует из конструкции: любое исполнение — SC.
3. **Параллельный режим** (S6-30…S6-38): поток на vCPU, разделяемая RAM, настоящие атомарные операции, host-барьеры, остановка всех vCPU, измерение масштабирования.
4. **JIT при нескольких vCPU** (S6-40…S6-43): кэш кода, инвалидация и освобождение блоков. Целиком `blocked` до интеграции JIT в путь машины.
5. **Завершение** (S6-50…S6-61): решение об аппаратном TSO, передача этапам 7/8/11, ревью, приёмка.

Режим чередования не выбрасывается после появления параллельного: он остаётся эталоном для сравнения, средством воспроизведения дефектов по seed и корректным fallback, которого требует roadmap.

**Первый срез, выполнимый уже сейчас** (не зависит от незакрытых задач этапа 4): `S6-00` (область и решения владельца) → `S6-01` (методика) → `S6-02` (факты о старте AP) → `S6-03` (контракт SMP) → `S6-04` (контракт модели памяти) → `S6-05` (корпус litmus и генератор) → `S6-08` (нативный режим litmus) → `S6-09` (прогон на физическом x86) → `S6-06` (замер кандидатов host-примитивов) → `S6-07` (инвентаризация однопроцессорных допущений). Из `S6-14` (профиль CPU для trampoline) сейчас выполнимы только срезы S6-14a (контракт) и S6-14b (оракул); срезы кода в `od-isa` — по ответу на вопрос D5. Весь остальной код машины ждёт `S4-21`.

**Первый вертикальный срез с кодом машины** (S6-10…S6-16): собственный гостевой probe без ОС — BSP посылает INIT и SIPI, AP проходит trampoline из real mode в long mode, оба vCPU обмениваются IPI и печатают маркеры в UART.

Вне этого этапа: x2APIC, горячее добавление процессоров, более 4 vCPU, SMI, топология с hyper-threading и несколькими сокетами, NUMA, запись и воспроизведение исполнения (record/replay), формат файла снимка (этап 9), инструкции non-temporal/WC-памяти, собственно Windows (этап 8). Однопроцессорная семантика инструкций принадлежит этапу 2; этап 6 добавляет только то, что возникает при нескольких процессорах.

## 4. Контракты, которые нельзя упростить ради прохождения теста

### 4.1. Модель памяти

- Цель — x86-TSO. Множество допустимых исходов каждого litmus-теста берётся из источника (публикация о модели x86-TSO, примеры раздела о порядке памяти Intel SDM) или из собственного перебора по операционной модели из этого источника. Оно **никогда** не берётся из того, что показала наша машина.
- Тест пройден, если каждый наблюдённый исход входит в допустимое множество. Отсутствие какого-то допустимого исхода (например, «оба потока прочитали 0» в тесте store buffering) ошибкой не является.
- Один запрещённый исход за любое число повторов — дефект.
- Корректность не зависит от аппаратного режима TSO процессоров Apple. Параллельный режим обязан быть корректным на обычном ARM64 со слабой моделью памяти.
- Достаточность выбранных host-барьеров обосновывается ссылкой на источник. Прошедший тест достаточность не доказывает.

### 4.2. Атомарность

- Каждая `LOCK`-операция и `XCHG` с памятью неделимы для всех vCPU: никакой другой vCPU не видит память между чтением и записью этой операции и не может записать в неё между ними.
- Загрузки и записи не переупорядочиваются с `LOCK`-операцией ни в какую сторону: более ранние записи этого vCPU видны остальным до неё, более поздние загрузки и записи не выполняются раньше неё. Все `LOCK`-операции всех vCPU имеют единый общий порядок (Intel SDM, том 3, раздел о порядке памяти — указать редакцию и номер).
- Выровненная запись или чтение 1, 2, 4 или 8 байт видны другим vCPU целиком. Побайтовое копирование такого доступа в разделяемую RAM запрещено.
- Невыровненный доступ 2, 4 или 8 байт, целиком лежащий в одной строке кеша, на настоящих процессорах тоже неделим (SDM, раздел о гарантированно атомарных операциях). План эту гарантию молча не сужает: реализовать её либо записать документированное отклонение — решение владельца, вопрос D8. До решения в параллельном режиме для **обычных** (не `LOCK`) таких доступов действует записанное отклонение; на `LOCK`-операции оно не распространяется.
- `CMPXCHG` при несовпадении всё равно выполняет запись (старого значения): требует права записи и выставляет dirty-бит. Проверка прав и исключение — до любого видимого эффекта.
- Обновление битов accessed/dirty в таблицах страниц — атомарная операция «сравнить и заменить» с повтором обхода при неудаче; потерять бит, установленный другим vCPU, нельзя.
- Split lock — легальный гостевой код. Он исполняется атомарно способом из `MEMORY_MODEL.md` по ответу на D8. Неатомарное исполнение запрещено всегда; остановка машины с явной ошибкой допустима только как записанное временное состояние до S6-34.

### 4.3. Гостевая RAM

- В параллельном режиме никто не держит долгоживущий Rust `&mut` на память, которую может менять другой vCPU, устройство или JIT ([архитектура](../ARCHITECTURE.md), «Память и MMU»).
- Гонка двух vCPU по обычной памяти — нормальное поведение гостя. Но неатомарная гонка в Rust — неопределённое поведение host. Поэтому каждый доступ к разделяемой RAM идёт через атомарные типы стандартной библиотеки или собственный ARM64 assembly; способ фиксирует `MEMORY_MODEL.md`.
- Достаточность доказывается в той модели, на которой написан код. Для атомарных типов Rust — по модели памяти Rust: проверить по документации `std::sync::atomic`, допустимы ли одновременные доступы **разной ширины** к перекрывающимся байтам (гость делает это постоянно: байтовая запись против 8-байтового чтения) и какие `Ordering` запрещают исход IRIW. Для собственного assembly — по Arm ARM. Нельзя доказать свойство в одной модели, а код написать в другой.
- В режиме чередования все, кто пишет в RAM (vCPU и устройства), работают в одном host-потоке и только на границе переключения. Появление отдельного потока ввода-вывода снимает это допущение и требует пересмотра.
- MMIO — не RAM: доступ к устройству может брать блокировку. Обычный доступ к RAM глобальную блокировку не берёт.

### 4.4. Старт AP и IPI

- AP не исполняет ни одной инструкции до SIPI. После INIT он возвращается в wait-for-SIPI с состоянием из колонки INIT таблицы инициализации Intel SDM (оно **не** совпадает с состоянием после включения: часть регистров и MSR INIT не трогает). Поведение BSP при INIT отличается и задаётся контрактом отдельно.
- Старт AP доказывается только гостевым кодом, который сам посылает INIT и SIPI. vCPU, созданный тестовым harness сразу в long mode, допустим для litmus и unit-тестов, но **не** является доказательством старта AP.
- Каждая комбинация полей ICR либо доставляется по контракту, либо даёт явную ошибку. Молча проигнорированный IPI запрещён.

### 4.5. Остановка всех vCPU

- После подтверждения остановки ни один vCPU не исполняет гостевую инструкцию и не меняет память до возобновления. vCPU в `HLT` и в wait-for-SIPI тоже участвуют.
- На safe point всё состояние vCPU лежит в его структуре; скрытых живых значений нет.
- Остановка ограничена по времени: не дождавшись vCPU, операция возвращает явную ошибку, а не зависает и не объявляет успех.
- Выход из `HLT` и из wait-for-SIPI всегда проходит проверку запроса остановки: vCPU, подтвердивший остановку во сне, не начинает исполнять из-за пришедшего позже прерывания.
- Прерывание или IPI, адресованные остановленному vCPU, не теряются: они остаются ожидающими в его LAPIC и входят в его состояние.
- Виртуальное время на остановке стоит.
- Очереди событий каждого vCPU сохраняются и восстанавливаются с теми же сроками. Потерянный или сработавший дважды таймер — дефект.

### 4.6. Воспроизводимость

- В режиме чередования одинаковые входы и одинаковый seed дают одинаковый результат: те же счётчики инструкций на каждом vCPU, те же байты UART, то же конечное состояние. Это верно **только** если виртуальное время считается по исполненным инструкциям и нет внешнего ввода-вывода. Если `S4-22` свяжет время с часами host, это правило пересматривается — вопрос D7.
- Параллельный режим недетерминирован. Документация и отчёты не называют его воспроизводимым; дефект, найденный в нём, сначала пытаются повторить в режиме чередования перебором seed.

### 4.7. Масштабирование

- Различать два статуса. **«Функционально доступно»**: гость видит N процессоров и работает корректно (достаточно режима чередования; этого требует Windows-плата для `S7-32`). **«Поддержано»**: число vCPU стабильно на длительном прогоне и не уменьшает реальную производительность многопоточной нагрузки по сравнению с меньшим числом — это требование roadmap.
- Режим чередования функционально корректен, но ускорения от второго vCPU не даёт, а общий темп на нём ниже. Его нельзя называть «масштабированием» или «поддержанным числом vCPU»; в документах и интерфейсе писать «функционально доступно».

### 4.8. Границы с другими этапами

  5. Подтверждение остановки и последующее чтение состояния и RAM остановившим потоком упорядочены так, что он видит все записи остановленных vCPU (порядок записать в контракт и обосновать).
  6. Виртуальное время на остановке стоит; в работе — по `SMP_CONTRACT.md`.
  7. Завершение машины, STOP и ошибка одного vCPU останавливают все потоки и возвращают результат без зависших потоков.
  8. Split lock, не помещающийся в 16 байт (по D8): vCPU до любого видимого эффекта инструкции запрашивает остановку остальных, выполняет операцию и возобновляет их. Если остановку одновременно запросили два vCPU, проигравший откатывается к началу своей инструкции (это safe point), подтверждает остановку и повторяет инструкцию после возобновления. Явная ошибка S6-31 для таких операций убирается.
- **Проверить:** probe S6-16 проходит в параллельном режиме многократно; litmus-счётчик с `LOCK`-операцией на операнде, пересекающем страницу, точен на 2 и 4 vCPU; тест «остановить во время обмена IPI — ни один счётчик инструкций не растёт — возобновить — probe завершается верно», повторённый число раз из `SMP.md`; тест потерянного пробуждения (kick сразу перед засыпанием, многократно, с тайм-аутом); тест «IPI спящему остановленному vCPU не запускает его до возобновления и не теряется»; тест тайм-аута остановки; после завершения нет живых потоков vCPU.
- **Готово:** vCPU исполняются параллельно и останавливаются все разом за ограниченное время, без потерянных пробуждений и прерываний.
