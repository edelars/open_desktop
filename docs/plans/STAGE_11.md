# Этап 11. Интеграция с macOS и качество настольного продукта — пошаговый план реализации

Статус: **план подготовлен, реализация этапа не начата**. Исходное состояние проверено 2026-11-06 на ветке `feat/s9-stage` (коммит `baa8999`). Все задачи S11 ниже открыты. Наличие этого документа, каталога, пустого модуля, Swift-файла или успешной сборки не закрывает ни одну задачу.

Нормативный объём — [этап 11 дорожной карты](../ROADMAP.md#этап-11-интеграция-с-macos-и-качество-настольного-продукта). Обязательные границы задают [архитектура](../ARCHITECTURE.md) (разделы 3 «Границы процессов», 4 «IPC», 6 «Граница Swift ↔ Rust», 7 «Диски, конфигурация и снимки», 8 «Гостевые компоненты»), [карта проекта](../PROJECT_LAYOUT.md), [виртуальная плата](../specs/VIRTUAL_BOARD.md), [состояние VM и операции](../specs/VM_STATE.md), [контракт машины](../specs/MACHINE_CONTRACT.md) и [политика зависимостей](../policies/DEPENDENCIES.md). Это план выполнения, а не вторая архитектура и не спецификация протоколов: спецификации создаются отдельными задачами ниже.

Документ написан так, чтобы исполнитель с ограниченным контекстом мог взять **одну** задачу, выполнить её по шагам и честно отчитаться. Если шаг непонятен — остановиться и записать вопрос в отчёт, а не угадывать.

## 0. Как читать этот план

1. Выполнять ровно одну задачу `S11-NN` за один заход. Не начинать следующую, пока текущая не прошла ревью или не записан точный blocker.
2. У каждой задачи есть поля: **Где** (какие файлы трогать), **Сделать** (пронумерованные шаги), **Проверить** (конкретные команды и наблюдения), **Готово** (критерий приёмки), **Не делать** (частые ошибки). Делать только то, что перечислено.
3. Чекбокс `- [ ]` ставится в `- [x]` только после ревью по правилам `AGENTS.md`. Исполнитель сам чекбокс не отмечает; он добавляет строку **Текущий статус (дата):** с фактами и ссылками на коммит и отчёт.
4. Слово «реализовано» означает: код есть, тесты проходят, ревью пройдено, отчёт записан. Слово «подготовлено» означает: есть документ или каркас без доказанного поведения. Не путать.
5. Если в задаче сказано «blocked до X», а X не существует, задача не выполняется. Записать blocker в `KNOWN_ISSUES.md` только если это найденный дефект; будущую функциональность туда не писать.
6. Пока в проекте нет загружающейся гостевой ОС (этапы 5, 7, 8 не начаты), единственные «машины», которые может запускать VMHost, — **test-only** профили дисплея этапа 10 без гостевого кода: `OD_DISPLAY_PROFILE_TEST_PATTERN` (1) и `OD_DISPLAY_PROFILE_TWO_SCREENS_TEST` (4) из [display_abi_v1.h](../../include/open_desktop/display_abi_v1.h). У них нет гостя, нет дисков и нет persistent root. Все проверки оболочки на них честно помечаются «на test-only профиле без гостя». Это не продуктовая VM.
7. Durability: по [VM_STATE.md §3](../specs/VM_STATE.md) до закрытия ISSUE-055 (S9-06) все mutating операции VM и durable operation record недоступны, ответ — `unsupported_durability`. В этом плане это правило встроено в S11-03: остановка сессии test-only профиля без persistent root не является forced stop из §3.4 и под правило не попадает; любая операция над машиной с диском и guest `SHUTDOWN` отвечают `unsupported_durability` до S9-06; создание файлов bundle и диска durability **не заявляет**.
8. Все пути ниже даны от корня репозитория. Команды выполнять из корня репозитория.

### Словарь

| Термин | Значение в этом плане |
|---|---|
| Приложение | `OpenDesktop.app`: процесс с окнами, библиотекой машин и мастером. Не исполняет гостевой CPU, не пишет в диск работающей VM. |
| VMHost | Отдельный процесс на одну машину. Владеет движком, дисками, host-ресурсами (звук, сеть, кадры). Запускается приложением или CLI; живёт, пока жив запустивший его процесс и открыт control-сокет. |
| Bundle VM | Каталог `<Имя>.odvm/` с конфигурацией, дисками, firmware/TPM-состоянием, снимками и логами. Единица хранения машины. |
| Библиотека машин (каталог) | Список известных bundle в UI. Это восстанавливаемый индекс, а не хранилище данных: его можно пересобрать по bundle. |
| Control v1 | Текущий wire format ограниченной same-code сессии: `HELLO/READY/RUN/STOP/RESULT` ([CONTROL_PROTOCOL_V1.md](../../protocols/control/CONTROL_PROTOCOL_V1.md)). Унаследованный `socketpair`, без listener и reconnect. Не управляет жизненным циклом VM. |
| Control v2 | Новый нормативный протокол жизненного цикла VM: configure, start, pause, resume, stop, query, передача ресурсов и события. Создаётся в S11-03. v1 не меняется. Транспорт тот же: унаследованный `socketpair`. |
| Lifecycle | Переходы состояний VM по [VM_STATE.md §3.1](../specs/VM_STATE.md): `stopped`, `running`, `paused`, `shutting_down`, `failed` и др. |
| Событие | Сообщение VMHost → управляющий процесс о переходе состояния, прогрессе, ошибке или агрегированной статистике. Истина о состоянии машины — события, а не догадки UI. |
| Request ID | Номер запроса в control v2 для сопоставления ответа с запросом в пределах **живого соединения**. Повтор с тем же номером в живом соединении — запрос статуса. Не переживает смерть VMHost и не является operation ID. |
| Operation ID | Идентификатор mutating операции по VM_STATE §3.2 с durable record; уникален в пределах identity VM. Недоступен до S9-06 (`unsupported_durability`). У pause и resume его нет. |
| Гостевой агент | Пользовательская программа внутри гостя (Windows/Linux). Делает буфер обмена, время, shutdown, файлы. Не имеет kernel-привилегий. |
| Канал агента | Устройство платы, через которое агент говорит с VMHost. Транспорт выбирается в S11-20 (кандидат — второй UART как COM2; требует подтверждения владельца, так как плата v0.1 имеет один UART). |
| Host backend | Код на стороне host, который выполняет системную работу для устройства: сокеты для NIC, CoreAudio для звука, файлы для общих папок. Живёт в `od-host`/VMHost, не в `od-machine`. |
| NAT | Режим сети, когда гость выходит в сеть через адрес host; входящих соединений извне нет. Модель NIC и семантика — собственные; реализация трансляции и TCP/IP в пользовательском пространстве — решение ADR-0008 (S11-30) по политике зависимостей. |
| Test-only профиль | Режим VMHost/`od-host` без гостевой ОС (узор, два экрана, позже probe). Разрешён для проверки оболочки; любой claim про него помечается как test-only. |
| Security-scoped bookmark | Способ macOS сохранить доступ к папке/файлу, выбранному пользователем в диалоге, между запусками приложения. Доступ по bookmark к файлу в другом процессе — не проверен, см. [ADR-0006](../decisions/ADR-0006-desktop-app-shell.md); VMHost получает уже открытый дескриптор (S11-03). |
| Передача дескриптора | Открытый файловый дескриптор (ISO, диск вне bundle, корень общей папки, файл drag-and-drop) передаётся VMHost через `SCM_RIGHTS` в единственном разрешённом для этого сообщении control v2 `ATTACH_RESOURCE`. Пути пользователя через control не ходят. |
| Entitlement | Разрешение в подписи процесса (например, `com.apple.security.cs.allow-jit`). Нужен только процессам, которые реально исполняют JIT, то есть VMHost. |

## 1. Результат этапа и первый срез

В конце этапа пользователь открывает приложение, видит библиотеку машин, создаёт машину мастером, запускает её, видит окно дисплея, ставит на паузу и продолжает, закрывает приложение с понятным предложением остановить машины, а каждая ошибка показана словами с действием. Mac засыпает и просыпается — машины ставятся на паузу и продолжают; меняются дисплеи — окна перестраиваются; кончается место или память — пользователь предупреждён до потери данных. Для гостя подготовлены канал агента, NAT-сеть, звук и общие папки: контракты, модели устройств и host-части проверены без ОС; гостевые части ждут этапов 4/5/7/8.

Лестница из roadmap, в порядке этого плана:

1. **Оболочка продукта:** приложение, bundle и каталог, control v2, lifecycle в VMHost, сборка, мастер, сообщения об ошибках, выход/сбой, сон/дисплеи/ресурсы, CLI. Полностью в этом плане, на test-only профилях.
2. **Канал агента и его сервисы:** протокол, устройство, host-сервис; буфер обмена, время, shutdown, drag-and-drop — host-части. Probe без ОС blocked до сессии «CPU + устройства» этапа 10 (S10-09). Агенты гостей blocked до этапов 5 и 8.
3. **Сеть:** контракт и решение о стеке, NAT backend с проверкой синтетическими кадрами; модель NIC blocked до PCI (S4-30); сквозной срез blocked до этапа 5.
4. **Звук:** решение о классе устройства, контракт, host backend с offline-проверкой; устройство и сквозной срез blocked.
5. **Общие папки, drag-and-drop, окна гостя, USB и печать:** контракты и host-части там, где они проверяемы без гостя; остальное — scope после гостевых драйверов.

**Первый вертикальный срез (S11-02…S11-14):** пользователь создаёт машину мастером → на диске появляется bundle с конфигурацией и RAW-диском → приложение запускает VMHost с control v2 → VMHost переходит в `running` и публикует кадры test-only профиля по транспорту этапа 10 → окно дисплея внутри приложения → пауза/продолжение/остановка из меню и из CLI (`odctl run` со сценарием) → события состояния приходят в библиотеку → выход из приложения останавливает VMHost с подтверждением. Это первая проверка архитектурного тезиса «Приложение macOS: тонкая оболочка рано» ([ROADMAP §6](../ROADMAP.md)) и подготовка к проверке «безопасное обновление bundle» из [ARCHITECTURE §10](../ARCHITECTURE.md).

Вне этого этапа: подпись Developer ID, нотарификация, обновление приложения, диагностические отчёты (этап 12); ускоренная графика (ступени 3–5 этапа 10); nested virtualization, USB passthrough, миграция; импорт чужих VM (этап 13); MCP-адаптер (roadmap: только при спросе, поверх стабильного CLI); фоновая жизнь машин после выхода приложения и центральный supervisor ([ARCHITECTURE §3](../ARCHITECTURE.md): вводить осознанно, отдельным решением); связь CLI ↔ приложение. Любой claim о «работе Windows/Linux в приложении» вне этапа, пока этапы 5/7/8 не дали загружающуюся ОС.

8. Ошибка гостя (неверный регистр, неверный пакет, неверное сообщение агента) — архитектурный результат устройства/протокола, не panic. Host panic, повреждение памяти и нарушение ABI не маскировать под гостевую ошибку. Данные от гостя (агент, пакеты, запросы к папкам) — недоверенный ввод: проверять длины и границы до использования.
9. Приложение не исполняет гостевой CPU, не читает память гостя и не пишет в диск работающей VM. Пиксели, звук, сетевые пакеты и содержимое файлов не идут через control protocol; файлы передаются как открытые дескрипторы в `ATTACH_RESOURCE`. `od-machine` не знает про AppKit, CoreAudio, сокеты и файлы пользователя; backend живёт в `od-host`/VMHost за узким интерфейсом. `libod_host.a` линкуется только в VMHost; приложение и CLI не линкуют движок.

## 4. Контракты, которые нельзя упростить ради прохождения теста

### 4.1. Процессы и владение

- Один VMHost — одна машина. Lock bundle — `flock` на `<bundle>/lock`, который берёт VMHost при старте через эксклюзивное открытие `od-host` (S9-04); второй VMHost на тот же bundle получает `busy` и выходит, управляющий процесс показывает понятное сообщение. Lock снимается ядром при смерти процесса; «мёртвых lock» и ручной очистки нет.
- VMHost живёт, пока жив управляющий процесс и открыт control-сокет (унаследованный `socketpair`, без listener). Фоновая жизнь машины после выхода приложения или CLI — отдельное архитектурное решение вне этапа ([ARCHITECTURE §3](../ARCHITECTURE.md)).
- Состояние машины в UI берётся только из событий VMHost и его exit status. UI не «догадывается», что машина запущена, по наличию процесса или окна.
- Аварийное завершение VMHost — явное состояние `stopped` с причиной (сигнал, код) и предложением действия. Приложение не перезапускает машину автоматически и не повторяет операцию, способную разрушить данные.
- Выход из приложения при работающих машинах — явный вопрос пользователю. Пока нет `suspend` (этап 9), единственный честный вариант — «Остановить»: pause не сохраняет состояние при завершении процесса ([VM_STATE §3.5](../specs/VM_STATE.md)). Не называть остановку «сохранением».

### 4.2. Control v2 и durability

- Собственная версия в каждом кадре; v1 не меняется. Поля с фиксированной шириной, endian и диапазоном; лимит размера кадра записан; парсер не принимает неограниченные длины и пути. Дескрипторы (`SCM_RIGHTS`) принимаются ровно в одном сообщении `ATTACH_RESOURCE`, по одному дескриптору, с проверкой `fstat` до использования; в любом другом сообщении дескриптор — протокольная ошибка.
- Request ID — корреляция в живом соединении; повтор в живом соединении — статус. Operation ID — отдельное поле; до S9-06 любая операция с operation ID отвечает `unsupported_durability` (VM_STATE §3). Неподдержанная операция возвращает явный код `unsupported` с причиной, а не тихо «успех».
- Остановка сессии профиля без persistent root (test-only) — не forced stop из VM_STATE §3.4 и durability не касается. Для машины с подключённым диском `START`/`STOP`/`SHUTDOWN` отвечают `unsupported_durability` до S9-06. `PREPARE_DISK` и запись `config.plist` — операции над bundle до появления identity VM; документы S11-02/S11-03 прямо пишут, что их durability не подтверждена (ISSUE-055: create, rename, directory entry).
- `PAUSE` имеет таймаут достижения safe point: по истечении — ошибка, состояние остаётся `running` (VM_STATE §3.4). `failed` — только когда VMHost не может установить состояние ресурсов (ошибка ABI при уничтожении/создании сессии); VMHost сообщает причину и завершается ненулевым кодом.
- Пиксели, звук, пакеты, файлы и содержимое буфера обмена больше лимита кадра не идут через control.
- Разрыв канала = остановка VMHost по правилам таймаутов (SIGTERM → ожидание → SIGKILL), как в текущем launcher; управляющий процесс показывает реальный exit status.

### 4.3. Bundle и каталог

- Конфигурация пишется атомарной заменой с версией схемы; при неизвестной версии bundle показывается как «несовместимый», не переписывается.
- Индекс библиотеки пересобирается по bundle; потеря индекса не теряет машины.
- Никакое действие приложения не удаляет диски, ISO или папки пользователя без явного подтверждения с именем объекта. Мастер при отказе удаляет только то, что сам создал в этом запуске.
- Движок не разбирает plist: VMHost получает путь bundle аргументом запуска (от доверенного управляющего процесса, с лимитом длины), проверенные фиксированные поля по control v2 и открытые дескрипторы через `ATTACH_RESOURCE`; отказывается от значений вне лимитов.

### 4.4. Ошибки для пользователя

- Каждый код ошибки control v2, каждый exit status/сигнал VMHost и каждая ошибка мастера имеют запись в каталоге S11-09: заголовок словами, что произошло, что сделать. Сырой код, путь и request ID — в раскрываемых «подробностях», не в заголовке.
- Неизвестная ошибка показывается как неизвестная с подробностями, не как «успех» и не как пустой диалог.
- Host panic/нарушение ABI — не «ошибка гостя» и не «ошибка пользователя».

### 4.5. Агент и каналы

- Протокол агента имеет версию, лимиты длины и очередей; каждое поле от гостя проверяется до использования. Агент работает без kernel-привилегий ([ARCHITECTURE §8](../ARCHITECTURE.md)).
- Shutdown через агента — `shutting_down` с таймаутом; таймаут — ошибка `shutdown_timeout`, машина остаётся `running`. Завершение процесса без подтверждения гостя — forced stop, не clean shutdown (VM_STATE §3.4). До S9-06 `SHUTDOWN` отвечает `unsupported_durability`; сервис агента проверяется test-only инъекцией.
- Буфер обмена синхронизируется только при включённой для машины настройке и только при подключённом агенте; размер ограничен; направление и лимит записаны.

### 4.6. Сеть

- Гость видит только NAT: нет входящих соединений, нет доступа к интерфейсам host помимо трансляции. Лимиты числа потоков и буферов записаны; при превышении пакет отбрасывается со счётчиком, не блокируя VMHost.
- Ошибка backend (сокет не открылся) — потеря пакета или ICMP unreachable для гостя, не panic и не остановка машины.
- Модель NIC и host backend разделены интерфейсом в `od-machine`; `od-machine` не открывает сокеты. Собственными обязательно остаются модель NIC и семантика устройства; выбор реализации трансляции — ADR-0008.

### 4.7. Общие папки

- Любой путь от гостя нормализуется и проверяется на принадлежность корню после разрешения ссылок; выход за корень — ошибка гостя, зафиксированная тестом с перебором (`..`, абсолютные пути, симлинки, NFD/NFC-варианты).
- Корень папки приходит в VMHost как открытый дескриптор каталога через `ATTACH_RESOURCE`; все операции — относительно него.
- По умолчанию только чтение; запись — явный флаг на папку в конфигурации.
- Семантика регистра имён и блокировок записана; «как получится» не является семантикой.

### 4.8. Звук

- Очереди ограничены; underrun — заполнение тишиной со счётчиком, не блокировка вычислений гостя.
- Host backend читает сэмплы блоками (порядка 10 мс), не вызывается на каждый сэмпл или регистр.

## 5. Стенд и доказательства

Основной host — MacBook Pro M3 Max, macOS Tahoe 26.7.1, host page size 16 KiB ([SUPPORT_MATRIX.md](../specs/SUPPORT_MATRIX.md)). Контрольный M1 Pro инвентаризуется позже. Mac mini с Ubuntu ([STAND.md](../testing/STAND.md)) для этого этапа не нужен, кроме сборки Linux-агента, когда он появится.

2. **Протокольные smoke:** Python-скрипт в `tests/system/` запускает VMHost с socketpair и проверяет control v2 по байтам, как существующие `vmhost_control_v1_*_smoke.py`.

4. **Ручная проверка UI:** чеклист в `docs/testing/DESKTOP_APP.md`, скриншоты в отчёт как факт. Не заменяет уровни 1–3.
5. **Гостевой уровень:** blocked до этапов 5/7/8; в отчёте так и пишется.

Измерения (S11-14, S11-31e, S11-34, S11-41, S11-61): время от команды `START` до события `running`, задержка `PAUSE` → `paused`, время создания bundle с RAW-диском 64 GiB, RSS приложения и VMHost; NAT: пропускная способность и задержка на loopback собственным генератором; звук: задержка от записи в кольцо до вывода; длительный прогон: RSS в начале и в конце. Повтор не менее 5 раз, отбрасывать первый прогрев, записывать fingerprint (модель Mac, macOS build, режим сборки). Без чисел не заявлять «быстро» и не выбирать оптимизацию.

Durability и состояния: таблица состояние × операция без пустых ячеек для `stopped` (начальное), `running`, `paused`, `shutting_down`, `failed`, `exited` (после `STOP` VMHost отправляет `STATE_CHANGED → stopped`, `ACK`, затем EOF и выход; повторный `START` в том же процессе невозможен — это отдельная строка таблицы).   5. Таймауты, EOF, teardown по образцу v1; коды ошибок — закрытый список с числовыми значениями, на который ссылается S11-09.
- **Проверить:** каждое поле имеет ширину/endian/диапазон; таблица состояние × операция без пустых ячеек; нет полей-указателей; `SCM_RIGHTS` упомянут ровно для одного сообщения; документ не меняет v1; FRAME_TRANSPORT §2 п.3 называет `--display-fd 5` и ничего больше не меняет.
- **Готово:** VMHost (S11-04), приложение (S11-06) и CLI (S11-13) можно писать независимо по документу.
- **Не делать:** не включать в v2 передачу пикселей, звука, пакетов, содержимого файлов; не вводить «универсальный» JSON-payload; не называть request ID operation ID.
