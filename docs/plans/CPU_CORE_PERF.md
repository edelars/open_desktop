# Производительность ядра CPU. От 2 млн инстр./с к быстрому исполнению — пошаговый план

Статус: **план подготовлен 2026-11-22; ни одна задача не начата**. Это отдельная линия работ `PERF-NN`. Она не принимает и не заменяет ни один этап: статусы этапов остаются в своих планах ([этап 3](STAGE_3.md), [доработка ядра этапа 3](STAGE_3_CORE.md), [этап 4](STAGE_4.md), [этап 7](STAGE_7.md)).

Причина появления линии: [замер загрузки Linux до /init](../reports/STAGE_7_BOOT_TIMING_2026-11-22.md) показал ≈2,0 млн гостевых инструкций в секунду и 20–27 минут до строки `Run /init as init process`. Профили двух прогонов того же маршрута (раздел 2) показали, что и прошивка, и ядро исполняются интерпретатором по одной инструкции за вызов, с ценой ≈8300–8400 инструкций host на одну инструкцию гостя; функций `crates/od-jit` в стеках профиля нет.

Обязательные границы задают [AGENTS.md](../../AGENTS.md) (раздел «Решения в критичных по производительности участках» — главный для этой линии), [архитектура](../ARCHITECTURE.md) (раздел 5 «Устройство собственного движка»), [карта проекта](../PROJECT_LAYOUT.md), [контракт CPU](../specs/CPU_CONTRACT.md), [контракт машины](../specs/MACHINE_CONTRACT.md), [модель памяти](../specs/MEMORY_MODEL.md), [контракт JIT](../specs/JIT_CONTRACT.md) и [протокол измерений](../testing/BENCHMARKS.md).

Документ написан так, чтобы исполнитель с ограниченным контекстом мог взять **одну** задачу, выполнить её по шагам и честно отчитаться. Если шаг непонятен — остановиться и записать вопрос в отчёт, а не угадывать.

## 0. Как читать этот план

1. Выполнять ровно одну задачу `PERF-NN` за один заход. Не начинать следующую, пока текущая не прошла ревью или не записан точный blocker.
2. У каждой задачи есть поля: **Где** (какие файлы трогать), **Сделать** (пронумерованные шаги), **Проверить** (команды и наблюдения), **Готово** (критерий приёмки), **Не делать** (частые ошибки). Делать только то, что перечислено.
3. Чекбокс `- [ ]` ставится в `- [x]` только после ревью по правилам [AGENTS.md](../../AGENTS.md). Исполнитель сам чекбокс не отмечает; он добавляет строку **Текущий статус (дата):** с фактами, числами и ссылками на коммит и отчёт.
4. Задачи идут от простых и быстрых к сложным и неоднозначным: ступень 0 (стенд) → A (сборка) → B (накладные расходы вокруг шага) → C (кеши) → D (структура интерпретатора) → E (блочное исполнение и JIT). Внутри ступени порядок — по убыванию ожидаемого эффекта.
5. «Ускорение» в этом плане — только измеренное по проверке K4 (раздел 5). Проценты из профиля в разделе 2 — **верхняя граница гипотезы**, а не обещание. Если замер не показал выигрыша вне разброса — правка не принимается, даже если она «очевидно быстрее».
6. Все пути даны от корня репозитория. Команды выполнять из корня репозитория. Номера строк указаны на коммит `29c1c07` и могут сдвинуться — искать по имени функции.

## 1. Результат линии и порядок ступеней

В конце линии загрузка Linux через собственную прошивку в unified-цикле идёт измеримо быстрее, поведение гостя побайтно совпадает с исходным на золотых прогонах, каждое принятое ускорение имеет записанный замер «до/после», а для шага за пределы интерпретатора (блочное исполнение, JIT) есть принятое архитектурное решение с измеренными прототипами и отдельный план.

| Ступень | Что делается | Сложность | Верхняя граница эффекта (гипотеза по профилю ядра, раздел 2) |
|---|---|---|---|
| 0. Стенд | Воспроизводимый замер, золотой прогон, профиль | низкая | 0 — без этого остальные задачи не принимаются |
| A. Сборка | Параметры release-сборки | низкая | выигрыш не ожидается (ISSUE-623); измерить |
| B. Накладные расходы вокруг шага | Не опрашивать устройства и не повторять допуск на каждой инструкции | низкая–средняя | ≈11 % времени: `stop` 4,6 %, опрос IRQ 5,4 %, CPUID и MSR в допуске 0,9 %; плюс неизвестная часть 5,9 % «своего» времени входа набора |
| C. Кеши | Кеш декодированных инструкций, кеш трансляции данных | высокая | ≈36 % времени: декодирование 25,2 % (выборка байтов 5,9 % уже внутри него), доступ к данным 10,8 % |
| D. Структура интерпретатора | Быстрый путь шага для самых частых операций | высокая | ≈32 % времени: «своё» время шага 30,1 % и сравнения операций 2,4 % |
| E. Блочное исполнение и JIT | Решение, прототипы и отдельный план | высокая, неоднозначная | порядок величины; только после решения |

Ориентир (гипотеза, не обещание): ступени B и C вместе убирают не больше ≈47–53 % времени, то есть дают не больше ≈2× (≈4 млн инстр./с; прогон на 3,2 млрд инструкций — ≈13–14 мин вместо ≈27). Доли нельзя складывать как гарантированный выигрыш: это верхние границы при полном устранении строки профиля. Ступень D может дать ещё заметный выигрыш. Скорости в десятки и сотни млн инстр./с достижимы только на ступени E.

Вне линии: сокращение числа инструкций, которые гость исполняет до /init (самотесты прошивки, параметры ядра, initramfs); несколько vCPU через EFI (S6-18b); скорость дисков, сети и графики; новые инструкции и кодировки; изменение гостевой модели времени.

## 2. Фактическая отправная точка

Измерено 2026-11-22 на коммите `29c1c07` (ветка `stage8`), Mac с Apple M3 Max (14 ядер, 36 ГиБ), macOS 26.7.1, `rustc 1.99.0`, `cargo build --release -p od-runner` с профилем release по умолчанию. Два прогона `od-runner boot-firmware --cpu-loop unified` на входах замера загрузки (ROM, ESP с ядром Ubuntu 7.0.0-38 и initramfs S7-31n): **П** — бюджет 300 млн инструкций (только прошивка: до входа в `exit_boot_services` гость исполняет ROM и EFI stub; по ISSUE-622 этот вход был на ≈1,24 млрд инструкций на входах среза S7-31d — на входах этой линии число может отличаться, его уточняет PERF-01; COM1 кончается самотестами `OD-FW …`), **Я** — бюджет 2,7 млрд (прошивка, затем ядро; в COM1 есть `Linux version 7.0.0-38`). ## 3. Правила исполнителя и размещение

## 4. Контракты, которые нельзя упростить ради ускорения

### 4.1. Эквивалентность

Для обычного прогона с одинаковыми входами и одинаковым бюджетом результат «после» побайтно равен результату «до»: весь JSON runner (включая `retired`, `quanta`, `virtual_ns`, `rip`, `unified.final_state`, `unified.interrupts`, счётчики исключений и IRQ), файл COM1 и снимок NVRAM. Различие в любом поле — дефект правки, а не «допустимое отклонение». Исправлять правку, а не эталон.

### 4.2. Диагностические режимы

Если оптимизация меняет счётчик, видимый только в диагностическом режиме (статистика кеша выборки, `walk_counts`, sweep, трассы), она в этом режиме выключается, и диагностический прогон идёт прежним путём. Нельзя «чинить» диагностические тесты правкой ожидаемых чисел.

### 4.3. Архитектурные эффекты памяти

Кеш не меняет ни одного архитектурного эффекта: порядок и вид исключений, биты accessed/dirty, видимость самомодифицирующегося кода, реакцию на запись в таблицы страниц. Образец точной политики — `WriteWatch` в `FetchTranslationCache` (S4-13). Политику «как TLB» (`GuestOnly`) эта линия не вводит и не расширяет.

### 4.4. Отказ по умолчанию

Каждый новый быстрый путь по умолчанию **выключен** для всех вызывающих, кроме названных в задаче. Остальные циклы (`parallel_run.rs`, `host_parallel.rs`, `smp_scheduler.rs`, `paged_host_loop.rs`, диагностические probe) продолжают работать как раньше, пока отдельная задача не докажет обратное. Исключения — PERF-06 и PERF-08: это перенос вычислений и сокращение повторных поисков без изменения результата; они действуют для всех вызывающих общего цикла `run_cpl0_set_loop_impl` (`host_parallel.rs`, `firmware_board/vcpu_quantum.rs`, `linux_direct.rs`) и поэтому проверяются расширенным набором тестов K2.

### 4.5. Одна семантика

Быстрый путь вызывает те же вспомогательные функции, что и общий (`arithmetic_result`, `read_operand`, `write_operand`, `transfer` и другие). Копировать формулы флагов и правила адресации в новое место запрещено.

### 4.6. Честность измерений

Сравниваются одна и та же нагрузка, одни и те же входы, одна машина, release-сборка, приоритет −5, последовательные (не параллельные) прогоны. Результат с перекрывающимися разбросами «до» и «после» — «выигрыш не подтверждён». Вместе с числом записываются коммит, параметры сборки, входы (SHA-256), число прогонов и разброс.

Скрипта `tools/bench/linux_boot_perf.py` пока нет: его создаёт PERF-01, профильную команду — PERF-02. До их приёмки ни одна задача ступеней A–E не начинается.

Длительность на исходном коде (оценка по ≈2 млн инстр./с): один прогон на 3,2 млрд инструкций — ≈27 мин; K4 на нагрузке K3200 — 3 прогона, ≈1,4 ч на сторону и ≈2,7 ч на «до» и «после»; задачи с несколькими вариантами (PERF-03 — четыре сборки, PERF-10 — три размера) кратно дольше. Поэтому каждый длинный прогон запускать отдельной фоновой командой с записью результата в файл и читать результат из файла, а не ждать его в одной команде; варианты внутри задачи сначала отсеивать по F100 и K3200 мерить только для «до» и для выбранного варианта.

Какой золотой прогон обязателен: для любой правки кода — G100 в ходе работы и G3200 для приёмки. Любой бюджет меньше ≈1,24 млрд инструкций покрывает только прошивку до ExitBootServices ([ISSUE-622](../KNOWN_ISSUES.md#issue-622): вход в `exit_boot_services` на 1 239 734 209-й инструкции на входах среза S7-31d): там нет кода ядра, патчинга кода ядром, а в первых 300 млн инструкций нет ни одного доставленного IRQ (`irqs_delivered = 0`) и ни одной инструкции CPL3 (`cpl3_retired = 0`). PERF-01 обязан записать, сколько IRQ доставлено и сколько инструкций CPL3 исполнено в G3200; если IRQ там ноль — это blocker для приёмки PERF-04 и PERF-05, и нужен больший бюджет; если ноль инструкций CPL3 — записать, что путь CPL3 золотым прогоном не покрыт и проверяется только тестами K2.

Чего золотой прогон не видит: содержимое RAM не хешируется, а `unified.final_state` содержит не все регистры. Поэтому `record` дополнительно снимает `--stop-snapshot` (все регистры общего назначения), если unified-цикл принимает этот флаг (проверяет PERF-01), и золотой прогон не заменяет тесты K2 и сверочный режим PERF-22.

Останавливать задачу и записывать blocker, если: золотой прогон не совпадает и причина не найдена; для совпадения нужно менять эталон или ожидаемые числа тестов; правка требует изменить гостевую семантику или модель времени; замер не показывает выигрыша вне разброса; нужно тронуть цикл, не названный в задаче.

Почему это безопасно для всех вызывающих (подтвердить чтением кода и записать в отчёт): при политике `WriteWatch` и попадание, и промах кеша дают тот же байт, что обход без кеша; кеш построен на `Rc`/`RefCell` и не получает уведомлений из других потоков; пропуск поиска меняет только внутренний порядок слотов и статистику кеша, которые в JSON обычного прогона не выводятся.
  2. Добавить в адаптер поле «последняя страница выборки»: номер линейной страницы, `context` вызова `fetch` (после той же нормализации `origin`, что в `fetch_through_cache`) и кадр, полученный из кеша при попадании. При следующем `fetch` той же линейной страницы с тем же `context` брать байт из этого кадра без поиска в кеше — той же функцией `read_ram_frame_u8(frame, address)`, что и путь с поиском (при метке `Leaf2M` кадр — база 2 МиБ, смещение считается от адреса запроса).
  3. Поле сбрасывать: в начале каждой инструкции (сейчас адаптер создаётся заново на каждую инструкцию — убедиться, что это так на момент выполнения задачи; если адаптер стал жить дольше — сбрасывать явно), после любого промаха кеша и при любом уведомлении о зафиксированной записи (`committed_write`/`watch`), включая фиксацию битов accessed/dirty обходами и записи при доставке исключения.
  4. В диагностическом режиме (sweep, отчёт кеша выборки) поле не использовать: число поисков в кеше там наблюдаемо.
  5. Тесты: инструкция через границу страницы читает второй байт из правильного кадра; при включённой статистике кеша счётчики равны прежним.
- **Проверить:** K1; K2; K3 на G100 и G3200; K4; K6 — доля `FetchTranslationCache::lookup_of` упала.
- **Готово:** золотые прогоны совпадают; выигрыш подтверждён замером.
- **Не делать:** не кешировать сами байты; не переносить поле между инструкциями; не менять `FetchTranslationCache`.
