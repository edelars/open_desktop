# Этап 3, доработка ядра. Единый допуск, generic путь и честные измерения — пошаговый план реализации

Этот документ — отдельная линия работ внутри этапа 3, которую можно вести параллельно активной линии этапа 4 (`S4-38L7`). Он не заменяет [план этапа 3](STAGE_3.md) и не принимает этап 3: основной план остаётся источником статуса задач `S3-00…S3-41`, а здесь описаны только задачи `S3-50…S3-57`.

Причина появления линии: допуск инструкции в блок, сборка блока и точки входа диспетчера размножены по формам. Каждая принятая форма добавила отдельную admission-структуру, отдельный вариант профиля сборки, отдельные методы `admits_*`, отдельную публичную функцию диспетчера, отдельный раздел контракта и отдельную команду в методике проверки. Эти механизмы независимо повторяют один и тот же цикл: декодирование, границы инструкций, проверка целей переходов, допуск. Критерий приёмки этапа 3 из [roadmap](../ROADMAP.md) требует измеренного ускорения раздельно для первого исполнения и прогретого кеша; измеренные числа сегодня показывают, что интерпретатор быстрее JIT и на холодном, и на прогретом ограниченном корпусе. Линия устраняет дублирование и доводит generic путь до кеша, fallback и сопоставимых измерений. Она не добавляет ни одной инструкции и ни одной кодировки.

## 0. Как читать этот план

1. Выполнять ровно одну задачу `S3-5N` за один заход. Не начинать следующую, пока текущая не прошла ревью или не записан точный blocker.
2. У каждой задачи есть поля: **Где** (какие файлы трогать), **Сделать** (пронумерованные шаги), **Проверить** (конкретные команды и наблюдения), **Готово** (критерий приёмки), **Не делать** (частые ошибки). Делать только то, что перечислено.
3. Чекбокс `- [ ]` ставится в `- [x]` только после ревью по правилам [AGENTS.md](../../AGENTS.md). Исполнитель сам чекбокс не отмечает; он добавляет строку **Текущий статус (дата):** с фактами и ссылками на коммит и отчёт.
4. Слово «реализовано» означает: код есть, тесты проходят, ревью пройдено, отчёт записан. Слово «подготовлено» означает: есть документ или каркас без доказанного поведения. Не путать.
5. Эта линия **не добавляет ни одной новой инструкции и ни одной новой кодировки** и **не ослабляет ни одного действующего условия допуска**. Если задача выглядит так, что её удобнее выполнить добавлением формы или снятием проверки, — это признак неверного понимания задачи, а не разрешение.
6. Все пути ниже даны от корня репозитория. Команды выполнять из корня репозитория.

## 1. Результат линии и первый срез

В конце линии допуск и сборка блока для регистрового набора выражены одним механизмом вместо 16 структур и 20 вариантов профиля; у диспетчера одна точка входа, через которую выражены 31 существующая функция регистрового пути; этот путь работает через уже существующий `MultiEntryBlockCache` и через interpreter fallback; cold и warm измерены на одном корпусе и сопоставлены с ранее записанными числами `S3-35a`/`S3-36b`. Публичные функции остаются рабочими как обёртки, поведение не меняется, множество допущенных форм не меняется.

**Первый срез (S3-50…S3-54):** инвентарь дублирования с числами → контракт единого допуска → один механизм допуска, доказанный корпусом эквивалентности → одна точка входа диспетчера → generic путь через существующий multi-entry кеш.

**Чего линия не обещает.** Memory-путь (`memory_dispatch.rs`, `memory_load_v2.rs`, профили `Checked*`, 151 строка `[partial]` задачи `S3-20`) остаётся отдельным механизмом и отдельной точкой входа; «одна точка входа» относится только к регистровому набору. Вне линии также: новые инструкции и кодировки; расширение регистрового набора; self-modifying code (`S3-24`); прямые связи блоков (`S3-31`); IR-преобразования (`S3-32`); физический gate (`S3-21`); любые изменения `crates/od-isa` и `crates/od-machine`; изменения C ABI `od-host`; приёмка этапа 3 (это `S3-41` основного плана).

## 4. Контракты, которые нельзя упростить ради прохождения теста

### 4.1. Эквивалентность

Единый механизм допускает ровно то же множество форм регистрового набора, что действующие структуры, отказывает ровно на том же, с той же причиной отказа, и даёт тот же IR, тот же машинный код, то же состояние регистров и флагов и то же retirement. Доказательство — параметризованный корпус по каждой форме и по каждому правилу отказа, а не один успешный прогон. Расхождение в одной форме означает, что задача не выполнена. Memory-путь в инвариант не входит: для него требуется лишь неизменность поведения при механической адаптации вызовов.

### 4.2. Точность правила и отказ по умолчанию

Правило допуска формулируется положительно: допускается только перечисленное. Правило обязано задавать класс операции, набор префиксов вплоть до конкретного байта REX, операнды, `operand_size`, `address_size` и точную длину — то есть быть не грубее действующих предикатов. Там, где декодированной формы недостаточно для различения, байтовая сверка сохраняется. Запрещено допускать форму по похожести на поддержанную, по опкоду без проверки операндов, по длине или по отсутствию явного правила отказа. Обобщение, которое допустило бы хотя бы одну кодировку сверх действующего множества, считается ошибкой, а не улучшением.

### 4.3. Границы параллельной работы

Линия меняет только `crates/od-jit`, `crates/od-host`, `tools/bench` и свои документы. Любая потребность изменить `od-isa` или `od-machine` — стоп и blocker, потому что те же файлы правит активная линия `S4-38L7`. Чтение `od-isa` разрешено и необходимо: декодер и интерпретатор — вход допуска и fallback. Отдельно учесть, что `tools/bench` (`od-bench`) зависит от `od-machine` с фичей `experimental-translation-probe-cache` и от `od-isa`: правок там нет, но сборка измерений компилирует активно правимые крейты, поэтому задача `S3-56` может встретить несборку после слияния чужих изменений. Это ожидаемое следствие, а не дефект линии; фиксировать как blocker с указанием коммита.

### 4.4. Кеш

Hit только при полном совпадении `TranslationKey` и валидных зависимостях. Stale запись не считается hit. Capacity по entries, code bytes и metadata соблюдается; при исчерпании есть явный путь. До `S3-25` освобождаются только заведомо неактивные записи; активная запись живёт до безопасной точки.

### 4.5. Fallback

Нулевой прогресс запрещён. Повторная компиляция того же недопущенного entry без исполнения запрещена. После helper-вызова валидность контекста и кода перепроверяется до возврата в JIT. Прогон, в котором всё ушло в fallback, не называется ускорением JIT ни в отчёте, ни в коммите.

### 4.6. Учёт

Compiled instructions, helper calls и interpreter steps считаются раздельно и попадают в metadata и в измерения. Одно число «выполнено инструкций» без разбивки не является доказательством.
