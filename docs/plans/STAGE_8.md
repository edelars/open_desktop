# Этап 8. Windows x64: от загрузки до поддерживаемой среды — пошаговый план реализации

Статус: **этап 8 начат 2026-11-20** (план подготовлен 2026-11-20; принятые задачи отмечены ниже, остальные — с текущим статусом). Исходное состояние снято 2026-11-20 на ветке `main` (коммит `a705ad5`), когда все задачи этапа были открыты. Текущие факты и результаты отдельных срезов записываются в отчёте этапа 8 `docs/reports/STAGE_8_REPORT.md` (его создаёт S8-00). Наличие этого документа, каталога `guest/windows/`, пустого модуля, ответ-файла или успешной сборки не закрывает задачу без её критериев и ревью.

Нормативный объём — [этап 8 дорожной карты](../ROADMAP.md#этап-8-windows-x64-от-загрузки-до-поддерживаемой-среды). Обязательные границы задают [архитектура](../ARCHITECTURE.md) (раздел 8 «Гостевые компоненты и графика», раздел 7 «Диски, конфигурация и снимки»), [карта проекта](../PROJECT_LAYOUT.md), [виртуальная плата](../specs/VIRTUAL_BOARD.md), [контракт машины](../specs/MACHINE_CONTRACT.md), [контракт CPU](../specs/CPU_CONTRACT.md), [требования гостя](../specs/GUEST_REQUIREMENTS.md), [требования Windows boot path](../specs/WINDOWS_PLATFORM_REQUIREMENTS.md) (аудит S7-30), [матрица поддержки](../specs/SUPPORT_MATRIX.md), [политика зависимостей](../policies/DEPENDENCIES.md) и правила [guest/windows/AGENTS.md](../../guest/windows/AGENTS.md). Это план выполнения, а не вторая архитектура: контракты и решения создаются отдельными задачами ниже.

Документ написан так, чтобы исполнитель с ограниченным контекстом мог взять **одну** задачу, выполнить её по шагам и честно отчитаться. Если какой-то шаг непонятен, остановиться и записать вопрос в отчёт, а не угадывать.

## 0. Как читать этот план

1. Выполнять ровно одну задачу `S8-NN` за один заход. Не начинать следующую, пока текущая не прошла ревью или не записан точный blocker.
2. У каждой задачи есть поля: **Где** (какие файлы трогать), **Сделать** (пронумерованные шаги), **Проверить** (конкретные команды и наблюдения), **Готово** (критерий приёмки), **Не делать** (частые ошибки). У ревью-задач вместо «Не делать» есть поле **Кто**. Делать только то, что перечислено.
3. Чекбокс `- [ ]` ставится в `- [x]` только после ревью по правилам `AGENTS.md`. Исполнитель сам чекбокс не отмечает; он добавляет строку **Текущий статус (дата):** с фактами и ссылками на коммит и отчёт.
4. Слово «реализовано» означает: код есть, тесты проходят, ревью пройдено, отчёт записан. Слово «подготовлено» означает: есть документ или каркас без доказанного поведения. Слово «наблюдалось» означает: факт виден в журнале конкретного прогона с записанным nonce и хешами входов. Не путать.
5. Если в задаче сказано «blocked до X», а X не принят, задача не выполняется. Записать blocker в `KNOWN_ISSUES.md` только если это найденный дефект; будущую функциональность туда не писать.
6. Все пути ниже даны от корня репозитория. Команды выполнять из корня репозитория.
7. Этап 8 **не исправляет** семантику CPU, JIT, MMU, SMP и прошивки в обход их владельцев. Найденный в Windows сбой классифицируется (S8-13) и передаётся владельцу: ISA и режимы — этап 2, JIT — этап 3, память/устройства/lifecycle — этап 4, несколько vCPU — этап 6, UEFI/ACPI/TPM — этап 7, диск и состояние — этап 9, дисплей — этап 10, сеть и приложение — этап 11. Исключение — устройства и инструменты, которые этот план поручает этапу 8 (раздел 3, «Владельцы изменений»): для устройств (дополнительные NVMe-контроллеры, xHCI/USB HID) это действует только после записанного решения о владельце в S8-01.
8. Windows, её установочный носитель, виртуальные диски, пакеты обновлений, дистрибутивы приложений, аварийные дампы, ключи продукта и пароли не хранятся в Git. Рабочие файлы — в `work/stage8/` (ignored); в Git попадают только собственные генераторы, маленькие собственные fixtures, хеши и короткие текстовые выдержки журналов.

### Словарь

| Термин | Значение в этом плане |
|---|---|
| WinPE | Windows Preinstallation Environment: минимальная Windows из `sources/boot.wim` установочного носителя, загружаемая в RAM-диск `X:`. Внутри неё работает Setup. |
| Setup | Установщик Windows. Работает в фазах (configuration passes): `windowsPE` → копирование образа на диск → перезагрузка → `specialize` → `oobeSystem` → первый вход. Между фазами Setup перезагружает машину. |
| Ответ-файл | `autounattend.xml` — XML-файл автоматической установки по документации Microsoft «Unattended Windows Setup Reference». Для несъёмного диска (наш носитель — NVMe) Setup в фазе `windowsPE` ищет его в каталоге `\Sources` дистрибутива, а корни проверяет только у съёмных носителей (Microsoft, «Windows Setup Automation Overview», порядок неявного поиска). Это штатный механизм Windows, а не обход. |
| OOBE | Out-of-Box Experience: экраны первой настройки после установки (регион, учётная запись, приватность). Ответ-файл может их пропустить. |
| Первый вход | Момент, когда созданный ответ-файлом локальный пользователь вошёл в систему (автоматически, через `AutoLogon` ответ-файла) и выполнились команды `FirstLogonCommands`. Без `AutoLogon` установка останавливается на экране входа. |
| BCD | Boot Configuration Data: хранилище настроек Windows Boot Manager (куст реестра на ESP). Изменяется только средствами самой Windows (`bcdedit`) внутри гостя. |
| Bugcheck / stop code | Аварийная остановка ядра Windows («синий экран») с кодом и четырьмя параметрами. Это гостевое событие: машина продолжает работать, Windows пишет дамп и перезагружается. |
| Аварийный дамп | `C:\Windows\MEMORY.DMP` или `C:\Windows\Minidump\*.dmp`, который Windows пишет при bugcheck через dump-путь драйвера диска (у NVMe — опрос без прерываний). |
| EMS/SAC | Emergency Management Services: вывод консоли управления и сведений о bugcheck Windows на последовательный порт. Включается `bcdedit /ems on` внутри гостя. У нас порт — COM1. |
| Остановка машины | Машина `od-machine` прекратила исполнение по своей причине (неподдержанная инструкция, backend-ошибка устройства, triple fault, `Reset`, `Shutdown`, исчерпание бюджета). Это **не** bugcheck: гость её не видит. |
| Модуль и RVA | Образ PE в памяти гостя (`ntoskrnl.exe`, `hal.dll`, драйвер), в котором находится адрес остановки, и смещение адреса от базы образа. По имени PDB, GUID и RVA сбой можно сопоставить с публичными символами Microsoft. |
| Nonce-маркер | Строка вида `OD8 <nonce> <фаза> <результат> <sha256>`, которую пишет команда внутри Windows в файл `OD8\markers.txt` на диске полезной нагрузки (основной канал) и, после принятого S4-24, дополнительно на COM1. Nonce генерирует инструмент прогона и кладёт в файл `OD8\nonce.txt` на диск полезной нагрузки этого прогона, поэтому старый журнал или эталон не может выдать себя за новый успех. |
| Обход | Любое отключение проверки ради прохождения: ключи `LabConfig` (`BypassTPMCheck`, `BypassSecureBootCheck`, `BypassCPUCheck` и т. п.), отключённый Secure Boot, удалённый TPM, `bcdedit /set testsigning on`, `nointegritychecks`, подмена файлов носителя. Результат с обходом записывается как обход; gate по нему не принимается. |
| Холодный перезапуск runner'ом | Временная замена перезагрузки до S7-26: при остановке `Reset` runner создаёт машину заново в том же процессе, передавая ей те же файлы дисков, байты NVRAM и persistent state TPM. Это не «перезагрузка как операция машины» и не закрывает S8-30. |
| Диск полезной нагрузки | Собственный GPT/FAT32 raw-диск, который host собирает из каталога (дистрибутивы, скрипты, входы), а гость читает и, при необходимости, пишет в него результаты. |
| Inbox-драйвер | Драйвер, входящий в состав выбранного образа Windows (`stornvme`, `usbxhci`, `hidusb`, `e1g`…). Использовать его допустимо: это гостевая ОС, а не наша реализация устройства. |
| WoW64 | Подсистема 64-битной Windows для 32-битных приложений. Требует от CPU IA-32e compatibility mode в CPL3. |
| Матрица совместимости | Таблица «приложение/сценарий × статус»: «не запускается», «запускается с ограничениями», «проходит приёмку». Ведётся с первого сценария (S8-02). |

## 1. Результат этапа и первый срез

В конце этапа выбранная Windows 11 Pro x64 (`GUEST_REQUIREMENTS.md`, ISO из `SUPPORT_MATRIX.md`) чисто устанавливается на виртуальный NVMe-диск нашей машины через собственную UEFI с включёнными Secure Boot и TPM, надёжно перезагружается, выключается и восстанавливается после аварийного завершения, получает сеть, время, ввод и экран, принимает накопительное обновление выбранной ветки, а выбранные приложения матрицы (7-Zip, LibreOffice, Node.js, Blender), 32-битные приложения, x87/SSE-код, гостевые JIT и целевые x64-драйверы проходят автоматическую и ручную приёмку на M3 Max и M1 Pro. Поддерживаемая конфигурация безопасности Windows описана явно.

Лестница из roadmap, в том же порядке:

1. **Загрузка с диагностикой сбоев:** снимок остановки машины, журнал фаз, дампы экрана, журналы Windows с диска, реестр сбоев (S8-10…S8-13).
2. **Полная установка на виртуальный диск:** дополнительные NVMe-контроллеры, файловый диск, диск полезной нагрузки, ответ-файл, перезапуски, первый сквозной срез, повторяемость (S8-20…S8-27).
3. **Перезагрузка, выключение и восстановление:** циклы, аварийное завершение, bugcheck и дамп (S8-30…S8-32).
4. **Сеть, время, ввод, экран, приложения:** S8-33, S8-40…S8-44, S10-20 (владелец — этап 10), S8-46…S8-49.
5. **Обновления и регрессии:** S8-50…S8-52.
6. **32-битные приложения, x87/SSE, гостевые JIT, x64-драйверы:** S8-60…S8-63.
7. **Гостевые компоненты в обычной конфигурации подписи:** S8-70…S8-72.

Подготовительные решения (S8-00…S8-05) и устройства, которых нет ни в одном плане (дополнительные NVMe-контроллеры S8-20, xHCI/USB HID S8-41…S8-43), выполняются до или параллельно со ступенями. Итог — S8-80…S8-91.

**Первый вертикальный срез (S8-20…S8-24):** runner собирает машину с тремя NVMe-дисками (сконвертированный установочный носитель S7-35, пустой файловый диск 64 GiB и диск полезной нагрузки S8-27 с nonce прогона и скриптом маркера), 2 vCPU, Secure Boot в UserMode и TPM → в каталог `sources\` сконвертированного носителя один раз добавлен постоянный ответ-файл (без nonce) → собственная UEFI загружает `bootmgfw.efi` → WinPE → Setup без участия человека размечает целевой диск, копирует образ Pro (индекс 6) → на каждую остановку `Reset` runner выполняет холодный перезапуск с теми же дисками, NVRAM и TPM → `specialize` → `oobeSystem` → автоматический вход локального пользователя (`AutoLogon`) → команда `FirstLogonCommands` находит диск полезной нагрузки по метке тома, читает nonce, пишет в `OD8\markers.txt` маркер с номером build и выполняет `shutdown /s /t 0` → машина останавливается с причиной `Shutdown` → инструмент прогона читает диск полезной нагрузки и сверяет nonce, причину остановки и хеши входов. Срез не требует клавиатуры, мыши, сети, окна и COM1 с прерываниями: всё управление — ответ-файл и диск полезной нагрузки. Он и есть проверка критерия «полная установка на виртуальный диск» в минимальных границах.

Вне этого этапа: ускоренная графика и собственный WDDM 3D (этап 10, ступени 3–5); формат диска со снимками, snapshot-согласование и шифрование состояния TPM на host (этап 9); оболочка приложения, агент, host-часть и протокол общих папок, звук, NAT-стек (этап 11; этап 8 использует их результаты; Windows-компонент общих папок — код этапа 11 по контракту S11-26; этап 8 отвечает только за подпись, упаковку и установку, S8-70…S8-72; решение (в) S8-01 подтверждено владельцем 2026-11-21); бета и коммерческий выпуск (этап 12); VBS, HVCI, Credential Guard, Hyper-V, WSL2, Windows Sandbox и nested virtualization — только отдельным решением с полным requirement-to-test (S8-05 записывает их как неподдерживаемые); ARM64-версии Windows; активация и лицензирование Windows сверх записи статуса (S8-05).

## 4. Контракты, которые нельзя упростить ради прохождения теста

### 4.1. Признак успеха

- Успех фазы — только nonce-маркер текущего прогона в канале доказательства плюс ожидаемая причина остановки машины. Канал доказательства — файл `OD8\markers.txt` на диске полезной нагрузки, прочитанный host после остановки машины; COM1 — дополнительный канал после принятого S4-24. Код выхода runner, «тишина» на COM1, совпадение с эталоном прошлого прогона или картинка на экране без маркера успехом не являются.
- Маркер пишет команда **внутри Windows** после реального достижения фазы (например, `FirstLogonCommands` после автоматического входа). Runner и инструмент прогона не пишут маркер сами, не подставляют его в журнал и не меняют диск полезной нагрузки между запуском машины и её остановкой.
- Каждый маркер содержит хеш результата фазы, который можно проверить независимо (номер build из реестра, SHA-256 выходного файла приложения, список драйверов).

### 4.2. Конфигурация безопасности

- Все прогоны приёмки — с Secure Boot в UserMode со штатными ключами по ADR-0011 и с TPM. Обходы из словаря допустимы только в отладочных прогонах с пометкой «обход» в отчёте; gate по ним не принимается.
- Конфигурация, которую мы называем поддерживаемой, описана в `WINDOWS_GUEST_PROFILE.md` (S8-05). Возможность загрузить Windows не означает поддержку VBS, HVCI, Hyper-V, WSL2 и других функций дополнительной виртуализации.

### 4.3. Перезагрузка и состояние

- Холодный перезапуск runner'ом передаёт новой машине **только** то, что сохраняет реальное железо: содержимое дисков, байты NVRAM, persistent state TPM. RAM, состояние CPU, volatile TPM (PCR, сессии) и регистры устройств создаются заново.
- Перезапуск процесса runner или потеря файлов NVRAM/TPM между фазами установки — отдельный сценарий отказа, а не способ «починить» установку.
- Диск гостя пишется через файловый backend с той семантикой flush, которую объявляет NVMe-контроллер (`VWC = 0`, запись сквозная). Ускорение за счёт отложенной записи без flush запрещено.

### 4.4. Диагностика

- Снимок остановки и дампы экрана читают состояние машины между квантами владельцем машины (как `read_frame_into` этапа 10). Диагностика не меняет гостевую память и не продолжает исполнение после backend-ошибки.
- Определение модуля по адресу использует только заголовки PE в памяти гостя (`MZ`/`PE`, debug directory `RSDS`). Не встраивать в инструменты таблицы адресов или сигнатуры из бинарей Windows.
- Журналы Windows извлекаются с образа диска только в режиме чтения и только после остановки машины.

## 5. Стенд и доказательства

Основной host — MacBook Pro M3 Max, macOS Tahoe 26.7.1 (build 25G241), host page size 16 KiB ([SUPPORT_MATRIX.md](../specs/SUPPORT_MATRIX.md)). Контрольный host — MacBook Pro с M1 Pro 16 GB (инвентаризация — S8-81, нужен доступ владельца). Конфигурация гостя первого среза (гипотеза до S8-05): 2 vCPU, 4 GiB RAM, три NVMe-контроллера (S8-20): носитель — вывод `od-image-tool import-install-media` (S7-35) с ответ-файлом в `sources\`, только чтение; целевой диск 64 GiB (sparse-файл); диск полезной нагрузки S8-27 с nonce прогона; Secure Boot UserMode, TPM CRB. Рабочий каталог прогона — `work/stage8/<run-id>/`: копии ROM и носителя по хешу, ответ-файл, NVRAM и TPM state, журнал COM1, дампы экрана, снимки остановки, извлечённые журналы.

Уровни доказательств:

1. **Host-side тесты** нового кода: устройства `od-machine`, runner, генераторы (unit/integration, без Windows).
2. **Журнал машины:** причина остановки, COM1, трассировка прошивки, снимок остановки (S8-10), периодические дампы экрана (S8-11).
3. **Nonce-маркеры** из Windows в `OD8\markers.txt` на диске полезной нагрузки, после S4-24 — и на COM1 (§4.1).
4. **Журналы с диска** после остановки (S8-12): `Panther\setupact.log`, `setuperr.log`, `setupapi.dev.log`, аварийные дампы, файлы результатов, записанные гостем на диск полезной нагрузки.
5. **Ручная проверка** в окне (после S10-20 и S8-44): скриншот и описание действий; записывается как факт, но не заменяет уровни 2–4.

Сведения о времени: каждый прогон записывает host-время по фазам и число исполненных инструкций/квантов; по ним S8-04 и S8-25 строят оценки. Сравнения скорости — по правилам `AGENTS.md` (одинаковая нагрузка, повторы, разброс, fingerprint: Mac, macOS build, режим сборки, интерпретатор/JIT, бюджет кванта, число vCPU).

Критерий roadmap — «чистая установка, пакет обновлений и выбранные реальные приложения проходят автоматическую и ручную приёмку на всей начальной матрице Mac» — выполнен только при принятых G2, G4 (в части приложений и ручной приёмки), G5 (в части S8-50 и S8-52) и G8. Честный частичный результат, например: «G1 принят; G2 blocked до S7-32 и задач этапа 2 по ADR-0013; G3 blocked до S7-26; G4 blocked до S11-32 и S10-16; G7 ждёт доступа владельца». Не расширять claim по факту наличия документа, каталога или одного удачного прогона.

Остановить задачу и записать blocker, если: нужна функция CPU, JIT, MMU, SMP, прошивки, NIC или дисплея, которой нет (владелец по §0 п. 7); прохождение возможно только с обходом; требуется чужая модель устройства, драйвер или ответ-файл; поведение Windows противоречит документации Microsoft и источника нет; прогон не укладывается в бюджет S8-04, а ускорение требует нарушить контракт машины; нужен доступ, внешнее действие или решение владельца (ключ продукта, Partner Center, выход в интернет, M1 Pro).
