## 0. Как читать этот план

1. Выполнять ровно одну задачу `S10-NN` за один заход. Не начинать следующую, пока текущая не прошла ревью или не записан точный blocker.
2. У каждой задачи есть поля: **Где** (какие файлы трогать), **Сделать** (пронумерованные шаги), **Проверить** (конкретные команды и наблюдения), **Готово** (критерий приёмки), **Не делать** (частые ошибки). Делать только то, что перечислено.
3. Чекбокс `- [ ]` ставится в `- [x]` только после ревью по правилам `AGENTS.md`. Исполнитель сам чекбокс не отмечает; он добавляет строку **Текущий статус (дата):** с фактами и ссылками на коммит и отчёт.
4. Слово «реализовано» означает: код есть, тесты проходят, ревью пройдено, отчёт записан. Слово «подготовлено» означает: есть документ или каркас без доказанного поведения. Не путать.
5. Если в задаче сказано «blocked до X», а X не существует, задача не выполняется. Записать blocker в `KNOWN_ISSUES.md` только если это найденный дефект; будущую функциональность туда не писать.
6. Все пути ниже даны от корня репозитория. Команды выполнять из корня репозитория.

### Словарь

| Термин | Значение в этом плане |
|---|---|
| Framebuffer (FB) | Непрерывный участок гостевой памяти, где каждый пиксель экрана занимает фиксированное число байт. Гость пишет пиксели, host читает и показывает. |
| Scanout | Процесс чтения framebuffer host-стороной для показа. Один scanout = один показанный кадр. |
| Поколение кадра (generation) | Монотонно растущее число, которое увеличивается на каждый готовый к показу кадр. Нужно, чтобы UI не показал устаревший или наполовину записанный буфер. |
| Слот (slot) | Один из нескольких буферов кадра в разделяемой памяти. Пока UI читает слот A, VMHost может заполнять слот B. |
| Dirty rect | Прямоугольник, который изменился с прошлого кадра. Позволяет копировать не весь экран. Опционально; сначала копировать весь кадр и измерить. |
| GOP | UEFI Graphics Output Protocol: интерфейс прошивки, через который загрузчик и ОС узнают адрес, размер и формат framebuffer. Требует собственную UEFI этапа 7. |
| Display-only driver | Гостевой драйвер, который умеет менять разрешение, двигать курсор и сообщать о нескольких экранах, но не ускоряет рисование. Для Windows это WDDM display-only (KMDOD). |
| WDDM | Windows Display Driver Model. Полный WDDM с 3D — это user-mode и kernel-mode части; display-only — только kernel-mode без 3D. |
| Metal | Системный графический API macOS. Разрешён как системный API. Используется только в UI-процессе для показа кадров и, позже, для ускорения. |
| IOSurface | Системный механизм macOS для обмена изображениями между процессами. Позже заменяет копирование через разделяемую память; не обещает ноль копий. |
| MMIO | Регистры устройства, отображённые в физическую память гостя. В `od-machine` это `MemoryRegionKind::Mmio` плюс `BusDevice` на `MachineBus`. |
| Device loss | Ситуация, когда GPU host перестал отвечать или сбросился. Ускоренный путь обязан это пережить без падения VMHost. |

## 1. Результат этапа и первый срез

В конце этапа гость рисует на экран через собственное дисплейное устройство, пользователь видит изображение в окне macOS через Metal, окно меняет размер, курсор и несколько экранов работают через собственный display-only драйвер, а ограниченный ускоренный путь для заранее выбранных сценариев переводит операции поддержанной версии Direct3D в Metal с проверками ресурсов, синхронизации и восстановления после GPU-сбоев.

Лестница из roadmap, в том же порядке:

1. **Framebuffer/GOP:** рабочий стол, базовый ввод, изменение размера.
2. **Собственный дисплейный драйвер:** динамическое разрешение, курсор, несколько экранов, Retina.
3. **Ограниченный ускоренный путь** для заранее выбранных 2D/3D сценариев.
4. **Собственный графический протокол** и перевод операций поддержанной версии Direct3D в Metal.
5. **Расширение** покрытия, шейдеров, синхронизации, памяти и обработки device loss.

Ступени 1–2 выполняются в этом плане полностью. Ступени 3–5 в этом плане получают только точный scope, контракты и входные условия (S10-30…S10-34); их реализация начинается после приёмки ступени 2 и после Windows этапа 8, потому что без работающего Windows и собственного WDDM-драйвера нечего ускорять.

**Первый вертикальный срез (S10-03…S10-09):** собственный гостевой probe (без ОС) пишет известный узор пикселей в framebuffer-память собственного дисплейного устройства в `od-machine` → VMHost читает кадр и публикует его в разделяемую память со слотами и поколением → процесс UI на macOS получает уведомление, загружает кадр в Metal texture и показывает в окне → при изменении размера окна изображение масштабируется без искажения пропорций → проверочный скрипт сравнивает пиксели показанного кадра с ожидаемым узором. Это тот самый «ранний технический эксперимент», который roadmap требует для оценки риска, и четвёртый проверочный срез архитектуры («Framebuffer из VMHost отображается в окне и меняет размер»).

Вне этого этапа: DirectX 12, Vulkan, OpenGL, совместимость с современными играми, видеодекодирование, захват экрана host, передача GPU в гостя (passthrough), аудио, интеграция гостевых окон с рабочим столом macOS (этап 11).

## 4. Контракты, которые нельзя упростить ради прохождения теста

### 4.1. Устройство и память framebuffer

- Размер, формат пикселя, stride и базовый адрес framebuffer определяются устройством и читаются гостем из регистров. Гость не угадывает их по константам в тестах.
- Запись гостя в framebuffer — обычная запись в память: без побочных эффектов на каждый байт, без вызова Swift и без MMIO-dispatch на каждый пиксель. MMIO — только для регистров управления.
- Устройство различает два класса ошибок. **Исправимые гостем:** неподдержанный режим (код в `STATUS`, старый режим сохраняется), запись в read-only регистр (игнорируется, одинаково всегда). **Backend-ошибки** по `MACHINE_CONTRACT.md` (доступ неподдержанной ширины, доступ вне окна регистров): это `DeviceError`, который останавливает текущий квант машины и не является гостевым исключением; гость их не «ловит». Контракт S10-02 перечисляет каждую ошибку с её классом.
- Смена режима атомарна с точки зрения scanout: host никогда не читает кадр со stride старого режима и размером нового.
- Устройство не хранит host pointers, Metal objects или дескрипторы в guest-visible состоянии. Всё, что гость видит, — числа с заданной шириной и endian.

### 4.2. Передача кадра VMHost → UI

- Кадр готов, когда writer закончил запись слота и опубликовал поколение. UI читает только слот с опубликованным поколением и проверяет поколение после чтения; при несовпадении кадр отбрасывается, не показывается наполовину.
- Число слотов, размер слота, формат пикселя и версия формата записаны в заголовке разделяемой памяти. Reader проверяет версию и размеры до первого чтения и отказывается при несовпадении.
- Потеря кадров допустима (UI показывает последний готовый), порча кадра — нет. Нельзя показывать смесь двух кадров.
- Разрыв соединения, завершение VMHost и смена режима — явные состояния UI («нет сигнала», «изменение режима»), а не зависший последний кадр без индикации.
- Дескрипторы разделяемой памяти передаются по правилам транспорта (S10-05), а не путём в файловой системе, который другой процесс может подменить.

### 4.3. Показ и ввод

- Масштабирование сохраняет пропорции кадра; при несовпадении пропорций окна — поля, а не растяжение. Пиксельный режим 1:1 должен быть проверяем для сравнения эталонов.
- Retina: кадр гостя в логических точках и физических пикселях различаются; в отчёте измерений указывать оба.
- Ввод мыши в окно переводится в координаты гостя по той же матрице масштабирования; ошибка округления не больше одного гостевого пикселя.

### 4.4. Ускоренный путь (ступени 3–5, scope-задачи)

- Трансляция шейдеров и операций — собственная. Системный Metal compiler компилирует только выходной Metal-код. DXIL не даёт права подключать LLVM.
- Каждый гостевой ресурс имеет явного владельца, время жизни и проверку границ; гость не получает доступ к памяти host мимо устройства.
- Device loss — обрабатываемое состояние: VMHost не падает, гость получает документированную ошибку устройства.
