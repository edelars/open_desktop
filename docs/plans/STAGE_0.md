# Этап 0. Технический контракт и проверка жизнеспособности

**Статус:** план реализации; задачи и эксперименты ещё не выполнены.

**Основание:** [roadmap](../ROADMAP.md), [архитектура](../ARCHITECTURE.md), [обязательные правила проекта](../../AGENTS.md).

**Горизонт:** 4–6 недель работы команды из 3–5 опытных инженеров. Недели отсчитываются от старта. Для меньшей команды календарь пересчитывается, критерии готовности сохраняются.

**Результат:** согласованный контракт первой виртуальной платформы и небольшой собственный x86-64 → ARM64 прототип, который корректно работает в подписанном процессе VMHost на macOS. Ключевые решения опираются на проверяемые требования и воспроизводимые измерения.

## 1. Границы этапа

### Обязательно сделать

- Выбрать начальные гости, пользовательские сценарии, Mac и версии macOS.
- Зафиксировать значение «с нуля», разрешённые зависимости и происхождение кода.
- Описать целевой CPU, виртуальную плату и требования Windows к их реализации.
- Подтвердить создание и исполнение собственного ARM64-кода в предполагаемой конфигурации поставки.
- Реализовать ограниченную сквозную цепочку: байты x86 → собственный decode → интерпретатор/простой JIT → результат.
- Проверить C ABI, управление жизненным циклом VMHost и изоляцию двух экземпляров.
- Подготовить минимальное независимое сравнение с физическим x86.
- Провести первые замеры и оформить решения с указанием границ применимости.
- Составить проверяемый backlog следующих этапов и пересчитать риски.

### В этот этап не входит

Полная ISA x86, системная MMU, SMP, загрузка Windows/Linux, собственная UEFI/TPM, драйверы, CoW-диски, снимки работающей машины, Direct3D и готовый пользовательский интерфейс. Для этих подсистем готовятся требования и интерфейсы, а не видимость завершённой реализации.

Мини-прототип не объявляет совместимость с процессором, ОС или приложениями. Успешный ARM64 smoke test без декодирования входных x86-байтов недостаточен для сквозной демонстрации транслятора.

## 2. Правила выполнения

1. **SOLID:** у CPU, JIT runtime, host-оболочки и проверяющего стенда разные обязанности и явные контракты.
2. **KISS:** создать минимальный рабочий вертикальный срез. Не строить универсальный plugin API, большой оптимизатор IR, daemon и сложную инфраструктуру сборки.
3. **DRY:** повторно использовать общие контракты и описания форматов. Сохранять независимость проверяющего пути: одинаковая ошибка в общем helper не доказывает корректность интерпретатора и JIT.
4. **Критичная производительность:** выбор алгоритма или оптимизации подтверждать замерами. Если данных недостаточно, решение остаётся предварительным с условиями повторной проверки.
5. **Корректность предшествует сравнению скорости:** варианты с разными результатами или разной семантикой не являются эквивалентными кандидатами.
6. **Прослеживаемость:** каждое требование связывать с задачей, экспериментом и выходным артефактом.

## 3. Роли и загрузка

| Роль | Ответственность на этапе 0 |
|---|---|
| Технический руководитель | Границы продукта, CPU/плата, зависимости, решения, итоговая приёмка |
| Инженер CPU/JIT | Ограниченный decoder/interpreter, ARM64 emitter, карты состояния и измерения |
| Инженер macOS | Подписанная сборка, JIT API, VMHost, ABI и процессный контракт |
| Инженер системной платформы | Требования загрузки, устройства, firmware, структура состояния |
| Инженер проверки | Физический x86-стенд, воспроизведение, сравнение результатов, методика замеров |

При трёх участниках совмещать роли руководителя и системной платформы, а проверку распределить между инженерами с независимой проверкой результатов. В каждой задаче должен быть один ответственный. Сроки доступности оборудования и сертификата подписи выяснить в первую неделю.

## 5. Рабочие задачи

### S0-01. Зафиксировать технические границы

**Ответственный:** технический руководитель. **Зависимости:** нет. **Оценка:** 1–2 рабочих дня.

Действия:

- Утвердить Swift для macOS-продукта и Rust для ядра как начальный стек.
- Разделить toolchain и runtime: использование штатного компилятора допустимо; LLVM как библиотека нашего JIT запрещён.
- Записать разрешение на стандартные библиотеки, SDK, Metal, системную криптографию, файловые/сетевые API и штатные компоненты гостя.
- Запретить сторонние реализации decoder, interpreter, JIT, firmware, TPM и графической трансляции.
- Определить простой контроль зависимостей Rust/Swift и учёт происхождения собственных таблиц и тестовых данных.
- Зафиксировать, что CPU/UI/process boundaries принимаются по ответственности и изоляции, а решения на горячем пути дополнительно требуют замеров.

**Выход:** политика зависимостей и запись архитектурного решения.

**Приёмка:** для каждой используемой зависимости понятно, является ли она разрешённым инструментом/системным API или запрещённой частью реализации; у CPU-прототипа нет сторонних runtime-пакетов.

### S0-02. Выбрать первую матрицу поддержки и сценарии

**Ответственный:** руководитель совместно с инженером проверки. **Зависимости:** S0-01. **Оценка:** 2–3 дня.

Зафиксировать конкретные версии, а не обозначения «актуальная ОС»:

| Объект | Что требуется записать |
|---|---|
| macOS | Минимальная версия, основная тестовая версия, точные build IDs |
| Apple Silicon | Основной Mac, второй контрольный Mac при доступности, SoC, RAM и размер host page |
| Linux | Один x86-64 kernel/build и минимальный initramfs для следующих этапов; конфигурация и хеши |
| Windows | Windows 11 x64, одна редакция/ветка и точная сборка установочного образа; источник и хеш |
| Проверяющий x86 | Доступная физическая Intel-машина; AMD — дополнительный контроль с отдельным учётом различий |
| Пользовательские задачи | 3–5 фиксированных сценариев, входные данные, результаты, требования к времени и памяти |

Начальные сценарии предложить из разных классов: небольшая CLI-задача, многопоточная обработка данных, типовое настольное приложение, приложение с гостевым JIT. Один выбранный графический сценарий нужен для будущего GPU-направления, но его реализация в этап 0 не входит.

Бюджеты времени устанавливать по практической задаче пользователя и нативным измерениям. До реализации гостевой ОС они остаются целями, а не подтверждёнными характеристиками продукта.

**Выход:** начальная support matrix и карточки пользовательских сценариев.

**Приёмка:** входные образы и данные можно однозначно идентифицировать; отмечено, какие версии/машины доступны и где проверка ещё не выполнена. Если второго Mac нет, совместимость с ним не считается доказанной.

### S0-03. Разобрать требования гостевых ОС

**Ответственный:** инженер системной платформы. **Зависимости:** S0-02. **Оценка:** 3–5 дней.

Разделить четыре группы требований: CPU/ISA, firmware/загрузка, виртуальное оборудование и конфигурация безопасности.

- Для Linux описать вход в выбранный протокол прямой загрузки, исходное состояние CPU, карту памяти и канал диагностики.
- Для Windows описать цепочку UEFI → boot manager → kernel, требования выбранной сборки к CPU и устройствам.
- Разделить инструкции, необходимые для загрузки, системного исполнения, 32-битных приложений и целевых программ.
- Отдельно учитывать UEFI с поддержкой Secure Boot, TPM 2.0 и графические требования Windows; базовый framebuffer не считать доказательством полного соответствия.
- Разделить техническую способность загрузки, заявленную поддерживаемую конфигурацию и требования производителей к сертификации. CPUID с подходящими битами не является подтверждением всех трёх.
- Описать VBS/HVCI/Hyper-V/WSL2 как отдельные возможности с явным статусом; не обещать их поддержку через сам факт запуска Windows.
- Сопоставить каждому будущему устройству гостевой драйвер: штатный или требующий собственной разработки.

**Выход:** таблица «требование → источник → подсистема → будущая проверка → статус».

**Приёмка:** не остаётся скрытых предположений вроде «SSE2 достаточно для любой Windows» или «наличие виртуального PCI-устройства обеспечивает драйвер». У неопределённых требований есть ответственный и способ проверки.

### S0-04. Определить контракт CPU v0.1

**Ответственный:** инженер CPU/JIT и руководитель. **Зависимости:** S0-03. **Оценка:** 3–4 дня.

Описать:

- Архитектурное состояние, начальные состояния и необходимые режимы CPU.
- Целевой профиль CPUID/MSR с категориями «обязательно», «позднее», «не поддерживается».
- Регистры, флаги, сегментацию, системные инструкции, исключения и их приоритеты.
- Будущие x87/SSE и дополнительные расширения, требуемые выбранной ОС/приложениями.
- Контракт guest virtual/guest physical/host address и границы MMIO.
- Семантику атомарности, порядок памяти и будущую синхронизацию vCPU.
- Точки остановки и правила восстановления архитектурного состояния из JIT.

Отдельно описать **прототипный набор этапа 0**. Он существенно уже целевого профиля CPU. Неподдерживаемая последовательность должна отвергаться явно, а не интерпретироваться приблизительно.

Не включать гостевую возможность в профиль только ради прохождения проверки загрузчика. У каждого объявляемого свойства должен быть план реализации и проверки.

**Выход:** CPU contract v0.1, таблица покрытия и контракт прототипа.

**Приёмка:** разработчики интерпретатора, JIT и проверяющего runner одинаково понимают поддерживаемое поведение, наблюдаемое состояние и правила сравнения.

### S0-05. Выбрать профиль виртуальной платы v0.1

**Ответственный:** инженер системной платформы. **Зависимости:** S0-03 и черновик S0-04. **Оценка:** 3–4 дня.

Для каждой позиции выбрать один основной вариант и записать причину:

| Подсистема | Решение этапа 0 |
|---|---|
| Загрузка | Прямой Linux boot для разработки, собственная UEFI для Windows; их разные начальные состояния |
| Firmware | Требуемые UEFI services, ACPI/SMBIOS и постоянное состояние |
| Прерывания/таймеры | Профиль APIC/IOAPIC, выбранные таймеры и виртуальное время |
| Шина | Минимальная PCI/PCIe-конфигурация и адресное пространство |
| Диагностика | UART и форматы диагностических событий |
| Диск | Кандидаты контроллера с доступными драйверами; RAW как первый backend |
| Сеть | Первое виртуальное устройство, драйвер и граница собственного NAT/network backend |
| Экран/ввод | GOP/framebuffer и начальный путь клавиатуры/мыши |
| Безопасность гостя | Место vTPM, UEFI variables, ключей и измеренной загрузки |

Не реализовывать все контроллеры для сравнения. Сначала сравнить требования и совместимость. Если выбор обосновывается скоростью, провести соответствующий минимальный эксперимент; при отсутствии данных отметить решение предварительным.

Обязательные расходы собственных UEFI, TPM, сетевой модели и драйверов явно включить в backlog. Для каждого интерфейса указать версию публичной спецификации.

**Выход:** virtual board v0.1 и схема владельцев состояния.

**Приёмка:** CPU, устройства и firmware согласованы; нет двух взаимоисключающих способов владения RAM, прерываниями или диском. Совместимость каждого пути имеет источник либо запланированную проверку.

### S0-06. Подготовить стенд и протокол измерений

**Ответственный:** инженер проверки. **Зависимости:** S0-01; уточняется после S0-02. **Оценка:** 2–3 дня плюс сопровождение.

- Зафиксировать аппаратные конфигурации, ОС, версии SDK/компиляторов и параметры сборки.
- Создать шаблон запуска: сценарий, вход, seed, число повторов, метод измерения и контроль результата.
- Выделить место для сырых результатов и компактного отчёта с привязкой к ревизии исходников.
- Описать условия питания/температуры, фоновой нагрузки и прогрева.
- Подготовить физический x86 runner для безопасных пользовательских последовательностей; привилегированные тесты остаются следующему этапу.
- Выяснить доступность Developer ID и отдельной macOS-среды для проверки запуска без debugger.

**Выход:** описание стенда, manifest окружения и шаблон benchmark report.

**Приёмка:** другой участник может повторить один нативный тест и получить тот же функциональный результат; разброс времени измерен и виден в отчёте.

### S0-07. Создать минимальный воспроизводимый каркас

**Ответственный:** инженеры CPU/JIT и macOS. **Зависимости:** S0-01. **Оценка:** 2–3 дня.

Создать только то, что нужно вертикальному срезу:

- Небольшой Cargo workspace с CPU-прототипом, JIT runtime и headless runner.
- VMHost, который подключает Rust static library через минимальный C ABI.
- Маленький launcher/supervisor на Swift для запуска и наблюдения helper.
- Сборку release-вариантов, явную конфигурацию подписи и manifest версий инструментов.
- Команду функционального smoke run и отдельный benchmark mode.

Фиксировать доступные stable toolchains, не подставлять непроверенные номера версий. Не создавать всю структуру будущего продукта пустыми модулями. Служебные документы не должны зависеть от установленной большой CI-системы.

**Выход:** исходники минимального среза и инструкция чистой локальной сборки.

**Приёмка:** из исходников собираются headless runner и подписываемый VMHost; зависимости соответствуют S0-01. Успех не зависит от состояния одной IDE-сессии.

### S0-08. Подтвердить JIT на macOS и путь поставки

**Ответственный:** инженер macOS. **Зависимости:** S0-06, S0-07. **Оценка:** 3–5 дней.

Эксперимент E01:

1. По документации для выбранной macOS определить допустимый способ выделения JIT arena и переключения записи/исполнения.
2. Выбрать согласованную комбинацию JIT API и entitlements. Не смешивать несовместимые механизмы write protection и callback allowlist.
3. Сгенерировать собственную небольшую ARM64-функцию с входными аргументами и проверяемым результатом.
4. Опубликовать код, синхронизировать instruction cache и выполнить его через определённый ABI.
5. Повторить генерацию/исполнение для серии функций и проверить контролируемое освобождение ресурсов.
6. Выполнить вне debugger в подписанном VMHost с запланированными настройками Hardened Runtime.
7. Повторить на всей доступной начальной macOS-матрице.

Добавить негативные случаи: неверная длина входа, отказ выделения, нарушение внутреннего контракта и намеренный host fault в отдельном экземпляре helper. Проверить диагностику и завершение только нужного процесса. На этапе 0 не пытаться возвращаться из произвольного host fault через Rust-стек: полноценные гостевые исключения проектируются отдельно.

Developer ID/нотаризация проверяются в доступной конфигурации. Если доступна только локальная или ad-hoc подпись, зафиксировать, что подтверждён лишь этот режим. Подготовленная инструкция нотарификации не равна выполненной проверке. Отсутствие нужного сертификата не блокирует независимую CPU-работу, но оставляет соответствующий критерий поставки незакрытым.

**Выход:** исполняемый JIT smoke, manifest подписи/entitlements и отчёт E01.

**Приёмка:** проверено фактическое выполнение сгенерированного ARM64 в выбранном режиме подписи и runtime; режимы, которые не проверялись, не объявлены поддерживаемыми.

### S0-09. Реализовать ограниченный сквозной x86 → ARM64 прототип

**Ответственный:** инженер CPU/JIT. **Зависимости:** S0-04, S0-07, S0-08. **Оценка:** 5–8 дней.

Зафиксировать небольшой набор конкретных кодировок и регистров. Предлагаемый объём: загрузка 64-битной константы в регистр, регистровые add/sub/compare, один условный переход и возврат результата. Конкретный набор окончательно записать до реализации.

- Вход — настоящие x86-байты собственных тестов.
- Decoder поддерживает только явно перечисленные формы; некорректные и неподдерживаемые входы возвращают отдельную ошибку.
- Интерпретатор исполняет этот же объявленный набор.
- JIT использует минимальное собственное представление и ARM64 emitter без стороннего assembler/JIT.
- Для прототипа разрешены только заранее проверяемые границы буфера, переходы внутри него и заданный контракт завершения.
- Задать instruction budget и правила остановки, чтобы бесконечный гостевой цикл можно было прервать.
- Результат включает определённые контрактом регистры и флаги. Если реализована только часть флагов/режимов, это явно ограничивает профиль прототипа.
- Сохранять связь входного offset с участком ARM64 для диагностики.

Подготовить минимум три разные программы: арифметическую, с зависимым циклом и с условным ветвлением. Проверить граничные входные значения, переполнения по поддерживаемой семантике, усечённые инструкции и неверные цели переходов.

**Выход:** mini-decoder, mini-interpreter, mini-JIT и фиксированные собственные тестовые программы.

**Приёмка:** программы исполняются двумя путями с одинаковым определённым результатом; unsupported input не исполняется приблизительно; нет зависимости от GUI. Это экспериментальный набор, а не покрытие полной ISA из этапа 2 roadmap.

### S0-10. Проверить ABI и минимальный IPC

**Ответственный:** инженер macOS. **Зависимости:** S0-07; сквозная проверка после S0-09. **Оценка:** 3–4 дня.

Сначала описать несколько ABI-операций: создать экземпляр, передать проверенный вход, выполнить с бюджетом, получить результат, остановить и освободить. Описать владение буферами, доступные потоки вызовов, ошибки и версию. Rust panic не пересекает границу языка.

Для launcher ↔ VMHost использовать предлагаемый унаследованный socketpair. Сообщения: handshake/version, run, request stop, status/result и error. Задать верхние размеры, обработку неполных сообщений, request ID и разрыва соединения. Не создавать универсальный RPC framework.

Прерывание выполнения должно иметь реальную точку проверки. Команда stop не считается рабочей, если она обрабатывается только после выхода бесконечного цикла. Отдельно определить, когда supervisor принудительно завершает неответивший helper.

**Выход:** контракт C ABI, спецификация минимального IPC и demo launcher.

**Приёмка:** launcher запускает VMHost, получает результат JIT, управляет остановкой и корректно обрабатывает недоступную версию/разрыв. Процесс VMHost не зависит от окна GUI.

### S0-11. Подтвердить изоляцию экземпляров

**Ответственный:** инженер macOS и инженер проверки. **Зависимости:** S0-10. **Оценка:** 1–2 дня.

Эксперимент E02:

- Одновременно запустить два VMHost с разными входами и собственными ресурсами.
- Проверить независимость результатов, каналов управления и JIT arena.
- Остановить один экземпляр и продолжить работу второго.
- Вызвать контролируемый аварийный выход одного helper.
- Проверить, что supervisor жив, второй helper завершает задачу, каналы и ресурсы погибшего закрываются.
- Явно проверить политику выхода supervisor и предотвращение оставшихся бесконтрольных helper.

**Выход:** повторяемый isolation scenario и отчёт E02.

**Приёмка:** нет влияния на работоспособность другого экземпляра и нет смешивания результатов. Это проверка процессов и владения ресурсами, а не доказательство полной защиты host от будущей гостевой ОС.

### S0-12. Выполнить независимое сравнение с x86

**Ответственный:** инженер проверки. **Зависимости:** S0-06, S0-09. **Оценка:** 2–3 дня.

Эксперимент E03:

- Исполнить собственные безопасные тестовые последовательности на физическом x86 через runner с явным ABI и сохранением нужного состояния.
- Сравнить их с интерпретатором и JIT на Apple Silicon по одной версии набора тестов.
- Сравнивать только определённые архитектурой и заявленные прототипом значения; маскировать неопределённые флаги по документированным правилам.
- Сохранять вход, начальное состояние, seed, ожидаемый/фактический результат и конфигурацию исполнителей.
- При несовпадении сократить пример и добавить его в регрессионный набор.

Не использовать Rosetta или другой эмулятор как замену физическому x86-исполнителю. Нативное выполнение на Intel Mac или другом доступном физическом x86 допустимо с учётом его ОС и ABI. Исполняемые последовательности проверяются на допустимость перед запуском; privileged/неограниченные произвольные программы в этот runner не входят.

**Выход:** минимальный oracle runner и отчёт E03.

**Приёмка:** все случаи поддерживаемого мини-набора совпадают по контракту между физическим x86, интерпретатором и JIT; каждое расхождение объяснено и исправлено либо исключено из заявленного набора с явной причиной. Широкая генерация ISA-тестов относится к этапу 1.

### S0-13. Измерить критичные механизмы и принять решения

**Ответственный:** инженер CPU/JIT и инженер проверки. **Зависимости:** S0-08–S0-12. **Оценка:** 3–5 дней.

Эксперимент E04 включает обязательные базовые измерения и только те сравнения альтернатив, которые влияют на ближайшую реализацию:

| Область | Что измерить | Допустимый вывод |
|---|---|---|
| JIT | Decode/translation/publication и холодный запуск отдельно | Цена подготовки поддерживаемого блока |
| Повторное исполнение | Прогретый JIT против собственного интерпретатора | Разница для конкретного мини-набора и размера задачи |
| Граница блоков | Dispatcher против простого прямого перехода, если оба реализуемы в timebox | Предварительный выбор ближайшего механизма вызова блоков |
| ABI | Пакетный вызов выполнения против более мелких вызовов на одинаковом объёме работы | Где граница Swift/Rust становится существенной |
| IPC | Задержка и разброс коротких команд при свободном и занятом helper | Пригодность control channel и stop policy |
| Ресурсы | RAM процесса, объём кода, стоимость создания/завершения helper | Начальный бюджет runtime и очистка ресурсов |

Не выбирать заранее «правильный» размер блока, порог кеша, IR-оптимизацию и структуру TLB без соответствующего эксперимента. На этом этапе можно не реализовывать два dispatcher: тогда решение остаётся временным, а недостающий benchmark переносится в явный backlog.

**Выход:** сырые данные E04, отчёт, записи решений и список повторных проверок.

**Приёмка:** каждое окончательное решение о скорости подтверждено воспроизводимым сравнением; неизвестные результаты названы неизвестными. Выводы не распространяются на будущую MMU, SMP, Windows и графику без новых измерений.

### S0-14. Провести итоговую техническую приёмку

**Ответственный:** технический руководитель, с проверкой другим участником. **Зависимости:** все обязательные задачи. **Оценка:** 1–2 дня.

- Сопоставить исходные требования, реализованные прототипы и фактические свидетельства.
- Разделить подтверждённые решения, предварительные гипотезы и внешние зависимости.
- Записать открытые риски, их владельцев и ближайшие способы снятия.
- Уточнить задачи этапа 1 и первые задачи этапов 2–4, не заменяя их пустыми каркасами.
- Пересчитать календарь и состав команды по фактической трудоёмкости.
- Подготовить минимальную демонстрацию и инструкцию воспроизведения на чистой конфигурации.

**Выход:** stage-0 report с решением «критерии выполнены» или «этап не завершён: перечень условий».

**Приёмка:** статус опирается на результаты, а не на окончание шестой недели. Невыполненный обязательный критерий не скрывается за условной отметкой готовности; независимая дальнейшая работа может продолжаться.

## 6. Методика измерений

Для каждого сравнения создать карточку до окончательного решения:

| Поле | Содержание |
|---|---|
| Вопрос | Какое решение проверяется и почему участок потенциально критичен |
| Варианты | Baseline и кандидат с одинаковой поддерживаемой семантикой |
| Вход | Версия байтов/данных, начальное состояние, seed и размер работы |
| Окружение | Mac/SoC/RAM, macOS build, compiler/SDK, release flags, ревизия исходников |
| Проверка | Ожидаемый результат, контрольное значение, проверка выполнения полного объёма работы |
| Метрика | Время, задержка или throughput; холодный/прогретый режим указан отдельно |
| Метод | Прогрев, повторы, чередование вариантов, разрешение таймера и поправка на harness |
| Результат | Сырые значения, медиана, разброс, число наблюдений и связанное потребление памяти |
| Вывод | Выбор, уверенность, ограничения и условия пересмотра |

Начальный протокол — не менее 20 парных прогонов после отдельной калибровки. Работу внутри прогона пакетировать так, чтобы цена таймера и вызова harness не определяла результат; ориентир продолжительности пакета — сотни миллисекунд, с корректировкой по реальным данным. Для холодного режима фиксировать, какой именно кеш/процесс пересоздаётся.

Порядок A/B чередовать или рандомизировать, следить за нагревом и не удалять неудобные значения без записанной причины. Для процентилей нужно достаточное число наблюдений; p95 из нескольких десятков общих запусков не объявлять устойчивой характеристикой.

Минимально полезный выигрыш определить до выбора победителя по нуждам конкретного решения. Если эффект сравним с разбросом, увеличить качество/объём измерений либо сохранить более простой вариант. Не назначать общий порог «ускорение на 10%» для всех подсистем.

Счётчики инструкций и подробная трассировка могут менять скорость. Измерять их влияние отдельно; не сравнивать instrumented interpreter с неинструментированным JIT как будто условия одинаковы. Результат должен использоваться проверяющим кодом, чтобы тест не превращался в устранённую компилятором работу.

Числа физического x86 и Apple Silicon имеют разные аппаратные основания. Использовать x86 прежде всего как проверяющий результат; сравнение времени между машинами сопровождать конфигурациями и не называть чистой «эффективностью транслятора».

## 7. Зависимости и критический путь

Основной путь прототипа:

**S0-01 → S0-07 → S0-08 → S0-09 → S0-12 → S0-13 → S0-14.**

Входной контракт S0-09 также зависит от S0-02 → S0-03 → S0-04. Проверка S0-13 требует завершённых ABI/IPC и изоляции по S0-10 → S0-11. Системное направление S0-05 выполняется параллельно и обязательно для итогового технического контракта.

Если доступ к физическому x86 или требуемой подписи задерживается, продолжать независимую разработку, но сохранять незакрытыми соответствующие критерии. Не подменять измерение предположением, чужим эмулятором или успешным debug-run.

Загрузка ОС, высокая скорость микроцикла или красивое окно сами по себе не заменяют эти критерии. Завершение этапа подтверждает пригодность выбранных механизмов для дальнейшей разработки; производительность полной VM пока неизвестна.

## 10. Дополнительные исследования при наличии резерва

Не обязательны для завершения этапа 0:

- Минимальное окно с разделяемым framebuffer и Metal presentation из отдельного helper.
- Сравнение копирования кадров и доступного системного механизма обмена поверхностями.
- Исследование формы собственного графического протокола и будущего WDDM/Metal пути.
- Черновые measurements host I/O для будущего RAW backend.

Эти эксперименты не должны разворачиваться в GPU, драйверную или дисковую реализацию. Если их результат влияет на критичный по скорости выбор, применяются те же правила измерений и фиксации выводов.

## 11. Риски этапа и действия

| Риск | Как обнаружить | Действие |
|---|---|---|
| Подпись/JIT работает только из IDE | E01 в чистом подписанном запуске | Выяснить API/entitlements и упаковку до расширения движка |
| Нет физического x86 или нужного сертификата | Проверка доступности на первой неделе | Продолжать независимые задачи; не закрывать отсутствующее свидетельство |
| Тест слишком мал и меряет harness | Калибровка, изменение размера пакета, профилирование | Перестроить тест; не принимать решение по шуму |
| Интерпретатор и JIT повторяют общую ошибку | E03 на физических x86-входах | Исправить семантику, добавить независимый регрессионный случай |
| Scope растёт до полноценного CPU/UI | Сравнение задачи с границами раздела 1 | Перенести расширение в следующие этапы |
| Требования Windows существенно расширяют CPU/firmware | S0-03 и S0-05 | Обновить оценки и профиль, не скрывать стоимость поддержки |
| IPC stop не обслуживается под CPU-нагрузкой | S0-10/E02 с циклическим входом | Добавить bounded execution/control polling и аварийную политику supervisor |
| Выбранные оптимизации привязаны к одному Mac | Контрольная конфигурация и manifest окружения | Сузить подтверждённый вывод, добавить повторную проверку |

## 12. Первые действия после принятия плана

1. Выполнить S0-01 и завести записи о предварительных решениях.
2. Зафиксировать доступное оборудование, версии SDK/toolchain и режим подписи по S0-02/S0-06.
3. Поднять минимальный каркас S0-07.
4. Первым исполняемым экспериментом подтвердить E01, затем развивать собственную x86-цепочку S0-09.
5. Остальные документы и проверки вести по зависимостям, не дожидаясь окончания всей документации для первого smoke test.

Этот файл является планом. Он не разрешает подменять отсутствующие результаты галочками и не означает, что реализация этапа уже началась.
