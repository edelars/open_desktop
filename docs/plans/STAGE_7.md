Статус: **план подготовлен, реализация этапа не начата**. Исходное состояние проверено 2026-11-07 на ветке `feat/s9-stage` (коммит `bacffa0`). Все задачи S7 ниже открыты. Решения владельца по вопросам S7-00, S7-20 и S7-24 получены 2026-11-07 и записаны в §1.1. Наличие этого документа, каталога `firmware/uefi/`, пустого модуля, Cargo-манифеста или успешной сборки не закрывает ни одну задачу.

Нормативный объём — [этап 7 дорожной карты](../ROADMAP.md#этап-7-собственные-uefi-acpi-и-платформа-для-windows). Обязательные границы задают [архитектура](../ARCHITECTURE.md) (раздел 2 «Стек по слоям», строка UEFI; раздел 5 «Планирование и устройства»; раздел 7 «Диски, конфигурация и снимки»; раздел 9 «Репозиторий и сборка»), [карта проекта](../PROJECT_LAYOUT.md), [виртуальная плата](../specs/VIRTUAL_BOARD.md), [контракт машины](../specs/MACHINE_CONTRACT.md), [требования гостя](../specs/GUEST_REQUIREMENTS.md), [состояние VM](../specs/VM_STATE.md), [политика зависимостей](../policies/DEPENDENCIES.md), правила каталога [firmware/AGENTS.md](../../firmware/AGENTS.md) и решения [ADR-0001](../decisions/ADR-0001-dependencies-and-boundaries.md), [ADR-0002](../decisions/ADR-0002-general-purpose-libraries.md). Это план выполнения, а не вторая архитектура и не спецификация прошивки: спецификации создаются отдельными задачами ниже.

Документ написан так, чтобы исполнитель с ограниченным контекстом мог взять **одну** задачу, выполнить её по шагам и честно отчитаться. Если какой-то шаг непонятен, остановиться и записать вопрос в отчёт, а не угадывать.

## 0. Как читать этот план

1. Выполнять ровно одну задачу `S7-NN` за один заход. Не начинать следующую, пока текущая не прошла ревью или не записан точный blocker.
2. У каждой задачи есть поля: **Где** (какие файлы трогать), **Сделать** (пронумерованные шаги), **Проверить** (конкретные команды и наблюдения), **Готово** (критерий приёмки), **Не делать** (частые ошибки). Делать только то, что перечислено.
3. Чекбокс `- [ ]` ставится в `- [x]` только после ревью по правилам `AGENTS.md`. Исполнитель сам чекбокс не отмечает; он добавляет строку **Текущий статус (дата):** с фактами и ссылками на коммит и отчёт.
4. Слово «реализовано» означает: код есть, тесты проходят, ревью пройдено, отчёт записан. Слово «подготовлено» означает: есть документ или каркас без доказанного поведения. Не путать.
5. Если в задаче сказано «blocked до X», а X не существует, задача не выполняется. Записать blocker в `KNOWN_ISSUES.md` только если это найденный дефект; будущую функциональность туда не писать.
6. Все пути ниже даны от корня репозитория. Команды выполнять из корня репозитория.
7. Каждая спецификация UEFI/ACPI/SMBIOS/TPM/PE/FAT цитируется с редакцией из раздела «Нормативные источники и редакции» `VIRTUAL_BOARD.md` (UEFI 2.11, ACPI 6.6, SMBIOS 3.9, PCIe 7.1, NVMe Base 2.4, TPM 2.0 Library v185, PC Client PTP 1.07 Errata 1.1). Если нужен другой документ (PE/COFF, Authenticode, FAT), источник и редакция записываются в задаче, которая его вводит.

### Словарь

| Термин | Значение в этом плане |
|---|---|
| Firmware image | Собственный freestanding образ прошивки, который `od-machine` размещает в ROM-регионе гостевой памяти и в который передаёт управление при старте машины. Не OVMF, не EDK II, не чужой код. |
| Handoff | Момент передачи управления от `od-machine` коду прошивки: фиксированное состояние CPU, адрес входа и указатель на handoff block. Сегодня в машине есть только handoff в flat probe этапа 4 (Long64, `RIP=0x400000`); real mode и reset vector `0xFFFF_FFF0` в CPU не реализованы и по `CPU_CONTRACT.md` не требуются. |
| Handoff block (board manifest) | Структура данных с версией, которую `od-machine` кладёт в память гостя и из которой прошивка узнаёт RAM, зарезервированные диапазоны, адреса устройств, маршруты IRQ, ECAM. Единственный источник карты платы для UEFI memory map, ACPI и SMBIOS: прошивка карту не назначает. |
| Boot Services (BS) | Таблица функций UEFI, доступная до `ExitBootServices`: память, протоколы, события, загрузка образов. |
| Runtime Services (RT) | Таблица функций, доступная и после `ExitBootServices`: переменные, время, сброс, `SetVirtualAddressMap`. |
| Protocol / handle | Протокол — структура с GUID и функциями; handle — объект, на который навешаны протоколы. База протоколов — часть BS. |
| PE/COFF | Формат исполняемых файлов Windows и UEFI-приложений. Загрузчик читает секции, применяет relocations и вызывает entry point. |
| ESP | EFI System Partition: раздел GPT с файловой системой FAT, где лежит `\EFI\BOOT\BOOTX64.EFI` или `\EFI\Microsoft\Boot\bootmgfw.efi`. |
| Variable store / NVRAM | Хранилище UEFI variables (имя, GUID, атрибуты, данные). Volatile — в RAM прошивки; non-volatile — в собственном NVRAM-устройстве `od-machine`, а его байты сохраняет host по контракту этапа 9 (S9-26). |
| AML | ACPI Machine Language — байт-код, в котором записана таблица DSDT. У нас — собственный кодировщик AML из описания платы, не копия чужих `.asl` файлов. |
| GOP | UEFI Graphics Output Protocol поверх собственного дисплейного устройства этапа 10 (`DISPLAY_DEVICE.md` §11). |
| vTPM | Собственная реализация TPM 2.0: процессор команд и состояние — на host-стороне (`od-machine` или отдельный crate по S7-20), интерфейс CRB — устройство на шине машины, прошивка — клиент через `EFI_TCG2_PROTOCOL`. По `firmware/AGENTS.md` TPM-устройство в прошивке не размещается. |
| CRB | Command Response Buffer — интерфейс регистров TPM по PC Client PTP: MMIO `0xFED4_0000`, locality, команды/ответы в буферах. |
| PCR | Platform Configuration Register: регистры TPM, которые расширяются хешами измеренных компонентов (measured boot). Event log — список того, что и чем измерено. |
| Secure Boot | Проверка подписи Authenticode у загружаемого PE по базам `db`/`dbx` и ключам `PK`/`KEK` в authenticated variables; режимы SetupMode/UserMode. |
| Freestanding сборка | Сборка без host std, для гостевого x86-64 target, отдельно от host workspace (`PROJECT_LAYOUT.md`: «Firmware и guest-компоненты собираются отдельно и не входят в host workspace»). Образец — [build_stage4_flat_probe.py](../../tools/build/build_stage4_flat_probe.py). |
| Host-side unit test | Тест чистой логики прошивки (парсер PE, FAT, кодек переменных, AML), который собирается и выполняется на host из отдельного Cargo-проекта `firmware/uefi/`, не входящего в корневой workspace. |

## 1. Результат этапа и первый срез

В конце этапа машина `od-machine` стартует с собственной прошивкой: прошивка строит UEFI memory map из handoff block, предоставляет Boot Services и необходимые Runtime Services, загружает PE/COFF-образы, даёт консоль, Block I/O поверх собственного NVMe-контроллера, собственную FAT и Simple File System, GOP поверх собственного дисплейного устройства, UEFI variables с постоянным хранилищем, таблицы ACPI/SMBIOS из того же manifest платы, собственный vTPM 2.0 с measured boot и включаемый Secure Boot; выбранный официальный установочный образ Windows загружается через эту прошивку и видит корректные CPU, память, диск, экран и системные интерфейсы.

Лестница этапа, в порядке выполнения:

1. **Ядро прошивки:** handoff → память → BS → PE loader → консоль → собственное тестовое EFI-приложение (S7-01…S7-08).
2. **Переменные и RT:** variable services, NVRAM-устройство, Runtime Services, сброс (S7-09…S7-11).
3. **Платформа:** AML, ACPI, SMBIOS, fixed hardware ACPI, GOP (S7-12…S7-15).
4. **Диск и boot manager:** NVMe-контроллер, драйвер прошивки, GPT, FAT, boot manager (S7-16…S7-19).
5. **TPM и Secure Boot:** ADR, процессор команд, CRB, TCG2, measured boot, authenticated variables, Authenticode (S7-20…S7-25).
6. **Надёжность, измерения и граница с этапом 9:** сброс, отказы, замеры, передача persistence этапу 9, промежуточное ревью (S7-26…S7-29, S7-33).
7. **Реальные ОС:** аудит требований Windows, транспорт установочного носителя, USB-клавиатура прошивки, загрузка Linux и Windows через собственную UEFI (S7-30…S7-32, S7-34, S7-35), итоговое ревью и приёмка (S7-40…S7-41).

**Первый вертикальный срез (S7-01…S7-08):** `od-machine` размещает firmware image в ROM-регионе верхних 16 MiB 32-битного адресного пространства и handoff block в RAM → передаёт управление в Long64 по контракту S7-02 → прошивка инициализирует стек, собственные таблицы страниц, аллокатор и UEFI memory map из handoff block → строит System Table, Boot Services и базу протоколов → загружает из собственного firmware volume встроенные тестовые PE-приложения → приложение `hello` печатает известную строку через `EFI_SIMPLE_TEXT_OUTPUT_PROTOCOL` (COM1) и возвращает `EFI_SUCCESS`; приложение `ebs` вызывает `ExitBootServices`, после чего пишет байт в COM1 напрямую и останавливается `HLT` → runner сравнивает вывод COM1 с эталоном. Срез не требует диска, PCI, TPM, GOP и ОС. Он зависит от ограничений машины, записанных в разделе 2 (только страницы 4 KiB, нет доставки IRQ в paged-режиме, нет APIC timer): решения S7-02 по исполнению из ROM и по модели таймеров обязаны учитывать их, иначе срез blocked до соответствующих задач этапа 4.

Вне этого этапа: установка и эксплуатация Windows (этап 8), Linux как стенд и модели устройств для него сверх NVMe (этап 5), SMP и x2APIC (этап 6), persistence-контейнеры, защита ключей TPM на host и snapshot-согласование UEFI/TPM в `od-storage`/`od-host` (этап 9: S9-26, S9-27, S9-28 — перенос пунктов roadmap «постоянное защищённое состояние ключей» и «восстановление машины» записывает S7-00), дисплейное устройство и его драйверы (этап 10), модель NIC и стратегия сетевых драйверов (S11-32; перенос записывает S7-00), сетевая загрузка (PXE/HTTP boot), legacy BIOS/CSM, сертификация UEFI/TPM. USB-клавиатура прошивки для `ConIn` остаётся в этапе по `VIRTUAL_BOARD.md` (строка «Ввод») как S7-34, blocked до xHCI-модели платы.

10. Все интерфейсы UEFI (функции таблиц, протоколов, entry point образов) объявляются с ABI `extern "efiapi"` (Microsoft x64: shadow space, выравнивание стека 16, регистры `RCX/RDX/R8/R9`). `extern "C"` (System V) для них запрещён — прошивка с ним не заработает с любым внешним EFI-приложением.

## 4. Контракты, которые нельзя упростить ради прохождения теста

### 4.1. Вход и память

- Карту платы назначает `od-machine` и передаёт в handoff block с версией; прошивка не содержит захардкоженных размеров RAM и адресов устройств сверх того, что записано в `FIRMWARE_BOOT.md` как архитектурная константа платы (адрес ROM, адрес handoff block).
- UEFI memory map, E820 (этап 4) и ACPI описывают одну и ту же карту; framebuffer, MMIO, ROM, NVRAM и handoff block никогда не показываются как `EfiConventionalMemory`.
- Прошивка после handoff строит **собственные** таблицы страниц в своей памяти и не зависит от таблиц, которые машина подготовила для входа; память, занятая кодом/данными прошивки, помечается `EfiBootServicesCode/Data` или `EfiRuntimeServicesCode/Data` по факту использования.
- `ExitBootServices` выполняется по спецификации: проверка `MapKey`, остановка таймеров прошивки, после возврата прошивка не трогает память, отданную ОС.

### 4.2. Сервисы и протоколы

- Каждый реализованный сервис BS/RT возвращает коды `EFI_STATUS` по UEFI 2.11 для перечисленных в `UEFI_PROFILE.md` случаев; нереализованный сервис возвращает `EFI_UNSUPPORTED` и записан в профиле как нереализованный. Заглушка, возвращающая `EFI_SUCCESS` без действия, запрещена.
- Протокол устанавливается только когда стоящее за ним устройство реально работает: `EFI_BLOCK_IO_PROTOCOL` без читающего NVMe-драйвера, `EFI_GRAPHICS_OUTPUT_PROTOCOL` без рисующего framebuffer и `EFI_TCG2_PROTOCOL` без работающего TPM не публикуются.
- PE loader проверяет границы секций, размеры заголовков, тип машины `x64`, relocations; битый образ → `EFI_LOAD_ERROR`/`EFI_UNSUPPORTED`, не чтение за пределами буфера.

### 4.3. Переменные, TPM, Secure Boot

- Атрибуты переменных (`NV`, `BS`, `RT`, `TIME_BASED_AUTHENTICATED_WRITE_ACCESS`) соблюдаются по спецификации; `RT`-переменные доступны после `ExitBootServices`; `QueryVariableInfo` отражает реальные лимиты хранилища.
- Non-volatile переменные переживают сброс машины внутри процесса через NVRAM-устройство; переживание перезапуска процесса — этап 9 (S9-26). Нельзя «сохранять» переменные в RAM и называть их NV.
- Secure Boot при `SecureBoot=1` отвергает неподписанный или не доверенный образ `EFI_SECURITY_VIOLATION`; `dbx` проверяется до `db`; проверка подписи — по Authenticode PE-хешу (с пропуском полей, указанных спецификацией), не по хешу файла целиком.
- TPM: PCR расширяются ровно тем, что записано в event log; `TPM2_PCR_Read` возвращает то, что получится при воспроизведении лога; команды вне профиля возвращают `TPM_RC_COMMAND_CODE`, не `TPM_RC_SUCCESS` с нулями. Seeds и persistent keys не логируются и не попадают в отчёты.

### 4.4. Границы честности

- «Загружается» означает: конкретный образ (хеш, источник, редакция) дошёл до конкретной наблюдаемой точки (строка на COM1, кадр на framebuffer, `TPM2_PCR_Read`) при заданной конфигурации. Загрузка собственного тестового приложения не называется «загрузкой Windows».
- Любой обход проверки (отключённый Secure Boot, пропуск TPM, «временно всегда SUCCESS») записывается в отчёт как обход и не входит в приёмку gate.

## 8. Итоговые gates

| Gate | Обязательное доказательство | Недостаточная замена |
|---|---|---|
| G1 — ядро прошивки | S7-01…S7-08: сборка, контракт входа с четырьмя решениями, ROM/handoff, память, BS, PE loader, консоль, сквозной срез из FV | Образ, который печатает строку без BS/PE; таблица BS с нулями или «SUCCESS без действия»; `extern "C"` вместо `efiapi` |
| G2 — переменные, RT и fixed hardware | S7-09…S7-11, S7-14: NV-переменные через атомарный store, RT после EBS при неидентичном отображении, `ResetSystem`/`GetTime` через реальные регистры; S7-26 — когда снят blocked S4-21 | Переменные только в RAM; `HLT` вместо сброса; `SetVirtualAddressMap` без переключения `CR3` |
| G3 — диск и boot manager | S7-16…S7-19, S7-28: NVMe с обязательными командами, Block I/O, GPT, FAT, `BOOTX64.EFI` с ESP, отказы без TPM/SB | Чтение диска в обход протоколов; образ в FV вместо ESP; «минимальный» NVMe без обязательных команд |
| G4 — платформа | S7-12, S7-13, S7-15: AML/DSDT, ACPI/SMBIOS из handoff block одним сериализатором, GOP с проверенным кадром | Таблицы с константами или из второго manifest; чужой `.aml`; GOP без кадра на устройстве |
| G5 — TPM и measured boot | S7-20…S7-23: ADR, команды фаз A/B, CRB с `INTF_ID`, TCG2, лог TCG_2 со Spec ID Event03, replay лога = PCR | `GetRandom` и `PCR_Read` без `Extend`-семантики; TPM в прошивке; временные хеши в PCR4 |
| G6 — Secure Boot | S7-24…S7-25: authenticated variables, Authenticode, `dbx` до `db`, отказ на неподписанное/отозванное, PCR7 с `VARIABLE_AUTHORITY`, отказы TPM/SB | `SecureBoot=1` без проверки; подпись «проверена» по хешу файла; без KEK |
| G7 — реальные ОС | S7-30…S7-32, S7-34, S7-35: аудит, транспорт носителя, Linux, установочный образ Windows до экрана Setup через нашу прошивку | Любой из них через чужую прошивку, с отключёнными проверками или с вручную распакованным носителем без записи |
| G8 — воспроизводимость | S7-27, S7-29 для G1–G3, затем S7-33, S7-40…S7-41 | Только итоговое сообщение в чате |

Честный частичный результат, например: «G1–G3 приняты по S7-29 (S7-26 blocked до S4-21); G4 принят без PCI-привязки; G5–G6 приняты на собственных ключах; G7 blocked до S4-30, S4-10, этапов 5/6 и S7-35; xHCI (S7-34) — если S7-30 подтвердит необходимость клавиатуры». Не расширять claim по факту наличия документа, каталога или сборки.

Остановить задачу и записать blocker, если: контракт входа противоречит `MACHINE_CONTRACT.md` или `CPU_CONTRACT.md`; нужен PCI (S4-30), 2 MiB страницы (S4-10), Linux (этап 5), SMP (этап 6) или установленная Windows (этап 8), которых нет; требуется чужая прошивка, TPM-реализация, `.aml` или драйвер; спецификация недоступна и источника нет; проверка подписи или TPM проходит только с обходом; замер показывает, что путь не укладывается в бюджет, а оптимизация требует нарушить контракт (CRC, границы, атомарность записи NVRAM).
