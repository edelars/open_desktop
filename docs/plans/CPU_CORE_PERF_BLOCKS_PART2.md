# Ступень E линии CPU_CORE_PERF, часть 2. Цена гостевой инструкции в блочном режиме — пошаговый план

Статус: **план написан 2026-11-24, прошёл независимое ревью (раздел 10); ни одна задача не начата.** Вход — задачи E4 и E6 [первой части](CPU_CORE_PERF_BLOCKS.md) приняты или закрыты. Часть 2 продолжает ступень E линии [CPU_CORE_PERF](CPU_CORE_PERF.md): блоки (ADR-0018, вариант (а)) уже включены по умолчанию при `--fast-path` (E1, отчёт 7.30), и задача части — снизить число инструкций хоста на одну гостевую инструкцию в этом режиме. Факты и результаты задач записываются в [отчёт линии](../reports/CPU_CORE_PERF_REPORT.md), а не сюда. Наличие этого документа, флага или кода не закрывает задачу без её критериев и ревью.

Документ написан так, чтобы исполнитель с ограниченным контекстом мог взять **одну** задачу, выполнить её по шагам и честно отчитаться. Если шаг непонятен — остановиться и записать вопрос в отчёт, а не угадывать. Вопросы о семантике и выбор варианта отдавать Claude Opus (high), а не пользователю; пользователя спрашивать только о доступах.

## 0. Как читать этот план

1. Выполнять ровно одну задачу `E<N>` за один заход. Не начинать следующую, пока текущая не прошла ревью или не записан точный blocker.
2. Поля задачи: **Кто** (модели), **Где** (файлы), **Сделать** (пронумерованные шаги), **Проверить** (команды и наблюдения), **Готово** (критерий приёмки), **Не делать**. Делать только перечисленное.
3. **Код во всех задачах этой части пишет Claude Opus с усилием `high`** (указание владельца 2026-11-23, раздел 3). Ревью — Claude Opus (`high`), только чтение.
4. Чекбокс `- [ ]` в `- [x]` ставит только ревью PERF-40. Исполнитель добавляет под задачей строку **Текущий статус (дата):** с фактами, коммитом и ссылкой на раздел отчёта.
5. «Реализовано» — код есть, тесты проходят, ревью пройдено, прогоны сняты, отчёт записан. «Подготовлено» — код без прогонов. Не путать.
6. Номера задач продолжают первую часть (E1–E6 там). Порядок выполнения — раздел 6: **E7 → E8 → E9 → E10 → E11, E12, E13 (условные) → E14 → E15**. E7 может поменять местами только E8 и E9 (решение Opus по измеренной разбивке, записанное в отчёт); E10 всегда после E9.
7. Все пути — от корня репозитория; команды — из корня. Номера строк не даются: искать по имени функции (`graphify query` первым, затем `rg`).
8. Оценки эффекта в разделе 6 — **гипотезы для порядка работ, а не цели**. Решение по каждой задаче принимается только по замеру K4 (раздел 5).

## 4. Контракты, которые нельзя упростить ради ускорения

Разрешённые изменения контрактов первой части — только принятым ADR (или записанным решением Opus, где задача это прямо допускает), с инвариантом «та же семантика, отказ до любого эффекта»:

- контракт 1 (каждая инструкция блока исполняется `try_fast_step` с сохранённым декодом) — меняют E10 (заранее выбранный обработчик и операнды) и E11 (ленивые флаги);

1. **Кеш данных** следует политике ADR-0016 (раздел 2, пп. 1–10). Отступление — только записанным решением Opus в ADR-0016 до кода.
2. **Наблюдаемые счётчики равны побайтно**: `retired`, `quanta`, `virtual_ns`, `unified.interrupts` (включая `irq_refused_masked`, `irq_refused_shadow`, `irqs_delivered`), счётчики исключений, `unified.final_state`, снимок `--stop-snapshot`, COM1, NVRAM.

4. **Диагностические режимы**: новая оптимизация в них выключена (план линии, 4.2), в том числе при включённой трассе вызовов (`call_trace`). Исключение — собственный сверочный режим задачи, который существует, чтобы её проверять.
