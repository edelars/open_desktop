# Этап 1. Основа проверки корректности — пошаговый план реализации

**Дата:** 22 октября 2026 года. **Статус:** этап 1 принят 22 октября 2026 года для ограниченного register-only профиля S0-09; результаты, evidence и ограничения указаны в [отчёте приёмки](../reports/STAGE_1_REPORT.md).

**Ревью реализации:** устранены дефекты S1-01/S1-08/S1-12 и сохранения входов/результатов S1-06. Полный повторный прогон объединил 10 ручных и 1000 generated cases, каждый исполнен дважды на M3 Max и физическом Mac mini без расхождений; [отчёт ревью](../reports/STAGE_1_REVIEW_2026-10-22.md). Статус принятого register-only среза сохранён; прежние evidence остаются историческими.

План предназначен для модели, которой нужны небольшие последовательные задания, точные границы и проверяемый результат. Выполнять одну задачу `S1-NN` за раз. Не начинать весь этап одним большим изменением.

Нормативный объём — [этап 1 дорожной карты](../ROADMAP.md#этап-1-основа-проверки-корректности). Размещение компонентов — [карта проекта](../PROJECT_LAYOUT.md), зависимости — [архитектура](../ARCHITECTURE.md). Исходная семантика ограниченного прототипа — [CPU contract](../specs/CPU_CONTRACT.md). Этот план не заменяет эти документы и не расширяет поддерживаемую ISA.

## 1. Результат этапа

Получить воспроизводимую цепочку:

```text
собственная fixture / seed
  → проверка формата и допустимого профиля
  → interpreter на Mac
  → JIT на Mac
  → нативное исполнение тех же байтов на Mac mini с Ubuntu
  → сравнение определённого архитектурой состояния
  → отчёт о различиях
  → сокращённая fixture и команда повторения
```

Первый сквозной срез использует только уже реализованные формы `MOV`, `ADD`, `SUB`, `CMP`, `JZ`, `JNZ`, регистры RAX/RCX/RDX/RBX и флаги текущего CPU contract. Полный интерпретатор относится к этапу 2, системная память и устройства — к последующим задачам дорожной карты.

К завершению этапа также нужны проверки самого стенда, генерация граничных входов, проверяемый путь расширения на память/исключения и генератор сценариев для существующего control protocol. Наличие интерфейса расширения не означает реализацию будущих возможностей CPU или устройств.

## 2. Исходное состояние и оборудование

Подтверждено содержимым репозитория на дату плана:

- `crates/od-isa/src/lib.rs`: ограниченные decoder/interpreter; `CpuState` содержит четыре GPR, `rip` и `rflags`.
- `crates/od-jit/` и `crates/od-host/`: ограниченный ARM64 JIT и macOS execution path.
- `tools/runner/`: `od-runner` принимает hex/hex-file и сравнивает interpreter/JIT; это ещё не физический oracle.
- `tests/fixtures/x86/`: четыре положительные S0-09 fixtures и пример неподдерживаемой формы, README и SHA-256 manifest.
- `crates/od-testkit` теперь содержит fixture/result/comparator для register-only профиля; `tools/x86-runner` выполняет проверенный subset на Linux x86-64, а `tests/cpu/stage1_oracle.py` сравнивает машины. Остальные задачи этапа перечислены ниже.
- S0-12/E03 был перенесён из Stage 0 и закрыт в этом этапе физическим oracle для ограниченного register-only профиля. Stage 0 остаётся не принятым отдельно от этого результата: проверка поставки остаётся открытой как ISSUE-004 в [реестре проблем](../KNOWN_ISSUES.md).

**Единственная доступная физическая x86-машина — Mac mini с Ubuntu.** Инвентаризация и обычное SSH-соединение с проверкой host key выполнены 22 октября 2026 года для предоставленной владельцем учётной записи `senya@192.168.1.14`. Конфигурация записана в [STAND](../testing/STAND.md) и [CPU_ORACLE](../testing/CPU_ORACLE.md).

Основной host — M3 Max; M1 Pro остаётся дополнительным ARM64 smoke-стендом. Покупка второй x86-машины для первого среза не требуется. Результат на одном CPU подтверждает только этот профиль и эту машину; поддержку других моделей x86 не заявлять.

## 6. Контракты первого среза

### 6.1. Fixture и snapshot

В S1-01 зафиксировать JSON v1 с такими обязательными сведениями:

- `schema_version`, уникальный `case_id`, `profile`, происхождение и необязательный `seed`.
- Байты программы, digest точных входных данных, начальный RIP как смещение от начала кода, четыре GPR, начальные моделируемые RFLAGS.
- Instruction budget для своих движков, отдельный wall-clock timeout для native child, максимальные размеры входа и результата.
- Явная область сравнения: регистры, определённые биты flags, конечный RIP, используемые регионы памяти и ожидаемый тип завершения.
- Для памяти — виртуальные адреса относительно заданной тестовой раскладки, размеры, права, начальные байты и маски сравнения; для исключений — vector, error code при наличии, faulting RIP и fault address при наличии. В первом профиле память данных и гостевые исключения отмечены как неподдерживаемые.

64-битные архитектурные значения хранить hex-строками с фиксированной шириной; не пропускать их через JSON floating-point. Не сериализовать Rust enum через его ordinal или адреса host-указателей. Неизвестная версия, переполнение размера, повторяющийся ID региона и некорректная маска — ошибки загрузчика.

Snapshot содержит фактически наблюдённое состояние и его доступность. Отсутствующее поле не равно нулю. `ExecutionResult` текущего прототипа адаптируется в snapshot без расширения публичного C ABI только ради тестов. Профиль из четырёх регистров не называть полным снимком x86-64.

### 6.2. Типы результата и правила сравнения

Разделить как минимум:

| Результат | Значение |
|---|---|
| `completed` | Программа дошла до согласованной точки завершения |
| `guest_exception` | Поддерживаемый адаптер наблюдал и нормализовал архитектурное исключение |
| `unsupported` | Вход вне явно поддерживаемого профиля |
| `invalid_input` | Повреждённый или противоречивый тестовый файл |
| `budget_exhausted` | Лимит инструкций собственного движка |
| `timeout` | Истёк лимит реального времени дочернего процесса |
| `harness_error` | Ошибка launcher, mapping, trampoline, I/O или неожиданный host fault |

Ни один из последних пяти результатов не считается подтверждением корректного исполнения инструкции. Совпавшие `unsupported` двух движков не закрывают тест ISA. `timeout` native нельзя сравнить с `budget_exhausted` как одинаковое состояние CPU. `StopRequested` остаётся отдельным исходом запуска, если он понадобится, и не подменяет `completed`.

Сравнивать только архитектурно определённые поля. Для текущих ADD/SUB/CMP маска арифметических flags — CF/PF/AF/ZF/SF/OF из CPU contract; MOV и Jcc должны сохранять сравниваемые флаги. Маски определяются до исполнения из нормативной семантики и provenance теста. Запрещено обнулять маску после обнаруженного несовпадения. Не сравнивать неизменяемые пользовательским процессом системные биты host RFLAGS.

Native RIP нормализовать в смещение в тестовом коде. Конец буфера текущего прототипа — условие runner, а не x86-инструкция: native wrapper должен передать управление в эпилог, не исполняя случайные байты после кода. Число native инструкций не выдумывать: в первом срезе оно может быть недоступно и исключено из архитектурного сравнения.

### 6.3. Ограничения native runner на Ubuntu

Первый профиль допускает только существующие register-only формы. Нельзя передавать произвольные hex-байты в исполняемую память без проверки профиля.

1. Отдельный дочерний процесс для каждого теста, watchdog в родителе, конечные лимиты CPU/памяти/выходного файла, обязательный `wait` после завершения/kill. Обычный запуск без `sudo`.
2. Собственные code/state/stack mappings с проверками размеров и охранными страницами. Заполнение кода в writable mapping, затем переключение на executable без постоянного RWX. Охранные страницы — защита стенда от ошибок, не реализация guest MMU.
3. Допустимые формы и branch targets проверяются по текущему профилю. Запретить memory operands, RSP, CALL/RET, syscalls, I/O, privileged/system instructions и выход за тестовый код. Native исполнение делает CPU Mac mini; программного вычисления результата вместо CPU быть не должно.
4. Первый физический прогон — линейные и ациклические короткие программы. Циклы добавлять отдельно после watchdog; wall-clock timeout не даёт точного останова на заданной x86-инструкции.
5. Trampoline сохраняет host ABI, подготавливает отдельный тестовый стек, устанавливает начальные guest GPR/моделируемые flags и немедленно после программы фиксирует итог. Служебные инструкции не должны изменить flags до снимка. Восстановление host состояния не должно затереть уже сохранённый guest snapshot.
6. Отдельно проверять wrapper на неизменяемые GPR, входные flags, taken/not-taken branch и ABI возврата. Библиотечные вызовы и logging не размещать между guest fragment и захватом состояния.
7. Сигнал child не превращать автоматически в guest exception. Неожиданный fault в trampoline или host panic — `harness_error`. Разрешённые проверки исключений вводятся отдельным профилем S1-10.
8. Первичная проверка разрешённого профиля может использовать свой decoder для допуска входа; нативные значения регистров/flags вычисляются независимо. Добавить прямые fixtures с вручную проверенными байтами, чтобы ошибка общего encoder/decoder не стала единственным источником «истины».

### S1-08. Сохранять и сокращать ошибку

**Файлы:** `od-testkit/src/minimize.rs`, harness, малые regression fixtures.

### S1-10. Подготовить проверки памяти, исключений и адресных режимов

**Файлы:** testkit, native adapter, CPU_ORACLE; production CPU менять только в отдельно порученном объёме.

1. Проверить comparator на memory regions и exception metadata синтетическими snapshots. Проверить нормализацию адресов между разными host mappings.
2. В отдельном Linux user-mode профиле стенда проверить guard-page fault и заведомо недопустимую инструкцию; получить faulting RIP и доступные OS context metadata. Такие входы не смешивать с безопасным арифметическим allowlist.
3. Сохранить raw signal/context и нормализованное событие раздельно. `SIGSEGV` сам по себе не доказывает нужный vector/error code; неизвестные данные отмечать недоступными. Fault в wrapper — ошибка стенда.
4. Составить таблицу следующих проверок: memory operand на границе страницы, cross-page доступ, ModR/M/SIB/displacement, permissions, точность состояния при fault. Для каждого поля указать необходимую возможность od-isa/od-machine и будущий этап.
5. Когда соответствующая группа инструкций действительно появится в этапе 2, включить её в общий физический harness до активной оптимизации. До этого не писать фиктивное прохождение end-to-end memory tests.

**Проверка / готово:** средства наблюдения и сравнения памяти/событий проверены как инструменты; CPU capabilities явно отделены от них. Ограничения Linux user mode записаны. Paging, привилегированные fault cases и собственный bare-metal стенд остаются отдельной работой: на единственном Mac mini они потребуют отдельного загрузочного носителя и согласованного окна перезагрузки. Не менять Ubuntu, загрузчик или диск для выполнения этого плана.

### S1-15. Проверить, что стенд ловит ошибки

Выполнить тесты самого проверяющего пути:

- Несовпадение digest, schema, profile и revision policy отвергается до сравнения.

**Проверка / готово:** отрицательные случаи действительно обнаружены; временные подмены отсутствуют в production path. Не сводить проверку harness к тесту его собственного happy path.

## 8. CLI и единый harness

Подтверждённые команды текущего профиля:

```sh
# Mac: один движок → один JSON result.
cargo run --offline -p od-runner -- --fixture CASE.json --engine interpreter --json
cargo run --offline -p od-runner -- --fixture CASE.json --engine jit --json
cargo run --offline -p od-runner -- --compare-results INTERPRETER.json NATIVE.json --case CASE.json --json

# Mac mini / Ubuntu: нативное исполнение реальным CPU.
cargo run --offline -p od-x86-runner -- --fixture CASE.json --json

# Полная локальная и физическая приёмка.
python3 tests/cpu/stage1_harness.py --suite all \
  --generated-count 1000 --seed 0x5eedcafe --repeats 2

# Отдельно: создать corpus или сократить локальное расхождение.
target/debug/od-runner --generate-corpus 0x5eedcafe 1000 work/stage1-generated
target/debug/od-runner --minimize CASE.json --output work/reduced.case.json --max-attempts 1000
```

Без `--suite all` harness запускает только выбранный набор. Oracle suite требует SSH к настроенному Mac mini; по умолчанию используются `senya@192.168.1.14` и отдельный checkout `/home/senya/projects/open_desktop-stage1`. Для другого стенда доступны `--host`, `--user` и `--remote-root`. Невыбранные suites маркируются `not_run`; выбранный обязательный oracle не пропускается.
