# Ступень E линии CPU_CORE_PERF. Блочное исполнение — пошаговый план (PERF-33)

Статус: **план написан 2026-11-24; ни одна задача не начата**. Это план выполнения [PERF-33](CPU_CORE_PERF.md#perf-33-план-ступени-e) линии [CPU_CORE_PERF](CPU_CORE_PERF.md) по решению [ADR-0018](../decisions/ADR-0018-block-execution-strategy.md) (вариант (а): кеш предекодированных прямолинейных блоков без генерации кода). Факты и результаты задач записываются в [отчёт линии](../reports/CPU_CORE_PERF_REPORT.md), а не сюда. Наличие этого документа, флага или кода не закрывает задачу без её критериев и ревью.

Продолжение ступени — [часть 2](CPU_CORE_PERF_BLOCKS_PART2.md) (задачи E7–E15: цена гостевой инструкции в блочном режиме; вход — E4 принята или закрыта).

Документ написан так, чтобы исполнитель с ограниченным контекстом мог взять **одну** задачу, выполнить её по шагам и честно отчитаться. Если шаг непонятен — остановиться и записать вопрос в отчёт, а не угадывать. Вопросы о семантике и выбор варианта отдавать Claude Opus (high), а не пользователю; пользователя спрашивать только о доступах.

## 0. Как читать этот план

1. Выполнять ровно одну задачу `E<N>` за один заход. Не начинать следующую, пока текущая не прошла ревью или не записан точный blocker.
2. Поля задачи: **Кто** (модели), **Где** (файлы), **Сделать** (пронумерованные шаги), **Проверить** (команды и наблюдения), **Готово** (критерий приёмки), **Не делать**. Делать только перечисленное.
3. Чекбокс `- [ ]` в `- [x]` ставит только ревью PERF-40. Исполнитель добавляет под задачей строку **Текущий статус (дата):** с фактами, коммитом и ссылкой на раздел отчёта.
4. «Реализовано» — код есть, тесты проходят, ревью пройдено, прогоны сняты, отчёт записан. «Подготовлено» — код без прогонов. Не путать.
5. **Номера задач не совпадают с порядком.** Порядок выполнения: **E2 → E3 → E5 → E1 → E4 (условная) → E6** (раздел 6). E1 — решение о включении, оно снимается на коде после E2, E3 и E5.
6. Все пути — от корня репозитория; команды — из корня. Номера строк не даются: искать по имени функции (`graphify query` первым, затем `rg`).

### Словарь

| Термин | Значение в этом плане |
|---|---|
| Блок | Последовательность инструкций, заранее декодированных с одного входного RIP на одной 4 КиБ странице кода: заканчивается после первого перехода (Jcc, JMP, CALL, RET), перед первой инструкцией вне быстрого пути, перед инструкцией, которой нужен байт другой страницы, на конце страницы или на `MAX_BLOCK_INSTRUCTIONS` = 64 (`crates/od-isa/src/predecoded_block.rs`). |
| Проход | Подряд исполненные из одного блока инструкции в одном пакетном вызове. Средняя длина прохода (5,47) больше средней длины построенного блока (4,64), потому что короткие блоки строятся чаще, а длинные чаще исполняются. |
| Кеш блоков | `DecodedBlockCache` (`crates/od-machine/src/decoded_block_cache.rs`): direct-mapped таблица на `DEFAULT_DECODED_BLOCK_SLOTS` = 2^14 записей; ключ — RIP, физическое место (регион, смещение), поколение страницы кода, `AccessContext`, эпоха (сброс по смене контекста трансляции). |
| Удержание блока (`block_holds`) | Проверка перед каждой следующей инструкцией прохода: поколение страницы кода и счётчик сбросов кеша выборки те же, что при поиске блока. Отказ — `holds_failed`. |
| stale | Поиск нашёл запись с тем же ключом места, но устаревшим поколением страницы. |
| Быстрый путь | `try_fast_step` (`crates/od-isa/src/execute.rs`), группы Г1–Г5 (ADR-0017), флаг runner `--fast-path`, по умолчанию выключен. |
| Фильтр блока | \`fast_block_role\` (\`predecoded_block.rs\`): решает, может ли инструкция стоять в блоке. Это копия статической части допуска \`try_fast_step\`; единое правило откатано по замеру (E3, −0,45 %), синхронизацию сторожит тест \`fast_step_static_filter_tests\`. |
| Контроль / блоки | Прогон с `--fast-path --data-cache-prototype` без блоков / с блоками. Все сравнения скорости этой ступени — контроль против блоков **на одном коммите**. |
| Сверочный режим PERF-22 | `--fast-path-verify`: каждая инструкция быстрого пути сверяется с записью и воспроизведением общего пути (план линии, PERF-22). |
| Две ветки | Правило раздела 3.3 (указание владельца): на каждой машине в любой момент идёт ровно одна долгая работа; локальная машина и M1 Pro заняты разными долгими работами. |

## 1. Результат ступени и границы

В конце ступени E кеш блоков включён по умолчанию в unified-цикле платы прошивки (`boot-firmware --cpu-loop unified`) **всякий раз, когда включён `--fast-path`**, выключается флагом `--no-block-cache`, не меняет ни одного байта вывода, не держит постоянных накладных расходов (атомарный счётчик ссылок, всегда включённые счётчики), имеет один источник правила допуска с быстрым путём, закрыт тестами неэквивалентности (мутации инвалидации, граница страницы), его прирост измерен на обеих машинах, а контракты и реестр проблем описывают его политику.

Вне этой ступени (отдельные решения, в этом плане не делать):

- включение `--fast-path` или `--data-cache-prototype` по умолчанию (путь без флагов остаётся прежним);
- блоки на других циклах: `od-runner linux` (`linux_direct.rs`, golden нет), `crates/od-machine/src/firmware_board/vcpu_quantum.rs`, `host_parallel.rs`, `smp_scheduler.rs`, `paged_host_loop.rs` (план линии, раздел 4.4);
- вариант (б) ADR-0018 (`od-jit` в цикле платы) и верхний ярус (в);
- блоки на CPL3 и пакетные вызовы на CPL3;
- Jcc в середине блока (блок по-прежнему кончается после любого перехода): по профилю это не нужно — средний проход 5,47 инструкции и 92,65 % инструкций уже исполняются из блоков;
- запись в кеш трансляции данных (отдельный срез PERF-12).

### 3.3. Где запускать: правило двух веток (указание владельца)

- **Правило:** на каждой машине в любой момент идёт **ровно одна** долгая работа (`record`, `measure`, `profile`, сверка, K2); две машины заняты **разными** долгими работами; следующую работу на машине запускать только **после окончания** предыдущей (результат прочитан из файла). Не ставить цепочки команд (`&&`, `;`, циклы оболочки с несколькими прогонами) и не ждать за `work/cpu-core-perf/.run.lock` (сообщение `another record, measure or profile is running` значит, что правило нарушено: разобраться, а не ждать в очереди).
- **Локальная машина** (M3 Max, этот checkout): K1, K2, G100, K4 (F100 — 5 прогонов, K3200 — 3 прогона), сверка 300 млн, K6.
- **M1 Pro** (`192.168.1.82`, тот же относительный путь `work/cpu-core-perf/`): G3200, сверка 3,2 млрд, 3 пары K3200 (контроль/блоки чередуются).
- Машины работают одновременно (долгая работа одной не ждёт другую). Числа K4 разных машин между собой не сравниваются; сравнивается только контроль с блоками на одной машине.
- Проверяемое условие «тот же код» (вместо «одинаковый HEAD») относится к прогонам, **заявленным как один код**: контроль и блоки одной задачи, прогоны одного коммита на двух машинах. Для них: одинаковые `runner_sha256` у всех сравниваемых прогонов одной машины; пустой `git diff <база> HEAD -- crates tools/runner tools/bench Cargo.toml Cargo.lock` между коммитом базы и коммитом прогона, в том числе между коммитами обеих машин (кроме `tools/bench/linux_boot_perf.py`, если он в том же коммите, что и проверяемая правка); поле `source_diff_sha256` в JSON каждого прогона равно SHA-256 пустого вывода (`e3b0c442…b855`). Это поле пишет `git_state()` в `linux_boot_perf.py` (хеш `git diff HEAD` по `crates`, `tools/runner`, `Cargo.toml`, `Cargo.lock`); другое значение — прогон снят на грязном дереве, и его нельзя заявлять как код коммита из поля `commit`. В паре «до/после» (правило ниже) `runner_sha256` различаются по построению: разница между «до» и «после» — **только проверяемая правка**. «До» — базовый коммит с пустым `source_diff_sha256`; «после» — либо тот же коммит с правкой в рабочем дереве (`source_diff_sha256` = хеш diff правки), либо коммит, который отличается от базового только правкой. В отчёт записать `commit` и `source_diff_sha256` обеих сторон. Между машинами `runner_sha256` может отличаться — записать оба. Перед прогонами на M1: `python3 tools/bench/linux_boot_perf.py build --runner-only`; SHA-256 остальных входов в `work/cpu-core-perf/inputs.json` совпадают с локальными.
- **Пара «до/после» (одна сессия).** «До» — K4 на сборке базового коммита (HEAD до правки), «после» — K4 на сборке с правкой; та же машина, те же входы (`inputs.json`), та же команда и приоритет. Между «до» и «после» на этой машине допустимы только K1, K2, G100 и сборка (`cargo build`, `build --runner-only`); других K4, сверок KV, прогонов с `--block-stats`, `profile` и K6 между ними нет — их ставить до «до» или после «после». Старые файлы замеров как «до» не используются. Слова «пара по правилу раздела 3.3» в задачах означают это правило.
- Каждый K4 — только через `sudo -n nice -n -5 sudo -n -u "$USER" python3 tools/bench/linux_boot_perf.py measure …`; в результате `preliminary: false`. Длинные прогоны — фоновой командой с выводом в файл; результат читать из файла.

### 3.4. Запреты, общие для всех задач

- Не менять путь по умолчанию (прогон без флагов) без `GOLDEN: MATCH` на G100 и G3200 против базы.
- Не удалять `work/cpu-core-perf/.run.lock` без проверки процессов. Сообщение `another record, measure or profile is running` — сначала `pgrep -fl 'od-runner|linux_boot_perf'`; есть процесс — ждать его конца; файл трогать только когда процессов нет.
- Не коммитить `tmp_dummy_never` и другие чужие файлы: только `git add <перечисленные файлы>`, никогда `git add -A` или `git add .`.
- Пустой устаревший `.git/index.lock` можно удалить, только убедившись, что git-процесса нет.
- Не «чинить» несовпадение правкой эталона, ожидаемых чисел тестов или ослаблением `compare`.
- Не вводить блоки в диагностических режимах (`--fast-path-verify`, трасса, гистограмма, sweep, отчёт кеша выборки, `--mark-rip`/`--sample-rip`): там бюджет вызова 1 или прежний путь (план линии, раздел 4.2). Явное исключение — сверочный режим блоков `--block-cache-verify` (E5, шаг 4): он существует, чтобы проверять блоки, и идёт с ними.
- Не подключать LLVM и сторонние JIT; не копировать формулы флагов и адресации (план линии, 4.5).

## 4. Контракты блока, которые нельзя упростить ради ускорения

1. **Блок меняет только источник декода.** Каждая инструкция из блока исполняется `try_fast_step` с сохранённым декодом; отказ быстрого пути (до любого эффекта) заканчивает проход, и инструкция идёт общим шагом, как без блоков.
2. **Граница пакетного вызова не меняется.** После каждой отретайренной инструкции — тот же учёт и тот же `set_loop_batch_boundary` (устройство, `stop()`, вектор IRQ, кандидат трассы), что у PERF-25. `retired`, `quanta` и доставки IRQ равны прогону без блоков.
3. **Инвалидация точная.** Блок исполняется дальше, только если поколение его страницы кода и счётчик сбросов кеша выборки те же, что при поиске; смена контекста трансляции повышает эпоху; ROM и MMIO не кешируются; блок не пересекает 4 КиБ страницу. Ни один источник инвалидации нельзя убрать без замены, доказанной тестом E5.
4. **Отказ по умолчанию.** Блоки включаются только в unified-цикле платы прошивки и только при `--fast-path`; в остальных циклах и в диагностических режимах — выключены (исключение — `--block-cache-verify`, раздел 3.4).
5. **Вывод обычного прогона побайтно равен прогону без блоков**: JSON runner (все поля, включая `unified`), COM1, NVRAM, снимок `--stop-snapshot`. Диагностические поля блоков появляются только с флагом статистики.

## 6. Задачи и минимальные зависимости

Зависимость означает принятую (прошедшую ревью) задачу. Порядок выполнения: **E2 → E3 → E5 → E1 → E4 (условная) → E6**.

| Задача | Зависимости | Сложность | Результат |
|---|---|---|---|
| E2 | ADR-0018 «Итог» (есть) | средняя | Rc вместо Arc; счётчики и `unified.block_stats` за флагом статистики; оценка памяти записана |
| E3 | E2 | средняя | Один источник статического допуска для `try_fast_step` и `fast_block_role`; тест совпадения |
| E5 | E3 | средняя | Мутации каждого источника инвалидации и граница страницы на плате и в od-testkit; сверка декода блоков; набор в K2 |
| E1 | E2, E3, E5 | высокая (решение) | Блоки по умолчанию при `--fast-path` в unified-цикле; `--no-block-cache`; golden, K4 на обеих машинах |

Параллельны только ветки прогонов одной задачи (раздел 3.3) и документная часть E6 с прогонами E6.
