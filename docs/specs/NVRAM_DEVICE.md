# Хранилище переменных UEFI

## Формат store

`ODVARSTR` v1 хранит снимок переменных с атрибутом `NV`. Размер снимка с заголовком не превышает 256 КиБ. S7-09 строит снимок в RAM прошивки из той же таблицы, которая обслуживает volatile-переменные. Обновление переменной с `NV` синхронно обновляет снимок. Удаление учитывает атрибуты сохранённой записи, в том числе при `Attributes = 0`. На плате с [устройством NVRAM](#устройство) S7-10 добавляет восстановление и `FLUSH` при записи.

Все многобайтовые числа имеют порядок little-endian. `GUID` кодируется как `u32 Data1`, `u16 Data2`, `u16 Data3`, восемь байт `Data4`. Байты за `total_size` лежат за пределами снимка. Между записями нет padding.

| Смещение | Ширина | Заголовок снимка |
|---|---:|---|
| `0x00` | 8 | ASCII `ODVARSTR` |
| `0x08` | 2 | Версия `1` |
| `0x0A` | 2 | Размер заголовка `24` |
| `0x0C` | 4 | `total_size` от начала заголовка до конца последней записи, `24…262144` |
| `0x10` | 4 | IEEE CRC-32 заголовка с нулём в этом поле |
| `0x14` | 4 | Зарезервировано, `0` |

| Смещение | Ширина | Запись переменной |
|---|---:|---|
| `0x00` | 4 | `record_size`, включая заголовок записи, имя и значение |
| `0x04` | 4 | `record_size` с инвертированными битами |
| `0x08` | 1 | Состояние `1` для действующей записи |
| `0x09` | 1 | Зарезервировано, `0` |
| `0x0A` | 2 | Число кодовых единиц имени, `1…127` |
| `0x0C` | 4 | Атрибуты UEFI с `NV` и `BS` |
| `0x10` | 4 | Число байт значения, `1…16384` |
| `0x14` | 16 | GUID поставщика |
| `0x24` | 4 | IEEE CRC-32 всей записи с нулём в этом поле |
| `0x28` | переменная | Имя UCS-2 без NUL и суррогатов, затем байты значения |

Стоимость записи равна `40 + 2 × name_units + value_size`. Таблица разделяет общий предел `262120` байт между всеми переменными. Записи идут в порядке создания ключей `(GUID, имя)`. Замена сохраняет позицию, удаление сразу уплотняет следующие записи, повторное создание добавляет ключ в конец. Снимок сохраняет этот порядок среди записей `NV`. `APPEND_WRITE` задаёт операцию записи и в снимок не попадает.

Декодер отклоняет неверный заголовок. Когда размер записи и его инверсия задают проверенную границу, неверный CRC или содержимое возвращает ошибку с байтовым смещением и декодер продолжает со следующей записи. При усечении или неверной границе он возвращает ошибку хвоста, сохраняя уже прочитанные записи. Ошибки формата обрабатываются как данные. Политика доступности, аутентификации и встроенных переменных описана в [профиле UEFI](UEFI_PROFILE.md#переменные).

## Защищённый формат v2

Для Secure Boot host создаёт `ODNVBANK` версии 2 с банками `ODVARSTR` версии 2. Размер снимка, размеры банков, порядок байтов и алгоритмы CRC те же. В v2 при открытии каждый непустой банк проходит проверку своего CRC и полного store. Неиспользованный банк целиком нулевой, как и байты после значения в каждом принятом банке. Повреждение защищённого снимка возвращает ошибку, включая случай, когда в другом банке сохранилась более ранняя политика. Legacy `ODNVBANK` v1 сохраняет восстановление последнего годного поколения. Для v2 запись NVRAM имеет `param0 = 2`. Плата выдаёт handoff v1.14 с флагом `secure_boot_disabled` и v1.15 при разрешённой проверке образов. Старый образ с `handoff_minor_max = 14` при запросе v1.15 получает `ProtectionRequiresFirmware` до запуска. [Handoff](FIRMWARE_BOOT.md#64-правило-расширения-и-версии), [ADR-0011](../decisions/ADR-0011-secure-boot-keys.md).

Заголовок `ODVARSTR` v2 имеет прежние 24 байта. В `0x08` версия `2`. В слове `0x14` бит 0 фиксирует отключённый режим Secure Boot, бит 1 — изменение набора vendor keys. Остальные биты зарезервированы и равны нулю. Заголовок и длина охватывают весь объём image без внешних байтов.

Обычная запись сохраняет обычные NV-атрибуты (`NV | BS` с необязательным `RT`) и предел 16 КиБ значения. Защищённые ключи определяются парой GUID и UCS-2 имени. Для `PK`/`KEK` используется `EFI_GLOBAL_VARIABLE`, для `db`/`dbx`/`dbt`/`dbr` — `EFI_IMAGE_SECURITY_DATABASE_GUID`. В store может быть одна запись на защищённый ключ. Значения `SecureBoot`, `SetupMode`, `AuditMode`, `DeployedMode`, `VendorKeys` и `SignatureSupport` под `EFI_GLOBAL_VARIABLE` определяются firmware-политикой, попытка положить их прямо в store отклоняется.

| Поле защищённой записи v2 | Значение |
|---|---|
| `0x08`, состояние | `1` — запись со значением, `2` — удалённая запись с отметкой времени |
| `0x09`, метаданные | `1` — защищённая запись с `EFI_TIME`, `0` для обычной записи |
| `0x0C`, атрибуты | `0x27` (`NV | BS | RT | TIME_BASED_AUTHENTICATED_WRITE_ACCESS`) |
| `0x10`, размер значения | `1…65536` для действующей записи, `0` для удалённой |
| После имени, 16 байт | Канонический `EFI_TIME` Auth2. Нули обозначают исходное значение без watermark. Удалённая запись содержит действительное время |
| После времени | Байты значения, если запись действующая |

`record_size` и CRC покрывают также 16 байт метаданных. Фактический x64 `dbx` Microsoft v1.7.2 занимает 21 388 байт и проходит v2 без усечения. Общий предел store — 256 КиБ. Обычные записи занимают до 128 КиБ с учётом framing. Для защищённых записей зарезервированы оставшиеся 128 КиБ за вычетом заголовка, 131 048 байт. За счёт этого заполнение store обычными переменными оставляет место для обновления политики и отзывов.

Обычный MMIO `WRITE` у v2 записывает кандидата в отдельный staging-буфер. При `FLUSH` устройство проверяет полное оформление кандидата и побайтно сравнивает заголовочные флаги и каждую защищённую запись с текущим банком по ключу. Перемещение записи при уплотнении допустимо. Подмена, удаление, повтор защищённого ключа, смена статуса, watermark, флага или версии дают `POLICY_REJECTED` (`0x8000_0005`). Успешный `FLUSH` атомарно переключает банк. При неполной передаче или отказе сохраняются оба ранее принятых банка. [ISSUE-530](../KNOWN_ISSUES.md#issue-530).

### Authenticated update v2

После полного `WRITE` команда `AUTH_UPDATE` (`CMD=4`) потребляет staging как запрос Auth2. Начальный `WRITE` принимает размер всего запроса. `AUTH_UPDATE` вызывает проверку и commit только в защищённом устройстве. В handoff v1.14 прошивка передаёт Auth2 из `SetVariable` устройству и обновляет рабочий образ прямым `READ`. Операции с обычными NV-переменными передают на `FLUSH` новый образ с побайтно сохранёнными защищёнными записями. Прошивка обновляет образ из устройства перед операциями чтения и записи, включая чтение параметров для следующего монотонного счётчика.

| Смещение | Поле запроса |
|---|---|
| `0x00` | `u32 Attributes`, `0x27` или `0x67` при `APPEND_WRITE` |
| `0x04` | `u16` числа UCS-2 единиц имени без NUL, `1…127` |
| `0x06` | `u16`, зарезервировано и равно нулю |
| `0x08` | GUID поставщика, 16 байт |
| `0x18` | Имя в UCS-2 LE, затем полный `EFI_VARIABLE_AUTHENTICATION_2` с новым значением |

Устройство проверяет Auth2 относительно текущего `PK` и `KEK` в активном банке. `PK` и `KEK` обновляет владелец текущего `PK`. Для `db`, `dbx`, `dbt` и `dbr` допустим текущий `PK` или проверенная цепочка до зачисленного `KEK`. При пустом `PK` режим SetupMode сохраняет проверку структуры, времени и нового значения. Пустой `CertData` допустим только в SetupMode для первоначального enroll. Непустой `CertData` декодируется как PKCS#7 и в SetupMode.

PKCS#7 ограничен 16 КиБ, новое значение — 64 КиБ. Для записи без append timestamp должен быть больше сохранённого. При append сохраняется максимум времени, уже записанные `EFI_SIGNATURE_DATA` того же типа пропускаются. Действительное удаление сохраняет watermark в tombstone. Принятая запись с прежним результатом и timestamp оставляет оба банка побайтно прежними. Изменение значения в SetupMode устанавливает липкий флаг `vendor_keys_modified`, который очищается явным host reset ключей в целевом workflow. Подписанное обновление сохраняет этот флаг.

| `STATUS` | Результат `AUTH_UPDATE` |
|---|---|
| `3` | Изменение применено или поданное обновление оставило результат прежним |
| `0x8000_0001` | Неверные поля запроса, имя, атрибуты или тип значения |
| `0x8000_0002` | Передача незавершена |
| `0x8000_0003` | Команда вызвана на legacy-устройстве |
| `0x8000_0004` | Исчерпано поколение для нового коммита |
| `0x8000_0005` | Неверный Auth2, время или авторизация |
| `0x8000_0006` | Удаляемая переменная отсутствует |
| `0x8000_0007` | Исчерпан предел размера запроса, значения или зоны store |

### Проверка PE-образа

Защищённое устройство принимает полный исходный PE в окне данных. Максимальный размер одного незавершённого образа — 64 МиБ. Начало новой передачи освобождает прежний буфер. `IMAGE_VERIFY` проверяет байты по `PK`, `db`, `dbx` и флагу отключения из активного банка на момент команды. Команды не меняют содержимое или поколения банков. Неполная передача не попадает в снимок и пропадает при открытии устройства заново.

| `CMD` | Вход | Успешный `STATUS` |
|---|---|---|
| `5` `IMAGE_BEGIN` | `ADDR=0`, `LEN` равен полному размеру PE, от 1 байта до 64 МиБ | `4` `IMAGE_COLLECTING` |
| `6` `IMAGE_CHUNK` | `ADDR` равен числу принятых байтов образа, `LEN` от 1 до 256 КиБ и не больше остатка. Записать ровно `LEN` байт по порядку с нулевого смещения окна | `2` `WRITE_READY` |
| `7` `IMAGE_VERIFY` | `ADDR=0`, `LEN=0`, все байты переданы | `5` `IMAGE_AUTHORIZED`, `6` `IMAGE_POLICY_DISABLED` или `0x8000_0005` `POLICY_REJECTED` |

Успешный `IMAGE_VERIFY` при активной политике устанавливает в `LEN` размер ответа. Чтение с нулевого смещения окна возвращает точную запись `EFI_SIGNATURE_DATA` из `db`, включая GUID владельца. `IMAGE_POLICY_DISABLED` означает SetupMode (отсутствует действующий `PK`) или установленный host-флаг `secure_boot_disabled`, данных ответа нет. Отозванный, неподдерживаемый или недоверенный образ даёт `POLICY_REJECTED`. Некорректные диапазоны дают `INVALID_RANGE`, неполная передача даёт `INCOMPLETE`, невозможность выделить буфер даёт `OUT_OF_RESOURCES`. Любая команда потребляет прежнее состояние окна. Только успешный `IMAGE_CHUNK` продолжает накопление или `IMAGE_VERIFY` публикует ответ. Legacy-устройство возвращает `INVALID_COMMAND`. В handoff v1.15 команды используются перед исполнением внешнего образа.

После `IMAGE_VERIFY` со статусом `POLICY_REJECTED` регистр `LEN` содержит действие из `EFI_IMAGE_EXECUTION_ACTION`. Значение `0` означает образ без сертификатов, `1` — неверную подпись или отозванный сертификат, `3` — подпись без доверенного совпадения в `db`, `4` — отозванный дайджест образа с сертификатом, `5` — отказ по профилю проверки. `ADDR=32` открывает первые 32 байта окна с Authenticode SHA-256, уже рассчитанным при проверке. `ADDR=0` сообщает об отсутствии дайджеста и закрывает окно. Любая следующая команда потребляет этот ответ. [UEFI 2.11 §32.4](https://uefi.org/specs/UEFI/2.11/32_Secure_Boot_and_Driver_Signing.html#image-execution-information-table).


В защищённом устройстве 32-битные регистры только для чтения `POLICY_EPOCH_LOW` (0x14) и `POLICY_EPOCH_HIGH` (0x18) образуют volatile-счётчик. Каждая команда Auth2, переключившая банк, увеличивает его на единицу. Обычный `FLUSH` и операции без commit его сохраняют. При новом экземпляре и открытии снимка счётчик равен нулю. При измерении PCR7 прошивка читает старшее слово до и после младшего, сверяет счётчик с прочитанным банком и с ответом верификатора. Пропущенные поколения Auth2 требуют перезапуска платформы перед продолжением загрузки.
### Первоначальные ключи и холодный сброс

`NvramDevice::with_secure_boot_keys(SecureBootKeys::Defaults { public_platform_key })` создаёт начальный защищённый образ. API принимает DER публичного сертификата PK. `PK`, два KEK Microsoft, четыре разрешённых сертификата `db` и исходный x64 `dbx` получают исходное состояние без watermark. Для сертификатов Microsoft в ESL используется `SignatureOwner` `77fa9abd-0359-4d32-bd60-28f4e78f784b`, как в исходных payload Microsoft. У PK используется GUID Open Desktop `59e9fee3-6100-4a0d-ad96-a6c8f63aaf68`. [Решения и источники](../decisions/ADR-0011-secure-boot-keys.md), [эталоны](../../tests/fixtures/firmware/certs/README.md).

`reset_secure_boot_keys` открывает предоставленный доверенной host-стороной защищённый снимок и возвращает новый экземпляр. Обычные записи сохраняются вместе с байтами значения и атрибутов. При `SetupMode` набор защищённых ключей и watermark становится пустым. При `Defaults` действующий публичный RSA-ключ PK должен быть новым, сравниваются modulus и exponent. Неподдержанный или повреждённый снимок и недействительный PK возвращают ошибку. Режим запущенного устройства меняется через обычный защищённый протокол; холодный host reset работает со снимком.

## Устройство

Плата с NVRAM использует handoff v1.7. Запись устройства 5 и регион типа `NVRAM` описывают один диапазон `[0xFF00_0000, 0xFF04_1000)`. Первые 256 КиБ служат окном данных, последние 4 КиБ содержат регистры. В карте UEFI это `EfiMemoryMappedIO` с `EFI_MEMORY_UC | EFI_MEMORY_RUNTIME`. [Контракт handoff](FIRMWARE_BOOT.md#63-таблица-устройств-запись-48-байт).

Регистры требуют выровненный 32-битный доступ. Смещения в таблице отсчитываются от `0xFF04_0000`. Многобайтовый доступ к данным передаёт 1, 2, 4 или 8 байт в порядке little-endian. Доступ должен целиком помещаться в выбранный диапазон данных или регистр.

| Смещение | Имя | Доступ | Поле |
|---|---|---|---|
| `0x00` | `ADDR` | R/W | Смещение в окне данных для следующей команды |
| `0x04` | `LEN` | R/W | Число байт для следующей команды |
| `0x08` | `CMD` | W | `1` READ, `2` WRITE, `3` FLUSH |
| `0x0C` | `STATUS` | R | Результат последней команды |
| `0x10` | `ACTIVE_LEN` | R | Число байт в последнем принятом снимке. Ноль при восстановлении legacy без действующего банка |

При открытии канонического `ODNVBANK` v1 плата выбирает исправный банк с наибольшим поколением. Если оба банка недействительны, путь загрузки legacy публикует `ACTIVE_LEN=0` и пустые банки. Прошивка пропускает READ, сохраняет созданные volatile defaults, восстанавливает обычные начальные NV-переменные и коммитит новый банк поколения 1 до публикации Variable Services. COM1 сообщает `OD-FW S7-10 NVRAM discarded both invalid banks`. Строгий API `NvramDevice::with_contents` возвращает ошибку для снимка без исправных банков. Защищённые v2, неизвестный формат и неоднозначные поколения также отклоняются при запуске платы.

`READ` запоминает непустой диапазон `[ADDR, ADDR + LEN)` внутри активного банка. Чтение производится через эти же смещения в окне данных. `WRITE` принимает `ADDR = 0` и `1 ≤ LEN ≤ 262144`, инвалидирует неактивный банк и запоминает длину снимка. Записи в окно идут подряд с нулевого смещения. Неверное смещение или ширина доступа сохраняют состояние и позицию передачи. Новая команда завершает предыдущую передачу.

`FLUSH` при полном WRITE вычисляет CRC по записанным байтам и новому поколению, затем делает этот банк активным. При неполной записи, неизвестной команде, недопустимом диапазоне или исчерпании поколений активный банк сохраняется. Гость меняет запись в рабочей таблице переменных только после успешного `FLUSH`.

| `STATUS` | Значение |
|---|---|
| `0` | Устройство только что создано |
| `1` | READ готов |
| `2` | WRITE готов |
| `3` | FLUSH завершён, новый банк активен |
| `0x80000001` | Недопустимый диапазон |
| `0x80000002` | FLUSH без полной записи |
| `0x80000003` | Неизвестная команда |
| `0x80000004` | Исчерпаны поколения |

Ошибки доступа на шине описаны в [контракте машины](MACHINE_CONTRACT.md#устройство-nvram). `STATUS` сообщает результат команды, записанной корректным доступом к `CMD`.

### Проверка сообщений PKCS#7

Защищённое устройство принимает `CMD=8` после полностью записанного через `WRITE` staging-запроса. Для `CMD=8` регистры `ADDR` и `LEN` равны нулю. Legacy-устройство возвращает `InvalidCommand`. Незавершённая запись возвращает `Incomplete`, некорректная рамка или диапазон — `InvalidRange`. Другая команда прекращает текущий обмен и делает предыдущий ответ недоступным.

Запрос начинается с 24 байт. Октет 0 равен `1`. Октет 1 определяет режим: `0` для embedded, `1` для detached, `2` для переданного SHA-256. Октеты 2–3 нулевые. Далее идут пять размеров `u32` little-endian и соответствующие им последовательные поля `SignedData`, входные байты, AllowedDb, RevokedDb и TimeStampDb. Каждая база состоит из полных `EFI_SIGNATURE_LIST`. Вход отсутствует для embedded, может быть пуст для detached, а для digest имеет размер 32 байта. Подпись и каждая база ограничены 64 КиБ, весь запрос — 256 КиБ.

После проверки `STATUS=7` открывает 12 байт с тремя `u32` little-endian: номер исхода EFI без бита ошибки, смещение embedded относительно `SignedData` и длина embedded. Возвращаются `0`, `3`, `14`, `21`, `26`, `33`. Смещение и длина равны нулю для ошибки, detached и digest. Устройство использует только переданные данные. Банк, поколения и `POLICY_EPOCH` не меняются. [UEFI 2.11 §37.4](https://uefi.org/specs/UEFI/2.11/37_Secure_Technologies.html#pkcs7-verify-protocol).

## Host API

`LoadedFirmwareBoard::nvram_snapshot() -> Option<Vec<u8>>` между квантами возвращает снимок двух банков или `None` для платы без NVRAM. `NvramDevice::with_contents(&bytes)` строго проверяет снимок и создаёт отдельное устройство. Для новой платы `FirmwareBoardConfig::nvram` принимает `None` без NVRAM, `Some(NvramConfig::Empty)` с пустым legacy v1 или `Some(NvramConfig::Snapshot(bytes))` с полученным либо подготовленным снимком. Runner использует `Snapshot` для повторного запуска того же ROM в одном процессе.

Host-снимок `ODNVBANK` v1 имеет длину `0x80030`. Числа little-endian. Первые 16 байт содержат magic `ODNVBANK`, `u32 version = 1`, `u32 reserved = 0`. Далее по порядку идут два слота по `0x40010` байт.

| Смещение в слоте | Ширина | Поле |
|---|---:|---|
| `0x00` | 8 | Поколение. `0` обозначает недействительный банк |
| `0x08` | 4 | Длина полезных байт `1…262144` |
| `0x0C` | 4 | IEEE CRC-32 над поколением, длиной и полезными байтами |
| `0x10` | `0x40000` | Полезные байты, далее нулевое заполнение до конца слота |

При записи снимка незавершённый банк и хвост за полезными байтами заполняются нулями. При создании устройства из снимка каждый банк проверяется отдельно. Выбирается наибольшее валидное поколение. Отсутствие валидных банков, два одинаковых валидных поколения или неверный заголовок дают ошибку. Регистры и курсор передачи создаются заново.

В новом устройстве банк 0 содержит поколение `1` и пустой `ODVARSTR` v1 из 24 байт. Банк 1 недействителен.

```text
4f 44 56 41 52 53 54 52 01 00 18 00 18 00 00 00 5b ed 3b 0b 00 00 00 00
```

### Persistence и совместимость

Для одного и того же размера оболочки заголовок `ODNVBANK` определяет версию полезных данных. Доступны legacy v1 и защищённый v2. У v2 каждый непустой банк проходит проверку CRC и полного `ODVARSTR` v2. Место неиспользуемого банка и хвост каждого принятого банка состоят из нулей. Неизвестная версия, неоднозначное поколение и недействительный защищённый снимок приводят к ошибке. CRC обнаруживает повреждение. Идентичность VM и допустимость отката определяет владелец контейнера. [Защищённый формат](#защищённый-формат-v2).

При загрузке платы есть отдельный путь восстановления legacy v1. Если оболочка прошла проверку, а оба банка недействительны, прошивка получает пустой store и может закоммитить новый банк. Строгий `with_contents` возвращает `NoValidBank` в том же случае. При восстановлении уже существующего состояния из bundle S9-26 проверяет снимок строго и обрабатывает повреждение отдельно от отсутствия файла.

При создании legacy VM без файла можно выбрать `NvramConfig::Empty`. Для новой VM с Secure Boot создатель формирует `NvramDevice::with_secure_boot_keys(keys)`, получает `NvramDevice::nvram_snapshot()` и передаёт байты через `NvramConfig::Snapshot`. Явный холодный сброс ключей строит новый защищённый снимок из прежнего через `NvramDevice::reset_secure_boot_keys(bytes, keys)`. Обычные NV-переменные сохраняются. Для VM с ожидаемым защищённым состоянием отсутствие файла требует решения S9-26 о восстановлении либо явном первоначальном создании. Автоматического перехода на legacy нет в контракте восстановления. [Первоначальные ключи и холодный сброс](#первоначальные-ключи-и-холодный-сброс).

Байты этапа 7 описывают зафиксированные банки. Регистры, staging и volatile `POLICY_EPOCH` создаются заново при открытии. Запись в bundle между процессами, согласованный захват с остальной VM и защита от подмены или отката относятся к S9-26. [Контракт участника сохранения](../plans/STAGE_9.md#s9-26-включить-uefi-variables-как-отдельного-участника).
