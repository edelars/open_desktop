**Статус:** документный контракт S6-03 принят после независимого архитектурного ревью `gpt-6.1-sol/high`. Плата с N LAPIC (S6-11), IPI/NMI/INIT/SIPI (S6-12a–S6-13) и планировщик чередования (S6-15, к Linux-циклу не подключён) реализованы; AP исполняется в legacy-режиме от SIPI до long mode (S6-16c, планировщик в цикл Linux не подключён; probe — S6-16e). ## 2. Набор vCPU и идентичность

- `N` задаётся конфигурацией платы при её создании и неизменен до выключения. Первое SMP target допускает `N = 2`; `N = 4` становится поддержанным только после gate измерений S6-38. `N = 1` сохраняет текущую конфигурацию. Значения больше 4 не входят в версию 1.
- Индекс vCPU 0 — BSP. Для всех vCPU `APIC_ID = index`; идентификаторы стабильны и равны `0…N−1`.
- Для `N > 1` CPUID.1 EBX сообщает `N` в поле logical processor count и ID текущего vCPU в поле initial APIC ID. CPUID topology leaves `0x0b`, `0x1f`, `0x80000026` в reference CPU profile отсутствуют.
- **Ограничение topology:** guest vendor `OpenDesktop ` не распознаётся vendor switch Linux 7.0.0-38.38 `topology_common.c`. Linux читает из CPUID.1 EBX начальный APIC ID и count shift, но не запускает известный legacy или extended topology parser; topology domains остаются defaults для одного logical CPU с нулевыми shifts. Поэтому CPUID/MADT/`cpu_count` должны согласовываться, но package/core classification Linux для N=2/4 этим source path не доказана. Решение по topology domains принадлежит S6-18.
- MADT содержит ровно `N` enabled Processor Local APIC entries, по одной на UID/APIC ID `0…N−1`. DSDT содержит matching processor device objects (`_HID=ACPI0007`, `_UID` равен MADT UID). Публикация MP Wakeup type `0x10` противоречит выбранному INIT/SIPI handoff.
- Платы и firmware передают одно и то же `N`. Firmware handoff block v1.0 сейчас нормативно требует `cpu_count=1`; переход к `N>1` — отдельное согласованное изменение S7-02, здесь он отмечен как зависимость, но не изменяется.

## 3. Состояния vCPU и переходы

Каждый vCPU владеет своим архитектурным состоянием CPU и своим LAPIC. Межпроцессорное сообщение записывается как pending event в LAPIC адресата. Изменить состояние чужого CPU можно только при обработке события самим адресатом на своей границе исполнения.

| Текущее состояние | Событие адресата | Результат |
|---|---|---|
| Power-on, индекс 0 | machine reset/handoff | `Running` с BSP ролью и состоянием handoff из `FIRMWARE_BOOT.md`. |
| Power-on, индекс > 0 | machine reset/handoff | `WaitForSipi`; AP не исполняет код до SIPI. |
| `Running` или `Halted`, AP | INIT assert | На своей границе применяет INIT state из §4, очищает локальное interrupt state согласно LAPIC INIT reset и входит в `WaitForSipi`. Pending STARTUP, принятый до INIT, удаляется; последующий SIPI остаётся отдельным событием. INIT не снимает Remote IRR маршрута IOAPIC к этому LAPIC: по SDM его снимает только EOI. |
| `WaitForSipi`, AP | SIPI | Первый SIPI переводит AP в `Running` с real-mode стартом по адресу `vector × 4096`; `vector` — младшие 8 бит поля Vector (`ICR[7:0]`). |
| AP уже покинул `WaitForSipi` | SIPI | Игнорируется: повторный startup не сбрасывает выполняющийся AP. |
| `Running` | HLT retirement | `Halted`; архитектурное состояние CPU сохраняется. |
| `Halted` | принимаемый Fixed interrupt | `Running`, когда interrupt допускается IF/priority правилами LAPIC/CPU; запрос доставляется как interrupt vector, не как прямой вызов handler. |
| `Halted` | NMI, NMI delivery не заблокирован | `Running`; NMI принимается независимо от IF и доставляется вектором 2. Если NMI blocking активен, запрос остаётся единственным pending NMI, CPU остаётся `Halted` и вложенной доставки нет. |
| Исполняемое состояние | Fault при обработке #DF, вызывающий shutdown | `Shutdown`, исполнение прекращается. Состояние запоминает `hardware_reset_only=true`, если shutdown произошёл во время NMI handler или SMM; иначе `false`. |
| `Shutdown` | machine reset | BSP получает BSP reset/handoff state; остальные vCPU — `WaitForSipi`. |
| `Shutdown` (`hardware_reset_only=false`) | INIT или NMI | INIT применяет соответствующий BSP/AP reset path; NMI возобновляет обработку через handler vector 2. Любые pending события обрабатываются после wake event. |
| `Shutdown` (`hardware_reset_only=true`) | INIT/NMI | Остаётся `Shutdown`; ни INIT, ни NMI не рестартуют CPU. Intel SDM требует hardware reset, если shutdown произошёл во время NMI handler или SMM. |
| Любое состояние | остановка VM host | vCPU приостанавливается на указанной безопасной границе; архитектурное состояние и LAPIC pending events сохраняются. Это pause, а не гостевой INIT/reset. |

Scheduler не выбирает `WaitForSipi` и `Shutdown` для исполнения. `Halted` может быть пропущен до появления принимаемого события. Pending INIT/SIPI не меняет удалённое состояние немедленно и не теряется при pause.

## 4. INIT, SIPI и reset state

Для выбранной Intel 64 family 06H архитектурной таблицы INIT из SDM §12.1.1/Table 12-1 CPU после INIT находится в real-address mode с `EFLAGS=2`, `EIP=0xFFF0`, `CR2/CR3/CR4=0`, `EFER=0`; по footnote 2 Table 12-1 `CR0 = (old_CR0 & 0x60000000) | 0x10`, то есть сохраняются только прежние `CD/NW`, устанавливается `ET=1`, а все прочие биты `CR0` очищаются. `CS` получает selector `0xF000`, base `0xFFFF0000`, limit `0xFFFF`; `SS/DS/ES/FS/GS` — selector/base 0 и limit `0xFFFF`. `EAX`, `EBX`, `ECX`, `ESI`, `EDI`, `EBP`, `ESP` и `R8–R15` очищаются; `EDX` сохраняет processor signature. `GDTR/IDTR` получают base 0 и limit `0xFFFF`; `LDTR/TR` получают selector/base 0, limit `0xFFFF`, reset attributes; debug registers получают значения Table 12-1.

INIT не равен power-on reset. Не очищаются x87/MMX, XMM/MXCSR, XCR0/XSS, `IA32_TSC`, `IA32_TSC_AUX`, `IA32_TSC_ADJUST`, `IA32_TSC_DEADLINE`, `IA32_SYSENTER_CS/ESP/EIP`, `IA32_STAR/LSTAR`, MTRRs, performance counters и machine-check banks. FS/GS base и EFER — исключения к общему сохранению MSRs: Table 12-1 задаёт для них reset values. Internal caches сохраняются; TLB и BTB инвалидируются (§12.1.1). LAPIC возвращается к INIT-reset state, сохраняя APIC ID и arbitration ID (§13.4.7.3).

- Гостевые ячейки vCPU при INIT: `EFER` и `CR2` обнуляются (Table 12-1); STAR, LSTAR, SYSENTER и FP-состояние не меняются. После включения у AP `EFER=0`.
- INIT для AP выполняется как выше и оставляет его в `WaitForSipi`; SIPI задаёт низкий real-mode startup vector.
- Состояние S6-13: INIT assert, адресованный BSP (vCPU 0), отказывается устройством LAPIC до изменения состояния; применение INIT к BSP отложено до S6-15/S6-16. Целевое поведение ниже остаётся нормой для этих срезов. INIT для BSP тоже выполняет архитектурное INIT state, но BSP flag/роль сохраняется. BSP не становится AP и не ждёт SIPI; после reset boundary он начинает bootstrap execution с reset-vector state. INIT protocol не выполняется заново после выбора BSP (SDM §11.4.2).
- INIT-deassert не является повторным INIT и не запускает код. Linux 7.0.0-38.38 посылает targeted INIT-deassert между assert и SIPI. В S6 xAPIC его запись принимается как совместимое no-op для CPU state и LAPIC pending state; delivery завершается, BSP/AP state не меняется. Это ограниченное поведение target, а не утверждение, что INIT-deassert поддерживается каждым поколением Intel CPU.
- SIPI запускает только AP в `WaitForSipi`. Для вектора `v` стартовый physical address равен `v << 12`; выбранный Linux target использует адрес из low-memory trampoline. SIPI для BSP или уже работающего AP завершается без повторной инициализации.

## 5. ICR: закрытый набор кодировок версии 1

Для xAPIC запись aligned Dword в `ICR_HIGH` сохраняет только destination byte и сама по себе не отправляет IPI. Aligned Dword запись в `ICR_LOW` начинает отправку; read-only Delivery Status bit игнорируется при записи и читается как Idle после завершения отправки. Сначала применяется таблица допустимых delivery/destination/shorthand. Затем таблица пары `(Level, Trigger)`. **Любая комбинация, не перечисленная как поддерживаемая ниже, возвращает явную ошибку LAPIC device и не ставит событие в очередь.** Reserved ICR bits дают device error. В shorthand destination byte и Destination Mode bit игнорируются, как требует xAPIC; это не реализует logical routing. Отправитель не ждёт синхронного исполнения адресата.

| Delivery mode | Destination mode | Shorthand | Vector | `(Level, Trigger)` | Итог |
|---|---|---|---|---|---|
| Fixed | Physical | None | `0x10–0xFF` | `(0,0)` | Доставить targeted Fixed IPI адресату `APIC_ID`; событие входит в локальный LAPIC pending/IRR. Это кодировка pinned Linux. |
| Fixed | ignored by shorthand | Self | `0x10–0xFF` | `(0,0)` или `(1,0)` | Доставить Fixed IPI отправителю. `(1,0)` сохраняет существующий S4-25c encoding; `(0,0)` — Linux source encoding. |
| Fixed | ignored by shorthand | All including self | `0x10–0xFF` | `(0,0)` | Доставить Fixed IPI всем vCPU, включая отправителя. Требуется планом S6-12. |
| Fixed | ignored by shorthand | All-but-self | `0x10–0xFF` | `(0,0)` | Доставить Fixed IPI каждому другому vCPU; используется Linux reboot stop path. |
| NMI | Physical | None | поле ignored; Linux emits 0 | `(0,0)` | Targeted NMI event. |
| NMI | ignored by shorthand | All-but-self | поле ignored; Linux emits 0 | `(0,0)` | NMI всем другим vCPU; используется Linux reboot/crash/debug stop paths. |
| INIT | Physical | None | ровно 0 | `(1,1)` assert; `(0,1)` deassert | Assert применяет INIT к адресату; deassert принимается как no-op CPU/LAPIC state. |
| Start-up (SIPI) | Physical | None | `Vector[7:0]` (`0x00–0xFF`) | `(0,0)` | Поставить SIPI vector адресату. |
| Все прочие значения: включая Lowest Priority, SMI, reserved modes, logical destination без shorthand, NMI Self/All, INIT/SIPI shorthand и неуказанные пары Level/Trigger | — | — | — | — | Явная ошибка LAPIC device; состояние всех vCPU остаётся прежним. |

Linux `__prepare_ICR()` в pinned source для Fixed/NMI и SIPI формирует `Level=0, Trigger=0`; trigger для этих delivery modes не управляет доставкой. Fixed дополнительно сохраняет уже принятый S4-25c `(Level, Trigger)=(1,0)` self-IPI encoding. Поэтому target принимает обе существующие формы, а не навязывает `Level=1` для Linux edge IPIs. Для INIT assert Linux пишет level-triggered assert; затем targeted level-triggered deassert; SIPI отправляется targeted physical с vector `start_eip >> 12`.

Подтверждено владельцем 2026-11-16 (срез S6-12a). (а) Self с `(0,0)` принимается наравне с `(1,0)`, поэтому прежнее ожидание теста, отвергавшее Self `(0,0)`, заменено. (б) Консервативные решения реализации: если любой адресат Fixed IPI (физический, All или All-but-self) имеет глобально выключенный LAPIC либо вектор, зарезервированный level-входом IOAPIC в его LAPIC, вся IPI отклоняется явной ошибкой устройства без изменения состояния всех vCPU. (в) All-but-self при одном vCPU не имеет адресатов: запись принимается, событий нет. Адресаты вне `0…N−1` (включая broadcast `0xFF`) — явная ошибка по правилу «не перечислено — ошибка».

Подтверждено владельцем 2026-11-16 (срез S6-13). (а) Отказ при `IA32_APIC_BASE.EN = 0` у адресата распространяется на INIT assert и SIPI так же, как на Fixed: явная ошибка устройства без изменения состояния. (б) Программное выключение через SVR (бит 8 сброшен, например `SVR = 0xFF`, при `EN = 1`) INIT и SIPI не мешает: адресат их принимает (SDM §10.4.3, по памяти). (в) INIT assert, адресованный BSP, — ошибка устройства до S6-15/S6-16; INIT deassert и SIPI для BSP принимаются (SIPI процессор игнорирует). (г) INIT не снимает Remote IRR (§3, §6).

Fixed IPI vector доставляется как maskable APIC interrupt через CPU/LAPIC acceptance path. Набор `0x10–0xFF` допускает SDM §13.5.2; `0xFF` также покрывает существующий S4-25c contract. Все Fixed shorthand из S6-12 (`Self`, `All including self`, `All-but-self`) перечислены выше. Lowest Priority отсутствует потому, что Linux target выбирает physical-flat xAPIC и не нуждается в priority arbitration; SMI, logical destinations и дополнительные shorthand не входят в доказанный S6-02 target.

## 6. IOAPIC, MSI и локальная адресация LAPIC

Для reference `OpenDesktop` target выбран physical-flat xAPIC: APIC destinations физические, `APIC_ID` адресата берётся из CPUID/MADT-consistent набора. IOAPIC и MSI маршрутизируют только Fixed physical interrupts к APIC ID `0…N−1`; logical и Lowest Priority routing для этого профиля отклоняются. MSI composition сохраняет физический адресат и Fixed delivery. *Обновление S7-32 (2026-11-26):* модели IOAPIC, MSI-X и ICR платы принимают также logical destination (flat/cluster по LDR/DFR) и Lowest Priority (одна цель — первая по адресату, арбитраж не моделируется), как их программирует HAL Windows; адресат маскированной записи IOAPIC хранится как записан и разрешается при снятии маски, а маршрут доставки по-прежнему всегда называет существующий vCPU (адресат, не называющий ни одного, у немаскированной записи — отказ); подробности — [контракт машины](MACHINE_CONTRACT.md). Edge/level, remote IRR, EOI и допустимая polarity наследуются из реализованных ограниченных правил IOAPIC в [контракте машины](MACHINE_CONTRACT.md#fixed-edge-ioapic-route-s4-26a) и его следующих S4 slices; S6-03 не расширяет electrical/SCI профили.

Каждый vCPU имеет отдельный LAPIC state. Владелец CPU execution context передаёт свой vCPU index в его memory adapter; доступ по LAPIC MMIO window адресуется LAPIC именно этого vCPU, без глобальной переменной «текущий APIC». Состояние на S6-11: плата создаёт N LAPIC по конфигурации (`vcpu_count`, по умолчанию 1), окно адресуется LAPIC выполняющего vCPU через явный индекс (см. [контракт машины](MACHINE_CONTRACT.md#lapic-на-каждый-vcpu-s6-11)); индекс пока не проводится от `Vcpu` на рабочих путях MMIO, Fixed IPI реализован (S6-12a, см. [контракт машины](MACHINE_CONTRACT.md#доставка-ipi-s6-12a)); INIT и SIPI реализованы как ожидающие события LAPIC адресата (S6-13, см. [контракт машины](MACHINE_CONTRACT.md#init-sipi-и-ожидание-sipi-s6-13)); применяет их сам адресат на своей границе только для AP, и до S6-15 это делают лишь тесты или ручной вызов `apply_pending_startup`; INIT, адресованный BSP, устройство отказывает (отложено до S6-15/S6-16); INIT не снимает Remote IRR маршрута IOAPIC к этому LAPIC (по SDM его снимает только EOI; решение владельца 2026-11-16); NMI (S6-12b, §7) ставится как одна защёлка в LAPIC адресата и доставляется адресатом через вектор 2 на его границе (`deliver_pending_nmi`, до S6-15 — тестами или ручным вызовом; IST в шлюзе NMI не поддержан), исполнение AP не запускается (S6-15/S6-16).

**Открытое расхождение: NMI в `Shutdown` (S6-12b).** §3 (строка `Shutdown` с `hardware_reset_only=false`) требует, чтобы NMI возобновлял обработку через handler вектора 2. Реализация S6-12b этого не делает: `deliver_pending_nmi` для `Shutdown` возвращает `Held` (`od_isa::deliver_nmi_cpl0_set` — `ActivityOutsideProfile`), NMI остаётся ожидающим. Поле `hardware_reset_only` в `CpuActivity` не моделируется. Владелец — S6-15 (планировщик) либо отдельный срез; до тех пор не реализовано.

## 7. NMI

NMI IPI принимает physical target и all-but-self broadcast в доказанных Linux путях. Поле vector в ICR не задаёт гостевой handler: CPU получает NMI event с архитектурным вектором 2 (Vol. 3A 6.7.1, 10.8.1; по памяти, источник недоступен). NMI не зависит от IF. После начала NMI delivery устанавливается NMI blocking; последующие NMI не вкладываются до начала исполнения `IRET` (Vol. 3A 6.7.1; по памяти, источник недоступен). При нескольких запросах до первой доставки они coalesce до одного события; пока блокировка активна, LAPIC сохраняет не более одного следующего ожидающего NMI, дополнительные запросы coalesce/drop. После `IRET` ожидающий NMI может быть доставлен на следующей границе инструкции. Для reference CPUID topology limits NMI-source reporting/FRED не включены.

Расхождение реализации S6-12b с SDM (открыто, по памяти, не сверено): блокировка NMI снимается только успешным `IRETQ`; при fault самого `IRETQ` (`#GP`, `#PF`) она остаётся до следующего успешного `IRETQ`, тогда как SDM снимает её и при `IRET` с fault. Подробности — [CPU_CONTRACT.md](CPU_CONTRACT.md) S6-12b и [MACHINE_CONTRACT.md](MACHINE_CONTRACT.md#nmi-s6-12b). Решения владельца по NMI: INIT-reset и `EN = 0` стирают защёлку NMI; NMI, принятый в ICR, до S6-15 не доставляется рабочим циклом (явный вызов `deliver_pending_nmi` на границе, тесты).

NMI обязателен в контракте: S6-02 source inventory находит targeted NMI и NMI all-but-self для reboot timeout fallback, panic/kdump, restart stop-other-CPU и KGDB roundup; PMU hard-lockup NMI остаётся условным и не считается основанием включать PMU. AP startup сам по себе NMI не отправляет.

## 8. Время и два режима исполнения

Раздел обновлён 2026-11-16 по принятым S4-22 и S4-23 (закрыты 2026-11-15 с переносом остатков, ISSUE-501) и решению владельца D7 ([STAGE_6.md](../plans/STAGE_6.md), раздел 11; [STAGE_6_REPORT](../reports/STAGE_6_REPORT.md), раздел 3). Источники кода: `crates/od-machine/src/clock_owner.rs` (`ClockOwner`), `idle_arbiter.rs`, `virtual_clock.rs` (`VirtualClockAdvancer`). Решения S4 здесь не пересматриваются. Раздел принят архитектурным ревью S6-15 шаг 0 (2026-11-16) с правками.

**Принятое для времени (D7).**

- При позднем отказе legacy-кванта AP планировщик учитывает уже завершённые инструкции один раз и затем возвращает исходную ошибку. Шаг с отказом стоит 0 нс. Если первый вызов long mode после передачи управления завершается ошибкой, сохраняется известный учёт трамплина, включая завершённый переход. [Проверки](../reports/STAGE_6_REPORT.md#s6-16c--учёт-прерванного-legacy-кванта).
- Время гостя виртуальное и только виртуальное: `VirtualClock` (`now_ns`, TSC как `now_ns × tsc_hz / 10^9`, одна шкала для всех vCPU, без смещения на vCPU). Host monotonic гостю не виден и ничем не продвигает часы; host wait нет.
- Единственный владелец часов — `ClockOwner`: он один раз забирает `VirtualClockAdvancer` (повторный claim — `ClockAlreadyOwned`) и поэтому один может двигать время. Планировщик режима чередования (S6-15) работает через этого владельца и не вводит второго. В режиме чередования методы `ClockOwner`, двигающие время (`account_retired`, `account_device_ns`, `idle_step`), вызывает только планировщик; хост (`SmpHost::run`, цикл платы) часы не двигает и не вызывает `charge_retired`/`charge_ns`/`idle_to`; `HLT` возвращается планировщику как конец хода, пропуск простоя делает только `idle_step`. Цикл `run_linux_boot_cpl0_set` с `enable_clock_owner` (S4-23j) сам вызывает владельца и поэтому хостом планировщика без выделения квант-функции быть не может. Путь Linux по умолчанию (`advance_standalone`, без `ClockOwner`, ISSUE-501) режимом чередования не является.
- Время движется ровно тремя способами: (1) инструкция, завершённая любым vCPU, стоит `NS_PER_RETIRED` = 1 нс (шаги × 1 нс, время общее, а не на vCPU); частичный прогресс `REP` ничего не стоит, `REP` стоит 1 нс при завершении; (2) фиксированные тики устройств (PM timer, PIT, RDTSC платы) начисляются обычными наносекундами (`account_device_ns`); (3) пропуск простоя: когда ни один vCPU не исполняется, часы одним прыжком идут к ближайшему сроку. Ничего другого время не стоит: применение INIT/SIPI, доставка NMI, исключения и внешнего прерывания через IDT, пробуждение из `HLT` и частичный прогресс `REP` идут за 0 нс и retired-инструкциями не являются (`HLT` сам стоит 1 нс при retirement). Требование к хосту: тик устройства начисляется до следующего шага — хост завершает вызов `run` сразу после шага, породившего тик (как предикат остановки цикла платы по `timer_tick_pending`/`port_tick_pending`/флагу RDTSC); планировщик начисляет `device_ns` вызова после его retired. Иначе момент `dispatch_timer` зависит от разрезания вызовов, то есть от кванта.
- Сроки LAPIC-таймеров всех vCPU (у каждого своя `EventQueue`) обслуживаются после каждого движения часов: один `dispatch_timer` на vCPU по порядку индексов, не больше одного запроса за вызов (периодический таймер сворачивает пропущенные периоды в один запрос и сохраняет фазу, one-shot срабатывает на границе шага).
- Шаг vCPU не должен переходить через ближайший срок: бюджет шага — `min(квант, (срок − now) / NS_PER_RETIRED)`, не меньше 1 (`ClockOwner::step_budget`). Иначе число тиков и момент прерывания зависят от размера кванта. Срок платы (источник IRQ платы, `irq_source.next_deadline_ns`) входит в ближайший срок наравне со сроками LAPIC. Состояние S6-16d: метод `SmpHost::board_deadline()` добавлен (по умолчанию `None`); планировщик передаёт срок в `step_budget` и `idle_step`, `BoardSmpHost` отдаёт срок источника платы, но НЕ снимает его (доставка источника платы BSP и пробуждение по нему не реализованы, открытый пункт S6-17; см. [MACHINE_CONTRACT.md](MACHINE_CONTRACT.md#s6-16d--квант-платы-для-любого-vcpu)) (снято в S6-21 шаг 1: см. [MACHINE_CONTRACT.md](MACHINE_CONTRACT.md#s6-21-шаг-1--источник-платы-и-срок-платы-в-планировщике); ограничение IOAPIC→AP — открыто). Подключение к циклу Linux (S6-17) без снятия срока запрещено: иначе IRQ0 зависит от кванта, а все `Halted`, ждущие IRQ платы, дают ложный `AllIdle`. Запись гостя в регистры таймера своего LAPIC (initial count, LVT timer) внутри вызова создаёт срок, не учтённый бюджетом вызова (наследие S4-23h): хост обязан завершать вызов после такой записи; реализовано в S6-16d (`CpuApic::timer_writes`, вызов `run_vcpu_set_quantum` кончается после принятой записи).

**Арбитр простоя для N vCPU** (`idle_arbiter::decide`, вызывается через `ClockOwner::idle_step`, одно решение и не больше одного прыжка за вызов, без цикла и ожидания). Порядок проверок: STOP; есть `Running` vCPU; есть `Halted` vCPU с IF=1 и принимаемым вектором (разбудить сейчас); иначе ближайший полезный срок среди таймеров halted vCPU с IF=1 (вектор не ждёт в IRR за обслуживаемым вектором или TPR) и сроков платы (в S6-15 список пуст, см. выше); при отсутствии срока — `AllIdle`, часы стоят. Равные сроки решаются по индексу. Срок не позже `now` — `NoProgress`. `WaitForSipi` и `Shutdown` никогда не выбираются; пробуждение NMI/INIT/SIPI арбитр не решает: адресат применяет их на своей границе до решения арбитра.

**Что определяет S6-15** (не S4): длину кванта по умолчанию и пределы, seed и его генератор, явное расписание, порядок вызовов на границе, перебор vCPU по кругу — раздел «Планировщик режима чередования (S6-15)» в [MACHINE_CONTRACT.md](MACHINE_CONTRACT.md). Значения кванта — `Fixed(1024)` по умолчанию и пределы seed 1..=256 — временные, не измерены и нормативными не являются: контракт гарантирует только, что заданная политика (вид, значение, seed, пределы или расписание) вместе с остальными входами даёт один и тот же прогон. Политика — вход прогона и записывается в его результат; значения по умолчанию пересматриваются по замеру темпа (S6-21/SMP.md, S6-38) без изменения этого раздела. Нормативны алгоритм SplitMix64, одно продвижение генератора на ход и L (строка «Чередование»).

**Граница планировщика и порядок (S6-15).** Круг: (1) STOP — конец без исполнения; (2) общий бюджет исчерпан — конец; (3) граница каждого vCPU по возрастанию индекса: сначала ожидающие INIT/SIPI его LAPIC (`apply_pending_startup`), затем его NMI (`deliver_pending_nmi`); INIT, применённый в той же границе, стирает защёлку NMI; (4) пробуждение каждого `Halted` с IF = 1 и вектором `eligible()` (тот же предикат, что `WakeNow` арбитра); (5) если есть `Running` — ход следующего `Running` по кругу, иначе один `idle_step` (не больше одного прыжка) и новый круг. Вне хода все vCPU стоят на своей границе, поэтому (3) — применение «на границе адресата» в смысле §3. Событие, поставленное во время хода (запись ICR: INIT/SIPI/NMI для любого vCPU, в том числе для себя), применяется в (3) после хода; хост не завершает вызов из-за такого события (иначе прогон зависит от хоста). Задержка — до одного хода, грубее аппаратной, особенно для NMI самому себе. Fixed-вектор исполняющему vCPU доставляет через IDT хост внутри хода; планировщик Fixed-векторы не доставляет. Ошибка границы любого vCPU (например, NMI vCPU в legacy-режиме: условия подключения, п. 6(д) раздела S6-16 плана; ошибка и в S6-16c) завершает прогон `SmpError::Host`.

**Бюджет и STOP.** Общий бюджет — в retired-инструкциях всех vCPU, счётчики — на каждый vCPU. Частичный `REP` бюджет не расходует, поэтому бюджет не ограничивает число шагов: vCPU в очень длинном `REP` при остальных `Halted` не даёт ни retired, ни времени, и прогон кончается только по STOP; предела шагов в S6-15 нет. STOP читается на каждой границе и предикатом внутри вызова, в том числе между итерациями `REP`; на STOP часы не двигаются (§9).

| Режим | Принято |
|---|---|
| Чередование | Один host-thread выполняет все vCPU, пишущие в RAM. **Шаг** планировщика — либо одна гостевая инструкция после полного commit, либо один возврат интерпретатора из незавершённого `REP` (частичный прогресс, `RunExit::RepIterationBudgetExhausted`). Интерпретатор возвращает управление из `REP` после L успешных итераций, считая от начала этого вызова интерпретатора; L = `REP_ITERATION_WORK_LIMIT` = 1024 — нормативная константа версии 1 этого контракта: её изменение меняет разбиение на шаги, а с ним прогоны по seed и записанные расписания, и оформляется как новая версия контракта. Отдельная итерация `REP` шагом и границей переключения не является: `REP` с начальным count ≤ L (включая count = 0) — один шаг, неделимый для других vCPU. На границе частичного прогресса RIP стоит на `REP`, память и `RCX/RSI/RDI` (для `CMPS/SCAS` — и флаги сравнения) отражают совершённые итерации. Итерация, на которой `REP` завершается (count стал 0 или сработало repeat condition, в том числе ровно на L-й итерации), входит в тот же шаг: RIP продвигается в нём, пустого шага нет. Частичный возврат — шаг кванта, но не retired-инструкция: он не стоит времени и не расходует общий бюджет; `REP` стоит 1 нс и одну единицу бюджета при завершении. По STOP интерпретатор возвращает управление и после любой итерации (`RunExit::StopRequested`): это точка остановки §9, она завершает ход; после возобновления начинаются новый ход и новый отсчёт L. Квант — целое число шагов одного vCPU; внутри инструкции и внутри среза `REP` переключения нет. Последовательный порядок шагов — SC-наблюдаемый порядок режима. Одинаковые входы («Воспроизводимость») дают одинаковое исполнение, включая счётчики инструкций на vCPU, байты UART и конечное состояние. | Закрыто ниже (S4-22/S4-23, S6-15). |
| Параллельный | Предназначен для x86-TSO и не обещает детерминизма расписания; seed и quantum lengths не обещают одинаковый interleaving host threads. | Реализовано S6-34 (ожидает ревью, [MACHINE_CONTRACT.md](MACHINE_CONTRACT.md#s6-34--потоки-vcpu-kick-и-остановка)): один host-поток на vCPU, единый `ClockOwner` остаётся один и стоит под замком (поток начисляет retired и тики устройств после своего вызова; скачок простоя делает поток, уходящий в сон последним, когда никто не занят); на остановке часы стоят; порядок начисления между потоками не детерминирован. Seed и кванты режима чередования параллельному режиму не нужны. |

**Шаг `REP` (принято ревью S6-15 шаг 0, 2026-11-16).** Граница частичного прогресса — точка возврата интерпретатора из `REP` после L = 1024 итераций (строка «Чередование»); L входит в контракт, а не только в реализацию od-isa. Последствия: (1) чередование внутри длинного `REP` грубее аппаратного — до L итераций между границами и до квант × L за ход; (2) `REP` с count ≤ L неделим для других vCPU — отличие от x86, записывается в выводе S6-19 так же, как неделимость `INC [x]`; (3) эталон S6-19 «SC при неделимости шага» обязан резать `REP` с count > L в тех же точках (после L, 2L, … итераций от начала инструкции), иначе такие тесты не входят в полный перебор; (4) пока vCPU исполняет срезы `REP`, его retirement время не двигает. Вариант L = 1 отвергнут: каждая итерация стала бы полным вызовом интерпретатора с повторным декодированием и всей работой цикла платы на вызов; нужен он только перебору S6-19, которому достаточно п. (3). Если S6-19 понадобится граница на каждой итерации, L становится параметром прогона, записываемым в результат, а не меняется глобально.

**Воспроизводимость.** Для чередования условие D7 выполнено: время считается по исполненным инструкциям, host monotonic не виден, поэтому одинаковые входы и seed дают те же счётчики инструкций на каждом vCPU, те же байты UART и то же конечное состояние. Условие «нет внешнего I/O» остаётся: внешний ввод, пришедший не по границе виртуального времени, воспроизводимость нарушает. Входы прогона: образ и конфигурация платы (N), политика кванта, L, бюджет и шаги, на которых пришёл STOP. `executed_schedule()` воспроизводит прогон как `Schedule` только если за ход не ставились события границы ни для какого vCPU (кадр NMI пишется в память и виден другим) — ограничение S6-19.

**Не определено S4 и остаётся за другими срезами:** Linux-видимые частота и поля времени (S4-38), LAPIC как источник пробуждения под Linux-профилем (S4-38), доставка вектора по IDT при пробуждении (делает цикл исполнения, не арбитр), параллельный режим (S6-24+). Закрыто в S6-16d: срок платы в `SmpHost` (`board_deadline`), конец вызова на тике и на записи в таймер LAPIC, `skip_first_boundary` на vCPU. Остаётся открытым (S6-17): снятие срока платы и доставка источника платы (PIC/IOAPIC/PIT) на границе BSP в `BoardSmpHost`; предел шагов для длинного `REP` (S6-21). (снято в S6-21 шаг 1: см. [MACHINE_CONTRACT.md](MACHINE_CONTRACT.md#s6-21-шаг-1--источник-платы-и-срок-платы-в-планировщике); ограничение IOAPIC→AP — открыто)

## 9. Остановка, pause и границы владения

По D1 этап 6 владеет остановкой vCPU и сохранением их состояния; S9-28 — полным barrier с I/O, epoch и публикацией. Stop request доставляется каждому vCPU как host control event. Все vCPU участвуют в stop, включая `Halted` и `WaitForSipi`; для спящих vCPU acknowledgement не требует гостевой инструкции. Каждый активный vCPU до общего конечного deadline достигает безопасной границы: завершённая инструкция либо точка частичного прогресса `REP` после любой итерации (интерпретатор проверяет STOP между итерациями); точка остановки шире границы переключения §8. На safe point всё изменяемое guest CPU состояние находится в структуре vCPU, без скрытых live host-register значений. После подтверждения всех CPU scheduler прекращает выбор vCPU и сохраняет CPU state, LAPIC registers/IRR/ISR/TMR, pending INIT/SIPI/NMI, таймеры и очередь событий с прежними сроками. Позже прибывший interrupt/IPI остаётся pending и не снимает stop acknowledgement; выход из `HLT`/`WaitForSipi` сначала проверяет stop request, и guest execution возобновляется только по явной команде resume. Виртуальное время на остановке не продвигается. Виртуальное время стоит на всём интервале stop. Timeout возвращает ошибку с перечнем vCPU, не достигших safe point; stop request снимается, припаркованные vCPU возвращаются к прежнему runnable/sleep state, pending events и deadlines сохраняются без потери/дублирования, частичный snapshot не публикуется. Полный storage/device/I/O snapshot barrier здесь не обещан и остаётся S9-28.

**S6-24 (реализовано в режиме чередования, ожидает ревью).** Остановка собрана как `SmpScheduler::stop_all`: подтверждение КАЖДОГО vCPU (`Boundary`, `RepRestart`, `Asleep`) за ограниченное число раундов, иначе `Timeout` со списком не пришедших, STOP снят, снимка нет; успех держит STOP до явного `resume`, часы не двигаются. Снимок — значение в памяти процесса (`VmSnapshot`: все vCPU, все LAPIC с таймерами и очередями событий, маршрут IOAPIC с Remote IRR, состояние планировщика); RAM и устройства в него не входят (`S9-24`/`S9-25`); восстановление — только в ту же остановленную машину, с часами на прежнем месте. Ход, прерванный STOP или концом бюджета, продолжается следующим `run` без новой границы после явного `resume`. Сброс платы (`reset_cpu_complex`) возвращает каждый AP в `WaitForSipi`, очищает ожидающие события во всех LAPIC и Remote IRR; решение «INIT не снимает Remote IRR» сохранено. Параллельный режим (ожидание подтверждения от потоков) — S6-34. Подробности и решения — [MACHINE_CONTRACT.md](MACHINE_CONTRACT.md#s6-24--остановка-всех-vcpu-снимок-и-сброс).

**Потоки vCPU, kick и остановка (S6-34, реализовано, ожидает ревью).** Параллельный режим — один поток на vCPU ([MACHINE_CONTRACT.md](MACHINE_CONTRACT.md#s6-34--потоки-vcpu-kick-и-остановка)). Остановка всех — запрос плюс подтверждение каждого vCPU на безопасной границе этого раздела: завершённая инструкция или точка рестарта `REP` (интерпретатор опрашивает запрос между инструкциями и между итерациями), а спящие (`Halted`, `WaitForSipi`, `Shutdown`) подтверждают сразу и остаются спать; тайм-аут называет не пришедших, запрос снимается, ничего не меняется. Подтверждение не ждёт замка, удерживаемого остановленным или спящим vCPU: поток не держит замок устройства, APIC, часов и слот vCPU через `HLT`, ожидание SIPI, сон и барьер. Выход из `HLT` и из ожидания SIPI сначала проходит барьер остановки: IPI/прерывание остановленному vCPU остаётся ожидающим в его LAPIC и не запускает его до явного `resume`; спящий пробуждается флагом kick и `unpark` из приёмника APIC без потерянного пробуждения. Подтверждение — `Release`/`SeqCst`, чтение контроллером — `Acquire`/`SeqCst`: контроллер видит все записи остановленных vCPU в их состоянии и в RAM. Split `LOCK`, не помещающийся в 16 байт, в параллельном режиме останавливает остальных vCPU тем же механизмом (шлюз с победителем и ждущим проигравшим) на время одной операции.

**Блокировки устройств (S6-33).** Поток vCPU берёт блокировки в порядке [«Порядок блокировок»](MACHINE_CONTRACT.md#порядок-блокировок-s6-33) (шина или источник IRQ, затем устройство, затем часы; RAM вне блокировок) и не держит их ни в `HLT`, ни в ожидании SIPI, ни на safe point остановки; блокировка APIC одна на все LAPIC, запись ICR доставляется под ней целиком, так что подтверждение остановки не ждёт замка, удерживаемого остановленным или спящим vCPU (замки не держатся через HLT, ожидание SIPI и safe point); ожидание занятой блокировки ограничено одним обращением другого потока.

## 10. Не входит в первую версию и оставшиеся границы

- x2APIC и MADT type 9; logical/cluster routing; Lowest Priority; SMI; hot-add/hot-remove; topology с несколькими threads per core; больше 4 vCPU.
- Generic `OpenDesktop` Linux package/core topology — S6-18; Windows CPU-06 — трасса Stage 8.
- Параллельный режим (S6-34): потоки vCPU, kick, остановка всех, split `LOCK` — реализованы и ждут ревью; состояние vCPU и LAPIC на остановленной параллельной машине (S6-35, шаги 1–3: значение в памяти, только в ту же машину; формат и сквозная проверка — S9-24, S9-25) — реализовано; Linux на нескольких потоках (S6-37) и litmus параллельного режима (S6-36) — не сделаны.
- Runtime AP execution, INIT/SIPI на границе (Fixed IPI реализован в S6-12a, постановка и доставка NMI явным вызовом — в S6-12b, постановка INIT/SIPI — в S6-13; доставка NMI на границе — планировщик S6-15; исполнение AP в legacy-режиме от SIPI до long mode реализовано на плате в S6-16c ([контракт машины](MACHINE_CONTRACT.md#s6-16c--исполнитель-ap-в-legacy-режиме-на-плате)); probe-образ — S6-16e, обмен IPI и отрицательные случаи — S6-16f), multi-LAPIC wiring по умолчанию (плата с `vcpu_count > 1` собирается, но по умолчанию 1), двух-/четырёх-vCPU Linux boot и выбранный delay provider ещё не выполнены.
- Квант платы для любого vCPU (`run_vcpu_set_quantum`, срок платы в `SmpHost`, конец вызова на записи таймера LAPIC, `skip_first_boundary`) реализован в S6-16d ([контракт машины](MACHINE_CONTRACT.md#s6-16d--квант-платы-для-любого-vcpu)); probe-образ — S6-16e; снятие срока платы и доставка источника платы BSP в `BoardSmpHost` — S6-17. (снято в S6-21 шаг 1: см. [MACHINE_CONTRACT.md](MACHINE_CONTRACT.md#s6-21-шаг-1--источник-платы-и-срок-платы-в-планировщике); ограничение IOAPIC→AP — открыто)
- TSC/HLT/event timing: определено в разделе 8 (S4-22/S4-23, D7); квант, seed и расписание — S6-15 (реализовано, значения временные, §8); Linux-видимые поля времени — S4-38.
- Реализация CPU exception/interrupt delivery остаётся в границах задач этапов 4/6; таблица описывает целевой контракт, не наличие реализации.

## 11. Проверки будущей реализации

S6-10/S6-11/S6-15/S6-17/S6-18 должны проверять как минимум: AP не исполняется до SIPI; INIT/SIPI меняет только target на его границе; INIT/AP reset registers и INIT BSP behavior; повторный SIPI ignored; все допустимые ICR кодировки таблицы; каждая запрещённая комбинация возвращает ожидаемый device error без изменения CPU/LAPIC; Fixed/NMI physical IDs и all-but-self destinations; NMI vector 2, coalescing и IRET unblock; IOAPIC/MSI physical Fixed routes; CPUID/MADT/handoff `cpu_count` consistency; безопасную остановку и сохранение LAPIC pending state. Проверки времени и воспроизводимости по seed — по разделу 8. Полный контракт принимает независимое архитектурное ревью до реализации.
