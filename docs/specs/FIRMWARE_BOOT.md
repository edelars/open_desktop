# Контракт входа в прошивку и handoff block (firmware board v1)

**Статус:** контракт подготовлен задачей S7-02 [плана этапа 7](../plans/STAGE_7.md#s7-02-описать-контракт-входа-в-прошивку-и-handoff-block) и ожидает архитектурного ревью. Это документ, а не реализация: ROM backing, загрузчика образа, handoff block и профиля платы в `od-machine` нет (их создаёт S7-03), кода прошивки нет (S7-01, S7-04). Ни одна гарантия ниже не считается выполненной до соответствующей задачи, её тестов и ревью.

Связанные документы: [виртуальная плата](VIRTUAL_BOARD.md), [контракт машины](MACHINE_CONTRACT.md) (разделы «Адреса и карта», «Stage 4 flat probe image and direct handoff (S4-32a)», «Huge-page и mode admission boundary», «Caller-driven virtual clock and RDTSC boundary», «Bounded COM1 polling UART»), [дисплейное устройство](DISPLAY_DEVICE.md) §3 и §16.3, [CPU contract](CPU_CONTRACT.md), [правила каталога прошивки](../../firmware/AGENTS.md), [архитектура](../ARCHITECTURE.md).

Нормативные источники: UEFI Specification 2.11 (декабрь 2024), §2.3.4 «x64 Platforms»; SMBIOS Reference Specification 3.9 (System UUID, Type 1); редакции — по разделу «Нормативные источники и редакции» `VIRTUAL_BOARD.md`. Страница `https://uefi.org/specs/UEFI/2.11/02_Overview.html` при подготовке документа (2026-11-07) вернула HTTP 403; перечень требований §2.3.4 в разделе 7 взят из плана этапа 7 и дополнен значениями FCW/MXCSR, которые S7-05 обязана сверить с текстом §2.3.4 до записи `UEFI_PROFILE.md` (источник пока не сверен).

## 1. Граница контракта

- Это **собственный документированный boot entry** платы (`firmware/AGENTS.md`: «явно фиксировать boot entry, CPU state»). Машина передаёт управление прошивке сразу в Long64, как flat probe S4-32a.
- Плата передаёт управление прошивке сразу в Long64; этот контракт не реализует reset vector `0xFFFF_FFF0`, ROM reset path или BIOS и не требует real/protected-mode входа для firmware handoff. Это не исключает отдельный AP startup path: выбранный для S6 Linux target запускает AP через INIT/SIPI и ограниченный real→protected→long-mode trampoline из [SMP contract](SMP_CONTRACT.md) и [S6-14a CPU profile](CPU_CONTRACT.md#s6-14a--bounded-ap-startup-trampoline-profile). Тот профиль относится только к AP startup и не создаёт общего обещания поддержки real/protected mode или исполнения этих режимов прошивкой.
- Карту платы назначает `od-machine`; прошивка её не меняет и не содержит других констант адресов, кроме перечисленных в разделе 2 как архитектурные константы платы.

Правила RAM:

- Общий объём RAM `R` кратен 2 MiB, `128 MiB ≤ R ≤ 0xF_F400_0000` (63,8125 GiB). Нижняя граница нужна для boot reservations, собственных таблиц и heap прошивки; верхняя следует из ширины 36: `high_end = 0x1_0000_0000 + (R − 0xF400_0000) ≤ 2^36`.
- `low_end = min(R, 0xF400_0000)`, `high = R − low_end`. RAM ниже 4 GiB никогда не заходит выше `0xF400_0000` (`DISPLAY_DEVICE.md` §16.3).
- Нижняя RAM — **один** регион `Ram` карты, а не набор смежных регионов: `PhysicalMemory` отвергает доступ, пересекающий границу регионов (`AccessCrossesRegion`), и не даёт backing регионам `Reserved`. Поэтому boot reservations ниже — поддиапазоны этого `Ram`, описанные типами в handoff block (раздел 6.2), а не отдельные `Reserved`-регионы `MachineMemoryMap`.
- Диапазон `[0xFC00_3000, 0xFEC0_0000)` и окна HPET, ACPI fixed hardware этим документом не назначаются: их выбирает S7-14 вне перечисленных выше диапазонов (`[0xFC00_1000, 0xFC00_3000)` занят окном NVMe, S7-16). Окно ECAM `[0xFC10_0000, 0xFC20_0000)` выбрано в S4-30a (MACHINE_CONTRACT.md); запись кода 7 — `PRESENT = 0`, пока плата не собрана с opt-in флагом `pci_ecam` (S4-30c), и `PRESENT = 1` с флагом.

## 3. Образ прошивки, ROM и решение об исполнении

### 3.1. Решение 1: исполнение из shadow-копии в RAM (вариант (а))

**Выбрано:** машина при старте копирует образ из ROM в регион `FIRMWARE_SHADOW` и передаёт управление туда. Исполнение из ROM не вводится.

**Причина (по коду):** в `physical_memory.rs` backing создаётся только для `Ram` и `Framebuffer`; `Rom` сейчас не читается вовсе (`UnreadableRegion`) и не пишется (`ReadOnlyRegion`). Page generations создаются только для `Ram`, `code_page_generation` и `MachineBus::tracked_code_snapshot` отвергают любой не-RAM регион, а instruction fetch в paged/identity адаптерах — RAM-only (`MACHINE_CONTRACT.md`, S4-27b: «instruction fetch remains RAM-only»). Исполнение из ROM потребовало бы нового класса кода без поколений в `physical_memory.rs`, `page_walk.rs` и инвалидации JIT (`od-jit`) — изменения принятых контрактов этапа 4 ради одного потребителя. Shadow требует только read backing для `Rom` и одной записи загрузчиком через существующий `write_bytes` (поколения страниц shadow повышаются обычным путём). RT-код всё равно должен жить в RAM-регионах `EfiRuntimeServicesCode` (решение 4).

**Исполнитель:** S7-03 (ROM read backing, копирование, тесты), S7-04 (разметка shadow в UEFI memory map), S7-26 (повторное копирование при сбросе).

Семантика ROM (реализует S7-03):

- ROM — источник истины образа и read-only. Чтение данных гостем разрешено (байты образа). **Уточнение S7-03:** Физическое чтение ROM на шине машины — разрешено (read backing). Гостевое чтение ROM через трансляцию страниц в текущем paged-пути — отклоняется (`UnreadableRegion(Rom)`), потому что `page_walk` допускает только Ram и Framebuffer; образ исполняется из shadow, поэтому v1 это не требует. Решение о гостевом чтении ROM — открытый вопрос для S7-04.
- Запись гостя в ROM — backend-ошибка `MemoryAccessError::ReadOnlyRegion(Rom)` (существующая классификация), запись не игнорируется. Если аудит S7-30 покажет, что Windows пишет в это окно, контракт меняется новой версией документа.
- Instruction fetch из ROM по контракту не происходит: образ исполняется только из shadow. Гостевой fetch по VA, отображённому на ROM, **нормативно** завершается архитектурным `#PF` на этапе page walk, до обращения к физическому региону: листья ROM помечены `P|NX` (раздел 4; то же обязаны делать собственные таблицы прошивки S7-04, раздел 7), `EFER.NXE = 1`, поэтому `page_walk.rs` отказывает fetch с `PageFaultReason::Protection { execute_denied: true, .. }`, error code `0x11` (P = 1, I/D = 1; W = U/S = RSVD = 0 при CPL0), линейный адрес — адрес fetch. Paged-квант возвращает этот fault как архитектурный результат (`MACHINE_CONTRACT.md`, S4-21b); если у прошивки уже есть IDT, он доставляется ей и ведёт к останову `code=0x10` с `detail` = вектор `14` (раздел 12). Backend-ошибка `UnreadableRegion(Rom)` fetch-пути (`page_walk.rs`: fetch допущен только для `Ram`) достижима лишь при листе ROM без NX, то есть при нарушении этого контракта таблицами машины или прошивки; S7-03 проверяет тестом, что fetch из ROM по временным таблицам даёт именно `#PF` с error code `0x11`, а не backend-ошибку.
- Page generations и code tracking для ROM не создаются.
- При каждом старте и сбросе машины shadow перезаписывается байтами ROM; изменения shadow гостем сброс не переживают.

### 3.2. Заголовок образа v1

Образ — плоский файл ровно `0x0040_0000` байт; он компонуется по адресу `0x0020_0000` (link base). Первые `0x40` байт — заголовок, который читает `od-machine`; остальную раскладку (секции, встроенный firmware volume) определяет S7-01 в `firmware/uefi/README.md`. Все поля little-endian.

| Смещение | Ширина | Поле | Значение v1 |
|---|---|---|---|
| `0x00` | 8 | `magic` | ASCII `ODFWIMG1` (`0x3147_4D49_5746_444F` как u64 LE) |
| `0x08` | 4 | `format_version` | `1` |
| `0x0C` | 4 | `header_size` | `0x40` |
| `0x10` | 8 | `image_size` | `0x0040_0000` |
| `0x18` | 8 | `link_base` | `0x0020_0000` |
| `0x20` | 8 | `entry_offset` | `header_size ≤ entry_offset < image_size`; `RIP = link_base + entry_offset` |
| `0x28` | 2 | `handoff_major` | `1` — major версии handoff block, которую понимает образ |
| `0x2A` | 2 | `handoff_minor_max` | наибольший понимаемый minor (для v1.0 — `0`) |
| `0x2C` | 4 | `flags` | `0` |
| `0x30` | 4 | `image_crc32` | CRC-32 (раздел 6.6) всего образа с этим полем, равным нулю |
| `0x34` | 12 | `reserved` | нули |

Машина проверяет все поля до создания vCPU; любое несовпадение (magic, версия, размер, link base, entry вне диапазона, ненулевые `flags`/`reserved`, CRC, `handoff_major ≠ 1`, `handoff_minor_max` меньше minor блока, который машина собирается выдать) — host-side ошибка загрузки, гость не запускается. Машина не парсит PE и не исполняет логику UEFI.

## 4. Временные таблицы страниц машины

- Формат: Long64, 4 уровня, **только страницы 4 KiB** (`MACHINE_CONTRACT.md` «Huge-page и mode admission boundary»: PS в PD → `UnsupportedPageSize`; PS в PDPT → гостевой RSVD `#PF`, S4-10c).
- Покрытие: identity (`VA = GPA`) для каждого региона карты — `Ram`, `Rom`, `Mmio`, `Framebuffer`. Дыры и неотображаемые резервы не отображаются.
- Флаги листьев: RAM — `P|RW`; ROM — `P|NX`; `Mmio`/`Framebuffer` — `P|RW|NX`. Промежуточные уровни — `P|RW`. Биты A/D изначально нули, `U/S = 0`. NX на листьях ROM нормативен: из-за него гостевой fetch из ROM — `#PF` (раздел 3.1), а не backend-ошибка.
- Расположение: PML4 — первая страница `BOOT_PAGE_TABLES` (`CR3 = 0x0060_0000`); порядок остальных страниц внутри региона — дело S7-03. Прошивка эти таблицы не разбирает и после переключения на собственные (S7-04) возвращает регион в `EfiConventionalMemory`.
- Объём: `N = (#различных 2 MiB-блоков, задетых отображаемыми регионами) + (#различных 1 GiB-блоков) + (#различных 512 GiB-блоков) + 1`. Машина вычисляет `N` по фактической карте и записывает длину региона `BOOT_PAGE_TABLES` в handoff block.

Вычисленные значения (окна раздела 2 при двух экранах и присутствующих NVRAM и TPM CRB; проверено `python3`):

| RAM | PT | PD | PDPT | PML4 | `N` | Объём |
|---|---|---|---|---|---|---|
| 128 MiB (минимум) | 106 | 2 | 1 | 1 | 110 | 440 KiB |
| 4 GiB (целевой минимум Windows) | 2090 | 5 | 1 | 1 | 2097 | 8 589 312 B ≈ 8,19 MiB |
| 63,8125 GiB (максимум при ширине 36) | 32714 | 64 | 1 | 1 | 32780 | 134 266 880 B = `0x0800_C000` ≈ 128,05 MiB |

Резервирование: регион `BOOT_PAGE_TABLES` начинается в `0x0060_0000` и для максимальной RAM заканчивается в `0x0860_C000` — внутри нижней RAM при любом `R`, потому что `N` растёт вместе с `R`. Собственные таблицы прошивки (S7-04) покрывают тот же набор регионов и требуют того же `N` страниц из `EfiConventionalMemory`; пиковая потребность до освобождения временных таблиц — `2·N` страниц (≈ 16,4 MiB при 4 GiB, ≈ 256,1 MiB при максимуме). Windows требует large pages (зависимость S7-32 от S4-10); на прошивку v1 это не влияет.

Без этого polling UART отклоняет запись THR. Повторная инициализация прошивкой по разделу 11 допустима и записывает те же значения |
| Исполнимые инструкции | только allowlist paged-кванта `PagedCpl0ProbeV1` ([CPU_CONTRACT.md](CPU_CONTRACT.md), S4-21b и «Расширение S7-03»): `MOV RAX,[RBX]`, `MOV [RBX],RCX`, `IN AL,DX`, `OUT DX,AL`, `HLT`, bare `CLD` (`FC`, S7-04), exact entry `MOV RAX,imm32` (`48 C7 C0 id`), `CMP RDI,RAX` (`48 39 C7`), `CMP RDI,0x00100000` (`48 81 FF 00 00 10 00`), helper `CMP RDX,0x9f` (`48 81 FA 9F 00 00 00`), exact `JNZ +0x24` (`75 24`) and Rust-entry `JNZ +0x77` (`75 77`), helper `JA/JNBE +0x0e` (`77 0E`), `MOV R8,RDI` (`49 89 F8`), `LEA RDI,[RIP+0x2b09]` (`48 8D 3D 09 2B 00 00`), `LEA RCX,[RIP+0x2b02]` (`48 8D 0D 02 2B 00 00`), Rust-entry/helper `LEA RDI,[RSP+8]` (`48 8D 7C 24 08`) and `LEA RDI,[RSP+0x50]` (`48 8D 7C 24 50`), `SUB RCX,RDI` (`48 29 F9`, Intel order; AT&T `subq %rdi,%rcx`), `XOR EAX,EAX` (`31 C0`), `REP STOSB` (`F3 AA`), `MOV RDI,R8` (`4C 89 C7`), exact `MOV ESI,0x00100000` (`BE 00 00 10 00`), exact `MOV EDX,0x00010000` (`BA 00 00 01 00`), exact `XOR ECX,ECX` (`31 C9`), exact `PUSH R14` (`41 56`), bare exact `PUSH RBX` (`53`), exact firmware/helper `CALL rel32` forms (`E8 83 01 00 00`, `E8 8D 02 00 00`, `E8 59 08 00 00`), Rust entry stack reserves `SUB RSP,0x58` (`48 83 EC 58`) and `SUB RSP,0xb8` (`48 81 EC B8 00 00 00`), plus exact Rust-helper `MOV RBX,RDI` (`48 89 FB`), `MOV RAX,RDI` (`48 89 F8`), and handoff magic load `MOV RDI,0x464f444e4148444f` (`48 BF 4F 44 48 41 4E 44 4F 46`), exact qword handoff comparison `CMP qword ptr [RSI],RDI` (`48 39 3E`), `MOV r8,imm8` (`B0+r ib`), `MOV r16,imm16` (`66 B8+r iw`). Константы (порт в `DX`, байт в `AL`) заглушка входа задаёт сама этими `MOV`; машина не выдаёт их в GPR |
| Виртуальное время | `VirtualClock` с `now_ns = 0` и частотой `tsc_hz` из handoff block |

Вход — ассемблерная заглушка образа, а не функция `efiapi`: она начинает с bare `CLD`, точного entry `MOV RAX,imm32`, `CMP RDI,RAX`, short `JNZ +0x24` и `MOV R8,RDI` (узкие расширения S7-04), сохраняет/проверяет handoff GPA и вызывает Rust entry. Допущены два entry `CALL`: из `0x200068` на `0x2001f0` с return RIP `0x20006d`, и из `0x20020e` на `0x2004a0` с return RIP `0x200213`; exact helper `CALL` из `0x2004b2` переходит на `0x200d10`. Runner исполняет Rust-entry `SUB RSP,0x58`, `CMP RDI,0x00100000`, невзятый `JNZ +0x77`, `LEA RDI,[RSP+8]`, exact `MOV ESI,0x00100000`, exact `MOV EDX,0x00010000` и `XOR ECX,ECX`. Затем runner исполняет exact `41 56` (`PUSH R14`), bare `53` (`PUSH RBX`), exact `SUB RSP,0xb8`, `MOV RBX,RDI` и `LEA RDI,[RSP+0x50]`; exact `E8 59 08 00 00` CALL переходит на helper `0x200d10`, exact `CMP RDX,0x9f` выполняется, затем taken `77 0E` (`JA/JNBE`) переходит на `0x200d2a`, где runner загружает handoff magic в RDI этой exact `MOV RDI,imm64` формой, затем сравнивает загруженный magic по `[RSI]` с RDI через exact `48 39 3E`; после 31 retired инструкций runner останавливается на `75 38` (`JNZ +0x38`, ISSUE-131, `Unsupported { opcode: 117 }`, RIP `0x200d37`). Полная проверка handoff ещё не завершена; COM1 в машине не достигнут. Остальные формы `MOV`, `CMP`, условных переходов и `CALL` вне allowlist paged-кванта. В машине также исполним мини-образ `build_firmware.py --smoke` (`MOV AL,imm8; MOV DX,imm16; OUT DX,AL; HLT`).

## 6. Handoff block v1.0

Блок лежит по `0x0010_0000`, полный размер — не больше 64 KiB. Все числа little-endian фиксированной ширины; host-pointers, пути файлов и строки без длины запрещены. Блок не дублирует то, что гость читает из устройств (PCI config space, регистры версии APIC/IOAPIC, `CAPS` дисплея): в нём только то, чего гость не может узнать из устройств.

### 6.1. Заголовок (`header_size = 0xA0`)

| Смещение | Ширина | Поле | Значение / по умолчанию |
|---|---|---|---|
| `0x00` | 8 | `magic` | ASCII `ODHANDOF` (`0x464F_444E_4148_444F`) |
| `0x08` | 2 | `version_major` | `1` |
| `0x0A` | 2 | `version_minor` | `0` |
| `0x0C` | 4 | `header_size` | `0xA0` для minor 0 |
| `0x10` | 4 | `total_size` | `header_size ≤ total_size ≤ 0x10000`, кратно 8; для v1.0 — `device_table_offset + device_count × device_entry_size` = `0xA0 + 32 × region_count + 336` |
| `0x14` | 4 | `crc32` | CRC-32 первых `total_size` байт с этим полем, равным нулю |
| `0x18` | 4 | `flags` | `0` (биты зарезервированы) |
| `0x1C` | 4 | `cpu_count` | `1` |
| `0x20` | 8 | `tsc_hz` | частота TSC vCPU, не ноль; по умолчанию `1_000_000_000` |
| `0x28` | 4 | `board_profile` | `1` — firmware board v1 |
| `0x2C` | 4 | `reserved0` | `0` |
| `0x30` | 4 | `region_table_offset` | от начала блока, кратно 8, `≥ header_size`; для v1.0 — `0xA0` (сразу за заголовком) |
| `0x34` | 4 | `region_count` | `1…128` |
| `0x38` | 4 | `region_entry_size` | `32` |
| `0x3C` | 4 | `device_table_offset` | от начала блока, кратно 8, `≥ header_size`, не внутри таблицы регионов; для v1.0 — `region_table_offset + region_count × region_entry_size` = `0xA0 + 32 × region_count` (сразу за регионами) |
| `0x40` | 4 | `device_count` | число записей устройств (для v1.0 — `7`) |
| `0x44` | 4 | `device_entry_size` | `48` |
| `0x48` | 16 | `system_uuid` | UUID машины в байтовом порядке поля UUID SMBIOS 3.9 (Type 1), копируется без перестановок; по умолчанию все нули («ID отсутствует» по SMBIOS) |
| `0x58` | 2 | `serial_len` | `0…64`; по умолчанию `0` (серийного номера нет) |
| `0x5A` | 6 | `reserved1` | нули |
| `0x60` | 64 | `serial` | первые `serial_len` байт — ASCII `0x20…0x7E`, остальные нули; без NUL-терминатора |

UUID и серийный номер задаёт конфигурация VM на host; машина копирует их байты, прошивка использует их только для SMBIOS (S7-13).

**Каноническая раскладка v1.0** (машина v1.0 выдаёт ровно её): заголовок `[0x00, 0xA0)`; таблица регионов с `0xA0`, `region_count` записей по 32 байта; таблица устройств сразу за ней, 7 записей по 48 байт (336 байт); `total_size` — конец таблицы устройств, без хвостовых байт. Например, при 12 регионах `region_table_offset = 0xA0`, `device_table_offset = 0x220`, `total_size = 0x370`; при максимуме 128 регионов `total_size = 0x11F0 ≤ 0x10000`. Все три значения кратны 8 при любом `region_count`. Прошивка проверяет не равенство канонической раскладке, а общие правила этой таблицы и раздела 6.5, чтобы блоки следующих minor с большим `header_size` или `*_entry_size` проходили те же проверки.

### 6.2. Таблица регионов (запись 32 байта)

| Смещение | Ширина | Поле | Значение |
|---|---|---|---|
| `0x00` | 4 | `type` | код из таблицы ниже |
| `0x04` | 4 | `attrs` | для `FRAMEBUFFER` биты 0–7 — номер экрана; для остальных `0` |
| `0x08` | 8 | `base` | кратно 4 KiB |
| `0x10` | 8 | `length` | не ноль, кратно 4 KiB, `base + length ≤ 2^36` |
| `0x18` | 4 | `owner_device` | индекс записи в таблице устройств или `0xFFFF_FFFF` |
| `0x1C` | 4 | `reserved` | `0` |

| Код | Тип | Откуда | UEFI memory map (S7-04) |
|---|---|---|---|
| 1 | `RAM` | `Ram` карты за вычетом boot reservations | `EfiConventionalMemory` (кроме того, что прошивка сама займёт) |
| 2 | `RESERVED` | `Reserved` карты | `EfiReservedMemoryType` |
| 3 | `MMIO` | `Mmio` карты (кроме NVRAM) | `EfiMemoryMappedIO` |
| 4 | `ROM` | `Rom` карты | `EfiReservedMemoryType` |
| 5 | `NVRAM` | окно NVRAM | `EfiMemoryMappedIO` + `EFI_MEMORY_RUNTIME` |
| 6 | `FRAMEBUFFER` | `Framebuffer` карты | `EfiMemoryMappedIO` |
| 7 | `HANDOFF` | поддиапазон RAM | `EfiReservedMemoryType` |
| 8 | `BOOT_STACK` | поддиапазон RAM | `EfiBootServicesData` |
| 9 | `FIRMWARE_SHADOW` | поддиапазон RAM | `EfiBootServicesCode` (код) / `EfiBootServicesData` (данные) по символам компоновки образа |
| 10 | `BOOT_PAGE_TABLES` | поддиапазон RAM | `EfiConventionalMemory` после переключения `CR3` |
| 11 | `ACPI_TABLES` | поддиапазон RAM, только при `version_minor ≥ 2` (S4-31c) | `EfiACPIReclaimMemory` (E820 ACPI reclaim, S4-37) |
| 12 | `ACPI_NVS` | поддиапазон RAM, только при `version_minor ≥ 2` (S4-31c) | `EfiACPIMemoryNVS` (E820 NVS, S4-37) |

Записи отсортированы по `base`, не пересекаются, описывают каждый регион `MachineMemoryMap` и только их; поддиапазоны 7–10 лежат внутри `Ram` и совпадают с константами раздела 2; поддиапазоны 11–12 (только v1.2, ниже) лежат внутри нижней `Ram` по константам из описания кода 9. Тип `RAM` в таблице никогда не накрывает поддиапазоны 7–12. Окончательные атрибуты (`EFI_MEMORY_UC/WB/RUNTIME` и т. п.) фиксирует S7-04 в `UEFI_PROFILE.md`; правило «framebuffer, MMIO, ROM, NVRAM и handoff block никогда не `EfiConventionalMemory`» (план §4.1) не меняется. S7-30 может уточнить типы для MMIO/framebuffer по фактическим требованиям Windows.

### 6.3. Таблица устройств (запись 48 байт)

| Смещение | Ширина | Поле | Значение |
|---|---|---|---|
| `0x00` | 4 | `type` | код устройства |
| `0x04` | 4 | `flags` | бит 0 `PRESENT`; бит 1 `PIO` (иначе MMIO); остальные `0` |
| `0x08` | 8 | `base` | GPA (MMIO) или номер порта (PIO); `0`, если `PRESENT = 0` |
| `0x10` | 8 | `length` | байты или число портов; `0`, если `PRESENT = 0` |
| `0x18` | 4 | `gsi` | вход IOAPIC (global system interrupt) или `0xFFFF_FFFF` — нет |
| `0x1C` | 4 | `irq_flags` | бит 0: 1 = level, 0 = edge; бит 1: 1 = active-low, 0 = active-high |
| `0x20` | 8 | `param0` | по типу |
| `0x28` | 8 | `param1` | по типу |

Устройства v1.0 (каждый тип 1–7 присутствует ровно один раз; отсутствующее устройство — `PRESENT = 0`, нули в адресах):

| Код | Устройство | Значения в firmware board v1 |
|---|---|---|
| 1 | COM1, UART 16550 polling profile | `PRESENT\|PIO`, `base = 0x3F8`, `length = 8`, `gsi = 4`, edge/high (IRQ4 по `VIRTUAL_BOARD.md`; доставки IRQ4 нет, прошивка опрашивает), `param0 = 1` (номер COM) |
| 2 | Local APIC | `PRESENT`, `0xFEE0_0000`, `0x1000`, `param0` = APIC ID (`0`) |
| 3 | IOAPIC | `PRESENT`, `0xFEC0_0000`, `0x1000`, `param0` = GSI base (`0`); ID и число входов в MADT — константы прошивки (ID = 1, входов 24); будущий регистр модели должен отдавать ID = 1 и Version с MRE = 23, иначе Linux получит другой диапазон GSI или ошибку шины (требование S4-26 и S4-38) |
| 4 | Дисплей | В штатном профиле `PRESENT`, регистры `0xFC00_0000`, `0x1000`; framebuffer-регионы — в таблице регионов с `owner_device` = индекс этой записи. Headless профили могут выставить `FirmwareBoardConfig::display_enabled = false`: код 4 остаётся в таблице один раз с `PRESENT = 0` и нулевыми адресами, а регистры/framebuffer не отображаются в bus или карте памяти. | 5 | NVRAM | `PRESENT = 0` до S7-10; затем `0xFF00_0000`, `0x0004_1000`; раскладку регистров задаёт `NVRAM_DEVICE.md` (S7-10) |

Коды 8–15 зарезервированы для NVMe без PCI (fallback S7-16, код 8), ACPI fixed hardware (код 9, S4-31c), RTC/CMOS и HPET (S7-14); их записи и поля определяют эти задачи, повышая `version_minor`. Коды 10–15 остаются свободными.

**Код 8, NVMe-контроллер без PCI (S7-16, `version_minor = 1`).** Статус: расширение S7-16 срез A, ожидает ревью; S7-02 не меняется по существу. Запись добавляется **только** когда плата сконфигурирована с NVMe-устройством; без него блок остаётся v1.0 (7 устройств). Запись: `PRESENT`, MMIO (бит `PIO` = 0), `base = 0xFC00_1000`, `length = 0x2000`, `gsi = 0xFFFF_FFFF` (нет IRQ в срезе A), `irq_flags = 0`, `param0 = param1 = 0`; в таблицу регионов добавляется регион типа `MMIO` с `owner_device` = индекс записи (7). При `version_minor = 1` `device_count = 8`, `total_size` вырастает на 48 байт и на один регион (32 байта), CRC считается заново. Образ прошивки, которому машина выдаёт v1.1, обязан объявлять `handoff_minor_max ≥ 1` (машина отклоняет иначе). Прошивка репозитория пока читает только minor 0 — разбор записи NVMe делает S7-17. Контракт устройства — [NVME_DEVICE.md](NVME_DEVICE.md). Устройство на PCI (NVMe после S4-30) в таблицу не входит: прошивка находит его перечислением ECAM.

**Код 9, ACPI fixed hardware: PM-блок и SCI (S4-31c, `version_minor = 2`).** Запись и два региона добавляются **только** при opt-in флаге платы `acpi_tables` (`FirmwareBoardConfig::acpi_tables`, по умолчанию `false`; флаг требует `acpi_pm`, иначе загрузка платы отклоняется: запись описывала бы незарегистрированные порты). Запись: `PRESENT | PIO` (`flags = 3`), `base = 0x0600`, `length = 0x10` (блок портов `0x0600..0x0610`), `gsi = 9`, `irq_flags = 0b11` (level, active-low; SCI идёт через interrupt source override, запись MADT — S4-31f), `param0` — четыре порта по 16 бит: биты 0–15 `PM1a_EVT_BLK` (`0x0600`), 16–31 `PM1a_CNT_BLK` (`0x0604`), 32–47 `PM_TMR_BLK` (`0x0608`), 48–63 `RESET_REG` (`0x060C`), то есть `param0 = 0x060C_0608_0604_0600`; `param1` — биты 0–7 `RESET_VALUE` (`0x06`), 8–15 `SLP_TYP` для S5 (`5`), остальные нули, то есть `param1 = 0x0506`. Длины регистров не передаются, это константы блока (`PM1_EVT_LEN = 4`, `PM1_CNT_LEN = 2`, `PM_TMR_LEN = 4`, `RESET_REG` — один байт); источник значений на машине — `ACPI_PM_DESCRIPTOR` (S7-14a). Индекс записи в таблице устройств: после кода 8, если он есть (девять записей: `ECAM = 6`, `NVMe = 7`, `ACPI = 8`), иначе `7` (восемь записей); прошивка ищет запись по `type`, а не по индексу. Таблица регионов: низкая RAM (`[0, 0x0010_0000)` до первой boot-резервации) режется на `RAM` `[0, 0x000E_0000)`, `ACPI_TABLES` (код 11) `[0x000E_0000, 0x000E_F000)` (в S4-37 это E820 ACPI reclaim; RSDP — на `0x000E_0000`), `ACPI_NVS` (код 12) `[0x000E_F000, 0x000F_0000)` (в S4-37 E820 NVS; сюда ляжет FACS на `0x000E_F000`) и `RAM` `[0x000F_0000, 0x0010_0000)` (нулевая RAM); `owner_device = 0xFFFF_FFFF`. Единая карта платы (`MachineMemoryMap`) не меняется: диапазон — часть нижней RAM, как поддиапазоны 7–10. Область таблиц машина не заполняет: байты таблиц и blob — S4-31d–g; типы E820 здесь только записаны в манифесте как решение, сам E820 соберёт S4-37. С флагом `region_count` растёт на 3, `device_count` на 1, `total_size` на `3 × 32 + 48 = 144` байта, CRC считается заново. Образ, которому машина выдаёт v1.2, обязан объявлять `handoff_minor_max ≥ 2` (машина отклоняет иначе). Разбор записи в репозитории прошивки — `AcpiPmEntry::from_entry` (`firmware/uefi/src/acpi/manifest.rs`, const fn, только проверка и декодирование записи; разбор всего блока — S7-04). Блок v1.0 (`BoardManifest`, семь записей) код 9 не принимает.

### 6.4. Правило расширения и версии

- Новые поля добавляются только в конец заголовка (растёт `header_size`) или в конец записи (растёт `*_entry_size`), новые устройства — новыми кодами; каждое такое изменение повышает `version_minor` и описывается здесь с значением по умолчанию для старых minor.
- Несовместимое изменение повышает `version_major`.
- Прошивка принимает блок только при `version_major = 1` и `version_minor ≤ handoff_minor_max` своего образа. Для меньшего minor отсутствующие поля и устройства имеют значения по умолчанию из этого документа. Для неизвестной версии прошивка **останавливается с сообщением** (раздел 12), не пытаясь читать известную часть.
- `version_minor` зависит от конфигурации платы: с флагом `acpi_tables` блок v1.2 (`version_minor = 2`) независимо от NVMe (запись кода 9 добавляется в конец таблицы устройств; без NVMe — восьмой записью, с NVMe — девятой); без флага `acpi_tables`: без NVMe-устройства блок v1.0 (`version_minor = 0`, 7 записей), запись кода 8 **отсутствует** (не выводится даже с `PRESENT = 0`); с NVMe-устройством — v1.1 (`version_minor = 1`, 8 записей, код 8 с `PRESENT = 1`). Вариант «запись с `PRESENT = 0`» не используется: так ведёт себя `firmware_board.rs` (`board_devices`, `load_firmware_image`), прошивка без разбора кода 8 получает прежний v1.0 байт в байт.
- Код 7 (S4-30c) лежит в слоте v1.0: с флагом `pci_ecam` `version_minor` остаётся `0`, `device_count = 7`, образу не нужен `handoff_minor_max ≥ 1`. Меняются только запись 7 (`PRESENT = 1`, поля выше) и таблица регионов: добавляется регион `MMIO` `[0xFC10_0000, 0xFC20_0000)` с `owner_device` = 6 (`region_count` и `total_size` растут на одну запись региона, 32 байта; CRC считается заново). Окно лежит в том же 2 MiB-блоке страниц, что регистры дисплея, поэтому `N` (раздел 4) не меняется. Без флага блок v1.0 прежний байт в байт (golden-тест `handoff_block_is_byte_identical_to_the_reference`). Машина на шине платы при этом не объявляет ни host bridge, ни одной PCI-функции; MCFG и PNP0C02 — S4-31, E820 и loader — S4-37.
- Машина собирает блок одним кодом из той же `MachineMemoryMap` и списка устройств, по которым строит шину (S7-03, п. 2); второго списка констант нет.

### 6.5. Проверки прошивки при входе

Прошивка проверяет в этом порядке и при первой ошибке останавливается с кодом раздела 12: `RDI`; `magic`; версию; `header_size` и `total_size`; CRC; смещения, количества и размеры записей (таблицы внутри `total_size`, не перекрывают заголовок и друг друга); регионы (типы известны: 1–10, а 11–12 только при `version_minor ≥ 2`, сортировка, отсутствие перекрытий, выравнивание, ширина 36, константы раздела 2, `FIRMWARE_SHADOW` = `link_base` и `image_size` самого образа); устройства (каждый тип v1.0 ровно один раз, зарезервированные биты нули); `cpu_count = 1`; `tsc_hz ≠ 0`; `serial_len` и символы; нули в зарезервированных полях.

### 6.6. CRC-32

Везде в этом документе — CRC-32 IEEE 802.3 в отражённой форме: полином `0xEDB8_8320`, начальное значение `0xFFFF_FFFF`, финальный XOR `0xFFFF_FFFF` (контрольное значение для ASCII `123456789` — `0xCBF4_3926`).

## 7. Решение 2: состояние при вызове EFI-образа

**Выбрано:** прошивка вызывает каждый EFI-образ (entry point через `StartImage`) и каждую функцию, которую образ ей передал (notify-функции событий и т. п.), в следующем состоянии; все функции таблиц и протоколов прошивки объявлены `extern "efiapi"`.

- Long64, CPL0, один процессор; страничная трансляция по **собственным** таблицам прошивки (S7-04), только 4 KiB, identity (`VA = PA`) для всех записей UEFI memory map, включая MMIO, ROM, NVRAM и framebuffer; листья ROM — `P|NX`, как во временных таблицах (нормативно, раздел 3.1).
- `CR0 = 0x8001_0033` (EM = 0, TS = 0, MP = 1, NE = 1), `CR4 = 0x0000_0620` (PAE, OSFXSR, OSXMMEXCPT), `EFER = 0x0D00`. Это состояние вызова образа, а не входа: при входе `CR4 = 0x0000_0020` (раздел 5). OSFXSR/OSXMMEXCPT прошивка ставит одной записью `MOV CR4` в начале S7-04, до первого вызова образа.
- x87 FCW = `0x037F` (после `FNINIT`), MXCSR = `0x1F80`; значения сверить с текстом §2.3.4 в S7-05 (раздел «Нормативные источники» выше).
- `RFLAGS`: DF = 0, IF = 1 на `TPL_APPLICATION`; при `RaiseTPL(TPL_HIGH_LEVEL)` IF = 0, при возврате ниже — IF = 1. Источников прерываний в v1 нет (раздел 8), поэтому IF = 1 ничего не доставляет; IDT прошивки имеет обработчик для каждого из 256 векторов, исключение или неожиданный вектор — останов с кодом `0x10`.
- Сегменты плоские из GDT прошивки: `CS = 0x08` (64-битный код, DPL 0), `SS = DS = ES = FS = GS = 0x10` (данные). Переход на них требует far return/`IRETQ` и загрузки сегментных регистров в paged Long64 — blocker S7-04 (ниже, «Blocker S7-04»).
- Стек: собственный стек прошивки 256 KiB (`EfiBootServicesData`) с неотображённой guard-страницей 4 KiB ниже; при входе в образ свободно не меньше 128 KiB. Перед `CALL` `RSP mod 16 = 0`, вызывающий выделяет 32 байта shadow space; на входе в образ `(RSP + 8) mod 16 = 0`.
- ABI Microsoft x64: аргументы `RCX, RDX, R8, R9`, далее стек; результат `RAX`; сохраняемые `RBX, RBP, RDI, RSI, R12–R15, XMM6–XMM15`. Entry point образа: `RCX = ImageHandle`, `RDX = *EFI_SYSTEM_TABLE`. `extern "C"` (System V) для интерфейсов UEFI запрещён (план §3, п. 10).

**Причина:** по плану этапа 7 (S7-02, п. 4) это требования UEFI 2.11 §2.3.4, которые чужой образ (Windows Boot Manager, Linux EFI stub) вправе предполагать; текст UEFI 2.11 §2.3.4 не сверен (сверку, включая FCW `0x037F` и MXCSR `0x1F80`, выполняет S7-05). Значения CR0/EFER совпадают с уже принятым handoff S4-32a; `CR4 = 0x620` входит в допустимую маску `CR4_ALLOWED` `page_walk.rs`.

**Исполнитель:** S7-04 (GDT/IDT, CR4, стек, собственные таблицы), S7-05 (TPL/IF, сверка §2.3.4), S7-06 (вызов entry point образа).

**Зависимость:** в `CPU_CONTRACT.md` запись `MOV CR4` с OSFXSR/OSXMMEXCPT допущена только профилем `Cr4Profile::FpInitLong64V1` (S2-25b). Если на момент S7-04 paged-сессия не исполняет `MOV CR4`, `FNINIT`, `LDMXCSR`, `STI`/`CLI` в Long64/CPL0, S7-04/S7-05 записывают blocker на CPU-профиль; машина не подменяет это значением `CR4` при handoff.

**Blocker S7-04 — переход на селекторы прошивки** (проверено по коду и контрактам на `feat/s9-stage`, `c1ae3dd`). Для `CS = 0x08` нужен far return (`LRETQ`, `48 CB`) или `IRETQ` с кадром CPL0→CPL0 в paged Long64; для `SS/DS/ES/FS/GS = 0x10` — загрузка сегментных регистров с чтением дескрипторов GDT через страничную трансляцию. Сейчас:

- `LRETQ` есть только как локальный профиль интерпретатора `od-isa` `LretqProfile::SameCpl0ValidFrameV1` (`CPU_CONTRACT.md`, S2-27l) и в `od-machine` не подключён (ни paged-, ни identity-путь).
- Paged `IRETQ` в `od-machine` есть только в узких профилях: возврат из `#PF`-обработчика после точной последовательности `LEA RSP,[RSP+8]; IRETQ` (S4-19e1) и синтетический выход CPL0→CPL3 (S4-20a, требует нулевых DS/ES/FS/GS); `run_same_cpl0_iretq` (S4-27b) работает только на flat identity-пути диагностической сессии.
- `MOV DS, AX` (`8E D8`, S2-27b) и `MOV ES, AX` (`8E C0`, S2-27c) — только локальные профили `od-isa` для CPL0; `MOV FS, AX`/`MOV GS, AX` (S2-22f/h) — только CPL3; `MOV SS` нет совсем. В paged-сессии `od-machine` ни одна загрузка сегментного регистра не подключена.
- Flat probe S4-32a исполняет только `MOV RAX,[RBX]`, `OUT DX,AL`, `HLT` и сегментов не меняет. Базовый paged-профиль `PagedCpl0ProbeV1` после решения S7-03 добавляет только `MOV r8,imm8` и `MOV r16,imm16` (`CPU_CONTRACT.md`, «Расширение S7-03»); этот blocker он не снимает.

Пока эти переходы не приняты в paged-профиле CPU, S7-04 записывает blocker на CPU-профиль (paged `LRETQ` или `IRETQ` CPL0→CPL0 и загрузка SS/DS/ES/FS/GS из GDT); машина не подменяет переход начальными значениями сегментов при handoff, а значения раздела 7 не ослабляются.

## 8. Решение 3: модель таймеров и событий

**Выбрано:** вариант (а) — опрос TSC в фиксированных точках, документированное отклонение от §2.3.4. Рекомендация плана подтверждена. Переход на вариант (б) — прерывания LAPIC timer — после принятия на этапе 4 доставки IRQ в paged-пути (S4-27), пробуждения из `HLT` и APIC timer (S4-28); переход — новая версия этого документа и `UEFI_PROFILE.md`.

**Причина** (проверено 2026-11-07 на базе `feat/s9-stage` HEAD `c1ae3dd`, ответвлённой от `main` в `8e0dc10`, и на `main` HEAD `4dcc340`):

- База `feat/s9-stage`: доставка прерываний в CPU — только caller-driven диагностика `DiagnosticVcpuSession` (S4-27a — вход и первая инструкция обработчика, S4-27b — гостевой EOI и same-CPL0 `IRETQ`) на flat identity-пути; нет автоматического опроса, paged-доставки и пробуждения из `HLT`.
- `main` дополнительно содержит S4-27c (`6d4773f`, `run_sti_apic_quantum`: квант в одну инструкцию по профилю STI), S4-27d (`6484f1a`, `into_halt_wait`/`poll_apic`: явное ожидание после `HLT` и пробуждение по готовому вектору APIC при синхронном опросе вызывающим) и S4-27e (`4dcc340`, `run_apic_quantum`: обычный квант с бюджетом 1 и арбитражем одного вектора на границе). По `MACHINE_CONTRACT.md` в `main` все три среза — diagnostic API на flat identity-пути: они требуют сессии без CR0/CR3/CR4 (то есть не paged), бюджета в одну инструкцию и вызова на каждой границе; нет доставки внутри многоинструкционного кванта или JIT-блока, асинхронного поступления, общего планировщика, интеграции `HLT` с paged-сессией и источника таймера. Parent S4-27 в `STAGE_4.md` `main` открыт.
- APIC timer (S4-28) не начат ни в базе, ни в `main`; без него у варианта (б) нет источника прерываний.

Поэтому вывод одинаков для базы и для `main`: прошивка в paged Long64 не может получать прерывания таймера, и вариант (а) остаётся единственным исполнимым. Вариант (б) сделал бы S7-05 и весь первый срез blocked до приёмки S4-27 (paged-доставка в обычном прогоне) и S4-28. Срезы S4-27c–e этот вывод не меняют; при переходе на (б) они — основа, а не замена paged-доставки.

Правила варианта (а) (реализует S7-05):

- Источник времени — `RDTSC`; длительность в единицах 100 ns переводится в такты как `ceil(t × tsc_hz / 10^7)` с промежуточным 128-битным значением; `tsc_hz` — только из handoff block.
- Точки опроса: `RaiseTPL` (без диспетчеризации), `RestoreTPL` (диспетчеризация ожидающих notify с TPL выше нового), `WaitForEvent`, `CheckEvent`, `SignalEvent`, `SetTimer`, `Stall`, `OutputString`/`ClearScreen`/`SetCursorPosition` консоли, `ReadKeyStroke`; все сервисы BS, которые внутри поднимают и восстанавливают TPL, опрашивают через `RestoreTPL`.
- Опрос: просрочка каждого timer-события проверяется по TSC; периодическое событие перевзводится от предыдущего срока, а не от момента опроса; несколько просроченных периодов дают одно срабатывание.
- Ожидание (`WaitForEvent`, `Stall`) — активный опрос без `HLT`: в paged-пути нет пробуждения из `HLT` (S4-27d в `main` — только flat identity-диагностика, см. выше), поэтому в v1 `HLT` у прошивки — только окончательный останов (раздел 12).
- Watchdog (`SetWatchdogTimer`) — то же timer-событие; срабатывает только в точке опроса и ведёт к `ResetSystem` (раздел 12).
- `ExitBootServices` останавливает все timer-события; после него прошивка не опрашивает.
- **Последствие отклонения** (S7-05 записывает в `UEFI_PROFILE.md`): образ, который ждёт notify timer-события в цикле без вызовов сервисов BS, не получит его; задержка notify равна интервалу между вызовами BS.

Требование к машине (реализует S7-03): виртуальное время в `od-machine` продвигается только явным `advance_time_ns` между квантами (`MACHINE_CONTRACT.md`, «Caller-driven virtual clock»). Подкоманда `boot-firmware` после каждого кванта продвигает время на `retired_instructions × 1 ns` — детерминированно, без host wall-clock. Для плат с `acpi_pm` `run_boot` добавляет тик 1 мкс на каждое гостевое чтение `PM_TMR` (`MACHINE_CONTRACT.md`, раздел ACPI, `PM_TMR`); квант заканчивается после такого чтения, поэтому `FirmwareRunReport.quanta` растёт на каждое такое чтение (видимое изменение поля отчёта). Без этого `Stall` и таймеры прошивки не завершаются. Значения `tsc_hz` и шага времени печатаются в отчёте прогона.

**Исполнитель:** S7-05 (события, TPL, `Stall`, запись отклонения), S7-03 (продвижение времени в runner), S7-07 (опрос в консоли).

## 9. Решение 4: перемещение RT-части после `SetVirtualAddressMap`

**Выбрано:** отдельный перемещаемый RT-образ — PE32+ с `.reloc`, subsystem `EFI_RUNTIME_DRIVER` (12), в firmware volume внутри образа ROM. Static-PIE всей прошивки с собственной таблицей relocations отклонён.

**Причина:** при одной компоновке нельзя гарантировать, что весь код, достижимый из RT (мономорфизации, `core::fmt`, `memcpy`, vtables), попадёт в RT-секции, а не в BS-память, которую ОС заберёт после `ExitBootServices`; отдельная единица компоновки даёт это по построению. Тот же собственный PE loader (S7-06), проверенный на битых образах, загружает RT-образ и применяет его relocations; второго формата relocations не появляется. PE32+ с `.reloc` даёт штатный target `x86_64-unknown-uefi` + `lld-link`, который S7-01 уже вводит для тестовых EFI-приложений; собственный упаковщик ELF→PE не нужен.

Правила (S7-01 — доказательство сборки PE32+ probe; боевой RT-образ и его размещение в FV — S7-11 (зависит от S7-06); S7-06 — загрузка, S7-11 — применение):

- Основной образ ROM — плоский, компонуется по `0x0020_0000`, исполняется только до `ExitBootServices` и relocations не имеет.
- RT-образ: весь образ — `EfiRuntimeServicesCode`; его пул — отдельный диапазон `EfiRuntimeServicesData`, выделенный до `ExitBootServices`; после EBS RT-образ не вызывает BS и не обращается к BS-памяти. Указатели в BS-память RT-образ не хранит. Переменные (S7-09/S7-10/S7-24, включая проверку authenticated variables криптобиблиотеками D9) живут в RT-образе; BS-ядро вызывает их через `gRT`.
- При загрузке PE loader сохраняет `.reloc` и для каждой записи `IMAGE_REL_BASED_DIR64` значение слова после применения relocations.
- `SetVirtualAddressMap`: для RT-образа вычисляется `delta = новый VA − текущий адрес`; relocation применяется повторно только к словам, чьё текущее значение равно сохранённому (слова, изменённые во время работы, не трогаются); затем RT-образ в своём обработчике `EVT_SIGNAL_VIRTUAL_ADDRESS_CHANGE` переводит через `ConvertPointer` собственные динамические указатели (пул, окно NVRAM, таблица `gRT`). Отсутствие `.reloc` у RT-образа — ошибка сборки, не допущение.
- Ограничение S7-01, п. 1 («не использовать `x86_64-unknown-uefi` для самой прошивки») относится к основному образу; RT-образ собирается как EFI-драйвер тем же способом, что тестовые приложения. Это уточнение выносится на ревью S7-02 и записывается в README S7-01.

**Исполнитель:** S7-01 (доказательство сборки PE32+ probe; боевой RT-образ и его размещение в FV — S7-11, зависит от S7-06), S7-06 (загрузка subsystem 12 в `EfiRuntimeServicesCode`), S7-11 (боевой RT-образ и размещение в FV, `SetVirtualAddressMap`, `ConvertPointer`, тест `rt` с неидентичным отображением).

## 10. Владение памятью

- Прошивка пишет только в RAM (свою и выделенную своим аллокатором), окно NVRAM и регистры устройств из таблицы устройств с `PRESENT = 1`; в ROM не пишет никогда.
- Регион `HANDOFF` прошивка только читает; ACPI/SMBIOS строит из прочитанных значений (S7-13), не из констант.
- Перевод регионов в типы UEFI memory map — таблица раздела 6.2; UEFI memory map, E820 (этап 4) и ACPI описывают одну и ту же карту.
- После `ExitBootServices` прошивка использует только RT-образ, его пул и окно NVRAM; единственное исключение — финальная строка COM1 в `ResetSystem` (раздел 12) до появления reset register.

## 11. Консоль COM1

Консоль прошивки — COM1 по bounded polling-профилю `uart16550.rs` (`MACHINE_CONTRACT.md`, «Bounded COM1 polling UART»):

- Только байтовые `IN AL,DX` и `OUT DX,AL` с портом в `DX` (другие формы I/O не поддержаны CPU-профилем); порт — из записи устройства 1.
- Инициализация: `LCR = 0x80` (DLAB), `DLL = 0x01`, `DLM = 0x00`, `LCR = 0x03` (8N1). IER, FCR и MCR не записываются (IER должен оставаться нулём, FIFO выключен). Машина при входе уже оставляет COM1 в этом конечном состоянии (раздел 5); повторная инициализация прошивкой допустима и его не меняет.
- Передача: перед каждой записью THR прошивка читает LSR и ждёт `THRE` (`0x20`), не больше `65536` опросов; при превышении байт отбрасывается и счётчик потерь растёт (без зависания). Перенос holding → shift и завершение передачи делает runner (S7-03) между квантами: в `uart16550.rs` они происходят только по явным вызовам `transfer_holding_to_shift`/`complete_transmission` через `Uart16550Handle`, а запись THR при занятом holding отклоняется ошибкой устройства без изменения состояния.
- **Контракт кванта для TX (выбран вариант «квант заканчивается на записи THR»).** Если инструкция кванта сделала holding занятым (`OUT DX,AL` в THR при DLAB = 0), квант завершается на следующей границе инструкции; runner S7-03 переносит и завершает байт, записывает его в транскрипт и только потом продвигает время и начинает следующий квант. При выходе кванта по `Halted`, бюджету или ошибке runner так же забирает оставшийся байт holding/shift до разбора вывода. Механизм есть в машине уже сейчас: paged-квант проверяет caller-предикат STOP на каждой границе до бюджета (`MACHINE_CONTRACT.md`, S4-21b); остановки кванта по событию UART внутри машины нет, предикат реализует runner (способ узнать занятость holding через handle добавляет S7-03). Следствие: каждый первый опрос LSR после записи видит `THRE`, лимит `65536` при соблюдении контракта не достигается, и строки `OD-FW STOP`/`OD-FW RESET` (раздел 12) не теряются при любом размере кванта.
- **Почему не предел кванта по числу опросов:** число инструкций в цикле опроса зависит от компилятора и кода S7-04/S7-07, поэтому безопасный предел пришлось бы подбирать и перепроверять при каждой правке; ошибка подбора молча теряет последние байты, то есть именно строку останова. Цена выбранного варианта — один квант на байт консоли; для отладочной консоли v1 это приемлемо.
- Проверки: S7-03 — тест runner, где прошивка выводит строку длиннее одного кванта при большом бюджете и транскрипт совпадает побайтно; S7-07 — `OutputString` и строки раздела 12 доходят до транскрипта целиком, счётчик потерь консоли равен нулю.
- Приём (для `ConIn`, S7-07): RBR читается только при `LSR.DR` (бит 0); чтение пустого RBR — ошибка устройства.
- Концы строк — `\r\n`; кодировка — ASCII, символы вне `0x20…0x7E` в `OutputString` заменяются на `?` (точное правило — S7-07).

## 12. Останов, коды состояния и сброс

Останов прошивки: строка на COM1, затем `CLI; HLT` в цикле. Это окончательное состояние: paged-сессия не выходит из `HLT`, а диагностическое пробуждение S4-27d (только в `main`, раздел 8) при IF = 0 остаётся в ожидании; runner видит `Halted`, забирает оставшийся байт UART по контракту кванта раздела 11 и разбирает последнюю строку.

- Формат: `OD-FW STOP code=0xNN detail=0xDDDDDDDDDDDDDDDD\r\n` (`detail` — смещение поля или значение, 16 hex-цифр).
- Коды: `0x01` — неверный `RDI`; `0x02` — magic; `0x03` — неизвестная версия (`detail = major << 16 | minor`); `0x04` — размеры; `0x05` — CRC; `0x06` — границы таблиц; `0x07` — регион; `0x08` — устройство; `0x09` — `cpu_count`; `0x0A` — `tsc_hz`; `0x0B` — серийный номер; `0x0C` — shadow не совпадает с link base/размером образа; `0x10` — исключение CPU или неожиданный вектор (`detail` = вектор); `0x21` — нечего загружать; `0x30` — внутренняя ошибка прошивки (panic handler).
- `ResetSystem` (S7-11): до появления reset register ACPI fixed hardware (S7-14) — строка `OD-FW RESET type=N status=0xSSSSSSSSSSSSSSSS\r\n` (`type` — `EFI_RESET_TYPE`, `status` — `ResetStatus`), затем `CLI; HLT`. После S7-14 — запись значения сброса в reset register, адрес которого прошивка берёт из записи устройства ACPI fixed hardware (новый minor handoff block); фактический сброс машины — S7-26 (blocked до S4-21); если машина не сбросилась, прошивка выводит ту же строку и останавливается.

## 13. Что прошивка гарантирует и чего нет

Гарантирует (после реализации S7-03…S7-11): не меняет карту платы; не пишет вне разрешённого в разделе 10; не показывает framebuffer, MMIO, ROM, NVRAM и handoff block как `EfiConventionalMemory`; строит собственные таблицы страниц и не зависит от временных; после `ExitBootServices` трогает только RT-регионы; неизвестную версию handoff block не угадывает.

Не гарантирует: SMP (один CPU, MP Services не предоставляются); legacy BIOS/CSM, real mode, reset vector; сетевую загрузку (PXE, HTTP boot, SNP — вне профиля v1, решение D1); large pages в собственных таблицах; прерывания таймера до перехода на вариант (б); S3/S4 resume, capsule update, обновление прошивки из гостя.

## 15. Проверка адресов (вычислено `python3`, 2026-11-07)

- ROM `[0xFFC0_0000, 0x1_0000_0000)`, NVRAM `[0xFF00_0000, 0xFF04_1000)` и handoff `[0x0010_0000, 0x0011_0000)` не пересекают `[0xF400_0000, 0xFC00_1000)`, `[0xFEC0_0000, 0xFEC0_1000)`, `[0xFED4_0000, 0xFED4_5000)`, `[0xFEE0_0000, 0xFEE0_1000)` и друг друга; ROM и NVRAM лежат внутри `0xFF00_0000–0xFFFF_FFFF`.
- RAM ниже 4 GiB заканчивается не выше `0xF400_0000`; boot reservations заканчиваются ниже `0x0060_0000 + 0x0800_C000 = 0x0860_C000` и при минимальной RAM — в `0x0066_E000 < 0x0800_0000`.
- Все окна ниже `2^32`, верхняя RAM ≤ `2^36`: карта совместима с `MachineMemoryMap::new(36, …)`; ни одного `Framebuffer` больше двух, их начала и длины кратны 4 KiB и не больше `0x0240_0000`.
