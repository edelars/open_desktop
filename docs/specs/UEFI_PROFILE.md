# Поддержанный профиль UEFI

## Таблицы UEFI и Boot Services

Внутренняя диагностика строит в RAM три таблицы UEFI x64. Размеры
`EFI_SYSTEM_TABLE`, `EFI_BOOT_SERVICES` и `EFI_RUNTIME_SERVICES` составляют
120, 376 и 136 байт. У каждой таблицы 24-байтовый заголовок, редакция
`0x0002006e` и CRC-32 IEEE по `HeaderSize` байтам с обнулённым полем CRC
при расчёте. System Table ссылается на обе таблицы сервисов и имя производителя
`Open Desktop` в UTF-16. Слот `Reserved` у Boot Services равен NULL.
[UEFI 2.11, §4](https://uefi.org/specs/UEFI/2.11/04_EFI_System_Table.html).

| Boot Service | Поведение диагностической реализации |
|---|---|
| `CalculateCrc32` | Вычисляет CRC-32 IEEE. При NULL, нулевом размере или размере больше `isize::MAX` возвращает `EFI_INVALID_PARAMETER` и сохраняет выходное значение. Вызывающий обеспечивает валидный читаемый диапазон и выровненный выходной `u32`, доступный для записи. |
| `CopyMem` | Копирует байты с поддержкой перекрытия в обоих направлениях. |
| `SetMem` | Заполняет ровно указанный диапазон одним байтом. |

Указатели реализованных сервисов имеют сигнатуры `extern "efiapi"`. Гостевая проверка
читает их из самой таблицы. Таблицы пока доступны только внутренней
диагностике. Публикация образам требует заполнения остальных слотов по
контрактам соответствующих сервисов.
[UEFI 2.11, §7.5](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#miscellaneous-boot-services).

### Сервисы памяти

В диагностической Boot Services подключены ещё пять функций. BSP передаёт
постоянно живущие буферы карты и признаков владения одному аллокатору.
Проверка повторного входа предшествует эксклюзивному доступу к аллокатору.
Сервисы возвращают `EFI_NOT_READY` до его инициализации и при повторном
входе в занятую секцию. Сервисы памяти не вызывают события внутри секции.

| Boot Service | Поведение диагностической реализации |
|---|---|
| `AllocatePages` | Поддерживает `AnyPages`, `MaxAddress` и `Address`. Записывает адрес при успехе. Отсутствие подходящего адресного диапазона при `Address` или `MaxAddress` даёт `EFI_NOT_FOUND`, нехватка памяти при `AnyPages` или места в карте даёт `EFI_OUT_OF_RESOURCES`. |
| `FreePages` | Освобождает только страницы из `AllocatePages`. Невыровненный адрес или недопустимое число страниц дают `EFI_INVALID_PARAMETER`, отсутствие владения даёт `EFI_NOT_FOUND`. |
| `GetMemoryMap` | Возвращает согласованный снимок без выделения памяти. При `EFI_BUFFER_TOO_SMALL` записывает нужный размер в байтах и запрошенные размер и версию дескриптора. Буфер карты и `MapKey` сохраняются. При достаточном размере NULL-буфер карты даёт `EFI_INVALID_PARAMETER`. Запрошенный `MapKey` выдаётся при успешном снимке. |
| `AllocatePool` | Выделяет выровненный на 8 байт блок и записывает указатель при успехе. |
| `FreePool` | Освобождает блок по точному указателю `AllocatePool`. NULL, смещённый и уже освобождённый указатели дают `EFI_INVALID_PARAMETER`. |

`GetMemoryMap` допускает NULL для необязательных для вызывающего выходов
`MapKey`, `DescriptorSize` и `DescriptorVersion`. При успешной выдаче
дескрипторы занимают ровно возвращённый размер. Оба аллокатора сохраняют
пользовательские типы `0x70000000…0xffffffff` в поле Type. Типы Reserved,
MMIO, Persistent и Unaccepted отклоняются на входе в сервисы выделения.
Числа в диапазоне `16…0x6fffffff` также дают `EFI_INVALID_PARAMETER`.
Если диапазон занят, выбор свободной памяти пропускает его даже с типом
Conventional. Запрос больше физической ёмкости профиля возвращает
`EFI_OUT_OF_RESOURCES` без изменения карты или выходного указателя.
[UEFI 2.11, §7.2](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#memory-allocation-services).

### База протоколов

Внутренняя база BSP хранит до 128 привязок `(EFI_HANDLE, EFI_GUID)`. GUID
хранится по значению. Указатель на интерфейс предоставляется вызывающим и
остаётся в его владении. NULL-указатель допускается для маркирующего
протокола. Идентификатор handle выдаётся один раз за запуск. После удаления
последней привязки этого handle база перестаёт его принимать.

| Boot Service | Поведение диагностической реализации |
|---|---|
| `InstallProtocolInterface` | С `EFI_NATIVE_INTERFACE` создаёт handle при NULL на входе или добавляет GUID к существующему handle. Дубликат GUID на том же handle даёт `EFI_INVALID_PARAMETER`. Исчерпание записей даёт `EFI_OUT_OF_RESOURCES`. |
| `ReinstallProtocolInterface` | Сверяет прежний указатель и заменяет его на новый с сохранением handle. |
| `UninstallProtocolInterface` | Удаляет запись после сверки указателя. Отсутствующая привязка даёт `EFI_NOT_FOUND`. |
| `HandleProtocol` | Ищет GUID на указанном действующем handle. При отсутствии GUID возвращает `EFI_UNSUPPORTED` и записывает NULL. |
| `LocateProtocol` | При NULL в `Registration` возвращает первую найденную привязку GUID. При отсутствии привязки возвращает `EFI_NOT_FOUND` и записывает NULL. |

Эти операции используют ту же эксклюзивную секцию BSP, что сервисы памяти.
Запись в базе протоколов обходится без выделения памяти и сохраняет
`MapKey`. Списки открытий, поиск массивов handles и уведомления идут
отдельными срезами S7-05.
[UEFI 2.11, §7.3](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#protocol-handler-services).

Редакция 2.11 задаёт для x64 при вызове EFI-образа `FCW = 0x037f` и
`MXCSR = 0x1f80`. Загрузка образа с этим состоянием CPU проверяется при
реализации пути вызова EFI-образа. [UEFI 2.11, §2.3.4](https://uefi.org/specs/UEFI/2.11/02_Overview.html#x64-platforms).

## Начальная карта памяти

После установки собственных CR3 и RSP прошивка преобразует отсортированные
регионы handoff в массив `EFI_MEMORY_DESCRIPTOR` версии 1. Размер записи
на x64 — 40 байт, выравнивание — 8 байт. Поля PhysicalStart, VirtualStart,
NumberOfPages и Attribute начинаются со смещений 8, 16, 24 и 32.
VirtualStart и четырёхбайтовый отступ после Type равны нулю. Начальный MapKey
равен 1. [UEFI 2.11, §7.2.3](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#efi-boot-services-getmemorymap).

Проекция типов задана контрактом handoff. Старые таблицы машины становятся
`EfiConventionalMemory` после переключения CR3. Новые таблицы и оба стека
занимают `EfiBootServicesData`, guard занимает одну страницу
`EfiReservedMemoryType`. Код shadow получает `EfiBootServicesCode`, а
`.rodata` и данные — `EfiBootServicesData` с разрезом по границам линкера.
Дыры между регионами не описываются. [FIRMWARE_BOOT, §6.2](FIRMWARE_BOOT.md#62-таблица-регионов-запись-32-байта).

| Область | Attribute |
|---|---|
| RAM, включая занятые области прошивки, handoff и ACPI | `EFI_MEMORY_WB` |
| ROM, MMIO и framebuffer | `EFI_MEMORY_UC` |
| Окно NVRAM | `EFI_MEMORY_UC` и `EFI_MEMORY_RUNTIME` |
| Guard и прочие reserved-области | 0 |

Атрибуты в записи описывают возможности региона. Текущие права R/W и NX
задаются таблицами страниц. Номер экрана из handoff не используется как
EFI-атрибут. С S7-05 буфер записей находится в статических данных
прошивки, уже отмеченных как `EfiBootServicesData`. При нехватке буфера построитель сообщает требуемое
число записей до записи в буфер.

ROM выводит в COM1 MapKey, версию и число записей, затем Type, PhysicalStart,
NumberOfPages и Attribute каждой записи. Та же карта доступна через
диагностический `GetMemoryMap`. [Проверки этапа 7](../reports/STAGE_7_REPORT.md#s7-04--начальная-карта-памяти-uefi).

## Выделение страниц

Внутренний аллокатор принимает количество страниц и режим `AnyPages`,
`MaxAddress` или `Address`. В режиме `Address` начало выровнено на 4 КиБ.
`AnyPages` выбирает самый высокий подходящий диапазон в conventional RAM,
а `MaxAddress` дополнительно ограничивает адрес последнего байта включительно.
Для выделения подходят только полностью покрытые диапазоны `EfiConventionalMemory`
ниже предела 36-битных физических адресов. Типы RuntimeServices получают
`EFI_MEMORY_RUNTIME`. Тип Code описывает назначение записи, действующие
права страниц задаёт текущая таблица PTE.

Аллокатор хранит признаки владения отдельно от EFI-дескрипторов.
`FreePages` принимает только страницы, ранее выделенные этим аллокатором,
и поддерживает освобождение части диапазона и соседних выделений. При
возврате восстанавливается `EfiConventionalMemory` с атрибутом WB.
Пересечение с занятыми при старте диапазонами или повторное освобождение
отклоняется. Совместимые соседние записи объединяются. Успешная операция
увеличивает `MapKey` ровно на единицу. При нехватке записей, переполнении
ключа или недопустимом диапазоне карта и ключ сохраняются.

Ёмкость буфера задаёт вызывающий код. Для начального профиля вся conventional
RAM имеет атрибут WB. Сервисы памяти используют этот же ключ и буфер. [UEFI 2.11, §7.2.1–2](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#memory-allocation-services).

## Выделение pool

Каждый блок pool занимает целое число смежных страниц. Заголовок начинается
на 8 байт выше начала диапазона, данные — на 40 байт выше начала. Такой
формат даёт требуемое 8-байтовое выравнивание и допускает размещение
в физической странице 0. Запрос нулевого размера получает освобождаемый
блок с местом минимум для одного байта.

Карта различает владение pool и обычными страницами. Соседние блоки pool
сохраняют отдельные записи. `FreePool` сверяет точный указатель и владение
по карте, затем проверяет заголовок. Границы возвращаемого диапазона берутся
из карты. Смещённый, чужой или уже освобождённый указатель отклоняется до
обращения к заголовку. `FreePages` отклоняет диапазон, принадлежащий pool.
Успешное выделение или освобождение увеличивает общий `MapKey` на единицу.

Профиль использует минимум одну страницу на блок. Гостевой доступ к заголовку
опирается на identity-map доступной для записи RAM. [UEFI 2.11, §7.2.4–5](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#efi-boot-services-allocatepool).
