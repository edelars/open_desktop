# Поддержанный профиль UEFI

## Подготовленный установочный диск

`od-image-tool import-install-media <image.iso> <out.raw>` переносит
каталоги и файлы ISO-9660 Level 1 или UDF 1.02 в GPT/FAT32.
Проверенный официальный Windows ISO сохраняет загрузочные файлы,
а большой `sources/install.wim` преобразуется в комплект SWM.
Прошивка читает результат через обычный NVMe Block I/O с секторами
512 байт. Системная проверка собирает ISO и UDF из собственного
EFI-приложения и подтверждает его запуск по `EFI/BOOT/BOOTX64.EFI`.
[Команда проверки](../../tests/system/firmware_install_media_smoke.py), [ADR-0012](../decisions/ADR-0012-install-media-transport.md).

## Таблицы UEFI и Boot Services

Внутренняя диагностика строит в RAM три таблицы UEFI x64. Размеры
`EFI_SYSTEM_TABLE`, `EFI_BOOT_SERVICES` и `EFI_RUNTIME_SERVICES` составляют
120, 376 и 136 байт. У каждой таблицы 24-байтовый заголовок, редакция
`0x0002006e` и CRC-32 IEEE по `HeaderSize` байтам с обнулённым полем CRC
при расчёте. System Table ссылается на обе таблицы сервисов и имя производителя
`Open Desktop` в UTF-16. Слот `Reserved` у Boot Services равен NULL.
[UEFI 2.11, §4](https://uefi.org/specs/UEFI/2.11/04_EFI_System_Table.html).

| Boot Service | Поведение диагностической реализации |
|---|---|
| `CalculateCrc32` | Вычисляет CRC-32 IEEE. При NULL, нулевом размере или размере больше `isize::MAX` возвращает `EFI_INVALID_PARAMETER` и сохраняет выходное значение. Вызывающий обеспечивает валидный читаемый диапазон и выровненный выходной `u32`, доступный для записи. |
| `CopyMem` | Копирует байты с поддержкой перекрытия в обоих направлениях. |
| `SetMem` | Заполняет ровно указанный диапазон одним байтом. |

Все 43 слота сервисов Boot Services имеют собственные сигнатуры
`extern "efiapi"`. Гостевая проверка читает указатели из самой таблицы.
Эти таблицы используются внутренней диагностикой. Первую передачу System
Table загруженному EFI-образу проверяет S7-06.
[UEFI 2.11, §7.5](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#miscellaneous-boot-services).

### Сервисы загрузки образов и монотонного счётчика

| Boot Service | Поддержанный профиль |
|---|---|
| `LoadImage` | Загружает PE32+ из буфера или по Device Path встроенного FV с известным parent handle. При наличии буфера использует его байты, а путь служит источником метаданных. Отсутствие источника и пути либо файла FV даёт `EFI_NOT_FOUND`. Повреждённый путь даёт `EFI_INVALID_PARAMETER`, повреждённый PE даёт `EFI_LOAD_ERROR`, неподдержанный тип даёт `EFI_UNSUPPORTED`. При ошибке сохраняет выход. |
| `StartImage` | Один раз вызывает точку входа загруженного образа при `TPL_APPLICATION`. До возврата вызывает `ConnectController` с `Recursive=TRUE` для новых и изменённых handles, оставшихся в базе. Возвращает статус точки входа или `Exit` и передаёт запрошенный `ExitData`. Ошибочный handle, повторный запуск или неверный TPL дают `EFI_INVALID_PARAMETER`. |
| `Exit` | Для текущего запущенного образа передаёт управление в `StartImage`. Для незапущенного образа освобождает его через `UnloadImage`. При ошибочном handle возвращает `EFI_INVALID_PARAMETER`. |
| `UnloadImage` | При TPL до `TPL_CALLBACK` освобождает страницы незапущенного или завершённого выгружаемого образа, возвращает RW/NX и снимает регистрацию. Для резидентного драйвера вызывает текущий `LoadedImage.Unload` на отдельном стеке, освобождает образ при `EFI_SUCCESS` и передаёт другие статусы с сохранением образа. NULL callback даёт `EFI_UNSUPPORTED`. При удержании протокола другим драйвером или повторной выгрузке активного образа возвращает `EFI_ACCESS_DENIED`. |
| `GetNextMonotonicCount` | NULL выход даёт `EFI_INVALID_PARAMETER`. Без энергонезависимой старшей части счётчика сервис возвращает `EFI_DEVICE_ERROR` и сохраняет выход. |

[UEFI 2.11, §§7.4 и 7.5.5](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#image-services).

Loaded Image Device Path содержит собственную копию всего входного пути.
`LoadedImage.DeviceHandle` указывает на устройство совпавшего
экземпляра, а `FilePath` хранит независимую копию его оставшихся узлов
с маркером `End Entire`. При загрузке из буфера без совпавшего
устройства эти два поля равны NULL. NULL входного пути даёт NULL
интерфейс Loaded Image Device Path. Поля пути лежат на RO/NX страницах
после округлённого конца PE. `ImageSize` содержит размер PE, а частная
запись хранит полный размер выделения для выгрузки.
[UEFI 2.11, §9](https://uefi.org/specs/UEFI/2.11/09_Protocols_EFI_Loaded_Image.html).

Встроенный FV публикует Device Path и `EFI_LOAD_FILE_PROTOCOL` на
одном handle. Путь устройства содержит Media Vendor с GUID
`369ec96f-b0dd-4a8e-bbcb-a60a59915839`. Один Media File Path задаёт
точное имя файла архива в UTF-16LE с начальным `\` и завершающим NUL.
Оба значения BootPolicy используют один поиск по точному имени.
`LoadFile` сообщает требуемый размер при NULL или коротком буфере
через `EFI_BUFFER_TOO_SMALL` без копирования. При загрузке без буфера
прошивка пробует экземпляры пути по порядку и читает содержимое через
общий поиск собственного провайдера FV.
[UEFI 2.11, §13.1](https://uefi.org/specs/UEFI/2.11/13_Protocols_Media_Access.html#load-file-protocol).

### Формат образов PE32+

Общий парсер `od-uefi-security::pe` принимает PE32+ для COFF machine `0x8664` и подсистем
EFI Application (10), Boot Service Driver (11) и Runtime Driver (12).
Профиль ограничен 96 секциями и размером отображённого образа до 2 ГиБ.
Размер optional header определяет начало таблицы секций, а число
каталогов ограничено доступными записями внутри этого заголовка.

Прошивка использует этот парсер для загрузки и вычисления Authenticode SHA-256.
Декодер `WIN_CERTIFICATE` ограничивает каждую запись объявленным диапазоном,
проверяет выравнивание следующих записей и нули за объявленной длиной.
Нули, включённые в `dwLength`, остаются частью поля данных для проверки границы DER.
[Microsoft PE Format](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format#the-attribute-certificate-table-image-only).

Файловый диапазон секции отделён от отображаемого. Область секции в
образе покрывает максимум из VirtualSize и SizeOfRawData. BSS задаёт
виртуальный размер без файловых байтов. Пересечения секций с
заголовками и между секциями отклоняются. При SectionAlignment меньше
4 КиБ FileAlignment должен совпадать с ним, а raw offset секции с
данными — с её RVA. Профиль принимает FileAlignment степенью двойки
от 512 байт до 64 КиБ.

Каталог base relocations должен лежать в файловых байтах одной
отображаемой секции. Security описывает выровненный на восемь байт
диапазон файла вне заголовков и raw-данных секций. Другие каталоги
остаются непрозрачными для парсера.
[Microsoft PE Format, редакция от 2026-09-10](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format).

`pe::load_into` отображает образ в переданный буфер по заданному адресу,
выровненному по большему из SectionAlignment и 4 КиБ. До записи он
проверяет вместимость, адресный диапазон и весь каталог base relocations,
затем обнуляет SizeOfImage,
копирует заголовки и raw-данные секций, затем возвращает адрес точки
входа. При отсутствии каталога требуется предпочитаемый ImageBase.
Флаг RELOCS_STRIPPED с непустым каталогом отклоняется. У блоков
проверяются границы, выравнивание и страничный RVA. Записи DIR64
прибавляют разность баз по модулю 2⁶⁴, ABSOLUTE пропускаются, остальные
типы, включая HIGHLOW, отклоняются. Каталог читается из исходного файла,
поэтому записи применяются в порядке таблицы даже при ссылках на сам
каталог.

`LoadImage` сначала пробует предпочитаемый ImageBase. При наличии
relocations загрузчик может выбрать другой выровненный диапазон.
Отсутствие подходящих страниц даёт `EFI_OUT_OF_RESOURCES`. Точка входа
должна находиться в исполняемой секции. До публикации образа загрузчик
копирует PE в RW/NX страницы и применяет права секций к существующим
4 КиБ identity mappings. Заголовки и зазоры получают RO/NX. Для страниц,
которые делят несколько секций, права записи и исполнения объединяются.
Обновление RW/NX сохраняет физические адреса, биты A/D и перечитывает CR3.
В карте UEFI executable-страницы имеют тип Code, остальные Data
соответствующей подсистемы. Страницы принадлежат загрузчику.
`FreePages` отклоняет их освобождение.

Успешная загрузка публикует `EFI_LOADED_IMAGE_PROTOCOL` и
`EFI_LOADED_IMAGE_DEVICE_PATH_PROTOCOL` с NULL interface для буфера без
пути. Уведомления о протоколах получают готовый handle после завершения
изменений карты и прав страниц.
[UEFI 2.11 §9](https://uefi.org/specs/UEFI/2.11/09_Protocols_EFI_Loaded_Image.html).

Вызов EFI использует отдельный стек 256 КиБ `EfiBootServicesData` с
неотображённой guard-страницей. Шлюз передаёт handle и System Table по
Microsoft x64 ABI и восстанавливает стек, флаги и FP-состояние вызывающего
при возврате или `Exit`. Вложенный вызов меняет активный handle для
`ExitBootServices` до завершения дочерней точки входа.

Если образ передаёт `ExitData` при ненулевом статусе, указатель должен
указывать на действующий буфер `AllocatePool` с завершающим нулём в части
`CHAR16`. После строки допускается
бинарный хвост. `StartImage` передаёт буфер вызывающему для `FreePool`.
Если указатель выхода NULL, прошивка освобождает буфер и сохраняет
выходной размер. Приложение освобождается при завершении. Драйвер с
успешным статусом или предупреждением остаётся резидентным.
[Состояние процессора при EFI-вызове](FIRMWARE_BOOT.md#7-решение-2-состояние-при-вызове-efi-образа).

### Дайджест Authenticode

S7-06 вычисляет SHA-256 образа из проверенного `PeImage`. Из заголовков
исключаются CheckSum и объявленная запись Security. Секции с файловыми
данными хешируются целиком по возрастанию PointerToRawData, включая raw
padding. Хвост начинается на файловом смещении
`SizeOfHeaders + сумма SizeOfRawData` даже при зазорах между секциями.
Сертификат исключается, когда его диапазон заканчивается на конце файла.
Другое положение сертификата возвращает `CertificateNotAtEnd`. Проверка
PKCS#7, цепочки и политики загрузки относится к S7-24.
[Windows Authenticode Portable Executable Signature Format, v1.0 от 2008-03-21](https://download.microsoft.com/download/9/c/5/9c5b2167-8017-4bae-9fde-d599bac8184a/Authenticode_PE.docx).

### Встроенный архив FV

Собственный архив версии 1 расположен в read-only части ROM. Поля
многобайтовых чисел записаны в little endian. Заголовок занимает 24 байта.

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 8 | `ODFVARC\0` |
| 8 | 2 | Версия `1` |
| 10 | 2 | Размер заголовка `24` |
| 12 | 4 | Полный размер архива |
| 16 | 4 | Число записей |
| 20 | 4 | IEEE CRC-32 всего архива с нулями в этом поле |

Затем идут записи без padding. У каждой сначала `u16` длины имени,
нулевой `u16` и `u32` длины данных, затем байты имени и данные.
Имя содержит 1–63 ASCII-байта из `[a-z0-9._-]`. Имена `.` и `..`
запрещены. Записи строго упорядочены по байтам имени, данные непустые,
последняя запись заканчивается вместе с архивом. Допускается пустой архив.

`build_firmware.py --with-test-apps` помещает в архив `ebs`, `echo`, `hello` и `vars`,
собранные из `firmware/uefi/tests/apps` с target `x86_64-unknown-uefi`.
`hello` читает Loaded Image через `HandleProtocol`. `ebs` читает карту,
передаёт её ключ в `ExitBootServices` и при успехе выводит `!` прямым
`OUT` в COM1 перед `HLT`. `echo` читает `ConIn` через `WaitForKey` и
отображает символы и названия стрелок в `ConOut` до перевода строки.
`vars` проверяет четыре [сервиса переменных](#переменные).
Приложения выводят начальную строку через `ConOut`.
[UEFI 2.11 §9.1](https://uefi.org/specs/UEFI/2.11/09_Protocols_EFI_Loaded_Image.html), [§12.4](https://uefi.org/specs/UEFI/2.11/12_Protocols_Console_Support.html).

### Runtime Services

Основной ROM запускает встроенный PE32+ Runtime Driver через `LoadImage`
и `StartImage`. Драйвер публикует 14 слотов UEFI x64 и маску доступных
сервисов в `EFI_RT_PROPERTIES_TABLE`. Система после `ExitBootServices`
может использовать физические адреса или один раз вызвать
`SetVirtualAddressMap`. Карта должна содержать отображение каждого
runtime-дескриптора из последней карты Boot Services. Драйвер проверяет
версию, шаг массива, отсутствие коллизий и каноничность адресов. Затем он
сигналит события смены адресов, применяет PE fixup, обновляет указатели
и пересчитывает CRC обеих таблиц. `ConvertPointer` работает внутри
уведомлений, а `EFI_OPTIONAL_PTR` разрешает NULL.
[Контракт памяти](FIRMWARE_BOOT.md#9-решение-4-перемещение-rt-части-после-setvirtualaddressmap), [UEFI 2.11, §8.4](https://uefi.org/specs/UEFI/2.11/08_Services_Runtime_Services.html#virtual-memory-services).

`GetTime` и `SetTime` обращаются к RTC/CMOS через порты `0x70/0x71`,
поддерживают календарь с 1900 по 9999 год и учитывают текущий BCD или
двоичный формат, 12- или 24-часовой режим. Разрешение равно одной секунде.
`SetTime` сбрасывает её дробную часть. TimeZone и Daylight остаются в
runtime-памяти текущей загрузки. RTC отсутствует в базовой конфигурации
платы. `GetWakeupTime`, `SetWakeupTime`, `UpdateCapsule` и
`QueryCapsuleCapabilities` возвращают `EFI_UNSUPPORTED`.
[UEFI 2.11, §8.3](https://uefi.org/specs/UEFI/2.11/08_Services_Runtime_Services.html#time-services).

При наличии ACPI fixed hardware `ResetSystem` выполняет аппаратный
запрос. Cold, Warm и PlatformSpecific используют ACPI reset-регистр.
Плата применяет Cold для Warm и для любого PlatformSpecific GUID,
поскольку собственных GUID сброса у неё нет. Shutdown пишет тип S5 и
`SLP_EN` в PM1a_CNT. Если описание PM-блока содержит нулевые reset
register и reset value, FADT скрывает возможность reset, а `ResetSystem`
использует S5. При отсутствии PM-блока или возврате из аппаратного
действия сервис печатает причину и код 0x22 на COM1, затем останавливается
в HLT. [Коды останова прошивки](FIRMWARE_BOOT.md#12-останов-коды-состояния-и-сброс).

`GetNextHighMonotonicCount` увеличивает старшее слово счётчика после
`ExitBootServices`. Прошивка также увеличивает его при загрузке и
переносе из младшего слова Boot Services. Старшее слово записывается в
защищённую переменную `ODMonotonicHigh` до возврата нового значения.
Сервис требует подключённого NVRAM. При сбое записи он возвращает
`EFI_DEVICE_ERROR`. [UEFI 2.11, §8.5](https://uefi.org/specs/UEFI/2.11/08_Services_Runtime_Services.html#miscellaneous-runtime-services).

### Конфигурационные таблицы

`InstallConfigurationTable` добавляет или заменяет запись GUID,
а с NULL-указателем удаляет её. NULL GUID даёт `EFI_INVALID_PARAMETER`,
удаление отсутствующей записи даёт `EFI_NOT_FOUND`. В массиве помещаются
32 записи. При исчерпании памяти или мест для новой записи возвращается
`EFI_OUT_OF_RESOURCES`. Адрес и жизненный цикл содержимого отдельной
таблицы определяет вызывающий.

Массив пар GUID и указателей создаётся при первой вставке в pool
`EfiRuntimeServicesData`. Блок переиспользуется после удаления всех
записей. Его выделение обновляет `MapKey`, последующие правки массива
сохраняют его. При пустом массиве System Table содержит нулевой счётчик
и NULL-указатель. При успешном изменении Boot Services публикует
указатель, счётчик и CRC System Table. Затем она доставляет
уведомления из группы с GUID таблицы по правилам TPL.
[UEFI 2.11, §7.5.6](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#efi-boot-services-installconfigurationtable).

### Сервисы памяти

В диагностической Boot Services подключены ещё пять функций. BSP передаёт
постоянно живущие буферы карты и признаков владения одному аллокатору.
Проверка повторного входа предшествует эксклюзивному доступу к аллокатору.
Сервисы возвращают `EFI_NOT_READY` до его инициализации и при повторном
входе в занятую секцию. Сервисы памяти не вызывают события внутри секции.

| Boot Service | Поведение диагностической реализации |
|---|---|
| `AllocatePages` | Поддерживает `AnyPages`, `MaxAddress` и `Address`. Записывает адрес при успехе. Отсутствие подходящего адресного диапазона при `Address` или `MaxAddress` даёт `EFI_NOT_FOUND`, нехватка памяти при `AnyPages` или места в карте даёт `EFI_OUT_OF_RESOURCES`. |
| `FreePages` | Освобождает только страницы из `AllocatePages`. Невыровненный адрес или недопустимое число страниц дают `EFI_INVALID_PARAMETER`, отсутствие владения даёт `EFI_NOT_FOUND`. |
| `GetMemoryMap` | Возвращает согласованный снимок без выделения памяти. При `EFI_BUFFER_TOO_SMALL` записывает нужный размер в байтах и запрошенные размер и версию дескриптора. Буфер карты и `MapKey` сохраняются. При достаточном размере NULL-буфер карты даёт `EFI_INVALID_PARAMETER`. Запрошенный `MapKey` выдаётся при успешном снимке. |
| `AllocatePool` | Выделяет выровненный на 8 байт блок и записывает указатель при успехе. |
| `FreePool` | Освобождает блок по точному указателю `AllocatePool`. NULL, смещённый и уже освобождённый указатели дают `EFI_INVALID_PARAMETER`. |

`GetMemoryMap` допускает NULL для необязательных для вызывающего выходов
`MapKey`, `DescriptorSize` и `DescriptorVersion`. При успешной выдаче
дескрипторы занимают ровно возвращённый размер. Оба аллокатора сохраняют
пользовательские типы `0x70000000…0xffffffff` в поле Type. Типы Reserved,
MMIO, Persistent и Unaccepted отклоняются на входе в сервисы выделения.
Числа в диапазоне `16…0x6fffffff` также дают `EFI_INVALID_PARAMETER`.
Если диапазон занят, выбор свободной памяти пропускает его даже с типом
Conventional. Запрос больше физической ёмкости профиля возвращает
`EFI_OUT_OF_RESOURCES` без изменения карты или выходного указателя.
[UEFI 2.11, §7.2](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#memory-allocation-services).

### База протоколов

Внутренняя база BSP хранит до 128 привязок `(EFI_HANDLE, EFI_GUID)`. GUID
хранится по значению. Указатель на интерфейс предоставляется вызывающим и
остаётся в его владении. NULL-указатель допускается для маркирующего
протокола. Идентификатор handle выдаётся один раз за запуск. После удаления
последней привязки этого handle база перестаёт его принимать.

| Boot Service | Поведение диагностической реализации |
|---|---|
| `InstallProtocolInterface` | С `EFI_NATIVE_INTERFACE` создаёт handle при NULL на входе или добавляет GUID к существующему handle. Дубликат GUID на том же handle даёт `EFI_INVALID_PARAMETER`. Исчерпание записей даёт `EFI_OUT_OF_RESOURCES`. |
| `ReinstallProtocolInterface` | Сверяет прежний указатель и заменяет его на новый с сохранением handle. |
| `UninstallProtocolInterface` | Удаляет запись после сверки указателя. На действующем handle отсутствие привязки или несовпадение указателя даёт `EFI_NOT_FOUND`. |
| `HandleProtocol` | Ищет GUID на указанном действующем handle. При отсутствии GUID возвращает `EFI_UNSUPPORTED` и записывает NULL. |
| `LocateProtocol` | При NULL в `Registration` возвращает первую найденную привязку GUID. С ключом регистрации возвращает следующий интерфейс для этого GUID. При отсутствии привязки возвращает `EFI_NOT_FOUND` и записывает NULL. |
| `OpenProtocol` | Поддерживает `BY_HANDLE_PROTOCOL`, `GET_PROTOCOL`, `TEST_PROTOCOL` и `BY_DRIVER`. Повторный `BY_DRIVER` того же агента даёт `EFI_ALREADY_STARTED` с указателем интерфейса. Другой драйвер получает `EFI_ACCESS_DENIED` с неизменённым выходом. Для `TEST_PROTOCOL` выход указателя игнорируется. |
| `CloseProtocol` | Удаляет все записи указанной пары agent/controller для выбранной привязки. При отсутствии записей возвращает `EFI_NOT_FOUND`. |
| `RegisterProtocolNotify` | Связывает GUID с действующим событием и выдаёт ключ поиска. Одно событие может обслуживать несколько регистраций. |
| `LocateHandle` | Перечисляет уникальные handles в режимах `AllHandles` и `ByProtocol`. В режиме `ByRegisterNotify` выдаёт один следующий handle. Малый буфер даёт `EFI_BUFFER_TOO_SMALL` с требуемым размером в байтах. Пустой результат даёт `EFI_NOT_FOUND`. |
| `LocateDevicePath` | Выбирает handle, который предоставляет запрошенный протокол и имеет самый длинный совпавший префикс Device Path. Указатель продвигается на целые совпавшие узлы. При полном совпадении он остаётся на маркере End. |
| `LocateHandleBuffer` | Выполняет тот же поиск и возвращает выделенный из pool массив handles и число элементов. |
| `ProtocolsPerHandle` | Возвращает массив указателей на копии GUID для действующего handle. Указатели и GUID живут в одном блоке pool. |
| `OpenProtocolInformation` | Возвращает массив 24-байтовых записей с agent, controller, режимом и счётчиком. Для существующей привязки без открытий выдаёт освобождаемый блок с нулевым числом элементов. |
| `InstallMultipleProtocolInterfaces` | Принимает список пар GUID и указателей с завершителем NULL GUID. Сначала проверяет весь пакет, затем устанавливает привязки на один handle. Повтор полного Device Path даёт `EFI_ALREADY_STARTED`. |
| `UninstallMultipleProtocolInterfaces` | Сверяет весь пакет указателей и открытий перед удалением. Любая ошибка даёт `EFI_INVALID_PARAMETER` с сохранением базы и её записей открытий. |
| `ConnectController` | Профиль базы протоколов без Driver Binding возвращает `EFI_NOT_FOUND` для действующего контроллера и `EFI_INVALID_PARAMETER` для NULL или неизвестного handle. |
| `DisconnectController` | Проверяет controller и ненулевой child handle. Ненулевой driver handle даёт `EFI_INVALID_PARAMETER`: диагностический профиль не публикует образы с Driver Binding. Без подходящих открытий `BY_DRIVER` возвращает `EFI_SUCCESS`. При открытии, которое потребовало бы вызова Stop, возвращает `EFI_DEVICE_ERROR` и сохраняет привязку и запись открытия. |

Таблица открытий вмещает до 128 записей, с отдельным счётчиком для
совпадающих handle, GUID, agent, controller и режима. Для `BY_DRIVER`
требуются существующие agent и controller. Для остальных поддержанных
режимов запись сохраняется при переданном agent. Только открытие
`BY_DRIVER` блокирует удаление и переустановку. После закрытия владельцем
остальные записи не препятствуют этим операциям. Успешная переустановка
или удаление снимает их. Режимы `BY_CHILD_CONTROLLER`, `EXCLUSIVE` и
`BY_DRIVER | EXCLUSIVE` возвращают `EFI_UNSUPPORTED`.

Эти операции используют ту же эксклюзивную секцию BSP, что сервисы памяти.
Запись в базе протоколов обходится без выделения памяти и сохраняет
`MapKey`. Блоки результатов выдаются из текущего аллокатора и освобождаются
вызывающим через `FreePool`.

База вмещает 64 регистрации. Ключи действительны до `CloseEvent`
и имеют независимые позиции поиска. Курсор продвигается только после
успешной выдачи результата. Поиск перебирает действующие привязки
по возрастанию ревизии установки или переустановки. Существующие
привязки доступны сразу после регистрации. Повторная переустановка
до чтения оставляет в выдаче последнюю ревизию данной привязки.
Успешная одиночная установка, переустановка и пакетная установка
сигналят соответствующие события после публикации привязок и выходных
параметров. Уведомления исполняются после освобождения доступа к состоянию
BSP. Закрытие события отзывает все его ключи. Вызов поиска с отозванным
ключом возвращает `EFI_INVALID_PARAMETER`.
[UEFI 2.11, §7.3](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#protocol-handler-services).

Пакет ограничен 128 парами. NULL указатель интерфейса обозначает маркер.
NULL GUID завершает список. Пустой пакет установки не создаёт handle.
Пустое удаление успешно для действующего handle. Ошибки установки
сохраняют входной handle и все привязки. Адаптер Win64 сохраняет
регистровые указатели в исходной области параметров и даёт обработчику
отдельную область сохранения регистров. Поэтому список продолжается
стековыми аргументами в исходном порядке.
[UEFI 2.11, §7.3.17–18](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#efi-boot-services-installmultipleprotocolinterfaces), [Microsoft x64 ABI](https://learn.microsoft.com/en-us/cpp/build/x64-calling-convention?view=msvc-170).

### Device Path

Узлы читаются как упакованные заголовки длиной четыре байта. Обход проверяет
длину, границы и маркеры End. Полезные данные обычных узлов сравниваются
как байты. При нескольких экземплярах поиск рассматривает
первый экземпляр входного пути и первый экземпляр зарегистрированного
кандидата. При равной длине выбирается первая встреченная привязка.
Повреждённый заголовок входного пути даёт `EFI_INVALID_PARAMETER`,
повреждённый зарегистрированный кандидат пропускается. Поиск без
совпадения возвращает `EFI_NOT_FOUND`. При ошибке входной указатель и
выходной handle сохраняются.

Профиль ограничивает обход 64 КиБ. Вызывающий обеспечивает доступность
памяти входного пути, а владелец установленного Device Path сохраняет
его буфер до снятия интерфейса. Указатели параметров ABI передают путь
переменной длины без отдельного поля размера. Пакетная установка сравнивает
пути до маркера End Entire включительно, учитывая все экземпляры.
Повреждённая структура нового или установленного пути приводит к
`EFI_INVALID_PARAMETER` при проверке пакета.
[UEFI 2.11, §7.3.8](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#efi-boot-services-locatedevicepath), [UEFI 2.11, §10.3.1](https://uefi.org/sites/default/files/resources/UEFI_Spec_Final_2.11.pdf).

Прошивка публикует `EFI_DEVICE_PATH_UTILITIES_PROTOCOL` на отдельном
handle. Доступны все восемь функций §10.5. Пути на входе и в результате
ограничены 64 КиБ. Копии и новые узлы выделяются в `BootServicesData`
и освобождаются вызывающим через `FreePool`. `GetNextDevicePathInstance`
возвращает отдельный экземпляр с `End Entire`, сохраняет входные байты
и продвигает указатель только после выделения. Пустой экземпляр
представлен четырёхбайтным `End Entire`. `CreateDeviceNode` обнуляет
полезные байты и записывает заголовок.
[UEFI 2.11, §10.5](https://uefi.org/specs/UEFI/2.11/10_Protocols_Device_Path_Protocol.html#device-path-utilities-protocol).

### GOP

При наличии записи дисплея прошивка проверяет принадлежащие ей регионы
регистров и framebuffer основного экрана. На отдельном handle она публикует
`EFI_GRAPHICS_OUTPUT_PROTOCOL`, аппаратный Memory Mapped Device Path
с включительными границами `0xFC00_0000` и `0xFC00_0FFF`, а также
`EFI_EDID_DISCOVERED_PROTOCOL` и `EFI_EDID_ACTIVE_PROTOCOL` с нулевой
длиной и указателем `NULL`. Начальный режим 0 соответствует 640×480.

`QueryMode` читает размеры из таблицы устройства и выделяет результат
в `BootServicesData`. Вызывающий освобождает его через `FreePool`.
Для номера вне таблицы `QueryMode` возвращает `EFI_INVALID_PARAMETER`,
а `SetMode` возвращает `EFI_UNSUPPORTED`. `SetMode` подтверждает размеры,
формат и stride по регистрам устройства, очищает видимую область в чёрный
и публикует кадр, в том числе при повторной установке текущего режима.
`PixelsPerScanLine` равен `STRIDE / 4`. `FrameBufferBase` равен базе
апертуры из регистров. `FrameBufferSize` охватывает `STRIDE × Height`
байт текущего режима в пределах ёмкости `FB_SIZE`.

`Blt` проверяет прямоугольники и смещения перед записью. Доступны
заливка, копирование с дисплея в буфер и обратно, а также копирование
между областями дисплея с учётом перекрытия. Для буфера с ненулевыми
координатами требуется байтовый `Delta`. `SetMode` и операции `Blt`,
которые пишут на дисплей, завершаются записью `FRAME_GENERATION`.

`ExitBootServices` оставляет активный режим и физический framebuffer
доступными ОС. В начальной карте UEFI его апертура имеет тип
`EfiMemoryMappedIO`, атрибут `EFI_MEMORY_UC` и доступна для отображения ОС
по `FrameBufferBase`. Сам GOP доступен до завершения Boot Services.
[UEFI 2.11, §12.9](https://uefi.org/specs/UEFI/2.11/12_Protocols_Console_Support.html#graphics-output-protocol),
[UEFI 2.11, §10.3.2.3](https://uefi.org/specs/UEFI/2.11/10_Protocols_Device_Path_Protocol.html#memory-mapped-device-path),
[DISPLAY_DEVICE.md, §11](DISPLAY_DEVICE.md#11-соответствие-uefi-gop).

### Хранилище

По записи NVMe `PRESENT` и её региону MMIO прошивка открывает регистры
`0xFC00_1000…0xFC00_2FFF`. Она инициализирует admin-очереди, выполняет
`Identify` и открывает одну пару очередей ввода-вывода. Команды завершаются
опросом очереди с ограниченным ожиданием через `Stall`. Буферы DMA и
очереди выделяются в `BootServicesData`. Обработчик `ExitBootServices`
выключает контроллер до освобождения этой памяти ОС. Прерывания в этом
профиле не требуются. [Контракт NVMe](NVME_DEVICE.md).

Путь контроллера начинается узлом Memory Mapped, а путь пространства имён
продолжает его узлом NVM Express Namespace c `NSID = 1`. На handle
пространства имён доступны `EFI_BLOCK_IO_PROTOCOL` ревизии 2 и
`EFI_DISK_IO_PROTOCOL`. Логические блоки имеют размер 512 байт. `IoAlign = 1`
разрешает невыравненные буферы. Disk I/O использует байтовые смещения.
Частичная запись блока читает исходный сектор, меняет указанные байты и
записывает сектор обратно. Адреса и длины проверяются до передачи.

Прошивка проверяет protective MBR, CRC заголовка и точной длины массива
записей GPT, расположение метаданных, границы разделов, пересечения и
уникальность GUID. Если основная GPT недействительна, прошивка проверяет
резервный заголовок в последнем LBA и его массив. Для каждого раздела
публикуется дочерний handle с Block I/O, Disk I/O, Partition Info, маркером
GUID типа и узлом Hard Drive. Узел сохраняет номер записи и уникальный GPT
GUID раздела. Записи с атрибутом No Block I/O проходят проверку геометрии
и исключаются из публикации дочерних устройств. `System` в Partition Info
обозначает раздел с GUID типа ESP. Если обе копии GPT повреждены, остаётся
handle пространства имён.
[UEFI 2.11, §5](https://uefi.org/specs/UEFI/2.11/05_GUID_Partition_Table_Format.html),
[§10](https://uefi.org/specs/UEFI/2.11/10_Protocols_Device_Path_Protocol.html),
[§13](https://uefi.org/specs/UEFI/2.11/13_Protocols_Media_Access.html).

### Файловая система

Simple File System ревизии 1 публикуется на handle системного раздела
GPT с распознанным FAT. Прошивка читает том через Disk I/O этого раздела.
Поддерживаются FAT12, FAT16 и FAT32, каталоги с фиксированным корнем
и с корнем в цепочке кластеров, короткие имена OEM CP437 и длинные
имена UCS-2. Поиск регистронезависимый. `Open` поддерживает абсолютные
и относительные пути, `.` и `..`. Границы тома, смещения и цепочки
проверяются при обращении. Отсутствующий путь даёт `EFI_NOT_FOUND`,
некорректная или циклическая цепочка — `EFI_VOLUME_CORRUPTED`.

File Protocol ревизии 1 читает файлы и перечисляет каталог по одной
записи. `GetInfo` возвращает `EFI_FILE_INFO` и `EFI_FILE_SYSTEM_INFO`,
включая размер тома, метку и число свободных байт по активной FAT.
Короткий буфер сообщает необходимый размер и сохраняет позицию.
Позиция чтения меняется после успешной операции. `SetPosition(0)`
перематывает каталог, позицию файла можно установить за его концом.
В конце файла `Read` возвращает ноль байт, чтение за концом даёт
`EFI_DEVICE_ERROR`. Операции с открытым файлом продвигают таймеры
Boot Services. Закрытие из уведомления откладывает освобождение
активного handle до завершения вызова.

Том доступен только для чтения. Открытие на запись или создание,
`Write`, `SetInfo` и `Flush` возвращают `EFI_WRITE_PROTECTED`.
`Delete` закрывает handle и возвращает `EFI_WARN_DELETE_FAILURE`.
Обновление FAT и метаданных и загрузка приложения с ESP выходят
за рамки S7-18. Нормативные источники — [Microsoft EFI FAT32 File System
Specification 1.03, 6 декабря 2000](https://download.microsoft.com/download/1/6/1/161ba512-40e2-4cc9-843a-923143f3456c/fatgen103.doc)
и [UEFI 2.11, §§13.3–13.6](https://uefi.org/specs/UEFI/2.11/13_Protocols_Media_Access.html).

### Boot manager

При обычной загрузке с опубликованным Block I/O прошивка пробует
`BootNext`, затем номера из `BootOrder`. `BootNext` удаляется до первого
запуска по этой переменной. Политика перебирает активные `Boot####`
обычной загрузочной категории. Числа в переменных кодируются little-endian,
описания опций хранятся в UCS-2. Поддерживаются полный Device Path, короткий путь к файлу
и короткий путь GPT Hard Drive. Сопоставление Hard Drive использует
номер и GUID раздела. Из списка путей `EFI_LOAD_OPTION` путь для
загрузки задаёт первый полный Device Path. Блок `OptionalData` после
всего списка копируется в `LoadOptions` образа. [UEFI 2.11, §§3.1–3.3](https://uefi.org/specs/UEFI/2.11/03_Boot_Manager.html).

Перед загрузкой опции устанавливается volatile-переменная `BootCurrent`.
Затем сигнализируются `ReadyToBoot` и `AfterReadyToBoot` в этом порядке.
Boot manager запускает только EFI-приложения. Watchdog запрашивается на
300 секунд и отключается при возврате. На плате без reset target
watchdog возвращает `EFI_UNSUPPORTED`, а загрузка продолжается. При
возврате приложения перебор продолжается независимо от статуса. В
профиле без клавиатуры и меню ожидания по `Timeout` нет.

После исчерпания списка прошивка ищет `\EFI\BOOT\BOOTX64.EFI` на ESP
фиксированного NVMe. Для обнаруженного раздела создаётся свободная
запись `Boot####` с полным путём и номер добавляется в `BootOrder`.
Сокращённые пути из существующих опций расширяются только на время
загрузки. Опции с прежними номерами и содержимым сохраняются. Если
никто не принял управление, COM1 сообщает `no bootable option`, затем
плата останавливается. Смена носителя и removable-media discovery
выходят за границы фиксированного NVMe-профиля.

`LoadImage` с `SourceBuffer = NULL` разрешает файловые узлы через
Simple File System, сохраняя фактический `DeviceHandle`, относительный
`FilePath` и копию полного пути на новом image handle. Запрос с
`SourceBuffer` использует переданные байты. Существующий Load File
обслуживает встроенный FV, `EFI_LOAD_FILE2_PROTOCOL` не используется.
На пути прямой загрузки прошивкой `LoadedImage.ParentHandle` равен NULL.
[UEFI 2.11, §7.4.1](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#efi-boot-services-loadimage), [§9](https://uefi.org/specs/UEFI/2.11/09_Protocols_EFI_Loaded_Image.html), [§10.3.5.4](https://uefi.org/specs/UEFI/2.11/10_Protocols_Device_Path_Protocol.html).

### Консоль COM1

Прошивка публикует `EFI_SIMPLE_TEXT_INPUT_PROTOCOL` и
`EFI_SIMPLE_TEXT_OUTPUT_PROTOCOL` на одном handle и пересчитывает CRC
System Table. `ConOut` и `StdErr` используют один интерфейс вывода.
Транспорт ввода до подключения USB-клавиатуры в S7-34 — COM1.
Текущий перечень консольных протоколов состоит из Simple Text Input
и Simple Text Output.

Вывод поддерживает режим 0 с 80 столбцами и 25 строками. Позиция
курсора, видимость, цвета и очистка передаются терминалу ANSI.
Поддерживаются печатная Basic Latin, Latin-1 `U+00A0…U+00FF` кроме
мягкого дефиса и графические символы UEFI. `OutputString` кодирует
доступные символы в UTF-8. Неподдержанный символ заменяется на `?` со
статусом `EFI_WARN_UNKNOWN_GLYPH`, а `TestString` для него возвращает
`EFI_UNSUPPORTED`. Ошибка передачи COM1 даёт `EFI_DEVICE_ERROR`.

Ввод декодирует тот же репертуар UTF-8 в CHAR16. Последовательности
ESC с `[` или `O` и суффиксом `A…D` дают четыре scan code стрелок.
Одиночный ESC выдаётся после двух срабатываний таймера опроса с
периодом 10 мс. Таймер и `WaitForKey` — отдельные события.
`WaitForKey` сигналится при готовом ключе. `ReadKeyStroke` продвигает
таймеры и возвращает `EFI_NOT_READY` при пустой очереди.
[UEFI 2.11, §12](https://uefi.org/specs/UEFI/2.11/12_Protocols_Console_Support.html).

### События и TPL

Диагностическая Boot Services поддерживает до 64 событий, включая
`EVT_NOTIFY_WAIT`, `EVT_NOTIFY_SIGNAL` и `EVT_TIMER`. `EVT_TIMER`
совместим с одним из двух типов уведомления. `CreateEventEx` принимает GUID
группы. `SignalEvent` меняет состояние всех её участников до первого
вызова уведомления. Повторный сигнал ожидающего в очереди события
объединяется с предыдущим. `CloseEvent` отменяет его место в очереди.
Идентификаторы закрытых событий считаются недействительными.

`CheckEvent` потребляет сигнал обычного события. При несигнальном
`EVT_NOTIFY_WAIT` она ставит уведомление в очередь и проверяет
состояние повторно после возможного вызова. Для `EVT_NOTIFY_SIGNAL`
проверка даёт `EFI_INVALID_PARAMETER`. `RaiseTPL` возвращает прежний
уровень, а `RestoreTPL` доставляет доступные уведомления. Поддержаны
уровни 4, 8, 16 и 31. Уведомления исполняются на 8 и 16, с более
высоким TPL первым и очередью FIFO внутри уровня.

Вызов уведомления выполняется после выхода из эксклюзивного доступа
к состоянию BSP. Callback на уровне 8 может синхронно породить
уведомление уровня 16. Уведомления равного или меньшего уровня ждут
снижения TPL. Callback может закрыть собственное событие. Доставленное
уведомление `EVT_NOTIFY_SIGNAL` потребляет состояние сигнала, и
последующий сигнал может снова поставить событие в очередь.
[UEFI 2.11, §7.1](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#event-timer-and-task-priority-services).

### Таймеры и ожидание

`SetTimer` поддерживает относительный и периодический таймер и отмену.
Период и срок округляются вверх из единиц 100 нс в такты по частоте
handoff. Нулевой интервал означает следующий такт TSC для одноразового
таймера и каждый такой такт для периодического. Новый периодический
срок отсчитывается от предыдущего, а несколько пропущенных периодов
дают один сигнал в текущем опросе. `CloseEvent` удаляет его срок.

`WaitForEvent` работает на `TPL_APPLICATION`. События проверяются в
порядке массива, и успешный вызов потребляет первый обнаруженный сигнал.
Для `EVT_NOTIFY_SIGNAL` функция возвращает `EFI_INVALID_PARAMETER` с
индексом. В ожидании вызываются уведомления `EVT_NOTIFY_WAIT`.
`Stall` принимает микросекунды, округляет длительность вверх
до такта и опрашивает таймеры до истечения срока.

В текущей реализации опрос происходит в `RaiseTPL`, `RestoreTPL`,
`SignalEvent`, `CheckEvent`, `SetTimer`, `WaitForEvent` и `Stall`.
`RaiseTPL` только ставит просроченные уведомления в очередь. Ожидания
проверяют TSC активно. Доставка привязана к этим точкам опроса и TPL.
Код EFI-приложения между ними выполняется без вызовов timer callback.
Это ограничение согласованной модели S7-02 для UEFI x64.
[Время и события](FIRMWARE_BOOT.md#8-решение-3-модель-таймеров-и-событий),
[UEFI 2.11, §7.1](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#event-timer-and-task-priority-services).

### Завершение Boot Services

`ExitBootServices` проверяет активный handle образа и TPL. Первая
попытка с допустимым handle на `TPL_APPLICATION` доставляет группу
`BEFORE_EXIT_BOOT_SERVICES`. Её обработчики могут изменить карту.
По возвращении из них сервис сравнивает `MapKey` с текущим ключом.
`EFI_INVALID_PARAMETER` при устаревшем ключе оставляет возможность
получить карту снова. Повтор со свежим ключом продолжает тот же
переход без вторичного уведомления BEFORE.

При совпадении ключа прошивка замораживает изменения карты, снимает
таймеры и ожидающие таймерные уведомления, затем доставляет группу
`EXIT_BOOT_SERVICES`. Специальный тип `EVT_SIGNAL_EXIT_BOOT_SERVICES`
в `CreateEvent` регистрирует в этой же группе. `Stall` продолжает
отмерять интервал по TSC, пока выполняется обработчик EXIT. После уведомлений
обнуляются три пары console handle и interface и указатель Boot Services
в System Table, пересчитывается CRC и закрывается доступ к состоянию
Boot Services. Указатели Runtime Services и конфигурационных таблиц
сохраняются.

Внутренняя диагностика привязывает собственный временный handle.
Привязка handle загруженного EFI-образа относится к S7-06.
[UEFI 2.11, §§7.1 и 7.4.6](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#efi-boot-services-exitbootservices).

### События в runtime-памяти

`CreateEvent` принимает `EVT_RUNTIME` как признак хранения в
runtime-памяти. Специальный тип `EVT_SIGNAL_VIRTUAL_ADDRESS_CHANGE`
привязывается к группе `VIRTUAL_ADDRESS_CHANGE` с сохранением исходного
типа. `CreateEventEx` принимает этот GUID с обычным типом события
и выбирает runtime-хранение сам. Специальный тип сигнализации для
`CreateEventEx` даёт `EFI_INVALID_PARAMETER`.

При первой регистрации выделяется массив записей в
`EfiRuntimeServicesData`. В нём сохраняются тип, идентификатор, группа,
указатели callback и context, а также TPL. Вызывающий отвечает за
runtime-время жизни callback и context. `CloseEvent` очищает запись.
Последующие операции переиспользуют массив и сохраняют `MapKey`.
По завершении BEFORE и проверке ключа прошивка записывает адрес массива
в runtime-область рядом с Runtime Services. Поле адреса лежит за
границей `HeaderSize` и CRC таблицы. Записи остаются в runtime-памяти
после `ExitBootServices`. Runtime Driver вызывает сохранённые уведомления
в физическом режиме `SetVirtualAddressMap`. Обработчики используют
`ConvertPointer` для своих динамических указателей.
[UEFI 2.11, §§7.1 и 8.4](https://uefi.org/specs/UEFI/2.11/08_Services_Runtime_Services.html#virtual-memory-services).

### Watchdog

`SetWatchdogTimer` принимает секунды и выставляет один срок на том же
TSC, который используют Boot Services. Нулевой интервал отменяет
взведение. Повторное взведение заменяет срок. Коды до `0xffff`
зарезервированы прошивкой. При взведении через диагностическую таблицу
такой код даёт `EFI_INVALID_PARAMETER`. Журнал содержит только
числовой код.

Взведение доступно при наличии валидной записи ACPI fixed hardware
в handoff. Без неё оно даёт `EFI_UNSUPPORTED`. Просрочка обрабатывается
в точке опроса даже при маскировании обычных уведомлений. После снятия
доступа к состоянию прошивка печатает код и пишет байт сброса в
reset-регистр ACPI из handoff. Машина фиксирует запрос сброса.
Успешный `ExitBootServices` отменяет watchdog.
[UEFI 2.11, §7.5.1](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#efi-boot-services-setwatchdogtimer).

Редакция 2.11 задаёт для x64 при вызове EFI-образа `FCW = 0x037f` и
`MXCSR = 0x1f80`. Перед вызовом ABI-трамплин выставляет оба значения, а после
возврата восстанавливает состояние прошивки. Этот путь исполняют гостевые
сценарии `hello` и `ebs`. [Запуск из FV](../reports/STAGE_7_REPORT.md#s7-06--загрузка-по-device-path-встроенного-fv). [UEFI 2.11, §2.3.4](https://uefi.org/specs/UEFI/2.11/02_Overview.html#x64-platforms).

## Trusted Computing

На плате с MMIO CRB прошивка публикует TPM2 в XSDT и устройство `MSFT0101` в DSDT. Она инициализирует TPM через locality 0 и предоставляет `EFI_TCG2_PROTOCOL` с единственным активным банком SHA-256. GetEventLog выдаёт формат TCG_2, а события после первого чтения доступны в retained final events table. Измеряются ROM, конфигурация, переменные загрузки, проверенная GPT, исполняемые PE и переход ExitBootServices. PE измеряется по Authenticode до выполнения. Полный набор форматов, PCR и ограничений описан в [VTPM.md](VTPM.md#measured-boot).

## Secure Boot

На S7-24 реализованы декодеры `EFI_SIGNATURE_LIST`, Auth2 и detached PKCS#7. С общим верификатором подтверждена проверка RSA-2048/SHA-256 Microsoft `dbx` update до зачисленного KEK 2023, а также отказы для чужого ключа и испорченной подписи. Защищённые переменные доступны с handoff v1.14. Для проверки образов с возможностью измерения PCR7 применяется v1.15. [ADR-0011](../decisions/ADR-0011-secure-boot-keys.md), [план S7-24](../plans/STAGE_7.md#s7-24-реализовать-secure-boot).

Слой Authenticode проверяет `SpcIndirectDataContent`, связывает его SHA-256 с обязательными подписанными атрибутами и проверяет RSA-2048/PKCS#1 v1.5 на DER SET OF этих атрибутов. Политика образов в общей библиотеке учитывает Authenticode SHA-256 из `dbx`, а у издателей цепочки сверяет TBS-хеш или тройку issuer, serial и TBS-хеш. Отзыв действует независимо от `TimeOfRevocation` по ADR-0011. Допуск по сертификату или PE-дайджесту из `db` возвращает полную запись `EFI_SIGNATURE_DATA` только после обхода всех записей таблицы и вложенных подписей. Максимум 16 подписей на образ и глубина вложения до 4. Неподдерживаемая структура подписи или неполная проверка достижимого издателя ведёт к отказу. В handoff v1.15 `LoadImage` допускает внешний PE до 64 МиБ по активной политике; `StartImage` повторяет проверку перед исполнением. Для повторной проверки используется закрытая копия исходника в страницах RO/NX. Подлинный `PathSource::FirmwareVolume` доверяется по происхождению из ROM. Передача внешнего буфера с таким путём проходит обычную проверку. [RFC 2315 §9.3](https://www.rfc-editor.org/rfc/rfc2315#section-9.3), [UEFI 2.11 §32.5.3.3](https://uefi.org/specs/UEFI/2.11/32_Secure_Boot_and_Driver_Signing.html#authorization-process).

Политический отказ для корректно загруженного PE возвращает `EFI_SECURITY_VIOLATION` и выгружаемый handle с NX-страницами. `StartImage` для этого handle возвращает тот же статус. Ограничение размера даёт `EFI_ACCESS_DENIED` с нулевым выходным handle. `SecureBoot` в защищённом режиме вычисляется по флагу платформы и наличию действующего PK; `SetupMode` отражает отсутствие PK. [UEFI 2.11 §7.4](https://uefi.org/sites/default/files/resources/UEFI_Spec_Final_2.11.pdf).

Handoff v1.15 публикует `EFI_IMAGE_EXECUTION_INFO_TABLE` под `EFI_IMAGE_SECURITY_DATABASE_GUID` в `EfiRuntimeServicesData`. Адрес таблицы сохраняется через `ExitBootServices`. К исходному `UINTN NumberOfImages = 0` дописываются записи отказов из `LoadImage` и повторной проверки `StartImage`. Повторный вызов для handle, уже отклонённого при загрузке, не добавляет запись. Запись содержит 32-битные `Action` и `InfoSize`, имя из последнего однозначного узла File Path, собственную копию Device Path и при наличии SHA-256 список `EFI_SIGNATURE_LIST` для результата проверки подписи. Для отсутствующего имени используется пустая строка CHAR16, для отсутствующего пути используется конечный узел. Таблица занимает 256 КиБ. При нехватке места операция сообщает `EFI_OUT_OF_RESOURCES` до публикации новой записи или handle. [UEFI 2.11 §32.4](https://uefi.org/specs/UEFI/2.11/32_Secure_Boot_and_Driver_Signing.html#image-execution-information-table).

При наличии TPM прошивка записывает в PCR7 конфигурацию `SecureBoot`, `PK`, `KEK`, `db`, `dbx`, непустые `dbt/dbr`, `AuditMode` и `DeployedMode`. Separator предшествует выбору загрузочного образа. `EV_EFI_VARIABLE_AUTHORITY` записывается при первой валидации по полной записи `EFI_SIGNATURE_DATA`. Успешный Auth2 в Boot Services инициирует повторное измерение изменившихся полей. Пропущенная последовательность прямых Auth2-команд и ошибка измерения останавливают допуск новых образов и переход в runtime. [PFP 1.06 r52 §3.3.4.8](https://medias.cdn.trustedcomputinggroup.org/production/TCG_PC_Client_Platform_Firmware_Profile_Version_1_06_Revision_52_pub_3_1184065dfc.pdf).

В handoff v1.16 прошивка публикует `EFI_PKCS7_VERIFY_PROTOCOL` до `ExitBootServices`. `LocateProtocol` возвращает интерфейс с `VerifyBuffer` и `VerifySignature` в ABI `efiapi`. Первый метод проверяет embedded или detached-контент и по запросу копирует подтверждённые байты. Недостаточный буфер получает требуемый размер. Второй метод проверяет переданный SHA-256 без копирования контента. Оба метода принимают массивы указателей на `EFI_SIGNATURE_LIST` с завершающим NULL и применяют переданные вызывающей стороной списки доверия, отзыва и TSA. [UEFI 2.11 §37.4](https://uefi.org/specs/UEFI/2.11/37_Secure_Technologies.html#pkcs7-verify-protocol).

Профиль протокола ограничен одним подписантом RSA-2048/SHA-256, 64 КиБ подписи и 64 списками на каждую базу. Для отзыва поддержаны сертификаты X.509, хеш сообщения SHA-256 и TBS-хеши SHA-256/384/512 с датой. Доверенный токен RFC 3161 может разрешить подпись до даты отзыва. Вызов использует staging защищённого NVRAM и сохраняет оба банка, поколения и счётчик политики. Несовместимый формат подписи или неподдержанный тип списка получает соответствующую ошибку UEFI. [ADR-0011](../decisions/ADR-0011-secure-boot-keys.md), [регистры и рамка](NVRAM_DEVICE.md#проверка-сообщений-pkcs7).

## Переменные

S7-09 заполняет четыре слота Runtime Services `GetVariable`, `GetNextVariableName`, `SetVariable` и `QueryVariableInfo`. Приложение `vars` проверяет их до `ExitBootServices`, а `rt` обслуживает проверку физического и виртуального режимов после выхода. Таблица и данные переменных находятся в `EfiRuntimeServicesData`. В runtime видимы записи с `EFI_VARIABLE_RUNTIME_ACCESS`.

- Ключ содержит GUID поставщика и имя UCS-2 длиной до 127 кодовых единиц. Имена сравниваются с учётом регистра. Малый буфер получает требуемый размер, а `GetVariable` также возвращает атрибуты. Перечисление начинается с пустого имени и проходит по видимым ключам в порядке создания.
- `RT` требует `BS`. `APPEND_WRITE` добавляет данные, пустой append ничего не меняет. Нулевой размер без append или отсутствие атрибутов доступа удаляет существующую запись. Остальные операции над существующим ключом требуют совпадающих атрибутов. `QueryVariableInfo` игнорирует `APPEND_WRITE` и возвращает общий бюджет таблицы, свободные байты и максимальный размер значения 16 КиБ.
- `HR` возвращает `EFI_UNSUPPORTED` до поддержки Hardware Error Record Persistence. Устаревший `AUTHENTICATED_WRITE_ACCESS` и `ENHANCED_AUTHENTICATED_ACCESS` возвращают `EFI_UNSUPPORTED`. `TIME_BASED_AUTHENTICATED_WRITE_ACCESS` поддерживается только для `PK`, `KEK`, `db`, `dbx`, `dbt` и `dbr` на защищённом NVRAM. `QueryVariableInfo` возвращает для них отдельную квоту и предел значения 64 КиБ. `GetNextVariableName` перечисляет действующие защищённые записи после обычных переменных. [Auth2 и квоты](NVRAM_DEVICE.md#защищённый-формат-v2).
- `PlatformLang` и `PlatformLangCodes` по умолчанию равны `en-US`. `ConIn`, `ConOut` и `ErrOut` содержат путь COM1, опубликованный на том же handle (`C0938024-BC5E-4EE6-ADF5-89166E13589A`). `Timeout = 0`; загрузочные записи появятся в S7-19. `OsIndicationsSupported`, `SetupMode`, `SecureBoot` и `PlatformLangCodes` доступны только для чтения. На защищённом NVRAM `SetupMode` равен 1 при отсутствии `PK`, `SecureBoot` равен 0 в отладочном режиме, `VendorKeys` определяется флагом снимка, `AuditMode` и `DeployedMode` равны 0. Двоичный `SignatureSupport` содержит GUID типов X.509, SHA-256 и X.509 SHA-256.
- Внутренняя модель хранилища после EBS скрывает переменные без `RT` и запрещает изменение volatile `RT`. Изменённая в EBS callback запись с `NV` попадает в снимок до финального перехода. Без NVRAM снимок живёт до сброса. [Формат store](NVRAM_DEVICE.md#формат-store).
- С NVRAM прошивка создаёт volatile defaults, восстанавливает поддерживаемые переменные с `NV` и добавляет недостающие значения по умолчанию. При восстановлении она сообщает о повреждённых записях и значениях по умолчанию, для которых не хватило места. `SetVariable` применяет изменение после `FLUSH`. При ошибке устройства он возвращает `EFI_DEVICE_ERROR`, рабочая таблица и предыдущий снимок сохраняются. [Устройство NVRAM](NVRAM_DEVICE.md#устройство).

[UEFI 2.11 §3.3](https://uefi.org/specs/UEFI/2.11/03_Boot_Manager.html#globally-defined-variables), [§8.2](https://uefi.org/specs/UEFI/2.11/08_Services_Runtime_Services.html#variable-services).

## Начальная карта памяти

После установки собственных CR3 и RSP прошивка преобразует отсортированные
регионы handoff в массив `EFI_MEMORY_DESCRIPTOR` версии 1. Размер записи
на x64 — 40 байт, выравнивание — 8 байт. Поля PhysicalStart, VirtualStart,
NumberOfPages и Attribute начинаются со смещений 8, 16, 24 и 32.
VirtualStart и четырёхбайтовый отступ после Type равны нулю. Начальный MapKey
равен 1. [UEFI 2.11, §7.2.3](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#efi-boot-services-getmemorymap).

Проекция типов задана контрактом handoff. Старые таблицы машины становятся
`EfiConventionalMemory` после переключения CR3. Новые таблицы и оба стека
занимают `EfiBootServicesData`, guard занимает одну страницу
`EfiReservedMemoryType`. Код shadow получает `EfiBootServicesCode`, а
`.rodata` и данные — `EfiBootServicesData` с разрезом по границам линкера.
Дыры между регионами не описываются. [FIRMWARE_BOOT, §6.2](FIRMWARE_BOOT.md#62-таблица-регионов-запись-32-байта).

| Область | Attribute |
|---|---|
| RAM, включая занятые области прошивки, handoff и ACPI | `EFI_MEMORY_WB` |
| ROM, MMIO и framebuffer | `EFI_MEMORY_UC` |
| Окно NVRAM | `EFI_MEMORY_UC` и `EFI_MEMORY_RUNTIME` |
| Guard и прочие reserved-области | 0 |

Атрибуты в записи описывают возможности региона. Текущие права R/W и NX
задаются таблицами страниц. Номер экрана из handoff не используется как
EFI-атрибут. С S7-05 буфер записей находится в статических данных
прошивки, уже отмеченных как `EfiBootServicesData`. При нехватке буфера построитель сообщает требуемое
число записей до записи в буфер.

ROM выводит в COM1 MapKey, версию и число записей, затем Type, PhysicalStart,
NumberOfPages и Attribute каждой записи. Та же карта доступна через
диагностический `GetMemoryMap`. [Проверки этапа 7](../reports/STAGE_7_REPORT.md#s7-04--начальная-карта-памяти-uefi).

## Выделение страниц

Внутренний аллокатор принимает количество страниц и режим `AnyPages`,
`MaxAddress` или `Address`. В режиме `Address` начало выровнено на 4 КиБ.
`AnyPages` выбирает самый высокий подходящий диапазон в conventional RAM,
а `MaxAddress` дополнительно ограничивает адрес последнего байта включительно.
Для выделения подходят только полностью покрытые диапазоны `EfiConventionalMemory`
ниже предела 36-битных физических адресов. Типы RuntimeServices получают
`EFI_MEMORY_RUNTIME`. Тип Code описывает назначение записи, действующие
права страниц задаёт текущая таблица PTE.

Аллокатор хранит признаки владения отдельно от EFI-дескрипторов.
`FreePages` принимает только страницы, ранее выделенные этим аллокатором,
и поддерживает освобождение части диапазона и соседних выделений. При
возврате восстанавливается `EfiConventionalMemory` с атрибутом WB.
Пересечение с занятыми при старте диапазонами или повторное освобождение
отклоняется. Совместимые соседние записи объединяются. Успешная операция
увеличивает `MapKey` ровно на единицу. При нехватке записей, переполнении
ключа или недопустимом диапазоне карта и ключ сохраняются.

Ёмкость буфера задаёт вызывающий код. Для начального профиля вся conventional
RAM имеет атрибут WB. Сервисы памяти используют этот же ключ и буфер. [UEFI 2.11, §7.2.1–2](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#memory-allocation-services).

## Выделение pool

Каждый блок pool занимает целое число смежных страниц. Заголовок начинается
на 8 байт выше начала диапазона, данные — на 40 байт выше начала. Такой
формат даёт требуемое 8-байтовое выравнивание и допускает размещение
в физической странице 0. Запрос нулевого размера получает освобождаемый
блок с местом минимум для одного байта.

Карта различает владение pool и обычными страницами. Соседние блоки pool
сохраняют отдельные записи. `FreePool` сверяет точный указатель и владение
по карте, затем проверяет заголовок. Границы возвращаемого диапазона берутся
из карты. Смещённый, чужой или уже освобождённый указатель отклоняется до
обращения к заголовку. `FreePages` отклоняет диапазон, принадлежащий pool.
Успешное выделение или освобождение увеличивает общий `MapKey` на единицу.

Профиль использует минимум одну страницу на блок. Гостевой доступ к заголовку
опирается на identity-map доступной для записи RAM. [UEFI 2.11, §7.2.4–5](https://uefi.org/specs/UEFI/2.11/07_Services_Boot_Services.html#efi-boot-services-allocatepool).
