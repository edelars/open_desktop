# Контракт сети: режимы none и nat, backend NAT в пользовательском пространстве

Статус: **написан в задаче S11-30 [плана этапа 11](../plans/STAGE_11.md), вариант (А) выбран Opus high 2026-11-22; ревью документа Opus high 2026-11-22 выполнено (первое — замечания исправлены в `964b9d3`; повторное — блокеров нет, один major и 13 minor исправлены в «S11-30 review fixes 2»); подтверждение владельца по стеку — ожидается** (вопрос 1 в [ADR-0008](../decisions/ADR-0008-network-backend.md), раздел «Вопросы владельцу»). Это спецификация, а не реализация: backend, trait, модель NIC и тесты в коде отсутствуют. Все числовые лимиты — **решения этого документа и гипотезы до замеров** (S11-31e, правило [AGENTS.md](../../AGENTS.md) о решениях по скорости): они записаны как числа, чтобы код и тесты имели проверяемую границу. Пока документ не уточнён замерами, лимиты правятся свободно, но каждая правка меняет и тест, который проверяет этот лимит.

Связанные документы: [ADR-0008](../decisions/ADR-0008-network-backend.md) (размещение и выбор стека), [виртуальная плата](VIRTUAL_BOARD.md) (NIC, совместимая с Intel 82540EM, PCI-владение), [контракт bundle](VM_BUNDLE.md) (поле `network`), [план этапа 11](../plans/STAGE_11.md) (S11-31a…e, S11-32, S11-33), [политика зависимостей](../policies/DEPENDENCIES.md), [реестр проблем](../KNOWN_ISSUES.md). Модель NIC описывает отдельный будущий документ `NIC_DEVICE.md` (S11-32); здесь только граница «NIC ↔ backend».

## 1. Область документа

Документ задаёт:

- режимы сети `none` и `nat` и то, что гость видит в каждом;
- адресацию гостя, шлюза и DNS;
- интерфейс «модель NIC ↔ backend» на уровне семантики (код trait пишет S11-31a);
- правила разбора кадров (Ethernet, ARP, IPv4), DHCP, DNS-пересылку, UDP, ICMP echo, TCP;
- лимиты (каждый — число) и поведение при их превышении;
- семантику отказов: что именно видит гость при каждой ошибке host-стороны;
- счётчики и что не входит в версию 1.

Документ не задаёт регистры NIC, кольца дескрипторов и прерывания (S11-32), не выбирает VirtIO-сеть (плата: 82540EM-совместимая, inbox-драйвер), не обещает пропускную способность.

## 2. Режимы

| Режим | Значение поля `network` в `config.plist` | Что есть у машины |
|---|---|---|
| `none` | `none` (по умолчанию) | Сетевого устройства в плате нет: функции NIC на шине нет, backend не создаётся. |
| `nat` | `nat` | Одна NIC (S11-32), к которой подключён backend этого документа. Гость выходит в сеть через сокеты host; входящих соединений извне нет. |

Других режимов в версии 1 нет (bridged, host-only, внутренняя сеть, нескольких NIC). Смена режима — только перезапуском машины: горячего подключения NIC и «отсоединения кабеля» во время работы в версии 1 нет. Пока устройство S11-32 не реализовано, запуск с `nat` отвечает `unsupported` ([VM_BUNDLE.md §3.5](VM_BUNDLE.md)); этот документ не меняет это правило.

## 3. Адресация

| Параметр | Значение | Причина |
|---|---|---|
| Подсеть гостя | `10.0.2.0/24` (маска `255.255.255.0`) | Частный диапазон RFC 1918 с маленькой вероятностью совпадения с сетью домашнего роутера (чаще `192.168.0.0/24`, `192.168.1.0/24`, `10.0.0.0/24`). Недостаток записан ниже. |
| Адрес гостя | `10.0.2.15` | Единственный адрес подсети, который backend выдаёт (один lease, раздел 7). |
| Шлюз | `10.0.2.2` | Адрес, на который гость отправляет всё, что вне подсети. |
| DNS | `10.0.2.3` | Отдельный адрес, чтобы гость не путал шлюз и резолвер; обслуживается backend (раздел 8). |
| Широковещательный | `10.0.2.255` | Служебный, пакеты на него отбрасываются (`drop_multicast_broadcast`, раздел 5, п. 6). |
| MAC шлюза и DNS | `02:4F:44:00:00:02` | Бит «локально администрируемый» выставлен, бит «групповой» сброшен; байты `4F 44` — ASCII «OD». Один MAC на оба адреса. |
| MAC гостя | задаёт identity bundle (S11-32); backend получает его при создании. Должен быть unicast (бит «групповой» сброшен) и не равен MAC шлюза `02:4F:44:00:00:02`; иначе конфигурация отклоняется (проверка — S11-32), backend не создаётся | Backend принимает кадры только с этим MAC источника. |
| MTU | **1500** (L3) | Максимальный кадр Ethernet без FCS и без VLAN-тега — **1514** байт. |

Недостаток выбора: адреса из `10.0.2.0/24`, кроме трёх выше, недоступны гостю, даже если такая сеть есть на стороне host или за VPN (гость на ARP-запрос получит тишину). Адрес и подсеть в версии 1 фиксированы, поля конфигурации для них нет; добавление поля требует новой версии схемы [VM_BUNDLE.md](VM_BUNDLE.md) и отдельного решения. Альтернатива `100.64.0.0/10` отклонена: этот диапазон часто занимают VPN-клиенты. Раздел [VIRTUAL_BOARD.md](VIRTUAL_BOARD.md) этим документом не меняется; ссылка на адресацию NAT добавляется туда при принятии (раздел 16, п. 5).

## 4. Граница «модель NIC ↔ backend»

Нормативная часть — семантика. Имена и сигнатуры уточняет S11-31a; требования ниже обязательны.

**Размещение.** Trait живёт в `crates/od-machine/src/net_backend.rs` (новый файл S11-31a); реализация NAT — в `crates/od-host/src/nat/`. `od-machine` не знает сокетов, файловых дескрипторов, потоков host, времени host и типов `od-host`: в trait входят только `&[u8]`, `&mut [u8]`, `usize`, закрытые перечисления и плоская структура счётчиков из `u64`.

**Операции.**

| Операция | Семантика |
|---|---|
| `transmit(frame) -> Result<(), Dropped>` | Кадр от гостя целиком, от поля адреса назначения Ethernet до конца данных (без FCS). Вызов **не блокируется**: ни на сокете, ни на резолвере, ни на ожидании очереди. Кадр копируется во внутреннюю ограниченную очередь (лимит L2). `Ok` — кадр принят в обработку; это не означает доставки. `Err(Dropped)` — кадр отброшен сразу (с причиной из закрытого перечисления); счётчик увеличен. |
| `poll_receive(buf) -> Option<usize>` | Не блокируется. Выдаёт следующий кадр для гостя и возвращает его длину; `None` — кадров нет. Длина `buf` должна быть не меньше **1514**: при меньшей длине вызов возвращает `None`, кадр **не** изымается, растёт счётчик `rx_buf_too_small` (ошибка вызывающей стороны, не panic). |
| `counters()` | Копия плоской структуры счётчиков (раздел 13). Счётчики монотонны за время жизни backend. |
| `reset()` | Сброс по сбросу NIC или машины: закрыть все сокеты и flow без отправки гостю чего-либо, очистить обе очереди; счётчики сохраняются, счётчик `resets` растёт. |

**Что модель NIC обязана.**

1. Передавать в `transmit` законченные кадры с верными контрольными суммами IPv4/TCP/UDP/ICMP: если NIC выполняет offload (вычисление контрольной суммы, сегментацию), она завершает его **до** вызова. Backend проверяет контрольные суммы и отбрасывает кадры с неверными (раздел 5); частичные («псевдозаголовочные») суммы не принимаются.
2. Считать `Err(Dropped)` **успешной передачей с точки зрения гостя**: дескриптор TX завершается как при обычной отправке, потому что настоящая сеть тоже теряет пакеты. Это не ошибка устройства и не сбой машины.
3. Вызывать `poll_receive` только когда в RX-кольце есть свободный дескриптор. Если свободных дескрипторов нет, кадры остаются в очереди backend до лимита L3; затем отбрасываются там (раздел 12).
4. Передавать `buf` длиной не меньше 1514 байт; сборка кадра в несколько дескрипторов — задача NIC, не backend.

**Что backend гарантирует.** Ни один ввод (любая длина от 0, любые байты) не вызывает panic, не читает и не пишет за пределами буфера и не обращается к сокету до проверки длин, версий и контрольных сумм; ошибка host-стороны (любой `errno`, исчерпание дескрипторов, отказ резолвера) становится потерей пакета, ответом гостю по таблице раздела 12 или записью в счётчик — но не panic и не ошибкой `transmit`/`poll_receive`. Host panic не маскируется под сетевую ошибку ([AGENTS.md](../../AGENTS.md), «Реализация и проверка»).

**Потоки выполнения.** Вызовы `transmit`/`poll_receive` делаются из потока устройства; backend исполняет сокетный ввод-вывод в **своих** потоках: один поток цикла ввода-вывода над неблокирующими сокетами и до 4 рабочих потоков резолвера (блокирующий `getaddrinfo`: вызов не прерывается, поток занят до его возврата, раздел 8). Это ограничение на число потоков — часть контракта (лимит L18). Устройство и vCPU не ждут backend.

**Пауза и остановка.** При паузе машины NIC не вызывает `poll_receive`; backend продолжает работать на часах host (`Instant` монотонные), входящие кадры копятся до лимита L3 и затем отбрасываются. Это означает: за долгую паузу удалённая сторона может закрыть TCP-соединение, а таймеры бездействия и ожидания `connect` (L9, L11, L12, L14) могут истечь, и тогда backend сам удаляет flow — после возобновления гость видит FIN/RST/тишину как после обрыва сети. Таймер L10 приостанавливается по «условию паузы таймера L10» (раздел 11). Заморозка таймеров backend на время паузы в версии 1 не делается (гипотеза, проверяется вместе с S11-04). При остановке машины backend уничтожается и закрывает все сокеты.

## 5. Кадры, Ethernet, IPv4: правила разбора

Все проверки выполняются **до** любого действия с сокетом, в этом порядке. Первое нарушение — отбрасывание кадра с соответствующим счётчиком; ответ гостю не отправляется (если не указано иное).

1. Длина кадра: меньше 14 — `drop_runt`; больше 1514 — `drop_oversize`. Кадры меньше 60 байт допустимы (NIC может не дополнять до минимума); хвостовое дополнение после IP-длины игнорируется.
2. MAC источника не равен MAC гостя — `drop_bad_src_mac`. MAC назначения не равен MAC шлюза и не является групповым (младший бит первого октета равен 1: `ff:ff:ff:ff:ff:ff`, `01:00:5E:…`, `33:33:…`) — `drop_bad_dst_mac`. Кадры с групповым MAC назначения проходят дальше на шаги 3 и 6, где получают `drop_unsupported_ethertype`, `drop_bad_dst_mac` (п. 6, подпункт а), `drop_multicast_broadcast` (подпункт в) или обслуживаются (ARP, DHCP).
3. EtherType: `0x0806` (ARP) — раздел 6; `0x0800` (IPv4) — дальше; любой другой, включая `0x86DD` (IPv6) и `0x8100` (VLAN), — `drop_unsupported_ethertype`.
4. IPv4: версия 4; IHL равен 5 (опции — `drop_ip_options`); общая длина не меньше 20 и не больше остатка кадра; контрольная сумма заголовка верна (иначе `drop_ip_malformed`). Фрагменты (флаг MF или ненулевое смещение) — `drop_ip_fragment`: сборка фрагментов в версии 1 не делается.
5. Адрес источника: `10.0.2.15` допустим. `0.0.0.0` допустим только при протоколе 17 (UDP) и адресе назначения `255.255.255.255` или `10.0.2.2` (DHCP-клиент без адреса, раздел 7): протокол и назначение известны из заголовка IPv4, поэтому проверяются здесь; иначе `drop_bad_src_ip`. Порты такого пакета (68→67) проверяются на п. 8 (иначе `drop_bad_src_ip`). Любой другой адрес источника — `drop_bad_src_ip`. Наличие lease не требуется: гость со статическим `10.0.2.15` работает.
6. Адрес назначения. Подпункты проверяются **по порядку** (а), (б), (в); первое совпадение отбрасывает кадр:
   - (а) Групповой MAC назначения (ранее пропущенный п. 2) при IP назначения, который не групповой и не широковещательный (не `224.0.0.0/4`, не `240.0.0.0/4`, не `255.255.255.255`, не `10.0.2.255`) — `drop_bad_dst_mac`.
   - (б) `127.0.0.0/8`, `0.0.0.0/8`, `169.254.0.0/16`, `10.0.2.15` и остальные адреса `10.0.2.0/24`, кроме `10.0.2.2`, `10.0.2.3` и `10.0.2.255`, — `drop_policy_dst`. Гость **не получает доступа к петле host**.
   - (в) `224.0.0.0/4` (multicast), `240.0.0.0/4`, `255.255.255.255` и `10.0.2.255` — `drop_multicast_broadcast`. Единственное исключение — `255.255.255.255` при протоколе 17 (DHCP, раздел 7; порты проверяются на п. 8); при любом другом протоколе — сразу `drop_multicast_broadcast`. Следствие: mDNS, LLMNR, SSDP, NetBIOS и IGMP (адрес назначения групповой) не работают.
   - Остальные однозначные (unicast) адреса, включая частные сети LAN и **собственные не-loopback адреса host**, — допустимы; межсетевого экрана в версии 1 нет (вопрос 2 ADR-0008).
   - `10.0.2.2` и `10.0.2.3` обслуживает сам backend (разделы 7–11); любой протокол или порт, которых там нет, — по таблице раздела 12 («обращение к адресам backend»).
7. Протокол IPv4: 1 (ICMP), 6 (TCP), 17 (UDP); любой другой (IGMP 2, GRE, ESP …) — `drop_unsupported_proto`.
8. Транспортный уровень: длины и контрольные суммы TCP/UDP/ICMP проверяются; несоответствие — `drop_l4_malformed`. Здесь же проверяются порты UDP у DHCP-пакетов: источник `0.0.0.0` требует портов 68→67, иначе `drop_bad_src_ip`; назначение `255.255.255.255` у источника `10.0.2.15` требует порта назначения 67, иначе `drop_multicast_broadcast`. UDP с нулевой контрольной суммой принимается (допускается RFC 768 для IPv4). Толкование поля длины UDP: значение меньше 8 или больше IP-нагрузки — `drop_l4_malformed`; значение меньше IP-нагрузки (но не меньше 8) принимается: датаграмма берётся по полю длины, контрольная сумма считается по ней же, хвост после неё отбрасывается.
9. TTL: значение 0 — `drop_ip_malformed`. Пакеты с TTL 1 к внешним адресам **не** порождают ICMP Time Exceeded: проверка маршрута (traceroute) вне версии 1.

Кадры, отправляемые гостю, backend собирает сам: TTL 64, контрольные суммы всех уровней вычислены, поле Don't Fragment выставлено, длина не больше 1514, идентификатор IP — счётчик по модулю 2^16, дополнение до 60 байт не требуется.

## 6. ARP

- Запрос «кто `10.0.2.2`» или «кто `10.0.2.3`» с верными полями (hardware Ethernet, protocol IPv4, длины 6 и 4, операция 1, отправитель — MAC гостя): ответ с MAC шлюза (раздел 3).
- ARP-проба (`sender IP = 0.0.0.0`) для `10.0.2.15` и анонсы (gratuitous; в том числе ARP-ответ, операция 2, у которого отправитель и цель равны `10.0.2.15`): без ответа, `drop_arp_other` не увеличивается — они считаются штатными (`arp_probe_ignored`).
- Любой другой ARP-запрос (адрес в подсети, не принадлежащий backend) — без ответа; гость получает «хост недоступен» собственными средствами. ARP-ответы от гостя и неверные поля — `drop_arp_other`.
- Таблицы соответствий backend не хранит: ответ полностью определён запросом.

## 7. DHCP

Обслуживание — UDP `10.0.2.2:67` от клиента с портом 68 (также на `255.255.255.255:67`, раздел 5, п. 6). Адрес выдаётся один: **один lease**, всегда `10.0.2.15` для MAC гостя. Состояния lease backend не хранит: после перезапуска машины или backend клиент получает тот же адрес.

| Сообщение клиента | Ответ |
|---|---|
| DISCOVER | OFFER с `yiaddr = 10.0.2.15` |
| REQUEST (selecting/init-reboot/renewing/rebinding) на `10.0.2.15`; `server identifier` отсутствует или `10.0.2.2` | ACK |
| REQUEST на другой адрес | NAK (при `giaddr = 0` всегда на `255.255.255.255`, L2 — `ff:ff:ff:ff:ff:ff`; RFC 2131, §4.1) |
| REQUEST с чужим `server identifier` | без ответа (клиент выбрал другой сервер) |
| DECLINE, RELEASE | без ответа, счётчик `dhcp_ignored`; lease не меняется |
| INFORM с `ciaddr = 10.0.2.15` | ACK на `ciaddr` (`yiaddr = 0`, без опций 51, 58, 59; RFC 2131, §4.3.5); счётчик `dhcp_acks`. INFORM с другим `ciaddr` — `dhcp_ignored` |
| `chaddr` не равен MAC гостя; нет magic cookie (BOOTP); тип сообщения не распознан; длина не соответствует | без ответа, `dhcp_malformed` |

Опции ответа: 1 (маска `255.255.255.0`), 3 (шлюз `10.0.2.2`), 6 (DNS `10.0.2.3`), 28 (широковещательный `10.0.2.255`), 26 (MTU 1500), 51 (время lease **86 400 с**), 54 (идентификатор сервера `10.0.2.2`), 58 (T1 43 200 с), 59 (T2 75 600 с), 53 (тип сообщения). Других опций нет (имя домена, NTP, WINS и т. д. не выдаются). Адрес назначения OFFER и ACK: L2 — MAC гостя; L3 — `255.255.255.255`, если `ciaddr = 0`, иначе `ciaddr`; для NAK — см. таблицу. Размер DHCP-сообщения (поле данных UDP) от клиента — от 240 байт (236 фиксированных + 4 magic cookie) и до 1472 байт; меньше или больше — `dhcp_malformed`. Спецификации: RFC 2131 (протокол), RFC 2132 (опции).

## 8. DNS-пересылка

Обслуживание — UDP `10.0.2.3:53`. Гость отправляет запрос; backend разбирает его и отвечает, **используя системный резолвер host** (`getaddrinfo` на рабочем потоке: он учитывает `/etc/hosts`, настройки сети и «scoped»-резолверы macOS, в отличие от чтения `resolv.conf`; гарантии macOS для этого не исследовались, проверка — S11-31b). Конструирование ответа — код проекта, не готового DNS-стека. `getaddrinfo` блокирует и не прерывается: слот запроса (всего 8) занят от приёма запроса до ответа гостю или таймаута 5 с и по таймауту освобождается, но **рабочий поток остаётся занятым до возврата `getaddrinfo`**. Новый запрос ждёт свободный рабочий поток (из 4), оставаясь в пределах 8 слотов; если все потоки зависли, запросы получают SERVFAIL по таймауту, число потоков не растёт.

Обрабатывается запрос, у которого: заголовок не короче 12 байт; бит QR равен 0; opcode 0; `QDCOUNT = 1`; имя без указателей сжатия, ≤ 255 октетов в wire-формате (включая октеты длин меток и завершающий нулевой), метки ≤ 63; класс IN. Запрос больше 512 байт (данные UDP) — без ответа, `dns_malformed`. EDNS: запрос без `OPT` — ответ без `OPT`; запрос с одним `OPT` версии 0 — ответ содержит минимальный `OPT` (имя — корень, тип 41, размер UDP-данных 512, расширенный RCODE и флаги 0, версия 0, без опций; RFC 6891, §6.1.1 и §7), опции запроса игнорируются; `OPT` с версией, отличной от 0, — BADVERS (расширенный RCODE 16) с минимальным `OPT` (RFC 6891, §6.1.3); два и более `OPT` в запросе — FORMERR без `OPT`.

| Запрос | Ответ |
|---|---|
| тип A | NOERROR и до **16** записей A, но не больше, чем помещается в ответ размером 512 байт (адреса из `getaddrinfo` для `AF_INET`; TTL всех записей **30 с**; из ответа вычёркиваются адреса, которые backend отбросит по правилу раздела 5, п. 6: `127.0.0.0/8`, `0.0.0.0/8`, `169.254.0.0/16`, вся подсеть `10.0.2.0/24`, `224.0.0.0/4`, `240.0.0.0/4`, `255.255.255.255`; если ничего не осталось — NOERROR без записей) |
| тип AAAA | NOERROR без записей (IPv6 вне версии 1; гость переходит на IPv4) — для **любого** имени, резолвер не вызывается |
| любой другой тип (PTR, MX, TXT, SRV, …) | RCODE 4 (NOTIMP) |
| имя не найдено (`EAI_NONAME`) | NXDOMAIN (RCODE 3) |
| отказ резолвера (`EAI_AGAIN`, `EAI_FAIL`, другая ошибка, истёк таймаут **5 с**) | SERVFAIL (RCODE 2) |
| класс не IN, `QDCOUNT` не 1, сжатие в вопросе, два `OPT` | FORMERR (RCODE 1), если заголовок разобран (`dns_formerr`); иначе без ответа (`dns_malformed`) |
| все 8 слотов запросов заняты | без ответа, `dns_dropped_busy`; гость повторит запрос |
| запрос ждёт свободного рабочего потока дольше 5 с | SERVFAIL по таймауту; поздний результат отбрасывается |

В ответе: тот же ID, QR=1, RD копируется, RA=1, AA=0; вопрос повторяется; записи — адреса для имени из вопроса (CNAME-цепочка не воспроизводится). Отдельно: TCP-соединение на `10.0.2.3:53` получает RST (DNS по TCP вне версии 1). Бит TC не выставляется: повтор по TCP невозможен, поэтому набор A-записей, не поместившийся в 512 байт, усекается без TC — **сознательное отклонение от RFC 2181, §9** (набор записей возвращается целиком либо с TC); гость может увидеть только часть адресов имени. Спецификация: RFC 1035.

## 9. ICMP echo

| Запрос гостя | Поведение |
|---|---|
| Echo request (тип 8, код 0) на `10.0.2.2` или `10.0.2.3` | **Синтетический** echo reply от backend: идентификатор, номер и данные копируются; пакет не покидает backend. |
| Echo request на внешний адрес | Backend отправляет запрос через непривилегированный сокет ICMP (`SOCK_DGRAM`, `IPPROTO_ICMP`), ждёт ответ **5 с**, переписывает идентификатор на гостевой и отправляет гостю reply. Нет ответа — тишина (как при потере). |
| Прочие типы ICMP от гостя (timestamp, redirect, error и т. д.) | `drop_unsupported_proto` |
| Данные echo больше 1472 байт | невозможно по длине кадра; см. раздел 5, п. 1 |

Источник по непривилегированному ICMP на macOS: исходный код `ping` в [apple-oss-distributions/network_cmds](https://github.com/apple-oss-distributions/network_cmds) (`ping.tproj/ping.c`): при `getuid() != 0` вызывается `socket(AF_INET, SOCK_DGRAM, IPPROTO_ICMP)`, при root — `SOCK_RAW`. Это исходник утилиты, а не документация API; поведение в процессе VMHost, вопросы о переписывании идентификатора ядром и о фильтрации адресов **не проверены**. Если S11-31c покажет, что сокет недоступен процессу VMHost или не возвращает ответы, остаётся только синтетический ответ для `10.0.2.2` и `10.0.2.3`, а внешние echo не получают ответа; такое сужение записывается в отчёт S11-31c и в `KNOWN_ISSUES.md`, контракт при этом остаётся верным (внешний echo без ответа разрешён). Одновременных запросов на внешние адреса — не больше **8** (лимит L6); больше — `drop_flow_limit_icmp`.

**Результат S11-31c (проверено на macOS 26, Darwin 25.6.0, ARM64, без root, только на адресе `127.0.0.1`).** Сокет `socket(AF_INET, SOCK_DGRAM, IPPROTO_ICMP)` создаётся и принимает `connect` с портом 0; ядро возвращает ответ **вместе с заголовком IP** (backend отбрасывает его перед разбором), **не переписывает** идентификатор и **не вычисляет** контрольную сумму ICMP (сообщение с нулевой суммой остаётся без ответа). Поэтому backend отправляет сообщение гостя как есть (его сумма уже верна) и принимает ответ только с тем же идентификатором и номером. Один запрос — один сокет и один flow с ключом (идентификатор, адрес назначения, номер): лимит L6 считает запросы, повторный запрос с тем же ключом заменяет ожидающий. Для остальных платформ сокет не реализован: внешний echo получает `drop_host_resource` и остаётся без ответа, синтетический ответ шлюза и DNS работает (см. [KNOWN_ISSUES.md](../KNOWN_ISSUES.md), ISSUE-653).

## 10. UDP

- Допустим любой порт назначения, кроме адресов backend (раздел 5, п. 6; к `10.0.2.3` — только порт 53, к `10.0.2.2` — только порт 67; остальное — по таблице раздела 12).
- Один flow = четвёрка (адрес и порт источника, адрес и порт назначения). На flow — один сокет UDP (`SOCK_DGRAM`, неблокирующий), создаётся при первой датаграмме и всегда подключается (`connect`) к назначению — чтобы получать ошибки доставки.
- Размер данных UDP от гостя — до 1472 байт (следствие MTU и отсутствия фрагментов). Ответ host, который не помещается в 1472 байта, **отбрасывается** (`drop_oversize_reply`): фрагментация для гостя в версии 1 не выполняется.
- Время жизни flow — **120 с** бездействия (обновляется датаграммой в любом направлении; RFC 4787, REQ-5: не менее двух минут). Лимит одновременных flow — **64** (L5): при превышении новая датаграмма отбрасывается (`drop_flow_limit_udp`), существующие flow не вытесняются.
- Вход с host на этот сокет с адреса, отличного от адреса назначения flow, не пересылается (после `connect` ядро фильтрует). Приём **извне без запроса гостя** невозможен: слушающих сокетов нет.

## 11. TCP

Backend завершает TCP гостя **на своей стороне** и открывает отдельное соединение host с адресом назначения (проксирование на уровне соединения, а не пакетная трансляция).

**Открытие.** SYN гостя → создаётся flow и неблокирующий `connect()` к назначению; до завершения `connect` гостю ничего не отправляется (повторные SYN гостя игнорируются). Завершение успешно → SYN-ACK гостю. Лимит одновременных flow — **128** (L4); при превышении SYN отбрасывается (`drop_flow_limit_tcp`), гость повторит SYN сам.

**Параметры стека гостю** (профиль версии 1 — осознанно усечённый): MSS **1460**; размер окна приёма backend — **65 535** (масштабирование окна не согласуется); SACK, временные метки, ECN, Fast Open — не согласуются (опции SYN гостя в этих частях игнорируются); данные вне порядка отбрасываются (`tcp_out_of_order_dropped`) без очереди пересборки: гость повторит их по ACK; MSS, объявленный гостем, ограничивается 1460 вниз.

**Передача.** Буфер данных гость→host на flow — **64 KiB**; данные host→гость — буфер **64 KiB**, отправка не превышает окно, объявленное гостем, и не больше 1460 байт на сегмент. Backend читает из сокета host, только когда в буфере есть место и очередь L3 не заполнена: давление передаётся назад через TCP, данные не теряются. Повторная передача к гостю по таймеру: начальный RTO **1 с**, удвоение, потолок **8 с**; исходная отправка и **6** повторов: если подтверждения нет, RST гостю и закрытие сокета host (`tcp_giveups`) через 1 + 2 + 4 + 8 + 8 + 8 + 8 = **39 с** после исходной отправки. Потолок 8 с — **отклонение от RFC 6298, §2.5** (рекомендует не менее 60 с): канал виртуальный, без реальной сети; значение — гипотеза до S11-31e. **Условие паузы таймера L10:** таймер не тикает, а счётчик повторов не растёт, пока в очереди L3 есть кадры, ожидающие `poll_receive` дольше текущего RTO (NIC не забирает кадры: пауза машины, нет RX-дескрипторов): потеря в этом случае произошла бы в самом backend, а не в сети. После нового подтверждения (ACK) от гостя RTO возвращается к 1 с (SRTT и RTTVAR не вычисляются).

**Закрытие.** FIN гостя → `shutdown(SHUT_WR)` на сокете host; FIN/EOF host → FIN гостю после отправки всех данных; RST гостя → немедленное закрытие сокета host; сброс соединения host (`ECONNRESET`, `EPIPE`) → RST гостю. После обмена FIN в обе стороны flow освобождается через **2 с** (L19, «FIN-linger»; на случай потерянного последнего ACK). Бездействие (нет сегмента ни в одном направлении и нет данных на сокете host; по истечении flow удаляется, сокет host закрывается вызовом `close()`): **7 440 с** (2 ч 4 мин) для установленного соединения (RFC 5382, REQ-5: не менее 2 ч 4 мин); **240 с** для полузакрытого соединения (получен FIN от одной стороны) и для не завершившего открытие (SYN-ACK отправлен гостю, ACK гостя не получен): 240 с — собственная гипотеза, не граница RFC 5382. Ожидание завершения `connect` — **30 с**; это таймаут попытки соединения прокси на host, а не таймер бездействия NAT из RFC 5382; затем flow молча удаляется (`tcp_connect_timeout`).

Сегмент гостя без существующего flow, не являющийся SYN и не содержащий RST, получает RST (счётчик `tcp_refused` не растёт: отдельный `tcp_orphan_rst`); RST от гостя без flow игнорируется.

**Ошибка `connect`:**

| Результат на host | Что видит гость |
|---|---|
| `ECONNREFUSED` | RST+ACK в ответ на SYN: «соединение отвергнуто» |
| `ENETUNREACH`, `EHOSTUNREACH`, `ENETDOWN`, `EHOSTDOWN` | ICMP Destination Unreachable (код 0 — сеть, код 1 — хост) с заголовком IP исходного пакета и 8 байтами данных |
| таймаут 30 с | тишина (SYN гостя уходит в повторы гостя и истекает у него) |
| исчерпание ресурсов (`EMFILE`, `ENFILE`, `ENOBUFS`, `ENOMEM`) | SYN отброшен, `drop_host_resource`; гость повторит SYN |
| другая ошибка (`EACCES`, `EPERM`, …) | RST+ACK |

**К адресам backend.** TCP на `10.0.2.2` или `10.0.2.3` (любой порт) — RST+ACK. Слушающих сокетов на host backend **не открывает** (план S11-31d, «Не делать»).

Эта часть — главный источник риска варианта А ([ADR-0008](../decisions/ADR-0008-network-backend.md), критерии выбора варианта Б).

| L18 | Потоки host (поток цикла + рабочие резолвера) | 1 + 4 | константа; счётчика нет (поток резолвера занят до возврата `getaddrinfo`, раздел 8) |

IP-фрагменты не собираются (буферов сборки нет).

| IPv4-кадр с групповым MAC назначения и unicast IP назначения (п. 6, подпункт а) | тишина | `drop_bad_dst_mac` |
| Источник IPv4 не `10.0.2.15` (и не DHCP с `0.0.0.0`) | тишина | `drop_bad_src_ip` |
| Адрес назначения 127.0.0.0/8, 169.254.0.0/16, остальные адреса подсети (п. 6, подпункт б) | тишина (ARP на них не отвечает никто) | `drop_policy_dst` |
| UDP на 10.0.2.2 (кроме 67) или 10.0.2.3 (кроме 53) | ICMP Destination Unreachable, код 3 | `gw_port_unreachable` |
| TCP на 10.0.2.2/10.0.2.3 | RST | `tcp_refused` |
| Ответ UDP host больше 1472 байт | тишина | `drop_oversize_reply` |
| Любая другая ошибка host на сокете установленного соединения | RST соединения | `tcp_host_reset` |
| Любая другая ошибка host при отправке UDP/ICMP | потеря датаграммы | `drop_host_resource` |
| Пауза машины | кадры копятся до L3, затем теряются; таймер L10 — по «условию паузы таймера L10» (раздел 11); соединения, закрытые за время паузы удалённой стороной или самим backend по таймеру (L9, L11, L12, L14), видны после возобновления как RST/FIN/тишина | `drop_rx_queue_full`, `tcp_idle_expired`, `udp_idle_expired`, `tcp_connect_timeout`, `icmp_echo_timeout` |
| Сброс NIC/машины | все соединения исчезли без уведомления; гость начинает с DHCP | `resets` |
| Выключение host-сети во время работы | как «на host нет сети»; уже открытые соединения — по `ECONNRESET`/таймауту | счётчики строки «На host нет сети вообще», `tcp_host_reset` |

ICMP-ошибки гостю (по `ENETUNREACH` и др.) содержат заголовок IP исходного пакета и первые 64 бита (8 байт) его данных (RFC 792); частота — L15.

Решения S11-31c (гипотезы до замеров и проверки на гостях). Источник адреса ICMP-ошибки: «порт недоступен» (код 3) — адрес назначения исходного пакета (так отвечает сам хост); «сеть/хост недоступны» (код 0/1) — шлюз `10.0.2.2` (так отвечает маршрутизатор). У каждого пакета гостя одна судьба: если ошибка поставлена в очередь L3, растёт счётчик ситуации (`udp_refused`, `udp_unreachable`, `gw_port_unreachable`) и `icmp_error_sent`; если она подавлена лимитом L15 — только `icmp_error_suppressed`; если не вошла в очередь L3 — только `drop_rx_queue_full`. Ошибка, которую ядро сообщает на следующем чтении сокета (`ECONNREFUSED` после отправки), относится к предыдущей датаграмме flow и цитирует её.

## 13. Счётчики

Плоская структура из `u64` (монотонные); как минимум:

- Кадры и байты: `tx_frames`, `tx_bytes` (принятые от гостя), `rx_frames`, `rx_bytes` (выданные гостю), `resets`, `rx_buf_too_small`.
- Отбрасывание: все `drop_*` документа (разделы 5, 6, 12; по одному счётчику на причину).
- ARP/DHCP/DNS: `arp_replies`, `arp_probe_ignored`, `dhcp_offers`, `dhcp_acks`, `dhcp_naks`, `dhcp_ignored`, `dhcp_malformed`, `dns_queries`, `dns_malformed`, `dns_nxdomain`, `dns_servfail`, `dns_formerr`, `dns_dropped_busy`.
- Транспорт: `tcp_opened`, `tcp_refused`, `tcp_unreachable`, `tcp_connect_timeout`, `tcp_connect_error`, `tcp_idle_expired`, `tcp_zero_window`, `udp_idle_expired`, `icmp_echo_timeout`, `tcp_host_reset`, `tcp_retransmits`, `tcp_giveups`, `tcp_orphan_rst`, `tcp_out_of_order_dropped`, `udp_flows_opened`, `udp_forwarded` (датаграммы гостя, переданные сокету host; добавлен в S11-31c: судьба принятой датаграммы), `udp_refused`, `udp_unreachable`, `icmp_echo_synthetic`, `icmp_echo_forwarded`, `icmp_error_sent`, `icmp_error_suppressed`, `gw_port_unreachable`.

Каждая строка таблицы 12.2 (кроме названных ниже) и каждый лимит, нарушение или срабатывание которого меняет состояние или видно гостю (L2–L7, L9–L17), имеют свой счётчик; L1 — `drop_oversize`, L8, L18 и L19 — константы без счётчика. Строки таблицы 12.2 без отказа («Нормальный …») счётчика не имеют; строка «Выключение host-сети во время работы» отражается счётчиками строки «На host нет сети вообще». S11-31a вправе уточнить имена, но не терять причины. Счётчик `drop_unhandled_l4` (S11-31a) — временный: он считает корректные пакеты TCP/UDP/ICMP, которых пока никто не обслуживает; последняя из задач S11-31b–d его удаляет (пункт «Сделать» S11-31d).

## 14. Проверки для задач S11-31a…e и S11-32

1. Каждый лимит L1…L7, L9…L17 — тест, который доводит значение до границы и на единицу выше и проверяет действие из таблицы 12.1 и счётчик; для констант (L8, L18, L19, а также TTL и таймаут в L16 и время lease в L17) — проверка значения, а не «на единицу выше»; для размеров в L16 и L17 (запрос, ответ, число записей, слоты, сообщение) — граница и на единицу выше.
2. Каждая строка таблицы 12.2 — тест на синтетических кадрах (генератор общий, `crates/od-testkit`, если подходит) с проверкой кадра, полученного гостем, либо его отсутствия.
3. Перебор длин 0…1600 и мусорных заголовков (детерминированный генератор): ноль panic, ноль выходов за буфер.
4. Тесты, которым нужен сервер на `127.0.0.1` (TCP/UDP/ICMP), используют **тестовый** параметр политики адреса назначения (разрешение петли только под `cfg(test)` или feature тестовой поддержки): в продуктовой конфигурации петля host недоступна гостю (раздел 5, п. 6). Эту границу фиксирует S11-31a.
5. S11-32: TX offload выполнен до `transmit` (раздел 4, п. 1); `Err(Dropped)` завершает дескриптор TX как успешную передачу; `poll_receive` вызывается только при свободном RX-дескрипторе; буфер 1514 байт.
6. Измерения (S11-31e) — только предварительные, без гостя и устройства; они уточняют L2, L3, L4, L5, L7 по правилам [AGENTS.md](../../AGENTS.md).

## 15. Не входит в версию 1

IPv6 (включая NDP, DHCPv6, RA); port forwarding и любые входящие соединения извне; режимы bridged, host-only, внутренняя сеть; несколько NIC; hot-plug и отключение кабеля; VLAN; multicast и broadcast (кроме DHCP); IP-фрагменты и опции IP; DNS по TCP, типы записей кроме A (AAAA — только пустой ответ), DNSSEC, опции EDNS (ответ содержит только минимальный `OPT`, раздел 8); ICMP Time Exceeded и traceroute; TCP: масштабирование окна, SACK, временные метки, ECN, сборка сегментов вне порядка; ограничения трафика (traffic shaping), межсетевой экран и запись трафика (pcap); обещания пропускной способности; сетевые протоколы UEFI (SNP/PXE/HTTP boot) в прошивке (решение владельца 2026-11-07, [VIRTUAL_BOARD.md](VIRTUAL_BOARD.md)).

## 16. Открытые вопросы и непроверенное

1. **Подтверждение владельца по стеку** (вариант А) — ожидается; ответ с датой вносится в ADR-0008.
2. **Системный резолвер:** поведение `getaddrinfo` для A-запросов (возвращает ли ошибку для имени без A-записей, обрабатывает ли scoped-резолверы VPN) не проверено на macOS; проверка — S11-31b. Расширение типов записей (пересылка «сырых» DNS-пакетов вышестоящему серверу) — отдельное решение при необходимости.
3. **Политика назначения:** гость может обращаться к LAN и к не-loopback адресам самого host без межсетевого экрана. Нужно ли по умолчанию это ограничить — вопрос владельцу (ADR-0008, вопрос 2).
4. **Непривилегированный ICMP** в процессе VMHost: источник — исходник `ping`, не документация API. S11-31c проверила сокет на `127.0.0.1` из тестового процесса (раздел 9); не проверено: внешние адреса, процесс VMHost под App Sandbox, поведение при отсутствии сети (ISSUE-653).
5. **Адресация в плате:** добавить ли строку про NAT-подсеть в [VIRTUAL_BOARD.md](VIRTUAL_BOARD.md) (план S11-30 допускает «при необходимости»); в этой задаче файл не менялся.
6. **Пауза и часы flow:** замораживать ли таймеры backend на время паузы; вопрос S11-04/S11-31d.
7. **Дескрипторы:** сколько их доступно VMHost (мягкий предел процесса) не измерялось; при нехватке лимиты L4–L6 уменьшаются, а не обходятся.
8. **Проверка на ОС:** поведение Windows (NCSI, NetBIOS, LLMNR) и Linux с этим профилем не проверено; подтверждение — S11-33 на Linux. Для Windows сетевого сценария нет.
9. Все лимиты — гипотезы до замеров S11-31e.
