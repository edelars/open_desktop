# Собственное дисплейное устройство: контракт версии 1

**Статус:** контракт написан в задаче S10-02 [плана этапа 10](../plans/STAGE_10.md#s10-02-описать-контракт-дисплейного-устройства), исправлен по первому архитектурному ревью и **ожидает повторного ревью**. Устройство не реализовано: модели в `crates/od-machine/src/` нет, ни один тест его не проверяет. Реализация — S10-03, гостевой probe — S10-08.

Документ задаёт guest-visible поведение устройства, адреса для платы без PCI, способ backing памяти framebuffer и host-side Rust API. Регистры и их поведение — собственный проект Open Desktop; они не основаны на карте регистров другого виртуального или физического дисплейного устройства. Из публичных стандартов используется только соответствие формата пикселя UEFI GOP (раздел 11).

Связанные документы: [виртуальная плата](VIRTUAL_BOARD.md) (строка «Экран»), [контракт машины](MACHINE_CONTRACT.md) (разделы «Синхронная MMIO/PIO bus», «Committed writes», «Bounded COM1 polling UART»), [методика проверки изображения](../testing/DISPLAY.md), [отчёт этапа 10](../reports/STAGE_10_REPORT.md).

## 1. Модель и границы

- Устройство состоит из двух непересекающихся регионов гостевой физической карты:
  - **окно регистров** — регион `MemoryRegionKind::Mmio`, к которому привязан `BusDevice` дисплея;
  - **память framebuffer** — регион нового вида `MemoryRegionKind::Framebuffer` (решение и причины — раздел 7).
- Гость меняет режим и сообщает о готовом кадре только через регистры. Пиксели он пишет обычными записями в память framebuffer: без MMIO-dispatch, без вызова устройства и без committed-write callback на каждую запись.
- Устройство синхронное и однопоточное, как остальная `MachineBus`: каждый доступ к регистру выполняется целиком в момент вызова `BusDevice::read`/`write`. Таймеров, фоновых потоков и асинхронных событий у устройства нет. Host не сканирует память по таймеру: о готовом кадре он узнаёт только по `FRAME_GENERATION` (раздел 6).
- Всё guest-visible состояние — 32-битные числа little-endian и байты framebuffer. Устройство не хранит в guest-visible состоянии host pointers, дескрипторы, объекты Metal или IOSurface.

## 2. Первая поддержанная конфигурация

| Параметр | Значение версии 1 |
|---|---|
| Число экранов | 1 |
| Формат пикселя | один: `FORMAT = 1` (`BGRX8888`) — 32 бита на пиксель; в памяти байт 0 = B, байт 1 = G, байт 2 = R, байт 3 = X; как 32-битное little-endian слово пиксель равен `0xXXRRGGBB` |
| Байт X | Гость может писать любое значение. Host при показе его игнорирует и не трактует как alpha; показанный пиксель непрозрачен. Устройство байт не изменяет |
| Stride | `STRIDE = ACTIVE_WIDTH × 4` байт, без паддинга |
| Минимальный размер | 1 × 1 |
| Максимальный размер | `MAX_WIDTH = 4096`, `MAX_HEIGHT = 2304` |
| Размер памяти framebuffer | `FB_SIZE = 4096 × 4 × 2304 = 37 748 736` байт = `0x0240_0000` = ровно 36 MiB |
| Расположение кадра | Пиксель `(x, y)` лежит по адресу `FB_BASE + y × STRIDE + x × 4`; кадр начинается со смещения 0 памяти framebuffer. Байты памяти framebuffer за пределами `STRIDE × ACTIVE_HEIGHT` доступны гостю как память, но host их не читает |

Размеры для замеров S10-10 укладываются в лимит: 1920×1080 даёт 8 294 400 байт, 2560×1600 — 16 384 000 байт.

### 2.1. Проверка переполнения

- Ограничения проверяются **до** любого умножения: `1 ≤ WIDTH ≤ 4096` и `1 ≤ HEIGHT ≤ 2304`. После этого `WIDTH × 4 ≤ 16 384 < 2^15` и `WIDTH × 4 × HEIGHT ≤ 37 748 736 < 2^26`. Оба значения помещаются в `u32` с большим запасом, умножение в `u32` безопасно.
- Если умножить непроверенные гостевые значения, переполнится даже `u64`: `(2^32 − 1) × 4 × (2^32 − 1) ≈ 2^66 > 2^64 − 1`. В `u32` уже `WIDTH × 4` переполняется при `WIDTH ≥ 2^30`. Поэтому реализация либо сначала сравнивает с лимитами, либо считает через `checked_mul` в `u64`/`u128`. Сравнение с лимитом после умножения с переносом запрещено.
- Дополнительная проверка `WIDTH × 4 × HEIGHT ≤ FB_SIZE` в версии 1 избыточна (максимальный кадр равен `FB_SIZE`), но обязательна: будущая версия может уменьшить память, не меняя `MAX_*`.
- Адреса: `FB_BASE + FB_SIZE = 0xF800_0000 + 0x0240_0000 = 0xFA40_0000 ≤ 2^32`; конец окна регистров `0xFC00_0000 + 0x1000 = 0xFC00_1000 ≤ 2^32`. Переполнения нет. Оба региона помещаются в любую ширину физического адреса от 32 бит. Сегодня в `od-machine` встречаются ширины 36 (stage4 probes, часть тестов) и 64 (часть тестов); обе подходят.
- Счётчики `generation` и `mode_change_count` — `u64`; правило насыщения — раздел 8.

## 3. Адреса для платы без PCI

PCI в `od-machine` пока нет ([S4-30](../plans/STAGE_4.md#s4-30-минимальная-pcipcie-configuration)), поэтому версия 1 использует фиксированные адреса. **Значения фиксируются здесь** и продублированы в [VIRTUAL_BOARD.md](VIRTUAL_BOARD.md).

| Регион | GPA начала | Длина | Конец (исключительно) | `MemoryRegionKind` |
|---|---|---|---|---|
| Память framebuffer | `0xF800_0000` | `0x0240_0000` (36 MiB) | `0xFA40_0000` | `Framebuffer` |
| Резерв для памяти дисплея (не отображается в карту, доступ = `BusAccessError::UnmappedPhysical`) | `0xFA40_0000` | `0x01C0_0000` (28 MiB) | `0xFC00_0000` | — |
| Окно регистров | `0xFC00_0000` | `0x1000` (4 KiB) | `0xFC00_1000` | `Mmio` |

Согласование с картой:

- Сегодня у `od-machine` нет общей карты платы. Существующие карты (stage4 probes, тесты `bus.rs`, `page_walk.rs`) содержат только RAM от нуля и тестовые MMIO-окна на малых адресах; выбранные диапазоны их не пересекают. `MachineMemoryMap::new` всё равно отвергает перекрытия.
- Диапазон `[0xF800_0000, 0xFC00_1000)` резервируется под дисплей. Будущая карта платы (S4-00, S4-30, APIC/IOAPIC, ECAM, firmware) не размещает там RAM и другие устройства. RAM ниже 4 GiB заканчивается не выше `0xF800_0000`; остальная RAM лежит выше 4 GiB.
- Выбор оставляет нетронутыми адреса, которые типовая x86-карта отдаёт другим блокам: `0xFEC0_0000` и выше (IOAPIC, Local APIC) и верхние 16 MiB под firmware (`0xFF00_0000–0xFFFF_FFFF`). В нашей карте эти адреса пока не назначены.
- База framebuffer выровнена на 64 MiB, длина кратна 2 MiB и host page 16 KiB. Это не требование гостя; выравнивание оставляет свободу будущему отображению памяти на host и BAR в S10-12.
- Discovery-представления карты (E820, UEFI memory map, ACPI; S4-31) не показывают регион `Framebuffer` как usable RAM.
- После S10-12 адрес будет задавать BAR. Фиксированный адрес останется только fallback-профилем для probe.

## 4. Карта регистров

Общие правила для всего окна:

- Каждый регистр — 32 бита, little-endian, выровнен на 4 байта. Допустимый доступ — только `AccessWidth::Dword` по смещению, кратному 4, в пространстве `IoSpace::Mmio`. Остальные доступы — backend-ошибки (раздел 9.2).
- **RO:** запись игнорируется полностью, состояние устройства не меняется, `STATUS` тоже. Поведение одинаково при любом значении и в любом состоянии.
- **RW:** запись сохраняет все 32 бита как есть. Проверка значения откладывается до `MODE_COMMIT`. Чтение возвращает последнее записанное значение.
- **WO:** чтение возвращает `0` и не имеет побочных эффектов.
- **RO + doorbell** (только `FRAME_GENERATION`): чтение возвращает счётчик, значение записи отбрасывается и никогда не сохраняется. Сам факт записи — команда устройству (раздел 6). Правило RW к этому регистру не применяется.
- **Зарезервированное смещение** (любое неназначенное в окне, включая `IRQ_*`): чтение возвращает `0`, запись игнорируется, ошибки нет. Это намеренно: будущий драйвер может проверять регистры версии 2 на устройстве версии 1, не останавливая квант.

| Смещение | Имя | Доступ | Значение после reset | Чтение | Запись, в том числе неверная |
|---|---|---|---|---|---|
| `0x000` | `ID` | RO | `0x4246_444F` (байты в памяти: `O`,`D`,`F`,`B`) | константа | игнорируется |
| `0x004` | `VERSION` | RO | `0x0000_0001` | версия контракта; растёт в S10-13 | игнорируется |
| `0x008` | `CAPS` | RO | `0x0000_0000` | битовая маска возможностей; в версии 1 возможностей нет, все биты зарезервированы под S10-13…S10-15 | игнорируется |
| `0x00C` | `MAX_WIDTH` | RO | `4096` (`0x1000`) | константа | игнорируется |

### 4.1. `STATUS`

| Биты | Поле | Значение |
|---|---|---|
| 0 | `ACTIVE` | 1 — активный режим установлен |
| 1 | `FRAME_SINCE_COMMIT` | 1 — после последнего успешного `MODE_COMMIT` был хотя бы один успешный doorbell, то есть у host есть кадр текущего режима |
| 7:2 | — | резерв, `0` |
| 15:8 | `COMMIT_ERROR` | результат последней записи в `MODE_COMMIT` |
| 23:16 | `FRAME_ERROR` | результат последней записи в `FRAME_GENERATION` |
| 31:24 | — | резерв, `0` |

Коды ошибок (общая нумерация для `COMMIT_ERROR` и `FRAME_ERROR`):

| Код | Имя | Где возникает |
|---|---|---|
| `0x00` | `NONE` | успех |
| `0x01` | `SIZE_NOT_SET` | `MODE_COMMIT`: `WIDTH = 0` или `HEIGHT = 0`, в том числе сразу после reset |
| `0x02` | `UNSUPPORTED_SIZE` | `MODE_COMMIT`: `WIDTH > MAX_WIDTH`, `HEIGHT > MAX_HEIGHT` или `WIDTH × 4 × HEIGHT > FB_SIZE` |
| `0x03` | `UNSUPPORTED_FORMAT` | `MODE_COMMIT`: бит `FORMAT` не установлен в `FORMATS` (включая `FORMAT = 0` и `FORMAT ≥ 32`) |
| `0x04` | `INVALID_COMMAND` | `MODE_COMMIT`: записано значение, отличное от `1` |
| `0x05` | `NO_ACTIVE_MODE` | `FRAME_GENERATION`: doorbell при `ACTIVE = 0` |
| `0x06` | `COUNTER_EXHAUSTED` | `MODE_COMMIT` при `mode_change_count = 2^64 − 1` или doorbell при `generation = 2^64 − 1` |

Остальные коды зарезервированы. Каждое поле перезаписывается только своей командой: ошибка doorbell не стирает ошибку commit, и наоборот.

## 5. `MODE_COMMIT`

Запись значения `v` в `MODE_COMMIT` выполняет проверки по порядку. Срабатывает первая неудачная:

1. `v ≠ 1` → `INVALID_COMMAND`.
2. `WIDTH = 0` или `HEIGHT = 0` → `SIZE_NOT_SET`.
3. `WIDTH > MAX_WIDTH`, `HEIGHT > MAX_HEIGHT` или `WIDTH × 4 × HEIGHT > FB_SIZE` (считается только после двух первых сравнений; раздел 2.1) → `UNSUPPORTED_SIZE`.
4. `FORMAT ≥ 32` или бит `FORMAT` не установлен в `FORMATS` → `UNSUPPORTED_FORMAT`.
5. `mode_change_count = 2^64 − 1` → `COUNTER_EXHAUSTED`.

**Неудача:** меняется только `STATUS.COMMIT_ERROR`. Активный режим (`ACTIVE_*`, `STRIDE`, `STATUS.ACTIVE`), `STATUS.FRAME_SINCE_COMMIT`, `mode_change_count`, `generation`, запрошенные `WIDTH`/`HEIGHT`/`FORMAT` и память framebuffer остаются прежними. Старый режим продолжает показываться.

**Успех** — одно атомарное изменение с точки зрения host, видимое целиком после возврата из `write`:

- `ACTIVE_WIDTH/HEIGHT/FORMAT ← WIDTH/HEIGHT/FORMAT`, `STRIDE ← WIDTH × 4`;
- `STATUS.ACTIVE ← 1`, `STATUS.FRAME_SINCE_COMMIT ← 0`, `STATUS.COMMIT_ERROR ← NONE`;
- `mode_change_count ← mode_change_count + 1`.

Повторный commit того же режима тоже считается сменой режима: счётчик растёт, `FRAME_SINCE_COMMIT` сбрасывается. Память framebuffer при commit не очищается и не перемещается. Host не показывает её содержимое в новом режиме, пока гость не позвонит doorbell (раздел 6).

Выключения режима командой в версии 1 нет. Значения `MODE_COMMIT`, отличные от `1`, зарезервированы и отвергаются кодом `INVALID_COMMAND`.

## 6. `FRAME_GENERATION` и готовность кадра

Гость дописывает кадр в память framebuffer, затем выполняет 32-битную запись любого значения в `FRAME_GENERATION`. Записанное значение отбрасывается.

- **При `ACTIVE = 1` и `generation < 2^64 − 1`:** `generation ← generation + 1`, `frame_mode_epoch ← mode_change_count`, `STATUS.FRAME_SINCE_COMMIT ← 1`, `STATUS.FRAME_ERROR ← NONE`.
- **Иначе:** `generation` и `frame_mode_epoch` не меняются, `STATUS.FRAME_ERROR ←` `NO_ACTIVE_MODE` или `COUNTER_EXHAUSTED`.

`frame_mode_epoch` — внутреннее поле, гостю не видно. Кадр принадлежит текущему режиму, только если `STATUS.ACTIVE = 1`, `generation > 0` и `frame_mode_epoch = mode_change_count`. Проверка `ACTIVE` обязательна: reset при насыщенном `mode_change_count` снимает режим, не меняя счётчик (раздел 8), и без неё равенство эпох ложно сообщило бы о кадре. Так host не прочитает старое содержимое памяти с размером и stride нового режима: после успешного commit кадр текущего режима отсутствует до следующего doorbell.

Host не сканирует память по таймеру и не выводит готовность кадра из записей в framebuffer. Единственный сигнал «кадр готов» — рост `generation`. На это решение опираются S10-06 и S10-08. Порядок записей пикселей и doorbell упорядочен самим исполнением: устройство синхронное, host читает кадр только между квантами (раздел 10.1).

## 7. Память framebuffer и способ backing

### 7.1. Семантика для гостя

- Регион ведёт себя как RAM для **данных**: чтение и запись 1, 2, 4 и 8 байт, невыровненный доступ внутри региона и пересечение гостевой 4 KiB-границы внутри региона разрешены в тех же CPU-профилях, где они разрешены для RAM. Записанные байты читаются обратно без изменений; устройство их не трогает.
- При включении машины память заполнена нулями.
- **Запрещено** (backend-ошибка, раздел 9.2): instruction fetch из региона и размещение в нём структур страничной трансляции (PML4/PDPT/PD/PT). Поэтому page walker никогда не пишет в регион A/D-биты.
- Доступ, пересекающий границу региона, отвергается как `MemoryAccessError::AccessCrossesRegion` / `BusAccessError::CrossesRegion`. Доступ в резерв `0xFA40_0000–0xFBFF_FFFF` отвергается как `MemoryAccessError::Unmapped` / `BusAccessError::UnmappedPhysical`. Это существующие правила `PhysicalMemory` и `MachineBus`.
- DMA и других записей в регион, кроме записей гостя и loader-а машины, в версии 1 нет.

### 7.2. Решение: вариант (б) — новый вид региона `MemoryRegionKind::Framebuffer`

Плану нужен выбор между двумя вариантами:

- **(а)** регион `MemoryRegionKind::Ram` с пометкой назначения;
- **(б)** новый вид региона с собственным backing без callback и вне `RamLimits`.

**Выбран вариант (б).** Сравнение по текущему коду:

| Критерий | (а) `Ram` с пометкой | (б) `Framebuffer` |
|---|---|---|
| Committed-write callback | `PhysicalMemory::write_bytes` вызывает `committed_write` на каждую успешную запись ([physical_memory.rs](../../crates/od-machine/src/physical_memory.rs)), и `MachineBus::write_physical`/`write_flat_bytes` направляют туда каждую RAM-запись ([bus.rs](../../crates/od-machine/src/bus.rs)). Для каждого пикселя сработал бы hook инвалидации кода, что запрещено (S10-03, «Не делать»). Подавить его по пометке значит превратить (а) в (б) со слабой типизацией | Callback — только для `Ram`. Записи в `Framebuffer` его не вызывают |
| `RamLimits` | 36 MiB засчитывались бы в бюджет гостевой RAM и смешивали бюджет RAM с памятью устройства | Backing вне `RamLimits` с отдельным фиксированным пределом (раздел 7.3) |
| Discovery | E820/UEFI map и все проверки `kind == Ram` увидели бы регион как обычную RAM. Каждый потребитель должен помнить про пометку, иначе ОС получит framebuffer как usable RAM | Регион по типу не `Ram`, отдельное представление в discovery-таблицах |
| Безопасность без callback и page generations | — | Callback и page generations нужны потребителям, которые зависят от байтов гостя: кешам транслированного кода и трансляций. На `main` код читается только через `tracked_code_snapshot`/`code_page_generation`, а эти пути требуют `Ram` (7.4). (б) запрещает fetch и page-table структуры в регионе, поэтому ни один такой потребитель от байтов framebuffer не зависит |
| Проверка компилятором | Новых веток нет, легко пропустить место | Новый вариант enum заставляет пересмотреть exhaustive `match`. Сравнения `==`/`!=` и ветки `_`/`Ok(kind)` компилятор не ловит, поэтому они перечислены в 7.4 |
| Цена | Минимум кода сейчас, скрытый долг | Правки в нескольких местах ветвления (7.4) |

### 7.3. Где живёт backing

Backing региона `Framebuffer` принадлежит `PhysicalMemory`, как и RAM. Это сохраняет правило [MACHINE_CONTRACT.md](MACHINE_CONTRACT.md) «Синхронная MMIO/PIO bus»: `MachineBus` не создаёт второй backing и не ведёт независимую карту. `BusDevice` дисплея хранит только регистры и счётчики, байтов кадра у него нет.

- `MachineMemoryMap::new` принимает не больше одного региона `Framebuffer`. Начало и длина кратны 4 KiB, длина ≤ `0x0240_0000`. Нарушение — ошибка построения карты до allocation.
- `PhysicalMemory::new` выделяет zeroed backing через `try_reserve_exact`, как для RAM. Размер не входит в `requested_ram` и не сравнивается с `RamLimits`; верхнюю границу задаёт проверка карты выше. Ошибка выделения — `AllocationFailed` до создания машины.
- Наружу не выдаются mutable slices, raw pointers или долгоживущие ссылки на backing. Host получает байты только копированием (раздел 10).
- **Согласование с устройством.** `FB_BASE` и `FB_SIZE` устройства должны в точности совпадать с началом и длиной региона `Framebuffer` в карте. Проверка выполняется при сборке `MachineBus`, как для `MmioBinding`. Ошибка построения возникает, если:
  - регион `Framebuffer` есть, а дисплейного устройства нет;
  - устройство есть, а региона нет;
  - начало или длина региона не совпадают с регистрами устройства;
  - окно регистров устройства не привязано к региону `Mmio` длины `0x1000`.
- **Требование к S10-03.** Host обращается к устройству через типизированный handle, полученный при создании устройства, по образцу `Uart16550Handle`. Downcast `Box<dyn BusDevice>` из `MachineBus` не используется.

### 7.4. Что затронет S10-03

S10-03 реализует ровно этот вариант. Если он нереализуем, задача останавливается и возвращает вопрос в S10-02.

**База сверки.** S10-02 пишется на ветке `feat/s9-stage`, которая отстаёт от `main` на 20 коммитов (merge-base `336083a`). В ветке нет page generations, `tracked_code_snapshot` и JIT-пути через tracked guest memory (`f300ef8`, `024a6eb`). Поэтому пункты (а)–(д) ниже проверены по `main` (`git show main:crates/od-machine/src/physical_memory.rs`, `main:crates/od-machine/src/bus.rs`, `main:docs/specs/MACHINE_CONTRACT.md`). На `feat/s9-stage` эквивалентного кода может не быть. S10-03 обязан заново сверить каждый пункт с базой, на которой он ведётся.

Обязательные условия безопасности «без callback» (проверены на `main`):

- **(а) Page generations не создаются.** `PhysicalMemory::new` на `main` создаёт `page_generations` только при `kind == Ram`. Для `Framebuffer` выделяется backing без вектора поколений.
- **(б) `write_bytes` пропускает callback и generation lookup.** На `main` `write_bytes` до копирования находит поколения затронутых страниц, проверяет их на переполнение (`CodeGenerationExhausted`), после копирования повышает их и вызывает callback. Для `Framebuffer` нужна отдельная ветка: копирование без lookup, без повышения и без callback. Иначе пустой `page_generations` даст отказ `AddressOverflow` на `get_mut`.
- **(в) Code-API отвергает регион.** `PhysicalMemory::code_page_generation` и `MachineBus::tracked_code_snapshot` на `main` требуют `Ram` (`UnreadableRegion` / `TrackedCodeSnapshotError::NotRam`). Это сохраняется для `Framebuffer`, тест обязателен.
- **(г) На отказе code-API держится аргумент про JIT.** `tracked_code_snapshot` — отдельный путь fetch: tracked `Fetch` с последующей проверкой региона. Через него host получает байты и generation для исполнения. Раз он отвергает `Framebuffer`, у JIT нет кода, зависящего от байтов framebuffer, и поколения там не нужны.
- **(д) Сверка с JIT-путём `od-host`.** На `main` JIT-загрузка идёт через tracked guest memory (`f300ef8`, `with_paged_mov_memory` / `PagedMovMemoryScope`). S10-03 проверяет:
  - данные из `Framebuffer` этим путём читаются как RAM-подобные;
  - ни один путь `od-host` не получает байты кода из `Framebuffer` в обход `tracked_code_snapshot`;
  - инвалидация aliased JIT-кода (`024a6eb`) не предполагает поколений у каждого backed-региона.

Места кода:

- `crates/od-machine/src/physical_memory.rs`:
  - вариант `MemoryRegionKind::Framebuffer`;
  - проверки карты из 7.3;
  - allocation вне `RamLimits`;
  - `write_bytes` вызывает callback и создаёт/повышает page generations только для `Ram` (см. пункт (б) ниже);

- `crates/od-machine/src/page_walk.rs`:

## 8. Счётчики

| Счётчик | Тип | Начало | Рост | Насыщение |
|---|---|---|---|---|
| `generation` | `u64` | `0` при включении машины | +1 на каждый успешный doorbell | при `2^64 − 1` doorbell отвергается кодом `COUNTER_EXHAUSTED`, значение не меняется |
| `mode_change_count` | `u64` | `0` при включении машины | +1 на каждый успешный commit и на каждый reset устройства при `ACTIVE = 1` | при `2^64 − 1` commit отвергается кодом `COUNTER_EXHAUSTED`; reset в этом состоянии счётчик не меняет |
| `frame_mode_epoch` | `u64`, только host | `0` | копия `mode_change_count` при успешном doorbell | — |

Счётчики монотонны всё время жизни объекта устройства. Насыщение практически недостижимо (2^64 событий), но определено, чтобы не было переноса через ноль.

## 9. Ошибки и их класс

### 9.1. Исправимые гостем

Это архитектурный результат устройства. Доступ завершается успешно, квант продолжается, гость видит результат в регистрах.

| Ситуация | Видимый результат | Состояние после |
|---|---|---|
| Commit без установленных размеров (`WIDTH` или `HEIGHT` = 0) | `COMMIT_ERROR = SIZE_NOT_SET` | старый режим (или его отсутствие) и всё остальное без изменений |
| Неподдержанный размер | `COMMIT_ERROR = UNSUPPORTED_SIZE` | то же |
| Неподдержанный формат | `COMMIT_ERROR = UNSUPPORTED_FORMAT` | то же |
| Неверная команда в `MODE_COMMIT` | `COMMIT_ERROR = INVALID_COMMAND` | то же |
| Doorbell без активного режима | `FRAME_ERROR = NO_ACTIVE_MODE` | `generation` без изменений |
| Насыщение счётчика | `COMMIT_ERROR` или `FRAME_ERROR = COUNTER_EXHAUSTED` | счётчик и режим без изменений |
| Запись в RO-регистр | нет: запись игнорируется, `STATUS` не меняется | полностью без изменений |
| Чтение WO-регистра (`MODE_COMMIT`) | возвращает `0` | без изменений |
| Чтение/запись зарезервированного смещения внутри окна | чтение `0`, запись игнорируется | без изменений |
| Запись в `WIDTH`/`HEIGHT`/`FORMAT` любого значения | значение сохраняется, проверка — при commit | меняется только этот регистр |

### 9.2. Backend-ошибки

Это не гостевое исключение. Они останавливают текущий квант машины как backend-результат; гость их не «ловит». Так прямо сказано в [paged_memory_adapter.rs](../../crates/od-machine/src/paged_memory_adapter.rs): «MMIO device errors are backend errors, not guest page faults». По контракту `BusDevice` и разделу «Синхронная MMIO/PIO bus» ошибка возвращается **до** изменения состояния устройства: регистры, счётчики и `STATUS` остаются прежними, операнд не коммитится, само устройство не производит RAM-эффектов и committed-write callback.

Исключение относится к трансляции, не к устройству. В tracked paged-пути page walk коммитит A-биты, а для записи — D-бит leaf, с committed-write callback **до** вызова устройства. При последующем `DeviceError` эти записи остаются: это существующее правило [paged_memory_adapter.rs](../../crates/od-machine/src/paged_memory_adapter.rs) и раздела «S4-06c» [MACHINE_CONTRACT.md](MACHINE_CONTRACT.md).

| Ситуация | Кто обнаруживает | Результат |
|---|---|---|
| Ширина доступа к регистру не 32 бита (`Byte`, `Word`, `Qword`) | устройство | `DeviceError::UnsupportedWidth` |
| 32-битный доступ по смещению, не кратному 4 | устройство | `DeviceError::Misaligned` |
| Доступ, выходящий за конец окна регистров `0x1000` или пересекающий его границу | шина, до вызова устройства | `BusAccessError::CrossesRegion` / `BusAccessError::UnmappedPhysical` в прямом пути; `MmioDispatchError::Backend` в tracked paged-пути. Устройство дополнительно возвращает `DeviceError::UnknownOffset`, если когда-нибудь получит `offset + 4 > 0x1000` |
| Доступ к устройству через `IoSpace::Pio` | устройство | `DeviceError::UnsupportedSpace` (устройство не привязывается к портам) |
| Instruction fetch из окна регистров | шина | существующий отказ «instruction fetch from MMIO is unsupported» |
| Instruction fetch из памяти framebuffer | page walker / adapter (S10-03) | backend-ошибка, не `#PF` |
| Элемент таблицы страниц внутри памяти framebuffer | page walker (S10-03) | backend-ошибка, не `#PF`; A/D-биты не пишутся |

В прямом пути `MachineBus::read_physical`/`write_physical` `DeviceError` приходит как `BusAccessError::Device { device_index, source }`. В tracked paged-пути — как `TrackedAccessError::MmioBackend` → `MemoryError::Backend`.

## 10. Reset и включение машины

**Включение машины** (создание устройства и `PhysicalMemory`):

- все регистры принимают значения из столбца «после reset» раздела 4;
- `generation = 0`, `mode_change_count = 0`, `frame_mode_epoch = 0`;
- активного режима нет: `STATUS = 0`;
- память framebuffer заполнена нулями.

**Reset устройства** — host-операция над handle устройства; гостевой команды reset в версии 1 нет:

- `WIDTH`, `HEIGHT`, `FORMAT`, `ACTIVE_*`, `STRIDE` и `STATUS` возвращаются к значениям после reset; активный режим снимается;
- если режим был активен, `mode_change_count` растёт на 1, и host видит смену режима на «нет режима»;
- `generation` и `frame_mode_epoch` сохраняются: монотонность поколения для host не нарушается. Поэтому `FRAME_GENERATION` после reset устройства может быть ненулевым;
- память framebuffer не очищается. Её содержимое детерминировано, но host его не показывает до нового commit и doorbell.

Reset всей машины, когда он появится, обязан пересоздать устройство или вызвать reset устройства и отдельно определить очистку памяти. Этот документ не вводит общий machine reset.

### 10.1. Что видит host: внутренний Rust API

Host-сторона (`od-host`, S10-04) получает состояние только через Rust API `od-machine`: без Metal, без указателей, без доступа к guest-visible регистрам в обход шины. Имена берутся из S10-03; обязательная семантика такая:

- `current_mode()` — активный режим (`width`, `height`, `stride`, `format`) или явное «режима нет»;
- `frame_generation() -> u64` и `mode_change_count() -> u64`;
- признак наличия кадра текущего режима: `ACTIVE && generation > 0 && frame_mode_epoch == mode_change_count` (раздел 6);
- доступ — через типизированный handle устройства (7.3), без downcast из `MachineBus`;
- `read_frame_into(&mut [u8]) -> Result<FrameInfo, DisplayReadError>` копирует ровно `STRIDE × ACTIVE_HEIGHT` байт с начала памяти framebuffer и возвращает режим, `generation` и `mode_change_count` скопированного кадра. Отказы:
  - нет режима;
  - нет кадра текущего режима;
  - длина буфера не равна размеру кадра;
  - `ModeChanged` — счётчик смены режима различается до и после копирования.
- API только читает: он не звонит doorbell, не сбрасывает ошибки и не меняет регистры. Чтение кадра не влияет на `generation`.
- API вызывается только между квантами исполнения гостя, владельцем `MachineBus`, в том же потоке, который исполняет квант. S10-03 записывает это правило в [MACHINE_CONTRACT.md](MACHINE_CONTRACT.md).

## 11. Соответствие UEFI GOP

`FORMAT = 1` по раскладке байтов совпадает с `PixelBlueGreenRedReserved8BitPerColor` типа `EFI_GRAPHICS_PIXEL_FORMAT` из Graphics Output Protocol в главе «Protocols — Console Support» [UEFI Specification 2.11](https://uefi.org/specs/UEFI/2.11/12_Protocols_Console_Support.html) (UEFI Forum, декабрь 2024). Там пиксель занимает 32 бита: байт 0 — синий, 1 — зелёный, 2 — красный, 3 — зарезервирован. `STRIDE / 4` соответствует `PixelsPerScanLine` при отсутствии паддинга. Номер подраздела в этой сессии не перепроверен: страница uefi.org вернула HTTP 403. S10-18 сверяет его вместе с разделом «Сопоставление с GOP»: какие режимы публиковать как GOP modes. GOP этим документом не реализуется.

## 12. Не входит в версию 1

- **Курсор** — аппаратный слой с позицией и hotspot: [S10-14](../plans/STAGE_10.md#s10-14-курсор), через расширение устройства и feature bit в `CAPS` ([S10-13](../plans/STAGE_10.md#s10-13-протокол-display-only-драйвера-и-расширение-устройства)).
- **Несколько экранов** — [S10-15](../plans/STAGE_10.md#s10-15-несколько-экранов).
- **Список режимов, события смены разрешения, `EVENT_PENDING`, протокол display-only драйвера** — S10-13, `VERSION = 2`; probe S10-08 продолжает работать на версии 1.
- **Прерывания** — `IRQ_*` зарезервированы. Прерываний у устройства нет; S10-13 использует опрос.
- **PCI** (BAR0 — регистры, BAR1 — память, class code display) — [S10-12](../plans/STAGE_10.md#s10-12-привязать-устройство-к-pci); фиксированные адреса раздела 3 останутся fallback-профилем probe.
- **Dirty rects** и отслеживание изменённых участков — только после замеров S10-10. В версии 1 host копирует кадр целиком; записи в framebuffer не отслеживаются.
- Другие форматы пикселя, паддинг stride, выключение режима командой, ускорение, 2D/3D-команды, IOSurface (S10-17).

## 13. Открытые вопросы для ревью

1. **Блокер для S10-08: нет dword MMIO-записей в CPU-пути.**
   - Tracked paged-путь CPU пишет в MMIO только qword (`PagedMovMemoryAdapter::write`: «non-qword writes» не поддержаны), а dword-чтения есть только в отдельном профиле.
   - Контракт требует 32-битного доступа к регистрам. Поэтому без dword MMIO store/load профиля в CPU/machine пути гостевой probe S10-08 не написать: qword-запись в регистр — backend-ошибка `UnsupportedWidth`.
   - Пункт не закрыт. Его нужно решить отдельной задачей до S10-08 или внутри неё. Ширину регистров ради текущего ограничения не расширять до 64 бит.
2. **Адреса раздела 3** выбраны до появления общей карты платы (S4-00/S4-30). Когда появится карта с ECAM, APIC и firmware, отсутствие перекрытий нужно подтвердить заново.
3. **`generation` не сбрасывается reset устройства** (раздел 10) — решение для ревью; альтернатива — пара (эпоха reset, поколение) в транспорте S10-05.
4. **Snapshot/restore:** когда [VM_STATE.md](VM_STATE.md) начнёт описывать устройства, в состояние войдут регистры, три счётчика и 36 MiB памяти framebuffer.
