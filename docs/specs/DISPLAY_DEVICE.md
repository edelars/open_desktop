Документ задаёт guest-visible поведение устройства, адреса для платы без PCI, способ backing памяти framebuffer и host-side Rust API. Регистры и их поведение — собственный проект Open Desktop; они не основаны на карте регистров другого виртуального или физического дисплейного устройства. Из публичных стандартов используется только соответствие формата пикселя UEFI GOP (раздел 11).

Связанные документы: [виртуальная плата](VIRTUAL_BOARD.md) (строка «Экран»), [контракт машины](MACHINE_CONTRACT.md) (разделы «Синхронная MMIO/PIO bus», «Committed writes», «Bounded COM1 polling UART»), [методика проверки изображения](../testing/DISPLAY.md), [отчёт этапа 10](../reports/STAGE_10_REPORT.md).

## 1. Модель и границы

- Устройство состоит из двух непересекающихся регионов гостевой физической карты:
  - **окно регистров** — регион `MemoryRegionKind::Mmio`, к которому привязан `BusDevice` дисплея;
  - **память framebuffer** — регион нового вида `MemoryRegionKind::Framebuffer` (решение и причины — раздел 7).
- Гость меняет режим и сообщает о готовом кадре только через регистры. Пиксели он пишет обычными записями в память framebuffer: без MMIO-dispatch, без вызова устройства и без committed-write callback на каждую запись.
- Устройство синхронное и однопоточное, как остальная `MachineBus`: каждый доступ к регистру выполняется целиком в момент вызова `BusDevice::read`/`write`. Таймеров, фоновых потоков и асинхронных событий у устройства нет. Host не сканирует память по таймеру: о готовом кадре он узнаёт только по `FRAME_GENERATION` (раздел 6).
- Всё guest-visible состояние — 32-битные числа little-endian и байты framebuffer. Устройство не хранит в guest-visible состоянии host pointers, дескрипторы, объекты Metal или IOSurface.

## 2. Первая поддержанная конфигурация

| Параметр | Значение версии 1 |
|---|---|
| Число экранов | 1 |
| Формат пикселя | один: `FORMAT = 1` (`BGRX8888`) — 32 бита на пиксель; в памяти байт 0 = B, байт 1 = G, байт 2 = R, байт 3 = X; как 32-битное little-endian слово пиксель равен `0xXXRRGGBB` |
| Байт X | Гость может писать любое значение. Host при показе его игнорирует и не трактует как alpha; показанный пиксель непрозрачен. Устройство байт не изменяет |
| Stride | `STRIDE = ACTIVE_WIDTH × 4` байт, без паддинга |
| Минимальный размер | 1 × 1 |
| Максимальный размер | `MAX_WIDTH = 4096`, `MAX_HEIGHT = 2304` |
| Размер памяти framebuffer | `FB_SIZE = 4096 × 4 × 2304 = 37 748 736` байт = `0x0240_0000` = ровно 36 MiB |
| Расположение кадра | Пиксель `(x, y)` лежит по адресу `FB_BASE + y × STRIDE + x × 4`; кадр начинается со смещения 0 памяти framebuffer. Байты памяти framebuffer за пределами `STRIDE × ACTIVE_HEIGHT` доступны гостю как память, но host их не читает |

Размеры для замеров S10-10 укладываются в лимит: 1920×1080 даёт 8 294 400 байт, 2560×1600 — 16 384 000 байт.

### 2.1. Проверка переполнения

- Ограничения проверяются **до** любого умножения: `1 ≤ WIDTH ≤ 4096` и `1 ≤ HEIGHT ≤ 2304`. После этого `WIDTH × 4 ≤ 16 384 < 2^15` и `WIDTH × 4 × HEIGHT ≤ 37 748 736 < 2^26`. Оба значения помещаются в `u32` с большим запасом, умножение в `u32` безопасно.
- Если умножить непроверенные гостевые значения, переполнится даже `u64`: `(2^32 − 1) × 4 × (2^32 − 1) ≈ 2^66 > 2^64 − 1`. В `u32` уже `WIDTH × 4` переполняется при `WIDTH ≥ 2^30`. Поэтому реализация либо сначала сравнивает с лимитами, либо считает через `checked_mul` в `u64`/`u128`. Сравнение с лимитом после умножения с переносом запрещено.
- Дополнительная проверка `WIDTH × 4 × HEIGHT ≤ FB_SIZE` в версии 1 избыточна (максимальный кадр равен `FB_SIZE`), но обязательна: будущая версия может уменьшить память, не меняя `MAX_*`.
- Адреса: `FB_BASE + FB_SIZE = 0xF800_0000 + 0x0240_0000 = 0xFA40_0000 ≤ 2^32`; конец окна регистров `0xFC00_0000 + 0x1000 = 0xFC00_1000 ≤ 2^32`. Переполнения нет. Оба региона помещаются в любую ширину физического адреса от 32 бит. Сегодня в `od-machine` встречаются ширины 36 (stage4 probes, часть тестов) и 64 (часть тестов); обе подходят.
- Счётчики `generation` и `mode_change_count` — `u64`; правило насыщения — раздел 8.

## 3. Адреса для платы без PCI

PCI в `od-machine` пока нет ([S4-30](../plans/STAGE_4.md#s4-30-минимальная-pcipcie-configuration)), поэтому версия 1 использует фиксированные адреса. **Значения фиксируются здесь** и продублированы в [VIRTUAL_BOARD.md](VIRTUAL_BOARD.md).

| Регион | GPA начала | Длина | Конец (исключительно) | `MemoryRegionKind` |
|---|---|---|---|---|
| Память framebuffer | `0xF800_0000` | `0x0240_0000` (36 MiB) | `0xFA40_0000` | `Framebuffer` |
| Резерв для памяти дисплея (не отображается в карту, доступ = `BusAccessError::UnmappedPhysical`) | `0xFA40_0000` | `0x01C0_0000` (28 MiB) | `0xFC00_0000` | — |
| Окно регистров | `0xFC00_0000` | `0x1000` (4 KiB) | `0xFC00_1000` | `Mmio` |

Согласование с картой:

- Сегодня у `od-machine` нет общей карты платы. Существующие карты (stage4 probes, тесты `bus.rs`, `page_walk.rs`) содержат только RAM от нуля и тестовые MMIO-окна на малых адресах; выбранные диапазоны их не пересекают. `MachineMemoryMap::new` всё равно отвергает перекрытия.
- Диапазон `[0xF800_0000, 0xFC00_1000)` резервируется под дисплей. Будущая карта платы (S4-00, S4-30, APIC/IOAPIC, ECAM, firmware) не размещает там RAM и другие устройства. RAM ниже 4 GiB заканчивается не выше `0xF800_0000`; остальная RAM лежит выше 4 GiB.
- Выбор оставляет нетронутыми адреса, которые типовая x86-карта отдаёт другим блокам: `0xFEC0_0000` и выше (IOAPIC, Local APIC) и верхние 16 MiB под firmware (`0xFF00_0000–0xFFFF_FFFF`). В нашей карте эти адреса пока не назначены.
- База framebuffer выровнена на 64 MiB, длина кратна 2 MiB и host page 16 KiB. Это не требование гостя; выравнивание оставляет свободу будущему отображению памяти на host и BAR в S10-12.
- Discovery-представления карты (E820, UEFI memory map, ACPI; S4-31) не показывают регион `Framebuffer` как usable RAM.
- После S10-12 адрес будет задавать BAR. Фиксированный адрес останется только fallback-профилем для probe.

## 4. Карта регистров

Общие правила для всего окна:

- Каждый регистр — 32 бита, little-endian, выровнен на 4 байта. Допустимый доступ — только `AccessWidth::Dword` по смещению, кратному 4, в пространстве `IoSpace::Mmio`. Остальные доступы — backend-ошибки (раздел 9.2).
- **RO:** запись игнорируется полностью, состояние устройства не меняется, `STATUS` тоже. Поведение одинаково при любом значении и в любом состоянии.
- **RW:** запись сохраняет все 32 бита как есть. Проверка значения откладывается до `MODE_COMMIT`. Чтение возвращает последнее записанное значение.
- **WO:** чтение возвращает `0` и не имеет побочных эффектов.
- **RO + doorbell** (только `FRAME_GENERATION`): чтение возвращает счётчик, значение записи отбрасывается и никогда не сохраняется. Сам факт записи — команда устройству (раздел 6). Правило RW к этому регистру не применяется.
- **Зарезервированное смещение** (любое неназначенное в окне, включая `IRQ_*`): чтение возвращает `0`, запись игнорируется, ошибки нет. Это намеренно: будущий драйвер может проверять регистры версии 2 на устройстве версии 1, не останавливая квант.

Колонка «Значение после reset» относится к устройству **версии 1**. В устройстве версии 2 все значения те же, кроме двух: `VERSION = 0x0000_0002`, `CAPS = 0x0000_0003` (раздел 14.3). Резервные строки этой таблицы, которые версия 2 занимает (`0x100–0x1FC`, `0x400–0x7FC`), заданы в разделе 14.5.

|---|---|---|
| 0 | `ACTIVE` | 1 — активный режим установлен |
| 1 | `FRAME_SINCE_COMMIT` | 1 — после последнего успешного `MODE_COMMIT` был хотя бы один успешный doorbell, то есть у host есть кадр текущего режима |
| 7:2 | — | резерв, `0` |
| 15:8 | `COMMIT_ERROR` | результат последней записи в `MODE_COMMIT` |

Коды ошибок (общая нумерация для `COMMIT_ERROR` и `FRAME_ERROR`):

| Код | Имя | Где возникает |
|---|---|---|
| `0x00` | `NONE` | успех |
| `0x01` | `SIZE_NOT_SET` | `MODE_COMMIT`: `WIDTH = 0` или `HEIGHT = 0`, в том числе сразу после reset |
| `0x02` | `UNSUPPORTED_SIZE` | `MODE_COMMIT`: `WIDTH > MAX_WIDTH`, `HEIGHT > MAX_HEIGHT` или `WIDTH × 4 × HEIGHT > FB_SIZE` |
| `0x03` | `UNSUPPORTED_FORMAT` | `MODE_COMMIT`: бит `FORMAT` не установлен в `FORMATS` (включая `FORMAT = 0` и `FORMAT ≥ 32`) |
| `0x04` | `INVALID_COMMAND` | `MODE_COMMIT`: записано значение, отличное от `1` |
| `0x05` | `NO_ACTIVE_MODE` | `FRAME_GENERATION`: doorbell при `ACTIVE = 0` |
| `0x06` | `COUNTER_EXHAUSTED` | `MODE_COMMIT` при `mode_change_count = 2^64 − 1` или doorbell при `generation = 2^64 − 1` |

Остальные коды зарезервированы. Каждое поле перезаписывается только своей командой: ошибка doorbell не стирает ошибку commit, и наоборот.

## 5. `MODE_COMMIT`

Запись значения `v` в `MODE_COMMIT` выполняет проверки по порядку. Срабатывает первая неудачная:

1. `v ≠ 1` → `INVALID_COMMAND`.
2. `WIDTH = 0` или `HEIGHT = 0` → `SIZE_NOT_SET`.
3. `WIDTH > MAX_WIDTH`, `HEIGHT > MAX_HEIGHT` или `WIDTH × 4 × HEIGHT > FB_SIZE` (считается только после двух первых сравнений; раздел 2.1) → `UNSUPPORTED_SIZE`.
4. `FORMAT ≥ 32` или бит `FORMAT` не установлен в `FORMATS` → `UNSUPPORTED_FORMAT`.
5. `mode_change_count = 2^64 − 1` → `COUNTER_EXHAUSTED`.

**Неудача:** меняется только `STATUS.COMMIT_ERROR`. Активный режим (`ACTIVE_*`, `STRIDE`, `STATUS.ACTIVE`), `STATUS.FRAME_SINCE_COMMIT`, `mode_change_count`, `generation`, запрошенные `WIDTH`/`HEIGHT`/`FORMAT` и память framebuffer остаются прежними. Старый режим продолжает показываться.

**Успех** — одно атомарное изменение с точки зрения host, видимое целиком после возврата из `write`:

- `ACTIVE_WIDTH/HEIGHT/FORMAT ← WIDTH/HEIGHT/FORMAT`, `STRIDE ← WIDTH × 4`;
- `STATUS.ACTIVE ← 1`, `STATUS.FRAME_SINCE_COMMIT ← 0`, `STATUS.COMMIT_ERROR ← NONE`;
- `mode_change_count ← mode_change_count + 1`.

Повторный commit того же режима тоже считается сменой режима: счётчик растёт, `FRAME_SINCE_COMMIT` сбрасывается. Память framebuffer при commit не очищается и не перемещается. Host не показывает её содержимое в новом режиме, пока гость не позвонит doorbell (раздел 6).

Выключения режима командой в версии 1 нет. Значения `MODE_COMMIT`, отличные от `1`, зарезервированы и отвергаются кодом `INVALID_COMMAND`.

## 6. `FRAME_GENERATION` и готовность кадра

Гость дописывает кадр в память framebuffer, затем выполняет 32-битную запись любого значения в `FRAME_GENERATION`. Записанное значение отбрасывается.

- **При `ACTIVE = 1` и `generation < 2^64 − 1`:** `generation ← generation + 1`, `frame_mode_epoch ← mode_change_count`, `STATUS.FRAME_SINCE_COMMIT ← 1`, `STATUS.FRAME_ERROR ← NONE`.
- **Иначе:** `generation` и `frame_mode_epoch` не меняются, `STATUS.FRAME_ERROR ←` `NO_ACTIVE_MODE` или `COUNTER_EXHAUSTED`.

`frame_mode_epoch` — внутреннее поле, гостю не видно. Кадр принадлежит текущему режиму, только если `STATUS.ACTIVE = 1`, `generation > 0` и `frame_mode_epoch = mode_change_count`. Проверка `ACTIVE` обязательна: reset при насыщенном `mode_change_count` снимает режим, не меняя счётчик (раздел 8), и без неё равенство эпох ложно сообщило бы о кадре. Так host не прочитает старое содержимое памяти с размером и stride нового режима: после успешного commit кадр текущего режима отсутствует до следующего doorbell.

Host не сканирует память по таймеру и не выводит готовность кадра из записей в framebuffer. Единственный сигнал «кадр готов» — рост `generation`. На это решение опираются S10-06 и S10-08. Порядок записей пикселей и doorbell упорядочен самим исполнением: устройство синхронное, host читает кадр только между квантами (раздел 10.1).

## 7. Память framebuffer и способ backing

### 7.1. Семантика для гостя

- Регион ведёт себя как RAM для **данных**: чтение и запись 1, 2, 4 и 8 байт, невыровненный доступ внутри региона и пересечение гостевой 4 KiB-границы внутри региона разрешены в тех же CPU-профилях, где они разрешены для RAM. Записанные байты читаются обратно без изменений; устройство их не трогает.
- При включении машины память заполнена нулями.
- **Запрещено** (backend-ошибка, раздел 9.2): instruction fetch из региона и размещение в нём структур страничной трансляции (PML4/PDPT/PD/PT). Поэтому page walker никогда не пишет в регион A/D-биты.
- Доступ, пересекающий границу региона, отвергается как `MemoryAccessError::AccessCrossesRegion` / `BusAccessError::CrossesRegion`. Доступ в резерв `0xFA40_0000–0xFBFF_FFFF` отвергается как `MemoryAccessError::Unmapped` / `BusAccessError::UnmappedPhysical`. Это существующие правила `PhysicalMemory` и `MachineBus`.
- DMA и других записей в регион, кроме записей гостя и loader-а машины, в версии 1 нет.

### 7.2. Решение: вариант (б) — новый вид региона `MemoryRegionKind::Framebuffer`

Плану нужен выбор между двумя вариантами:

- **(а)** регион `MemoryRegionKind::Ram` с пометкой назначения;
- **(б)** новый вид региона с собственным backing без callback и вне `RamLimits`.

**Выбран вариант (б).** Сравнение по текущему коду:

| Критерий | (а) `Ram` с пометкой | (б) `Framebuffer` |
|---|---|---|
| Committed-write callback | `PhysicalMemory::write_bytes` вызывает `committed_write` на каждую успешную запись ([physical_memory.rs](../../crates/od-machine/src/physical_memory.rs)), и `MachineBus::write_physical`/`write_flat_bytes` направляют туда каждую RAM-запись ([bus.rs](../../crates/od-machine/src/bus.rs)). Для каждого пикселя сработал бы hook инвалидации кода, что запрещено (S10-03, «Не делать»). Подавить его по пометке значит превратить (а) в (б) со слабой типизацией | Callback — только для `Ram`. Записи в `Framebuffer` его не вызывают |
| `RamLimits` | 36 MiB засчитывались бы в бюджет гостевой RAM и смешивали бюджет RAM с памятью устройства | Backing вне `RamLimits` с отдельным фиксированным пределом (раздел 7.3) |
| Discovery | E820/UEFI map и все проверки `kind == Ram` увидели бы регион как обычную RAM. Каждый потребитель должен помнить про пометку, иначе ОС получит framebuffer как usable RAM | Регион по типу не `Ram`, отдельное представление в discovery-таблицах |
| Безопасность без callback и page generations | — | Callback и page generations нужны потребителям, которые зависят от байтов гостя: кешам транслированного кода и трансляций. На `main` код читается только через `tracked_code_snapshot`/`code_page_generation`, а эти пути требуют `Ram` (7.4). (б) запрещает fetch и page-table структуры в регионе, поэтому ни один такой потребитель от байтов framebuffer не зависит |
| Проверка компилятором | Новых веток нет, легко пропустить место | Новый вариант enum заставляет пересмотреть exhaustive `match`. Сравнения `==`/`!=` и ветки `_`/`Ok(kind)` компилятор не ловит, поэтому они перечислены в 7.4 |
| Цена | Минимум кода сейчас, скрытый долг | Правки в нескольких местах ветвления (7.4) |

### 7.3. Где живёт backing

Backing региона `Framebuffer` принадлежит `PhysicalMemory`, как и RAM. Это сохраняет правило [MACHINE_CONTRACT.md](MACHINE_CONTRACT.md) «Синхронная MMIO/PIO bus»: `MachineBus` не создаёт второй backing и не ведёт независимую карту. `BusDevice` дисплея хранит только регистры и счётчики, байтов кадра у него нет.

- `MachineMemoryMap::new` принимает не больше одного региона `Framebuffer`. Начало и длина кратны 4 KiB, длина ≤ `0x0240_0000`. Нарушение — ошибка построения карты до allocation.
- `PhysicalMemory::new` выделяет zeroed backing через `try_reserve_exact`, как для RAM. Размер не входит в `requested_ram` и не сравнивается с `RamLimits`; верхнюю границу задаёт проверка карты выше. Ошибка выделения — `AllocationFailed` до создания машины.
- Наружу не выдаются mutable slices, raw pointers или долгоживущие ссылки на backing. Host получает байты только копированием (раздел 10).
- **Согласование с устройством.** `FB_BASE` и `FB_SIZE` устройства должны в точности совпадать с началом и длиной региона `Framebuffer` в карте. Проверка выполняется при сборке `MachineBus`, как для `MmioBinding`. Ошибка построения возникает, если:
  - регион `Framebuffer` есть, а дисплейного устройства нет;
  - устройство есть, а региона нет;
  - начало или длина региона не совпадают с регистрами устройства;
  - окно регистров устройства не привязано к региону `Mmio` длины `0x1000`.
- **Требование к S10-03.** Host обращается к устройству через типизированный handle, полученный при создании устройства, по образцу `Uart16550Handle`. Downcast `Box<dyn BusDevice>` из `MachineBus` не используется.

### 7.4. Что затронет S10-03

S10-03 реализует ровно этот вариант. Если он нереализуем, задача останавливается и возвращает вопрос в S10-02.

**База сверки.** S10-02 пишется на ветке `feat/s9-stage`, которая отстаёт от `main` на 20 коммитов (merge-base `336083a`). В ветке нет page generations, `tracked_code_snapshot` и JIT-пути через tracked guest memory (`f300ef8`, `024a6eb`). Поэтому пункты (а)–(д) ниже проверены по `main` (`git show main:crates/od-machine/src/physical_memory.rs`, `main:crates/od-machine/src/bus.rs`, `main:docs/specs/MACHINE_CONTRACT.md`). На `feat/s9-stage` эквивалентного кода может не быть. S10-03 обязан заново сверить каждый пункт с базой, на которой он ведётся.

Обязательные условия безопасности «без callback» (проверены на `main`):

- **(а) Page generations не создаются.** `PhysicalMemory::new` на `main` создаёт `page_generations` только при `kind == Ram`. Для `Framebuffer` выделяется backing без вектора поколений.
- **(б) `write_bytes` пропускает callback и generation lookup.** На `main` `write_bytes` до копирования находит поколения затронутых страниц, проверяет их на переполнение (`CodeGenerationExhausted`), после копирования повышает их и вызывает callback. Для `Framebuffer` нужна отдельная ветка: копирование без lookup, без повышения и без callback. Иначе пустой `page_generations` даст отказ `AddressOverflow` на `get_mut`.
- **(в) Code-API отвергает регион.** `PhysicalMemory::code_page_generation` и `MachineBus::tracked_code_snapshot` на `main` требуют `Ram` (`UnreadableRegion` / `TrackedCodeSnapshotError::NotRam`). Это сохраняется для `Framebuffer`, тест обязателен.
- **(г) На отказе code-API держится аргумент про JIT.** `tracked_code_snapshot` — отдельный путь fetch: tracked `Fetch` с последующей проверкой региона. Через него host получает байты и generation для исполнения. Раз он отвергает `Framebuffer`, у JIT нет кода, зависящего от байтов framebuffer, и поколения там не нужны.
- **(д) Сверка с JIT-путём `od-host`.** На `main` JIT-загрузка идёт через tracked guest memory (`f300ef8`, `with_paged_mov_memory` / `PagedMovMemoryScope`). S10-03 проверяет:
  - данные из `Framebuffer` этим путём читаются как RAM-подобные;
  - ни один путь `od-host` не получает байты кода из `Framebuffer` в обход `tracked_code_snapshot`;
  - инвалидация aliased JIT-кода (`024a6eb`) не предполагает поколений у каждого backed-региона.

Места кода:

- `crates/od-machine/src/physical_memory.rs`:
  - вариант `MemoryRegionKind::Framebuffer`;
  - проверки карты из 7.3;
  - allocation вне `RamLimits`;
  - `write_bytes` вызывает callback и создаёт/повышает page generations только для `Ram` (см. пункт (б) ниже);
  - внутренняя copy-out функция для host-чтения кадра.
- `crates/od-machine/src/bus.rs`:
  - `read_physical`: сейчас ветка `_` вернёт `UnreadableRegion`, нужна явная ветка;
  - `write_physical`: exhaustive `match`, нужна ветка без callback;
  - `read_flat_bytes`/`write_flat_bytes`: ветки `kind =>`;
  - `access_tracked` не меняется, он обслуживает только `Mmio`.
- `crates/od-machine/src/page_walk.rs`:
  - классификация операнда `is_mmio` (сейчас `Ok(kind)` отвергает всё, кроме `Ram`/`Mmio`): данные — как RAM без callback, `Fetch` — backend-ошибка;
  - `check_ram` в bounded cross-page read: чтение данных разрешить;
  - чтения элементов таблиц `memory.read_u64(entry_address)` в обоих walker-ах: с появлением backing они начнут проходить, поэтому нужен явный отказ для `Framebuffer`;
  - тестовые наборы видов регионов.
- `crates/od-machine/src/identity_memory_adapter.rs`: fetch проверяет `== Mmio`; без правки fetch из framebuffer пройдёт через `read_flat_bytes`. Нужно условие `!= Ram`.
- `crates/od-machine/src/paged_memory_adapter.rs`: явных веток нет. Новые отказы должны отображаться в `MemoryError::Backend`, а не в `#PF`; нужны тесты.
- `crates/od-machine/src/pio_step.rs`: fetch уже требует `Ram`, правка не нужна, нужен тест.
- `crates/od-machine/src/translation_probe_cache.rs`: проверить, что кеш не предполагает callback для любого backed-региона.
- `crates/od-machine/src/lib.rs`: экспорт нового модуля `display_device.rs`.
- Тесты в `crates/od-machine/tests/`; `tools/bench/src/page_walk_compare.rs` — только сборка.
- `docs/specs/MACHINE_CONTRACT.md`:
  - раздел «Адреса и карта»: backing не только у RAM;
  - раздел «Committed writes» правится **по тексту `main`**, где он уже описывает page generations и проверку до копирования: callback и поколения только для RAM, `Framebuffer` их пропускает;
  - новый раздел устройства по образцу «Bounded COM1 polling UART».

## 8. Счётчики

| Счётчик | Тип | Начало | Рост | Насыщение |
|---|---|---|---|---|
| `generation` | `u64` | `0` при включении машины | +1 на каждый успешный doorbell | при `2^64 − 1` doorbell отвергается кодом `COUNTER_EXHAUSTED`, значение не меняется |
| `mode_change_count` | `u64` | `0` при включении машины | +1 на каждый успешный commit и на каждый reset устройства при `ACTIVE = 1` | при `2^64 − 1` commit отвергается кодом `COUNTER_EXHAUSTED`; reset в этом состоянии счётчик не меняет |
| `frame_mode_epoch` | `u64`, только host | `0` | копия `mode_change_count` при успешном doorbell | — |

Счётчики монотонны всё время жизни объекта устройства. Насыщение практически недостижимо (2^64 событий), но определено, чтобы не было переноса через ноль.

## 9. Ошибки и их класс

### 9.1. Исправимые гостем

Это архитектурный результат устройства. Доступ завершается успешно, квант продолжается, гость видит результат в регистрах.

| Ситуация | Видимый результат | Состояние после |
|---|---|---|
| Commit без установленных размеров (`WIDTH` или `HEIGHT` = 0) | `COMMIT_ERROR = SIZE_NOT_SET` | старый режим (или его отсутствие) и всё остальное без изменений |
| Неподдержанный размер | `COMMIT_ERROR = UNSUPPORTED_SIZE` | то же |
| Неподдержанный формат | `COMMIT_ERROR = UNSUPPORTED_FORMAT` | то же |
| Неверная команда в `MODE_COMMIT` | `COMMIT_ERROR = INVALID_COMMAND` | то же |
| Doorbell без активного режима | `FRAME_ERROR = NO_ACTIVE_MODE` | `generation` без изменений |
| Насыщение счётчика | `COMMIT_ERROR` или `FRAME_ERROR = COUNTER_EXHAUSTED` | счётчик и режим без изменений |
| Запись в RO-регистр | нет: запись игнорируется, `STATUS` не меняется | полностью без изменений |
| Чтение WO-регистра (`MODE_COMMIT`) | возвращает `0` | без изменений |
| Чтение/запись зарезервированного смещения внутри окна | чтение `0`, запись игнорируется | без изменений |
| Запись в `WIDTH`/`HEIGHT`/`FORMAT` любого значения | значение сохраняется, проверка — при commit | меняется только этот регистр |

### 9.2. Backend-ошибки

Это не гостевое исключение. Они останавливают текущий квант машины как backend-результат; гость их не «ловит». Так прямо сказано в [paged_memory_adapter.rs](../../crates/od-machine/src/paged_memory_adapter.rs): «MMIO device errors are backend errors, not guest page faults». По контракту `BusDevice` и разделу «Синхронная MMIO/PIO bus» ошибка возвращается **до** изменения состояния устройства: регистры, счётчики и `STATUS` остаются прежними, операнд не коммитится, само устройство не производит RAM-эффектов и committed-write callback.

Исключение относится к трансляции, не к устройству. В tracked paged-пути page walk коммитит A-биты, а для записи — D-бит leaf, с committed-write callback **до** вызова устройства. При последующем `DeviceError` эти записи остаются: это существующее правило [paged_memory_adapter.rs](../../crates/od-machine/src/paged_memory_adapter.rs) и раздела «S4-06c» [MACHINE_CONTRACT.md](MACHINE_CONTRACT.md).

| Ситуация | Кто обнаруживает | Результат |
|---|---|---|
| Ширина доступа к регистру не 32 бита (`Byte`, `Word`, `Qword`) | устройство | `DeviceError::UnsupportedWidth` |
| 32-битный доступ по смещению, не кратному 4 | устройство | `DeviceError::Misaligned` |
| Доступ, выходящий за конец окна регистров `0x1000` или пересекающий его границу | шина, до вызова устройства | `BusAccessError::CrossesRegion` / `BusAccessError::UnmappedPhysical` в прямом пути; `MmioDispatchError::Backend` в tracked paged-пути. Устройство дополнительно возвращает `DeviceError::UnknownOffset`, если когда-нибудь получит `offset + 4 > 0x1000` |
| Доступ к устройству через `IoSpace::Pio` | устройство | `DeviceError::UnsupportedSpace` (устройство не привязывается к портам) |
| Instruction fetch из окна регистров | шина | существующий отказ «instruction fetch from MMIO is unsupported» |
| Instruction fetch из памяти framebuffer | page walker / adapter (S10-03) | backend-ошибка, не `#PF` |
| Элемент таблицы страниц внутри памяти framebuffer | page walker (S10-03) | backend-ошибка, не `#PF`; A/D-биты не пишутся |

В прямом пути `MachineBus::read_physical`/`write_physical` `DeviceError` приходит как `BusAccessError::Device { device_index, source }`. В tracked paged-пути — как `TrackedAccessError::MmioBackend` → `MemoryError::Backend`.

## 10. Reset и включение машины

**Включение машины** (создание устройства и `PhysicalMemory`):

- все регистры принимают значения из столбца «после reset» раздела 4;
- `generation = 0`, `mode_change_count = 0`, `frame_mode_epoch = 0`;
- активного режима нет: `STATUS = 0`;
- память framebuffer заполнена нулями.

**Reset устройства** — host-операция над handle устройства; гостевой команды reset в версии 1 нет:

- `WIDTH`, `HEIGHT`, `FORMAT`, `ACTIVE_*`, `STRIDE` и `STATUS` возвращаются к значениям после reset; активный режим снимается;
- если режим был активен, `mode_change_count` растёт на 1, и host видит смену режима на «нет режима»;
- `generation` и `frame_mode_epoch` сохраняются: монотонность поколения для host не нарушается. Поэтому `FRAME_GENERATION` после reset устройства может быть ненулевым;
- память framebuffer не очищается. Её содержимое детерминировано, но host его не показывает до нового commit и doorbell.

Reset всей машины, когда он появится, обязан пересоздать устройство или вызвать reset устройства и отдельно определить очистку памяти. Этот документ не вводит общий machine reset.

### 10.1. Что видит host: внутренний Rust API

Host-сторона (`od-host`, S10-04) получает состояние только через Rust API `od-machine`: без Metal, без указателей, без доступа к guest-visible регистрам в обход шины. Имена берутся из S10-03; обязательная семантика такая:

- `current_mode()` — активный режим (`width`, `height`, `stride`, `format`) или явное «режима нет»;
- `frame_generation() -> u64` и `mode_change_count() -> u64`;
- признак наличия кадра текущего режима: `ACTIVE && generation > 0 && frame_mode_epoch == mode_change_count` (раздел 6);
- доступ — через типизированный handle устройства (7.3), без downcast из `MachineBus`;
- `read_frame_into(&mut [u8]) -> Result<FrameInfo, DisplayReadError>` копирует ровно `STRIDE × ACTIVE_HEIGHT` байт с начала памяти framebuffer и возвращает режим, `generation` и `mode_change_count` скопированного кадра. Отказы:
  - нет режима;
  - нет кадра текущего режима;
  - длина буфера не равна размеру кадра;
  - `ModeChanged` — счётчик смены режима различается до и после копирования.
  - Сверка с кодом S10-03 (при написании версии 2): реализация принимает ещё `&MachineBus` (`read_frame_into(&MachineBus, &mut [u8])`) и добавляет пятый отказ `Memory` (ошибка чтения региона). Семантику выше это не меняет; реализованная сигнатура записана в [MACHINE_CONTRACT.md](MACHINE_CONTRACT.md), «Display device (S10-03)».
- API только читает: он не звонит doorbell, не сбрасывает ошибки и не меняет регистры. Чтение кадра не влияет на `generation`.
- API вызывается только между квантами исполнения гостя, владельцем `MachineBus`, в том же потоке, который исполняет квант. S10-03 записывает это правило в [MACHINE_CONTRACT.md](MACHINE_CONTRACT.md).

## 11. Соответствие UEFI GOP

`FORMAT = 1` соответствует `PixelBlueGreenRedReserved8BitPerColor`.
Четыре байта пикселя содержат синий, зелёный, красный и зарезервированный
каналы в этом порядке. `PixelsPerScanLine` равен `STRIDE / 4`.
GOP публикует список режимов основного экрана из таблицы устройства
версии 2 (раздел 14.6) в том же порядке. Установка режима и запись через
`Blt` публикуют кадр записью регистра `FRAME_GENERATION`.
[Профиль GOP прошивки](UEFI_PROFILE.md#gop),
[UEFI 2.11, §12.9](https://uefi.org/specs/UEFI/2.11/12_Protocols_Console_Support.html#graphics-output-protocol).

1. **Блокер для S10-08 «нет dword MMIO-записей в CPU-пути» — снят (решение Opus high, архитектурная рекомендация; запись решения — [STAGE_10.md, S10-08](../plans/STAGE_10.md#s10-08-сделать-гостевой-probe-дисплея); решение координатора: Opus high, 2026-11-22).**

Этот путь **не расширяется**: ширину регистров до 64 бит не расширять, dword-запись в stage4-путь ради probe не добавлять.

Это подтверждено тестами `firmware_display_mmio_commits_the_bound_device_and_publishes_a_frame` (dword-чтение `ID`, dword-записи `WIDTH`/`HEIGHT`/`FORMAT`/`MODE_COMMIT`/`FRAME_GENERATION`: режим 640×480 установлен, `generation = 1`) и `firmware_display_mmio_rejects_a_wide_register_write_before_retirement` (qword-запись в регистр отвергается до выполнения инструкции: `UnsupportedWidth`, `generation = 0`) в `crates/od-machine/src/firmware_board.rs`, а также приёмкой S7-15 (GOP собственной UEFI пишет регистры как `u32`).
   - Решение: гостевой probe S10-08 загружается и исполняется путём платы firmware (образ ODFWIMG1, `load_firmware_image`, `run_boot`), а не через `stage4_flat_probe`. Реализация и проверка — S10-08 (`stage10_display_probe`); для гостевых ОС этапов 5 и 8 путь платы firmware поддерживает dword MMIO, отдельной задачи не требуется.
2. **Адреса раздела 3** выбраны до появления общей карты платы (S4-00/S4-30). Когда появится карта с ECAM, APIC и firmware, отсутствие перекрытий нужно подтвердить заново.
3. **`generation` не сбрасывается reset устройства** (раздел 10) — решение для ревью; альтернатива — пара (эпоха reset, поколение) в транспорте S10-05.
4. **Snapshot/restore:** когда [VM_STATE.md](VM_STATE.md) начнёт описывать устройства, в состояние войдут регистры, три счётчика и 36 MiB памяти framebuffer.

### 14.2. Правило совместимости с версией 1

Устройство версии 2 — строгое надмножество версии 1:

1. Все регистры версии 1 (раздел 4) сохраняют смещения, классы доступа, значения после reset и поведение. То же верно для `MODE_COMMIT`, doorbell, `STATUS`, кодов `0x00–0x06`, счётчиков, памяти framebuffer, backend-ошибок, reset и host API раздела 10.1. Меняются только значения RO-регистров `VERSION` (`1 → 2`) и `CAPS` (`0 → 0x3`).
2. Новые регистры версии 2 занимают только смещения, которые версия 1 объявила резервными: `0x100–0x1FC` и `0x400–0x7FC`. Остальные резервные смещения версии 1 остаются резервными с тем же правилом: чтение `0`, запись игнорируется. Смещения `0x0C0–0x0C8` (`IRQ_*`) не трогаются.
   - Блоки `0x200–0x2FC` и `0x300–0x3FC` закреплены за функциями курсора (S10-14) и второго экрана (S10-15), а не за номером версии.
   - Регистры там могут появиться без смены `VERSION`, но только вместе с установленным битом `CAPS` своей функции (14.3).
   - Пока бит равен `0`, блок — обычный резерв.
   - Других смещений эти функции без смены `VERSION` не занимают.
3. Механизм событий **инертен**, пока гость не записал поддержанную версию в `DRIVER_PROTOCOL`. До этого `EVENT_PENDING = 0`, а host API отвергает постановку запроса (`NoDriver`, 14.13). Гость версии 1 этот регистр не пишет, поэтому событий у него никогда нет, и host показывает его кадр масштабированием (S10-11).
4. Таблица режимов и `MODE_COUNT` — чистое RO-чтение без побочных эффектов. Гость версии 1 их не читает.

Обязанности гостя, без которых правило не работает (они же в протоколе, раздел 10):

- проверять `VERSION ≥ N` нужной ревизии, а не равенство;
- игнорировать неизвестные биты `CAPS`;
- не писать в смещения, не определённые в нужной гостю ревизии.

Probe S10-08 по своему плану пишет `WIDTH`, `HEIGHT`, `FORMAT`, `MODE_COMMIT`, `FRAME_GENERATION` и читает `STATUS`; `VERSION` и `CAPS` он не сравнивает. Поэтому на устройстве версии 2 он работает без изменений. Если S10-08 будет проверять версию, проверка — `VERSION ≥ 1`.

Отдельного «режима версии 1» у устройства нет: одно устройство обслуживает оба вида гостей. Причина: пункт 3 уже даёт гостю версии 1 его поведение, а второй профиль удвоил бы тесты без нового покрытия.

### 14.3. `VERSION` и `CAPS`

`VERSION = 0x0000_0002`. Номер означает ревизию контракта, которую реализует устройство; ревизия `N` — надмножество ревизии `N − 1` по правилу 14.2. Опциональные блоки внутри ревизии обнаруживаются только по битам `CAPS`.

| Бит `CAPS` | Имя | Версия 2 | Значение |
|---|---|---|---|
| 0 | `MODE_LIST` | `1` | есть `MODE_COUNT` и таблица режимов (14.6) |
| 1 | `EVENTS` | `1` | есть `DRIVER_PROTOCOLS`/`DRIVER_PROTOCOL`, `EVENT_STATUS`, очередь событий, `MODE_REQUEST` и ответ на него (14.7–14.9) |
| 2 | `CURSOR` | `0`, **зарезервирован** за S10-14; после реализации раздела 15 — `1` | аппаратный курсор; блок `0x200–0x2FC` (раздел 15) |
| 3 | `SECOND_SCREEN` | `0`, **зарезервирован** за S10-15 | второй экран; регистров нет |
| 31:4 | — | `0` | резерв |

`CAPS = 0x0000_0003`. В устройстве ревизии 2 биты 0 и 1 всегда равны `1`. Они заданы, чтобы драйвер проверял любой блок одним способом, по `CAPS`, а не сочетанием версии и битов.

Правило для S10-14 и S10-15 — то же, что 14.2, пункт 2. Блок курсора занимает только `0x200–0x2FC` и существует только при бите 2. Блок второго экрана занимает только `0x300–0x3FC` и существует только при бите 3. В этих пределах и без изменения смысла существующих регистров `VERSION` остаётся `2`, потому что блоки опциональны и видны только по `CAPS`. Если функции нужно больше места или изменение существующего регистра, `VERSION = 3`. Пока задачи не приняты, бит равен `0`, блока нет, его смещения — резерв.

### 14.4. Новый класс доступа: RW с проверкой

К правилам раздела 4 добавляется класс для `DRIVER_PROTOCOL`.

**RW с проверкой:** запись проверяется сразу. Допустимое значение применяется. Недопустимое не меняет регистр и записывает код ошибки в своё поле `EVENT_STATUS`. Чтение возвращает текущее применённое значение.

Остальные новые регистры используют классы версии 1: RO, RW (хранит 32 бита как есть) и WO (чтение `0`). Команды записываются в WO-регистры, как `MODE_COMMIT`.

### 14.6. Список режимов

**Решение: таблица только для чтения в окне регистров** (`MODE_COUNT` + `MODE_TABLE`), а не индексный регистр и не таблица в памяти гостя.

| Вариант | Плюсы | Минусы |
|---|---|---|
| Индекс + окно записи (`MODE_INDEX` RW, `MODE_INFO_*` RO) | 4 регистра при любом размере списка | Скрытое состояние: индекс нужно сбрасывать, сохранять в snapshot и защищать от гонки двух потоков драйвера, которые перечисляют режимы одновременно. Лишняя запись на каждую запись списка |
| Таблица в памяти гостя (RAM или framebuffer) | Драйвер читает обычной памятью | DMA у устройства нет (7.1). Запись устройства в RAM пошла бы через committed-write callback и инвалидацию JIT (раздел «Committed writes» `MACHINE_CONTRACT.md`), нужны проверка адреса, заданного гостем, и порядок записи. Таблица внутри framebuffer пересекается с байтами кадра: кадр начинается со смещения 0 и может занимать весь `FB_SIZE`. Отдельный регион потребовал бы нового вида региона и новых проверок сборки шины |
| **Таблица RO в окне регистров** | Без состояния и побочных эффектов, без гонок, тот же синхронный путь MMIO, без новых регионов и без DMA. Reset и snapshot её не касаются | Занимает 1 KiB окна; предел — 64 записи |

Цена выбранного варианта — три MMIO-чтения на запись, 42 чтения на весь список. Перечисление выполняется один раз при запуске драйвера, путь не критичен по скорости, поэтому замер для выбора не нужен.

Свойства:

- `1 ≤ MODE_COUNT ≤ 64`. Записи уникальны и упорядочены по возрастанию `(width, height)`. Каждая проходит проверки `MODE_COMMIT` 2–4 (раздел 5).
- Список — константа устройства ревизии 2. Он не зависит от host и не меняется за время жизни экземпляра; reset его не трогает.
- **Список не ограничивает `MODE_COMMIT`.** Commit принимает любой размер по правилам версии 1. Это сохраняет поведение версии 1 (probe S10-08 ставит 64×48, которого в списке нет) и позволяет установить размер окна из `MODE_REQUEST`.
- Предпочтительного режима в списке нет. Желаемый размер host сообщает только `MODE_REQUEST`.

### 14.7. Очередь событий

**Состояние** (guest-visible через регистры 14.5):

- `queue` — FIFO записей `{seq: u64, type: u32, arg: [u32; 4]}`, не больше `EVENT_CAPACITY = 16` записей;
- `latch` — запись, взятая гостем; нулевая (`seq = 0`, `type = 0`) — пусто;
- `next_event_seq: u64` — `1` при включении машины.

Запись — 28 байт (8 + 4 + 4 × 4), 7 регистров защёлки. Вся очередь — 16 × 28 = 448 байт состояния. Смысл типов и аргументов — DISPLAY_DRIVER_V1.md, раздел 5.

**Ёмкость 16.** В версии 2 существует один тип события (`MODE_REQUEST`), и объединение держит в очереди не больше одного `MODE_REQUEST` на экран. Значит, сейчас в очереди не бывает больше одной записи, а с S10-15 — больше двух. Остальная ёмкость — запас под события, которые добавят S10-14/S10-15 (например, подключение и отключение экрана) без смены раскладки. Цена запаса — 448 байт. Ёмкость видна гостю в `EVENT_CAPACITY`, и драйвер не должен считать её константой.

**`EVENT_POP ← v`** — проверки по порядку, срабатывает первая неудачная:

1. `v ≠ 1` → `POP_ERROR = INVALID_COMMAND`.
2. `DRIVER_PROTOCOL = 0` → `NOT_ENABLED`.
3. Очередь пуста → `QUEUE_EMPTY`.

При неудаче меняется только `POP_ERROR`, защёлка остаётся прежней. При успехе: `latch ← голова`, голова удаляется, `POP_ERROR ← NONE`.

Защёлку меняют только успешный `EVENT_POP`, `DRIVER_PROTOCOL ← 0` и reset. Поэтому гость читает её несколькими доступами без разрыва, даже если между ними прошли кванты и host ставил события. Это то же рассуждение, что для `FRAME_GENERATION`/`_HI` в разделе 4.

**Постановка события** — только host, только между квантами (правило 10.1). Для типа с объединением сначала определяется удаляемая запись (для `MODE_REQUEST` — 14.8). Затем проверки по порядку, все до любого изменения:

1. `DRIVER_PROTOCOL = 0` → отказ `NoDriver`.
2. Аргументы недопустимы для типа → отказ (для `MODE_REQUEST` — `InvalidMode`).
3. `next_event_seq = 2^64 − 1` → отказ `SequenceExhausted`.
4. После удаления объединяемой записи в очереди нет свободного места → отказ `QueueFull`.

При отказе очередь, защёлка, открытый запрос и `next_event_seq` не меняются. При успехе объединяемая запись удаляется, новая получает `seq ← next_event_seq` и ставится в хвост, `next_event_seq` растёт на 1.

**Политика переполнения: отказ новому, старые не сбрасываются.**

| Вариант | Оценка |
|---|---|
| Сбрасывать старые | Гость теряет событие, о котором не знает. Нужен флаг или счётчик переполнения и процедура пересинхронизации в каждом драйвере (Linux, Windows): больше кода в ядре гостя. Сброс без учёта типа может выбросить событие другого типа, например подключение экрана, ради очередного запроса размера. Запрос, сброшенный до того, как гость его увидел, остался бы у host «ожидающим» без ответа |
| **Отказывать новому** (выбрано) | Отказ получает host синхронно в точке вызова. Host владеет желаемым состоянием (размер окна) и повторит постановку позже, ничего не потеряв. Гость видит упорядоченную последовательность без потерь, и в драйвере нет кода обработки переполнения. Очередь не растёт, когда гость не потребляет события (драйвера нет, драйвер завис) |

Семантику «важно только последнее» обеспечивает не сброс, а **объединение по типу**: оно определено для каждого типа явно (в версии 2 — только `MODE_REQUEST`) и не задевает события других типов. Для `MODE_REQUEST` отказ `QueueFull` в версии 2 недостижим: объединение освобождает место, а других типов нет. Ветку проверяют через внутренний тестовый хук, как `ModeChanged` в S10-03 (14.14).

**Номера событий.** `seq` уникален за всё время жизни экземпляра устройства и строго растёт. Reset `next_event_seq` не сбрасывает, поэтому номер запроса, выданный до reset, не совпадёт ни с одним номером после него. Насыщение при `2^64 − 1` практически недостижимо, но определено, как для счётчиков раздела 8.

### 14.8. Запрос смены разрешения

**Состояние:** `mode_request` — последний поставленный запрос экрана 0 или «запросов не было». Поля:

- `seq`;
- `width`, `height`, `format`;
- `outcome` ∈ {`Pending`, `Accepted`, `Rejected(reason)`, `Superseded`, `Cancelled`}.

Открыт только запрос в состоянии `Pending`.

**Постановка** (`post_mode_request`, 14.13):

- Допустимость аргументов (шаг 2 из 14.7): `width`, `height`, `format` проходят проверки `MODE_COMMIT` 2–4 (раздел 5); экран только 0. Иначе — `InvalidMode`. Это host-ошибка вызова, не гостевая.
- Объединение: если в очереди есть ещё не взятый `MODE_REQUEST` экрана 0, он удаляется.
- При успехе предыдущий `mode_request` в состоянии `Pending` переходит в `Superseded`. Новый становится `mode_request` в состоянии `Pending`, в очередь ставится запись `type = 1`, `arg = [width, height, format, 0]`.

**`REQUEST_RESPONSE ← v`** — кодирование `v` задаёт DISPLAY_DRIVER_V1.md, 6.1. Номер запроса `S = RESPONSE_SEQ_HI << 32 | RESPONSE_SEQ_LO`. Проверки по порядку, срабатывает первая неудачная:

1. `v` не является допустимым значением по таблицам DISPLAY_DRIVER_V1.md, 6.1 → `RESPONSE_ERROR = INVALID_COMMAND`.
2. `DRIVER_PROTOCOL = 0` → `NOT_ENABLED`.
3. Нет открытого запроса или `S ≠ mode_request.seq` → `STALE_REQUEST`.
4. `verdict = ACCEPT`, а `STATUS.ACTIVE = 0` или (`ACTIVE_WIDTH`, `ACTIVE_HEIGHT`, `ACTIVE_FORMAT`) ≠ (`width`, `height`, `format`) запроса → `MODE_MISMATCH`.

При неудаче меняется только `RESPONSE_ERROR`, запрос остаётся открытым. При успехе `outcome ← Accepted` или `Rejected(reason)`, `RESPONSE_ERROR ← NONE`. Повторный ответ на закрытый запрос даёт `STALE_REQUEST`.

**Почему `ACCEPT` проверяет активный режим, а не применяет его сам.** Режим меняет по-прежнему только `MODE_COMMIT`, один путь с проверками версии 1. ОС гостя устанавливает режим своим путём и в своё время (в драйвере ОС commit идёт из её процедуры установки режима), поэтому драйвер отвечает после commit. Проверка не даёт драйверу ответить `ACCEPT`, не установив режим: для host `Accepted` значит «режим установлен».

Устройство не закрывает запросы по времени: таймеров у него нет (раздел 1).

### 14.9. `DRIVER_PROTOCOL`

Запись `v` (класс «RW с проверкой», 14.4):

| `v` | Текущее значение | Результат |
|---|---|---|
| `0` | любое | Протокол выключен: очередь очищается, защёлка обнуляется, открытый запрос → `Cancelled`. Регистр ← `0`. Режим, framebuffer, `MODE_COMMIT`/doorbell, `RESPONSE_SEQ_*` и `next_event_seq` не меняются. `PROTOCOL_ERROR ← NONE` |
| `v < 32`, бит `v` есть в `DRIVER_PROTOCOLS` | `0` | Протокол включён: регистр ← `v`; очередь уже пуста. `PROTOCOL_ERROR ← NONE` |
| то же | `= v` | Состояние не меняется, `PROTOCOL_ERROR ← NONE` |
| то же | другое ненулевое | `PROTOCOL_ERROR ← UNSUPPORTED_PROTOCOL`, состояние не меняется: переход между версиями только через `0`. В версии 2 недостижимо, поддержана одна версия |
| остальные | любое | `PROTOCOL_ERROR ← UNSUPPORTED_PROTOCOL`, состояние не меняется |

Host видит `DRIVER_PROTOCOL` через `driver_protocol()` (14.13). По переходу `0 → 1` host узнаёт, что драйвер готов, и может поставить запрос с текущим размером окна.

### 14.10. `EVENT_STATUS` и новые коды ошибок

| Биты | Поле | Результат последней записи в |
|---|---|---|
| 7:0 | `POP_ERROR` | `EVENT_POP` |
| 15:8 | `RESPONSE_ERROR` | `REQUEST_RESPONSE` |
| 23:16 | `PROTOCOL_ERROR` | `DRIVER_PROTOCOL` |
| 31:24 | — | резерв, `0` |

Каждое поле перезаписывает только своя команда, как в `STATUS` (раздел 4.1). `STATUS` версии 1 не меняется: ошибки версии 2 в него не попадают, его резервные биты остаются `0`.

Коды продолжают общую нумерацию таблицы 4.1. `0x00 NONE` и `0x04 INVALID_COMMAND` используются повторно. Новые коды:

| Код | Имя | Где возникает |
|---|---|---|
| `0x07` | `NOT_ENABLED` | `EVENT_POP`, `REQUEST_RESPONSE` при `DRIVER_PROTOCOL = 0` |
| `0x08` | `QUEUE_EMPTY` | `EVENT_POP` при пустой очереди |
| `0x09` | `STALE_REQUEST` | `REQUEST_RESPONSE`: нет открытого запроса с этим `seq` (не было, вытеснен, отвечен, отменён) |
| `0x0A` | `MODE_MISMATCH` | `REQUEST_RESPONSE`: `ACCEPT`, но активный режим не равен запрошенному |
| `0x0B` | `UNSUPPORTED_PROTOCOL` | `DRIVER_PROTOCOL`: значение не поддержано, или переход между двумя ненулевыми версиями |

**Класс ошибок.** Все ошибки версии 2 исправимы гостем (раздел 9.1): доступ завершается успешно, результат виден в `EVENT_STATUS`. Запись в RO-регистры версии 2 и в резерв игнорируется, `EVENT_STATUS` не меняется. Backend-ошибки (9.2) для новых смещений те же: ширина, выравнивание, пространство, выход за окно. Ошибки host API (`NoDriver`, `InvalidMode`, `QueueFull`, `SequenceExhausted`) — результаты вызова host, гость их не видит.

### 14.11. Опрос вместо прерываний

Прерываний у устройства нет: `IRQ_STATUS`/`IRQ_MASK`/`IRQ_ACK` остаются резервом, MSI нет до PCI (S10-12). Гость узнаёт о событиях **только опросом** `EVENT_PENDING`. В каждом шаге опроса он также читает `DRIVER_PROTOCOL`: после reset устройства (14.12) это поле равно `0`, а `EVENT_PENDING` остаётся `0` навсегда. По `DRIVER_PROTOCOL = 0` драйвер повторяет инициализацию, включая установку режима. Устройство не требует опроса для корректности и само не отслеживает время.

Период опроса драйвера — **100 мс номинально, не больше 200 мс между опросами в установившемся режиме**. Нормативное определение, обоснование и выборка до опустошения очереди — DISPLAY_DRIVER_V1.md, раздел 7. Период — гипотеза до замеров S10-21/S10-22.

Если прерывания появятся, их введёт новая версия протокола или новый бит `CAPS`. Опрос останется допустимым.

### 14.12. Reset и включение машины

**Включение машины** — к разделу 10 добавляется:

- `DRIVER_PROTOCOL = 0`, очередь пуста, защёлка нулевая;
- `RESPONSE_SEQ_LO/HI = 0`, `EVENT_STATUS = 0`;
- `next_event_seq = 1`, запросов не было.

**Reset устройства** — к разделу 10 добавляется:

- те же действия, что `DRIVER_PROTOCOL ← 0` (14.9): открытый запрос → `Cancelled`;
- `RESPONSE_SEQ_LO/HI ← 0`, `EVENT_STATUS ← 0`;
- `next_event_seq` сохраняется, как `generation`: номера не повторяются;
- список режимов не меняется.

Snapshot (13.4) дополнительно включает `DRIVER_PROTOCOL`, очередь, защёлку, `next_event_seq`, `mode_request`, `RESPONSE_SEQ_*` и `EVENT_STATUS`.

### 14.13. Host API: дополнение к 10.1

Имена задаёт реализация. Обязательная семантика:

- `driver_protocol() -> u32` — текущее значение `DRIVER_PROTOCOL`; `0` — драйвера нет.
- `post_mode_request(width, height, format) -> Result<u64, …>` — ставит `MODE_REQUEST` экрана 0 по 14.7/14.8 и возвращает его `seq`. Отказы: `NoDriver`, `InvalidMode`, `QueueFull`, `SequenceExhausted`; при отказе состояние не меняется.
- `mode_request_state()` — последний поставленный запрос (`seq`, режим, `outcome`) или «запросов не было». У последнего запроса `outcome` бывает `Pending`, `Accepted`, `Rejected` или `Cancelled`. `Superseded` получает только вытесненный запрос, а он из этого API уже не виден.
- Правило вызова то же: только между квантами, владельцем `MachineBus`, в потоке, исполняющем кванты, через типизированный `DisplayHandle` (7.3, 10.1).
- Существующие функции 10.1 не меняются. `read_frame_into` не зависит от событий.

Передача запроса из окна UI через VMHost и C ABI `od-host` в этот API в S10-13 не входит. Это открытый вопрос 14.15.1.

Unit-тесты в `display_device.rs` и интеграционные в `crates/od-machine/tests/display_device.rs`:

1. **Совместимость с версией 1:**
   - все существующие тесты версии 1 проходят; ожидаемые значения меняются только у `VERSION` (`2`) и `CAPS` (`0x3`);

   - `post_mode_request` без драйвера → `NoDriver`, `EVENT_PENDING = 0`.
2. Значения после reset всех регистров 14.5. Запись `0xFFFF_FFFF` в каждый RO-регистр и резерв версии 2 не меняет ни его, ни `EVENT_STATUS`, ни `STATUS`.
3. Таблица режимов совпадает с 14.6. Записи с `i ≥ MODE_COUNT` и поле `+0xC` читаются `0`. Каждая запись проходит `MODE_COMMIT`.
4. `DRIVER_PROTOCOL`: все строки таблицы 14.9, в том числе `0 → 1 → 1 → 0`, неподдержанные `2`, `32`, `0xFFFF_FFFF`.
5. Очередь: постановка → `EVENT_PENDING = 1` → `EVENT_POP` → значения защёлки. `EVENT_POP` на пустой очереди → `QUEUE_EMPTY`, защёлка прежняя. `EVENT_POP ← 0` и `← 2` → `INVALID_COMMAND`. `EVENT_POP` при выключенном протоколе → `NOT_ENABLED`.
6. Объединение:
   - два запроса подряд → `EVENT_PENDING = 1`, в защёлке второй;
   - запрос, взятый в защёлку, затем новый → ответ на старый `STALE_REQUEST`, новый в очереди.
7. Ответ:
   - `ACCEPT` без commit → `MODE_MISMATCH`; commit, затем `ACCEPT` → `Accepted`;
   - `ACCEPT`, когда режим уже равен запрошенному, без commit → `Accepted`;
   - каждая причина `REJECT`;
   - все неверные кодирования (1);
   - чужой `seq`, в том числе отличающийся только в `RESPONSE_SEQ_HI`;
   - повторный ответ → `STALE_REQUEST`.
8. Отказы host API: каждый отказ 14.7 по порядку проверок без изменения состояния. `QueueFull` и `SequenceExhausted` — через внутренний тестовый хук (заполнение очереди записями без объединения; установка `next_event_seq`).
9. Reset: открытый запрос → `Cancelled`; очередь, защёлка и `DRIVER_PROTOCOL` обнулены; `seq` первого запроса после reset больше любого до reset.
10. Backend-ошибки на смещениях версии 2 (`Byte`/`Word`/`Qword`, невыровненное, PIO) — до изменения состояния.

Реализация обновляет раздел «Display device (S10-03)» в [MACHINE_CONTRACT.md](MACHINE_CONTRACT.md): ревизия 2, новые регистры, правило вызова host API постановки. Строка «Экран» в [VIRTUAL_BOARD.md](VIRTUAL_BOARD.md) обновляется после ревью этого раздела.

## 15. Курсор (S10-14)

**Статус:** написано в задаче [S10-14](../plans/STAGE_10.md#s10-14-курсор), **ожидает ревью**; код не начат. Реализация — отдельная задача: `crates/od-machine/src/display_device.rs`, display host ABI, VMHost, UI. Передача в UI нормативна в [FRAME_TRANSPORT_V1.md](../../protocols/control/FRAME_TRANSPORT_V1.md), раздел 10 (frame transport v2).

### 15.1. Что добавляется

Аппаратный курсор — маленькое изображение с позицией и hotspot, которое host накладывает при показе поверх кадра. Кадр гостя курсор не меняет. Гость рисует курсор один раз (при смене формы), а перемещает одной записью регистра, без перерисовки кадра и без doorbell.

| Что | Где нормативно |
|---|---|
| Регистры, классы доступа, значения после reset, порядок проверок, коды ошибок, формат и память образа, счётчики курсора, reset, host API | этот раздел |
| Раскладка разделяемой памяти курсора, сообщение `CURSOR`, seqlock курсора, наложение в просмотрщике | FRAME_TRANSPORT_V1.md, раздел 10 |
| Последовательность драйвера (установка формы, перемещение, повторная инициализация после reset) | [DISPLAY_DRIVER_V1.md](../../protocols/guest/DISPLAY_DRIVER_V1.md); дополняется задачей реализации (15.15, п. 4) |

### 15.2. Совместимость

- Курсор — опциональный блок ревизии 2 по правилу 14.2, п. 2 и 14.3. Он занимает только смещения `0x200–0x2FC` и существует только при `CAPS` бит 2 = `1`. `VERSION` остаётся `2`. С реализацией этого раздела `CAPS = 0x0000_0007`. Других смещений, других регионов карты и изменений существующих регистров нет. Поэтому `VERSION = 3` не нужна.
- Драйвер, не знающий курсора (гость версии 1, драйвер ревизии 2 без S10-14), бит 2 игнорирует (14.2) и в блок не пишет. Пока гость не включил курсор (`CURSOR_ENABLE = 0`, состояние после reset), host его не показывает. Поведение кадра для такого гостя не меняется.
- Probe S10-08 пишет только регистры версии 1 и не сравнивает `CAPS` (14.2). Он не затрагивается.
- Курсор не зависит от `DRIVER_PROTOCOL` и очереди событий: событий курсор не добавляет. Регистры курсора доступны при любом `DRIVER_PROTOCOL`, и `DRIVER_PROTOCOL ← 0` курсор не меняет.
- Единственный экран — экран 0. Курсор второго экрана определяет S10-15 в своём блоке `0x300–0x3FC` или новой ревизией.

### 15.3. Инварианты

1. Ни одна запись в блок курсора и ни одна host-операция курсора не меняют `generation`, `frame_mode_epoch`, `mode_change_count`, `STATUS`, `EVENT_STATUS`, активный режим, очередь событий и память framebuffer.
2. Ни одна запись в регистры версий 1 и 2 вне блока курсора не меняет состояние курсора. Исключение одно — reset устройства (15.9). В частности, `MODE_COMMIT` курсор не трогает. Позиция, принятая в старом режиме, может оказаться вне кадра нового режима. Тогда host рисует только часть образа внутри кадра или ничего (FRAME_TRANSPORT_V1.md, 10.8).
3. Перемещение, скрытие, показ и смена формы курсора не публикуют кадр: host не получает нового `generation`, и VMHost не отправляет `FRAME` (FRAME_TRANSPORT_V1.md, 10.7).
4. Образ курсора не лежит в памяти framebuffer и в карте физической памяти гостя (15.5). Запись образа не вызывает committed-write callback и не трогает page generations, как любой доступ к регистрам.

### 15.4. Регистры блока курсора

Общие правила раздела 4 действуют без изменений: 32 бита, little-endian, только `AccessWidth::Dword` по смещению, кратному 4, в `IoSpace::Mmio`. Нарушение — backend-ошибка 9.2 до изменения состояния, в том числе до автоинкремента `CURSOR_IMAGE_INDEX`.

Классы доступа — из раздела 4 и 14.4, плюс один новый: **RW с автоинкрементом** (только `CURSOR_IMAGE_INDEX`). Запись сохраняет все 32 бита как есть, без проверки. Чтение возвращает текущее значение. Кроме записи гостя, значение растёт на 1 при каждой успешной записи в `CURSOR_IMAGE_DATA` (15.6.1).

Упакованные пары `X/Y` (`CURSOR_HOTSPOT`, `CURSOR_POSITION`): биты 15:0 — `X`, биты 31:16 — `Y`, оба беззнаковые.

| Смещение | Имя | Доступ | После reset | Чтение | Запись, в том числе неверная |
|---|---|---|---|---|---|

Проверено вычислением (`python3 -c`):

- 13 именованных регистров (`0x200…0x234`) попарно различны, кратны 4 и лежат в `0x200–0x2FC`;
- ни одно из них не совпадает с 23 смещениями версии 1 (включая `IRQ_*`) и 273 смещениями версии 2 (17 именованных и 256 полей `MODE_TABLE`);
- ни одно смещение версий 1 и 2 не лежит в `0x200–0x2FC`, блок второго экрана `0x300–0x3FC` не тронут;
- в блоке остаются резервными `0x22C` и 50 слов `0x238–0x2FC`;
- `X`, `Y` позиции не больше `4095 < 2^16`; hotspot не больше `63`; индекс staging-буфера — 12 бит (`0…4095`).

### 15.5. Образ курсора: размер, формат, память

**Размер: от 1 × 1 до 64 × 64** (`CURSOR_MAX_WIDTH/HEIGHT`).

- 64 × 64 — значение курсора по умолчанию в Linux DRM: `DRM_CAP_CURSOR_WIDTH/HEIGHT`, если драйвер не задаёт своё.
- Образ 64 × 64 × 4 = 16 384 байт. Это ровно одна гранула 16 KiB раскладки frame transport (FRAME_TRANSPORT_V1.md, раздел 3), то есть одна страница на слот курсора. Полная загрузка формы — 4 096 записей данных (15.6.1).
- Больше 64 × 64 гость не загрузит: обе ОС умеют программный курсор, и драйвер возвращает отказ, если форма больше предела. Предел видит гость, и драйвер не считает его константой. Увеличение предела меняет размер слота транспорта и число записей загрузки, поэтому оно требует `VERSION = 3` (14.3) и новой версии транспорта.
- Предел Windows (`MaxPointerWidth/Height` в caps драйвера WDDM) объявляет сам драйвер. S10-22 сверяет 64 × 64 с требованиями своей ОС (15.15, п. 3).

**Формат: `CURSOR_FORMAT = 2` — `BGRA8888_PREMUL`.** 32 бита на пиксель: в памяти байт 0 = B, 1 = G, 2 = R, 3 = A. Как 32-битное little-endian слово пиксель равен `0xAARRGGBB`. Цвет **предумножен** на альфу.

- Показанный пиксель: `out = min(255, C + D × (255 − A) / 255)` для каждого канала B, G, R. Здесь `C` — канал образа, `D` — канал кадра под ним. Байт X кадра курсор не меняет. При `A = 255` результат равен `C`, при `A = 0` и `C = 0` — `D`; в обоих случаях без округления.
- Значения `C > A` допустимы, результат насыщается до 255. Устройство значения пикселей не проверяет и не меняет.
- Номер `2` взят из общей нумерации форматов раздела 2. В `FORMATS` (кадр) бита 2 нет, поэтому `MODE_COMMIT` с `FORMAT = 2` по-прежнему даёт `UNSUPPORTED_FORMAT`. В `CURSOR_FORMATS` нет бита 1: формат без альфы курсору не нужен.
- Почему предумноженная альфа: такой формат у плоскости курсора Linux DRM по умолчанию (`DRM_FORMAT_ARGB8888`, режим смешивания «Pre-multiplied»), и это тот же порядок байтов. На host это одна операция смешивания Metal (`one`, `oneMinusSourceAlpha`) без деления, точная при `A ∈ {0, 255}`, поэтому эталон строится без допуска (15.13). Прямая альфа потребовала бы умножения на host и не дала бы точности. Драйвер, у ОС которого прямая альфа, предумножает сам.
- Монохромные курсоры и курсоры с XOR-маской (инверсия фона) не поддержаны: инверсию нельзя выразить смешиванием с альфой. Драйвер отказывает в такой форме, и ОС рисует курсор программно (15.15, п. 3).

**Память образа: только регистровое окно, буферы внутри устройства.** Образ лежит в состоянии `BusDevice` дисплея, а не в карте физической памяти гостя:

- `staging` — 4 096 слов `u32` (16 KiB). Гость пишет его через `CURSOR_IMAGE_INDEX`/`CURSOR_IMAGE_DATA`. Пиксель `(i, j)` формы ширины `W` — слово с индексом `j × W + i`. Строки упакованы, паддинга нет.
- `active` — опубликованная форма: копия первых `W × H` слов `staging` и параметры формы на момент успешного `CURSOR_IMAGE_COMMIT`. Host читает только её.
- Оба буфера выделяются при создании устройства (32 KiB вне `RamLimits`), заполнены нулями. Это не нарушает 7.3: байтов **кадра** у устройства по-прежнему нет, а образ курсора к кадру не относится.

Сравнение вариантов:

| Вариант | Оценка |
|---|---|
| **Регистровое окно + буферы в устройстве** (выбрано) | Укладывается в блок `0x200–0x2FC`, поэтому `VERSION` остаётся `2`. Новых регионов и правил карты нет. Конфликта с регионом `Framebuffer` нет: курсор не в нём. Committed-write callback, page generations, запреты fetch и page tables не затрагиваются: это обычный MMIO. `staging` и `active` разделены, поэтому host никогда не видит наполовину загруженную форму. Цена — `W × H` MMIO-записей на смену формы: 4 096 для 64 × 64, 1 024 для 32 × 32. Перемещение — одна запись |
| Отдельный регион в резерве `0xFA40_0000–0xFBFF_FFFF`, RAM-подобный | Гость пишет образ обычными записями, это быстрее. Но регион вне `0x200–0x2FC` — это «больше места», то есть `VERSION = 3` (14.3). Нужен новый вид региона или второй `Framebuffer` (сейчас карта принимает не больше одного, 7.3), новое согласование при сборке шины, новая строка в discovery, повтор всех запретов 7.4 (fetch, таблицы страниц) и место в BAR S10-12. Host читает такой регион между квантами, пока гость может его переписывать: без отдельного staging форма рвётся |
| Внутри памяти framebuffer за кадром | Кадр 4096 × 2304 занимает весь `FB_SIZE`, места нет. Меньший режим после смены может перекрыть образ, а `MODE_COMMIT` по правилу 14.2 менять нельзя. Тот же разрыв формы при чтении между квантами |
| Образ в RAM гостя по GPA, копирование при commit | У устройства нет DMA (7.1), а `BusDevice::write` не имеет доступа к памяти. Нужны проверка адреса, заданного гостем, и порядок чтения относительно записей CPU |

Правило 4.1 плана («без MMIO на каждый пиксель») относится к кадру. Образ курсора не больше 4 096 слов и загружается только при смене формы, а не на каждом кадре. Стоимость загрузки 64 × 64 в CPU-пути реализация измеряет (15.13, п. 9). Если она неприемлема, RAM-подобный регион вводится новой ревизией (15.15, п. 1).

### 15.6. Команды и порядок проверок

В каждой команде срабатывает первая неудачная проверка. При неудаче меняется только своё поле `CURSOR_STATUS`. При успехе своё поле становится `NONE`.

#### 15.6.1. `CURSOR_IMAGE_DATA ← v`

1. `CURSOR_IMAGE_INDEX ≥ 4096` → `DATA_ERROR = INDEX_OUT_OF_RANGE`; `staging` и индекс не меняются.

Успех: `staging[CURSOR_IMAGE_INDEX] ← v`, `CURSOR_IMAGE_INDEX ← CURSOR_IMAGE_INDEX + 1` (после проверки переноса нет). Запись в `staging` не меняет `active`, `cursor_seq` и то, что показывает host.

Индекс не сбрасывается сам: драйвер пишет `CURSOR_IMAGE_INDEX ← 0` перед загрузкой. `staging` сохраняется после commit. Поэтому смена только hotspot — две записи (`CURSOR_HOTSPOT`, `CURSOR_IMAGE_COMMIT`) без повторной загрузки пикселей.

#### 15.6.2. `CURSOR_IMAGE_COMMIT ← v`

1. `v ≠ 1` → `IMAGE_ERROR = INVALID_COMMAND`.
2. `CURSOR_WIDTH = 0` или `CURSOR_HEIGHT = 0` → `SIZE_NOT_SET`.
3. `CURSOR_WIDTH > CURSOR_MAX_WIDTH` или `CURSOR_HEIGHT > CURSOR_MAX_HEIGHT` → `UNSUPPORTED_SIZE`. Сравнение 32-битных значений, без умножения.
4. `CURSOR_FORMAT ≥ 32` или бит `CURSOR_FORMAT` не установлен в `CURSOR_FORMATS` → `UNSUPPORTED_FORMAT`.
5. `HOTSPOT.X ≥ CURSOR_WIDTH` или `HOTSPOT.Y ≥ CURSOR_HEIGHT` → `HOTSPOT_OUT_OF_IMAGE`.
6. `cursor_seq = 2^64 − 1` → `COUNTER_EXHAUSTED`.

Успех — одно атомарное изменение с точки зрения host: `active ← {W, H, FORMAT, HOTSPOT, staging[0 … W × H − 1]}`, `cursor_seq ← cursor_seq + 1`, `shape_seq ← cursor_seq` (новое значение). Commit не требует активного режима и не меняет `CURSOR_ENABLE` и `CURSOR_POSITION`. Commit при показанном курсоре заменяет форму сразу. Повторный commit тех же данных — тоже новая форма с новым `shape_seq`.

#### 15.6.3. `CURSOR_POSITION ← v` (RW с проверкой)

1. `STATUS.ACTIVE = 0` → `POSITION_ERROR = NO_ACTIVE_MODE`.
2. `X ≥ ACTIVE_WIDTH` или `Y ≥ ACTIVE_HEIGHT` → `POSITION_OUT_OF_FRAME`.
3. `v` отличается от текущего значения, а `cursor_seq = 2^64 − 1` → `COUNTER_EXHAUSTED`.

При неудаче регистр сохраняет прежнее значение. Успех: регистр ← `v`; если значение изменилось, `cursor_seq ← cursor_seq + 1`. Запись того же значения успешна и `cursor_seq` не меняет.

`X/Y` — позиция **hotspot** в пикселях кадра. Левый верхний угол образа — `(X − HOTSPOT.X, Y − HOTSPOT.Y)` и может быть отрицательным. Тогда host рисует только часть образа внутри кадра. Пара упакована в один регистр, поэтому перемещение — одна запись, и host не увидит новое `X` со старым `Y`. Проверка по активному кадру означает, что точка hotspot всегда внутри кадра, в котором её поставили.

#### 15.6.4. `CURSOR_ENABLE ← v` (RW с проверкой)

1. `v ∉ {0, 1}` → `ENABLE_ERROR = INVALID_COMMAND`.
2. `v = 1`, а опубликованной формы нет (`shape_seq = 0`) → `NO_CURSOR_IMAGE`.
3. `v` отличается от текущего значения, а `cursor_seq = 2^64 − 1` → `COUNTER_EXHAUSTED`.

При неудаче регистр сохраняет прежнее значение. Успех: регистр ← `v`; если значение изменилось, `cursor_seq ← cursor_seq + 1`. `0` (скрыть) допустим всегда, кроме насыщения счётчика. Форма, позиция и `staging` при скрытии сохраняются, и показ (`← 1`) возвращает тот же курсор без повторной загрузки.

### 15.7. `CURSOR_STATUS` и новые коды

| Биты | Поле | Результат последней записи в |
|---|---|---|
| 7:0 | `DATA_ERROR` | `CURSOR_IMAGE_DATA` |
| 15:8 | `IMAGE_ERROR` | `CURSOR_IMAGE_COMMIT` |
| 23:16 | `POSITION_ERROR` | `CURSOR_POSITION` |
| 31:24 | `ENABLE_ERROR` | `CURSOR_ENABLE` |

Каждое поле перезаписывает только своя команда, как в `STATUS` (4.1) и `EVENT_STATUS` (14.10). Ошибки курсора не попадают в `STATUS` и `EVENT_STATUS`.

Коды продолжают общую нумерацию 4.1 и 14.10. Повторно используются `0x00 NONE`, `0x01 SIZE_NOT_SET`, `0x02 UNSUPPORTED_SIZE`, `0x03 UNSUPPORTED_FORMAT`, `0x04 INVALID_COMMAND`, `0x05 NO_ACTIVE_MODE`, `0x06 COUNTER_EXHAUSTED` в своём смысле. Новые:

| Код | Имя | Где возникает |
|---|---|---|
| `0x0C` | `INDEX_OUT_OF_RANGE` | `CURSOR_IMAGE_DATA` при `CURSOR_IMAGE_INDEX ≥ 4096` |
| `0x0D` | `HOTSPOT_OUT_OF_IMAGE` | `CURSOR_IMAGE_COMMIT`: hotspot вне образа |
| `0x0E` | `POSITION_OUT_OF_FRAME` | `CURSOR_POSITION`: точка вне активного кадра |
| `0x0F` | `NO_CURSOR_IMAGE` | `CURSOR_ENABLE ← 1` без опубликованной формы |

**Класс ошибок.** Все ошибки курсора исправимы гостем (9.1): доступ завершается успешно, результат виден в `CURSOR_STATUS`. Запись в RO-регистры и в резерв блока игнорируется, `CURSOR_STATUS` не меняется. Backend-ошибки (9.2) те же, что для любого смещения окна: ширина, выравнивание, пространство, выход за окно. Они возникают до изменения состояния, в том числе до записи в `staging` и автоинкремента.

### 15.8. Счётчики курсора (только host)

| Счётчик | Тип | Начало | Рост | Насыщение |
|---|---|---|---|---|
| `cursor_seq` | `u64` | `0` при включении машины | +1 на успешный `CURSOR_IMAGE_COMMIT`, на успешную запись `CURSOR_POSITION`/`CURSOR_ENABLE`, которая изменила значение, и на reset (15.9) | команды курсора при `2^64 − 1` отвергаются кодом `COUNTER_EXHAUSTED`; reset в этом состоянии счётчик не меняет |
| `shape_seq` | `u64` | `0` — формы нет | ← `cursor_seq` при успешном commit | — |

`cursor_seq` меняется ровно тогда, когда меняется то, что показал бы host: форма, позиция или видимость. Запись в `staging` и в RW-регистры формы его не меняет. Счётчик монотонен всё время жизни устройства, reset его не сбрасывает. Поэтому frame transport использует его как слово публикации без ABA (FRAME_TRANSPORT_V1.md, 10.5). Внутри экземпляра устройства одно значение `shape_seq` всегда означает одни и те же байты `active`.

Счётчики курсора независимы от `generation` и `mode_change_count` (15.3, п. 1). Гостю они не видны: подтверждение commit гость получает в `CURSOR_STATUS.IMAGE_ERROR`.

### 15.9. Reset и включение машины

**Включение машины** — к разделам 10 и 14.12 добавляется: все регистры блока имеют значения после reset (15.4), `staging` и `active` заполнены нулями, формы нет (`shape_seq = 0`), `cursor_seq = 0`.

**Reset устройства** — к разделам 10 и 14.12 добавляется:

- регистры блока возвращаются к значениям после reset: курсор скрыт, позиция `(0, 0)`, `CURSOR_IMAGE_INDEX = 0`, `CURSOR_STATUS = 0`;
- `staging` и `active` обнуляются, форма снимается (`shape_seq ← 0`);
- если до reset была форма, курсор был включён или позиция была ненулевой, `cursor_seq` растёт на 1. Так host увидит скрытие курсора. Иначе показанное состояние не изменилось, и счётчик не меняется;
- **допущение для `cursor_seq = 2^64 − 1`:** состояние на практике недостижимо (2^64 изменений курсора). Если оно всё же наступило, reset выполняется так же, курсор скрывается, но счётчик не растёт. Host тогда не узнает о скрытии через frame transport, потому что новое значение для публикации неоткуда взять. Это осознанно принятое допущение, как насыщение `mode_change_count` в разделе 8;
- `generation`, `mode_change_count` и `next_event_seq` ведут себя по разделам 10 и 14.12, курсор их не трогает.

Драйвер узнаёт о reset по `DRIVER_PROTOCOL = 0` (14.11) и повторяет инициализацию, включая форму и позицию курсора. Драйвер без протокола событий о reset не узнаёт. Это уже верно для режима (14.11), и курсор нового не добавляет.

Snapshot (13.4) дополнительно включает регистры блока, `staging`, `active` (32 KiB) и оба счётчика.

### 15.10. Host API: дополнение к 10.1 и 14.13

Имена задаёт реализация. Обязательная семантика:

- `cursor_state()` возвращает `cursor_seq`, `enabled`, позицию `(x, y)` и форму. Форма — либо «нет», либо `shape_seq`, `width`, `height`, `format`, `hot_x`, `hot_y` из `active`.
- `read_cursor_image_into(&mut [u8]) -> Result<CursorShapeInfo, CursorReadError>` копирует ровно `width × height × 4` байт `active` и возвращает параметры скопированной формы. Отказы: `NoShape` и `BufferLength` (длина буфера не равна размеру образа). Шина не нужна: образ лежит в устройстве.
- Правило вызова то же: только между квантами, владельцем `MachineBus`, в потоке, исполняющем кванты, через `DisplayHandle` (10.1). Поэтому `cursor_state()` и следующее за ним `read_cursor_image_into` без кванта между ними описывают одно состояние.
- Функции только читают: ни регистры, ни счётчики, ни `CURSOR_STATUS` не меняются.
- Существующие функции 10.1 и 14.13 не меняются. `read_frame_into` курсор не учитывает: кадр отдаётся без курсора.

### 15.11. Путь до VMHost и UI

- **display host ABI.** VMHost получает состояние и образ курсора через [display host ABI](DISPLAY_HOST_ABI_V1.md). Нужно одно чтение состояния вместе с образом в буфер вызывающего (или два вызова без `step` между ними) и `shape_seq`, чтобы образ не копировать повторно. По правилу ABI §1 это новые функции и структуры с новым идентификатором версии; символы v1 не меняются. Для сквозной проверки нужен test-only профиль `3` (`OD_DISPLAY_PROFILE_TEST_CURSOR`, ABI §2, правило 1; значение `2` уже отдано S10-08). Он рисует тот же кадр, что профиль 1, задаёт форму из генератора (15.13) в известной позиции. Каждый `step` перемещает курсор записью `CURSOR_POSITION` и не звонит doorbell. Точные значения формы, позиции и закона движения фиксирует задача реализации в DISPLAY_HOST_ABI_V1.md и README эталонов. Предложение: форма 16 × 16, hotspot `(1, 1)`, начальная позиция `(20, 12)`, шаг `X ← (X + 1) mod 64`. **Отклонение (S10-14, реализация):** test-only профиль `3` не реализован по решению координатора, функции курсора ABI реализованы; см. [DISPLAY_HOST_ABI_V1.md](DISPLAY_HOST_ABI_V1.md), раздел 9, и [STAGE_10_REPORT.md](../reports/STAGE_10_REPORT.md), раздел S10-14.
- **VMHost → UI** — frame transport v2 (FRAME_TRANSPORT_V1.md, раздел 10): отдельная область курсора в разделяемой памяти со своим seqlock и сообщение `CURSOR`. Перемещение курсора не порождает `FRAME`.
- **Наложение** в просмотрщике — FRAME_TRANSPORT_V1.md, 10.8.

### 15.12. Не делать

- Аппаратный курсор через IOSurface, `NSCursor` хоста или системный курсор macOS: это S10-17 и поведение UI, а не устройство.
- Изменение формата кадра, памяти framebuffer, `MODE_COMMIT` и doorbell: курсор их не трогает (15.3).
- Курсор внутри кадра гостя, программное рисование курсора на host в байты кадра, события курсора в очереди 14.7.

### 15.13. Проверки реализации (для задачи кода)

`od-machine` (unit-тесты в `display_device.rs` и интеграционные в `crates/od-machine/tests/display_device.rs`):

1. **Совместимость.** `VERSION = 2`, `CAPS = 0x7`. Все тесты версий 1 и 2 проходят; ожидаемое значение меняется только у `CAPS` (`0x3` → `0x7`) и у чтения смещений `0x200–0x234`, которые больше не резерв. Последовательность probe S10-08 даёт на смещениях раздела 4 те же значения, что раньше. Резерв `0x22C` и `0x238–0x2FC` читается `0`, запись игнорируется.
2. Значения после reset всех регистров 15.4. Запись `0xFFFF_FFFF` в каждый RO-регистр и резерв блока не меняет ни его, ни `CURSOR_STATUS`, ни `STATUS`.
3. `CURSOR_IMAGE_DATA`: автоинкремент, `INDEX = 4095` → успех и `INDEX = 4096`, следующая запись → `INDEX_OUT_OF_RANGE` без изменения `staging`; `INDEX = 0xFFFF_FFFF` → та же ошибка; чтение `DATA`/`COMMIT` → `0`.
4. `CURSOR_IMAGE_COMMIT`: каждая проверка 15.6.2 по порядку, парами, как в 14.14 п. 8; граничные `1×1`, `64×64`, `65×1`, hotspot `(W − 1, H − 1)` и `(W, 0)`. После commit запись в `staging` не меняет то, что отдаёт `read_cursor_image_into`. Повторный commit даёт новый `shape_seq`.
5. `CURSOR_POSITION`: без режима → `NO_ACTIVE_MODE`; `X = ACTIVE_WIDTH − 1` → успех, `X = ACTIVE_WIDTH` → `POSITION_OUT_OF_FRAME`, регистр прежний; то же значение → `cursor_seq` не меняется.
6. `CURSOR_ENABLE`: `1` без формы → `NO_CURSOR_IMAGE`; `2`, `0xFFFF_FFFF` → `INVALID_COMMAND`; `0 → 1 → 1 → 0` с ростом `cursor_seq` только на изменениях.
7. **Курсор не трогает кадр.** После активного режима и одного doorbell: 1 000 записей `CURSOR_POSITION`, переключение `CURSOR_ENABLE`, commit формы, загрузка 4 096 слов. `frame_generation()`, `mode_change_count()`, `has_current_frame()`, `STATUS`, `EVENT_STATUS` и байты framebuffer (сравнение `read_frame_into` до и после) не меняются; `cursor_seq` вырос. Обратное: `MODE_COMMIT` и doorbell не меняют `cursor_state()`.
8. Reset по 15.9: форма снята, курсор скрыт, `cursor_seq` вырос ровно на 1 при показанном курсоре и не вырос на чистом устройстве; насыщение через подготовку состояния в unit-тесте; `COUNTER_EXHAUSTED` для всех трёх команд.
9. Backend-ошибки на смещениях блока (`Byte`/`Word`/`Qword`, невыровненное, PIO) — до изменения состояния и до автоинкремента. Замер: время загрузки формы 64 × 64 (4 102 записи) через `MachineBus` и через CPU-путь платы firmware (блокер 13.1 снят). Результат — в отчёт.

Сквозные проверки плана (транспорт и UI — FRAME_TRANSPORT_V1.md, 10.9):

### 15.14. Порядок реализации

Бит `CAPS` 2 устанавливается в той же задаче, что и регистры, до появления host-пути. Драйверов курсора ещё нет, поэтому промежуточного состояния «гость рисует курсор, host его не показывает» у реальных гостей не будет. Затем ABI и VMHost, затем transport v2 и UI — обе стороны транспорта меняются вместе (FRAME_TRANSPORT_V1.md, 10.2).

### 15.15. Открытые вопросы

1. **Стоимость загрузки формы через MMIO** не измерена (15.13, п. 9). Анимированный курсор Windows (несколько смен формы в секунду) умножает её. Если её не принять, RAM-подобный регион образа вводится ревизией 3 (15.5, второй вариант).
2. **Курсор и абсолютная позиция ввода.** Абсолютного pointer device в плате нет (INPUT_TRANSPORT_V1.md, раздел 11). Поэтому курсор гостя на экране и курсор хоста расходятся. Скрыть курсор хоста над окном — поведение UI (S10-16, захват указателя), не устройства.
3. **Требования ОС** к размеру (64 × 64), формату (предумноженная альфа) и монохромным/XOR-курсорам сверяют S10-21/S10-22 по документации своей ОС.
4. **DISPLAY_DRIVER_V1.md** пока говорит, что регистров курсора нет (абзац «Блоки курсора и второго экрана»). Последовательности драйвера для курсора добавляет задача реализации вместе с кодом.

## 16. Второй экран (S10-15)

**Статус:** написано в задаче [S10-15](../plans/STAGE_10.md#s10-15-несколько-экранов), **ожидает ревью**; код не начат. Реализация — отдельная задача: `crates/od-machine/src/display_device.rs`, `physical_memory.rs`, `bus.rs`, display host ABI, VMHost, UI. Передача в UI нормативна в [FRAME_TRANSPORT_V1.md](../../protocols/control/FRAME_TRANSPORT_V1.md), раздел 11 (frame transport v3).

### 16.1. Что добавляется и где что нормативно

Устройство ревизии 2 получает **конфигурацию с двумя экранами**. Экран 0 — существующий экран разделов 4–15: его регистры, память, счётчики и поведение не меняются. Экран 1 — опциональный блок `0x300–0x3FC` (бит `CAPS` 3 `SECOND_SCREEN`) и второй регион `Framebuffer` в карте гостя. У экрана 1 свой режим, своя память, свои `generation`, `mode_change_count` и `frame_mode_epoch`, и он может быть явно отключён гостем (16.6). Аппаратного курсора у экрана 1 нет (16.8). Третьего экрана нет.

| Что | Где нормативно |

| Регистры блока экрана 1, классы доступа, значения после reset, порядок проверок, отключение, счётчики, адрес и размер памяти экрана 1, правила карты и сборки шины, reset, host API | этот раздел |
| Разделяемая память и сообщения двух экранов, состояния reader-а на экран, окна | FRAME_TRANSPORT_V1.md, раздел 11 |
| Последовательность драйвера для экрана 1 | [DISPLAY_DRIVER_V1.md](../../protocols/guest/DISPLAY_DRIVER_V1.md); дополняется задачей реализации (16.15, п. 5) |

**Второй экран — часть того же устройства, а не второе устройство.** Блок лежит в том же окне регистров, reset общий, а `MachineBus` по-прежнему принимает одно дисплейное устройство (`DisplayBindingError::MultipleDevices` не меняется).

### 16.2. Конфигурация и совместимость

- Число экранов — свойство конфигурации машины, заданное при создании устройства и карты: `1` (по умолчанию) или `2`. Гость его не меняет, за время жизни экземпляра оно постоянно.
- **Конфигурация с одним экраном** — ровно текущее устройство: `CAPS = 0x0000_0007`, блок `0x300–0x3FC` — резерв (чтение `0`, запись игнорируется), в карте один регион `Framebuffer`. Профиль ABI 1, probe S10-08 и все смоуки первого экрана работают в ней и не меняются.
- **Конфигурация с двумя экранами:** `CAPS = 0x0000_000F` (бит 3 = `1`), `VERSION = 2`, блок 16.4 существует, в карте второй регион `Framebuffer` (16.3).
- Драйвер, не знающий второго экрана (гость версии 1, драйвер ревизии 2 без S10-15), бит 3 игнорирует (14.2) и в блок не пишет. Экран 1 у такого гостя остаётся без режима, host показывает его окно как «нет сигнала» (FRAME_TRANSPORT_V1.md, 11.7). Экран 0 работает как в конфигурации с одним экраном.
- Probe S10-08 пишет только регистры версии 1 и не сравнивает `CAPS` (14.2), поэтому в обеих конфигурациях он рисует только на экране 0.

**Почему `VERSION` остаётся `2`.** Правило 14.3 разрешает блоку `0x300–0x3FC` появиться без смены `VERSION` при своём бите `CAPS`, если функции не нужно больше места в окне и не меняется смысл существующих регистров. Блок экрана 1 занимает 17 слов внутри `0x300–0x3FC` (16.4) и не меняет ни одного регистра разделов 4, 14, 15. Регион памяти экрана 1 — второй экземпляр **существующего** вида `Framebuffer` с теми же правилами 7.1–7.4. Гость находит его только через `S1_FB_BASE_*`/`S1_FB_SIZE` внутри блока, а без бита 3 региона нет. Раздел 15.5 назвал отдельный регион для образа курсора поводом для `VERSION = 3`. Там регион требовал нового вида или новых правил и отдельного staging против разрыва формы. Здесь ни того, ни другого нет: регион ведёт себя как память экрана 0. Это толкование 14.3 вынесено на ревью (16.15, п. 1). Если ревью его отвергнет, единственное guest-visible изменение — `VERSION = 3`: драйверы проверяют `VERSION ≥ N` (14.2) и продолжают работать.

### 16.3. Память экрана 1

| Регион | GPA начала | Длина | Конец (исключительно) | `MemoryRegionKind` |
|---|---|---|---|---|
| Память framebuffer экрана 1 | `0xF400_0000` | `0x0240_0000` (36 MiB) | `0xF640_0000` | `Framebuffer` |
| Резерв для памяти экрана 1 (не отображается, доступ = `BusAccessError::UnmappedPhysical`) | `0xF640_0000` | `0x01C0_0000` (28 MiB) | `0xF800_0000` | — |
| Память framebuffer экрана 0 (раздел 3, без изменений) | `0xF800_0000` | `0x0240_0000` | `0xFA40_0000` | `Framebuffer` |

- **Уточнение раздела 3.** Под дисплей резервируется диапазон `[0xF400_0000, 0xFC00_1000)` в **любой** конфигурации, чтобы карта платы не зависела от числа экранов. RAM ниже 4 GiB заканчивается не выше `0xF400_0000` (было `0xF800_0000`). В конфигурации с одним экраном `[0xF400_0000, 0xF800_0000)` не отображается. Строку «Экран» в [VIRTUAL_BOARD.md](VIRTUAL_BOARD.md) обновляет задача реализации после ревью.
- Выбор адреса: база выровнена на 64 MiB, как у экрана 0 (раздел 3), длина кратна 2 MiB и 16 KiB. Диапазон смежен с резервом дисплея и не трогает `0xFC00_1000–0xFEBF_FFFF`, `0xFEC0_0000` и выше (IOAPIC, Local APIC) и верхние 16 MiB под firmware. Сегодняшние карты `od-machine` (RAM от нуля, тестовые MMIO на малых адресах) его не пересекают; `MachineMemoryMap::new` всё равно отвергает перекрытия. Повторная сверка с общей картой платы — открытый вопрос 13.2.
- Регион подчиняется всем правилам 7.1–7.4 без исключений: данные как RAM, без committed-write callback, без page generations; instruction fetch и элементы таблиц страниц в регионе — backend-ошибки (9.2); host получает байты только копированием. Discovery (E820, UEFI map, ACPI) не показывает регион как usable RAM.
- При включении машины память заполнена нулями. Reset её не очищает (10).
- Образ курсора к этому региону отношения не имеет: буферы курсора лежат внутри устройства (15.5), а не в карте. Пересечения с ними нет по построению.

**Границы адресов и объёма** (проверено вычислением, `python3 -c`):

- `0xF400_0000 + 0x0240_0000 = 0xF640_0000 ≤ 0xF800_0000`: регион не пересекает память экрана 0, её резерв `0xFA40_0000–0xFBFF_FFFF` и окно регистров `0xFC00_0000–0xFC00_0FFF`. Конец дисплейного диапазона `0xFC00_1000 ≤ 2^32`, поэтому подходит любая ширина физического адреса от 32 бит (сегодня 36 и 64).
- Две памяти по 36 MiB — `75 497 472` байт (`0x0480_0000`, 72 MiB) backing вне `RamLimits`.

**Правила карты и сборки шины (изменение 7.3):**

- `MachineMemoryMap::new` принимает **не больше двух** регионов `Framebuffer`. Каждый проверяется как сейчас: начало и длина кратны 4 KiB, длина ≤ `0x0240_0000`. Третий регион — ошибка построения карты до allocation (сегодняшняя `MultipleFramebufferRegions` или новый вариант с тем же смыслом). Суммарный backing регионов `Framebuffer` поэтому не больше 72 MiB. Отдельный общий лимит не вводится: он следует из двух проверок.
- `PhysicalMemory::new` выделяет каждый регион отдельно через `try_reserve_exact`, как сейчас. Ошибка выделения второго региона — `AllocationFailed` до создания машины, первый регион освобождается вместе с неудавшимся построением.
- **Согласование с устройством.** Устройство сообщает шине по одной паре (база, длина) на экран: экран 0 — `FB_BASE`/`FB_SIZE`, экран 1 — `S1_FB_BASE`/`S1_FB_SIZE`. Множество регионов `Framebuffer` карты должно в точности совпасть с этим множеством, сопоставление — по базе. Ошибка построения возникает, если:
  - у устройства с одним экраном в карте больше одного региона `Framebuffer`;
  - у устройства с двумя экранами в карте нет региона экрана 1 или он не совпадает по базе или длине;
  - выполнено любое условие 7.3 для экрана 0.
- Сегодняшний `BusDevice::framebuffer_binding() -> Option<FramebufferBinding>` описывает один регион. Реализация меняет его на список привязок или добавляет вторую функцию. Имена выбирает реализация, семантика — правило выше.

### 16.4. Регистры блока экрана 1

**Правило зеркала.** Регистр экрана 1 лежит по смещению `0x300 + смещение` одноимённого регистра экрана 0 и ведёт себя как он, но над состоянием экрана 1. | `0x380` | `S1_FRAME_GENERATION` | RO + doorbell | `0` при включении; reset сохраняет | младшие 32 бита `generation_1` | значение отбрасывается; запись — «кадр экрана 1 готов» (16.5) |
| `0x384` | `S1_FRAME_GENERATION_HI` | RO | как выше | старшие 32 бита `generation_1` | игнорируется |
| `0x388–0x3FC` | — | резерв | `0` | `0` | игнорируется |

Проверено вычислением (`python3 -c`):

- 17 именованных регистров (`0x30C…0x384`) попарно различны, кратны 4 и лежат в `0x300–0x3FC`; каждый равен `0x300 +` смещение одноимённого регистра экрана 0;
- ни одно из них не совпадает с 23 смещениями версии 1 (включая `IRQ_*`), 273 смещениями версии 2 (17 именованных и 256 полей `MODE_TABLE`) и 13 регистрами курсора;
- ни одно смещение версий 1, 2 и курсора не лежит в `0x300–0x3FC`;
- в блоке 47 резервных слов: `0x300–0x308`, `0x324–0x33C`, `0x350–0x35C`, `0x374–0x37C`, `0x388–0x3FC`. Суммарный размер блока — 64 слова, 256 байт.

### 16.5. Режим и кадр экрана 1

- **`S1_MODE_COMMIT ← 1`** — проверки раздела 5 по порядку над `S1_WIDTH`/`S1_HEIGHT`/`S1_FORMAT`, `S1_MAX_*`, `S1_FB_SIZE`, `S1_FORMATS` и `mode_change_count_1`; правило 2.1 (сравнение до умножения) то же. Неудача меняет только `S1_STATUS.COMMIT_ERROR`. Успех — как раздел 5 над состоянием экрана 1, и дополнительно `S1_STATUS.DISABLED ← 0`.
- **`S1_FRAME_GENERATION`** — раздел 6 над экраном 1: при `S1_STATUS.ACTIVE = 1` и `generation_1 < 2^64 − 1` растут `generation_1`, `frame_mode_epoch_1 ← mode_change_count_1`, `S1_STATUS.FRAME_SINCE_COMMIT ← 1`; иначе `S1_STATUS.FRAME_ERROR ← NO_ACTIVE_MODE` или `COUNTER_EXHAUSTED`. Кадр экрана 1 текущий, только если `ACTIVE_1 = 1`, `generation_1 > 0` и `frame_mode_epoch_1 = mode_change_count_1`.
- Пиксель `(x, y)` экрана 1 лежит по `S1_FB_BASE + y × S1_STRIDE + x × 4`, формат — раздел 2.

**Независимость экранов** (инварианты):

1. Запись в блок экрана 1 меняет только состояние экрана 1. `generation`, `mode_change_count`, `frame_mode_epoch`, `STATUS`, активный режим экрана 0, `EVENT_STATUS`, очередь событий, `DRIVER_PROTOCOL`, состояние курсора и память экрана 0 не меняются.
2. Запись в регистры разделов 4, 14, 15 не меняет состояние экрана 1. В частности, `MODE_COMMIT` экрана 0 и `DRIVER_PROTOCOL ← 0` экран 1 не трогают.
3. Счётчики экранов независимы и монотонны. Одинаковые числовые значения `generation` двух экранов ничего не означают: host сравнивает их только внутри экрана.
4. Исключение одно — reset устройства (16.9): он действует на оба экрана.

### 16.6. Отключение экрана 1

**Решение: явная команда `S1_MODE_COMMIT ← 2` (`DISABLE`) и бит `S1_STATUS.DISABLED`**, а не только «`ACTIVE_1 = 0`».

| Вариант | Оценка |
|---|---|
| Только `ACTIVE_1 = 0` | Состояние «гость выключил экран» не отличить от «режим ещё не ставили», а снять режим гость не может: команды выключения в версии 1 нет (раздел 5). Остаётся молчать, и host показывает замороженный последний кадр — именно то, что план запрещает |
| Отдельный регистр `S1_ENABLE` | Второе независимое состояние рядом с режимом: «включён без режима», «выключен с режимом» — четыре сочетания вместо трёх и отдельный порядок проверок. Ничего не добавляет к варианту ниже |
| **Команда `2` в `S1_MODE_COMMIT` + бит `DISABLED`** (выбрано) | Отключение — та же точка, что смена режима, и тот же счётчик: host видит его как смену режима, а транспорт — как `MODE` с флагом (FRAME_TRANSPORT_V1.md, 11.4). Три состояния экрана: «нет режима», «режим», «отключён». Соответствует выключению вывода в ОС (снятие режима CRTC, неактивный путь VidPN) |

Состояние экрана 1 — одно из трёх: `NO_MODE` (`ACTIVE = 0`, `DISABLED = 0`), `ACTIVE` (`ACTIVE = 1`, `DISABLED = 0`), `DISABLED` (`ACTIVE = 0`, `DISABLED = 1`). Сочетание `ACTIVE = 1`, `DISABLED = 1` невозможно.

**`S1_MODE_COMMIT ← 2`** — проверки по порядку:

1. Состояние уже `DISABLED` → успех без изменений: `COMMIT_ERROR ← NONE`, `mode_change_count_1` не растёт.
2. `mode_change_count_1 = 2^64 − 1` → `COMMIT_ERROR = COUNTER_EXHAUSTED`, состояние без изменений.

Успех: `S1_ACTIVE_*` и `S1_STRIDE ← 0`, `ACTIVE ← 0`, `FRAME_SINCE_COMMIT ← 0`, `DISABLED ← 1`, `COMMIT_ERROR ← NONE`, `mode_change_count_1 ← mode_change_count_1 + 1`. Запрошенные `S1_WIDTH/HEIGHT/FORMAT`, `generation_1`, `frame_mode_epoch_1` и память экрана 1 не меняются. Отключение из `NO_MODE` тоже растит счётчик: host должен увидеть переход «нет сигнала → отключён».

Следствия:

- doorbell на отключённом экране → `FRAME_ERROR = NO_ACTIVE_MODE`, `generation_1` не растёт, кадра текущего режима нет. Поэтому host не публикует кадры отключённого экрана: публиковать нечего (FRAME_TRANSPORT_V1.md, 11.5);
- включение обратно — обычный `S1_MODE_COMMIT ← 1` (16.5): `DISABLED ← 0`, затем кадр после doorbell;
- память экрана 1 остаётся доступной гостю как память и в отключённом состоянии; host её не показывает;
- **экран 0 отключить нельзя.** Для `MODE_COMMIT` значение `2` по-прежнему `INVALID_COMMAND` (раздел 5): смысл регистров версии 1 не меняется. Отключение экрана 0 потребовало бы `VERSION = 3`; в S10-15 его нет.

### 16.7. `S1_STATUS`

| Биты | Поле | Значение |
|---|---|---|
| 0 | `ACTIVE` | 1 — активный режим экрана 1 |
| 1 | `FRAME_SINCE_COMMIT` | 1 — после последнего успешного commit был успешный doorbell экрана 1 |
| 2 | `DISABLED` | 1 — экран отключён командой `2` (16.6) |
| 7:3 | — | резерв, `0` |
| 15:8 | `COMMIT_ERROR` | результат последней записи в `S1_MODE_COMMIT` |
| 23:16 | `FRAME_ERROR` | результат последней записи в `S1_FRAME_GENERATION` |
| 31:24 | — | резерв, `0` |

Новых кодов ошибок нет: используются `0x00–0x06` таблицы 4.1 в своём смысле. Все ошибки экрана 1 исправимы гостем (9.1), видны только в `S1_STATUS` и не попадают в `STATUS`, `EVENT_STATUS`, `CURSOR_STATUS`. Каждое поле перезаписывает только своя команда. Бит 2 у `STATUS` экрана 0 остаётся резервом `0`.

### 16.8. Курсор и события

- **Курсор принадлежит только экрану 0.** Блок 15 не меняется: `CURSOR_POSITION` проверяется по активному режиму экрана 0 (15.6.3). Блока курсора у экрана 1 нет, и в блоке 16.4 нет регистров курсора.
- Обоснование. Вариант «один курсор с регистром номера экрана» меняет смысл проверок блока курсора (позиция против какого режима) и связывает два бита `CAPS`. Вариант «отдельный блок курсора на экран» удваивает 32 KiB буферов и 13 регистров ради экрана, у которого ОС умеет программный курсор. Когда указатель уходит на экран 1, драйвер скрывает аппаратный курсор (`CURSOR_ENABLE ← 0`), и ОС рисует курсор в кадре экрана 1 сама. S10-21/S10-22/S10-23 сверяют это с требованиями своей ОС (16.15, п. 4).
- **Событий для экрана 1 нет.** `MODE_REQUEST` ставится только для экрана 0 (`arg3 = 0`, 14.8), host API постановки не меняется. Событий подключения и отключения нет: экран 1 существует всё время жизни машины в конфигурации с двумя экранами, а отключает его только гость (16.6). Запрос размера окна экрана 1 требует согласия драйвера на `arg3 = 1` (14.15, п. 5); это задача S10-23.

### 16.9. Reset и включение машины

**Включение машины** — к разделам 10, 14.12, 15.9 добавляется: регистры блока имеют значения после reset (16.4), состояние экрана 1 `NO_MODE`, `generation_1 = mode_change_count_1 = frame_mode_epoch_1 = 0`, память экрана 1 заполнена нулями.

**Reset устройства** — к разделам 10, 14.12, 15.9 добавляется:

- `S1_WIDTH/HEIGHT/FORMAT`, `S1_ACTIVE_*`, `S1_STRIDE`, `S1_STATUS` возвращаются к значениям после reset; состояние ← `NO_MODE`;
- если состояние было `ACTIVE` или `DISABLED`, `mode_change_count_1` растёт на 1, и host видит переход в «нет режима». При `2^64 − 1` счётчик не меняется (то же допущение, что в разделе 8);
- `generation_1` и `frame_mode_epoch_1` сохраняются; память экрана 1 не очищается.

Snapshot (13.4) дополнительно включает регистры блока, состояние экрана 1, три счётчика и 36 MiB памяти экрана 1.

### 16.10. Host API: дополнение к 10.1, 14.13 и 15.10

Имена задаёт реализация. Обязательная семантика:

- `screen_count() -> u32` — `1` или `2`, по конфигурации.
- Для экрана `s < screen_count()`: режим (`width`, `height`, `stride`, `format`), либо «режима нет», либо «отключён»; `frame_generation(s)`, `mode_change_count(s)`, признак кадра текущего режима (16.5); `read_frame_into(s, …)` с отказами 10.1 и отказом «нет такого экрана» при `s ≥ screen_count()`.
- Существующие функции 10.1 без номера экрана описывают экран 0 и не меняются. Функции 14.13 и 15.10 относятся к экрану 0.
- Правило вызова то же: только между квантами, владельцем `MachineBus`, в потоке, исполняющем кванты, через `DisplayHandle`. Поэтому чтения двух экранов без кванта между ними описывают одно состояние машины.
- Функции только читают.

**Display host ABI.** VMHost получает число экранов, режим и кадр экрана 1 через [display host ABI](DISPLAY_HOST_ABI_V1.md) по его правилам §1–2: новые функции с номером экрана, символы и значения v1 и курсора не меняются, функции без номера относятся к экрану 0. Флаг «отключён» в режиме экрана — новое значение флага (правило 1 §2), которое функции экрана 0 никогда не возвращают. Точные имена, структуры и идентификатор версии фиксирует задача реализации в DISPLAY_HOST_ABI_V1.md. Источник машины с двумя экранами для сквозной проверки — 16.13, п. 10.

### 16.11. Путь до VMHost и UI

- **VMHost → UI** — frame transport v3 (FRAME_TRANSPORT_V1.md, раздел 11): отдельный объект разделяемой памяти на экран, свой `ANNOUNCE`, номер экрана в `ANNOUNCE`, `MODE`, `FRAME`, `CURSOR`, флаг `DISABLED` в `MODE`.
- **UI** — окно на экран, создаётся при `ANNOUNCE` экрана; закрытие окна экрана 1 не останавливает VMHost (FRAME_TRANSPORT_V1.md, 11.8).

### 16.12. Не делать

- Третий экран, произвольное число экранов, таблица экранов.
- Аппаратный курсор на экране 1, перенос курсора между экранами, события подключения экрана и `MODE_REQUEST` для экрана 1 (S10-23).
- Отключение экрана 0, изменение регистров и поведения разделов 4, 14, 15.
- Общая память двух экранов (один регион, разделённый пополам): экран 0 при 4096 × 2304 занимает все 36 MiB, а `FB_SIZE` экрана 0 менять нельзя.

### 16.13. Проверки реализации (для задачи кода)

`od-machine` (unit-тесты в `display_device.rs`, интеграционные в `crates/od-machine/tests/display_device.rs`):

1. **Совместимость.** Конфигурация с одним экраном: `CAPS = 0x7`, `0x300–0x3FC` читается `0`, запись игнорируется; все существующие тесты версий 1, 2 и курсора проходят без изменений. Конфигурация с двумя экранами: `VERSION = 2`, `CAPS = 0xF`; те же тесты проходят с единственным изменением ожидаемого `CAPS`; последовательность probe S10-08 даёт на смещениях раздела 4 те же значения, что в конфигурации с одним экраном.
2. Значения после reset 17 регистров 16.4. Запись `0xFFFF_FFFF` в каждый RO-регистр и в каждое из 47 резервных слов блока не меняет ни его, ни `S1_STATUS`, ни `STATUS`.
3. `S1_MODE_COMMIT ← 1`: каждая проверка раздела 5 по порядку, граничные `4096 × 2304` и `4097 × 1`. `S1_MODE_COMMIT ← 0`, `← 3`, `← 0xFFFF_FFFF` → `INVALID_COMMAND`. На экране 0 `MODE_COMMIT ← 2` по-прежнему `INVALID_COMMAND`.
4. **Независимые поколения.** После режима и кадра на обоих экранах: на экране 1 — 1 000 doorbell, смена режима, отключение и включение. `frame_generation(0)`, `mode_change_count(0)`, признак кадра экрана 0, `STATUS`, `EVENT_STATUS`, `cursor_state()` и байты кадра экрана 0 (`read_frame_into(0)` до и после) не меняются. Обратное: такая же последовательность на экране 0 не меняет счётчики, `S1_STATUS` и кадр экрана 1.
5. **Отключение — явное состояние.** Переходы `NO_MODE → DISABLED`, `ACTIVE → DISABLED`, `DISABLED → DISABLED` (без роста счётчика), `DISABLED → ACTIVE` (commit, `DISABLED ← 0`); на каждом переходе `mode_change_count_1` растёт ровно по 16.6. Doorbell в `DISABLED` → `NO_ACTIVE_MODE`, `generation_1` прежний, host API возвращает «отключён» и отказывает в кадре. `COUNTER_EXHAUSTED` через подготовку состояния.
6. Reset по 16.9: оба экрана сняты, счётчики экрана 1 растут только из `ACTIVE`/`DISABLED`, `generation_1` сохранён, память обоих экранов не очищена.
7. **Граница суммарной памяти.** Карта с двумя регионами по 36 MiB строится и выделяет 72 MiB при `RamLimits` меньше 72 MiB (backing вне лимита). Отказы построения: третий регион `Framebuffer`; второй регион длиной `0x0240_1000`; второй регион, перекрывающий память экрана 0, окно регистров или RAM; устройство с двумя экранами без региона экрана 1 или с регионом не по `S1_FB_BASE`; устройство с одним экраном и двумя регионами.
8. Правила 7.1–7.4 для региона экрана 1 — те же тесты, что для экрана 0 (fetch, таблицы страниц, `tracked_code_snapshot`, отсутствие callback), параметризованные регионом.
9. Backend-ошибки на смещениях блока (`Byte`/`Word`/`Qword`, невыровненное, PIO) — до изменения состояния.

Сквозные проверки плана (транспорт и UI — FRAME_TRANSPORT_V1.md, 11.10):

10. **Probe рисует разные узоры на двух экранах; два дампа совпадают со своими эталонами.** Экран 0 — `bars`, 64 × 48, seed 0 (эталон `bars_64x48_seed0.raw`). Экран 1 — другой режим и другой узор: `checker`, 80 × 60, seed `0x204080`. Новый эталон `checker_80x60_seed0x204080.raw` (19 200 байт) строит `tools/build/display_pattern.py`, SHA-256 записывается в [README эталонов](../../tests/fixtures/guest/stage10/README.md). Оба дампа 1:1 сравниваются с допуском 0. Источник машины: гостевой probe S10-08 в конфигурации с двумя экранами. Блокер 13.1 снят, но probe S10-08 рисует один экран, поэтому эта проверка остаётся **blocked** до расширения probe двумя экранами; разрешить ли test-only профиль ABI с двумя экранами (правило 0 DISPLAY_HOST_ABI_V1.md это запрещает) — решение координатора (16.15, п. 2).
11. **Независимые поколения на уровне транспорта** и **отключение в окне** — FRAME_TRANSPORT_V1.md, 11.10.

### 16.14. Порядок реализации

Сначала `od-machine` (карта, шина, блок, host API) с битом `CAPS` 3 только в конфигурации с двумя экранами. Затем ABI, затем transport v3 и UI — обе стороны транспорта меняются в одной задаче (FRAME_TRANSPORT_V1.md, 11.2). Профиль 1 и все смоуки экрана 0 остаются в конфигурации с одним экраном.

### 16.15. Открытые вопросы

1. **`VERSION = 2` при втором регионе** (16.2). Толкование 14.3 «регион существующего вида, найденный через блок, — не „больше места“» требует подтверждения ревью; альтернатива — `VERSION = 3` без других изменений.
2. **Источник двух экранов для сквозной проверки.** Probe S10-08 не написан. Test-only профиль ABI с двумя экранами противоречит правилу 0 DISPLAY_HOST_ABI_V1.md (для курсора профиль 3 отклонён координатором). До решения проверка 16.13, п. 10 blocked, а транспорт и UI проверяются тестами с синтетическим writer-ом (FRAME_TRANSPORT_V1.md, 11.10).
3. **PCI (S10-12).** Экрану 1 нужен свой BAR памяти (например, BAR2 при бите `CAPS` 3) или общий BAR на 72 MiB. Решает S10-12; фиксированные адреса 16.3 остаются fallback-профилем.
4. **Курсор на экране 1** (16.8) — сверка S10-21/S10-22/S10-23 с требованиями ОС: допустим ли программный курсор на втором выходе.
5. **DISPLAY_DRIVER_V1.md** пока говорит, что регистров второго экрана нет (абзац «Блоки курсора и второго экрана»). Последовательность драйвера (обнаружение по `CAPS` бит 3, режим экрана 1, отключение, повторная инициализация после reset) добавляет задача реализации вместе с кодом.
6. **GOP (S10-18)** публикует только экран 0; экран 1 доступен только драйверу ОС.
