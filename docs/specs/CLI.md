# CLI `odctl`

Статус: **реализован в задаче S11-13 [плана этапа 11](../plans/STAGE_11.md), ожидает ревью, не принят** (состояние на 2026-11-06). Документ задаёт команды, коды завершения, формат JSON-вывода и формат файла сценария `odctl`. Код — `apps/cli/Sources/odctl/` (цель `odctl` в `apps/Package.swift`), общая часть — цель `ODShared` (клиент control v2, каталог, каталог ошибок, `BundleConfig`). Краткое руководство — [apps/cli/README.md](../../apps/cli/README.md).

Связанные документы: [ADR-0006](../decisions/ADR-0006-desktop-app-shell.md) (решения (в) «модель CLI» и (г) «размещение CLI»), [control v2](../../protocols/control/CONTROL_PROTOCOL_V2.md), [bundle и библиотека](VM_BUNDLE.md) (разделы 2, 2.1, 5.1, 8), [каталог пользовательских ошибок](USER_FACING_ERRORS.md).

Все результаты — про test-only профили (машины без гостевой ОС). Команда `run` проверяет жизненный цикл процесса машины и кадры тестовой картинки, не гостевую систему. Машины с дисками до закрытия S9-06 не запускаются (`unsupported_durability`, ISSUE-055).

## 1. Модель

- `odctl` не демон и не слушает endpoint. Фоновых процессов нет: когда команда вернула управление, процесс машины (`od-vmhost`) уже завершился. Команда `run` при ошибке завершает процесс машины запросом `STOP` (для машины с диском — закрытием соединения, раздел 2, `run`), при SIGINT и SIGTERM — по правилам клиента control v2 (SIGTERM, до 500 мс, SIGKILL).
- Второго протокола и второго формата конфигурации нет: `config.plist` и `Library.plist` читает и пишет тот же код, что в приложении (`ODShared`).
- Одна машина — один процесс машины — один `flock` на `<bundle>/lock` (VM_BUNDLE 2.1). Машина, запущенная приложением или другим `odctl`, даёт `busy` (код завершения 3); `odctl` не подключается к чужому процессу машины.
- **Связь CLI ↔ приложение вне этапа 11.** `odctl` не знает о запущенном приложении, кроме как по занятому `lock`. Управление машиной, которую держит приложение, фоновая жизнь машин после выхода CLI и центральный supervisor не реализованы (ADR-0006 (в), «Вне этапа»). MCP не реализуется.

## 2. Команды

Список ниже совпадает с `odctl --help` (проверяется при приёмке среза). Значение `<имя|путь>`: аргумент с `/` или с суффиксом `.odvm` — путь к каталогу машины (индекс не читается); любой другой — имя машины в библиотеке (поле `name` из `config.plist` или имя каталога без `.odvm`). Неоднозначное имя — ошибка использования (код 2), в подробностях пути; укажите путь.

Общие параметры: `--library DIR` (раздел 5), `--vmhost PATH` (для `create --disk-gib` и `run`; по умолчанию `$ODCTL_VMHOST`, затем файл `od-vmhost` рядом с `odctl`), `--json` (кроме `run`), `--help`.

### list

`odctl list [--json] [--library DIR]` — показывает машины библиотеки: имя, состояние каталога (`valid`, `incompatible`, `invalid`, `missing`, `not_a_directory`), профиль, память, путь. Процесс машины не запускается. Предупреждения каталога (повреждённый или новый индекс, предел записей) — в stderr или в `warnings` JSON.

### inspect

`odctl inspect <имя|путь> [--json] [--library DIR]` — конфигурация и состояние каталога одной машины: идентичность, профиль, память, экраны, диски (для образа внутри bundle — размер файла), состояние блокировки (`free`, `busy`, `invalid`, `error`), отказ запуска (`launch_refusal`: `unsupported_durability`, `unsupported`, `host_memory_exceeded` или `null`). Блокировка проверяется пробой VM_BUNDLE 2.1 (снимок, не захват). Повреждённый или несовместимый `config.plist` — не ошибка команды: состояние и проблема в выводе, код 0. Процесс машины не запускается.

### delete

`odctl delete <имя|путь> --confirm <имя> [--files] [--json] [--library DIR]` — удаляет **только остановленную** машину (иначе `busy`, код 3). `--confirm` должен повторить имя машины (`name` из `config.plist`, при нечитаемом файле — имя каталога без `.odvm`); несовпадение — код 2, ничего не удалено. Без `--files` машина только убирается из индекса (каталог не трогается). С `--files` удаляется каталог машины по правилам S11-06b: имя с суффиксом `.odvm` и обычный файл `config.plist`, сам каталог не символическая ссылка (ссылка — «это не каталог», цель не трогается), `lock` свободен. Проверка `lock` и удаление идут под одной блокировкой: `odctl` берёт `lock` (`flock`) и держит до конца удаления, так что другой процесс не успеет запустить машину между проверкой и удалением; занят — `busy` (код 3), ничего не удалено. Файлы дисков не удаляются до S9-06 (ISSUE-055): отказ `unsupported_durability` (код 4, текст «Файлы машины с дисками не удаляются»), ничего не удалено, если в конфигурации есть `disks`, **или** в каталоге `disks/` есть любой файл — независимо от того, читается ли `config.plist` (несовместимая, повреждённая и отсутствующая конфигурация не снимают защиту диска). Убрать из индекса можно без `--files`. Без `--files` для машины, которой нет в индексе (путь к каталогу), команда ничего не меняет и говорит об этом (`"index_removed": false`). Процесс машины не запускается.

### create

`odctl create --name N --profile P --memory-mib M [--disk-gib G] [--library DIR] [--vmhost PATH] [--json]` — создаёт машину в каталоге библиотеки в порядке VM_BUNDLE 5.1: каталог `<имя>.odvm` и подкаталоги, `lock`, затем (только с `--disk-gib`) процесс машины: `CONFIGURE` без `disks`, `PREPARE_DISK` (`disks/disk0.img`, RAW, `G` ГиБ, разреженный файл), `STOP`; `config.plist` пишется последним. Без `--disk-gib` процесс машины не запускается. Профили: `display-test-pattern`, `display-two-screens-test`. Память — 256…65536 МиБ и не больше половины памяти компьютера. Существующий каталог с тем же именем — ошибка (код 1), существующее не трогается. После ошибки уже созданное **не удаляется** (в приложении удаление спрашивает диалог; у CLI диалога нет): путь и остаток — в подробностях.

### run

`odctl run <имя|путь> --script FILE [--json-events] [--library DIR] [--vmhost PATH]` — запускает процесс машины, отправляет `CONFIGURE` из `config.plist`, выполняет строки сценария (раздел 6) и завершается вместе с процессом машины. Сценарий проверяется целиком до запуска (ошибка — код 2, процесс не запускался). Занятая машина — `busy`, код 3. Сценарий без `stop` в конце завершается `STOP`, который добавляет `odctl`. **Машина с диском** (`disks` в конфигурации) до S9-06 не запускается и не останавливается запросом (CONTROL_PROTOCOL_V2 §7.2 п. 5, §7.3): сценарий со `start` (или со `stop`, который VMHost отклонил бы в любом состоянии) отклоняется до запуска процесса: `unsupported_durability`, код 4. Любой другой сценарий (`query`, `wait`, `sleep`, `pause`, `resume`) выполняется, `STOP` не отправляется: в конце `odctl` закрывает соединение, VMHost видит EOF в `stopped` и завершается со статусом 0 (нормальный конец, код 0); при отказе на команде соединение закрывается так же, код — по отказу. С `--json-events` stdout — по одному JSON-объекту на строку (раздел 4.3).

## 3. Коды завершения

| Код | Значение | Когда |
|---|---|---|
| 0 | успех | команда выполнена; для `run` — процесс машины завершился статусом 0 после `STOP` |
| 1 | ошибка операции | отказ процесса машины, ошибка файловой системы, машина не найдена, тайм-аут `wait`, процесс завершился аварийно или сигналом (статус «завершён сигналом»), `odctl` получил SIGINT/SIGTERM (процесс машины при этом остановлен) |
| 2 | использование | неизвестная команда или параметр, неверное значение, ошибка в сценарии, неверное `--confirm`, неоднозначное имя |
| 3 | `busy` | `lock` машины занят (`run`, `delete`; запись `config.plist` при создании) |
| 4 | `unsupported_durability` | машина с диском: `run` со `start` (или `stop`), `delete --files` |

## 4. Вывод и JSON

### 4.1. Тексты

Тексты ошибок берутся из `ErrorCatalog` ([USER_FACING_ERRORS](USER_FACING_ERRORS.md)): заголовок, объяснение, действие. Сырой код (`busy`, `unsupported_durability`, статус процесса, errno) в текст по умолчанию не входит; он есть в `--json`. Ошибки использования — собственные короткие фразы (в каталоге для них записей нет). Ошибки пишутся в stderr, результат — в stdout.

### 4.2. JSON (`--json`)

Один объект в одной строке stdout, ключи отсортированы. Обязательные поля: `schema` (целое, сейчас **1**; растёт только при несовместимом изменении поля), `command`, `ok`. Успех (`ok: true`) добавляет поля команды; ошибка (`ok: false`) добавляет `error`: `code` (имя кода control v2 — `busy`, `unsupported_durability` — либо ключ записи каталога), `title`, `message` (объяснение и действие), `exit_code`, при наличии `details` (массив технических строк).

| Команда | Поля успеха |
|---|---|
| `list` | `library` (каталог), `machines` (массив: `name`, `path`, `status`, а для `valid` — `profile`, `memory_mib`, `disks` (число); иначе `problem`), `warnings` (массив `{code, message}`) |
| `inspect` | `machine`: `name`, `path`, `status`, `listed`, `lock`; для `valid` — `identity`, `profile`, `memory_mib`, `vcpu_count`, `display_screens`, `network`, `audio`, `clipboard_sync`, `boot_media`, `launch_refusal`, `disks` (массив: `location` `in_bundle`/`external`, `format`, `writable`, для `in_bundle` — `name`, `size_bytes`); иначе `problem` |
| `delete` | `name`, `path`, `files_deleted`, `warnings` (строки; сбой записи индекса после удаления — предупреждение, не ошибка) |
| `create` | `name`, `path`, `profile`, `memory_mib`, `disk_bytes` (число или `null`), `vmhost_started`, `warnings` |

### 4.3. События `run --json-events`

Каждая строка stdout — объект с `schema`, `command: "run"` и `event`:

| `event` | Поля |
|---|---|
| `ready` | — (получен `READY`) |
| `state_changed` | `from`, `to` (`stopped`, `running`, `paused`, `shutting_down`, `failed`), `reason` (`user`, `system_sleep`, `system_wake`, `guest_shutdown`, `host_failure`, `disk_space`), `request_id` |
| `command` | `line` (номер строки сценария), `script` (текст команды), `ok`, `state` (после ответа); для `query` — также `configured`, `disks_non_empty`, `last_reason` |
| `error` | `error` (как в 4.2), `fatal` (`ERROR` процесса машины) |
| `exited` | `status` или `signal` (завершение процесса машины) |
| `result` | последняя строка: `ok`, `exit_code`; при ошибке — `error`. Печатается и при SIGINT/SIGTERM у `odctl` (`ok: false`, `exit_code: 1`, `error.code` — `interrupted`) |

Без `--json-events` `run` печатает те же факты короткими строками. События `STATS` и `PROGRESS` не выводятся.

## 5. Библиотека

Без `--library` каталог библиотеки — каталог приложения: индекс `~/Library/Application Support/OpenDesktop/Library.plist`, каталог машин по умолчанию `~/Documents/Open Desktop/` (VM_BUNDLE 8). С `--library DIR` каталог машин — `DIR`, индекс — `DIR/Library.plist` (тот же формат); ничего вне `DIR` не читается и не пишется — так работают проверки.

Решение по открытому вопросу VM_BUNDLE 8 (п. 7 правил, раздел 11 п. 8): CLI **читает** индекс тем же кодом `Catalog` и **пишет** его только в двух случаях — `create` добавляет созданную машину, `delete` убирает запись; блокировки на `Library.plist` нет, действует «последний выигрывает» (VM_BUNDLE 8, правило 2). Потерянная запись о машине из каталога по умолчанию восстанавливается сканированием. `inspect <путь>` и `run <путь>` индекс не читают.

## 6. Файл сценария (`run --script`)

Текст UTF-8, до 64 КиБ, до 1000 команд, строка до 256 байт (считается строка целиком, вместе с комментарием; строка из одного комментария тоже). Одна команда в строке; пустые строки пропускаются; `#` начинает комментарий до конца строки. Регистр строчный. Команды:

| Команда | Действие |
|---|---|
| `start` | запрос `START` (operation ID 0); успех — состояние `running` |
| `pause` | запрос `PAUSE` с причиной `user` |
| `resume` | запрос `RESUME` с причиной `user` |
| `query` | запрос `QUERY`; состояние выводится |
| `stop` | запрос `STOP`; после него команд быть не должно |
| `wait <состояние> [тайм-аут_мс]` | ждёт состояния `stopped`, `running`, `paused`, `shutting_down` или `failed`; тайм-аут по умолчанию 10000 мс, не больше 600000; если состояние уже достигнуто, возвращается сразу; тайм-аут — код 1 |
| `sleep <мс>` | пауза 0…600000 мс |

Отказ процесса машины на любой команде прекращает сценарий: процесс машины останавливается (`STOP`, для машины с диском — закрытием соединения; при неудаче — SIGTERM/SIGKILL по правилам клиента), код завершения — по отказу (`busy` — 3, `unsupported_durability` — 4, иначе 1). Ошибка в тексте сценария (неизвестная команда, лишние аргументы, неизвестное состояние, число вне диапазона, команда после `stop`, пустой сценарий) — код 2 с номером строки; процесс машины при этом не запускается.

Пример (жизненный цикл S11-13):

```text
# test-only, без гостя
start
wait running
pause
wait paused 5000
resume
wait running
stop
```

## 7. Расхождения с приложением

Мастер создания (`CreateMachineExecutor`, S11-08b) лежит в цели приложения и использует `ErrorPresentation`, `Combine` и модель окна; вынести его в `ODShared` без правки UI нельзя. Поэтому порядок VM_BUNDLE 5.1, правила имени (3.2), имя каталога (2, п. 4) и отказ при памяти выше половины памяти компьютера повторены в `apps/cli/Sources/odctl/CreateCommand.swift` на общих типах. Отличия: нет проверки свободного места тома (S11-12, пороги живут в цели приложения; процесс машины сам отвечает `insufficient_space`); нет отката по подтверждению (CLI диалога не имеет, остаток не удаляется); правило удаления bundle (S11-06b) — одно правило в двух местах: у приложения `LibraryModel.removeBundleFiles` (цель приложения), у CLI `BundleRemoval` в `ODShared` (`OdctlRules.swift`; дополнено удержанием `lock` до конца удаления и проверкой `disks/` при нечитаемой конфигурации), перевод приложения на `BundleRemoval` — следующий срез; при занятом имени каталога `create` — ошибка (`creation_directory_exists`), без числового суффикса (в VM_BUNDLE §2 п. 4 суффикс подбирается); SIGINT и SIGTERM во время `create --disk-gib` не обрабатываются: процесс `odctl` завершается сигналом по умолчанию, VMHost видит EOF на соединении и завершается сам (при `PREPARE_DISK` в полёте — как при потере транспорта), в bundle остаются каталоги без `config.plist` (не машина; удаляется вручную); ошибки ожидания (`wait_timeout`) и использования — собственные фразы CLI, не записи каталога.

## 9. Диагностические флаги od-runner (не odctl)

### 9.1. Диагностика `od-runner boot-firmware --op-histogram-out` (PERF-20)

Это не команда `odctl`, а диагностический флаг раннера (`tools/runner`, не часть пользовательского CLI). `--op-histogram-out <файл>` допустим только с `--cpu-loop unified` (иначе отказ при разборе аргументов) и не должен совпадать с другими файлами запуска. Перед каждой инструкцией она декодируется чтением без побочных эффектов (без битов accessed/dirty, без изменения кэшей и счётчиков), а после шага, если инструкция исполнена (retired), увеличивается счётчик по ключу «вариант `Operation` + вид операндов + размер операнда + CPL». Вид операндов: `mem` (есть операнд в памяти), `reg` (только регистры), `none` (явных операндов нет); он определяется явным разбором вариантов, формой имени варианта и текстом `Debug` декодированной операции (подробности и ограничения ниже). Размер — `operand_size` инструкции в байтах. Инструкция, исполненная, но не декодированная чтением, считается под ключом `<undecoded>`, поэтому сумма счётчиков равна числу исполненных инструкций.

Режим включается только флагом: цикл получает его константным параметром (как `TRACE_ENABLED`), в обычном прогоне проверки в горячем цикле нет. В режиме декодированный кэш инструкций остаётся, но каждый шаг дополнительно декодируется, поэтому прогон с гистограммой медленнее обычного и не годится для замера времени. Гистограмма считает исполнения, это не профиль времени.

Файл — JSON: `retired`, `total` (сумма счётчиков), `sum_equals_retired`, `keys`, `by_cpl` (`cpl0`…`cpl3`: `count`, `share`) и `entries` по убыванию счётчика, у каждой записи `key` (`Операция/вид/размер/cplN`), `operation`, `operands`, `operand_bytes`, `cpl`, `count`, `share`, `cumulative_share`. В отчёт запуска добавляется `op_histogram` (путь, `total`, `retired`, `sum_equals_retired`, `keys`, `cpl0`, `cpl3`).

Ограничения классификации вида операндов:

- `StackRegister` (PUSH/POP регистра) — один вариант с полем `push`; в ключе он разделён на `StackRegisterPush` и `StackRegisterPop`, вид `reg` (обращение к стеку как к памяти не считается).
- Формы SSE/MMX с индексами регистров (имена на `Register`, `RegisterMasked`, `ImmediateRegister`) и варианты с полем `Register` (`LoadTr`, `LoadLdt`, `Load*SelectorReg`, `ReadCr*Into`, `WriteCr*From`, `WriteDebugRegister`) — `reg`.
- Варианты с адресом, заданным самим вариантом (`*MemoryRax`, x87 `F*M16/M32/M64/M80*Rax`, `Fnstenv`/`Fnsave`/`Frstor`/`FldenvRax`, `WriteCr0Rdi`, `Fxsave64Rax*`), и формы FS/GS (`MovFsLoad`, `AddGsMem`, ...) — `mem`.
- `Movs`/`Stos`/`Lods`/`Scas`/`Cmps` обращаются к памяти неявно и остаются `none`.
- `Lea` несёт операнд `MemoryOperand` и считается `mem`, хотя память не читает и не пишет.
- Остальные варианты разбираются текстом `Debug`: `MemoryOperand` — `mem`, `RegisterView` — `reg`, иначе `none`; вид — оценка по форме операции, а не измерение обращений к памяти.

### 9.2. Диагностика `od-runner boot-firmware --fast-path-verify` (PERF-22)

Диагностический флаг раннера (не часть пользовательского CLI), допустим только с `--cpu-loop unified` (иначе отказ при разборе аргументов). Сверочный режим «быстрый путь против общего» по ADR-0017, раздел 5: каждая инструкция исполняется общим путём по-настоящему над памятью машины через обёртку, которая записывает каждое обращение к `GuestMemory` (метод, адрес, контекст доступа, ширину, записанные байты или значения, результат; выборки декодера хранятся отдельно и не сравниваются). Затем быстрый путь (`try_fast_step`) воспроизводится на копии состояния CPU, снятой до шага, над записью: воспроизведение отвечает из журнала и не обращается ни к RAM, ни к устройствам, поэтому устройства видят каждое обращение ровно один раз, а MMIO-инструкции сверяются тем же механизмом. Сравниваются всё `LongModeState`, маска `rflags_defined`, исход шага и полная упорядоченная последовательность обращений к памяти (чтения тоже). Первое расхождение останавливает прогон: раннер завершается с кодом 5, видом ошибки `run_error` и сообщением с RIP, байтами и декодированной инструкцией, различающимися полями состояния и первым расходящимся обращением к памяти. Без расхождений в результат добавляется `fast_path_check`: `compared` (инструкции, которые взял быстрый путь и которые сравнены), `refused_by_admission` (быстрый путь вернул «не обработано»), `before_decode` (шаг закончился до декодирования), `not_decoded`, `memory_calls_compared`, `divergences`.

С PERF-23 (группа Г2) быстрый путь берёт `Arithmetic`, `Logic` и `Shift` без операнда-памяти при CPL0, RF = 0, TF = 0, без тени STI/MOV SS, без префиксов LOCK/REP/REPNE и сегментов FS/GS; всё остальное — `refused_by_admission`. Ожидаемый результат — `divergences = 0` и `compared > 0` (до PERF-23 быстрый путь был пуст: `compared = 0`); сравнитель проверяется тестами. Это готовит приёмку срезов. Режим включается константным параметром цикла и полем набора CPL0 (`Cpl0ProfileSet::with_fast_path_verify`): без флага в цикле нет кода проверки и поведение не меняется. Прогон в режиме в несколько раз медленнее (копия состояния и запись каждого обращения на каждой инструкции, декодирование повторяется, кэш декодированных инструкций обходится). Вне сравнения остаются порты и ячейки профилей набора (MSR, половина x87 в ячейке FP, ячейки CR3): быстрый путь не вправе их трогать (ADR-0017, раздел 4). Кеша блоков в этом режиме нет: `--fast-path --fast-path-verify` идёт без блоков и без ошибки (раздел 9.6); блоки сверяет `--block-cache-verify` (раздел 9.5).

### 9.3. Флаг `od-runner boot-firmware --fast-path` (PERF-23)

Диагностический флаг раннера, допустим только с `--cpu-loop unified` (иначе отказ при разборе аргументов; повтор флага тоже отказ). Включает быстрый путь группы Г2 в обычном шаге (ADR-0017, раздел 3, «Включение»): `try_fast_step` вызывается сразу после декодирования, до цепочки условий верхнего уровня; ответ «не обработано» оставляет инструкцию общему пути без изменений. Поле набора CPL0 — `Cpl0ProfileSet::with_fast_path`; по умолчанию выключено, и без флага поведение строго прежнее. Прогон с флагом даёт те же `retired`, состояние, вывод COM1 и обращения к памяти, что и без него. С `--fast-path-verify` побеждает сверка: общий путь исполняется по-настоящему, быстрый только воспроизводится для сравнения. Циклы `parallel_run`, `host_parallel`, SMP, `vcpu_quantum`, `linux_direct` и режим трассы флаг не получают. С PERF-33 (E1) флаг в unified-цикле по умолчанию включает и кеш предекодированных блоков (раздел 9.6).

### 9.4. Флаг `od-runner boot-firmware --block-stats` (PERF-33)

Диагностический флаг раннера, допустим только с включённым кешем блоков (раздел 9.6: `--cpu-loop unified` и `--fast-path`, без `--no-block-cache` и `--fast-path-verify`); иначе — отказ при разборе аргументов с сообщением `--block-stats requires the block cache (--cpu-loop unified and --fast-path, without --no-block-cache or --fast-path-verify)`, повтор флага тоже отказ. По умолчанию выключен. С флагом кеш предекодированных блоков (PERF-31, ADR-0018, вариант (а)) ведёт счётчики (ADR-0018, раздел 5, M1), и в отчёт запуска добавляется `unified.block_stats`: `lookups`, `hits`, `empty_hits`, `misses`, `stale`, `built_blocks`, `built_instructions`, `flushes`, `resets`, `holds_failed`, `runs`, `retired_from_blocks`, `retired_in_runs_of_two_or_more`, `run_lengths` (корзины `1`, `2`, `3`, `4-7`, `8-15`, `16-31`, `32+`), `mean_run_length`, `mean_built_block_length`, `share_retired_from_blocks`, `share_retired_in_runs_of_two_or_more`. PERF-33 (E4, шаг 2) добавляет причины конца блока и общий шаг: `end_reasons` — прогоны блоков по причине конца, все ключи всегда есть, сумма равна `runs`: дошли до конца блока — `branch` (блок кончается Jcc/JMP/CALL/RET, норма), `outside_fast_path` (блок кончается перед инструкцией, которую не пропускает фильтр `fast_block_role`), `branch_prefix_filtered` (перед Jcc/JMP/CALL/RET с префиксом LOCK/REP/REPNE или FS/GS: фильтр их не пропускает, блок обрывается перед ними), `page_end`, `page_crossing` (перед инструкцией, которой нужен байт следующей страницы), `length_limit` (64), `decode_error`; оборваны внутри блока — `refused` (быстрый путь отказал инструкции, которую пропустил фильтр), `branch_prefix_refused` (так отказано Jcc/JMP/CALL/RET с другими префиксами не по умолчанию — 66, сегмент CS/DS/ES/SS, REX: фильтр их пропускает, это отказ быстрого пути, а не конец блока), `not_retired` (сбой или другой выход шага), `holds_failed`, `call_end` (пакетный вызов кончился внутри блока: граница пакета, бюджет, остановка), `unknown` (конец блока не записан при сборке; в прогоне раннера 0); `end_outside_fast_path_by_key` — прогоны с концом `outside_fast_path` и `branch_prefix_filtered` по ключу инструкции, перед которой кончился блок; `general_by_reason` — инструкции, исполненные общим шагом (не из блока), по причине, все ключи всегда есть: `no_lookup` (поиск блока не прошёл ворота: трансляции нет в кеше выборки, не RAM и т. п.), `not_block_form`, `branch_prefix_filtered`, `page_crossing`, `decode_error` (блок с этого RIP не начинается по этой причине), `refused`, `branch_prefix_refused` (как выше), `single_step` (вызов в одну инструкцию, где блоков нет: CPL3, RF, тени кеша выборки); `general_by_key` — те же инструкции по ключу `<причина>:<Operation>/<операнды>/<байты>/cpl<N>` (ключ PERF-20, как `key` в `--op-histogram-out`; инструкция декодируется только для чтения, `<undecoded>/none/0`, если не декодировалась); `general_retired`, `share_retired_general`; `sum_equals_retired` — `general_retired + retired_from_blocks == retired`. Без флага поля нет, а release-сборка не пишет ни одного счётчика кеша блоков на горячем пути (каждое обновление стоит за проверкой одного поля `bool` кеша); debug-сборка считает всегда (константа `od_machine::BLOCK_CACHE_COUNTED`, для тестов), но поле в отчёт попадает тоже только с флагом. Исполнение от флага не зависит: `retired`, состояние, COM1, NVRAM и снимок остановки те же, отчёт отличается только полем `unified.block_stats`. `tools/bench/linux_boot_perf.py` передаёт флаг раннеру как есть (`record`, `measure`, `profile` с `--block-stats`) и пишет `block_stats` в метаданные записи; замеры K4 снимаются без него.

### 9.5. Диагностика `od-runner boot-firmware --block-cache-verify` (PERF-33, E5)

Диагностический флаг раннера, допустим только с включённым кешем блоков (раздел 9.6: `--cpu-loop unified` и `--fast-path`, без `--no-block-cache`); иначе — отказ при разборе аргументов с сообщением `--block-cache-verify requires the block cache (--cpu-loop unified and --fast-path, without --no-block-cache)`; вместе с `--fast-path-verify` — отказ с сообщением `--block-cache-verify does not combine with --fast-path-verify`; повтор флага тоже отказ. По умолчанию выключен; с `--block-stats` сочетается. Сверочный режим кеша предекодированных блоков: поиск блока и проход по нему идут как в обычном прогоне с блоками (те же условия: быстрый путь, пакетные вызовы обычного прогона, бюджет вызова прежний), но каждая инструкция исполняется общим шагом со свежим декодом — кеш декодированных инструкций в этом режиме не используется, декодер читает байты выборкой, как без кешей, — и этот декод сравнивается с инструкцией, которую блок хранит для того же RIP. Сравнение не читает память и не меняет кешей: адаптер памяти отдаёт декод, уже сделанный шагом (`GuestMemory::take_decoded_for_block_check`). Первое расхождение останавливает прогон: раннер завершается с кодом 5, видом ошибки `run_error` и сообщением с RIP, номером инструкции в блоке, длиной блока, полями обеих инструкций и байтами по RIP (`bytes=`, прочитаны после остановки обходом без побочных эффектов, как `rip_bytes`); счётчики до расхождения остаются в отчёте ошибки. Без расхождений в результат добавляется `block_cache_check`: `compared` (инструкции блоков, чей свежий декод сравнён с блоком), `not_decoded` (шаг закончился без декода: сравнивать нечего, проход блока кончается), `divergences`. Ожидаемый результат — `divergences = 0` и `compared > 0`. Отличие от прохода в обычном прогоне: отказ быстрого пути происходит внутри общего шага и сверке не виден, поэтому после такой инструкции проход блока продолжается, а не начинается поиск нового блока; в обоих случаях сравнивается декод тех же байтов. Режим включается константным параметром цикла (`Cpl0ProfileSet::with_block_cache_verify`, отдельный экземпляр функции цикла): без флага в цикле нет кода сверки. Прогон в режиме медленнее обычного прогона с блоками (общий шаг и декод каждой инструкции) и для замеров скорости не предназначен.

### 9.6. Кеш блоков по умолчанию с `--fast-path`; флаг `--no-block-cache` (PERF-33, E1)

В unified-цикле `od-runner boot-firmware` флаг `--fast-path` по умолчанию включает кеш предекодированных блоков (PERF-31, ADR-0018, вариант (а)): пакетные вызовы исполняют быстрый путь из сохранённых прямолинейных блоков. Блоки меняют только источник декода: `retired`, состояние, COM1, NVRAM, снимок остановки и все поля отчёта (включая `unified`) те же, что без них; поля о блоках появляются только с `--block-stats` (раздел 9.4) и `--block-cache-verify` (раздел 9.5). Без `--fast-path` блоков нет, и поведение строго прежнее; цикл прошивки (`--cpu-loop firmware`), `od-runner linux` и остальные циклы блоков не получают.

| Флаги (вместе с `--cpu-loop unified`) | Результат |
|---|---|
| без `--fast-path` | блоков нет |
| `--fast-path` | блоки включены |
| `--fast-path --no-block-cache` | быстрый путь без блоков (контроль замеров K4) |
| `--fast-path --fast-path-verify` | блоков нет, без ошибки: сверка быстрого пути — диагностический режим (раздел 9.2) |
| `--no-block-cache` без `--fast-path` (в любом цикле) | отказ: `--no-block-cache requires --cpu-loop unified and --fast-path` |
| `--block-cache-verify` без блоков (без `--fast-path` или с `--no-block-cache`) | отказ (раздел 9.5) |
| `--block-cache-verify` вместе с `--fast-path-verify` | отказ: `--block-cache-verify does not combine with --fast-path-verify` |
| `--block-stats` без блоков (без `--fast-path`, с `--no-block-cache` или с `--fast-path-verify`) | отказ (раздел 9.4) |
| `--block-boundary-verify` без блоков или вместе с другой сверкой | отказ (раздел 9.8) |

Повтор `--no-block-cache` — отказ. Отказы — при разборе аргументов (код 3, `invalid_input`), до загрузки образа. Флага `--block-cache-prototype` (PERF-31, до E1 включал блоки явно) больше нет: раннер отказывает в нём как в любом неизвестном аргументе. `tools/bench/linux_boot_perf.py` (`record`, `measure`, `profile`) передаёт `--no-block-cache` раннеру как есть и сам отказывает в нём без `--fast-path`; в метаданные записи пишет `no_block_cache` и `block_cache` — фактическое состояние кеша блоков (`--fast-path` без `--no-block-cache`). Записи до E1 вместо `block_cache` несут `block_cache_prototype` (наличие прежнего флага); `compare` ни одно из этих полей не сравнивает.

### 9.7. Кеш трансляции данных: `--data-cache-prototype` и сверка `--data-cache-verify` (PERF-11, PERF-12, E8)

`--data-cache-prototype` (только с `--cpu-loop unified`, иначе отказ `--data-cache-prototype requires --cpu-loop unified`) включает кеш трансляции данных unified-цикла (ADR-0016): обращения к данным внутри одной 4 КиБ страницы — чтения 1, 2, 4 и 8 байт и записи 1, 2, 4 и 8 байт с происхождением `Explicit` (с E8; до E8 — только чтения 8 байт) — берут перевод из кеша одного кванта вместо обхода таблиц. Кеш точный: `retired`, состояние, COM1, NVRAM, снимок остановки и все поля отчёта те же, что без него. Без флага, в цикле прошивки и в диагностических режимах (отчёт кеша выборки, наблюдения, трасса) кеша нет.

`--data-cache-verify` — сверочный режим кеша (ADR-0016, решение Д5); допустим только с `--data-cache-prototype` (иначе отказ `--data-cache-verify requires --data-cache-prototype`), вместе с `--fast-path-verify` или `--block-cache-verify` — отказ `--data-cache-verify does not combine with --fast-path-verify or --block-cache-verify`; повтор флага — отказ; с `--fast-path` (блоки по умолчанию) и `--block-stats` сочетается. Кеш служит как в обычном прогоне, но на каждом попадании, до использования записи, делается обход таблиц без побочных эффектов (без битов A/D, без уведомлений, без изменения кешей) и сравнивается с записью: обход успешен, тот же физический кадр, те же кадры таблиц пути, бит A во всех записях пути, бит D листа у записи класса Write, попадание записи — только в запись класса Write. Первое расхождение останавливает прогон: раннер завершается с кодом 5, статусом `run_error`, `error.kind` = `data_cache_check` и сообщением с линейным адресом, RIP, видом попадания и причиной; счётчики до расхождения остаются в отчёте ошибки. Без расхождений в результат добавляется `data_cache_check`: `verified_reads`, `verified_writes` (сверенные попадания чтения и записи), `divergences`. Ожидаемый результат — `divergences = 0` при ненулевых `verified_reads` и `verified_writes`. Прогон в режиме медленнее обычного (обход на каждое попадание) и для замеров скорости не предназначен. `tools/bench/linux_boot_perf.py` этот флаг не передаёт: сверку запускают прямым вызовом раннера (проверка KD плана части 2).

### 9.8. Сверка короткой границы: `--block-boundary-verify` (E9, ADR-0019)

С кешем блоков пакетный вызов unified-цикла внутри прохода блока делает короткую границу (ADR-0019): после инструкции блока, за которой идёт следующая инструкция того же блока, проверяются только счётчик обращений к устройствам и атомарные флаги остановки (`host_stop`, флаги пробуждения xHCI и NIC, тик RDTSC), и только когда источник IRQ «тихий» (сохранённый ответ «вектора нет»). `--block-boundary-verify` — сверочный режим этой границы; допустим только с включённым кешем блоков (раздел 9.6), иначе отказ `--block-boundary-verify requires the block cache (--cpu-loop unified and --fast-path, without --no-block-cache)`; вместе с `--block-cache-verify`, `--fast-path-verify` или `--data-cache-verify` — отказ `--block-boundary-verify does not combine with --block-cache-verify, --fast-path-verify or --data-cache-verify`; повтор флага — отказ; с `--data-cache-prototype` и `--block-stats` сочетается. В режиме сверки на каждой границе, где короткая проверка ответила бы «да», она только записывает предсказание (RIP следующей инструкции и номер отретайренной инструкции в проходе), а цикл делает полную границу; та подтверждает предсказание: записи инструкции в адаптере пусты, полная граница отвечает «продолжать», ничего не передаёт циклу (ни остановки, ни вектора), не меняет хук IRQ (счётчики отказов и доставок, сохранённый ответ, пропуск первой границы) и готовит адаптер к предсказанному RIP. Предсказание, которое вызов не подтвердил (вызов закончился раньше полной границы), — тоже расхождение. Первое расхождение останавливает прогон: раннер завершается с кодом 5, статусом `run_error`, `error.kind` = `block_boundary_check` и сообщением с RIP, номером инструкции в проходе и причиной; счётчики до расхождения остаются в отчёте ошибки. Без расхождений в результат добавляется `block_boundary_check`: `verified_boundaries` (подтверждённые короткие границы), `divergences`. Ожидаемый результат — `divergences = 0` при `verified_boundaries > 0`. Прогон в режиме идёт с полными границами, поэтому его JSON (кроме `block_boundary_check`), COM1 и NVRAM равны прогону без флага; для замеров скорости он не предназначен. `tools/bench/linux_boot_perf.py` флаг не передаёт: сверку запускают прямым вызовом раннера (проверка KS плана части 2).
