# Методика проверки Windows-гостя (этап 8)

Статус: **методика, а не результат.** Документ создан задачей S8-02 [плана этапа 8](../plans/STAGE_8.md) и описывает, как доказать, что фаза Windows-гостя наступила. Windows в нашей VM пока не запускалась; ни один прогон не выполнен, инструменты S8-10, S8-11, S8-12, S8-21, S8-22 и S8-27 реализованы и проверены только на macOS (разделы §8–§12, §15, §16), на Windows они не запускались; остальные упомянутые ниже «будущие» инструменты не существуют. Формулировки «должен», «пишет» относятся к требованиям к инструментам и скриптам, которые создают другие задачи (S8-10…S8-12, S8-22, S8-23, S8-27); до их приёмки это требования, а не описание готового поведения. Факты по задачам и прогонам пишутся в [отчёт этапа 8](../reports/STAGE_8_REPORT.md), результаты по приложениям и сценариям — в [матрицу совместимости](../../tests/compat/WINDOWS_MATRIX.md).

Границы этапа и словарь (nonce-маркер, обход, холодный перезапуск runner'ом, диск полезной нагрузки и др.) — в [плане этапа 8](../plans/STAGE_8.md), разделы 0, 3 и 4. Конфигурация безопасности и поддерживаемый профиль Windows — отдельный документ `docs/specs/WINDOWS_GUEST_PROFILE.md`, его создаёт S8-05.

## 2. Слова, которыми записываются результаты

- «Реализовано» — код есть, тесты проходят, ревью пройдено, отчёт записан.
- «Подготовлено» — есть документ или каркас без доказанного поведения.
- «Наблюдалось» — факт виден в журнале конкретного прогона с записанным nonce и хешами входов.

Рабочий стол Windows сам по себе не является продуктовым milestone. Не писать «Windows работает» без ссылки на run-id и принятые gates.

## 3. Nonce-маркеры

### 3.1. Формат строки

```
OD8 <nonce> <phase> <status> <sha256>
```

- Поля разделены ровно одним пробелом (U+0020); строка заканчивается ровно одним терминатором, `\n` или `\r\n`; в строке нет других символов. Скрипты гостя пишут `\n` (§3.4).
- `nonce` — 128 бит из системного CSPRNG host, 32 символа hex в нижнем регистре. Один nonce на один прогон.
- `phase` — имя из фиксированного списка (§3.2).
- `status` — `ok` или `fail`.
- `sha256` — 64 символа hex в нижнем регистре: хеш результата фазы, который можно проверить независимо.

Регулярное выражение для разбора одной строки (Python, `re.fullmatch` после удаления ровно одного терминатора, `\n` или `\r\n`):

```python
OD8_MARKER = re.compile(
    r"OD8 (?P<nonce>[0-9a-f]{32}) "
    r"(?P<phase>firstlogon|boot|build|shutdown|update|app:[a-z0-9][a-z0-9._-]{0,31}) "
    r"(?P<status>ok|fail) "
    r"(?P<sha256>[0-9a-f]{64})"
)
```

Правила разбора:

- Файл читается как ASCII (без BOM; скрипты гостя обязаны писать в ASCII — UTF-16 и UTF-8 с BOM не разбираются). Строка, не совпавшая целиком с выражением, — **нераспознанная**: она не считается маркером, попадает в `run.json` как нераспознанная и делает прогон подозрительным до разбора.
- Терминатор — ровно один. Пустая строка и строка, у которой после снятия одного терминатора остался `\r` или `\n` (например, `\r\r\n`), — нераспознанные. Последняя строка файла без терминатора — оборванная запись (машина остановлена посреди записи): она нераспознанная и не принимается, даже если совпала с выражением.
- Файл только дописывается; разбор не предполагает порядка и уникальности строк. Для проверки фазы берутся строки с nonce текущего прогона (§4).
- Неоднозначность: если для одного nonce и одной фазы в файле есть и строка `ok`, и строка `fail`, вердикт по этой фазе не принимается, прогон считается неоднозначным (`verdict = ambiguous`, разбор по §7, повторный прогон с новым nonce). Несколько строк `ok` или несколько строк `fail` неоднозначности не создают (например, `boot` на каждой загрузке).
- Допустимое значение `phase` проверяется списком, а не только синтаксисом; новое имя добавляет задача, которая его вводит, одновременно с правкой этой таблицы и регулярного выражения.

### 3.2. Фазы

Смысл `sha256` каждой фазы фиксирует задача, которая вводит фазу; общее требование — хеш можно пересчитать независимо (§4.1 плана: номер build из реестра, SHA-256 выходного файла приложения, список драйверов). Пока строка таблицы не заполнена задачей-владельцем, фаза не может использоваться как доказательство. Хеши фаз `firstlogon`, `boot` и `shutdown` ниже совпадают с `guest/windows/tests/firstlogon.ps1` (S8-22); скрипт на Windows не запускался (S8-24).

| `phase` | Когда пишется | Что хешируется | Определяет |
|---|---|---|---|
| `firstlogon` | После автоматического входа, из `FirstLogonCommands`; пишется после регистрации задачи `OD8Boot` (§3.4) | SHA-256 UTF-8 строки `<CurrentBuild>.<UBR>` из `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion`; при `fail` — SHA-256 UTF-8 текста ошибки | S8-22 |
| `boot` | Задача `OD8Boot` на каждой загрузке после первого входа, до `boot.ps1` | То же, что у `firstlogon` (строка `<CurrentBuild>.<UBR>`; при `fail` — текст ошибки) | S8-22 |
| `build` | Фаза с номером build Windows | не определено в плане (пример из §4.1: номер build из реестра); фиксирует задача-автор | S8-24 или S8-22 |
| `shutdown` | Непосредственно перед `shutdown /s /t 0`; пишет скрипт первого входа и задача `OD8Boot` (после `boot.ps1`) | SHA-256 байтов `markers.txt` до этой строки (все предыдущие строки вместе с терминаторами). `status = fail`, если предыдущая фаза скрипта завершилась с `fail` или `boot.ps1` вернул ненулевой код; правило хеша то же | S8-22 |
| `update` | После установки накопительного обновления | не определено в плане; фиксирует S8-50 | S8-50 |
| `app:<name>` | После запуска приложения матрицы | SHA-256 выходного файла приложения (§4.1) | задачи S8-46…S8-49 |

### 3.3. Каналы

**Основной канал — файл `OD8\markers.txt` на диске полезной нагрузки.**

- Диск полезной нагрузки — собственный GPT/FAT32 raw-диск, который собирает S8-27. Метка тома фиксирована: `OD8PAYLOAD`. Гость находит том по метке, а не по букве.
- Каталог `OD8\`: `nonce.txt` (nonce прогона, пишет инструмент прогона **до** запуска машины), `markers.txt` (изначально пустой, дописывается гостем), `boot.ps1` (необязательный сценарий, запускаемый `OD8Boot`).
- Гость дописывает строку и сбрасывает файл на диск (`flush` файла). Диск пишется через файловый backend с сквозной записью (`VWC = 0` по NVMe-контракту, §4.3 плана).
- Host читает `markers.txt` **только после остановки машины**, только для чтения. Runner и инструмент прогона не пишут маркер и не меняют диск между запуском машины и её остановкой.

**COM1 — дополнительный канал, только после принятого S4-24.** Родительская задача [S4-24](../plans/STAGE_4.md) на 2026-11-20 **не принята**: COM1 на firmware board — bounded polling без доставки IRQ4, а inbox `serial.sys` Windows работает с прерываниями. Поэтому до принятия S4-24 COM1 даёт вывод прошивки и **ничего не доказывает о Windows**: маркеры на COM1 не пишутся и не принимаются, EMS (S8-32) не используется. **Открытый пункт.** После принятия S4-24 команда записи в COM1 — `mode COM1:115200,n,8,1` и запись в устройство `COM1` — должна быть подтверждена документацией Microsoft; ни команда, ни источник сейчас не подтверждены. Источник записывается в этот раздел в момент принятия S4-24, пока источник не записан — канал не используется.

### 3.4. Задача планировщика `OD8Boot`

Определена в S8-22 п. 2; описание ниже сверено с текущей версией `guest/windows/tests/firstlogon.ps1` (S8-22). Скрипт проверен только разбором и тестами на macOS; на Windows не запускался (S8-24), поэтому описание — требование к поведению, а не наблюдение.

- Один скрипт `firstlogon.ps1` работает в двух режимах: `-Mode FirstLogon` (по умолчанию; запускается `FirstLogonCommands` с диска полезной нагрузки, §8) и `-Mode Boot` (запускается задачей `OD8Boot`). Каждая строка дописывается в `markers.txt` в кодировке UTF-8 без BOM (только ASCII), с терминатором `\n`, со сквозной записью и сбросом (`Flush`) на устройство.
- Порядок режима FirstLogon: найти том `OD8PAYLOAD` (ожидание до 120 с) и прочитать `OD8\nonce.txt`; **сначала** зарегистрировать задачу планировщика `OD8Boot` «при запуске системы» от имени SYSTEM, **затем** дописать маркер `firstlogon`; затем дописать маркер `shutdown`, сбросить файл на диск и выполнить `shutdown /s /t 0`. Хеш `firstlogon` — SHA-256 строки `<CurrentBuild>.<UBR>`; если регистрация задачи или чтение реестра завершились ошибкой, пишется `status = fail`, хеш — SHA-256 текста ошибки, а маркер `shutdown` получает тот же `status`, и машина всё равно выключается.
- Задача не требует входа пользователя. **Требование (гипотеза до источника S8-22/S8-24):** `AutoLogon` и `FirstLogonCommands` срабатывают один раз, поэтому на каждой следующей загрузке работает только `OD8Boot`. Источник, что `LogonCount = 1` даёт ровно один автоматический вход, не подтверждён: Windows прибавляет 1 к `LogonCount` (известная проблема справочника, см. комментарий в шаблоне `tools/build/make_windows_unattend.py`), поэтому шаблон первой командой `FirstLogonCommands` записывает `AutoLogonCount = 0`. Поведение проверяется на S8-24 (`setupact.log`, число маркеров `firstlogon`).
- На каждой загрузке `OD8Boot` находит диск полезной нагрузки по метке `OD8PAYLOAD` (до 120 с; буква тома между загрузками может меняться), запускает с него `firstlogon.ps1 -Mode Boot`, который читает `OD8\nonce.txt`, пишет маркер `boot` (хеш и `fail` — как у `firstlogon`) и, если на диске есть `OD8\boot.ps1`, запускает его в отдельном процессе PowerShell; сценарий получает корень диска и nonce в переменных окружения `OD8_ROOT` и `OD8_NONCE` и может дописывать свои маркеры. Так работают сценарии S8-30…S8-63.
- После возврата из `boot.ps1` задача сама пишет маркер `shutdown` (`status = fail`, если `boot.ps1` вернул ненулевой код) и выключает машину. Сценарий, которому нужно перезагрузить машину или работать дальше, не возвращается из `boot.ps1`; тогда маркера `shutdown` нет, и это записывается в вердикт.
- Если диск полезной нагрузки или `nonce.txt` не найдены либо содержимое `nonce.txt` (после обрезки пробельных символов по краям) не совпало с видом из следующего пункта, маркер не пишется (без допустимого nonce он невозможен): скрипт делает запись в `%ProgramData%\OD8\diag.txt` на системном диске и завершается с кодом 1; хост считает фазу не пройденной. Диагностический файл не заменяет маркер.
- Nonce — ровно 32 символа hex в нижнем регистре (§3.1), то есть `^[0-9a-f]{32}\z` с учётом регистра. Это требование и хоста, и скрипта. Хост: `od-image-tool make-data-disk --nonce` принимает только такой вид (без опции пишет пустой `nonce.txt`), а разбор маркеров отвергает строки, не совпавшие с регулярным выражением §3.1. Скрипт: `Read-Nonce` читает `nonce.txt`, обрезает пробельные символы по краям и проверяет значение через `-cnotmatch '^[0-9a-f]{32}\z'`; несовпадение (пустой файл, прописные буквы, иная длина, лишние символы) завершает его ошибкой, затем запись в `diag.txt` и код выхода 1 **без маркера**. Диск без nonce этого вида прогоном не является.
- Механизм регистрации: скрипт использует `Register-ScheduledTask` (`New-ScheduledTaskTrigger -AtStartup`, субъект SYSTEM, `ServiceAccount`); `schtasks /create /sc onstart /ru SYSTEM` — документированная альтернатива. Источники (страницы Microsoft Learn, прочитаны 2026-11-20) указаны в комментарии скрипта; источник того, что `ExecutionTimeLimit = 0` означает «без ограничения», не найден, поэтому задан явный предел 7 суток.

## 4. Правило успеха и обходы

### 4.1. Успех только по маркеру текущего nonce

Фаза считается достигнутой, если одновременно:

1. В `OD8\markers.txt` есть строка, полностью совпавшая с регулярным выражением §3.1, с nonce **текущего** прогона (равным `nonce` в `run.json` и в `OD8\nonce.txt` этого диска), нужной `phase` и `status = ok`.
2. `sha256` маркера независимо воспроизведён по данным фазы (см. §3.2).
3. Машина остановлена с ожидаемой причиной (например, `Shutdown` после маркера `shutdown`; для фазы, не завершающейся выключением, — причина, указанная в задаче).
4. В `run.json` нет обходов (§4.2) и нет неразобранных строк-нарушителей.
5. Для этой фазы и этого nonce нет одновременно строки `ok` и строки `fail` (§3.1): иначе вердикт не принимается, прогон неоднозначный.

Всё остальное успехом не является: код выхода runner; «тишина» на COM1; совпадение с эталоном прошлого прогона; картинка на экране без маркера; маркер с чужим, пустым или старым nonce (он игнорируется и записывается как «чужой nonce» — это признак повторного использования диска или журнала); строка, записанная не командой внутри Windows. Маркер `fail` — результат прогона «фаза не пройдена» и подлежит разбору (§7).

Ошибка гостя (bugcheck, отказ драйвера, ошибка Setup) — гостевой результат, который записывается и разбирается. Остановка машины из-за неподдержанной инструкции, backend-ошибки устройства или host panic — дефект нашей платформы; его не маскируют перезапуском и не считают нестабильностью Windows.

### 4.2. Обходы

Обход — любое отключение проверки ради прохождения. Список из словаря плана; прогон с любым из пунктов — **отладочный**, записывается в отчёт с пометкой «обход», в `run.json` пишется в поле `bypasses`, gate по нему не принимается и в матрице совместимости не получает статус «проходит приёмку»:

- ключи `LabConfig` (`BypassTPMCheck`, `BypassSecureBootCheck`, `BypassCPUCheck` и т. п.);
- отключённый Secure Boot (SetupMode или Secure Boot выключен);
- удалённый TPM;
- `bcdedit /set testsigning on`;
- `nointegritychecks`;
- подмена файлов носителя (кроме добавления ответ-файла `sources\Autounattend.xml` новым выходным файлом `od-image-tool`, которое план разрешает).

## 5. Структура прогона и `run.json`

### 5.1. Каталог

Все рабочие файлы прогона — в `work/stage8/<run-id>/` (каталог `work/` игнорируется Git). В Git не попадают Windows, установочный носитель, виртуальные диски, пакеты обновлений, дистрибутивы приложений, аварийные дампы, ключи продукта и пароли; в Git попадают только собственные генераторы, маленькие fixtures, хеши и короткие выдержки журналов (вместе с данными измерений до 100 KiB на файл в `docs/reports/data/stage8/`). Пароль для ответ-файла лежит в `work/stage8/secret` и в отчёты не попадает.

`<run-id>` — уникальный идентификатор прогона. Рекомендуемая форма по образцу `work/stage3-harness`: `stage8-YYYYMMDD-HHMMSS-<10 hex>`; точный формат закрепляет инструмент прогона (S8-23/S8-24), расхождение исправляется здесь.

Содержимое каталога:

| Файл или каталог | Что |

| ответ-файл | Копия `Autounattend.xml` (без пароля в отчёте) |

### 5.2. `run.json`

Формат предварительный: поля ниже — обязательный минимум по плану (§3 п. 6, §5); точные имена и схему закрепляет код runner и задачи S8-11, S8-23, S8-24. Прогон без полей «хеши» и «nonce» доказательством не является.

| Поле | Содержимое |
|---|---|
| `run_id` | Идентификатор прогона |
| `task` | Задача этапа 8, для которой снят прогон |
| `hashes` | SHA-256: ROM (прошивка), носитель, ответ-файл, диск полезной нагрузки (и манифест), исполняемый файл runner (и коммит), исходные NVRAM и TPM state |
| `machine` | Конфигурация машины: число vCPU, RAM, список NVMe-дисков (роль, размер, источник), Secure Boot (режим), TPM, интерпретатор или JIT, бюджет кванта |

| `stop_reason` | Причина остановки машины (`Shutdown`, `Reset`, исчерпание бюджета, неподдержанная инструкция, backend-ошибка, triple fault и т. д.) |
| `markers` | Разобранные строки `markers.txt`: принятые (nonce совпал), чужие, нераспознанные |

## 7. Разбор сбоев

Повторяемая процедура S8-13 для каждого нового сбоя Windows или остановки машины. Здесь записана только процедура; записей `ISSUE-NNN` она не создаёт, и этот раздел не означает, что сбои уже разбирались. Шаги, опирающиеся на инструменты S8-10…S8-12, применимы после приёмки этих инструментов (§7.3); для Windows они не проверены, пока нет реального сбоя (S8-10 и S8-11 приняты по host-side критериям, S8-12 — частично, см. §7.3 и [§9](#9-журналы-с-диска-s8-12)); без этого разбор ограничивается тем, что уже есть в журнале машины (уровень 2).

### 7.1. Процедура

1. **Собрать входы.** Взять прогон с остановкой или bugcheck и его `run.json`. Собрать:
   - снимок остановки S8-10 (регистры, модуль и RVA по PE-заголовкам в памяти гостя, байты инструкции);
   - последние дампы экрана S8-11;
   - журналы Windows с диска S8-12 (`setupact.log`, `setuperr.log`, `setupapi.dev.log`, аварийные дампы);
   - stop code с экрана и из журнала — после S8-32; EMS на COM1 — только после принятого S4-24 (на 2026-11-20 не принят, §3.3).
2. **Классифицировать по владельцу.** Различить гостевой результат (bugcheck, отказ драйвера, ошибка Setup) и остановку машины (неподдержанная инструкция, backend-ошибка, triple fault, host panic — дефект нашей платформы). Определить владельца по таблице ниже. Этап 8 не исправляет семантику CPU, JIT, MMU, SMP и прошивки в обход их владельцев.
3. **Завести запись в `docs/KNOWN_ISSUES.md`** по её правилам, если проблема не устранена к завершению задачи: компонент, суть и последствия, воспроизведение (run-id, nonce, модуль и RVA, байты инструкции), статус, следующий шаг — задача владельца. Для неподдержанной инструкции записывать кодировку, режим, модуль и RVA; одинаковые кодировки объединять в одну запись. Предположения не выдавать за подтверждённые дефекты; записей «по памяти» нет; будущая функциональность (ещё не реализованная возможность) в реестр не записывается.

| Что сломалось | Владелец |
|---|---|
| ISA и режимы CPU | этап 2 |
| JIT | этап 3 |
| Память, устройства, lifecycle | этап 4 |
| Несколько vCPU | этап 6 |
| UEFI, ACPI, TPM | этап 7 |
| Диск и состояние | этап 9 |
| Дисплей | этап 10 |
| Сеть и приложение | этап 11 |
| Устройства и инструменты, которые план поручает этапу 8 (дополнительные NVMe-контроллеры, xHCI/USB HID; только после записанного решения о владельце в S8-01) | этап 8 |

### 7.2. Проверка и закрытие

- Каждая запись воспроизводима по run-id и хешам входов.
- Повтор прогона с тем же входом даёт тот же модуль и RVA (детерминизм одного vCPU) либо различие записывается.
- Запись не закрывается без принятой задачи владельца и повторного прогона.
- Классификация не заменяет исправления: внутри разбора не правят CPU и прошивку.

Процедура принята по ревью (чекбокс S8-13 отмечен); S8-10 и S8-11 приняты по host-side критериям (см. [§15](#15-снимок-остановки-s8-10) и [§16](#16-журнал-фаз-и-дампы-экрана-s8-11)). Условие п. 3 плана «если сбоев ещё нет — на собственном образе S8-10» закрыто примером ниже; он **не** заменяет разбор сбоя Windows после S8-24.

### 7.4. Пример разбора: собственный образ (S8-13)

Запись в `docs/KNOWN_ISSUES.md` не заводится: дефекта нет. Пример показывает, какие поля, в каком порядке и с какой проверкой записываются в разбор; значения для Windows будут другими.

**Вход и воспроизведение.**

- Run-id `s8-13-example-20261120T2222`; каталог `work/stage8/s8-13-example-20261120T2222/` (в Git не кладётся: `/work/**` игнорируется).

- `od-runner` — `target/release/od-runner`, SHA-256 `972bf4db5f12d8482548b75f88205654479a3b79b9c55dc955b77b46090f60f7`, пересобран `cargo build --release -p od-runner --offline` 20 ноября 2026 в 22:21 (местное время, −03:00) из рабочего дерева ветки `stage8`: код равен коммиту `716e399`, в рабочем дереве изменены только документы. Первый прогон примера (run-id `s8-13-example-20261120T2211`) выполнен более ранней сборкой (SHA-256 `9aca3aaa…2467`); пример ниже воспроизведён пересобранным бинарником.

Код выхода 5, `exit = budget_exhausted`, `status = error` в отчёте. SHA-256 `stop.json` — `982f01186ff65b436cc9ac7bb3c0873c27cafd708b457c41959223fcff617931`, `phases.jsonl` — `e83518c91af94c030c4fbb913a91064fff4a25562a633134de86fe77d2ad3312` (содержит host-время, поэтому при повторе отличается; у первого прогона `6c409bb6…65a3`).

**Шаг 1. Снимок остановки (§15).**

| Поле | Значение | Проверка |
|---|---|---|
| `reason` | `exit = budget_exhausted`; `stop_reason`, `unsupported_opcode`, `page_fault`, `memory_error`, `fw_stop` — `null` | совпадает с `report.json` |
| vCPU, режим | 0, `long64`, `activity = Running`; `cs_selector` и `cpl` — `null` (CS ещё не загружался, §15) | — |
| RIP | `0x301006` | равен `rip` отчёта |
| Байты RIP | `48 35 34 12 00 00 c3 cc cc cc 00 00 00 00 00 00` (прочитано 16, ошибки нет) | сверено с байтами PE по RVA `0x1006` |
| Инструкция | `xor rax, 0x1234` | декодирована вручную и сверена с `/usr/bin/objdump` (Apple LLVM 21.0.0, `coff-x86-64`; отдельного `llvm-objdump` в `PATH` нет, см. сверку ниже): `.text` по RVA `0x1000` — `48 89 c8` (`mov rax, rcx`), `48 31 d0` (`xor rax, rdx`), `48 35 34 12 00 00`, `c3` (`ret`) |
| Счётчики | `retired = 2`, `quanta = 1`, `virtual_ns = 2`, `budget = 2` | две инструкции до RIP исполнены: RIP указывает на третью, не исполненную |
| Модуль | `base = 0x300000`, `rva = 0x1006` (= RIP − base), `size_of_image = 20480`, `machine = 0x8664`, `pages_scanned = 2` | `ImageBase` заголовка `0x140000000`, образ размещён по `0x300000`, а не по `ImageBase`; `base` взят из страницы `MZ`, а не из заголовка |
| `time_date_stamp` | 1795218787 (`0x6B00DD63`) | равен `TimeDateStamp` заголовка PE |
| PDB | `hello_dbg.pdb`, GUID `A4CAA660-C88D-38B3-4C4C-44205044422E`, age 1, `symbol_key = A4CAA660C88D38B34C4C44205044422E1`, `pdb_error = null` | запись RSDS по RVA `0x2020` (debug directory `0x2004`) прочитана независимо: байты GUID `60a6caa4 8dc8 b338 4c4c4420 5044422e` после перестановки полей дают тот же GUID; age `01000000` |
| GPR | `rsp = 0x150000`, `rdi = 0x100000`, остальные 0 | — |
| Стек | 8 слотов от `0x150000`, все нулевые, модуль у них не найден | вызывающий модуль не определяется |

Сверка с дизассемблером. PE вынут из ROM в раскладке памяти, поэтому `PointerToRawData` секций указывают на нули, и `objdump -d` по вынутому файлу печатает пустую `.text`. На копии вне репозитория в заголовках секций `PointerToRawData` заменён на `VirtualAddress` (вынутый файл не менялся); после этого `objdump -d` разобрал `.text` по VMA `0x140001000`: `movq %rcx, %rax`, `xorq %rdx, %rax`, по `0x140001006` — `xorq $0x1234, %rax` (`48 35 34 12 00 00`), `retq`. Адрес `0x140001006` = `ImageBase + RVA 0x1006`, то есть RVA из снимка указывает на ту же инструкцию, что и RIP. `objdump -p` показывает debug directory по RVA `0x2004`, размер `0x1c`. Сверка RVA S8-10 с независимым дизассемблером на этом примере выполнена; для Windows не проверялась.

Ограничение: PDB не сохранён, поэтому символизация по `symbol_key` не выполнялась; проверено только, что GUID, age и имя совпадают с PE. Остаток GUID — ASCII `LLD PDB.` (синтетический GUID линкера); у PDB, собранных Microsoft, будет настоящий.

**Шаг 2. Журнал фаз и экран (§16).** `phases.jsonl` — одно событие: `stop` (`exit = budget_exhausted`, `instructions = 2`, `quanta = 1`, `virtual_ns = 2`, `restart = 0`). Событий `first_com1_write` и `com1_marker` нет: `com1_bytes = 0`, COM1 пуст. Дампы экрана не заказывались (`--framebuffer-*` не заданы; PE не вызывает GOP). Журналов диска (S8-12) нет: диска у прогона нет; stop code и EMS (S8-32, S4-24) неприменимы.

**Шаг 3. Классификация по владельцу (§7.1).** `budget_exhausted` — остановка по бюджету, который оператор задал флагом `--budget 2`; это не результат гостя и не дефект платформы. Владельца нет, запись реестра не нужна. Для сравнения, как та же причина распределяла бы владельцев: `unsupported_opcode` (например, намеренный `UD2` в тестах §15) — этап 2, с записью кодировки, режима, модуля и RVA; `page_fault` или `memory_error` — этап 4; `fw_stop` — этап 7; bugcheck — гостевой результат, до классификации по stop code с экрана (S8-32). В этом прогоне `UD2` нет.

**Повторяемость (§7.2).** Повтор с тем же ROM дал `stop.json`, байт в байт равный снимку первого прогона S8-10 (`work/stage8/s8-10-11/real/stopdbg.json`, тот же SHA-256 `982f0118…7931`); пересобранный `od-runner` (run-id `s8-13-example-20261120T2222`, команда из этого раздела) дал `stop.json` с тем же SHA-256 `982f0118…7931`, а `report.json` по `jq -S` отличается от первого прогона только путями каталога. Тот же модуль, RVA и байты — детерминизм одного vCPU на таком коротком пути подтверждён; на длинных путях и на Windows не проверялся.

## 12. Файловый диск в `boot-firmware` (S8-21)

`od-runner boot-firmware ... --disk <path>` подключает существующий RAW-файл через постоянный
backend этапа 5: каждая гостевая запись durable-flush'ится, файл заблокирован на время прогона;
второй runner получает ошибку блокировки (exit 3). Файл не создаётся и не расширяется.
Взаимоисключающ с `--nvme-image` (копия в памяти для smoke-наборов). Пока один диск; второй
`--disk` отклоняется (нужен S8-20). Пустой sparse-образ: `od-image-tool create-raw <каталог> <имя> <байты>`.

**Режим `--disk <path>,ro`.** Файл открывается без доступа на запись под общей блокировкой
(`flock(LOCK_SH)`): живой писатель даёт отказ (exit 3), пока ro-прогон идёт, писатель файл не заблокирует,
несколько ro-прогонов одного файла совместимы. Гостю namespace виден как защищённый от записи
(`NSATTR` бит 0), запись завершается статусом «Namespace is Write Protected» (0/`0x20`, DNR = 1),
чтение работает, файл не меняется. Поведение Windows Setup и `stornvme` на такой namespace не
проверено (NOT VERIFIED, NVME_DEVICE.md §14.6): для установки на диск ro непригоден, режим нужен
носителю установки. Проверка «диск не изменился» — SHA-256 файла до и после прогона. Диск ro,
как и записываемый, не должен совпадать с файлами ROM и NVRAM.

## 15. Снимок остановки (S8-10)

Запуск: `od-runner boot-firmware ... --stop-snapshot <file>`. JSON записывается после остановки машины, при любой остановке кроме `stop_reason = Shutdown` (ACPI S5, штатное выключение; в отчёте тогда `stop_snapshot.skipped`). Снимок пишется и для `Halted`, `BudgetExhausted`, `Reset`, `Fault`, `Unsupported`, `Backend`, `Shutdown` процессора, и для ошибки самого прогона (`run_error`): гость, остановившийся «тихо» на HLT или исчерпавший бюджет, тоже нуждается в адресе. Путь не должен совпадать ни с одним другим файлом прогона. Один запуск = одна загрузка: с `--nvram-reboot-out` (перезапуски — S8-23) и `--sample-rip` флаг не сочетается и отклоняется. Результат записи — поле `stop_snapshot` отчёта runner (`written`, `path`, `error`); ошибка записи код выхода не меняет.

**Поля JSON.** `reason` (поля отчёта: `exit`, `exit_detail`, `unsupported_opcode`, `stop_reason`, `page_fault`, `memory_error`, `fw_stop`); `vcpu` (номер; одно-vCPU путь `boot-firmware` — 0); `mode` (`long64` для long-mode модели исполнения, `legacy_model` для остальных; поле выставляется из `long_mode_model` vCPU); `cs_selector` и `cpl` (`CS & 3`; `null`, пока селектор CS не известен: состояние хранит `cs_selector` только после того, как CS загружен, например дальним переходом, LRETQ, доставкой прерывания или исключения, IRETQ, SYSCALL/SYSRET или входом в long mode); `activity`; `rip`; `rip_bytes` (до 16 байт по RIP: `hex`, сколько прочитано `read`, причина обрыва `error`); `gpr` (16 регистров); `rflags`, `cr0`, `cr2`, `cr3`, `cr4`, `efer`; `counters` (число исполненных инструкций, квантов, виртуальное время, бюджет); `inputs` (SHA-256 образа и handoff-блока, бюджет, `--fv-app`, TPM, SHA-256 входного NVRAM, для `--nvme-image` — путь, размер и SHA-256, для `--disk` — путь, `read_only` (`true` для `,ro`) и размер без хеша: диск без `ro` записывается гостем, и он может занимать десятки ГиБ); `module` — для RIP; `stack` — первые 8 слотов от RSP, у каждого `value` и `module` (так виден вызывающий модуль); `peeks` — только с `--peek` (S7-32): у каждого чтения `address` (`null`, если смещение задано от образа у RIP, а образа нет), `rip_module_offset` (для формы `rip_module+`), `read`, `hex`, `error`.

Прогон `--fv-app blk` на ro-диске (`work/stage8/s8-21/blk-gpt-ro.*`) остановился: STOP 0x35, detail 0x48 (STOP_BOOT_SERVICES); причина не разобрана, UEFI-драйвер NVMe на ro-диске не проверен.

**Определение модуля** (`tools/runner/src/guest_module.rs`). Таблиц адресов и сигнатур бинарей Windows в инструментах нет. От страницы адреса назад по гостевым виртуальным адресам с шагом 4 КиБ (до 64 МиБ) ищется страница, начинающаяся с `MZ`, у которой `e_lfanew` лежит в первой странице и указывает на `PE\0\0` (PE32+ и PE32), а `SizeOfImage` покрывает адрес; подходящий по заголовку образ, не покрывающий адрес, пропускается. Поиск прекращается на первой нечитаемой странице (в `reason` — страница и причина трансляции). Из debug directory берётся запись CodeView `RSDS`. В JSON: `base`, `rva` (= адрес − `base`), `size_of_image`, `time_date_stamp`, `machine`, `pdb` (`path`, `guid` в виде `XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX`, `age`, `symbol_key` — GUID без дефисов и `age` в hex, имя каталога сервера символов), `pdb_error` (если запись не читается: нет каталога отладки, нет записи CodeView, данные в отброшенной секции и т. п.; `base`, `rva`, `time_date_stamp` и `size_of_image` при этом остаются).

**Чтение гостя.** Только чтение через API `od-machine` (`LoadedFirmwareBoard::diagnostic_vcpu_state`, `diagnostic_read_virtual`; обе принимают `&self`): таблицы страниц (4 уровня, страницы 4 КиБ, 2 МиБ, 1 ГиБ) проходятся с CR3 vCPU без установки битов accessed/dirty; байты читаются только из RAM, ROM и framebuffer — MMIO не затрагивается, состояние устройств не меняется; права доступа не проверяются. Причина невозможности (не отображено — уровень и запись; не-canonical адрес; CR0.PG сброшен; CR4.LA57 — пятиуровневая трансляция не поддержана; нечитаемая таблица) пишется в `rip_bytes.error`, `module.reason` или `peeks[].error`, снимок при этом создаётся. Снимок не продолжает исполнение и не пишет в гостевую память; после ошибки backend'а состояние остаётся таким, каким его оставил прогон.

**Как пользоваться.** Адрес инструкции в образе = `base` + `rva`; с `pdb.path`, `guid` и `age` (или `symbol_key`) находится нужный PDB без запуска отладчика. Одинаковый вход даёт одинаковый снимок (одна vCPU детерминирована); различия записывают в разбор (§7).

**Проверено (macOS, не Windows).** Тесты: `cargo test -p od-machine --offline --lib -- stop_diagnostic firmware_board::tests::diagnostic_reads firmware_board::tests::quantum_hook` (трансляция 4 КиБ/2 МиБ/1 ГиБ, ошибки по уровням, неотображённые и MMIO-адреса, чтение через границу страниц); `cargo test -p od-runner --offline --bin od-runner -- stop_snapshot guest_module run_journal` (поиск образа с RVA и RSDS, пропуск неподходящих заголовков, пределы поиска, остановка на странице без отображения — снимок пишет причину и не падает) и `--test firmware_boot_cli` (флаг через CLI). Тестовый PE собран в тесте (RSDS, GUID, age, имя PDB), помещён в образ ODFWIMG1, остановка — намеренный `UD2`. Вручную на реальных PE, собранных rustc/lld-link для `x86_64-unknown-uefi` (образ ODFWIMG1 с PE, остановка по бюджету внутри образа): для `hello.efi` тестовых приложений прошивки (в debug directory только запись Repro, CodeView нет — `pdb_error`) и для отдельного PE, собранного с `-C debuginfo=2` (CodeView есть): `rva` совпал с адресом `llvm-objdump -d` минус `ImageBase`, байты по RIP — с кодировкой инструкции в дизассемблере, GUID, `age`, имя PDB и `TimeDateStamp` — с `llvm-readobj --coff-debug-directory`, `SizeOfImage` — с заголовком. Тестовые приложения прошивки в сборке без CodeView; добавлять отладочную информацию в сборку этих приложений должен владелец прошивки (этап 7), этот этап её не меняет.

**Не проверено / ограничения.** Реального сбоя Windows нет (первый — S8-13 на прогоне S8-24): не известно, читаются ли у модулей Windows debug directory и страницы заголовка в момент остановки (страницы INIT/pageable могут быть не отображены — тогда будет `pdb_error` или поиск оборвётся раньше). Только 64-битные таблицы страниц; номер vCPU — параметр API, но `boot-firmware` работает с vCPU 0; многопроцессорный запуск — S6-51/S8-24. В режиме без CS (ранняя загрузка прошивки) `cpl` — `null`.

**Диагностический режим `--device-errors log` (S7-32).** Цикл S7-32 «прогон → остановка → срез» тратит прогон на каждый пробел модели устройства: прогон в режиме `stop` (по умолчанию) останавливается на первом обращении гостя, которое устройство отвергло. `--device-errors log[:<n>]` (только `--cpu-loop unified`) показывает за один прогон ближайшие пробелы. Это **диагностика, а не результат совместимости**: начиная с первого «проглоченного» отказа гость видит машину, какой модель не обещает, и дальнейший путь может отличаться от пути на настоящем оборудовании.

- *Что поглощается.* Обращение гостя к PIO или MMIO, которое устройство отвергло (`DeviceError`: `UnsupportedConfiguration`, `UnknownOffset`, `ReadOnly`, `WriteOnly`, `UnsupportedWidth`, `Misaligned` и т. п., кроме `ClockOverflow` — это конец виртуального времени, а не пробел модели), а также порт без устройства (`UnmappedPort`) и обращение через границу привязки порта (`CrossesRegion`). `Busy` устройства (THR UART занят, запись таймера LAPIC в момент срабатывания, OCW 8259 посреди инициализации) тоже поглощается: это ситуация, которую модель не описывает, и в отчёте она видна как `kind` = `Busy`, но гость после неё видит отброшенную запись там, где на настоящем оборудовании она прошла бы. Запись отбрасывается (устройство по контракту `BusDevice` при отказе ничего не меняет; `mmio_written` не взводится; отброшенная запись в порт, как и принятая, считается обращением к порту (`SetPortWatch`): запись, задевающая порты PIT, завершает квант там, где его завершает принятая запись в PIT (источник с `pit_write_ends_quantum`), — лишняя граница кванта, состояние PIT не меняется), чтение возвращает все единицы ширины доступа (`0xFF`, `0xFFFF`, `0xFFFF_FFFF`, `u64::MAX`), инструкция завершается штатно. **Чтение-модификация-запись на MMIO при CPL0** читает операнд обычным чтением: если это чтение поглощено, запись той же инструкции по пересекающемуся адресу в устройство **не отправляется** (её значение выведено из выдуманных единиц, а устройство могло бы его принять — например, `or dword [lapic+0xB0], 0` записал бы EOI) — она отбрасывается и записывается отдельным видом события `SuppressedAfterAbsorbedRead` (устройство, адрес, значение); если журнал полон, прогон на ней останавливается. Не поглощаются и останавливают прогон, как раньше: MMIO по адресу без окна набора и без RAM; MMIO внутри окна, но вне региона устройства, и через границу региона (в отличие от порта без устройства, который поглощается: для портов «нет привязки» — пробел модели, для MMIO адрес вне регионов — ошибка раскладки); неподдерживаемая ширина MMIO (16-байтные SSE-операнды); выборка инструкции из MMIO; чтение-модификация-запись с намерением записи (`ReadForWrite`, CPL3) и `LOCK` на MMIO; занятая таблица устройств. Строковых команд портов (`INS`/`OUTS`) в наборе od-isa нет: такая команда — остановка ISA (`Unsupported`), режим её не меняет. Обращение к порту определяется по первому порту: dword- или word-доступ, который начинается с порта без привязки и задевает устройство (например, `in eax, dx` с `0x1E` задевает 8259 на `0x20`–`0x21`), записывается как `UnmappedPort` с `device_index` `null`, а начинающийся внутри привязки и выходящий за её конец — как `CrossesRegion` (тоже `null`); задетое устройство в таких группах определяют по адресу и ширине.
- *Где.* В представлении шины одной инструкции общего шага набора (`MachineBusSetStepIo`, `crates/od-machine/src/bus.rs`; журнал — `bus/device_error_log.rs`), только на пути ошибки: успешное обращение режим не проверяет; единственное, что добавлено на путь успешного обращения, — сверка записи MMIO с поглощённым чтением этой же инструкции (одна загрузка `Cell`; без журнала там всегда `None`). Общий шаг цикла (`run_cpl0_set_loop`, `paged_memory_adapter.rs`) отдаёт представлению RIP, CPL и число инструкций вызова; плата задаёт базу (число инструкций прогона до вызова) раз в квант и на каждой склейке квантов turbo. Семантика od-isa не меняется. Turbo-движок свой отказ не поглощает: `TurboExit::DeviceError` в режиме `log` передаёт инструкцию общему шагу (как медленный выход), и тот обращается к устройству ещё раз — с контекстом; устройство при этом видит отказанное обращение не менее двух раз (если граница вызова пришлась между ними, turbo попробует его снова; так же и после исчерпания предела), счётчик `device_access_counter` растёт на столько же, состояние устройства не меняется.
- *Предел.* После `<n>` поглощённых событий (по умолчанию 100 000, от 1 до 10⁹) или когда новая группа не помещается в 4096 групп, следующий отказ не поглощается: прогон останавливается на нём как в `stop` (тот же `exit`, `exit_detail`), а в отчёте `device_errors.stopped` = `event_limit` или `group_limit`.
- *Отчёт.* Только в режиме `log` в отчёте runner появляются `diagnostic_run: true` и `device_errors`: `mode`, `diagnostic: true`, `compatibility_result: false`, `note`, `event_limit`, `group_limit`, `events`, `stopped`, `groups`. Группа — ключ (`space` `pio`/`mmio`, `device_index` — индекс устройства на шине или `null`, если обращение до устройства не дошло (`UnmappedPort`, `CrossesRegion`), `address` — порт или физический адрес, `direction`, `width` в байтах, `kind` — вид отказа или `SuppressedAfterAbsorbedRead`) и `region_base` (начало привязки устройства), `count`, `first_retired`/`last_retired` (число инструкций, исполненных до инструкции первого и последнего обращения, как поле `retired` отчёта при остановке на ней), `first_rip`, `first_cpl`, `first_value` (значение первой записи; `null` у чтения). Группы идут в порядке первого обращения. Пометка и журнал есть в каждом отчёте `log`-прогона, в том числе завершившегося ошибкой runner до или после загрузки (`run_error`, запись COM1, гистограмма, `--framebuffer-out`, `--nvram-out`, `--acpi-out`, повторная проверка путей). Снимок остановки (`--stop-snapshot`) получает `inputs.device_errors` = `log:<n>`. **Статус и код выхода.** Коды `boot-firmware`: 0 — `completed`; 3 — `invalid_input`; 4 — `loader_error`; 5 — `error` или `run_error`; 6 — `firmware_stop`; 7 — `completed_with_absorbed_device_errors`. `log`-прогон, который поглотил хотя бы одно событие и дошёл до остановки, считающейся завершением (`hlt`, остановка машины), не получает `completed` и код 0: его статус — `completed_with_absorbed_device_errors`, код 7 (диагностический прогон нельзя выдать за успешный). Без поглощённых событий `log`-прогон завершается как обычно (`completed`, 0, с `diagnostic_run`); остановки с ошибкой (`error`, 5) и `firmware_stop` (6) считаются как в `stop`. В режиме `stop` отчёт и снимок побайтно прежние: новых полей нет.
- *Ограничения.* Один vCPU (`boot-firmware` единого цикла и так работает с одним): база числа инструкций — одна на шину, её задаёт только цикл платы единого прогона прошивки; в других циклах (`linux_direct`, параллельный режим) журнал через CLI не включается. CPL — 0 или 3 (по входу набора: RPL селектора CS равен 3 или нет). Индекс устройства — номер в таблице шины платы (порядок — `firmware_board.rs`, сборка шины), имени устройства в отчёте нет; устройство определяют по `region_base` и адресу.
- *Проверено.* `cargo test -p od-machine --lib device_error` — журнал (группировка, первое и последнее, пределы событий и групп, `ClockOverflow`), шина (запись отброшена, чтение — все единицы, порт без устройства и `CrossesRegion`, MMIO-запись без `mmio_written`, `ClockOverflow` портом и MMIO и занятая таблица не поглощаются, без журнала и без контекста инструкции ошибка и текст `backend_error` прежние, запись после поглощённого чтения той же инструкции не доходит до устройства, а в следующей инструкции доходит), единый цикл Windows на ROM (`s7_32_the_device_error_log_*`: LAPIC `0x3F0` запись и чтение, порт без устройства, dword в байтовый регистр COM1; общий шаг и turbo дают один отчёт, turbo достигает устройства на 2 обращения больше; без журнала остановка на первой записи с прежним текстом; предел останавливает на следующем отказе — PIO и MMIO, с turbo и без; на госте Linux единого цикла (у гостя Windows склеек нет: таймер ведёт clock owner) после склеек квантов turbo на тиках `RDTSC` число инструкций группы равно числу, на котором останавливается прогон без журнала — инъекция «без обновления базы на склейке» ловится: 3 вместо 98), `s7_32_a_lapic_read_modify_write_after_an_absorbed_read_does_not_write_the_device` (`add dword [lapic+0x3F0], 1` и `or dword [lapic+0xB0], 0`: чтения поглощены, записи — `SuppressedAfterAbsorbedRead`, к LAPIC дошли только 2 чтения; с turbo и без; инъекция «без подавления» ловится) и `linux_direct::…::the_device_error_log_records_a_refused_cpl3_access_with_cpl_3` (отказ входа CPL3 записан с CPL 3). CLI: `cargo test -p od-runner --test firmware_boot_cli device_errors` (`stop` = по умолчанию, отчёт тот же; поля `log`-прогона, статус `completed_with_absorbed_device_errors` и код 7, `log` без событий — `completed` и 0; `log:1` и снимок; пометка сохраняется при отказе `--framebuffer-out` и `--nvram-out` после загрузки; 9 отказов валидации) и `cargo test -p od-runner --bin od-runner a_run_error_of_a_device_errors_log_run` (пометка в `run_error`). Приёмочные наборы (`tests/system/firmware_*.py`, `tools/build/firmware_*.py`) опцию не передают.

## 16. Журнал фаз и дампы экрана (S8-11)

Флаги `od-runner boot-firmware` (любая загрузка, не только `--fv-app gop`): `--phase-log <file>` — журнал фаз в формате JSON Lines (по соглашению `phases.jsonl` в каталоге прогона); `--framebuffer-every <секунды виртуального времени>` (положительное, допускается дробное, например `0.5`) вместе с `--framebuffer-dir <dir>` — периодические дампы; `--framebuffer-max-files <n>` (по умолчанию 2000) и `--framebuffer-max-bytes <n>` (по умолчанию 4 ГиБ) — пределы. Флаги дампов задаются только парой; с `--nvram-reboot-out` и `--sample-rip` не сочетаются. Каталог `--framebuffer-dir` создаётся при отсутствии и обязан быть пустым (дампы двух прогонов не смешиваются). В отчёт runner добавляется `journal` (число событий, число файлов и байт, `skipped_unchanged`, `skipped_by_limit`, ошибки). Каталог дампов и журнал в Git не кладут.

**Когда смотрят на машину.** Между квантами, из потока владельца машины, через общие ссылки: хук `run_boot_with_quantum_hook` читает расшифровку COM1, часы и кадр (`read_display_frame_into`, `DisplayHandle::read_frame_into` этапа 10) и ничего не пишет в машину (хук получает `&self`, а не `&mut self`; журнал вызывает только читающие методы `diagnostic_*`/`read_*`, но тип не запрещает `&self`-методы, меняющие состояние дисплея, — это соглашение, не гарантия типа); кадр не читается из другого потока во время кванта. Кванты хук **не** режет: он видит границы, которые создают ввод-вывод гостя и бюджет, поэтому прогон с хуком исполняется так же, как без него. Проверено только тестом `quantum_hook_sees_each_boundary_and_leaves_the_run_unchanged` (`od-machine`), где хук не делает ввода-вывода и `FirmwareRunReport` с хуком равен отчёту без него; хук журнала (запись файлов, чтение кадра) этим тестом не охвачен. Отдельно CLI-тест `the_report_with_the_journal_equals_the_report_without_it_except_the_journal_field` (`--test firmware_boot_cli`, один синтетический гость с двумя кадрами, не Windows) сравнивает отчёт `boot-firmware` с `--phase-log`/`--framebuffer-*` и без них: равны, кроме полей `journal` и пути COM1. Следствие: `--framebuffer-every` означает «не чаще чем раз в N виртуальных секунд», а не гарантированный период: кадр смотрят только на границах квантов, и длинный квант (гость долго исполняет код без ввода-вывода) даёт редкие дампы; кроме того, границы квантов в `boot-firmware` создают только запись в COM1, doorbell NVMe, чтение таймера ACPI PM и бюджет (`rdtsc_tick` и PIT включаются только при `linux_profile`, runner `boot-firmware` его не включает, поэтому обращения к RDTSC и PIT кванты не режут), и гость, который долго исполняет код без этих обращений, не даст новых дампов до конца кванта; запрос остановки через ACPI PM — причина остановки прогона, а не граница кванта (в `boot-firmware` `set_host_stop` не вызывается, хост-запроса остановки нет); на остановке кадр снимается, только если он есть, новее записанного, пределы не превышены и ранее не было ошибки записи кадра (`FrameDumper::poll`). Существующий файл `--phase-log` при успешном старте прогона усекается (как и раньше); если запуск отказан (например, каталог `--framebuffer-dir` не пуст или не является каталогом), файл не трогается, а созданный этим вызовом удаляется.

**Дамп.** Файл `fb-<номер, 6 цифр>-<виртуальные мс>ms.raw`: заголовок 64 байта (little-endian: `ODFBRAW1`, размер заголовка = 64, ширина, высота, stride, формат (1 = BGRX8888), 0, поколение кадра, число смен режима, виртуальное время в нс, число исполненных инструкций), затем `stride × height` байт кадра как их отдаёт `read_frame_into`. Пишется только если изменилось поколение кадра (число успешных doorbell гостя) или режим; на каждой остановке (в том числе ошибочной) последний кадр записывается, если он новее записанного. Поколение растёт с каждым doorbell гостя, даже если пиксели не изменились: поэтому файл — «гость сообщил о новом кадре», а не «изменился хеш». Пока гость не включил режим и не позвонил в doorbell, дампов нет. Выводится только основной экран (второй экран платы не снимается). Переполнение пределов не прерывает прогон: пропуски считаются в `skipped_by_limit`.

**Журнал фаз.** Одна строка JSON на событие: `event`, `host_unix_ms` (часы host), `host_elapsed_ns` (с начала журнала), `instructions` и `quanta` (на границе кванта, где событие обнаружено; точность — один квант), `virtual_ns`, `restart`. События: `first_com1_write`; `com1_marker` (строка COM1 целиком по форме §3.1 — `nonce`, `phase`, `status`, `sha256`, `channel = com1`, `evidence = false`: COM1 не канал доказательства до принятия S4-24, §3.3) и `com1_marker_unrecognized` (строка, начатая с `OD8 `, но не совпавшая с формой); `stop` (`exit`, `stop_reason`). `restart` — **зарезервировано** для S8-23: перезапуск runner'ом не реализован, значение всегда 0. События `exit_boot_services` **нет**: трассы `ExitBootServices` у прошивки нет — она не пишет ничего в COM1 при этом вызове, а определять вызов по адресам или сигнатурам нельзя (§4.4 плана). Вариант: строка COM1 в `exit_boot_services` прошивки (владелец — этап 7) и одна строка в таблице событий runner'а; до этого события не будет.

**PNG.** `python3 -I tools/build/display_raw_to_png.py <dump> <out.png>` (только стандартная библиотека; существующий файл не перезаписывается); для файла без заголовка (`--framebuffer-out`) — `--raw-size 640x480`. До этого генератора PNG в репозитории не было (проверено поиском по `tools` и `tests`).
