## 2. Persistence domain и границы утверждения

- Испытуемая комбинация: macOS (версия и build фиксируются при запуске), APFS, выбранный носитель (модель, прошивка, контроллер), `F_FULLFSYNC` как barrier.
- Claim допустим только для этой комбинации. Mini (Linux) и симуляция/kill процесса — отдельные уровни и не заменяют это испытание.
- Отключение внешнего накопителя проверяет только его persistence domain, а не внутренний SSD Mac.

## 3. Подготовка стенда

1. Выделенный том создаётся только на выбранном одноразовом носителе; перед созданием пользователь подтверждает идентификатор устройства (`diskutil info`).
2. На томе — образ формата CoW v1 (`od-image-tool`), известное содержимое, seed для воспроизведения.
3. Журнал acknowledgement ведётся **вне испытуемого тома**: на внутреннем диске, в `work/stage9/<run-id>/ack.log`, построчно с `fsync` до вывода в протокол; каждая строка — номер операции, `DurableAck` получен или нет, hash данных.
4. Перед каждым прогоном фиксируются commit/config/artifact hashes и `run_checks.sh`-fingerprint.

## 4. Схема одного прогона

1. Запустить серию записей и коммитов, журнал ack пишется после каждого `DurableAck`.
2. На выбранной стадии (до барьера 1, между барьерами, после барьера 2, во время compaction/create) пользователь физически прерывает питание выбранного носителя (или всего Mac — только по отдельному разрешению на перезапуск рабочего Mac, которое здесь не выдано).
3. Восстановление: подключение носителя, `od-image-tool check`, затем `od-image-tool salvage` в **новый** target, если open не проходит.
4. Проверка: каждый подтверждённый ack операции присутствует в данных; неподтверждённая операция либо видна целиком, либо отсутствует; повреждённых данных нет; полный сырой вывод сохраняется.
5. Повторить на каждой стадии не менее N раз (N задаётся до прогона; предварительно предлагается N = 20 на стадию).

## 5. Критерии

- Passed: все подтверждённые ack сохранены, нет неописанных расхождений, все стадии выполнены N раз.
- Failed: любой подтверждённый ack потерян или данные повреждены без обнаружения.
- Not run / blocked: нет носителя, нет разрешения, нет физического доступа к питанию.

## 6. Что нужно от пользователя до запуска

1. Какой носитель одноразовый: подтвердить идентификатор (например `disk6`, если это ваш выделенный накопитель, или другой).
2. Как прерывать питание: физически выдернуть этот накопитель в заданные моменты (ручной режим с подсказками) или другой способ.
3. Одобрение этой процедуры и числа повторов N.

### 8.2. Что изменено в драйвере

Драйвер [`tools/power-loss/src/main.rs`](../../tools/power-loss/src/main.rs) получил три новые точки отключения. Их берёт обёртка `Cutter` над host-файлом: `CowFile::commit` делает ровно два durable flush, и обёртка считает их только внутри отрезаемого коммита. Библиотека хранилища не менялась.

| `--cut` | Где | Допустимый исход после восстановления |
|---|---|---|
| `after-b1` | барьер 1 вернулся (блоки, карта и копия корня N+1 сброшены), корень N+1 ещё не записан в слот | старое состояние N (корень N+1 не опубликован; копия в хвосте игнорируется, пока второй слот валиден); новое N+1 — дефект |
| `before-b2` | корень N+1 записан в слот, барьер 2 ещё не вызван | старое N или новое N+1. Порванная запись слота даёт roll-forward из копии (§9.6 STORAGE_FORMAT) |
| `after-b2` | барьер 2 вернулся, подтверждение ещё не в журнале | **только новое N+1.** Перед окном драйвер пишет в журнал `flushed commit=C generation=G`, и `verify` считает потерю G дефектом |

Окно теперь пишет `absent_after_ms`: задержку от точки отключения до первого опроса (раз в 50 мс), который не нашёл носитель. За это время накопитель мог сам сбросить кэш. Локальная проверка без отключения (2026-11-18, окно 1 с) показала: все три точки срабатывают на коммите 10, `verify ok=true`. Подложенная строка `flushed` с несохранённым поколением даёт `verify ok=false`. Журнал `after-b1` без строки подтверждения отрезанного коммита при durable-поколении этого коммита тоже даёт `verify ok=false`: `verify` разбирает строку `cutpoint` и для `block0`, `rootcopy` и `after-b1` не допускает публикации неподтверждённого отрезанного коммита. `--cut-commit` вне `1..=--commits` отклоняется, ошибка записи в журнал внутри окна останавливает `run`.

### 8.3. Носитель и границы утверждения

- **Вариант A (по умолчанию).** Тот же внешний USB-накопитель `disk6`/`disk7s1` (§0), отключение выниманием. Утверждение ограничено этим накопителем: проверяется, что после возврата `F_FULLFSYNC` подтверждённое поколение переживает отключение питания именно на нём.
- **Вариант B.** Целевая комбинация — внутренний SSD — требует отключения питания всего Mac. На это нужно **отдельное явное разрешение**, здесь оно не запрашивается. Без варианта B утверждение для целевой комбинации остаётся открытым.
- **Ограничение обоих вариантов.** Ручное отключение занимает от сотен миллисекунд до секунд. Накопитель, который ложно подтверждает сброс, но успевает дописать кэш за это время, тестом не обнаруживается. Прогоны с `absent_after_ms` больше 2000 отмечаются как слабое свидетельство.

### 8.4. Прогон

Для стадии S, повтора k и N. N задан владельцем 2026-11-18: **5 на стадию** (`after-b1`, `before-b2`, `after-b2`; 15 отключений), вариант A — USB-накопитель `ProductCode` 125.8 GB (после переподключения `disk16`, том `disk17s1` `/Volumes/128`, тот же носитель, что в §0).

```
B=target/release/od-power-loss
$B run --dir /Volumes/128/s39-S-k --ack work/stage9/s39-S-k/ack.log --seed 4242 \
       --commits 12 --cut S --cut-commit 10 --window-s 120
# по строке cutpoint в журнале сразу вынуть disk6; дождаться завершения run
# переподключить disk6
$B verify --image /Volumes/128/s39-S-k/cow.img --ack work/stage9/s39-S-k/ack.log --seed 4242
```

Сборка: `cargo build --release -p od-power-loss --offline`. Каждый прогон — в новой директории на носителе. Журнал лежит на внутреннем диске и не версионируется. Результат строки `verify` и `absent_after_ms` записываются в таблицу §7.

### 8.5. Критерии

- **Прогон засчитывается** только при `absent_seen=true` в строке `window_end` и ошибке следующей операции в журнале (как в §7): без отключения в окне коммит подтверждается и прогон ничего не доказывает.
- **Passed по стадии:** все N засчитанных прогонов дают `verify ok=true`. `verify` сам проверяет исходы §8.2: для `after-b1` (и `block0`, `rootcopy`) неподтверждённый отрезанный коммит не должен стать durable; для `after-b2` поколение из `flushed` обязано сохраниться; `before-b2` допускает оба исхода.
- **Failed:** потеряно поколение `flushed` или подтверждённое; после `after-b1` видно новое N+1; данные повреждены без обнаружения.
- Результат относится только к носителю выбранного варианта.
