## 2. Формат кадра и эталонов

- Raw-файл `width × height × 4` байта; порядок байтов пикселя в памяти `B, G, R, X`, `X` — зарезервированный байт (в эталонах `0x00`).
- Stride = width × 4, без паддинга в версии 1 (см. S10-02).
- Эталоны генерирует `tools/build/display_pattern.py` (`gradient`, `bars`, `checker`); формулы описаны в [README эталонов](../../tests/fixtures/guest/stage10/README.md). Чужие изображения, скриншоты ОС и большие файлы в Git не хранятся; размер одного эталона не больше 1 MiB.

## 3. Допуски

| Сценарий | Допуск | Причина |
|---|---|---|
| Синтетический узор, передача кадра VMHost → reader (уровень 2) | 0 | Байтовая копия без масштабирования; любое отличие — дефект |
| Показ в offscreen texture 1:1 (уровень 3) | 0 | Масштаб 1:1, без фильтрации; сравнение должно быть точным |
| Показ с масштабированием, `fit` (уровень 3, S10-11) | По значению 0 (канал B, G, R, X); по положению семпла допуск ±1 тексель только на точной границе текселя (полоса 0,01 текселя); поля — ровно `00 00 00 00` | Фильтрация nearest: каждый пиксель окна равен значению одного пикселя кадра без смешивания, поэтому отличие по значению недопустимо. Позиция семпла при нецелом масштабе может попасть точно на границу текселя (например 100/64: x = 12), где выбор соседа зависит от округления float у GPU; на этом Mac при тесте 100×100 и 200×50 такие пиксели выбирают нижнего соседа, при 32×24 — верхнего. Вне полосы выбор однозначен |
| Показ `pixel-exact` (уровень 3, S10-11) | 0 | Кадр копируется 1:1 в центр drawable без масштабирования; поля — фон. Если drawable меньше кадра, виден центральный фрагмент кадра (viewport ограничивается drawable, координаты текстуры сужаются), тоже побайтно; при нечётной положительной разности лишний пиксель идёт в правое/нижнее поле, при нечётной отрицательной (кадр больше drawable) срезается слева/сверху (floor-деление) |

Любой допуск, отличный от 0, записывается сюда вместе с причиной и сценарием до того, как им пользуются в проверке.

## 4. Инструменты

- `python3 tools/build/display_pattern.py --width W --height H --pattern {gradient,bars,checker} --seed S --output FILE` — пишет raw-файл и печатает SHA-256. Выход детерминирован.
- `python3 tests/system/display_compare.py EXPECTED ACTUAL --width W --height H [--tolerance N]` — код выхода 0 при совпадении в пределах допуска, 1 при отличиях (печатает число отличающихся пикселей и первые 10 координат), 2 при ошибке аргументов, допуска, размера или чтения файла.
- Сборка бинарников для уровней 2–3 (S11-05c; нормативна одна система, SwiftPM): `cargo build -p od-host --offline`, затем `cd apps && swift build`. Бинарники `apps/.build/debug/od-vmhost` и `apps/.build/debug/open-desktop-display-viewer` — значения по умолчанию в `tests/system/display_transport_smoke.py`, `display_viewer_dump_smoke.py`, `display_viewer_scaled_smoke.py`, `cursor_overlay_smoke.py`, `input_channel_smoke.py` (пути можно передать аргументами). Прежние команды `xcrun swiftc` и `target/od-vmhost-smoke` удалены.
- `python3 tests/system/display_end_to_end_smoke.py [--repeat N] [VIEWER [VMHOST]]` (S10-09) — одна команда для цепочки «гостевой probe → устройство → VMHost → разделяемая память → Metal → кадр»: просмотрщик в offscreen режиме запускает VMHost `--display-smoke probe`, скрипт сравнивает дамп `--dump-frame` с эталоном из манифеста S10-08 (`display_probe_bars_64x48_seed0.json`) побайтно, по SHA-256 и через `display_compare.py` с допуском 0, проверяет, что VMHost сообщил `HLT` после `expected_retired` инструкций, и без GPU проверяет отказ при исчерпании бюджета. Код выхода 0 — всё прошло; 1 — проверка не прошла; 3 — `BLOCKED`: просмотрщик сообщил `no Metal device`, цепочка до Metal **не проверена** и это не успех. Это тестовый probe, не ОС: уровень 3 для этого сценария подтверждён только для узора `bars` 64×48 в масштабе 1:1.
- `python3 tests/system/display_failure_smoke.py [--repeat N] [--only 1a,3a,...] [VIEWER [VMHOST]]` (S10-24) — сценарии отказов транспорта и процесса, раздел 6. Код выхода 0 — все прошли; 1 — проверка не прошла; 2 — нет бинарников; 3 — `BLOCKED`: просмотрщик сообщил `no Metal device`, сценарии с состоянием UI через просмотрщик **не проверены** (это не успех). Нужна **debug**-сборка VMHost (хук отказов, раздел 6.1). Узкие XCTest: `(cd apps && swift test --filter DisplayFailureXCTests)` (`apps/vmhost/Tests/DisplayFailureTests.swift`; сначала `cargo build -p od-host --offline`).
- `python3 -m unittest tools/build/test_display_pattern.py` — тесты генератора и сравнения (повторная генерация, зафиксированные хеши эталонов, детекция сдвига одного байта, допуск, ошибка размера).

## 5. Ограничения методики

- Генератор и формулы пока проверены только на эталонах 64×48. Полноразмерные проверки 1920×1080 и 2560×1600 выполняются в S10-09/S10-10.
- Проверка уровня 2 доказывает, что VMHost передал байты корректно, но не доказывает, что гостевой код записал правильный узор; это задача S10-08 (probe) с манифестом ожидаемого хеша.
- Масштабированный показ проверяется `tests/system/display_viewer_scaled_smoke.py` на кадре 64×48 (размеры окна 128×96, 100×100, 99×99, 200×50, 50×200, 32×24, pixel-exact с обрезкой 10×10, 63×47, 40×100, 200×30 и Retina: логический размер и `--backing-scale 2`, физический размер drawable в отчёте). Отчёт показывает **оба** размера: логический (точки) и физический (пиксели) = округление(логический × scale). Реальный экран Retina смотрелся только как число (`window geometry`), не глазами.
- Уровень 3 опирается на macOS Metal; результаты зависят от версии macOS и GPU. Версия и модель записываются в отчёт.

## 6. Отказы транспорта и процесса (S10-24)

Статус: реализовано и проверено локально (macOS 26.7.1, Apple Silicon, debug-сборка); ревью не проходило. Контракт — [FRAME_TRANSPORT_V1.md](../../protocols/control/FRAME_TRANSPORT_V1.md) (раздел 5.2 seqlock, 6.3 режимы, 6.4 очередь, 7.2 состояния, 8 совместимость и отказы); контракт не менялся.

### 6.1. Как вызываются отказы

- **Реальный VMHost + хук.** `od-vmhost --display-smoke pattern --display-test-fault NAME` (`apps/vmhost/Sources/DisplayFaultHook.swift`). Хук **есть только в debug-сборке** (`#if DEBUG`): релизный `od-vmhost` отвечает на флаг ошибкой использования (код 1, проверено сборкой `swift build -c release`). Хук не меняет формат и алгоритм публикации: каждый кадр идёт через настоящий `FrameTransportWriter.publishFrame`, подменяются только источник пикселей и тайминг. Имена: `mid-write:1`, `mid-write:2` (запись первой/второй публикации останавливается на половине пикселей слота навсегда; слот имеет `generation = 0`, `FRAME` не отправлен), `flood:N` (после первого кадра N синтетических кадров пачками по 500 за такт, каждые 100 кадров — новый режим; пиксель кадра поколения `g` равен `[g, g>>8, g>>16, 0]`, поэтому смесь двух кадров обнаруживается), `mode-change` (через 400 мс после первого кадра `MODE` с половинным размером без кадра, попытка опубликовать кадр заменённого режима, через 800 мс — первый кадр нового режима). Допустимо только для профиля `pattern`, одного экрана, без `--display-hold-until-claim`.
- **Fake VMHost** (`display_failure_smoke.py --fake-vmhost KIND`) для чужих версий: VMHost, который говорит `VERSION 9`, `ANNOUNCE` версии 2, память с заголовком версии 2 или `pixel_format = 9`. Это тестовый двойник, а не хук в продукте.
- **Состояние UI** берётся из настоящего читателя: `open-desktop-display-viewer --vmhost PATH --watch-ms N` (offscreen, без окна и дампа) печатает строку `viewer-state: …` на каждое изменение состояния экрана 0 и `viewer-end: …` в конце. Имена состояний — раздел 7.2 протокола. Слова окна для каждого состояния — `MachineWindowModel.overlay` (проверены в `apps/macos/Tests/MachineWindowTests.swift`): `NO_SIGNAL` — «Нет сигнала», `MODE_CHANGING` — «Смена режима экрана» (в просмотрщике «Changing mode»), `DISCONNECTED` — «Нет сигнала: VMHost отключился» и причина, `INCOMPATIBLE` — «Несовместимая версия» и причина. Кадр рисуется только в `SHOWING`.
- **Счётчики очереди уведомлений.** `NotificationQueue` считает замененные до отправки уведомления (`superseded_frames`, `superseded_modes`, `superseded_cursors`) и наибольший объём очереди (`high_water_bytes`); `--display-smoke` печатает их в stderr при завершении: `od-vmhost-smoke: notification queue: …`. Счётчики не входят в протокол.

### 6.3. Что здесь не доказано

- Слова состояний проверены моделью окна (`MachineWindowModel`, тесты без окна) и строками просмотрщика, **не глазами** на реальном окне.
- Убийство VMHost делается сигналом SIGKILL в заданной хуком точке (внутри копии пикселей, `generation = 0`). Случайный момент убийства (произвольная инструкция записи) не перебирается; безопасность такого момента следует из seqlock (раздел 5.2) и проверяется модульным тестом переписанного слота.
- «Читатель подключился позже writer-а» понимается как «читатель принял память и читает уведомления позже»: VMHost публикует кадры только после `HELLO` и `ANNOUNCE` (раздел 6.1), поэтому кадра до подключения не бывает (2a). Окно, которое вообще не открывалось, проверяет только состояние `CONNECTING`/`NO_SIGNAL`.
- Перезапуск VMHost после отказа не проверяется (ISSUE-669). Исключение `SIGBUS` (8.3) снято наблюдением на macOS 26.7.1, не гарантией и не на минимальной поддерживаемой версии (ISSUE-668).
- Сценарии проверены на debug-сборке; хук в релизной сборке отсутствует, поэтому сценарии 1–3 и 5 релизным бинарником не воспроизводятся.
