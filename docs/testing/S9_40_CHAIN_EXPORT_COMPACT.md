# S9-40: воспроизводимый бенчмарк хранилища — цепочки, export, compaction и повтор записи

Статус: измерение на одной машине 2026-11-18. Дополняет [S9_40_COMMIT_LATENCY.md](S9_40_COMMIT_LATENCY.md) и [S9_40_THROUGHPUT.md](S9_40_THROUGHPUT.md). В отличие от них код бенчмарка лежит в репозитории. Документ не делает выводов о долговечности при потере питания.

## Что измерялось

Код: [`tools/bench/src/bin/s9_40_storage.rs`](../../tools/bench/src/bin/s9_40_storage.rs). Всё идёт через production host backend `HostFileStorage` (эксклюзивный `flock`, `F_FULLFSYNC`) и библиотеку `od-storage`. Ни один барьер, checksum или проверка не отключены.

- **`write`.** RAW in place против прототипа CoW (`CowFile`, блок 512 Б) на диске 16 MiB, заполненном заранее (заполнение в замер не входит). Записи по 4 КиБ, случайные, без повторов смещений. Один барьер (RAW) или один commit (CoW, 2 барьера) на группу из G операций:
  - G = 32, 16 MiB данных;
  - G = 1, 1 MiB данных.

  WA — байты, принятые `write_at` (обёртка `Counting`), делённые на байты пользователя. После прогона файл открывается заново и весь диск сверяется с моделью. Для CoW это полный `CowFile::open` с проверкой CRC, его время записано как `open_ms`.
- **`chain`.** Базовый `SnapFile` 2 MiB (`MAX_DISK_BLOCKS` = 4096 блоков) и дочерние слои до глубины d. Две раскладки:
  - **`chain_d`, d ∈ {0, 1, 2, 4, 8}, с префиксами.** Файл слоя выделяет все блоки ниже самой старшей записи, поэтому слой k пишет префикс из d−k+1 восьмушек, и восьмушка r читается со слоя d−r. Объём данных цепочки растёт с глубиной: 2 + d(d+1)/8 MiB, то есть 2 / 2.25 / 2.75 / 4.5 / 11 MiB. При d = 8 база не обслуживает ни одного блока.
  - **`chain_empty_d`, d ∈ {1, 2, 4, 8}, пустые дети.** Дочерние слои без записей, только снимок. Объём равен одной базе, и каждый блок читается из базы через все d уровней. Эта раскладка отделяет глубину от объёма и даёт худший случай поиска уровня при чтении.

  Родители открываются через `ParentLease`, как в офлайн-CLI. Время `SnapFile::open` верхнего слоя включает проверку всей цепочки (S9-16). Затем весь диск читается одним `read_at` и сверяется с моделью.
- **`export`.** `export_raw` верхнего слоя `chain_d` при d = 0 и d = 8 в новый RAW. В измеренное время входят:
  - открытие и проверка цепочки;
  - запись;
  - durable flush;
  - обратное чтение и сравнение со вторым чтением источника.

  Поэтому `effective_mb_s` — не пропускная способность канала. Результат сверяется с моделью.
- **`compact`.** База 2 MiB, 8 полных перезаписей, после каждой снимок. 7 старых снимков удаляются, затем выполняется `compact_to` в заранее созданный пустой файл (создание в замер не входит). Измеряются время и размер файла до и после. Голова и оставшийся снимок сверяются с моделью, проверяется, что в новом файле только оставшийся снимок.
- **Память.** RSS процесса (`ps -o rss=`) в конце каждого прогона.

## Методика

Сначала один неучитываемый прогрев (run 0, уменьшенный диск для `write`), затем 5 прогонов. Внутри прогона сценарии идут в фиксированном порядке:

1. `write` G=32;
2. `write` G=1;
3. `chain` (export выполняется внутри);
4. `compact`.

Файлы создаются заново (`create_new_exclusive`) и удаляются после сценария. Cold — run 1, сводка по 5 прогонам: p50, mean, sd между прогонами (n−1), min..max. Кэш ОС не сбрасывался, поэтому чтение идёт из page cache. Первая строка вывода (`# env`) печатается самим бинарником: дата, ОС, модель, CPU, память, питание, `df` каталога, HEAD, профиль сборки.

Повторить:

```
cargo build -p od-bench --release --offline --bin s9_40_storage
mkdir <empty-dir-on-the-measured-volume>
target/release/s9_40_storage <empty-dir> 5 > out.csv
```

Сырые данные этого прогона: [S9_40_storage_2026-11-18.csv](../reports/data/stage9/S9_40_storage_2026-11-18.csv), сводка в конце файла.

- **Open определяется объёмом проверяемых данных цепочки, а не числом уровней.** При постоянном объёме (пустые дети) время open на глубине 1…8 одинаково, около 20 мс. Наличие хотя бы одного предка добавляет к одиночной базе (9 мс) около 11 мс постоянной цены. При растущем объёме (префиксы) время ложится на прямую примерно 10.8 мс × объём − 3.4 мс: 26.3 и 45.2 мс по прямой при измеренных 25.7 и 43.9 мс. Подгонка по двум крайним точкам d = 1 и d = 8 — расчёт по этим данным, не модель реализации.
- **Чтение.** При любой глубине ≥ 1 полное чтение около 136–152 MB/s против 266 MB/s у одиночной базы. От числа уровней оно не зависит: худший случай, когда всё читается из базы через 8 уровней, даёт 142 MB/s. Перебор уровней в памяти (`chain_read`) на скорость заметно не влияет. Падение примерно вдвое, по-видимому, связано с путём чтения блоков предков; профилирования не было, это гипотеза.
- **Холодный прогон и выброс run 5.** Run 1 открывает заметно медленнее: база 13.9 мс против 9.0 мс в run 2…4. Наибольший вклад в sd первых строк даёт run 5: open базы 25.1 мс, d = 1 — 51.4 мс, чтение 171 и 110 MB/s. p50 от этих значений не зависит.

## Решение по производительности (S9-40)

Данные не дают основания менять структуры формата CoW v1 или лимиты прототипа. Решение — оставить их без изменений:

- **`MAX_CHAIN_DEPTH = 8` сохраняется,** но это не ограничитель времени open. Измерено:
  - при постоянном объёме глубина 1…8 стоит одинаково (около 20 мс);
  - open растёт с объёмом проверяемых данных цепочки, около 11 мс/MiB на этом томе.

  Гипотеза: на реальных размерах гостевого диска главным пределом будет именно объём, проверяемый при open (S9-16 проверяет каждого предка). Лимит глубины его не ограничивает. Следующий эксперимент — open цепочки на реальном размере диска после появления гостевого storage device (S9-13). Кэш проверенных предков или ленивая проверка без измеренной цели не вводятся: это ослабило бы S9-16 без подтверждённой пользы.
- **Полная перезапись карты блоков в commit CoW остаётся.** Она главный источник WA (4 при G=32, 97 при G=1 на 16 MiB). По расчёту из формата WA растёт линейно с размером карты; на других размерах диска это не измерялось. Это известный предел прототипа, а не дефект. Инкрементальная карта — кандидат на следующий эксперимент, если целевой сценарий гостевого диска покажет, что commit-latency или WA выходят за требования. Требований в цифрах пока нет (S9-13).
- **Ускорение за счёт отключения барьеров, checksum или проверок не рассматривалось** (план S9-40, «Проверить»).

## Ограничения

- Одна машина, одна сессия. Параллельно шли сборки и прогоны других сессий, фоновые процессы не отключались. Видимые следствия:
  - большие sd у холодного run 1 и выброс run 5 в `chain_d` d = 0…1 (open 25.1 и 51.4 мс);
  - выброс CoW G=32 в run 5 (10.15 MB/s);
  - выброс `compact` в run 4 (376.9 мс);
  - разброс open у CoW G=1 (sd 14.8 мс).

  Предыдущий прогон того же кода без сценария пустых детей (не опубликован отдельно) давал те же p50 в пределах 5–10%, а `compact` там рос от прогона к прогону: 245.9 → 302.5 мс. Тренд и выбросы не исследовались.
- Чтение идёт из page cache, кэш накопителя не контролируется. Барьеры `F_FULLFSYNC` выполнялись, но долговечность здесь не проверяется (S9-39).
- Диски малые: 16 MiB у `CowFile`, 2 MiB у снимочного слоя (`MAX_DISK_BLOCKS`). Масштаб на реальных размерах гостевого диска не измерен.
- Не измерено и заблокировано: пауза и длительность checkpoint, restore (S9-29…S9-31); фрагментация на длительной нагрузке; recovery после реального сбоя (в `S9_40_THROUGHPUT.md` есть только roll-forward).
- WA считается на уровне вызовов backend, а не записи на носитель.
