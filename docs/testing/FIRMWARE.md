# Методика проверки прошивки

S7-01 определяет проверку формата образа ROM и PE32+ probe и host-side тесты чистой логики. Требования к toolchain приведены в [README прошивки](../../firmware/uefi/README.md#команды). Результаты выполнения кода в машине фиксируются в [отчёте этапа 7](../reports/STAGE_7_REPORT.md).

Успешный `cargo check --workspace` прошивку **не** проверяет: она не член корневого workspace. Успешная сборка образа не доказывает работу прошивки.

## Одна команда

Запуск из корня проекта с установленными [инструментами сборки прошивки](../../firmware/uefi/README.md#команды).

**Все проверки прошивки (S7-40).**

```sh
python3 tools/build/firmware_check_all.py --table-out work/stage7/firmware-check-all.txt
```

Команда выполняет по порядку: (а) `cargo build --release -p od-runner --offline`; (б) два ROM — базовый и с `--with-test-apps` (для `firmware_tpm_smoke.py`, которому нужны `--runner`, `--rom` и `--app` = `tpm.efi` из каталога сборки); (в) все `tests/system/firmware_*_smoke.py`: `boot`, `esp_boot`, `nvram`, `failure`, `install_media`, `pkcs7` (`--runner`, `--rom`), `secure_boot` (`--work`), `tpm`, `reset` (5 циклов; `--reset-cycles` меняет число) — скрипты, у которых аргументы необязательны, сами собирают недостающее; ROM с `--with-reboot-app` собирает только `firmware_reset_smoke.py` ([ISSUE-624](../KNOWN_ISSUES.md#issue-624)); (г) `cargo test --manifest-path firmware/uefi/Cargo.toml --offline`; (д) два ignored-теста `od-machine` из разделов [«Отказ TPM при Startup»](#отказ-tpm-при-startup) и [«Проверка PCR7 и отказов Secure Boot»](#проверка-pcr7-и-отказов-secure-boot) с переменными `OD_TPM_FAILURE_ROM`, `OD_TPM_FAILURE_ESP`, `OD_SB_PCR7_ROM`, `OD_SB_PCR7_FIXTURES` (ROM и fixtures PCR7 берутся из `--work` прогона `secure_boot`); (е) `python3 -m unittest` для `tools/build/test_build_firmware.py`, `test_s7_31a_rom_inventory.py`, `test_firmware_check_all.py` и `tests/system/test_firmware_*.py`.

Шаг, упавший или пропущенный из-за упавшего предварительного шага, не останавливает остальные. В конце печатается таблица «шаг — код выхода — секунды — ключевая строка», команда возвращает `1` при любом провале (в том числе при `--skip`). Журналы каждого шага — в `<work>/logs/` (`--work` принимает пустой каталог, по умолчанию создаётся временный). `--list` печатает шаги, `--only <glob>` запускает выбранные вместе с обязательными предшественниками. Полный прогон занимает порядка часа; 50 циклов сброса и воспроизводимые измерения (`firmware_boot_bench.py`) в него не входят. Запускать на чистом checkout: `git worktree add <каталог вне репозитория> <коммит>`. Результат последнего прогона на чистом checkout — красный из-за [ISSUE-628](../KNOWN_ISSUES.md#issue-628); таблица — в [отчёте этапа 7](../reports/STAGE_7_REPORT.md#s7-40--единая-проверка-прошивки) и в `docs/reports/data/stage7/firmware-check-all-2026-11-21.txt`.

Прежние отдельные команды остаются в силе:

```sh
python3 tests/system/firmware_boot_smoke.py &&
python3 tests/system/firmware_esp_boot_smoke.py &&
python3 tests/system/firmware_nvram_smoke.py &&
python3 tests/system/firmware_failure_smoke.py
```

Эта последовательность проверяет G1–G3 и входит в команду выше. Каждый скрипт собирает необходимые
ROM и тестовые EFI-приложения и завершает запуск кодом ошибки при расхождении.
Штатный запрос `ResetSystem`, который остановил плату аппаратно, возвращает
`exit=stopped` и `stop_reason=Reset` или `Shutdown`. Для `--fv-app rt`
успех требует `Shutdown`. Возобновление работы после `Reset` — сброс платы
в процессе, [раздел S7-26a](#сброс-и-перезагрузка-s7-26a): `firmware_reset_smoke.py`
в эту последовательность не входит (5 циклов занимают около 15 минут).

## Измерения пути загрузки S7-27

На macOS запустить из корня репозитория с тем же toolchain, что для системных
проверок прошивки.

```sh
python3 tools/bench/firmware_boot_bench.py \
  --work-dir work/stage7/firmware-bench \
  --out work/stage7/firmware-bench/results.json
```

Скрипт собирает release-интерпретатор, ROM и одно тестовое EFI-приложение.
На каждый повтор он запускает новую плату с одним vCPU, 128 МиБ RAM, свежим
NVRAM, TPM CRB с обоими банками PCR и фиксированным NVMe. Приложение упаковано
в FV под именем `hello` и в FAT32 ESP как `EFI/BOOT/BOOTX64.EFI`.
Для каждого пути один запуск определяет адрес загруженного образа и точки
наблюдения. Следующий запуск отбрасывается как прогрев, затем нужны десять
валидных повторов. Адрес входа сверяется с `AddressOfEntryPoint` PE.
Для ESP тест требует маркер завершения приложения и штатный останов
`0x21/1` после его возврата в менеджер загрузки. Для FV требуется
завершение приложения с `EFI_SUCCESS` и штатный останов `0x21/0`.

`--sample-rip` в `od-runner boot-firmware` принимает до 64 адресов в
порядке наблюдения. Повторный адрес соответствует отдельному посещению.
Отметки берутся перед выборкой гостевой инструкции, с числом
завершённых квантов и выполненных инструкций на тот момент. Для пути
handoff → вход отсчёт начинается на первой инструкции ROM, а заканчивается
перед первой инструкцией приложения. В режиме FV скрипт также измеряет пары
отметок перед `CALL` и по адресу возврата для пустой функции и трёх
сервисов. Вывод COM1 и проверка результатов находятся за пределами этих
интервалов.

Приложение читает одним вызовом `ReadBlocks` 64 МиБ через Block I/O сырого
NVMe namespace. Первые 1 МиБ этого диапазона содержат PE32+ с
инициализированной секцией `.rdata`. `LoadImage` загружает этот буфер,
после чего приложение проверяет содержимое отображённой секции. Вызов
`HashLogExtendEvent` без флагов хеширует тот же 1 МиБ, записывает событие
и расширяет PCR 8. Приложение проверяет SHA-256 события и значение PCR
через `TPM2_PCR_Read`.

В JSON записываются нативные наносекунды монотонных часов, число выполненных
гостевых инструкций и завершённых квантов, сырые повторы, среднее, p50,
p95 по ближайшему рангу, минимум, максимум и размах. Пустая функция
показывает накладные расходы короткого интервала, её время из измерений
не вычитается. Бюджет задаётся на всю загрузку и уменьшается после каждого
кванта. События устройств могут завершить квант раньше. NVMe обслуживается
из памяти процесса, чтение файла образа на host происходит до измерений.
Параметры и результаты серии приведены в [отчёте этапа 7](../reports/STAGE_7_REPORT.md#s7-27--измерения-пути-загрузки).

## Базовая загрузка

```sh
python3 tests/system/firmware_boot_smoke.py
```

Скрипт собирает release-версию `od-runner`, базовый ROM и ROM с тестовыми приложениями. На плате с 128 МиБ RAM он проверяет базовую диагностику и запускает `hello`, `ebs`, `vars`, `rt`, `acpi`, `gop` и `blk` столько раз, сколько задаёт манифест эталонов.

| Режим | Проверка гостя и результата runner |
|---|---|
| Без `--fv-app` | Базовый ROM завершает диагностику ядра и Boot Services по `HLT`, процесс возвращает `0`. |
| `--fv-app hello` | `LoadImage` читает PE32+ из FV по пути устройства. Приложение пишет `OD-UEFI hello 0.1.0` через `ConOut` и возвращает `EFI_SUCCESS`. Прошивка печатает статус образа и останавливается по `HLT` с кодом `0x21`, `detail = 0`. Процесс возвращает `6`. |
| `--fv-app ebs` | Приложение находит framebuffer через GOP, проверяет его тип и атрибуты в UEFI memory map и записывает пиксель. После `ExitBootServices` оно читает пиксель по тому же физическому адресу, пишет `!` напрямую в COM1 при совпадении и выполняет `HLT`. Процесс возвращает `0`. |
| `--fv-app vars` | Приложение читает встроенные переменные из Runtime Services и проверяет защиту `SetupMode`, создание, чтение, малый буфер, добавление, перечисление, удаление и возврат занятого места. Прошивка печатает `EFI_SUCCESS` и останавливается с `0x21`, `detail = 0`. Процесс возвращает `6`. |
| `--fv-app rt` | Приложение выходит из Boot Services, включает неидентичное отображение Runtime Services и завершает машину через ACPI PM1a с `Shutdown`. Процесс возвращает `0`. |
| `--fv-app acpi` | Приложение обходит EFI configuration tables, проверяет ACPI и SMBIOS и возвращает `EFI_SUCCESS`. Процесс возвращает `6` после останова `0x21`. Скрипт сверяет handoff с бинарным эталоном и побайтно сравнивает 64 КиБ ACPI из гостя с freestanding blob. |
| `--fv-app gop` | Приложение перечисляет режимы, проверяет ошибки, смену режима, доставку события таймера через вызовы GOP и четыре операции `Blt`. Затем оно рисует полосы в 640×480. Runner сохраняет кадр через `DisplayHandle::read_frame_into`. Скрипт сверяет метаданные кадра и сравнивает его с `display_pattern.py --pattern bars --seed 0` при `--tolerance 0`. Процесс возвращает `6` после останова `0x21`. |
| `--fv-app blk` | Runner подключает GPT-образ из `make_test_disk.py` через `--nvme-image`. Гость читает первые секторы разделов, печатает их имена, проверяет поиск ESP по GUID, запись на границе секторов, `FlushBlocks`, `Reset` и доставку таймера во время `ReadBlocks`. Отдельные образы проверяют восстановление по резервной GPT и доступ к пространству имён при повреждении обеих копий. Процесс возвращает `6` после останова `0x21`. |

Для каждого прогона скрипт сверяет COM1 побайтово, включая CRLF, управляющие последовательности и последний байт `!`. При расхождении он печатает diff с видимыми управляющими байтами. [Манифест](../../tests/fixtures/firmware/manifest.json) задаёт ожидаемые остановы, SHA-256 эталонов и пределы инструкций и квантов. Скрипт сверяет хеш ROM из отчёта runner с хешем собранного образа и печатает время каждого запуска. Отдельная проверка запрашивает `ebs` из базового ROM и ожидает останов `0x35` с `EFI_NOT_FOUND`.

В базовом ROM обработчик `ExitBootServices` записывает переменную с `NV` через живую Runtime Services table. После завершения EBS диагностика читает снимок в сохранённой памяти и печатает `OD-FW S7-09 variable image retained` только при совпадении записи. [Профиль переменных](../specs/UEFI_PROFILE.md#переменные).

## Сброс и перезагрузка S7-26a

Сброс платы — операция внутри процесса ([FIRMWARE_BOOT.md, раздел 12.1](../specs/FIRMWARE_BOOT.md#121-сброс-платы-внутри-процесса-s7-26a)): `ResetSystem` пишет в reset register, `run_boot` останавливается с `Reset`, владелец платы вызывает `LoadedFirmwareBoard::platform_reset` и снова `run_boot`. Ничего не создаётся заново; `--nvram-reboot-out` остаётся отдельным сценарием (плата пересоздаётся из снимка NVRAM, это не сброс).

```sh
# Единичные проверки (машина, CRB, TPM, runner)
cargo test -p od-machine --offline --lib -- firmware_board::tests::platform_reset firmware_board::tests::cold_reset firmware_board::tests::reboot_app tpm_crb::tests::platform_reset acpi_pm::
cargo test -p od-tpm --offline --lib -- init_at
cargo test -p od-runner --offline --bin od-runner -- firmware_boot

# Цикл в процессе: 5 циклов (около 13 минут), затем 50 (около 2,2 часа: 7 952 с в прогоне ниже)
python3 tests/system/firmware_reset_smoke.py
python3 tests/system/firmware_reset_smoke.py --cycles 50 --rss-limit-kib 4096

# Прямой запуск runner (JSON в stdout, COM1 всех циклов в --com1-out, ход по циклам в stderr)
target/release/od-runner boot-firmware --image <rom-with-apps.bin> --fv-app reboot \
  --reboot-cycles 50 [--reboot-kind cold|warm] --com1-out <file> --budget 700000000
```

`firmware_reset_smoke.py` собирает ROM с тестовыми приложениями и `--with-reboot-app` и runner, запускает приложение `reboot` (читает и увеличивает `ODBootCount` в NVRAM, печатает его и PCR0 на COM1, вызывает `ResetSystem(Cold)`) и проверяет: каждый цикл заканчивается остановкой `Reset`; виртуальное время растёт сквозь сброс; `BootCount` равен номеру цикла; PCR0 одинаков во всех циклах и не равен начальному значению; COM1 побайтно одинаков во всех циклах, кроме строки `BootCount`; память runner в начале и в конце отличается не больше порога. Цена цикла определяется гостевым хешированием ROM (4 MiB, банки SHA-256 и SHA-384) для PCR0: около 3,66·10⁸ инструкций, 160–165 с в release на M3 Max; бюджет `--budget` действует на каждый цикл.

### Измерения 2026-11-21

Условия: Apple M3 Max, macOS 26.7.1 (25G241), `cargo 1.99.0` / `rustc 1.99.0`, `cargo build --release` без LTO и без `target-cpu`; ROM с тестовыми приложениями, в том числе `reboot`, SHA-256 `5df0b465d5a527e9a43a13d69ed8b78eada1b9591d3fb82fb7aaf6110ae06643` во всех прогонах таблицы. Образ, собранный на коммите `5aa1791` командой `build_firmware.py --with-test-apps --with-reboot-app`, имеет тот же SHA-256 (напечатан сборщиком при прогоне `firmware_reset_smoke.py`): `pack_fv` сортирует файлы по имени, поэтому переход от `reboot` в `TEST_APPS` к флагу не меняет архив; runner запускался без `nice` (это проверка корректности и памяти, не решение по скорости). Память — из отчёта runner: `rss_kib_*` (`ps -o rss`) и `footprint_kib_*` (`footprint -p`, включает сжатые страницы).

**Что показали измерения.**

- Первый цикл (пустой NVRAM) выполняет на 33 028 инструкций меньше следующих; причина не исследована. Дальше число инструкций постоянно и меняется только от длины десятичного счётчика (+79 инструкций с цикла 10).
- PCR0 одинаков в каждом цикле и в Cold, и в Warm, и не равен начальному значению: TPM начинает каждый цикл после `_TPM_Init`, прошивка заново выполняет `TPM2_Startup(CLEAR)` и измерения. `BootCount` растёт ровно на 1 за цикл: закоммиченный банк NVRAM пережил все сбросы.
- COM1 побайтно одинаков во всех циклах, кроме строки `OD-UEFI reboot BootCount=N` (проверяет скрипт; в сводке по циклам все 50 SHA-256 COM1 с замаскированным счётчиком совпадают); в Cold и в Warm PCR0 один и тот же.
- **RSS по `ps` на macOS шумит из-за сжатия памяти**: RSS процесса падает с 188 МБ до 149 МБ, когда система сжимает неиспользуемые страницы (пять циклов Cold: 184 224 → 149 904), и возвращается. Поэтому порог проверяется по `footprint` (physical footprint включает сжатые страницы); без утилиты `footprint` скрипт сравнивает RSS. **Известное ограничение:** RSS за те же 50 циклов вырос на 5 136 KiB (184 208 → 189 344), то есть на платформе без `footprint` 50-цикловый прогон с порогом 4096 KiB не пройдёт; порог под RSS не менялся, для такой платформы нужен отдельный замер и отдельное значение.
- Footprint растёт в основном в первых циклах (после цикла 1 — 184 976 KiB, в конце — 185 712 KiB: +736 KiB за 49 циклов, последние 15 циклов — без изменений), то есть это прогрев аллокатора, а не рост на цикл. Временная проба (в репозиторий не вошла) выполнила 600 сбросов платы на простом образе (Cold и Warm по очереди, TPM, NVRAM, NVMe): footprint вырос на 1 104 KiB за первые сто сбросов и на 16 KiB за остальные пятьсот.
- **Порог `--rss-limit-kib` = 4096 KiB** (по умолчанию в скрипте) — это запас над измеренным, а не округление: footprint вырос на 3 024 KiB за 50 циклов и на 2 528–2 656 KiB за 5 (четыре прогона по 5 циклов, у Warm 1 616 KiB). ## Раскладка образа и CRC таблиц Boot Services и Runtime Services

Строка `OD-FW S7-05 table CRC ST=… BS=… RT=…` печатает CRC трёх таблиц до сервисных вызовов. Таблицы Boot Services и Runtime Services состоят из указателей на функции ядра, поэтому их CRC зависит от раскладки кода образа: он меняется при любой правке кода прошивки, которая сдвигает функции. Для одних и тех же исходников значение Runtime Services зависит и от абсолютного пути каталога сборки (порядок элементов единственного codegen-unit), поэтому один и тот же коммит в разных каталогах даёт разные `RT=` при совпадении всех остальных строк. CRC System Table покрывает адреса данных и от раскладки не зависит. Измерения и бисект — [ISSUE-611](../KNOWN_ISSUES.md#issue-611).

Поэтому `firmware_boot_smoke.py`, `firmware_nvram_smoke.py` и `firmware_esp_boot_smoke.py` сравнивают транскрипты с маской значений `BS=` и `RT=` (`mask_layout_crcs`): остальные байты, включая `ST=`, число и порядок строк, должны совпасть точно. Содержимое таблиц по именам проверено разово (ISSUE-611); постоянной проверки значений указателей нет.

Когда меняется код ядра прошивки, в эталонах меняются ровно четыре строки: три строки `OD-FW MEM type=0x…3` и `…4` (размер образа кода и сдвиг следующих регионов) и значения в строке CRC. Правило обновления: получить фактический COM1 теми же командами `boot-firmware` и параметрами, что в `manifest.json` и в скриптах, записать его поверх эталонов, убедиться по `git diff`, что отличаются только эти строки, пересчитать `fixture_sha256` в `tests/fixtures/firmware/manifest.json` и повторить скрипты без правок. Не принимать новый эталон, если отличаются другие строки: это изменение поведения.

Чтобы убедиться, что таблицы не изменились по именам, а не только по CRC, использовались две проверки. Boot Services (376 байт) читаются из физической RAM после останова по адресу из последней строки `exit boot services verified BS=0x…`; CRC пересчитывается `zlib.crc32` с нулевым полем, а целевая функция каждого поля сопоставляется с символом ELF (`nm -C`). Runtime Services к останову заменены таблицей драйвера RT, поэтому исходная таблица собирается из `RuntimeServices::diagnostic` (поле → символ) и адресов символов ELF, а полученный CRC сравнивается с напечатанным. Скриптов в репозитории нет: чтение RAM потребовало временной правки runner.

## Что проверяет S7-05 (таблицы UEFI)

В прогоне по умолчанию строка `OD-FW S7-05 Boot Services utilities verified`
появляется после вызовов `SetMem`, `CopyMem` и `CalculateCrc32` через
фактические указатели таблицы. Строка `OD-FW S7-05 table CRC` перед ней
показывает исходные CRC трёх таблиц. Для независимой проверки после `HLT` считать
120 байт System Table с напечатанного адреса в identity-mapped RAM. В
полях по смещениям 88 и 96 находятся адреса Runtime Services (136 байт)
и Boot Services (376 байт). В каждой копии заголовка сохранить ожидаемую
контрольную сумму, обнулить четыре байта со смещения 16 и пересчитать
CRC по полному размеру таблицы через Python `zlib.crc32`. Адреса утилит
по смещениям 344, 352 и 360 в Boot Services сверить по символам ELF.
После успешного `ExitBootServices` CRC System Table меняется, его
указатель Boot Services обнулён. Последняя строка диагностики содержит
исходный адрес Boot Services для чтения её байтов извне.
[Результаты запуска и независимой сверки](../reports/STAGE_7_REPORT.md#s7-05--таблицы-uefi-и-утилиты-boot-services).

Строка `OD-FW S7-05 Boot Services memory verified` подтверждает вызовы
пяти функций по указателям той же таблицы. Диагностика запрашивает
размер карты и успешный снимок, выделяет две страницы и блок pool,
проверяет отказ повторного выделения по занятому адресу и освобождает
память. Карта возвращается с ключом `0x0f` вместо исходного `0x0b`.
[Результаты проверки сервисов памяти](../reports/STAGE_7_REPORT.md#s7-05--сервисы-памяти-uefi).

Строка `OD-FW S7-05 Boot Services protocol registry verified` подтверждает
выделение буфера pool, установку интерфейса, поиск по handle и GUID,
замену интерфейса на NULL-маркер, удаление и освобождение буфера. После
удаления повторный поиск GUID и использование прежнего handle отклоняются.
Диагностика также проверяет открытие владельцем, отказ второго драйвера,
блокировку удаления и переустановки до закрытия. `GET_PROTOCOL` оставляет
привязку доступной для последующей переустановки.
Диагностика запрашивает размер для `LocateHandle`, перечисляет handles,
находит агентов по GUID, проверяет снимок протоколов и записи обоих
открытий. Блоки результатов освобождаются через `FreePool`.
[Результаты перечисления](../reports/STAGE_7_REPORT.md#s7-05--перечисление-протоколов-и-handles).

`LocateDevicePath` проверяется на двух PCI-префиксах и пути с именем
файла. Проверка включает выбор длиннейшего совпадения, точный поиск,
фильтр по поддерживаемому протоколу, обработку первого экземпляра,
неправильную длину и сохранение указателей при ошибке.
[Результаты поиска пути устройства](../reports/STAGE_7_REPORT.md#s7-05--поиск-пути-устройства).

`InstallMultipleProtocolInterfaces` и `UninstallMultipleProtocolInterfaces`
вызываются через указатели с переменным числом параметров. Гость проверяет
пустой список, две пары на границе регистров и стека, сохранение привязок

## Подпись тестовых PE для Secure Boot S7-25

`tools/build/sign_test_app.py` принимает неподписанный x64 EFI, PEM-сертификат и соответствующий ему RSA-2048 ключ. Для теста создаются собственные эфемерные ключи и сертификаты. Ключ используется только в scratch-каталоге, удаляемом после прогона. Инструмент создаёт новый PE с `WIN_CERTIFICATE` и сохраняет Authenticode SHA-256 исходного образа с выравниванием до восьми байт.

```sh
python3 tools/build/sign_test_app.py unsigned.efi \
  --certificate test.crt --key test.key --out signed.efi \
  --openssl /usr/bin/openssl
```

Тестовый инструмент сам формирует DER `SpcIndirectDataContent` и подписанные атрибуты PKCS#7. Для RSA он вызывает `openssl dgst` с явным PKCS#1 v1.5. Так `SpcIndirectDataContent` остаётся SEQUENCE в PKCS#7 ContentInfo. Встроенный CMS-путь OpenSSL упаковывает содержимое в OCTET STRING. На одной эфемерной паре LibreSSL 3.3.6 и OpenSSL 4.1.0 создали побайтно одинаковый PE. Независимый digest и общий verifier подтвердили допуск при зачисленном сертификате и отказ при подмене секции, отзыве и отсутствии подписи. Инструмент отклонил PSS-only и чужой ключ, повторное подписание и повторную запись выходного файла. [RFC 2315 §9.3](https://www.rfc-editor.org/rfc/rfc2315#section-9.3), [план S7-25](../plans/STAGE_7.md#s7-25-проверить-secure-boot-на-собственных-приложениях).

Для первого запуска в SetupMode подготовьте защищённый снимок через API сброса ключей команды runner. `defaults` подготавливает UserMode. Параметр `--nvram-in <protected snapshot>` выбирает холодный сброс существующего снимка с сохранением обычных переменных. Подготовленный снимок передаётся через `boot-firmware --nvram-in`.

```sh
target/release/od-runner prepare-secure-boot-nvram setup --out setup.nv
target/release/od-runner prepare-secure-boot-nvram defaults --out defaults.nv
```

В `defaults` runner запускает OpenSSL с RSA-2048 и возвращает только DER публичного PK в API provisioning. Запись приватного ключа направляется в `/dev/null`. Каждый штатный сброс создаёт новый PK. Команда требует новый выходной файл и печатает SHA-256 снимка.

`python3 tests/system/firmware_secure_boot_smoke.py` по умолчанию пять раз проверяет запуск неподписанного PE в SetupMode, зачисление `KEK`, `db`, `PK` с ESP, допуск подписанного PE после холодного старта, отказ неподписанному PE и отказ чужой подписи со штатным набором ключей. Скрипт сверяет записи зачисленного снимка и точные окончания COM1. `--work` принимает пустой каталог для сохранения открытых fixtures, сборок и логов. Готовые `--runner`, `--rom` и `--apps` передаются вместе. Каталог приложений содержит `hello.efi`, `enroll.efi` и `esp-boot-probe.efi`. Зачисляющее приложение также задаёт тестовый `BootOrder=[10,11]` из двух файлов `.OPT`. Системный сценарий ставит неподписанный `BOOTX64.EFI` первым и подписанный `CHECK.EFI` вторым. Гостевой `CHECK.EFI` проверяет `BootCurrent=11`, путь и свои `LoadOptions`. Подписанный `enroll.efi` в UserMode проверяет `EFI_SECURITY_VIOLATION` от `LoadImage` для неподписанного PE. Затем он загружает подписанный PE, добавляет его Authenticode SHA-256 в `dbx` через Auth2 с подписью KEK и проверяет `EFI_SECURITY_VIOLATION` от `StartImage`. Перед возвратом приложение также сверяет неизменность указателя EFI Image Execution Information Table и две записи отказов. Оно проверяет имя и точный Device Path неподписанного PE, конечный узел для отсутствующего пути подписанного PE и SHA-256 в списке подписей записи об отзыве. Скрипт сверяет сохранённый `dbx` и отказ тому же PE при холодном старте. Проверка штатного набора начинается с пустого `BootOrder` и завершается остановом `0x21/1`.

### PKCS7 Verify Protocol

```sh
python3 tests/system/firmware_pkcs7_smoke.py
```

Скрипт создаёт ключи для проверки сообщения и отдельного TSA через OpenSSL. Ключи находятся во временном каталоге. Начальная загрузка зачисляет тестовый `PK`, `KEK` и `db` через Auth2. Затем прошивка запускает подписанный EFI-пробник на ESP с Secure Boot. При handoff v1.16 пробник находит протокол через `LocateProtocol` и вызывает оба метода. Для `VerifyBuffer` он проверяет обновление размера при коротком буфере и итоговые байты embedded и detached. Для `VerifySignature` он проверяет переданный SHA-256, неверные хеш и длину. Отдельные вызовы проверяют отсутствие контента, конфликт двух источников, некорректный DER, пустой и повреждённый списки доверия, хеш сообщения в отзыве. Доверенный токен RFC 3161 проходит до даты отзыва. Более ранний и безусловный отзыв, отсутствие доверенного TSA и токен, перенесённый с другой подписи, приводят к отказу.

Проверка требует один итоговый маркер COM1 и сверяет значения защищённых переменных в снимках до и после запуска. `--work` сохраняет открытые fixtures, сборки и логи в пустом каталоге. Готовые `--runner` и `--rom` передаются вместе. [Граница поддержки](../specs/UEFI_PROFILE.md#secure-boot).

### Отказ TPM при Startup

При корректном CRB-ответе `TPM_RC_FAILURE` на `TPM2_Startup(CLEAR)` загрузка продолжается. Журнал COM1 содержит `OD-FW TPM unavailable: TPM2_Startup returned TPM_RC_FAILURE`. Прошивка скрывает TPM2 и устройство TPM из ACPI, не публикует TCG2 и таблицу финальных событий. При активном Secure Boot проверка образов остаётся включённой. Ошибки транспорта и прочие ответы Startup останавливают инициализацию прошивки. [TCG PFP 1.06 r52, §§3.3.2.1 и 7.1](https://medias.cdn.trustedcomputinggroup.org/production/TCG_PC_Client_Platform_Firmware_Profile_Version_1_06_Revision_52_pub_3_1184065dfc.pdf).

```sh
od_tpm_failure=$(mktemp -d)
python3 tools/build/build_firmware.py --out "$od_tpm_failure/firmware.bin" \
  --target-dir "$od_tpm_failure/firmware-target"
cargo build --manifest-path firmware/uefi/tests/apps/Cargo.toml --bin tpm-absent \
  --offline --release --target x86_64-unknown-uefi --target-dir "$od_tpm_failure/app-target"
python3 tools/build/make_test_disk.py --esp-fat32 \
  --bootx64 "$od_tpm_failure/app-target/x86_64-unknown-uefi/release/tpm-absent.efi" \
  --out "$od_tpm_failure/esp.raw"
OD_TPM_FAILURE_ROM="$od_tpm_failure/firmware.bin" OD_TPM_FAILURE_ESP="$od_tpm_failure/esp.raw" \
  cargo test --offline --release -p od-machine --lib \
  firmware_boot_continues_after_tpm_startup_failure -- --ignored --nocapture
```

Тестовая сборка `od-machine` подставляет ответ CRB для Startup. Гостевое приложение из ESP проверяет отсутствие протокола и таблицы событий. Host-тест сверяет COM1, ACPI и освобождение locality с возвратом CRB в idle.

Второй тест запускает три платы с действующим TPM. Он извлекает журнал Event03 из гостевой RAM, самостоятельно вычисляет SHA-256 и SHA-384 для каждого события PCR7 и сверяет replay с `TPM2_PCR_Read` через CRB. Зачисленные и отозванные записи сверяются побайтно с исходными ESL, сохранёнными системным скриптом. PCR7 различается в SetupMode, после зачисления и после отзыва.

#### Полный пересчёт журнала Event03 для PCR0–7 (ISSUE-630)

Модуль `crates/od-machine/src/firmware_board/tcg_log_replay_tests.rs` пересчитывает весь журнал, а не только PCR7. `replay_log` проверяет заголовок Spec ID Event03 с двумя банками (SHA-256 и SHA-384), проходит по событиям до первого пустого слота или до конца журнала и для каждого события кроме `EV_NO_ACTION` расширяет PCR в обоих банках: `PCR = H(PCR || digest)`, где `digest` — запись журнала для этого банка. Событие вне PCR0–7, неверный формат заголовка или выход за границы журнала дают ошибку. Для типов, у которых профиль TCG определяет дайджест как хеш данных события (`EV_SEPARATOR`, `EV_ACTION`, `EV_EFI_ACTION`, `EV_EFI_VARIABLE_DRIVER_CONFIG`, `EV_EFI_VARIABLE_AUTHORITY`), `replay_log` дополнительно сверяет дайджесты обоих банков с хешем данных. Для остальных типов дайджест берётся из журнала как есть; в наблюдаемых журналах это типы `0x8000000a` (PCR0), `0x8000000b` (PCR1) и `0x80000003` (`EV_EFI_BOOT_SERVICES_APPLICATION`, PCR4), у которых дайджест не равен хешу данных события. Их содержимое тест не проверяет, это граница теста: он доказывает согласованность журнала с PCR, но не правильность самих дайджестов этих событий. `read_pcrs` читает PCR0–7 через `TPM2_PCR_Read` по CRB двумя командами: `TPML_DIGEST` содержит не более 8 дайджестов, поэтому один банк занимает одну команду.

- **Живой прогон** (ignored-тест из предыдущего раздела): после каждой из трёх загрузок `check_boot` сверяет пересчёт со значениями `TPM2_PCR_Read` для PCR0–7 обоих банков, а не только PCR7. Результат 2026-11-21: `ok`, 1306,62 с (`unsigned.raw` 364987762 инструкций, `enroll.raw` 366990104, `revoke.raw` 367749573); ROM — базовый `firmware.bin` из `--work` прогона `firmware_secure_boot_smoke.py` (sha256 `f7920b37…a83562`).
- **Всегда выполняемый тест** `recorded_boot_logs_replay_to_the_recorded_pcr0_to_7_in_both_banks` не требует ROM. Он пересчитывает три журнала, записанные этим живым прогоном, и сверяет с записанными в тех же файлах PCR0–7 обоих банков; проверяет, что каждая из PCR0–7 расширена хотя бы раз, а PCR ненулевой ровно тогда, когда журнал её расширял. Тест `a_corrupted_log_no_longer_replays_to_the_recorded_pcrs` показывает, что проверка различает повреждения: один изменённый октет дайджеста SHA-256 меняет только банк SHA-256, SHA-384 — только банк SHA-384; потерянное последнее событие, обрыв внутри события и испорченный заголовок не проходят.
- **Фикстуры** `tests/fixtures/firmware/tcg_log_{unsigned,enroll,revoke}.bin` (20812, 23817 и 25317 октетов, не более 100 КиБ): 8 × 32 октета PCR0–7 SHA-256, 8 × 48 октетов PCR0–7 SHA-384 и использованная часть журнала. Происхождение: тот же ignored-тест, основа — коммит `5e07d1c`, 2026-11-21, три платы (`unsigned.raw` — запуск неподписанного `hello` в SetupMode, `enroll.raw` — зачисление PK/KEK/db, `revoke.raw` — отзыв и `dbx`). Фикстура фиксирует журнал той прошивки; изменение прошивки её не ломает — расхождение новой прошивки ловит живой прогон.

```sh
# Перезапись фикстур (после изменения измерений прошивки): тот же прогон, плюс каталог записи.
OD_SB_PCR7_ROM="$od_sb_pcr7/firmware.bin" OD_SB_PCR7_FIXTURES="$od_sb_pcr7" \
  OD_TCG_LOG_FIXTURE_DIR="$PWD/tests/fixtures/firmware" \

```

При установленной `OD_TCG_LOG_FIXTURE_DIR` прогон перед проверками пишет в каталог также `tcg_log_<имя>.full` (вся область журнала, 256 КиБ) для разбора упавшего пересчёта; эти файлы в репозиторий не коммитятся.

- В Git хранятся небольшие эталоны COM1 и JSON-манифесты с хешами. Образы ESP генерируются при проверке скриптом из `tools/build/`. Чужие образы прошивок, `.aml`, дампы SMBIOS и большие файлы в Git не хранятся.
- Каталог `tests/fixtures/firmware/` содержит `boot_core_com1.txt` с диагностикой ядра и отдельные транскрипты COM1 для приложений из FV. Для `fs` скрипт `tools/build/make_test_disk.py --esp-fat32 --out <path>` создаёт GPT с разреженным FAT32 ESP. Размер файла 40 MiB даёт FAT32 необходимое число кластеров. Измеренное выделение на APFS составляет 1 753 088 байт. Скрипт пишет BPB, FSInfo, две FAT, корневой каталог и `\EFI\BOOT\README.TXT` собственным кодом. `firmware_boot_smoke.py` проверяет SHA-256, подключает файл к NVMe и сверяет COM1 с `fs_com1.txt`.
- Временные артефакты — в `work/stage7/` (каталог `work/` игнорируется Git): образ `work/stage7/firmware.bin`, cargo target `work/stage7/firmware-target/`, probe `work/stage7/efi_probe.efi` (target `work/stage7/firmware-target-efi-probe/`).
- Новый вывод сверяется с контрактом в разделах 11–12 и фиксируется вместе с изменением кода. Команда выше сохраняет транскрипт для сравнения с эталоном.

## Гостевая загрузка с ESP

`python3 tests/system/firmware_esp_boot_smoke.py` собирает stock ROM,
`hello.efi` и проверочное приложение. Генератор ESP размещает их по
путям `\EFI\BOOT\BOOTX64.EFI` и `\EFI\BOOT\CHECK.EFI` в разреженном
образе. Тест запускает прошивку без FV-селектора и сверяет полные байты
COM1, SHA-256 обоих дисков и SHA-256 сохранённых NVRAM snapshots.
Сценарии проверяют загрузку по умолчанию, отсутствие ESP, fallback после
отсутствующего файла, приоритет `BootNext` и восстановление снимка.
Проверочное приложение сверяет `BootCurrent`, `LoadOptions`, `DeviceHandle`
и оба интерфейса пути. Проверка снимка читает поколения банков и CRC.
[Формат NVRAM](../specs/NVRAM_DEVICE.md#host-api).

## Диагностика пути Linux через UEFI (S7-31a)

Диагностический срез, не приёмка S7-31. Ядро и initramfs берутся из `work/stage4/` основной копии репозитория (в Git их нет). Запись остановки неизменённого `vmlinuz` Ubuntu 7.0.0-38 и двух диагностических копий (ImageBase 0x1000000; то же и SizeOfHeaders 0x400), по два прогона каждой:

```sh
cargo build --release -p od-runner --offline
python3 tests/system/firmware_linux_uefi_stop_record.py \
  --stage4-dir <корень>/work/stage4 --out work/stage7/linux-uefi-stop-record.json
```

Запись efivarfs и ACPI (S7-31n, диагностика): `python3 tests/system/firmware_linux_uefi_efivars_acpi.py --stage4-dir <корень>/work/stage4 --out <record.json>` собирает `work/stage7/s7-31n/initramfs.cpio` (`tools/build/build_s7_31n_initramfs.py`), загружает ядро на едином цикле с зерном NVRAM (`Boot0001`, `BootOrder`, `ODBootCount`) и записывает имена переменных `efivarfs` и строки ACPI из dmesg (хеш и выдержки COM1; код 0 — записи прогонов совпали, а не что ACPI чист). Узкие проверки: `python3 -m unittest tools/build/test_build_s7_31n_initramfs.py`.

Код 0 у записи остановки означает, что записи обоих прогонов каждого варианта совпали, а не что Linux загрузился; сама остановка описана в JSON (RIP, байты у RIP из ROM или файла PE, символ, отметки, строка COM1). Ожидаемая остановка на текущем ROM: `stock` — «no bootable option» ([ISSUE-620](../KNOWN_ISSUES.md#issue-620)); `rebased` — `Unsupported { opcode: 131 }` в `load_into` ([ISSUE-621](../KNOWN_ISSUES.md#issue-621)); `rebased-hdr` — `Unsupported { opcode: 30 }` на первой инструкции stub ([ISSUE-622](../KNOWN_ISSUES.md#issue-622)). Один прогон занимает 45–95 с. Статический инвентарь инструкций stub:

```sh
cargo build --release -p od-isa --example firmware_profile_probe --offline
python3 tools/build/s7_31a_efi_stub_isa_inventory.py --vmlinuz <vmlinuz-7.0.0-38-generic>
```

ESP для этих прогонов собирает `tools/build/make_test_disk.py --esp-fat32 --bootx64 <efi> --boot-file INITRD.IMG=<файл>` (дополнительные файлы только в `\EFI\BOOT\` с короткими именами 8.3). Результаты и выводы: [отчёт этапа 7](../reports/STAGE_7_REPORT.md#s7-31a--диагностика-пути-linux-через-собственную-uefi-2026-11-20), [ADR-0013](../decisions/ADR-0013-uefi-linux-cpu-profile.md).


## Политика LoadImage для образа без перемещений (S7-31b)

Host-тесты `pe::loader::tests` и `mem::pages::image::tests` проверяют политику ISSUE-620 без запуска гостя: `cargo test --manifest-path firmware/uefi/Cargo.toml --offline --lib pe::` и `--lib mem::pages`.

- `stub_layout_image_is_position_independent_and_loads_without_fixups` собирает заголовки EFI stub ядра Ubuntu 7.0.0-38 с нуля (ImageBase 0, Characteristics `0x206`, SizeOfHeaders `0x1000`, четыре секции с теми же VA, `SizeOfImage=0x10f0000`). Запускается всегда; байтов ядра в Git нет.
- `ubuntu_kernel_efi_stub_is_position_independent_and_loads_without_fixups` читает настоящий `vmlinuz-7.0.0-38-generic` как данные. Файл ищется по `work/stage4/linux-7.0.0-38.38/vmlinuz-7.0.0-38-generic` вверх от каталога `firmware/uefi` либо по переменной `OD_UBUNTU_VMLINUZ` (полный путь).
- Переменная `OD_REQUIRE_UBUNTU_VMLINUZ=1`: если файла нет, этот тест **падает**. Без неё тест при отсутствии файла печатает `skipped` и проходит (ядро не хранится в Git). Команда приёмки S7-31 задаёт переменную, чтобы пропуск не считался прохождением.
- Размещение: образ с ImageBase 0 без каталога перемещений ставится по самому нижнему свободному адресу не ниже 1 МиБ, выровненному на 2 МиБ; образ с каталогом — по самому верхнему; закреплённый образ с ImageBase 0 получает `EFI_OUT_OF_RESOURCES`. Проверено на модели карты платы 128 МиБ ([FIRMWARE_BOOT.md](../specs/FIRMWARE_BOOT.md), раздел 2).
