# Методика проверки приложения и жизненного цикла VM (этап 11)

Статус: методика S11-01. Документ описывает, **как** проверять оболочку настольного приложения, VMHost и жизненный цикл машины на этапе 11. Он сам ничего не подтверждает: ни приложение, ни жизненный цикл, ни скрипты, которые в нём названы как будущие, ещё не существуют.

Связанные документы: [план этапа 11](../plans/STAGE_11.md) (разделы 0, 5, 6), [отчёт этапа 11](../reports/STAGE_11_REPORT.md), [ADR-0006](../decisions/ADR-0006-desktop-app-shell.md), [состояние VM и операции](../specs/VM_STATE.md) (раздел 3), [протокол control v1](../../protocols/control/CONTROL_PROTOCOL_V1.md), [методика проверки control](CONTROL_PROTOCOL_TESTING.md), [методика проверки изображения](DISPLAY.md), [стенд](STAND.md), [матрица поддержки](../specs/SUPPORT_MATRIX.md).

## 1. Пять уровней доказательств

| Уровень | Что проверяется | Команда запуска | Критерий прохождения |
|---|---|---|---|
| 1. Unit-тесты без окон и процессов | Swift-модели (каталог, конфигурация, клиент control v2, состояния, представление ошибок); Rust (storage ABI, канал агента, NAT backend, файловый сервис) | Rust: `cargo test -p <crate> --offline` (существует). Swift: `cd apps && swift build && swift test` (после `cargo build -p od-host --offline`; существует с S11-05a) | Код выхода 0; число выполненных тестов больше нуля и совпадает с ожидаемым в задаче; каждая ошибка даёт заявленный класс отказа. Тест, который ничего не выполнил или был пропущен, не засчитывается |
| 2. Протокольный smoke | Control v2 по байтам: запрос, ответ, событие, отказ, лимиты, мусор на входе, `unsupported_durability`. VMHost запускается с `socketpair`, как в существующих `vmhost_control_v1_*_smoke.py` | `python3 tests/system/vmhost_control_v2_lifecycle_smoke.py` (существует с S11-04; без аргументов) | Код выхода 0; скрипт сам сверяет каждое отправленное и полученное сообщение с ожидаемыми байтами; на каждый отрицательный случай приходит заявленный отказ без зависания (таймаут скрипта считается провалом); VMHost завершается с кодом, заявленным в `CONTROL_PROTOCOL_V2.md` (S11-03) |
| 3. Сценарий без UI | Полный жизненный цикл машины на test-only профиле одной командой-обёрткой: создать, запустить, получить `running`, пауза, продолжение, остановка, удаление (обёртка сама вызывает отдельные команды) | `odctl create`, `odctl run <bundle> --script FILE` (сценарий: start, wait, pause, resume, sleep, query, stop) и `odctl delete` (S11-13), плюс скрипт-обёртка `tests/system/odctl_lifecycle_smoke.py` (S11-13), который сверяет события и коды выхода | Код выхода обёртки 0; последовательность событий в выводе равна последовательности в сценарии; коды выхода `odctl` совпадают с таблицей в `docs/specs/CLI.md` (создаёт S11-13); после сценария не остаётся процесса VMHost и висящей блокировки bundle |
| 4. Ручная проверка UI | Окна, меню, диалоги, видимое состояние | Чеклист раздела 2 этого документа | Все пункты чеклиста выполнены, к каждому приложено доказательство из колонки «Приложить». Уровень 4 — факт для отчёта, а не доказательство правильности |
| 5. Гостевой уровень | Поведение с реальной гостевой ОС: загрузка, агент, сеть, звук, общие папки | Нет команды: blocked до этапов 5, 7, 8 | Пока блокировка не снята, в отчёте записывается слово `blocked` с указанием этапа. Результат test-only профиля его не заменяет |

Правила уровней:

1. Нижний уровень не заменяет верхний. Зелёные unit-тесты не доказывают, что VMHost отвечает по протоколу; зелёный smoke не доказывает, что кнопка в окне работает.
2. Уровень 4 никогда не бывает единственным доказательством. Каждый пункт чеклиста опирается на проверку состояния через события VMHost (уровни 2–3) или явно записан как «только вид».
3. Состояние машины, которое показывает UI, сверяется с событиями VMHost, а не с догадками интерфейса ([план, раздел 0](../plans/STAGE_11.md): истина — события).
4. Если уровень пока недоступен (нет команды), в отчёте пишется `не запускалось: <причина>`, а не `прошло`.

### Какую проверку добавить вместе с изменением

| Что меняется | Минимум доказательств в той же задаче |
|---|---|
| Swift-модель без процессов (каталог, состояния, ошибки, клиент control v2) | Уровень 1 с позитивными и отрицательными случаями |
| Сообщение, событие, лимит или отказ control v2; поведение VMHost | Уровень 2 по байтам, включая отказ на мусор и усечённые кадры; уровень 1, если есть Swift-разбор |
| Переход состояния VM, запуск/остановка, выход приложения, сбой VMHost | Уровень 2 и, начиная с S11-13, уровень 3 |
| Экран, меню, диалог, мастер | Уровень 1 для модели, которую они показывают, и пункт чеклиста раздела 2 (уровень 4) |
| Всё, что требует гостя | Уровень 5 записывается как `blocked`; на test-only профиле проверяется только та часть, которая гостя не требует |

## 2. Ручной чеклист UI

Чеклист применяется к `OpenDesktop.app` и выполняется человеком на основном host ([стенд](STAND.md)). **До появления библиотеки машин в приложении (S11-06) пункты не выполнимы**: в отчёте они записываются как `не запускалось: приложения ещё нет`. Автоматизация UI не обещается (см. раздел 5).

Условия: все проверки идут на test-only профиле ([план, раздел 0, пункт 6](../plans/STAGE_11.md)): профиль `OD_DISPLAY_PROFILE_TEST_PATTERN` или `OD_DISPLAY_PROFILE_TWO_SCREENS_TEST`, без гостя, без дисков, без persistent root. Каждый результат помечается словами «test-only, без гостя». Перед прогоном записывается fingerprint из раздела 3. Структуру и поля bundle определяет `docs/specs/VM_BUNDLE.md` (создаёт S11-02), поведение команд — `protocols/control/CONTROL_PROTOCOL_V2.md` (S11-03); чеклист не заменяет их. Если спецификация предписывает отказ (в том числе `unsupported_durability`), ожидаемое наблюдение — этот отказ с объяснением на экране и неизменность bundle.

Что прикладывать:

- **Скриншот** окна или диалога. В отчёте рядом с ним записывается текстом, что на нём видно, дата и fingerprint. Скриншот не заменяет описание. *Предложение, не из плана:* бинарные файлы в Git не добавляются без отдельного решения владельца.
- **Текст события** — строка или кадр из лога VMHost, события control v2 (имя события, состояние, код ошибки), скопированные как текст.
- **Проверка файловой системы** — вывод `ls` каталога bundle до и после.

| № | Шаг | Ожидаемое наблюдение | Приложить |
|---|---|---|---|
| 1 | Создание машины: открыть мастер, ввести имя, выбрать test-only профиль, подтвердить | Машина появилась в библиотеке с введённым именем и состоянием `stopped`; на диске есть каталог `<Имя>.odvm/` с конфигурацией; на экране нет обещаний о гостевой ОС и о сохранности данных | Скриншот библиотеки; `ls` каталога bundle; пометка «test-only, без гостя» |
| 2 | Запуск | Состояние сменилось `stopped` → `running` по событию VMHost, а не раньше; в системе появился один процесс VMHost для этой машины | Текст события `running`; скриншот; вывод `ps` по процессу VMHost |
| 3 | Окно дисплея | Открылось окно; показан тестовый узор профиля (для профиля 4 — оба экрана); размер кадра совпадает с размером профиля; гостевого содержимого нет | Скриншот окна; размер кадра текстом |
| 4 | Пауза | Состояние `paused` по событию; узор не обновляется (для статичного узора — обновление не наблюдается и событие `paused` получено); кнопки паузы и продолжения отражают состояние | Текст события `paused`; скриншот |
| 5 | Продолжение | Состояние `running` по событию; окно живое | Текст события `running`; скриншот |
| 6 | Остановка | Состояние `stopped` по событию; окно закрылось или показывает остановленное состояние; процесс VMHost завершился с кодом, заявленным в `CONTROL_PROTOCOL_V2.md` (S11-03); блокировка bundle снята | Текст события `stopped`; `ps` без процесса; код выхода VMHost из лога |
| 7 | Удаление (доступно только в состоянии `stopped`; для запущенной машины действие недоступно или отвергается) | Два подслучая. (а) Только из библиотеки, переключатель «удалить файлы с диска» выключен: запись пропала из библиотеки, каталог bundle остаётся на диске без изменений. (б) С файлами: после подтверждения каталог bundle удалён с диска. Если спецификация (`VM_BUNDLE.md`, `CONTROL_PROTOCOL_V2.md`) заявляет отказ на этом профиле, ожидается заявленный отказ, bundle не тронут | Скриншот подтверждения и результата; `ls` каталога до и после для каждого подслучая |
| 8 | Выход из приложения: с запущенной машиной и с остановленной | С запущенной машиной приложение предупреждает о последствиях и действует по решению S11-11; VMHost после выхода не остаётся сиротой; повторный запуск приложения показывает фактическое состояние машины, а не запомненное | Скриншот предупреждения; `ps` после выхода; скриншот после повторного запуска |

Если пункт не прошёл, это дефект либо найденное ограничение; записать в отчёт точное наблюдение. Если пункт нельзя выполнить из-за отсутствия функции других задач, записать `blocked` с номером задачи. Пропускать пункт молча нельзя.

## 3. Измерения

Правила из раздела «Решения в критичных по производительности участках» [AGENTS.md](../../AGENTS.md) действуют целиком: без чисел не заявлять «быстро» и не выбирать оптимизацию; до замера любое утверждение о скорости — гипотеза.

| Что мерить | Начало и конец отсчёта | Где появится |
|---|---|---|
| Время запуска | От отправки команды `START` до события `running` | S11-14 |
| Задержка паузы | От отправки `PAUSE` до события `paused` | S11-14 |
| Время создания bundle с RAW-диском 64 GiB | От начала команды создания до подтверждения готовности; дополнительно записываются логический размер файла и фактически выделенный размер на диске | S11-08, S11-14 |
| RSS приложения и VMHost | `ps -o rss= -p <pid>` (KiB) в заданные моменты сценария | S11-14, S11-61 |
| NAT на loopback: пропускная способность и задержка | Собственный генератор нагрузки (не готовый инструмент как «истина»), loopback | S11-31e |
| Звук: задержка от записи в кольцо до вывода | От записи в кольцо до наблюдаемого вывода звуковой подсистемы host | S11-41 |
| Длительный прогон: RSS в начале и в конце | Начало и конец заданной длительности; длительность записывается | S11-61 |
| Сеть с гостем: пропускная способность и задержка | Определяет S11-34 | S11-34, blocked до гостя (после S11-33) |

Правила прогона:

1. **Повторы.** Не менее 5 повторов (план, раздел 5). Первый прогон (прогрев) отбрасывается из статистики и записывается отдельно с пометкой. Входит ли прогрев в пять или нет — трактовка исполнителя, ждёт подтверждения владельца.
2. **Fingerprint** записывается в каждый файл результатов. *Обязательно по плану (раздел 5):* модель Mac (`sysctl -n hw.model`), сборка macOS (`sw_vers -buildVersion`), режим сборки (`debug` или `release`). *Предложение, не из плана:* версия macOS (`sw_vers -productVersion`), чип (`sysctl -n machdep.cpu.brand_string`), размер страницы host (`sysctl -n hw.pagesize`), версии `xcrun swiftc --version` и `rustc --version`, ревизия Git и признак «рабочее дерево чистое или нет», профиль VMHost. Пометка «test-only, без гостя» записывается всегда.
3. **Единицы и разброс.** Для каждой величины указываются единица, минимум, максимум и медиана учитываемых прогонов. Разброс приводится вместе со значением; различие в пределах шума не называется ускорением.
4. **Условия.** Записываются сценарий и точное командное воспроизведение; работает ли Mac от сети; нагрузка на host; одинаковые условия при сравнении вариантов.
5. **Куда класть.** JSON в `docs/reports/data/stage11/` (каталог создаёт первая задача, которая пишет туда данные). *Предложение, не из плана:* имя `s11-NN-<метрика>-<ГГГГ-ММ-ДД>.json` и набор полей `task`, `metric`, `unit`, `command`, `fingerprint`, `warmup`, `samples`, `min`, `median`, `max`, `label`, `notes`. Ограничение из плана (S11-14): файл JSON не больше 100 KiB.
6. В отчёте этапа даётся ссылка на файл и вывод одной строкой. Числа из отчёта без файла результатов не принимаются.
7. Данные профиля test-only не переносятся на продуктовую VM: заявление о скорости запуска или памяти реальной машины без гостя недопустимо.
8. RSS, снятый через `ps -o rss`, не годится как мера утечки за длительный прогон: на этом хосте он колеблется в пределах десятков процентов внутри одного прогона, а VMHost в «спящем» состоянии падает примерно на 86 % (S11-61). Для длительного прогона нужна мера `phys_footprint` с несколькими замерами внутри прогона.

## 4. Правила честности

1. **Метка профиля.** Любой результат, полученный на test-only профиле (узор, два экрана), помечается словами «test-only, без гостя» в отчёте, в названии измерения и в поле `label`. Это не продуктовая VM; у профиля нет гостя, дисков и persistent root.
2. **`unsupported_durability` — ожидаемое поведение.** До закрытия ISSUE-055 (S9-06) по [VM_STATE.md §3](../specs/VM_STATE.md) все изменяющие операции VM и долговечная запись операции (термины `mutating` и `durable operation record` из VM_STATE §3) недоступны, ответ — `unsupported_durability`. Операции над машиной с диском и гостевой `SHUTDOWN` отвечают именно так. Это не дефект: тест на отказ **проверяет** его и считается пройденным, когда отказ получен с этим кодом. В `KNOWN_ISSUES.md` такое поведение не записывается. Дефектом будет другое: операция выполнилась, хотя должна была отказать, или отказ пришёл с другим кодом. Остановка сессии test-only профиля без persistent root под это правило не попадает ([план, раздел 0, пункт 7](../plans/STAGE_11.md)).
3. **Durability не заявляется.** Создание файлов bundle и диска не доказывает сохранность данных при потере питания; слов «надёжно» и «сохраняется» в отчётах об этих проверках нет.
4. **Гость.** Пока этапы 5, 7, 8 не начаты, уровень 5 записывается как `blocked`. Результат test-only профиля не выдаётся за результат с гостем.
5. **«Реализовано» и «подготовлено».** «Реализовано» — код есть, тесты проходят, ревью пройдено, отчёт записан. Скрипт, команда, файл, которые только описаны, — «подготовлено» или «появится в S11-NN».
6. **Не запускалось — значит не запускалось.** Если проверка не выполнялась (нет команды, нет приложения, нет доступа к Mac), в отчёте так и пишется, с причиной. Недоступное ревью записывается словами.
7. **Только факты.** Повторяемая команда и код выхода — доказательство; впечатление «работает» — нет. Скриншот без записи того, что на нём видно, — не доказательство.
8. **Нет подмены.** Заглушка, эхо-ответ или хардкод события не засчитываются как поведение VMHost.

## 5. Ограничения методики

- **XCUITest не используется и не обещается.** В репозитории нет Xcode project; сборка идёт через Swift Package ([ADR-0006](../decisions/ADR-0006-desktop-app-shell.md), решение (а)), и там же записано, что Xcode project пересматривается на этапе 12 или при необходимости UI-автоматизации. Пока его нет, UI проверяется вручную (уровень 4), а сквозное автоматическое доказательство lifecycle без окон — только уровень 3 через `odctl`.
- Уровень 4 зависит от конкретного Mac, версии macOS и состояния экрана; результат относится к записанному fingerprint и не переносится на другие системы.
- Уровни 2–3 есть (S11-04 и S11-13): smoke control v2 и `odctl`, команда в разделе 8.
- Измерения этапа 11 проводятся на test-only профиле, без гостя; они описывают оболочку и VMHost, а не производительность гостевой системы.
- Контрольный M1 Pro инвентаризуется позже ([план, раздел 5](../plans/STAGE_11.md)); до этого результаты относятся только к основному host.
- Документ не определяет форматы bundle, протокола, ошибок и CLI. Их определяют `VM_BUNDLE.md`, `CONTROL_PROTOCOL_V2.md`, `USER_FACING_ERRORS.md`, `CLI.md` (задачи S11-02, S11-03, S11-09, S11-13); после появления они приоритетнее этого документа.

## 6. Условия host: сон, экраны, место, память (S11-12)

Реализация и источники — `apps/macos/README.md`, раздел «Сон, экраны, место и память (S11-12)». Автоматические проверки (`swift test --filter HostConditions`) вызывают обработчики с подставленными событиями; настоящий сон, настоящая смена дисплеев и настоящее давление памяти ими **не проверяются**. Как и в разделе 2, процедура ниже выполняется человеком на основном host на test-only профиле, результат помечается «test-only, без гостя». **Сон не выполняется из скрипта и из автотеста.** До выполнения процедуры в отчёте записано: «не запускалось».

### Пороги места: ГИПОТЕЗА

Предупреждение — свободно меньше **5 GiB** на томе bundle; жёсткий порог — меньше **1 GiB**. Источника и измерения у этих чисел нет: это первое предположение (`DiskSpaceThresholds.hypothesis`). Решение о значениях принимается после замеров на S11-14 и S11-61; пока числа не замерены, их нельзя называть безопасными. Проверка идёт перед `START` и `PREPARE_DISK`, а в `running` — раз в 30 с (30 с — тоже предположение, не замер). Ёмкость RAW-образа при `PREPARE_DISK` из свободного места не вычитается (RAW может быть sparse — гипотеза, не проверена).

### Ручная процедура сна

Условия: Mac от сети; библиотека с test-only машиной (профиль `OD_DISPLAY_PROFILE_TEST_PATTERN`); пункт меню «Машина» → «Приостанавливать машины при сне» включён (по умолчанию).

| № | Шаг | Ожидаемое наблюдение | Приложить |
|---|---|---|---|
| 6.1 | Запустить машину, дождаться `running` и окна с узором | Строка машины «Запущена», окно рисует | Скриншот |
| 6.2 | Закрыть крышку или выполнить в Terminal **вручную** `pmset sleepnow`; подождать 20–30 с | Mac засыпает | Время начала сна |
| 6.3 | Разбудить Mac | Строка машины «Запущена» (`PAUSE reason=system_sleep`, затем `RESUME reason=system_wake`); окно рисует, а не показывает замороженный кадр или «Пауза»; строки об отказе нет | Скриншот; события из лога/строки машины |
| 6.4 | Повторить 6.2–6.3 с машиной, поставленной на паузу кнопкой «Приостановить» до сна | После пробуждения машина остаётся «Приостановлена»: пауза пользователя не снимается | Скриншот |
| 6.5 | Выключить пункт «Приостанавливать машины при сне», запустить машину, повторить 6.2–6.3 | Машина не получает `PAUSE` перед сном; что с ней после пробуждения, записать как наблюдение (не заявлять заранее) | Скриншот, наблюдение |
| 6.6 | Если после пробуждения у машины строка об отказе паузы или продолжения | Строка называет операцию словами каталога («Пауза перед сном: …»), состояние строки совпадает с последним событием VMHost | Текст строки |

### Ручная процедура смены дисплеев

Нужен внешний монитор.

| № | Шаг | Ожидаемое наблюдение | Приложить |
|---|---|---|---|
| 6.7 | Подключить внешний монитор, запустить машину, перетащить окно машины на внешний монитор | Окно рисует на внешнем мониторе | Скриншот |
| 6.8 | Отключить внешний монитор при открытом окне | Окно оказалось на основном экране целиком в видимой области; узор не искажён, рамка не растянута (проверить режимы «По размеру окна» и «Пиксель в пиксель») | Скриншот |

### Место и память (по возможности)

- Место: настоящее исчерпание места не воспроизводится на рабочем томе. Достаточно автоматических проверок с подставленной ёмкостью и запуска `OpenDesktop --simulate-host-event low-space` (test-only аргумент; машина должна быть `running` через секунду после запуска): ожидаемо `PAUSE reason=disk_space`, строка «Машина приостановлена: на диске почти нет места», машина не продолжается сама, «Продолжить» снимает паузу (если «место» всё ещё симулируется, следующая проверка через 30 с поставит паузу снова).
- Память: `OpenDesktop --simulate-host-event memory` показывает баннер уровня `critical` при живой машине; настоящее давление памяти не создаётся. Приложение ничего не останавливает.
- Что считается результатом: наблюдаемый факт со скриншотом. «Вид баннера» и «вид строки» глазами записываются отдельно от unit-тестов.

## 8. Одна команда проверки гейтов G1–G3 (S11-62)

Команда запускается из корня чистого checkout (например, `git clone --branch feat/s9-stage <репозиторий> <каталог>`), без артефактов предыдущих сборок:

```bash
cargo build -p od-host --offline && python3 tools/build/build_app_bundle.py && (cd apps && swift build) && python3 tests/system/vmhost_control_v2_lifecycle_smoke.py && python3 tests/system/desktop_lifecycle_smoke.py --skip-build && python3 tests/system/odctl_lifecycle_smoke.py
```

- Шаг `cargo build -p od-host --offline` нужен, потому что `apps/Package.swift` линкует `target/debug/libod_host.a` для `swift build` (debug), а `build_app_bundle.py` собирает `od-host` в release. Без этого шага чистый checkout не собирается (проверено: первый запуск упал на линковке `od-vmhost`).
- Код выхода всей цепочки 0 означает, что каждый шаг прошёл.
- Проверено 2026-11-06 на клоне коммита `d769a5b` (Mac15,11, macOS 26.7.1, arm64): протокольный smoke control v2 — все группы `ok`; `desktop_lifecycle_smoke.py` — 5 из 5 повторов `ok` (окно процесса найдено в каждом); `odctl_lifecycle_smoke.py` — `ok`; `CHAIN_EXIT=0`.
- Что это не покрывает: сон Mac, смену дисплеев, давление памяти и место, гостя, визуальную проверку окон глазами (см. раздел 2 и разделы 5–6).
