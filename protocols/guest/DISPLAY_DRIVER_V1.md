# Протокол display-only драйвера, версия 1

**Статус:** документ написан в задаче S10-13 [плана этапа 10](../../docs/plans/STAGE_10.md#s10-13-протокол-display-only-драйвера-и-расширение-устройства) и **ожидает архитектурного ревью**. Устройство реализовано в `crates/od-machine/src/display_device.rs`: `VERSION = 2`, регистры `0x100–0x1FC` и таблица режимов `0x400–0x7FC` (S10-13); блок курсора `0x200–0x2FC` при бите `CAPS` 2 (S10-14); блок второго экрана `0x300–0x3FC` при бите `CAPS` 3 в конфигурации с двумя экранами (S10-15). `CAPS = 0x3`, с курсором `0x7`, с двумя экранами `0xF`. Не выполнено:

- ни одного драйвера нет: Linux-путь (S10-21) заблокирован этапом 5, Windows-драйвер (S10-22) — этапом 8 ([guest/AGENTS.md](../../guest/AGENTS.md));
- ни одна последовательность этого документа не выполнялась гостевым кодом: единственный гостевой код — probe S10-08 (профиль 2), он знает только регистры ревизии 1 и рисует один экран; события, ответы, курсор и экран 1 проверены записями и чтениями через `MachineBus` и host-тестами.

Документ нормативен для обмена между гостевым display-only драйвером и собственным дисплейным устройством Open Desktop. Регистры и протокол — собственный проект; они не основаны на чужих виртуальных или физических дисплейных устройствах и их драйверах.

## 1. Границы и где что нормативно

Протокол покрывает только регистры и события устройства: обнаружение, согласование версии, список режимов, очередь событий host → гость, запрос смены разрешения и ответ на него, период опроса. Не покрывает:

- 3D, команды ускорения, ресурсы и fences — S10-31; этот протокол не расширяется в их сторону;
- обнаружение через PCI — S10-12; до него устройство находится по фиксированным адресам;
- GOP — S10-18;
- способ, которым ОС внутри гостя узнаёт о новом режиме (DRM hotplug, WDDM re-enumeration), — дело конкретного драйвера (S10-21, S10-22);
- путь запроса от окна UI до VMHost — вне этого документа (раздел 11).

| Что | Где нормативно |
|---|---|
| Адреса окна регистров и памяти framebuffer, карта регистров ревизий 1 и 2, классы доступа, значения после reset, поведение устройства (проверки, порядок, ёмкость очереди, объединение и переполнение), коды ошибок в `STATUS`/`EVENT_STATUS`, reset, host API | [DISPLAY_DEVICE.md](../../docs/specs/DISPLAY_DEVICE.md): разделы 3–10 (ревизия 1) и 14 (ревизия 2) |
| Номера версий протокола, типы событий и смысл их аргументов, кодирование ответа (вердикт, причина), последовательности действий драйвера, период опроса, правила совместимости для драйвера | этот документ |

Имена регистров ниже — имена из DISPLAY_DEVICE.md. Смещения приведены для удобства; при расхождении верна таблица DISPLAY_DEVICE.md (раздел 4 для ревизии 1, раздел 14.5 для ревизии 2).

**Термины.** *Ревизия устройства* — значение `VERSION` (1 или 2). *Версия протокола* — значение, которое драйвер пишет в `DRIVER_PROTOCOL`; этот документ задаёт версию протокола `1`. Устройство ревизии 2 поддерживает версию протокола 1. Числа совпадать не обязаны.

## 2. Кодирование

- Каждый регистр — 32-битное беззнаковое число, little-endian. Допустим только 32-битный доступ по смещению, кратному 4, в MMIO (DISPLAY_DEVICE.md, раздел 4). Драйвер использует 32-битные MMIO-примитивы своей ОС. Доступ другой ширины — backend-ошибка, которая останавливает квант машины; гость её не получает и обработать не может (раздел 9).
- 64-битные значения передаются парой регистров `*_LO`/`*_HI`.
- Разделяемых структур в памяти гостя нет. Устройство не пишет в RAM гостя (DMA нет). Единственная общая память — framebuffer, его формат задаёт DISPLAY_DEVICE.md, раздел 2.
- Все записи и чтения регистров синхронны: результат команды виден в регистрах сразу после возврата из записи.

## 3. Обнаружение и согласование

До S10-12 устройство находится по фиксированным адресам DISPLAY_DEVICE.md, раздел 3: окно регистров `0xFC00_0000`, 4 KiB.

Драйвер протокола версии 1 при запуске:

1. Читает `ID` (`0x000`). Значение не `0x4246_444F` — устройства нет, драйвер не загружается.
2. Читает `VERSION` (`0x004`). Требование — `VERSION ≥ 2`, **никогда не равенство**. При `VERSION = 1` — раздел 3.1.
3. Читает `CAPS` (`0x008`). Нужны биты 0 (`MODE_LIST`) и 1 (`EVENTS`). Неизвестные биты драйвер игнорирует и не предполагает, что они равны нулю.
4. Читает `DRIVER_PROTOCOLS` (`0x100`). Нужен бит 1 (версия протокола 1).
5. Пишет `DRIVER_PROTOCOL` (`0x104`) ← `0`: сброс событий, оставшихся от прежнего экземпляра драйвера (раздел 8).
6. Пишет `DRIVER_PROTOCOL` ← `1`. Читает `EVENT_STATUS` (`0x108`): поле `PROTOCOL_ERROR` (биты 23:16) должно быть `0x00`. Читает `DRIVER_PROTOCOL`: должно быть `1`.
7. Читает `MAX_WIDTH`, `MAX_HEIGHT`, `FORMATS`, `FB_BASE_LO/HI`, `FB_SIZE`. Гость не угадывает их по константам.
8. Читает список режимов (раздел 4) и устанавливает начальный режим путём ревизии 1: `WIDTH`, `HEIGHT`, `FORMAT`, `MODE_COMMIT ← 1`, проверка `STATUS.COMMIT_ERROR`.
9. Запускает опрос (раздел 7).

Пока драйвер не выполнил шаг 6, устройство событий не держит и host не может поставить запрос смены разрешения (DISPLAY_DEVICE.md, 14.2). Поэтому гость, не знающий протокола, никогда не видит событий.

### 3.1. Устройство ревизии 1

На устройстве с `VERSION = 1` смещения `0x100–0x1FC` и `0x400–0x7FC` зарезервированы: чтение даёт `0`, запись игнорируется (DISPLAY_DEVICE.md, раздел 4). Драйвер:

- не пишет в `DRIVER_PROTOCOL` и другие регистры ревизии 2;
- работает без событий и без списка режимов устройства: режимы выбирает ОС в пределах `MAX_WIDTH × MAX_HEIGHT` и `FORMATS`, смена разрешения по запросу host недоступна;
- либо отказывается загружаться — выбор драйвера; его фиксирует S10-21/S10-22.

## 4. Список режимов

Список — режимы, которые устройство рекомендует показать ОС. Он лежит в окне регистров как таблица только для чтения, `MODE_TABLE`. Чтение не требует включения протокола и не меняет состояния устройства:

1. `n ← MODE_COUNT` (`0x110`). В ревизии 2 `1 ≤ n ≤ 64`.
2. Для `i = 0 … n − 1` запись `i` начинается со смещения `E = 0x400 + 16 × i`:

| Смещение | Поле | Значение |
|---|---|---|
| `E + 0x0` | `width` | ширина в пикселях |
| `E + 0x4` | `height` | высота в пикселях |
| `E + 0x8` | `format` | код формата (`FORMAT`) |
| `E + 0xC` | — | резерв, `0` |

Таблица занимает `0x400–0x7FC`: 64 записи по 16 байт. Записи с `i ≥ MODE_COUNT` читаются нулями. Каждое поле — отдельный 32-битный регистр, правила доступа раздела 2.

Свойства, на которые драйвер может опираться:

- Список неизменен всё время жизни экземпляра устройства, reset его не меняет. Повторно читать его не нужно; поколения списка нет. Записи можно читать в любом порядке и из нескольких потоков: скрытого индекса нет.
- Каждая запись проходит проверки `MODE_COMMIT` (DISPLAY_DEVICE.md, раздел 5): размеры в пределах `MAX_*`, кадр помещается в `FB_SIZE`, формат есть в `FORMATS`. Записи не повторяются и упорядочены по возрастанию `(width, height)`.
- **Список не ограничивает `MODE_COMMIT`.** Commit принимает любой размер по правилам ревизии 1, в том числе размер из `MODE_REQUEST`, которого в списке нет. Драйвер добавляет такой размер в набор режимов своей ОС сам.
- Предпочтительного режима список не задаёт. Желаемый host-ом размер приходит только событием `MODE_REQUEST`.

Состав списка ревизии 2 — DISPLAY_DEVICE.md, 14.6.

## 5. События host → гость

### 5.1. Модель

- Устройство держит FIFO-очередь событий ёмкостью `EVENT_CAPACITY` (`0x144`; в ревизии 2 — 16). Host ставит события только между квантами исполнения гостя.
- `EVENT_PENDING` (`0x140`) — число событий в очереди, `0 … EVENT_CAPACITY`. Между двумя чтениями гостя значение может вырасти: host поставил событие. Объединение (раздел 5.4) удаляет одно событие и ставит одно, поэтому число не уменьшает. Без участия гостя `EVENT_PENDING` уменьшается только при reset устройства, который заодно выключает протокол.
- Гость не читает очередь напрямую. Команда `EVENT_POP` (`0x148`) ← `1` переносит голову очереди в **защёлку**: регистры `EVENT_SEQ_LO/HI`, `EVENT_TYPE`, `EVENT_ARG0…3`. Событие при этом удаляется из очереди.
- Защёлку меняют только `EVENT_POP` самого гостя, `DRIVER_PROTOCOL ← 0` и reset устройства. Host её не трогает. Поэтому чтение нескольких регистров защёлки не рвётся, даже если между чтениями прошли кванты и host поставил новые события.
- Потребитель один: драйвер выполняет `EVENT_POP` и чтение защёлки из одного потока или под своей блокировкой. Та же блокировка обязательна для ответа (раздел 6.1). Ответ — три записи, и если поток опроса и путь установки режима ОС — разные потоки, без блокировки чужая запись `RESPONSE_SEQ_*` может вклиниться между ними.

### 5.2. Запись события (защёлка)

| Регистр | Смещение | Поле | Значение |
|---|---|---|---|
| `EVENT_SEQ_LO` | `0x150` | `seq[31:0]` | номер события |
| `EVENT_SEQ_HI` | `0x154` | `seq[63:32]` | |
| `EVENT_TYPE` | `0x158` | `type` | раздел 5.3 |
| `EVENT_ARG0` | `0x160` | `arg0` | по типу |
| `EVENT_ARG1` | `0x164` | `arg1` | по типу |
| `EVENT_ARG2` | `0x168` | `arg2` | по типу |
| `EVENT_ARG3` | `0x16C` | `arg3` | по типу |

Запись — 7 dword = 28 байт. `seq` — 64-битный номер, уникальный за всё время жизни экземпляра устройства: `seq ≥ 1`, строго растёт в порядке постановки, после reset не начинается заново. `seq = 0` и `type = 0` означают «защёлка пуста» (после включения, reset, `DRIVER_PROTOCOL ← 0`). Неиспользуемые аргументы равны `0`.

### 5.3. Типы событий

| `type` | Имя | Объединение | Назначение |
|---|---|---|---|
| `0` | `NONE` | — | защёлка пуста; в очереди не бывает |
| `1` | `MODE_REQUEST` | да, по экрану | host просит установить режим (раздел 6) |
| `2 … 0xFFFF_FFFF` | — | — | зарезервированы |

Устройство ставит только типы, определённые включённой версией протокола. В версии 1 это только `MODE_REQUEST`. Новые типы (подключение экрана S10-15 и т. п.) требуют либо новой версии протокола, либо явного согласия драйвера, которое определит задача, вводящая тип. Неизвестного типа драйвер версии 1 не получит. Если получил — это ошибка устройства: драйвер пропускает событие и пишет диагностику своей ОС.

### 5.4. `MODE_REQUEST`

| Аргумент | Значение |
|---|---|
| `arg0` | ширина в пикселях |
| `arg1` | высота в пикселях |
| `arg2` | код формата (`FORMAT`); в ревизии 2 всегда `1` (`BGRX8888`) |
| `arg3` | индекс экрана; в ревизии 2 всегда `0` (S10-15 определит другие) |

Гарантии устройства (DISPLAY_DEVICE.md, 14.7–14.8):

- Значения проходят проверки `MODE_COMMIT` 2–4: `MODE_COMMIT` с ними не даст `SIZE_NOT_SET`, `UNSUPPORTED_SIZE` или `UNSUPPORTED_FORMAT`.
- **Объединение.** На каждый экран открыт не больше одного запроса: последний поставленный. Новый запрос удаляет из очереди ещё не взятый `MODE_REQUEST` того же экрана и закрывает предыдущий открытый запрос как вытесненный. Поэтому в очереди не больше одного `MODE_REQUEST` на экран, и последовательная смена размера окна не порождает в госте цепочку промежуточных режимов.
- Запрос, уже взятый в защёлку, из защёлки не исчезает, но может быть вытеснен. Ответ на вытесненный запрос отвергается кодом `STALE_REQUEST`; к тому моменту в очереди уже лежит новый.
- События других типов не теряются: при полной очереди устройство отказывает host-у в постановке, а не удаляет старые события (DISPLAY_DEVICE.md, 14.7). В версии 1 других типов нет.

## 6. Ответ на `MODE_REQUEST`

### 6.1. Кодирование

Ответ — три записи:

1. `RESPONSE_SEQ_LO` (`0x180`) ← `seq[31:0]` запроса;
2. `RESPONSE_SEQ_HI` (`0x184`) ← `seq[63:32]`;
3. `REQUEST_RESPONSE` (`0x188`) ← значение ответа.

`RESPONSE_SEQ_LO/HI` хранят записанное как есть. Команду выполняет только запись в `REQUEST_RESPONSE`.

Три записи и следующее за ними чтение `EVENT_STATUS.RESPONSE_ERROR` драйвер выполняет под той же блокировкой, что `EVENT_POP` и чтение защёлки (раздел 5.1). Блокировку берут и поток опроса, и путь установки режима ОС, из которого обычно пишется `ACCEPT`. Иначе второй поток может переписать `RESPONSE_SEQ_*` между записями первого, и ответ уйдёт с чужим `seq`.

Значение `REQUEST_RESPONSE`:

| Биты | Поле | Значение |
|---|---|---|
| 7:0 | `verdict` | `1` — `ACCEPT`, `2` — `REJECT`; остальные — зарезервированы |
| 15:8 | `reason` | при `ACCEPT` — `0`; при `REJECT` — код причины ниже |
| 31:16 | — | должны быть `0` |

| `reason` | Имя | Когда драйвер его выбирает |
|---|---|---|
| `0x01` | `UNSUPPORTED` | ОС или драйвер не может использовать такой режим |
| `0x02` | `DECLINED` | режим допустим, но политика гостя его не меняет (например, пользователь закрепил разрешение) |
| `0x03` | `FAILED` | смену начали, но она не удалась (в том числе `MODE_COMMIT` вернул ошибку) |

Остальные значения `reason` зарезервированы. Ответ с неверным кодированием отвергается кодом `INVALID_COMMAND`. Примеры: `0x0000_0001` — принять; `0x0000_0102` — отклонить, `UNSUPPORTED`; `0x0000_0302` — отклонить, `FAILED`.

### 6.2. Последовательность

1. Драйвер берёт `MODE_REQUEST` в защёлку и копирует `seq`, `arg0…3` в свою память.
2. Передаёт запрос ОС способом, принятым в ней (S10-21/S10-22).
3. **Принять:** ОС устанавливает режим. Драйвер выполняет путь ревизии 1: `WIDTH ← arg0`, `HEIGHT ← arg1`, `FORMAT ← arg2`, `MODE_COMMIT ← 1`, проверка `STATUS.COMMIT_ERROR = 0x00`. Затем пишет ответ `ACCEPT`. Устройство принимает `ACCEPT` только если активный режим уже равен запрошенному (`MODE_MISMATCH` иначе). Поэтому `ACCEPT` означает «режим установлен», а не «попробую». Если запрошенный режим уже активен, commit не нужен. Затем драйвер рисует кадр и звонит `FRAME_GENERATION`, как в ревизии 1.
4. **Отклонить:** ответ `REJECT` с причиной. Режим не меняется.
5. После записи ответа драйвер читает `EVENT_STATUS.RESPONSE_ERROR` (биты 15:8):
   - `0x00` — ответ принят;
   - `STALE_REQUEST` — запрос закрыт без ответа гостя:
     - **вытеснен** новым запросом: новый уже в очереди, драйвер ничего не делает и получит его при опросе;
     - **отменён** (`DRIVER_PROTOCOL ← 0` или reset устройства): очередь пуста, нового запроса нет; при reset драйвер повторяет раздел 3 (раздел 7.1, шаг 1);
   - `MODE_MISMATCH` — драйвер ответил `ACCEPT`, не установив режим; это ошибка драйвера;
   - `INVALID_COMMAND`, `NOT_ENABLED` — ошибка драйвера.

Драйвер обрабатывает только последний полученный запрос. Если во время обработки он взял новый `MODE_REQUEST`, старый он бросает без ответа. Ответ на старый всё равно дал бы `STALE_REQUEST`.

Ответ не обязан приходить за ограниченное время: устройство таймеров не имеет и запрос сам не закрывает. Драйвер отвечает сразу, как только ОС установила режим или отказалась. Если ОС требует подтверждения пользователя, ответ откладывается до него. Как долго host ждёт ответа — раздел 7.2.

## 7. Опрос

### 7.1. Обязанности драйвера

Прерываний у устройства нет: `IRQ_*` зарезервированы (DISPLAY_DEVICE.md, раздел 4), MSI нет до S10-12. Драйвер узнаёт о событиях **только опросом** `EVENT_PENDING`.

| Параметр | Значение |
|---|---|
| Номинальный период опроса `P` | **100 мс** |
| Наибольший интервал между двумя опросами в установившемся режиме | 200 мс (`P` плюс задержки планировщика гостя); не включает время, когда гость приостановлен или не исполняется |
| Наименьший интервал вне выборки | 10 мс |
| Выборка | при `EVENT_PENDING > 0` драйвер сразу повторяет `EVENT_POP`, проверку `POP_ERROR`, чтение защёлки, обработку, затем перечитывает `EVENT_PENDING` и продолжает, пока не получит `0`. Это не нарушает нижнюю границу |

Шаг опроса:

1. Прочитать `DRIVER_PROTOCOL`. При `0` устройство сброшено (раздел 8): протокол выключен, режим снят, `EVENT_PENDING` навсегда `0`. Драйвер сообщает ОС о потере режима и повторяет раздел 3, в том числе установку режима (шаг 8). Продолжить опрос по `EVENT_PENDING` в этом случае нельзя: драйвер молча потерял бы и события, и режим.
2. Прочитать `EVENT_PENDING`. При `0` — ждать до следующего периода.
3. `EVENT_POP ← 1`, прочитать `EVENT_STATUS.POP_ERROR` (биты 7:0):
   - `0x00` — прочитать защёлку и обработать событие;
   - `QUEUE_EMPTY` — очередь пуста, драйвер вызвал `EVENT_POP` без события; защёлка не изменилась, продолжить с шага 1;
   - `NOT_ENABLED` — протокол выключен reset-ом устройства; перейти к шагу 1 (он повторит раздел 3);
   - `INVALID_COMMAND` — ошибка драйвера.
4. Перейти к шагу 1.

Шаг 1 — второе 32-битное MMIO-чтение на период. Reset устройства — host-операция, его не видно ни по какому другому регистру протокола. `STATUS.ACTIVE = 0` тоже признак, но он не отличает reset от состояния до первого commit.

Почему 100 мс: смена режима — редкое событие, вызванное человеком. Задержка до 200 мс плюс время установки режима в ОС остаётся в пределах, которые пользователь воспринимает как реакцию на отпускание края окна. Один опрос без событий — два 32-битных MMIO-чтения (`DRIVER_PROTOCOL`, `EVENT_PENDING`), 20 чтений в секунду. **Это гипотеза до замера** (правило «Решения в критичных по производительности участках» в корневом `AGENTS.md`): задержка «resize → новый кадр гостя» и CPU простаивающего гостя измеряются в S10-21/S10-22, и период уточняется по результату. Менять период без замера нельзя.

### 7.2. Что host не может предполагать

- Host не зависит от периода ради корректности: он не рассчитывает, что событие взято за `P`.
- Host показывает запрос как ожидающий, пока устройство не сообщит ответ. Рекомендация для UI (не часть wire format): через **5 с** без ответа (25 номинальных периодов плюс время установки режима ОС) показывать кадр гостя масштабированным, как в S10-11, не снимая запроса. Поздний ответ всё ещё принимается.
- Пока `DRIVER_PROTOCOL = 0`, host запросов не ставит (их отвергает устройство) и только масштабирует кадр.

## 8. Остановка и повторная инициализация

- Перед выгрузкой драйвер пишет `DRIVER_PROTOCOL ← 0`. Очередь и защёлка очищаются, открытый запрос закрывается как отменённый. Режим и framebuffer не меняются: последний кадр остаётся у host.
- Драйвер, запускающийся после аварийного завершения прежнего экземпляра, начинает с `DRIVER_PROTOCOL ← 0` (раздел 3, шаг 5). Запись `1` при уже включённом протоколе состояния не меняет, и без шага 5 драйвер получил бы старые события.
- Reset устройства (host-операция) выключает протокол так же, как `DRIVER_PROTOCOL ← 0`, и дополнительно снимает режим (DISPLAY_DEVICE.md, разделы 10 и 14.12). Драйвер обнаруживает reset в каждом шаге опроса по `DRIVER_PROTOCOL = 0` (раздел 7.1, шаг 1), считает устройство сброшенным и повторяет раздел 3, включая установку режима. Иначе после reset `EVENT_PENDING` остаётся `0` навсегда, и драйвер ждал бы событий, которых не будет, без режима на экране.

## 9. Ошибки

**Исправимые гостем.** Доступ завершается успешно, результат виден в регистрах. Коды — общая таблица DISPLAY_DEVICE.md (4.1 и 14.10). Каждое поле `EVENT_STATUS` перезаписывает только своя команда:

| Команда | Поле | Возможные коды |
|---|---|---|
| `DRIVER_PROTOCOL ← v` | `PROTOCOL_ERROR` (23:16) | `NONE`, `UNSUPPORTED_PROTOCOL` |
| `EVENT_POP ← v` | `POP_ERROR` (7:0) | `NONE`, `INVALID_COMMAND`, `NOT_ENABLED`, `QUEUE_EMPTY` |
| `REQUEST_RESPONSE ← v` | `RESPONSE_ERROR` (15:8) | `NONE`, `INVALID_COMMAND`, `NOT_ENABLED`, `STALE_REQUEST`, `MODE_MISMATCH` |
| `MODE_COMMIT ← v` | `STATUS.COMMIT_ERROR` | как в ревизии 1 |

**Backend-ошибки** — доступ не 32-битной ширины, невыровненный, через PIO, за пределами окна (DISPLAY_DEVICE.md, 9.2). Они останавливают квант машины. Гость их не получает, и протокол не даёт способа их обработать. Корректный драйвер их не вызывает.

## 10. Совместимость и версии

- **Драйвер ↔ ревизия устройства.** Драйвер проверяет `VERSION ≥` нужной ревизии и биты `CAPS` нужных блоков, не равенство. Неизвестные биты `CAPS` и `DRIVER_PROTOCOLS` игнорирует. В регистры, не определённые в нужной ему ревизии, не пишет.
- **Гость ревизии 1** (probe S10-08 и любой код, знающий только ревизию 1) на устройстве ревизии 2 видит поведение ревизии 1. Отличаются только значения `VERSION` и `CAPS`, а смещения `0x100–0x1FC` и `0x400–0x7FC`, зарезервированные в ревизии 1, больше не все читаются нулями. Правило — DISPLAY_DEVICE.md, 14.2.
- **Новая версия протокола** (например, с прерываниями после S10-12) получает новый бит в `DRIVER_PROTOCOLS` и новое значение `DRIVER_PROTOCOL`. Устройство, поддерживающее несколько версий, ведёт себя по той, которую включил драйвер. Версия 1 остаётся рабочей, пока её бит есть в `DRIVER_PROTOCOLS`; опрос остаётся допустимым и при наличии прерываний.
- **Блоки курсора и второго экрана.** Биты `CAPS` 2 (`CURSOR`, S10-14, DISPLAY_DEVICE.md раздел 15) и 3 (`SECOND_SCREEN`, S10-15, раздел 16, ниже 10a) — опциональные блоки внутри ревизии 2: `0x200–0x2FC` при бите 2, `0x300–0x3FC` при бите 3 (он выставлен только в конфигурации с двумя экранами). Без своего бита блок — резерв: чтение `0`, запись игнорируется. Драйвер проверяет бит перед использованием блока и без бита в блок не пишет. События экрана 1 не существуют (16.8); `MODE_REQUEST` с `arg3 = 1` определит S10-23.

## 10a. Второй экран (S10-15, DISPLAY_DEVICE.md 16)

Существует только при `CAPS` бит 3 (`SECOND_SCREEN`). Драйвер обслуживает оба экрана одним кодом с базой `0x000` (экран 0) или `0x300` (экран 1) по правилу зеркала (16.4): `WIDTH`, `HEIGHT`, `FORMAT`, `MODE_COMMIT`, `STATUS`, `FRAME_GENERATION` и активный режим — со смещением базы. Отличия экрана 1:

- `MODE_COMMIT` принимает `2` — отключить экран (16.6). Экран 0 отключить нельзя.
- Отключённый экран (`STATUS.DISABLED = 1`) не принимает doorbell: `FRAME_ERROR = NO_ACTIVE_MODE`. Драйвер переводит экран в «выключен» и перестаёт рисовать; включение — обычный `MODE_COMMIT ← 1`.
- Событий и `MODE_REQUEST` для экрана 1 нет (16.8). Драйвер экрана 1 согласует размер окна отдельно (S10-23), здесь не описано.
- Курсора у экрана 1 нет: при уходе указателя на экран 1 драйвер скрывает аппаратный курсор экрана 0 (`CURSOR_ENABLE ← 0`) и рисует курсор в кадре экрана 1 программно.

Последовательность для экрана 1 (база `0x300`): проверить `CAPS` бит 3; записать `WIDTH`, `HEIGHT`, `FORMAT`; `MODE_COMMIT ← 1`; при ненулевом `COMMIT_ERROR` — ошибка, режим не изменён; записать пиксели в `S1_FB_BASE`; `FRAME_GENERATION` (doorbell). Для отключения: `MODE_COMMIT ← 2`. Порядок опроса событий (раздел 7) к экрану 1 не относится.

**Повторная инициализация после reset (DISPLAY_DEVICE.md 16.9, 16.16 п. 2).** Reset устройства снимает режим обоих экранов: экран 1 возвращается в `NO_MODE` (в том числе из `DISABLED`), `S1_WIDTH`, `S1_HEIGHT`, `S1_FORMAT` и `S1_STATUS` — к значениям после reset, устройство режим не восстанавливает, `generation_1` и память экрана 1 сохраняются. Драйвер узнаёт о reset шагом 1 опроса (раздел 7.1): `DRIVER_PROTOCOL = 0` (раздел 8). После `DRIVER_PROTOCOL = 0` драйвер повторяет раздел 3 для экрана 0, включая установку режима (шаг 8), и ставит режим экрана 1 заново по последовательности выше: `WIDTH`, `HEIGHT`, `FORMAT`, `MODE_COMMIT ← 1`, пиксели, doorbell. Если ОС держит экран 1 выключенным, драйвер повторяет `MODE_COMMIT ← 2`: отключение reset не переживает. Пока драйвер не поставил режим, host показывает окно экрана 1 как «нет сигнала».

Драйвер, который не знает бита 3, в блок не пишет (14.2) и экран 1 не видит.

## 11. Открытые вопросы

1. **Путь запроса от окна до устройства.** Не задано, как UI передаёт желаемый размер окна в VMHost (обратное сообщение `ODFT`, control v1 или отдельный канал) и как VMHost вызывает host API устройства через `od-host` (новая функция C ABI `display_abi_v1.h`). Это host-сторона S10-21/S10-23. Задача S10-13 даёт только API `od-machine`.
2. **Период опроса 100 мс** — гипотеза до замеров S10-21/S10-22 (раздел 7.1).
3. **Как ОС узнаёт о новом режиме** (DRM hotplug в Linux, повторное перечисление режимов в WDDM KMDOD) — по документации ОС через Context7 в S10-21/S10-22; протокол на это не опирается.
4. **Нужен ли host-у debounce** запросов при живом resize. Объединение в устройстве делает его ненужным для корректности, но гость может успеть установить промежуточный режим. Решить по замеру в S10-21/S10-23.
