# Frame transport v1: кадры VMHost → UI

**Статус:** нормативная спецификация задачи S10-05 [плана этапа 10](../../docs/plans/STAGE_10.md#s10-05-специфицировать-транспорт-кадров-vmhost--ui), **ожидает ревью**. Реализации нет: writer — S10-06 (VMHost), reader — S10-07 (UI-просмотрщик). Слова ДОЛЖЕН, НЕ ДОЛЖЕН и МОЖЕТ — требования протокола. Нарушение требования другой стороной — ошибка протокола (раздел 8), а не повод для догадки.

Документ — единственный источник байтов разделяемой памяти кадров и сообщений этого канала. [Control protocol v1](CONTROL_PROTOCOL_V1.md) и [v0](CONTROL_PROTOCOL_V0.md) этим документом не меняются: ни их кадры, ни виды сообщений, ни профиль READY. Устройство, чьи кадры передаются, — [DISPLAY_DEVICE.md](../../docs/specs/DISPLAY_DEVICE.md); VMHost получает кадр из `od-host` через [display host ABI v1](../../docs/specs/DISPLAY_HOST_ABI_V1.md) ([`display_abi_v1.h`](../../include/open_desktop/display_abi_v1.h)).

Пиксели по сокету не передаются. Сокет несёт только дескриптор памяти и маленькие уведомления.

## 1. Обзор

- Writer (VMHost) создаёт объект разделяемой памяти: заголовок, блок reader-а, описатели слотов, данные слотов. Слотов от 2 до 4; для гипотезы этапа рекомендуется 3 (раздел 3.4).
- Дескриптор памяти передаётся reader-у (UI) один раз сообщением `ANNOUNCE` с `SCM_RIGHTS` по унаследованному `socketpair`. Путь или имя объекта не передаются никогда.
- Writer пишет кадр в слот, который reader не читает, и публикует его одной атомарной записью `generation` с семантикой release. Затем отправляет `FRAME` с номером слота и `generation`.
- Reader копирует слот и перепроверяет `generation` (seqlock). Если значение изменилось, кадр отбрасывается и не показывается. Потеря кадра допустима, смесь двух кадров — нет.
- Смена режима устройства передаётся сообщением `MODE`. Его состояние reader показывает явно (раздел 7).

## 2. Топология процессов и канал

1. UI-процесс (на этапе 10 — просмотрщик S10-07) запускает VMHost тем же кодом, что [launcher.swift](../../apps/macos/Sources/launcher.swift): `socketpair(AF_UNIX, SOCK_STREAM, 0)`, `SO_NOSIGPIPE` на обоих концах, `posix_spawn` с `adddup2` конца VMHost на дескриптор 3 и закрытием остальных концов в потомке. Аргументы: `--socket-fd 3` и флаг дисплейного режима (имя флага задаёт S10-06, например `--display-smoke pattern`). UI закрывает свою копию конца VMHost после spawn.
2. Соединение несёт **только** frame transport v1. Протокол выбирает режим запуска VMHost, а не распознавание первых байтов. Кадр control v0/v1 (magic `ODCP`) на этом соединении — ошибка протокола. VMHost в обычном control-режиме, получив `HELLO` с magic `ODFT`, закрывает соединение как при любой ошибке framing control v1. Поэтому неверный запуск обнаруживается по EOF, а не по зависанию.
3. Когда VMHost будет одновременно обслуживать control и дисплей, frame transport получит отдельный унаследованный `socketpair` с номером дескриптора из аргумента запуска. Формат этого документа от номера дескриптора не зависит.
4. Владение: UI владеет процессом VMHost. Политика остановки потомка та же, что у launcher в control v1 (SIGTERM, ожидание до 500 мс, SIGKILL, reap) — см. раздел «EOF, teardown and failures» [CONTROL_PROTOCOL_V1.md](CONTROL_PROTOCOL_V1.md#eof-teardown-and-failures). Перезапуск VMHost (S10-24) — новый процесс, новый `socketpair` и новая память. Состояние reader-а начинается заново, а `generation` и `mode_change_count` нового VMHost не сравниваются со значениями прежнего.

### 2.1. Кто создаёт память: VMHost

Память создаёт VMHost (writer). Причины:

- Раскладку (число слотов, размер слота, максимальный режим) определяет writer по своему устройству. Если бы память создавал reader, раскладку пришлось бы согласовывать отдельным сообщением.
- Время жизни памяти совпадает с экземпляром VMHost. Новый VMHost не наследует слоты и блок reader-а, наполовину записанные упавшим предшественником, и ему не нужно доверять их содержимому.
- Ресурс относится к процессу VM. Будущий VMHost, запущенный не этим UI, отдаёт память тем же сообщением.

Отвергнутый вариант: UI создаёт память и передаёт её при `posix_spawn` как дескриптор 4. Он проще, `SCM_RIGHTS` не нужен, но память переживает VMHost, а раскладку всё равно задаёт VMHost.

### 2.2. Создание памяти (writer)

Writer ДОЛЖЕН выполнить шаги 1–7 до отправки `ANNOUNCE`:

1. Имя: `/odft.` + 16 шестнадцатеричных цифр из `arc4random_buf` (22 символа, в пределах лимита имени POSIX shm на macOS). Имя никому не передаётся.
2. `shm_open(name, O_RDWR | O_CREAT | O_EXCL, 0600)`. При `EEXIST` — новое имя, не более 8 попыток. Любая другая ошибка или исчерпание попыток — отказ хоста: VMHost закрывает соединение.
3. Сразу `shm_unlink(name)`. Ошибка — `close` и отказ хоста. После этого шага объект доступен только по дескриптору.
4. Один вызов `ftruncate(fd, total_size)`. Повторное изменение размера в v1 запрещено обеим сторонам: reader НЕ ДОЛЖЕН вызывать `ftruncate` на принятом дескрипторе. Что будет, если writer нарушит запрет, — раздел 8.3.
5. Установить `FD_CLOEXEC` на дескриптор: другие дочерние процессы VMHost не наследуют память.
6. `mmap(NULL, total_size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0)`.
7. Заполнить заголовок (раздел 3.1). Блок reader-а, описатели и данные остаются нулями от `ftruncate`; writer их не трогает. Выполнить `fence(release)`. Видимость заголовка reader-у обеспечивает допущение раздела 5.4.

После успешной отправки `ANNOUNCE` writer МОЖЕТ закрыть свой дескриптор: отображение остаётся. Закрывать дескриптор до возврата из `sendmsg` нельзя.

## 3. Разделяемая память

Все числа — беззнаковые little-endian фиксированной ширины. Каждое поле выровнено на свой размер; неявного padding нет. Смещения отсчитываются от начала объекта; отображение начинается на границе страницы, поэтому выравнивание смещения — выравнивание адреса. Гранула раскладки — `16384` байт (host page на поддержанном macOS ARM64, [SUPPORT_MATRIX.md](../../docs/specs/SUPPORT_MATRIX.md)). Если `getpagesize()` не делит `16384`, хост не поддержан: reader и writer отказываются до создания или отображения памяти.

| Смещение | Размер | Область | Пишет |
|---:|---:|---|---|
| 0 | 64 | Заголовок (3.1) | writer, один раз до `ANNOUNCE` |
| 64 | 64 | Блок reader-а (3.2) | только reader |
| 128 | 64 × `slot_count` (до 256) | Описатели слотов (3.3) | только writer |
| 128 + 64 × `slot_count` | до 16384 | Резерв, нули | никто |
| 16384 | `slot_size` × `slot_count` | Данные слотов (3.4) | только writer |

Первые 16384 байт — «страница заголовка». Данные слотов начинаются на границе 16 KiB, и каждый слот кратен 16 KiB. Reader отображает страницу заголовка на чтение и запись, а данные слотов — только на чтение (раздел 4.2).

### 3.1. Заголовок (64 байта)

| Смещение | Размер | Поле | Значение v1 |
|---:|---:|---|---|
| 0 | 4 | `magic` | ASCII `ODFS` (`4f 44 46 53`) |
| 4 | 2 | `version` | `1` |
| 6 | 2 | `header_size` | `64` |
| 8 | 4 | `reader_block_offset` | `64` |
| 12 | 4 | `descriptors_offset` | `128` |
| 16 | 4 | `descriptor_size` | `64` |
| 20 | 4 | `slot_count` | `2…4` |
| 24 | 4 | `slots_offset` | `16384` |
| 28 | 4 | `slot_size` | кратно `16384`; `max_width × 4 × max_height ≤ slot_size ≤ 37 748 736` |
| 32 | 4 | `pixel_format` | `1` = `BGRX8888` |
| 36 | 4 | `max_width` | `1…4096` |
| 40 | 4 | `max_height` | `1…2304` |
| 44 | 4 | `flags` | `0` |
| 48 | 8 | `total_size` | `slots_offset + slot_count × slot_size` |
| 56 | 8 | `reserved` | `0` |

- Фиксированные смещения и размеры записаны явно, чтобы reader проверил, что раскладка та, которую он знает. Это не механизм расширения: другое значение — несовместимость (раздел 8).
- `pixel_format` использует нумерацию `FORMAT` из [DISPLAY_DEVICE.md](../../docs/specs/DISPLAY_DEVICE.md) и `OD_DISPLAY_FORMAT_BGRX8888` из `display_abi_v1.h`. В памяти пиксель занимает 4 байта: B, G, R, X. Байт X не определён, reader не трактует его как альфу.
- `max_width`/`max_height` ограничивают каждый режим, который writer может опубликовать. Writer дисплейного устройства, способного менять режим, объявляет предел устройства `4096 × 2304`. Test-only writer с фиксированным режимом (профиль `OD_DISPLAY_PROFILE_TEST_PATTERN`, 64×48) МОЖЕТ объявить свой режим. Режим больше объявленного опубликовать нельзя (раздел 6.3).
- Writer НЕ ДОЛЖЕН менять заголовок после отправки `ANNOUNCE`. Reader проверяет заголовок один раз (раздел 4.2) и дальше пользуется своей частной копией проверенных значений; повторно читать заголовок из памяти ему не нужно.

### 3.2. Блок reader-а (64 байта, смещение 64)

| Смещение | Размер | Поле | Значение |
|---:|---:|---|---|
| 64 | 4 | `reader_claim` | `0` — reader не держит слот; `k + 1` — reader читает слот `k` |
| 68 | 60 | `reserved` | reader пишет нули; writer не читает |

`reader_claim` — атомарное 32-битное слово (раздел 5). Это подсказка writer-у, а не блокировка: корректность чтения обеспечивает только перепроверка `generation`. Writer читает из памяти только это слово и считает его недоверенным вводом: значение `0` или больше `slot_count` означает «reader ничего не держит».

### 3.3. Описатель слота (64 байта)

Описатель слота `i` находится по смещению `128 + 64 × i`.

| Смещение в описателе | Размер | Поле | Значение |
|---:|---:|---|---|
| 0 | 8 | `generation` | `0` — слот недействителен (пуст или пишется); иначе — опубликованное поколение кадра устройства. Атомарное слово публикации |
| 8 | 8 | `mode_change_count` | `mode_change_count` устройства для этого кадра |
| 16 | 4 | `width` | `1…max_width` |
| 20 | 4 | `height` | `1…max_height` |
| 24 | 4 | `stride` | ровно `width × 4` |
| 28 | 4 | `format` | равен `pixel_format` заголовка |
| 32 | 4 | `state` | `0` = `EMPTY` (публикаций не было), `1` = `READY` |
| 36 | 4 | `reserved0` | `0` |
| 40 | 24 | `reserved1` | нули |

- `generation` и `mode_change_count` — значения `od_display_frame_info` того чтения, которое записало пиксели, без преобразований ([DISPLAY_DEVICE.md](../../docs/specs/DISPLAY_DEVICE.md), раздел 8). Поколение кадра устройства всегда больше 0, поэтому `0` свободно как метка «недействителен».
- Поля 8…63 действительны только для успешно перепроверенного чтения (раздел 5.2). Для такого чтения `state` ДОЛЖЕН быть `READY`. `EMPTY` при ненулевом `generation`, неизвестное `state` и ненулевые reserved — ошибка протокола. Другие значения `state` в v1 не определены.

### 3.4. Данные слотов

Слот `i` начинается по смещению `16384 + i × slot_size`. Кадр занимает первые `stride × height` байт слота: строка `r` начинается с байта `r × stride`. Остаток слота не определён и не читается.

Число слотов — гипотеза, решение о нём принимается по замерам S10-10. Двух слотов достаточно для корректности: writer тогда пропускает публикацию, пока reader держит единственный свободный слот (раздел 6.2). Три слота — рекомендация: при `reader_claim` на старом кадре и новом опубликованном кадре у writer-а остаётся третий слот. Четыре слота — верхняя граница v1.

### 3.5. Размеры и проверка переполнения

`FRAME_MAX = 4096 × 4 × 2304 = 37 748 736 = 0x0240_0000` (36 MiB, равен `FB_SIZE` устройства, кратен 16384: `2304 × 16384`).

| Конфигурация | `slot_size` | Смещения слотов | `total_size` |
|---|---:|---|---:|
| 64×48, 3 слота (test pattern, кадр 12 288 байт) | 16 384 | 16 384; 32 768; 49 152 | 65 536 (`0x0001_0000`) |
| 4096×2304, 2 слота | 37 748 736 | `0x0000_4000`; `0x0240_4000` | 75 513 856 (`0x0480_4000`) |
| 4096×2304, 3 слота (рекомендация) | 37 748 736 | `0x0000_4000`; `0x0240_4000`; `0x0480_4000` | 113 262 592 (`0x06C0_4000`) |
| 4096×2304, 4 слота (максимум v1) | 37 748 736 | `0x0000_4000`; `0x0240_4000`; `0x0480_4000`; `0x06C0_4000` | 151 011 328 (`0x0900_4000`) |

- `MIN_TOTAL = 16384 + 2 × 16384 = 49 152`, `MAX_TOTAL = 16384 + 4 × 37 748 736 = 151 011 328`.
- 32-битные поля: `slot_size ≤ 0x0240_0000`; `slots_offset = 0x4000`; смещение последнего слота `≤ 0x06C0_4000`; `stride ≤ 16 384`; `stride × height ≤ 37 748 736 < 2^26`. Даже `MAX_TOTAL < 2^28` помещается в 32 бита. `total_size` — `u64`, потому что сравнивается с `off_t` из `fstat` и передаётся в `mmap` как `size_t`.
- Порядок проверок без переполнения: сначала диапазоны `slot_count`, `max_width`, `max_height`, затем произведение `max_width × 4 × max_height` (после проверки `< 2^26`), затем `slot_size`, затем `total_size` в `u64`. Для описателя — сначала `width ≤ max_width` и `height ≤ max_height`, потом `stride` и `stride × height`.
- Объём: 3 слота максимального размера — 108 MiB виртуальной памяти на VMHost. Сколько физических страниц занимает объект, когда запись идёт только в первые `stride × height` байт слота, не измерено (S10-10).

## 4. Сообщения

### 4.1. Заголовок сообщения

Все сообщения в обе стороны начинаются с 16-байтного заголовка, за которым идут ровно `payload_length` байт. Числа little-endian, padding нет.

| Смещение | Размер | Поле | Значение |
|---:|---:|---|---|
| 0 | 4 | `magic` | ASCII `ODFT` (`4f 44 46 54`) |
| 4 | 2 | `version` | `1` |
| 6 | 2 | `kind` | из таблицы 4.2 |
| 8 | 4 | `reserved` | `0` |
| 12 | 4 | `payload_length` | ровно длина из таблицы для `kind` |

Инвариант всех версий: байты 0–5 заголовка сообщения — `magic` `ODFT` и `version` (`u16` LE). Будущие версии ДОЛЖНЫ сохранить его, чтобы несовпадение версии распознавалось (раздел 8.1). Остальные поля заголовка при чужой версии не проверяются и не толкуются.

Наибольшее сообщение — `MODE`, 48 байт. Читающая сторона проверяет заголовок до приёма payload и обрабатывает частичные чтения и записи: системный вызов не задаёт границу сообщения. Вход буферизуется в пределах одного наибольшего сообщения.

### 4.2. Виды

| `kind` | Имя | Направление | Payload | Дескриптор | Когда |
|---:|---|---|---:|---|---|
| 0 | `VERSION` | VMHost → UI | 0 | нет | только ответ на `HELLO` с чужой версией, затем VMHost закрывает соединение (8.1). Заголовок несёт версию VMHost. Для UI v1 `VERSION` с `version = 1` — ошибка протокола |
| 1 | `HELLO` | UI → VMHost | 0 | нет | первое и единственное сообщение UI |
| 2 | `ANNOUNCE` | VMHost → UI | 16 | ровно один, `SCM_RIGHTS` | первое сообщение VMHost, ровно один раз, после `HELLO` |
| 3 | `MODE` | VMHost → UI | 32 | нет | сразу после `ANNOUNCE`, затем при каждом изменении `mode_change_count` |
| 4 | `FRAME` | VMHost → UI | 24 | нет | после каждой публикации слота |

Других видов в v1 нет. После `HELLO` UI ничего не отправляет: любые следующие байты от UI — ошибка протокола для VMHost. VMHost следит за чтением сокета, чтобы заметить EOF.

**`ANNOUNCE` (16 байт)**

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 8 | `total_size` — равен `total_size` заголовка памяти |
| 8 | 4 | `slot_count` — равен `slot_count` заголовка памяти |
| 12 | 4 | `reserved = 0` |

**`MODE` (32 байта)** — текущий режим устройства.

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 8 | `mode_change_count` |
| 8 | 4 | `flags`: бит 0 `ACTIVE` (режим установлен); остальные биты 0 |
| 12 | 4 | `width` |
| 16 | 4 | `height` |
| 20 | 4 | `stride` |
| 24 | 4 | `format` |
| 28 | 4 | `reserved = 0` |

При `ACTIVE = 0` поля `width`, `height`, `stride` и `format` равны 0: это «нет сигнала». При `ACTIVE = 1` действуют диапазоны описателя (3.3): `1 ≤ width ≤ max_width`, `1 ≤ height ≤ max_height`, `stride = width × 4`, `format = pixel_format`. Источник значений — `od_display_session_mode` (флаг `OD_DISPLAY_MODE_FLAG_ACTIVE`) или `od_display_frame_info` (раздел 6.3). `mode_change_count` строго растёт от одного `MODE` к следующему. Первый `MODE` МОЖЕТ нести любое значение, включая 0. Промежуточные смены режима между двумя `MODE` МОГУТ быть пропущены.

**`FRAME` (24 байта)** — кадр опубликован.

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 8 | `generation` — больше 0, строго растёт от одного `FRAME` к следующему |
| 8 | 8 | `mode_change_count` — равен значению последнего `MODE`, отправленного перед этим `FRAME` |
| 16 | 4 | `slot_index` — меньше `slot_count` |
| 20 | 4 | `reserved = 0` |

Writer отправляет `MODE` со значением `C` раньше любого `FRAME` со значением `C` и не отправляет `FRAME` со значением меньше последнего `MODE`, поставленного в очередь (6.3).

### 4.3. Передача дескриптора

- Writer отправляет `ANNOUNCE` одним `sendmsg`: данные — все 32 байта сообщения (заголовок и payload), ancillary — один `cmsghdr` с `cmsg_level = SOL_SOCKET`, `cmsg_type = SCM_RIGHTS`, `cmsg_len = CMSG_LEN(sizeof(int))` и одним дескриптором.
- Если `sendmsg` вернул `-1` с `EAGAIN`/`EWOULDBLOCK` или `EINTR`, ни один байт и дескриптор не отправлены. Writer дожидается готовности сокета на запись и повторяет **именно `sendmsg` с тем же ancillary**. Обычная запись в этом случае запрещена: она отправила бы `ANNOUNCE` без дескриптора. Другая ошибка `sendmsg` — отказ хоста, соединение закрывается.
- Если `sendmsg` отправил от 1 до 31 байта, дескриптор уже прикреплён к первому байту. Остаток досылается обычной записью без ancillary.
- `ANNOUNCE` не входит в очередь уведомлений (6.4): пока он не отправлен целиком, другие сообщения не отправляются.
- Reader читает соединение **только** через `recvmsg` с буфером ancillary на `CMSG_SPACE(sizeof(int))`, чтобы заметить любой неожиданный дескриптор. `ANNOUNCE` — первое сообщение VMHost, поэтому его первый байт начинает поток, и дескриптор приходит в том `recvmsg`, который вернул первый байт потока. Reader принимает дескриптор только в этом случае.
- Ошибки протокола: `MSG_CTRUNC`; другие `cmsg_level`/`cmsg_type`; больше одного дескриптора; дескриптор в любом другом `recvmsg`; отсутствие дескриптора у `ANNOUNCE`; второй `ANNOUNCE`. Любой принятый лишний дескриптор reader немедленно закрывает.
- Принятый дескриптор reader сразу помечает `FD_CLOEXEC` (`fcntl(F_SETFD)`) до любых других действий.

## 5. Атомарность и барьеры

Атомарно, через операции shim (5.3), выполняется каждый доступ к `reader_claim` и к **каждому полю описателя слота**. Поля `u64` выровнены на 8, поля `u32` — на 4. Естественно выровненные 4- и 8-байтные записи и чтения на ARM64 однократно атомарны. Слово публикации — `generation`; остальные поля описателя пишутся и читаются `store_relaxed`/`load_relaxed`. Обычной памятью остаются только пиксели. Их и поля описателя защищает протокол seqlock ниже (C11 fence-based seqlock, H.-J. Boehm, «Can Seqlocks Get Along With Programming Language Memory Models?», MSPC 2012).

Обозначения C11 и их отображение на ARM64:

| Операция | C11 | ARM64 (ожидаемая кодогенерация clang) |
|---|---|---|
| `store_relaxed` | `atomic_store_explicit(…, memory_order_relaxed)` | `STR` |
| `store_release` | `atomic_store_explicit(…, memory_order_release)` | `STLR` |
| `load_relaxed` | `atomic_load_explicit(…, memory_order_relaxed)` | `LDR` |
| `load_acquire` | `atomic_load_explicit(…, memory_order_acquire)` | `LDAR`/`LDAPR` |
| `fence(release)` | `atomic_thread_fence(memory_order_release)` | `DMB ISH` |
| `fence(acquire)` | `atomic_thread_fence(memory_order_acquire)` | `DMB ISHLD` |

### 5.1. Writer: публикация в слот `s`

1. Выбрать `s` по разделу 6.2.
2. `store_relaxed(desc[s].generation, 0)`.
3. `fence(release)`: метка «недействителен» становится видимой раньше любой следующей записи в описатель или пиксели.
4. Записать пиксели в данные слота `s` (S10-06: `od_display_session_read_frame` прямо в слот, длина `stride × height`). Если чтение кадра не удалось (`MODE_CHANGED` и т. п.), остановиться: слот остаётся с `generation = 0`, публикации нет.
5. Проверки до публикации. Пусть `N` и `C` — `generation` и `mode_change_count` из `od_display_frame_info`, а `Q` — `mode_change_count` последнего `MODE`, **поставленного в очередь** (6.3). Если `N` не больше последнего опубликованного writer-ом поколения или `C < Q`, остановиться: слот остаётся с `generation = 0`, публикации и `FRAME` нет. Если `C > Q`, поставить в очередь `MODE`, построенный из этого `frame_info` (`ACTIVE = 1`).
6. Записать в описатель `store_relaxed` по одному на поле: `mode_change_count`, `width`, `height`, `stride`, `format`, `state = READY` и нулевые reserved. Значения берутся из того же `od_display_frame_info`.
7. `store_release(desc[s].generation, N)`.
8. Поставить в очередь `FRAME { N, C, s }` (раздел 6.4). Запись в сокет выполняется после шага 7.

Начальное заполнение памяти (раздел 2.2, шаг 7) завершается `fence(release)` до `sendmsg(ANNOUNCE)`. Writer никогда не читает из памяти описатели и заголовок: его состояние (последний опубликованный слот и поколение) хранится в частной памяти.

### 5.2. Reader: чтение слота `s`, объявленного `FRAME { N, C, s }`

1. `store_relaxed(reader_claim, s + 1)`.
2. `g1 = load_acquire(desc[s].generation)`. Если `g1 ≠ N`, перейти к шагу 7 и отбросить кадр (слот уже переписан или пишется).
3. Прочитать каждое поле описателя 8…63 **ровно один раз** через `load_relaxed` (`u64` или `u32` shim) в локальную переменную. Все проверки шага 4, вычисление длины и копирование шага 5 используют только эти локальные копии; повторно читать поле из памяти запрещено. Без этого правила чтение — гонка данных, а недоверенный writer может изменить поле между проверкой и использованием (TOCTOU), например увеличить `height` после проверки границ.
4. Проверить локальные значения: `width ≤ max_width`, `height ≤ max_height` (до умножения), `stride = width × 4`, `stride × height ≤ slot_size`, `format = pixel_format`, `state = READY`, reserved = 0, `mode_change_count = C`, режим равен последнему принятому `MODE`. Если проверка не прошла, пиксели не копировать, выполнить шаги 6–7. Если `g2 = g1`, это ошибка протокола, иначе — отброшенный кадр.
5. Скопировать `stride × height` байт слота (по локальным значениям шага 3) в частный буфер reader-а (`memcpy`, `MTLTexture.replace(region:…withBytes:…)` и т. п.). Скопированное НЕ ДОЛЖНО показываться до шага 6. Если копия идёт прямо в texture, у reader-а должна быть другая texture с последним показанным кадром.
6. `fence(acquire)`, затем `g2 = load_relaxed(desc[s].generation)`. Если `g2 ≠ g1`, кадр отбрасывается.
7. `store_relaxed(reader_claim, 0)`.

Кадр годен только при `g1 = g2 = N` и успешной проверке шага 4. Почему этого достаточно: если хотя бы одно чтение шага 3 или 5 увидело запись, сделанную writer-ом после шага 3 раздела 5.1, то `fence(acquire)` reader-а синхронизируется с `fence(release)` writer-а, и `g2` видит `0` или новое `N' > N`. ABA исключено: опубликованные поколения строго растут и никогда не повторяются, `0` никогда не публикуется.

Поля описателя гонки не образуют: они атомарны (relaxed). Обычные чтения пикселей, которые параллельно пишет другой процесс, — формально гонка данных в модели C11 и Swift. Протокол её допускает только потому, что результат такого чтения отбрасывается, а не используется. Длина и границы копии берутся из локальных копий, уже проверенных на шаге 4, поэтому никакое поведение writer-а не выводит чтение за пределы слота.

### 5.3. Swift

Swift-реализации writer-а и reader-а ДОЛЖНЫ выполнять операции раздела 5 через маленький C-shim: `static inline` функции в заголовке, который Swift импортирует через `-import-objc-header`, как сейчас `VMHostABI.h`. Функции принимают обычные указатели (`uint64_t *`, `uint32_t *`) и используют встроенные функции clang `__atomic_load_n`, `__atomic_store_n`, `__atomic_thread_fence` с `__ATOMIC_ACQUIRE`/`__ATOMIC_RELEASE`/`__ATOMIC_RELAXED`. Типы `_Atomic` в сигнатурах не используются, потому что Swift их не импортирует. Нужный набор: `load_relaxed`/`store_relaxed` для `u32` и `u64`, `load_acquire` и `store_release` для `u64`, оба вида `fence`.

- Почему не `Synchronization.Atomic`: этот тип владеет своим хранилищем и не создаётся поверх адреса в чужом отображении. Пакет `swift-atomics` — внешняя зависимость без необходимости. Если S10-06 выберет другой способ, он должен давать те же операции и быть оформлен по [политике зависимостей](../../docs/policies/DEPENDENCIES.md).
- Один заголовок shim используют обе сборки (VMHost и UI), без копии. Где он лежит, решает S10-06 по [PROJECT_LAYOUT.md](../../docs/PROJECT_LAYOUT.md). Это внутренний заголовок приложений, не публичный ABI `include/`.
- Отображение на инструкции из таблицы раздела 5 — ожидание. Подтверждается дизассемблированием в S10-06, а не названием функции.

### 5.4. Допущение: порядок через системный вызов

Два места протокола опираются на порядок между записью в память и сообщением в сокете:

- writer: `fence(release)` → `sendmsg(ANNOUNCE)`, reader: `recvmsg` → `fence(acquire)` → чтение заголовка (2.2, шаг 7; 7.1, шаг 4);
- writer: `store_release(generation, N)` → отправка `FRAME`, reader: приём `FRAME` → `load_acquire(generation)` (5.1, шаги 7–8; правило `g1 < N` в 7.3).

По модели C11 эти пары формально не синхронизируются: fence синхронизируется только через атомарный объект, который читает другая сторона, а сокет таковым не является. Порядок обеспечивает системный вызов: ядро передаёт данные сокета под своими блокировками, а это барьеры на обеих сторонах. **Это допущение v1, а не доказанная гарантия.** Источник о гарантиях ядра macOS не найден; S10-06/S10-24 проверяют его тестом. Если допущение не подтвердится, правило «`g1 < N` — ошибка протокола» (7.3) заменяется отбрасыванием кадра, а начальное чтение заголовка получает отдельную проверку. Это изменение версии протокола.

## 6. Поведение writer-а (VMHost)

### 6.1. Начало соединения

1. Создать и заполнить память (раздел 2.2). Создание можно выполнить до `HELLO`.
2. Прочитать 16 байт заголовка `HELLO`. Неверный magic — закрыть соединение без ответа. Magic `ODFT` и `version ≠ 1` — ответ `VERSION` (8.1), затем закрыть соединение; остальные поля такого заголовка не проверяются. Неверный вид, длина или ненулевой reserved при `version = 1` — закрыть соединение без ответа.
3. Отправить `ANNOUNCE` (раздел 4.3), затем `MODE` с текущим режимом.
4. Цикл: продвижение машины, проверка `od_display_session_mode` не чаще заданной частоты (параметр S10-06), публикация по 5.1, уведомления по 6.4. Одновременно следить за EOF или байтами от UI.

### 6.2. Выбор слота

Кандидаты — все слоты, кроме:

- `front` — слота последнего опубликованного кадра (из частного состояния writer-а);
- `reader_claim − 1`, если `1 ≤ reader_claim ≤ slot_count` (`load_relaxed`).

Из кандидатов writer берёт слот с наименьшим опубликованным поколением (самый старый; пустой слот — старше всех). Если кандидатов нет, что возможно только при 2 слотах, публикация пропускается без чтения кадра и повторяется на следующей проверке. Writer НЕ ДОЛЖЕН ждать reader-а: ни блокировки, ни ожидания `reader_claim`.

Writer не пишет в `front`. Поэтому слот последнего объявленного кадра не меняется, пока writer не опубликует более новый кадр. Отсюда гарантия: если reader отбросил кадр на шаге 2 или 6 раздела 5.2, после этого `FRAME` writer уже поставил в очередь более новое уведомление `FRAME` или `MODE`. Reader-у не нужен опрос по таймеру.

### 6.3. Режимы

- Writer хранит `Q` — `mode_change_count` последнего `MODE`, **поставленного в очередь** (а не отправленного: неотправленный `MODE` может ещё заменяться). Если `od_display_session_mode` показывает значение, отличное от `Q`, writer ставит в очередь `MODE` и обновляет `Q`.
- Для кадра со значением `C` из `od_display_frame_info` проверка делается **до** публикации (5.1, шаг 5, то есть до шага 7). При `C > Q` сначала ставится `MODE` из `frame_info` (`ACTIVE = 1`), затем после публикации `FRAME`. При `C < Q` кадр не публикуется и `FRAME` не отправляется: кадр принадлежит режиму, который уже заменён в очереди.
- Режим, превышающий `max_width`/`max_height`, или формат, отличный от `pixel_format`, опубликовать нельзя. Это отказ хоста для данного соединения: writer закрывает его. Расширить память в пределах соединения нельзя: в v1 одна память на соединение.

### 6.4. Очередь уведомлений

Запись в сокет не блокирует продвижение гостя (неблокирующий сокет, ожидание готовности на запись). Выход ограничен одним частично отправленным сообщением, одним ожидающим `MODE` и одним ожидающим `FRAME`, то есть не более 48 + 48 + 40 = 136 байт.

- Новый `FRAME` заменяет неотправленный `FRAME`.
- Новый `MODE` заменяет неотправленный `MODE` и удаляет неотправленный `FRAME`: кадр старого режима после нового `MODE` не отправляется.
- Порядок отправки: сначала дописать частичное сообщение, затем `MODE`, затем `FRAME`.
- Ни одно сообщение очереди не отправляется, пока `ANNOUNCE` не отправлен целиком (4.3). `ANNOUNCE` отправляется только через `sendmsg` с ancillary и при `EAGAIN` повторяется тем же `sendmsg`.

### 6.5. Завершение

EOF или ошибка сокета, любые байты от UI после `HELLO`, отказ хоста — writer прекращает публикацию и закрывает соединение. Сообщения об ошибке в v1 нет: UI узнаёт причину по EOF и статусу завершения процесса, как launcher. `munmap` и `close` выполняются при teardown; имя объекта уже удалено (2.2, шаг 3), поэтому объект освобождается, когда его не отображает ни один процесс.

## 7. Поведение reader-а (UI) и его состояния

### 7.1. Приём памяти

1. Отправить `HELLO`.
2. Прочитать первые 16 байт от VMHost (`recvmsg`, 4.3) и сначала проверить байты 0–5. Magic `ODFT` и `version ≠ 1` — переход в `INCOMPATIBLE` с показом версии VMHost; остальные поля и отсутствие дескриптора в этом случае не проверяются. EOF до 16 байт — `DISCONNECTED`. Иначе это должен быть `ANNOUNCE` по 4.3. Проверить payload: `MIN_TOTAL ≤ total_size ≤ MAX_TOTAL`, `total_size` кратен 16384, `2 ≤ slot_count ≤ 4`, `reserved = 0`.
3. `fstat(fd)` **до** `mmap`: `st_size` ДОЛЖЕН быть равен `total_size`. Меньше `MIN_TOTAL` (заголовок не помещается), больше `MAX_TOTAL` или не равно объявленному — отказ: дескриптор закрывается, переход в «разрыв» (ошибка протокола). Все размеры v1 кратны 16384, поэтому округление размера объекта до страницы при поддержанной странице не меняет `st_size`. Это предположение S10-06/07 проверяет тестом; источник о поведении `fstat` для POSIX shm на macOS не найден.
4. Отобразить страницу заголовка: `mmap(NULL, 16384, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0)`. Отобразить данные: `mmap(NULL, total_size − 16384, PROT_READ, MAP_SHARED, fd, 16384)`. Затем `fence(acquire)`, после чего дескриптор МОЖНО закрыть. Пара `fence(release)` writer-а → `sendmsg` → `recvmsg` → `fence(acquire)` формально по C11 не синхронизируется; видимость заголовка — допущение 5.4.
5. Проверить заголовок по таблице 3.1 в порядке раздела 3.5 и сверить `total_size` и `slot_count` с `ANNOUNCE`. Сохранить проверенные значения в частной памяти. Записать `reader_claim = 0`.

### 7.2. Состояния

| Состояние | Что показывает UI | Вход |
|---|---|---|
| `CONNECTING` | «нет сигнала» | запуск VMHost, до успешного 7.1 |
| `NO_SIGNAL` | «нет сигнала» | память принята (7.1), годного кадра текущего режима нет, и выполнено одно из двух: последний `MODE` имеет `ACTIVE = 0` (или `MODE` ещё не было); либо `ACTIVE = 1`, но на этом соединении ещё не был показан ни один кадр (`shown_once = false`) |
| `MODE_CHANGING` | «изменение режима» | последний `MODE` имеет `ACTIVE = 1`, годного кадра этого режима нет, и на этом соединении уже был показан кадр (`shown_once = true`); ждём годный кадр нового режима |
| `SHOWING` | кадр | успешное чтение 5.2 кадра с `mode_change_count` последнего `MODE` |
| `DISCONNECTED` (разрыв) | «нет сигнала: VMHost отключён» и причина | EOF, ошибка сокета, ошибка протокола, завершение VMHost, истечение срока ожидания `ANNOUNCE`; закрытие соединения без заголовка `VERSION` |
| `INCOMPATIBLE` | «несовместимая версия» и версия VMHost, если она известна | заголовок с magic `ODFT` и `version ≠ 1` (в том числе `VERSION`, 8.1); несовместимый заголовок памяти (8.2) |

Reader хранит флаг `shown_once`. Он равен `false` после `ANNOUNCE`, становится `true` при первом входе в `SHOWING` и до конца соединения не сбрасывается. При `ACTIVE = 1` без годного кадра `MODE_CHANGING` и `NO_SIGNAL` различаются только этим флагом. Если кадра на соединении ещё не было, reader остаётся в `NO_SIGNAL`. Если кадр был, reader переходит в `MODE_CHANGING`, даже если между ними прошёл `NO_SIGNAL`. Пример: `SHOWING` → `MODE(ACTIVE = 0)` → `NO_SIGNAL` → `MODE(ACTIVE = 1)` → `MODE_CHANGING`.

Ни в одном состоянии, кроме `SHOWING`, UI НЕ ДОЛЖЕН показывать последний кадр как текущий. Оформление (текст, цвет) выбирает S10-07.

Переходы (полный список; иное сочетание состояния и события состояние не меняет):

- `CONNECTING → NO_SIGNAL` — успешное 7.1 (`ANNOUNCE` принят, память проверена). Кадра нет.
- `NO_SIGNAL → NO_SIGNAL` — `MODE` с `ACTIVE = 0`; или `MODE` с `ACTIVE = 1` при `shown_once = false`.
- `NO_SIGNAL → MODE_CHANGING` — `MODE` с `ACTIVE = 1` при `shown_once = true`.
- `NO_SIGNAL → SHOWING` — первый годный кадр текущего режима.
- `SHOWING → SHOWING` — годный кадр с большим `generation`. Отброшенный кадр состояние не меняет: показывается предыдущий годный кадр того же режима.
- `SHOWING → MODE_CHANGING` — `MODE` с `ACTIVE = 1` и новым `mode_change_count`.
- `MODE_CHANGING → MODE_CHANGING` — ещё один `MODE` с `ACTIVE = 1`.
- `MODE_CHANGING → SHOWING` — первый годный кадр текущего режима.
- `SHOWING | MODE_CHANGING → NO_SIGNAL` — `MODE` с `ACTIVE = 0`.
- Любое состояние → `DISCONNECTED` или `INCOMPATIBLE` — по условиям таблицы. Оба состояния конечны для соединения: UI делает `munmap` обеих областей, закрывает сокет и останавливает VMHost по разделу 2, пункт 4. Выход из них — только новое соединение (`CONNECTING`).

UI МОЖЕТ ограничить ожидание `ANNOUNCE` сроком, значение выбирает S10-07. Это не опрос: другие события после `ANNOUNCE` ограничений по времени не имеют, потому что VMHost без смены кадра молчит законно.

### 7.3. Обработка уведомлений

Reader МОЖЕТ объединять уведомления: прочитать все доступные сообщения, применить все `MODE` по порядку и читать слот только последнего `FRAME`. Проверки сообщений, нарушение которых — ошибка протокола:

- `MODE`: `mode_change_count` больше предыдущего (кроме первого); поля по правилам 4.2.
- `FRAME`: `generation` больше предыдущего `FRAME`; `mode_change_count` равен последнему `MODE`; `slot_index < slot_count`; последний `MODE` активен.
- В 5.2 значение `g1` ненулевое и меньше `N`: публикация видна до отправки уведомления (5.1, шаги 7–8; допущение 5.4), поэтому меньшее поколение означает нарушение writer-а. `g1 = 0` или `g1 > N` — законная перезапись слота.

## 8. Совместимость и отказы

### 8.1. Версия

- Frame transport v1 — это одновременно `version = 1` в заголовке сообщения и `version = 1` в заголовке памяти. Согласования, понижения и fallback нет. Одна сторона, одна версия.
- Несовпадение версии обнаруживается по инварианту байтов 0–5 заголовка (4.1) и ДОЛЖНО быть видно UI как «несовместимая версия» (план, §4.2).
- VMHost, получивший `HELLO` с magic `ODFT` и `version ≠ 1`, отвечает **одним 16-байтным заголовком** `VERSION`: magic `ODFT`, `version = 1` (своя версия), `kind = 0`, `reserved = 0`, `payload_length = 0`. Затем он закрывает соединение. Память при этом не передаётся. Остальные поля чужого `HELLO` VMHost не проверяет.
- UI, получивший заголовок с magic `ODFT` и `version ≠ 1` (`VERSION` или любое другое сообщение), переходит в `INCOMPATIBLE` и показывает полученную версию; остальные поля такого заголовка не толкуются. Если соединение закрыто, а заголовок не пришёл, состояние — `DISCONNECTED`: причину по одному EOF не различить.
- Этот ответ действует и в обратную сторону: будущий VMHost vN, получив `HELLO` v1, отвечает заголовком со своей версией, и UI v1 показывает «несовместимая версия vN».
- Изменение любого поля, размера, смещения, вида, значения `state`, `flags` или формата пикселя — новая версия протокола. Курсор (S10-14) и несколько экранов (S10-15) требуют новой версии; внутри v1 их добавить нельзя. Числа и поля v1 не переиспользуются с другим смыслом.

### 8.2. Неизвестные значения

Неизвестные значения не являются расширением. Reserved-поля и неопределённые биты пишутся нулями и проверяются читающей стороной; ненулевое значение — отказ. Исключение одно: writer не читает `reserved` блока reader-а и не проверяет его.

| Условие | Результат на стороне UI |
|---|---|
| magic памяти не `ODFS`; `version`, `header_size`, `reader_block_offset`, `descriptors_offset`, `descriptor_size`, `slots_offset` не равны значениям v1; `pixel_format ≠ 1`; `flags ≠ 0` | `INCOMPATIBLE` |
| Заголовок с magic `ODFT` и `version ≠ 1`, в том числе `VERSION` | `INCOMPATIBLE`, показывается версия VMHost |
| `VERSION` с `version = 1` | `DISCONNECTED`, ошибка протокола |
| Другой magic сообщения, неизвестный `kind`, неверное направление, длина payload не равна фиксированной, ненулевой reserved, нарушение порядка (4.2, 7.3), нарушения передачи дескриптора (4.3), размер памяти (7.1), недопустимые `slot_count`/`max_*`/`slot_size`/`total_size`, нарушение описателя при `g1 = g2` (5.2) | `DISCONNECTED`, причина — ошибка протокола |
| Хост с `getpagesize()`, не делящим 16384 | отказ до создания или отображения памяти |

Ошибки протокола закрывают соединение без ответного сообщения на обеих сторонах. Единственный ответ перед закрытием — `VERSION` на `HELLO` с чужой версией (8.1). Повтора и переподключения в v1 нет. Перезапуск VMHost — решение UI (S10-24), а не механизм протокола.

### 8.3. Доверие

Каждая сторона считает данные другой недоверенными. VMHost исполняет гостевой код, поэтому UI проверяет каждое значение из памяти и сообщений до использования и не читает за пределами проверенных границ. Каждое поле описателя читается атомарно один раз, и проверки идут по локальной копии (5.2, шаг 3), поэтому writer не может подменить значение между проверкой и использованием. UI НЕ ДОЛЖЕН падать или показывать смесь кадров из-за **содержимого** памяти. VMHost читает из памяти только `reader_claim`, и любое его значение безопасно.

**Исключение v1 до S10-24: `SIGBUS` при уменьшении объекта.** В macOS нет запечатывания размера объекта (аналога `F_SEAL_SHRINK`). Если неисправный writer вызовет повторный `ftruncate` с меньшим размером после `mmap` reader-а, обращение reader-а к отрезанным страницам даст `SIGBUS`, и UI завершится. Это нарушение требования «UI не падает», и v1 явно его допускает: в v1 нет обработки этого случая. Защита в v1 одна — запрет повторного `ftruncate` (2.2, шаг 4). S10-24 ДОЛЖЕН закрыть исключение одним из двух способов: подтвердить тестом, что macOS отвергает повторный `ftruncate` POSIX shm, или ввести обработку (например, чтение слота в контролируемом обработчике `SIGBUS`). До этого исключение записано в разделе S10-05 отчёта этапа. Источник о поведении `ftruncate` для POSIX shm на macOS не найден.

VMHost от действий UI `SIGBUS` не получает. Объект удалён из пространства имён (2.2, шаг 3) и живёт, пока его отображает или держит дескриптор хотя бы один процесс. Поэтому `munmap`, `close` или завершение UI не отнимают страницы у VMHost. Уменьшить объект UI мог бы только нарушением 2.2, шаг 4. UI — владелец процесса VMHost (раздел 2) и для VMHost доверенная сторона, поэтому такое нарушение в модель угроз v1 не входит.

## 9. Вне v1

- Передача пикселей по сокету и доступ к памяти по пути или имени.
- Несколько экранов, курсор, dirty rects, сжатие, другие форматы пикселя, stride с padding, смена раскладки памяти в пределах соединения.
- IOSurface и передача через Mach ports: решение S10-17 по замерам.
- Команды UI → VMHost, кроме `HELLO`. Ввод — отдельный канал S10-16.
- Измеренные свойства производительности. Одна копия на стороне writer-а (память устройства → слот) и одна на стороне reader-а (слот → texture) — гипотеза до S10-10.
