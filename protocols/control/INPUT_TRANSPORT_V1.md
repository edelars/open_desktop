# Input transport v1: события ввода UI → VMHost

**Статус:** нормативная спецификация задачи S10-16 [плана этапа 10](../../docs/plans/STAGE_10.md#s10-16-ввод-мыши-и-клавиатуры-из-окна), **ожидает ревью**. Host-часть реализована, ожидает ревью: UI (`apps/macos/Sources/Input*.swift`, `HIDUsage.swift`, `DisplayWindow.swift`) и VMHost (`apps/vmhost/Sources/InputChannel.swift`, очередь до границы `od-host`). Доставки в гостя нет, ручной ввод в окне не проверен. Слова ДОЛЖЕН, НЕ ДОЛЖЕН и МОЖЕТ — требования протокола. Нарушение требования другой стороной — ошибка протокола (раздел 9).

**Доставки в гостя нет.** В плате v0.1 устройство ввода — PCI xHCI с USB HID keyboard и mouse ([VIRTUAL_BOARD.md](../../docs/specs/VIRTUAL_BOARD.md), строка «Ввод»). На 2026-11-06 этого устройства нет ни в `od-machine`, ни в C ABI `od-host`. Поэтому события, принятые по этому протоколу, доходят только до ограниченной очереди VMHost (раздел 7) и в гостя не попадают. VMHost сообщает это флагом `GUEST_DELIVERY = 0` в `ACCEPT` (4.2). Пока флаг равен 0, протокол и его реализация НЕ ДОЛЖНЫ описываться как «ввод работает».

Документ — единственный источник байтов этого канала. Он не меняет [control protocol v1](CONTROL_PROTOCOL_V1.md), [v0](CONTROL_PROTOCOL_V0.md) и [frame transport v1](FRAME_TRANSPORT_V1.md): ни их кадров, ни видов сообщений, ни правил соединения.

## 1. Обзор

- Отдельный унаследованный `socketpair` (раздел 2). Сообщения короткие, фиксированной длины, с заголовком `ODIT`. Дескрипторы по каналу не передаются.
- UI собирает события окна, переводит их в значения USB HID (клавиши и кнопки — HID usage, мышь — относительные перемещения и колесо) и кладёт в свою ограниченную очередь. Из очереди события пишутся в сокет неблокирующей записью.
- VMHost читает сокет, проверяет каждое сообщение и кладёт событие в свою ограниченную очередь по тем же правилам (раздел 7). Потребитель очереди VMHost — будущий input ABI `od-host` (раздел 10). До его появления у очереди нет потребителя, и она не растёт.
- Позиция мыши передаётся и как абсолютный пиксель гостя, привязанный к режиму дисплея (раздел 5). Абсолютного pointer device в плате v0.1 нет. Поле нужно для теста координат на границе `od-host` и для будущего решения по плате (раздел 11).

## 2. Канал

### 2.1. Решение: отдельный socketpair, а не сокет frame transport

Ввод идёт по **отдельному** унаследованному `socketpair`. Сокет frame transport (дескриптор 3 в дисплейном режиме) для ввода не используется, даже с другим magic. Причины:

1. Frame transport v1 запрещает это сам. Соединение несёт только frame transport ([FRAME_TRANSPORT_V1.md](FRAME_TRANSPORT_V1.md) §2, п. 2). После `HELLO` любые байты от UI — ошибка протокола (§4.2, §6.5). Общий сокет потребовал бы frame transport v2.
2. Разделение управления и потока данных ([ARCHITECTURE.md](../../docs/ARCHITECTURE.md) §4). Ввод — «интенсивный ввод» с собственной ограниченной очередью и политикой переполнения. Поэтому он не идёт ни в control-сообщениях, ни в канале кадров. Тот же подход frame transport уже заявил для себя: при одновременной работе control и дисплея у него будет отдельный `socketpair` ([FRAME_TRANSPORT_V1.md](FRAME_TRANSPORT_V1.md) §2, п. 3).
3. Нет блокировки в начале очереди (head-of-line). Кадры и ввод идут в противоположных основных направлениях и имеют разные очереди. На общем потоке байтов полный буфер одной стороны задерживал бы другую.
4. Разные правила приёма. Reader кадров читает только через `recvmsg` и ждёт ровно один дескриптор в первом `recvmsg` (§4.3). В канале ввода дескрипторов нет совсем. Смешение каналов усложнило бы обе проверки.
5. Независимые отказы. Ошибка протокола ввода закрывает только канал ввода (раздел 8.3). Показ кадров при этом продолжается.

Цена — ещё один дескриптор при запуске. Отвергнутый вариант — тот же сокет с magic `ODIT`. Он требует новой версии frame transport, смешивает направления и усложняет проверку дескрипторов.

### 2.2. Запуск и владение

1. UI создаёт второй `socketpair(AF_UNIX, SOCK_STREAM, 0)` тем же способом, что [VMHostLaunch.swift](../../apps/macos/Sources/VMHostLaunch.swift): `SO_NOSIGPIPE` на обоих концах, `posix_spawn` с `adddup2` конца VMHost на дескриптор **4**, закрытие остальных концов в потомке, закрытие копии конца VMHost в UI после spawn. VMHost получает аргумент `--input-fd 4`. Номер дескриптора задаётся аргументом; формат протокола от номера не зависит.
2. Без `--input-fd` у VMHost нет канала ввода. UI, который не создал канал, события ввода не собирает.
3. VMHost ставит на свой конец `FD_CLOEXEC`, чтобы другие его потомки не унаследовали канал. Обе стороны переводят свой конец в неблокирующий режим.
4. Владение и остановка процесса — как у frame transport ([FRAME_TRANSPORT_V1.md](FRAME_TRANSPORT_V1.md) §2, п. 4). Перезапуск VMHost (S10-24) создаёт новый процесс и новые `socketpair` для обоих каналов. Состояние канала ввода (очереди, нажатые клавиши, фокус) начинается заново.
5. Неверный запуск обнаруживается по EOF. Если `HELLO` с magic `ODIT` придёт в канал frame transport, VMHost закроет соединение по правилу неверного magic (§6.1, п. 2). Если в канал ввода придёт `HELLO` с magic `ODFT` или `ODCP`, VMHost закроет канал ввода по разделу 9.

## 4. Сообщения

### 4.1. Заголовок

Каждое сообщение начинается с 16-байтного заголовка, за которым идут ровно `payload_length` байт. Числа — little-endian фиксированной ширины, padding нет, знаковые — дополнительный код.

| Смещение | Размер | Поле | Значение |
|---:|---:|---|---|
| 0 | 4 | `magic` | ASCII `ODIT` (`4f 44 49 54`) |
| 4 | 2 | `version` | `1` |
| 6 | 2 | `kind` | из таблицы 4.2 |
| 8 | 4 | `reserved` | `0` |
| 12 | 4 | `payload_length` | ровно длина из таблицы для `kind` |

Инвариант всех версий, как в frame transport (§4.1): байты 0–5 — `magic` и `version`. При чужой версии остальные поля не проверяются и не толкуются.

Наибольшее сообщение — `MOTION`, 64 байта. Сторона проверяет заголовок до приёма payload и обрабатывает частичные чтения и записи. Вход буферизуется в пределах одного наибольшего сообщения своего направления: 64 байта у VMHost, 48 у UI. Обе стороны читают через `recvmsg` с буфером ancillary. Любой управляющий заголовок (`cmsghdr`) или `MSG_CTRUNC` — ошибка протокола; принятый дескриптор сразу закрывается.

### 4.2. Виды

| `kind` | Имя | Направление | Payload | Сообщение целиком | Когда |
|---:|---|---|---:|---:|---|
| 0 | `VERSION` | VMHost → UI | 0 | 16 | только ответ на `HELLO` с чужой версией, затем VMHost закрывает канал (9.1) |
| 1 | `HELLO` | UI → VMHost | 0 | 16 | первое сообщение UI, ровно один раз |
| 2 | `ACCEPT` | VMHost → UI | 8 | 24 | первое сообщение VMHost, ровно один раз, ответ на `HELLO` |
| 3 | `FOCUS` | UI → VMHost | 8 | 24 | смена фокуса окна (раздел 6.4) |
| 4 | `USAGE` | UI → VMHost | 8 | 24 | нажатие или отпускание клавиши либо кнопки мыши |
| 5 | `MOTION` | UI → VMHost | 48 | 64 | перемещение мыши и колесо |
| 6 | `STATUS` | VMHost → UI | 32 | 48 | изменились счётчики VMHost (7.5) |

Других видов в v1 нет. **Неизвестный `kind` — ошибка протокола**, как и вид не своего направления. Отправлять `FOCUS`, `USAGE` и `MOTION` UI МОЖЕТ только после приёма `ACCEPT`.

**`ACCEPT` (8 байт)**

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 4 | `flags`: бит 0 `GUEST_DELIVERY` — у машины есть устройство ввода, и события очереди уходят в него. В v0.1 всегда `0`. Остальные биты `0` |
| 4 | 4 | `reserved = 0` |

UI ДОЛЖЕН показать `GUEST_DELIVERY = 0` явно, например текстом «ввод не доставляется в гостя». Ёмкость очередей в v1 — константа (раздел 7), в `ACCEPT` она не передаётся.

**`FOCUS` (8 байт)**

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 4 | `state`: `0` = `LOST`, `1` = `GAINED` |
| 4 | 4 | `reserved = 0` |

**`USAGE` (8 байт)** — изменение состояния одного HID usage.

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 2 | `usage_page`: `0x07` (Keyboard/Keypad) или `0x09` (Button) |
| 2 | 2 | `usage_id` — допустимые значения в 6.1 |
| 4 | 4 | `state`: `0` = `UP`, `1` = `DOWN` |

**`MOTION` (48 байт)**

| Смещение | Размер | Поле | Смысл |
|---:|---:|---|---|
| 0 | 8 | `mode_change_count` | `mode_change_count` кадра, по которому вычислена абсолютная позиция (5.3). При `ABS_VALID = 0` равен `0` |
| 8 | 4 | `dx` (i32) | относительное перемещение по X в отсчётах гостя (5.4), положительное — вправо |
| 12 | 4 | `dy` (i32) | по Y, положительное — вниз |
| 16 | 4 | `wheel` (i32) | вертикальное колесо в 1/120 щелчка, положительное — от пользователя (HUT 1.7, `Wheel`: значения растут при прокрутке вперёд, от пользователя) |
| 20 | 4 | `pan` (i32) | горизонтальная прокрутка (`AC Pan`) в 1/120 щелчка, положительное — вправо |
| 24 | 4 | `abs_x` | пиксель гостя по X, `< abs_width` |
| 28 | 4 | `abs_y` | пиксель гостя по Y, `< abs_height` |
| 32 | 4 | `abs_width` | ширина кадра, по которому вычислена позиция, `1…4096` |
| 36 | 4 | `abs_height` | высота кадра, `1…2304` |
| 40 | 4 | `flags` | бит 0 `ABS_VALID`; остальные биты `0` |
| 44 | 4 | `reserved` | `0` |

При `ABS_VALID = 0` поля `mode_change_count`, `abs_*` равны 0. Хотя бы одно из `dx`, `dy`, `wheel`, `pan` ненулевое, или `ABS_VALID = 1`: пустой `MOTION` — ошибка протокола. `MOTION` с нулевыми дельтами и `ABS_VALID = 1` пустым не является и разрешён: так UI передаёт позицию клика (5.2). Пределы `4096 × 2304` — пределы устройства ([FRAME_TRANSPORT_V1.md](FRAME_TRANSPORT_V1.md) §3.1).

**`STATUS` (32 байта)** — накопительные счётчики VMHost с начала канала. Значения не уменьшаются.

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 8 | `rejected_downs` — нажатия (`USAGE DOWN`), которым очередь VMHost отказала (7.3) |
| 8 | 8 | `merged_motions` — `MOTION`, объединённые с предыдущей записью очереди VMHost |
| 16 | 8 | `dropped_unfocused` — события, отброшенные в состоянии `GAINED_PENDING` (7.4) |
| 24 | 4 | `queue_depth` — число записей в очереди VMHost в момент отправки |
| 28 | 4 | `reserved = 0` |

## 5. Мышь

### 5.1. Модель

Мышь в протоколе — стандартная относительная HID mouse:

- кнопки — usage Button Page `0x09`, передаются как `USAGE`;
- перемещение — `X`/`Y` Generic Desktop, передаётся как `dx`/`dy`;
- колесо — `Wheel` и `AC Pan`.

Абсолютная позиция — дополнительное поле. Устройство v0.1 его не использует (раздел 11).

### 5.2. Кнопки

`NSEvent.buttonNumber` `n` (0 — левая, 1 — правая, 2 — средняя, 3 и 4 — дополнительные) передаётся как usage `0x09`:`n + 1` (Button 1 primary, Button 2 secondary, Button 3 tertiary, Button 4, Button 5; HUT 1.7, таблица 12.1). Кнопки с `n ≥ 5` в v1 не передаются: UI их отбрасывает и учитывает. Ctrl-click не превращается в правую кнопку: передаются отдельно `LeftControl` и Button 1.

**Позиция клика.** `USAGE` координат не несёт, а `mouseMoved` перед кликом не гарантирован (5.4). Поэтому перед каждым `USAGE` кнопки (`DOWN` и `UP`, страница `0x09`) UI ДОЛЖЕН поставить в очередь `MOTION` с нулевыми дельтами и `ABS_VALID = 1`. Позиция в нём — `event.locationInWindow` этого события кнопки, переведённая в пиксель гостя по 5.3. Если абсолютная позиция невычислима (5.3, шаг 6), `MOTION` не ставится. По правилам 7.3 такой `MOTION` объединяется с хвостом-`MOTION` или занимает запись, которая всегда есть по инварианту. Поэтому отказа он не получает и запас для `USAGE` не уменьшает.

### 5.3. Перевод координат (матрица S10-11)

Перевод использует ту же геометрию, по которой рисует presenter, — [`Viewport.swift`](../../apps/macos/Sources/Viewport.swift), без копии формул.

1. Точка события в окне — `p = view.convert(event.locationInWindow, from: nil)`, в логических точках. У `DisplayView` начало координат внизу слева (вид не flipped).
2. Размер drawable `(Dw, Dh)` = `ViewportLayout.drawableSize(bounds, backingScaleFactor)` — то же значение, что `DisplayWindow.refresh` ставит в `layer.drawableSize`. Bounds — `(Bw, Bh)`.
3. Физический пиксель под курсором: `cx = floor(p.x × Dw / Bw)`, `cy = floor((Bh − p.y) × Dh / Bh)`; ось Y переворачивается. Используется отношение `Dw/Bw`, а не `backingScaleFactor`, поэтому края bounds точно попадают на края drawable, несмотря на округление `drawableSize`.
4. Viewport = `ViewportLayout.viewport(mode, W, H, Dw, Dh)`, где `W × H` — размер **показанного** кадра (`MetalPresenter.shownSize`), а `mode` — режим показа окна. Используется полный viewport без обрезки: в `pixelExact` он может иметь отрицательное начало.
5. Пиксель гостя = `ViewportLayout.guestPixel(pixelX: cx + 0.5, pixelY: cy + 0.5, viewport, W, H)`. Берётся центр физического пикселя: так же GPU выбирает тексель при nearest-выборке, поэтому результат — тот пиксель гостя, который нарисован под курсором.
6. `ABS_VALID = 1` только если выполнены все три условия: состояние reader-а frame transport — `SHOWING`, показанный кадр принадлежит последнему `MODE`, `guestPixel` вернул не `nil`. Тогда `mode_change_count` = `mode_change_count` показанного кадра, `abs_width`/`abs_height` = `W`/`H`. В остальных случаях `ABS_VALID = 0`: поля окна, состояния «нет сигнала», «смена режима», «разрыв».

**Точность.** Пусть `k = W / viewport.width` — гостевых пикселей на физический (по Y аналогично).

- Результат шага 5 совпадает с тем гостевым пикселем, который presenter рисует в физическом пикселе под курсором. Исключение — точная граница текселя: там GPU может выбрать соседний ([DISPLAY.md](../../docs/testing/DISPLAY.md) §3). Ошибка относительно показанного не больше 1 гостевого пикселя.
- **Решение: абсолютная позиция соответствует нарисованному текселю.** Это выбор протокола, у него есть цена.
- Углы при этом выборе. Левый верхний физический пиксель viewport даёт `floor(k/2)`, правый нижний — `W − ceil(k/2)`.
  - При `k < 2` это точно `(0, 0)` и `(W − 1, H − 1)`. Сюда входят `pixelExact` и любое увеличение.
  - При `k ≥ 2` тексель 0 на экране не нарисован: nearest-выборка в центре первого физического пикселя берёт тексель `floor(k/2) ≥ 1`. При `2 ≤ k < 4` ошибка угла остаётся не больше 1 гостевого пикселя.
  - При `k ≥ 4` абсолютная позиция никогда не даёт `(0, 0)` и `(W − 1, H − 1)`: угловые пиксели гостя этим путём недостижимы, а ошибка левого верхнего угла — `floor(k/2) ≥ 2`. Пример: кадр 4096×2304 в окне 640×360 @1 (`k = 6.4`). Клик в левый верхний угол даёт `(3, 3)`, в правый нижний — `(4092, 2300)`. Тест в этом случае ожидает нарисованный тексель, а не угол гостя (раздел 12).
- Отвергнутая сейчас альтернатива — растянуть концы: первый физический пиксель viewport отображать в `0`, последний — в `W − 1` (`x = round(c × (W − 1) / (vw − 1))`). Углы тогда достижимы всегда, но позиция внутри кадра расходится с нарисованным текселем до `k/2` пикселей гостя. Альтернатива отложена: абсолютная позиция в плате v0.1 никуда не доставляется, а нужна она будущему absolute pointer device. Это отдельное решение по плате (раздел 11, п. 1). Отображение концов выбирается вместе с этим решением и меняет версию протокола (9.1).
- Примеры (кадр; окно в точках при scale; viewport; углы):
  - 64×48; 100×100 @2; `0,25,200,150`, `k = 0.32` → `(0,0)` и `(63,47)`;
  - 1920×1080; 640×480 @1; `0,60,640,360`, `k = 3` → `(1,1)` и `(1918,1078)`;
  - 4096×2304; 640×360 @1; `0,0,640,360`, `k = 6.4` → `(3,3)` и `(4092,2300)`;
  - 64×48 `pixelExact`; 10×10 @1; `-27,-19,64,48` → физические `(0,0)` и `(9,9)` дают `(27,19)` и `(36,28)`.

**Смена режима и геометрии.** Шаги 2–5 выполняются для каждого события заново, по текущим bounds, scale и показанному кадру. Готовую матрицу UI между событиями не хранит. Поэтому resize, смена экрана и смена режима гостя учитываются без отдельного сброса. `MOTION`, уже стоящий в очереди с прежним `mode_change_count`, не пересчитывается: VMHost отбросит его абсолютную часть как устаревшую (8.2).

### 5.4. Относительное перемещение

- Источник — `NSEvent.deltaX`/`deltaY` событий `mouseMoved` и `*MouseDragged`, в логических точках (допущение, раздел 11). Переход в физические пиксели — умножение на `Dw/Bw` и `Dh/Bh`. Переход в отсчёты гостя — умножение на `k`, если кадр показан, иначе на 1. Масштаб `k` нужен для того, чтобы при показе кадра с масштабом курсор гостя без ускорения проходил то же видимое расстояние, что курсор хоста.
- UI копит дробный остаток по каждой оси отдельно и отправляет целую часть (усечение к нулю). Остаток сбрасывается при смене `k` и при `FOCUS LOST`.
- Ось Y у `deltaY` в AppKit направлена вниз, как и у `dy`. Это допущение проверяет тест знака (раздел 12).
- `MOTION` отправляется и при `ABS_VALID = 0`: относительное перемещение от положения курсора над кадром не зависит.
- `mouseMoved` не обязателен: AppKit может не доставить его перед кликом, например без tracking area или при первом событии после фокуса. Поэтому позицию клика UI фиксирует сам (5.2): `MOTION` с `ABS_VALID = 1` и нулевыми дельтами разрешён и пустым не считается (4.2).

### 5.5. Колесо

- Перевод в 1/120 щелчка:
  - `hasPreciseScrollingDeltas = false` (колесо со щелчками): `scrollingDeltaY × 120`;
  - `true` (трекпад, гладкое колесо): `scrollingDeltaY × WHEEL_UNITS_PER_POINT`. Значение параметра выбирает S10-16 и записывает в отчёт (открытый вопрос, раздел 11).
- Остаток копится, как в 5.4.
- Направление — физическое направление устройства. Если `isDirectionInvertedFromDevice = true` («естественная прокрутка»), UI меняет знак обратно. Своё направление прокрутки применяет гость.
- Перевод в отчёты устройства с Resolution Multiplier (HUT 1.7 §4.3.1) или без него — задача будущего устройства, а не протокола.

## 6. Клавиатура и фокус

### 6.1. Допустимые usage

| `usage_page` | Допустимые `usage_id` (HUT 1.7) |
|---|---|
| `0x07` Keyboard/Keypad | `0x04…0xA4`, `0xB0…0xDD`, `0xE0…0xE7` |
| `0x09` Button | `0x01…0x05` |

- `0x00` не передаётся. `0x01…0x03` (`ErrorRollOver`, `POSTFail`, `ErrorUndefined`) — состояния клавиатуры, а не клавиши, и тоже не передаются.
- Зарезервированные `0xA5…0xAF`, `0xDE…0xDF`, `0xE8…0xFFFF` и любые другие страницы — ошибка протокола.
- PS/2 scan codes протокол не знает: каждое значение — HID usage.

### 6.2. Таблица `kVK_*` → usage

- UI переводит `NSEvent.keyCode` (`kVK_*`) в usage страницы `0x07` по собственной таблице. Таблица — код S10-16, не часть протокола. Коды позиционные: раскладку (ANSI, ISO, JIS) переводит гость. Примеры строк таблицы:
  - `kVK_ANSI_A` `0x00` → `0x04`;
  - `kVK_Return` `0x24` → `0x28`;
  - `kVK_Escape` `0x35` → `0x29`;
  - `kVK_ISO_Section` `0x0A` → `0x64` (Non-US `\` и `|`);
  - `kVK_JIS_Yen` `0x5D` → `0x89` (International3);
  - `kVK_JIS_Kana` `0x68` → `0x90` (LANG1);
  - `kVK_Control`/`Shift`/`Option`/`Command` `0x3B`/`0x38`/`0x3A`/`0x37` → `0xE0`/`0xE1`/`0xE2`/`0xE3`;
  - правые модификаторы `0x3E`/`0x3C`/`0x3D`/`0x36` → `0xE4`/`0xE5`/`0xE6`/`0xE7`.
- Таблица указывает редакцию HUT (1.7) и версию SDK. У `kVK_Function` (Fn) usage на странице `0x07` нет, поэтому Fn не передаётся.
- Код без строки в таблице не передаётся. UI учитывает его в счётчике `unmapped` и пишет в журнал один раз на код.
- Тест покрытия (раздел 12) проверяет, что каждый `kVK_*` из SDK либо имеет строку, либо записан как непередаваемый с причиной.

### 6.3. Нажатия, повтор, модификаторы

- `keyDown` с `isARepeat = true` не передаётся: USB HID keyboard не шлёт автоповтор, повтор делает гость.
- UI хранит множество нажатых usage (обе страницы). Он НЕ ДОЛЖЕН отправлять `DOWN` для уже нажатого usage и `UP` для ненажатого. VMHost проверяет то же (8.2).
- Модификаторы приходят событием `flagsChanged`. Нажатие или отпускание определяется по биту конкретной клавиши (левой или правой) в device-dependent части `modifierFlags`, а не по общему флагу.
- Caps Lock: `flagsChanged` приходит на каждое переключение, отдельного отпускания нет. UI передаёт на каждое такое событие пару `DOWN`, `UP` usage `0x39`. Синхронизации индикатора Caps Lock в v1 нет (раздел 11).
- Командные комбинации. AppKit может не доставить `keyUp` в окно, пока нажата Command, и может перехватить комбинацию как key equivalent меню. UI ДОЛЖЕН получать `keyDown`/`keyUp` до разбора меню, например локальным монитором событий или в `sendEvent`. Каждое переданное `DOWN` ДОЛЖНО иметь пару `UP` или закрываться `FOCUS LOST`. Это требование к реализации, а способ проверяется в S10-16 (раздел 11).
- Системные сочетания (Cmd-Tab, Mission Control и т. п.) macOS перехватывает до окна, и в гостя они не передаются. Cmd-Tab уводит фокус, поэтому `FOCUS LOST` отпускает Command, нажатую до переключения.

### 6.4. Фокус

- Окно в фокусе, если оно key window активного приложения.
- UI отправляет `FOCUS GAINED`, когда окно стало key (`windowDidBecomeKey`) или когда пришёл `ACCEPT`, а окно уже key.
- UI отправляет `FOCUS LOST` при `windowDidResignKey`, `applicationDidResignActive`, свёртывании и закрытии окна.
- **`FOCUS LOST` отпускает всё.** UI очищает множество нажатых usage без отдельных `UP` и сбрасывает остатки 5.4–5.5. VMHost отпускает все usage, которые считал нажатыми. Будущее устройство отдаёт гостю отчёт «ничего не нажато». Так клавиши и кнопки не залипают, если отпускание пришло уже в другое окно.
- Без фокуса UI не отправляет `USAGE` и `MOTION`. Событие, пришедшее до входа в фокус, отбрасывается и учитывается.
- Начальное состояние канала после `ACCEPT` — `UNFOCUSED`.
- Порядок по фокусу строгий: `GAINED` и `LOST` чередуются, первым идёт `GAINED`. Повтор того же `state` — ошибка протокола.

## 7. Ограниченные очереди

### 7.1. Где и сколько

Очередь UI (между обработчиком событий AppKit и сокетом) и очередь VMHost (между сокетом и границей `od-host`) устроены одинаково:

| Параметр | Значение v1 |
|---|---:|
| Ёмкость `N` | 256 записей |
| Размер записи | 64 байта (наибольшее сообщение, `MOTION`) |
| Память очереди | 256 × 64 = 16 384 байт |
| UI всего | 16 384 + 64 (частично отправленное сообщение) + 48 (вход: наибольшее сообщение VMHost, `STATUS`) = 16 496 байт |
| VMHost всего | 16 384 + 64 (вход: `MOTION`) + 48 (частично отправленное) + 48 (ожидающий `STATUS`) = 16 544 байт |
| Наибольшее число одновременно нажатых usage | 126 (7.3) |

Память выделяется при открытии канала и потом не растёт. Без потребителя очередь доходит до `N` записей и дальше работает по правилам 7.3: объединяет перемещения и отказывает в нажатиях. 256 — гипотеза. Её подтверждают или меняют замеры S10-10/S10-24; изменение ёмкости — новая версия протокола.

### 7.2. Обозначения

- `free` — число свободных записей.
- `tail` — последняя запись, ещё стоящая в очереди. Запись, отправка или потребление которой уже началось, из очереди удалена, и `tail` её не касается.
- `h` — число usage, у которых `DOWN` принят в очередь, а `UP` ещё нет.
- `m = 0`, если `tail` — `MOTION`, иначе `1` (в том числе для пустой очереди).
- `suppressed` — множество usage, которым отказано в `DOWN` (или отброшенных по 7.4); их `UP` не ставится в очередь. Хранится битовой картой на 256 + 5 usage.

**Инвариант** (в состоянии `FOCUSED`): `free ≥ 2h + m + 1`. Запас — по паре «перемещение + отпускание» на каждый нажатый usage, одна запись под перемещение после последнего события и одна под `FOCUS LOST`.

### 7.3. Правила постановки

| Событие | Правило | Отказ возможен |
|---|---|---|
| `MOTION`, `tail` — `MOTION` | объединить с `tail`: `dx`, `dy`, `wheel`, `pan` складываются с насыщением i32; `abs_*`, `flags`, `mode_change_count` берутся из нового. Промежуточные позиции старых перемещений сбрасываются, суммарное перемещение сохраняется | нет |
| `MOTION`, иначе | добавить запись (по инварианту `free ≥ 1`) | нет |
| `USAGE DOWN` | принять, только если `free ≥ 2h + 5` (после приёма инвариант выполняется для `h + 1`). Иначе отказ: usage — в `suppressed`, счётчик отказов +1, событие **не объединяется и не откладывается** | **да** |
| `USAGE UP` usage из `suppressed` | убрать из `suppressed`, в очередь не ставить | — |
| `USAGE UP` нажатого usage | добавить (по инварианту `free ≥ 2h`) | нет |
| `FOCUS LOST` | добавить (по инварианту `free ≥ 1`); `h = 0`, `suppressed` очищается; состояние `UNFOCUSED` | нет |
| `FOCUS GAINED` | добавить, если `free ≥ 3`; состояние `FOCUSED`. Иначе — состояние `GAINED_PENDING` (7.4) | откладывается |

- `USAGE` никогда не объединяются и не переставляются; клавиатурные события не теряются молча. Отказ получает только нажатие, и о нём сообщается: UI ведёт свой счётчик и журнал и МОЖЕТ показать его в окне; VMHost сообщает `rejected_downs` в `STATUS`.
- Отпускание и перемещение в фокусе не получают отказа никогда: инвариант оставляет для них место. Нажатие с отказом не создаёт залипания: его `UP` тоже не ставится.
- `h ≤ 126`: нажатие принимается, только если `2h + 5 ≤ 256`, то есть при `h ≤ 125` до приёма.
- Удаление записи из головы (отправка, потребление) только увеличивает `free` и инвариант не нарушает. Пустая очередь (`m = 1`) даёт `free = 256 ≥ 2 × 126 + 2`.

### 7.4. `GAINED_PENDING`

Если для `FOCUS GAINED` нет трёх свободных записей, сторона переходит в `GAINED_PENDING`. В этом состоянии:

- `MOTION` и `USAGE DOWN` отбрасываются и учитываются (`dropped_unfocused`), отброшенный `DOWN` добавляется в `suppressed`;
- `UP` из `suppressed` убирается из множества;
- `FOCUS LOST` только отменяет ожидание: в очередь ничего не ставится, `suppressed` очищается, состояние — `UNFOCUSED`.

После каждого удаления из головы сторона проверяет `free ≥ 3`. Если условие выполнено, она ставит отложенный `GAINED` и переходит в `FOCUSED`, после чего инвариант 7.2 снова выполняется.

На стороне UI это состояние почти недостижимо: VMHost читает сокет непрерывно. На стороне VMHost без потребителя это обычный случай.

### 7.5. Выход в сокет

- UI пишет в сокет из головы своей очереди неблокирующей записью. Ожидание готовности на запись не задерживает главный поток AppKit.
- VMHost читает сокет всегда, когда в нём есть данные, и сразу применяет 7.3 к своей очереди. Поэтому сокет не копит события, пока VMHost жив, даже если у его очереди нет потребителя.
- Выход VMHost: одно частично отправленное сообщение и один ожидающий `STATUS`, новый `STATUS` заменяет неотправленный. VMHost отправляет `STATUS`, когда счётчики изменились, не чаще раза в 100 мс; последнее изменение уходит не позже чем через 100 мс.
- Чтение сокета и разбор сообщения не блокируют продвижение гостя. Объём работы на одно сообщение ограничен.

## 8. Состояния

### 8.1. UI

| Состояние | Вход | События окна |
|---|---|---|
| `OFF` (не подключён) | VMHost запущен без канала ввода | не собираются |
| `HANDSHAKE` | `HELLO` отправлен, ждём `ACCEPT` | отбрасываются и учитываются |
| `READY / UNFOCUSED` | `ACCEPT` принят; или `FOCUS LOST` | не собираются |
| `READY / FOCUSED` | `FOCUS GAINED` поставлен в очередь | по 7.3 |
| `READY / GAINED_PENDING` | 7.4 | отбрасываются и учитываются |
| `CLOSED` (разрыв) | EOF, ошибка сокета, ошибка протокола, `VERSION` с `version = 1` | не собираются |
| `INCOMPATIBLE` | заголовок `ODIT` с `version ≠ 1` | не собираются |

- `CLOSED` и `INCOMPATIBLE` конечны для канала. UI освобождает очередь, очищает нажатые usage и закрывает свой конец. Показ кадров при этом продолжается. UI показывает «ввод отключён» и причину, отдельно от состояния кадров.
- Переподключения в v1 нет. Новый канал — только с новым VMHost.
- UI МОЖЕТ ограничить ожидание `ACCEPT` сроком; его значение выбирает S10-16.

### 8.2. VMHost

1. `WAIT_HELLO`. Первые 16 байт должны быть заголовком `HELLO`:
   - неверный magic — закрыть канал без ответа;
   - magic `ODIT` и `version ≠ 1` — `VERSION`, затем закрыть;
   - неверный вид, длина или reserved — закрыть без ответа.
2. Отправить `ACCEPT` (`GUEST_DELIVERY = 0`, пока нет устройства), затем перейти в `UNFOCUSED`.
3. `UNFOCUSED` / `FOCUSED` / `GAINED_PENDING` — по 6.4 и 7.3–7.4. Проверки, нарушение которых — ошибка протокола:
   - `USAGE` или `MOTION` в `UNFOCUSED`;
   - повтор `FOCUS` с тем же `state`;
   - `DOWN` для usage, который нажат или лежит в `suppressed`;
   - `UP` для usage, который не нажат и не лежит в `suppressed`;
   - недопустимый usage (6.1);
   - пустой `MOTION`;
   - `abs_x ≥ abs_width` или `abs_y ≥ abs_height`;
   - `abs_*` вне пределов 4.2;
   - ненулевые reserved или неопределённые биты.
4. **Абсолютная позиция, устаревшая из-за смены режима.** Если `ABS_VALID = 1`, а `mode_change_count` не равен текущему `mode_change_count` дисплея VMHost (`od_display_session_mode`), VMHost сбрасывает `ABS_VALID` в записи. Ошибкой это не является: событие могло встать в очередь до смены режима. Если счётчик равен текущему, но `abs_width`/`abs_height` не равны размеру текущего режима, — ошибка протокола. Если дисплея у VMHost нет, `ABS_VALID` сбрасывается всегда. Относительная часть записи сохраняется в любом случае. Если после сброса у записи нет ненулевых дельт, она пуста: при приёме VMHost не ставит её в очередь, а на выходе очереди не передаёт потребителю (например, `MOTION` позиции клика). В `GAINED_PENDING` любой `MOTION`, и такой пустой тоже, отбрасывается и учитывается в `dropped_unfocused` (7.4). В `FOCUSED` отброшенный пустой `MOTION` не считается в `merged_motions`: он не объединён с записью очереди (4.2, `STATUS`).

   Эта проверка выполняется дважды. **При приёме** — до постановки в очередь, тогда же проверяются размеры. **На выходе очереди VMHost** — перед передачей записи потребителю (раздел 10), потому что режим мог смениться, пока запись стояла в очереди. На выходе VMHost сравнивает `mode_change_count` с текущим. Если значение устарело, VMHost сбрасывает `ABS_VALID` и абсолютные поля. Запись, у которой после этого не осталось ненулевых дельт, отбрасывается целиком и потребителю не передаётся: например, `MOTION` позиции клика (5.2). Объединение (7.3) берёт абсолютную часть из нового `MOTION`, поэтому запись с устаревшей позицией свежую позицию не затирает.

### 8.3. Разрыв

- EOF, ошибка сокета или ошибка протокола на канале ввода закрывают **только** канал ввода. VMHost ставит в свою очередь `FOCUS LOST`, если он был в `FOCUSED`, и перестаёт читать канал. По инварианту место для этой записи есть.
- Машина и frame transport продолжают работу. Завершать VMHost — решение UI, как в frame transport §6.5.
- Сообщения об ошибке в v1 нет. Причину UI узнаёт по EOF.

## 9. Совместимость и отказы

### 9.1. Версия

- Одна сторона, одна версия: согласования, понижения и fallback нет.
- VMHost, получивший `HELLO` с magic `ODIT` и `version ≠ 1`, отвечает одним 16-байтным `VERSION` со своей версией и закрывает канал.
- UI, получивший заголовок `ODIT` с `version ≠ 1`, переходит в `INCOMPATIBLE` и показывает версию.
- `VERSION` с `version = 1` — ошибка протокола.
- Изменение любого поля, размера, вида, значения `state`, `flags`, допустимых usage, ёмкости очереди или правил 7.3 — новая версия протокола. Числа и поля v1 не переиспользуются с другим смыслом. Несколько экранов (S10-15) и абсолютный pointer device требуют новой версии.

### 9.2. Неизвестные значения

| Условие | Результат |
|---|---|
| Неизвестный `kind`; вид не своего направления; второй `HELLO` или `ACCEPT`; `FOCUS`/`USAGE`/`MOTION` до `ACCEPT` | ошибка протокола |
| Другой magic; длина payload не равна фиксированной; ненулевой reserved; неопределённые биты `flags`; неизвестное значение `state` | ошибка протокола |
| Нарушения 6.1, 6.4, 8.2 п. 3; дескриптор или `cmsghdr` в любом сообщении | ошибка протокола |
| Заголовок `ODIT` с `version ≠ 1` | `INCOMPATIBLE` (UI) / `VERSION` и закрытие (VMHost) |

Ошибка протокола закрывает канал ввода без ответного сообщения (8.3). Повтора нет.

### 9.3. Доверие

- VMHost исполняет гостевой код, поэтому UI считает его сообщения недоверенными. Из сообщений VMHost UI только показывает `flags` `ACCEPT` и счётчики `STATUS` и ничего по ним не вычисляет.
- UI — владелец процесса VMHost, как в frame transport §8.3. Тем не менее VMHost проверяет каждое сообщение по разделу 9.2, а разбор не принимает длин, дескрипторов и путей сверх фиксированных.

## 10. Граница `od-host` и будущий input ABI

- В [`display_abi_v1.h`](../../include/open_desktop/display_abi_v1.h) ([DISPLAY_HOST_ABI_V1.md](../../docs/specs/DISPLAY_HOST_ABI_V1.md)) функций ввода нет. Этот документ ABI не добавляет и `display_abi_v1.h` не меняет. По правилу расширения DISPLAY_HOST_ABI_V1.md §1 ввод не входит в дисплейный ABI v1.
- В S10-16 «граница `od-host`» — это выход очереди VMHost (раздел 7). Реализация S10-16 МОЖЕТ дать test-only потребителя этого выхода (например, флаг трассировки VMHost, печатающий записи). Через него тест проверяет, что запись дошла до границы с нужными usage и координатами. Имя флага выбирает реализация. Без этого потребителя у очереди потребителя нет.
- Требования к будущему input ABI (отдельный opt-in ABI, по образцу display ABI; появляется вместе с xHCI/HID устройством платы):
  1. Неблокирующая передача одной записи: `USAGE` (страница, usage, состояние), `MOTION` (`dx`, `dy`, `wheel`, `pan`; абсолютная часть — только если плата получит absolute pointer), `FOCUS LOST` как «отпустить всё». Результат — «принято» или «очередь устройства полна». При «полна» запись остаётся в голове очереди VMHost. Перед каждой передачей, в том числе повторной, VMHost сверяет `mode_change_count` записи с текущим режимом (8.2, п. 4). Устаревшую абсолютную часть он сбрасывает, а запись без дельт отбрасывает.
  2. Значения — в единицах HUT 1.7 этого документа, без PS/2 и без кодов macOS.
  3. Запрос «устройство присутствует». По нему VMHost выставляет `GUEST_DELIVERY` в `ACCEPT`.
  4. Разбиение больших `dx`/`dy`/`wheel` на HID-отчёты с пределами полей отчёта, отчёт «ничего не нажато» по `FOCUS LOST` и boot protocol для UEFI — обязанности устройства, а не VMHost и не этого протокола.

## 11. Блокер доставки, открытые решения и допущения

**Блокер.** До устройства ввода платы — строка «Ввод» [VIRTUAL_BOARD.md](../../docs/specs/VIRTUAL_BOARD.md): PCI xHCI (`0C0330`, xHCI 1.2) с USB HID keyboard и mouse — события до гостя не доходят. Очередь VMHost при этом ограничена (7.1) и без потребителя не растёт. `GUEST_DELIVERY = 0`. Снятие блокера требует устройства в `od-machine`, input ABI `od-host` (раздел 10) и смены флага; протокол v1 для этого не меняется.

Открытые решения:

1. **Абсолютный pointer device** (HID tablet/digitizer) в плату v0.1 не входит. Добавлять его или нет — решение по плате. Без него курсор гостя и курсор хоста расходятся: у гостя своё ускорение и своя начальная точка. Поле `abs_*` протокола готово к такому устройству, но новое устройство потребует новой версии протокола ввода (9.1), если изменится смысл полей.
2. **Захват указателя** (скрыть курсор хоста, отвязать его от мыши, «host key» для выхода) — поведение UI, в протокол не входит. До решения по п. 1 без захвата пользоваться относительной мышью неудобно.
3. **Командные сочетания:** передавать ли Cmd-Q, Cmd-W и подобные в гостя или оставлять их приложению, и как выйти из захвата клавиатуры.
4. **`WHEEL_UNITS_PER_POINT`** для точной прокрутки (5.5) — по замеру S10-16.
5. **Индикаторы клавиатуры** (Caps Lock, Num Lock) от гостя в UI — обратного сообщения в v1 нет.
6. **Метки времени событий** для замеров задержки (S10-10) в v1 нет.
7. **Ёмкость 256** — гипотеза до замеров (7.1).
8. **Критерий плана «угол ±1 на любом размере окна».** Принято решение: абсолютная позиция соответствует нарисованному текселю (5.3).
   - Цена: при `k ≥ 2` тексель 0 не нарисован. При `k ≥ 4` абсолютная позиция никогда не даёт `(0, 0)` и `(W − 1, H − 1)`. Пример: 4096×2304 в окне 640×360 @1, `k = 6.4`, клик в левый верхний угол → `(3, 3)`.
   - Критерий плана выполняется при `k < 4`. При `k ≥ 4` тест сравнивает с нарисованным текселем.
   - Альтернатива — растянуть концы viewport на `0` и `W − 1`. Она отложена до решения по absolute pointer device (п. 1): до него абсолютная позиция в гостя не доставляется.

Допущения, которые S10-16 проверяет тестом или наблюдением; источник Apple, подтверждающий их, не найден:

- единицы `NSEvent.deltaX/deltaY` — логические точки, а ось Y направлена вниз;
- доставка `keyUp` при нажатой Command — локальный монитор или `sendEvent`;
- device-dependent биты модификаторов в `modifierFlags`;
- Caps Lock приходит одним `flagsChanged` на переключение.

## 12. Проверки реализации S10-16

1. **Координаты** — unit-тест поверх `ViewportLayout`, без AppKit:
   - для набора окон S10-11 (логический размер, scale, `fit`/`pixelExact`, обрезка) и кадров 64×48, 1920×1080, 4096×2304 левый верхний и правый нижний физические пиксели viewport дают углы по формуле 5.3: `(0, 0)` и `(W − 1, H − 1)` ±1 при `k < 4`;
   - каждый физический пиксель кадра 64×48 при `k ≤ 1` даёт тот же пиксель, что nearest-выборка эталона.
2. **Перевод точки AppKit**: начало внизу слева, Retina @2, нецелый `drawableSize` — край bounds попадает на край drawable.
3. **Очередь**:
   - без потребителя 10⁶ случайных событий (перемещения, нажатия, отпускания, фокус) не увеличивают память сверх 7.1;
   - инвариант 7.2 выполняется после каждого шага;
   - отпускание и перемещение в фокусе ни разу не получают отказа;
   - счётчики `STATUS` сходятся с моделью.

   Модель правил 7.3–7.4 прогнана при написании спецификации на Python (300 прогонов по 20 000 событий, в том числе без потребителя): нарушений инварианта не было. Это проверка правил, а не реализации.
4. **Таблица usage**: каждый `kVK_*` SDK имеет строку или записан как непередаваемый; все значения таблицы лежат в 6.1.
5. **Фокус**: нажатие, потеря фокуса, отпускание в другом окне. В очереди VMHost есть `FOCUS LOST`, а лишнего `UP` нет.
6. **Протокол**: неизвестный `kind`, чужая версия, неверная длина, `USAGE` до `ACCEPT`, повтор `DOWN` и дескриптор в сообщении закрывают только канал ввода; кадры продолжают показываться.
7. **Граница**: записи доходят до test-only потребителя VMHost (раздел 10) с теми же usage и координатами. `ACCEPT` несёт `GUEST_DELIVERY = 0`.

## 13. Вне v1

- Абсолютный pointer device, touch, перо, жесты трекпада, кроме прокрутки.
- PS/2 и скан-коды любого набора; передача символов или текста вместо usage (IME работает в госте).
- Consumer-клавиши (громкость, яркость) и страница `0x0C`, кроме `AC Pan` в `MOTION`.
- Несколько экранов (S10-15), обратный канал индикаторов, метки времени.
- Передача ввода через control v1 или frame transport v1.
