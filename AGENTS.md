# Правила проекта Open Desktop

Эти правила обязательны для разработки и архитектурных решений во всём проекте.

## Принципы проектирования

- **SOLID:** разделять ответственность модулей, задавать явные контракты и направлять зависимости через необходимые интерфейсы. Применять принципы к реальным границам системы.
- **KISS:** выбирать наиболее простое решение, удовлетворяющее текущим требованиям. Не создавать спекулятивные абстракции, дополнительные слои и инфраструктуру без конкретной необходимости.
- **DRY:** не дублировать знания, правила и логику. Объединять действительно общую семантику; внешнее сходство кода само по себе не является основанием для абстракции.

## Модели, роли и ревью

- Для Codex написание и изменение кода выполнять с `gpt-6-luna`, уровень рассуждения `high`.
- Для Codex независимое ревью кода выполнять с `gpt-6.1-sol`, уровень рассуждения `high`.
- Для Codex архитектурный анализ и решения выполнять с `gpt-6.1-sol`, уровень рассуждения `high`. Архитектурно значимые решения сверять с `docs/ARCHITECTURE.md`.
- Если среда поддерживает несколько агентов, распределять между ними независимые подзадачи или роли реализации и ревью. Не делегировать связанную последовательную работу, если это создаёт конфликты или мешает сохранить контекст изменений пользователя. Если мультиагентность недоступна, выполнить те же роли последовательно.
- После каждой завершённой подзадачи или этапа передавать изменённый код на отдельное ревью, предпочтительно агенту с ролью ревью и указанной выше моделью. Ревьюер проверяет diff и затронутые контракты, сообщает конкретные дефекты и риски; автор исправляет подтверждённые проблемы и повторно запрашивает ревью затронутой части.
- Не считать этап завершённым, пока ревью не выполнено либо явно не записано, почему оно было недоступно. В итоговом отчёте указывать результат ревью и оставшиеся замечания.

### Правила для Claude

- Для написания и изменения кода использовать Claude Sonnet с уровнем усилия `high`.
- Для независимого ревью кода использовать Claude Opus с уровнем усилия `high`.
- Для архитектурного анализа и решений использовать Claude Opus с уровнем усилия `high`.
- Если используемая среда Claude поддерживает несколько агентов, применять их для независимых подзадач и отдельного ревью; иначе выполнять роли последовательно.
- После каждой завершённой подзадачи или этапа перед коммитом отдавать изменённый код на независимое ревью. Исправить подтверждённые замечания и повторно проверить затронутую часть.
- После успешного ревью создать коммит по результатам подзадачи/этапа, затем обновить Graphify. В итоговом отчёте указать результат ревью, коммит и статус Graphify.

## Решения в критичных по производительности участках

Все решения по критичным по производительности участкам принимать на основании замеров скорости. Предположения, интуиция и теоретическая сложность могут определять гипотезу, но не заменяют измерения.

- Определять критичные участки по профилированию и измерениям целевых сценариев. Для новых участков без готовой реализации сравнивать минимальные прототипы вариантов до окончательного выбора.
- Сравнивать исходный вариант и предлагаемые изменения на одинаковой репрезентативной нагрузке, в сопоставимых условиях и с одинаковыми требованиями к корректности.
- Запускать все бенчмарки через `nice` и проверять, что итоговое значение nice у процесса равно `-5`. Если для установки приоритета нужен `sudo`, сам бенчмарк выполнять от обычного пользователя.
- Измерять подходящие сценарию показатели: время выполнения, задержки или пропускную способность. Для JIT отдельно учитывать холодное исполнение и прогретый кеш, когда это влияет на решение.
- Использовать повторные прогоны и учитывать разброс результатов. Не считать шум измерений подтверждённым ускорением.
- Вместе с решением фиксировать сценарий, аппаратную и программную конфигурацию, параметры сборки, способ воспроизведения, результаты сравнения и вывод. Отмечать связанные изменения потребления памяти и других ресурсов, если они существенны.
- При отсутствии достаточных замеров считать решение предварительной гипотезой. Не заявлять об ускорении и не принимать окончательное решение по производительности без данных.
- Сохранять корректность и надёжность обязательными условиями: ускорение за счёт нарушения семантики гостевой машины недопустимо.

Из нескольких вариантов, удовлетворяющих измеренным требованиям, предпочитать более простой и понятный. Усложнение критичного участка должно иметь подтверждённую измерениями пользу.

## Перед началом работы

1. Прочитать этот файл, `docs/PROJECT_LAYOUT.md` и план выполняемого этапа в `docs/plans/`.
2. До изменения файла прочитать все `AGENTS.md` от корня до его каталога. Вложенные инструкции дополняют корневые; правила соседних каталогов не заменяют правила целевого каталога.
3. Для архитектурных изменений свериться с `docs/ARCHITECTURE.md`; для объёма работ — с `docs/ROADMAP.md`. Сейчас реализация ограничивается задачей, порученной пользователем; наличие каталога не означает разрешения реализовать всю подсистему.
4. Проверить существующее содержимое и изменения пользователя. Не перезаписывать их и не перемещать файлы только ради личного предпочтения.
5. Найти правильный каталог в карте проекта. Не создавать альтернативные `src/`, `lib/`, `common/`, `shared/`, `utils/` и `misc/` в корне. Новый верхнеуровневый компонент требует обновления карты и обоснования границы ответственности.

## Размещение и границы компонентов

- `apps/` — только macOS UI и оболочка VMHost; CPU/JIT/MMU размещать в `crates/`.
- `crates/` — собственные Rust-библиотеки. Не размещать здесь Swift UI, firmware или Windows drivers.
- `include/` — общий публичный C ABI host-продукта. Внутренние заголовки устройства/драйвера остаются рядом с его реализацией.
- `protocols/` — нормативные форматы межпроцессных и гостевых сообщений. Общие обзоры в `docs/specs/` ссылаются на них, а не дублируют wire format.
- `firmware/` — собственный freestanding код, не часть обычной host-сборки.
- `guest/` — компоненты, исполняемые внутри Windows/Linux; не host backends.
- `tools/` — исполняемые инструменты разработчика; повторно используемая семантика CPU принадлежит библиотеке, не копируется в runner.
- `tests/` — межкомпонентные сценарии и небольшие собственные fixtures. Локальные unit tests находятся рядом с реализацией.
- `docs/` — проектные документы, планы, спецификации, решения и долговечные результаты измерений.
- `work/` — промежуточные данные, логи, локальные образы VM и эксперименты. `outputs/` — подготовленные deliverables. Они не заменяют исходники и спецификации.

Подробная карта, разрешённые зависимости и назначение каждого компонента: `docs/PROJECT_LAYOUT.md`. Не менять структуру и рабочий каталог процесса во время запуска инструмента, чтобы скрыть неправильный путь.

## Самостоятельная реализация

- Библиотеки общего назначения разрешены: логирование, CLI, конфигурация, сериализация, коллекции, очереди, синхронизация, асинхронная инфраструктура, bindings системных API и инструменты тестирования/измерений. Добавлять их при реальной необходимости согласно [политике зависимостей](docs/policies/DEPENDENCIES.md), без отдельного согласования каждого разрешённого пакета с пользователем.
- Ключевая технология остаётся собственной: семантика/декодер x86, интерпретатор, IR, ARM64 emitter/JIT, MMU, модели оборудования, firmware, TPM-протокол, собственные драйверы и графическая трансляция. Готовые реализации этих компонентов, в том числе транзитивно, запрещены. Не копировать их исходники, таблицы или реализации под видом собственного кода.
- Стандартные библиотеки, компиляторы, SDK и системные API допустимы. Компилятор Rust может использовать LLVM; подключать LLVM как движок нашего runtime-JIT нельзя.
- Общая библиотека предоставляет инфраструктуру, а не определяет архитектурную семантику нашего движка. Например, сериализатор допустим; wire format, его ограничения и поведение протокола определяем мы. Криптографические примитивы можно брать из системных API или библиотек общего назначения; TPM/UEFI-протоколы и их состояние реализуем сами.
- При добавлении зависимости фиксировать назначение, версию, источник, лицензию и необходимые features; учитывать транзитивные зависимости. Не добавлять пакеты «на будущее». Выбор на критичном участке подтверждать замерами согласно правилам выше.
- Описания публичных стандартов использовать можно; фиксировать источник и версию. Форматы, таблицы, фикстуры и генераторы собственной реализации должны иметь понятное происхождение.

## Документирование результатов и открытых проблем

- По завершении каждой задачи фиксировать реализованные части в соответствующих документах `docs/`: что работает, в каких границах, какими проверками подтверждено. Обновлять существующие описания и статус плана этапа по фактическому результату; не считать финальный ответ в чате заменой документации.
- Найденные в процессе работы недоделки и проблемы, которые не устранены к завершению задачи, обязательно записывать в отдельный реестр [docs/KNOWN_ISSUES.md](docs/KNOWN_ISSUES.md). Для каждой записи указывать затронутый компонент, суть и последствия, условия воспроизведения или основание обнаружения, статус и необходимый следующий шаг. Не выдавать предположения за подтверждённые дефекты.
- При устранении зарегистрированной проблемы обновлять её запись, указывать результат проверки и ссылку на документацию реализации. Не оставлять решённую проблему в статусе открытой.

## Реализация и проверка

- Названия, интерфейсы и исходники — на английском; проектная документация и инструкции могут быть на русском. Следовать стилю существующего файла.
- Не выдавать каркас, пустой модуль, debug-run или неподдерживаемый fallback за реализованную возможность. Не добавлять фиктивные тесты и программы, которые сообщают об успешной работе отсутствующей функции.
- Сначала один проверяемый вертикальный срез; не добавлять speculative frameworks, сервисы, генераторы и плагины.
- Host panic, нарушение ABI или повреждение памяти не являются гостевым исключением. Не скрывать их через общее перехватывание ошибок.
- Не хранить в Git гостевые ОС, большие образы дисков, секреты, сертификаты подписи, пользовательские данные и build outputs.
- Не исправлять конфликт зависимостей переносом macOS UI в ядро или копированием CPU-семантики в tools/testkit.
- Проверять соразмерно изменению. Для Rust-кода — форматирование и сборка затронутых компонентов, затем необходимые проверки поведения. Для документации/структуры — ссылки и карта каталогов; запуск CPU-тестов без изменения CPU не нужен.
- При изменении структуры запустить `python3 tools/check_layout.py`. Для Rust workspace доступны `cargo fmt --all -- --check` и `cargo check --workspace --all-targets --offline`. Успешная сборка пустого каркаса не доказывает готовность движка.
- В отчёте различать выполненные проверки, непроверенные условия и ограничения. Правила проекта изменять при реальном изменении требований, а не для обхода проверки.

## Code Search Tool Responsibilities

### Graphify — Primary
- Use Graphify for codebase discovery, symbol lookup, dependencies, callers/callees, and impact analysis.
- Reuse Graphify results instead of repeating repository searches.
- Do not reconstruct relationships already available in Graphify.

### ast-grep — Structural Search Only
- Use ast-grep only when syntax-aware matching or structural rewriting is required.
- Restrict searches to files or directories identified by Graphify.
- Prefer `ast-grep run -p 'PATTERN' -l LANG PATH` for targeted matching.
- Use `ast-grep outline --view signatures PATH` only when a compact local file overview is needed.
- Use ast-grep to verify recently modified code when Graphify's index may be stale.
- Never use ast-grep for general codebase discovery or dependency analysis.

### Efficiency Rules
- Do not run Graphify and ast-grep for the same question unless verification is necessary.
- Prefer `rg` for simple text searches.
- Avoid repository-wide scans and large tool outputs.
- Skip tool calls when existing context already answers the question.
- Read full source files only when targeted context is insufficient.
- Use Context7 exclusively for external library documentation.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

When the user types `/graphify`, use the installed graphify skill or instructions before doing anything else.

Rules:
- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- Dirty graphify-out/ files are expected after hooks or incremental updates; dirty graph files are not a reason to skip graphify. Only skip graphify if the task is about stale or incorrect graph output, or the user explicitly says not to use it.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
- A committed graphify-out/graph.json is rewritten whole on every build, so a large diff to it in a pull request is expected. Do not flag it as churn or suggest skipping the graph rebuild or its hooks.
